# Starcat 调试工具使用指南

> **本文档**：集中说明 Starcat 项目里**仅开发期可见**的调试工具/开关——它们如何打开、如何关闭、底层走的是什么机制、Release 包是否能被外人意外开启。
>
> 创建：2026-06-02
> 维护原则：每加一个新的 debug-only 开关，必须在本文档「2. 开关清单」追加一行；每删一个，划掉那一行（不删，保留历史）。

---

## 0. 核心约定

所有调试工具遵循同一套约定，新加开关必须满足：

1. **Release 包硬关**：用 `#if DEBUG` 包住读取逻辑，编译期切走，外人传 launch args 也无法开启。
2. **DEBUG 包默认关**：UserDefaults 默认 `false`，不主动开就跟没有一样，不污染日常开发体验。
3. **集中登记**：所有开关都加在 `Starcat/Shared/Utilities/DebugFlags.swift`，**禁止**在散落的 View / ViewModel 里直接读 UserDefaults。
4. **本文档同步**：「2. 开关清单」每个开关一行，列出 key 名 + 用途 + 落地代码位置。

## 1. 底层机制：为什么 UserDefaults 就是"配置文件"

| 机制 | 读取时机 | 持久化位置 | 切换方式 | 用于 Starcat? |
|---|---|---|---|---|
| **`UserDefaults`** ⭐ | 运行时 | `~/Library/Containers/com.starcat.app/Data/Library/Preferences/com.starcat.app.plist`（自动） | Scheme launch args / LLDB / `defaults` 命令 / UI 开关 | **本项目调试开关统一走这个** |
| `#if DEBUG` 编译宏 | 编译期 | N/A（代码层切走） | 改代码重新编译 | 与 UserDefaults 配合做 Release 硬关 |
| Info.plist | 启动时 | 在 App bundle 内（只读） | 改 plist 重新打包 | 仅用于声明 bundle id / 权限/ 协议处理 |
| 自定义 JSON / plist | 自己解码 | 任意路径 | 编辑文件 | **不用**（对调试开关过度设计） |
| 环境变量 / `CommandLine.arguments` | 启动时 | 不自动持久化 | Xcode Scheme 改 env | 不用（不如走 UserDefaults） |

### 1.1 关键设计：Apple 的 "command-line preferences"

macOS / iOS 内置一个约定：**Xcode Scheme 启动参数里以 `-Key Value` 形式传入的参数，会被自动注册到 `UserDefaults.standard`**，**不需要写一行解析代码**。

也就是说，下面这三种方式底层走的是同一个 key-value 存储，等价：

```swift
// 同一个开关，三种来源都能读到
UserDefaults.standard.bool(forKey: "DebugLayoutOverlay")
```

| 来源 | 持久化 | 适合场景 |
|---|---|---|
| Xcode Scheme launch args | 跟 Scheme 走（在 `xcuserdata/` 默认 .gitignore） | 个人长期开发常开 |
| LLDB 运行时 `expr UserDefaults...` | 不写盘，重启丢失 | 临时一次性 |
| `defaults write com.starcat.app KEY -bool YES` | 写入 plist 文件 | 不开 Xcode 的命令行验证 |

参考：[Apple Foundation - User Defaults](https://developer.apple.com/documentation/foundation/userdefaults)、搜索词 "command-line preferences NSUserDefaults"。

### 1.2 为什么不直接读 JSON / plist 文件

也能做，但对调试开关是**过度设计**：

- 需要自己定义 `Codable` struct + `JSONDecoder` + 路径处理 + 文件缺失兜底
- 修改后没有 SwiftUI 自动响应能力（UserDefaults 配合 `@AppStorage` 才有）
- 跨 dev / runtime / 生产环境的"哪个文件优先"需要自己定规则
- macOS 已经有 UserDefaults，走标准机制让 Apple 工具链帮我们处理（Xcode Scheme / `defaults` 命令都现成）

**结论**：调试开关 = UserDefaults；只有产品级"用户偏好"/"复杂结构化配置"才考虑外置文件，目前 Starcat 没有这种需求。

## 3. 怎么用：以 `DebugLayoutOverlay` 为例

下面三种方式**等价**，按场景挑：

### 3.1 方式 A · Xcode Scheme launch args（**推荐**）

适合：**个人开发期长期常开**，重启 App 立即生效，不进 git。

操作：

1. Xcode 菜单 `Product` → `Scheme` → `Edit Scheme...`（或快捷键 `⌘<`）
2. 左侧选 `Run` → 顶部 tab 选 `Arguments`
3. **Arguments Passed On Launch** 区域点 `+`，新增一行：

   ```
   -DebugLayoutOverlay YES
   ```

4. 关闭弹窗，重新 Run（`⌘R`）。右上角立刻浮起 `1800 × 872` 这样的胶囊。
5. 不想用了：那行 checkbox 关掉或直接 `-` 删除，重启即可。

**关键性质**：Scheme 设置写在 `Starcat.xcodeproj/xcuserdata/<user>.xcuserdatad/...`，xcodegen 模板的 `.gitignore` 默认排除 `xcuserdata/`，所以**每个开发者的 Scheme 配置是本地私有的，不会跟着 git 提交污染团队**。

### 3.2 方式 B · LLDB 运行时切换（临时）

适合：**调试时偶尔开一下看看**，不想重启 App。

在 Xcode 调试控制台输入：

```
expr UserDefaults.standard.set(true, forKey: "DebugLayoutOverlay")
```

然后让 SwiftUI 重读：拖一下窗口尺寸、切一下 sidebar 选择，或者 `continue` 后做点 UI 操作。开关不写盘，App 重启后丢失，再开需要再 `expr`。

关掉：

```
expr UserDefaults.standard.removeObject(forKey: "DebugLayoutOverlay")
```

### 3.3 方式 C · 命令行 `defaults` 命令（持久化）

适合：**不开 Xcode、用 Release-DEBUG 包独立运行时验证**。

```bash
# 开
defaults write com.starcat.app DebugLayoutOverlay -bool YES

# 看当前值
defaults read com.starcat.app DebugLayoutOverlay

# 关
defaults delete com.starcat.app DebugLayoutOverlay
```

这种方式直接写入 `~/Library/Containers/com.starcat.app/Data/Library/Preferences/com.starcat.app.plist`——直接拿文本编辑器打开它改也一样，本质就是写 plist 文件。

## 4. Release 安全：为什么外人开不了

`DebugFlags` 用了双保险：

```swift
static var layoutOverlay: Bool {
    #if DEBUG
    return UserDefaults.standard.bool(forKey: "DebugLayoutOverlay")
    #else
    return false
    #endif
}
```

- **DEBUG 包**：走 UserDefaults，可被上述任意一种方式打开
- **Release 包**：`#if` 在**编译期**就把读取逻辑替换成 `return false`，UserDefaults 那行代码**根本不存在**于二进制——即使有人传了 `-DebugLayoutOverlay YES`、改了 plist、用 LLDB 切了开关，也读不到。

这意味着可以安心新增调试开关，不用担心用户分发版有任何泄露。

## 5. 新增调试开关的 SOP

当后续要加新调试能力时（例如：fake 网络延迟 / 打印请求耗时 / 隐藏某段未完成 UI），请按下面流程：

1. **在 `DebugFlags.swift` 加 static 计算属性**，遵循双保险模板：

   ```swift
   /// <做什么 + 何时开>
   static var <featureName>: Bool {
       #if DEBUG
       return UserDefaults.standard.bool(forKey: "<DebugCamelCaseKey>")
       #else
       return false
       #endif
   }
   ```

2. **使用方在 View / ViewModel 顶层判断**，关闭时尽可能"零 overhead"：

   ```swift
   .overlay {
       if DebugFlags.<featureName> {
           <昂贵的调试视图>  // 条件渲染，关闭时不实例化
       }
   }
   ```

   或：

   ```swift
   if DebugFlags.fakeNetworkLatency {
       try await Task.sleep(for: .seconds(2))  // 仅 DEBUG 包 + 主动开启时生效
   }
   ```

3. **在本文档「2. 开关清单」追加一行**，登记 key 名 + 用途 + 代码位置 + 日期。

4. **可选：在 README / 开发者文档**指出某个特定调试视图（如 LayoutDebugOverlay）也可以接 Settings UI 一键开关（参考"已知未做项 §6.1"）。

5. **禁止**：在散落的代码里直接写 `UserDefaults.standard.bool(forKey: "DebugXxx")`——必须经过 `DebugFlags`。这样集中管理，方便审计"项目里有哪些 debug-only 行为"。

## 6. 已知未做项 / 后续可扩展

### 6.1 Settings UI 暴露开关

目前所有调试开关只能通过 Scheme / LLDB / `defaults` 切，没有 GUI 入口。如果未来希望非 dev 用户也能开（例如内测玩家需要看 overlay），可以在 `SettingsView` 加一个隐藏的 "Developer" tab：

```swift
#if DEBUG
DeveloperSettingsView()  // 提供 Toggle binding 到 UserDefaults
#endif
```

但目前不做——dong4j 的需求是个人验证三栏宽度，三种命令行方式已足够。

### 6.2 测量整个 NSWindow frame 而非 contentView

当前 `LayoutDebugOverlay` 已改为通过 `NSViewRepresentable` 读取 `NSWindow.contentView.bounds.size`，显示的是 AppKit contentView 的真实内容区尺寸。这样做是为了避免 `NavigationSplitView` 折叠 sidebar 后，纯 `GeometryReader` 误读成 toolbar / 局部容器尺寸（例如 798×50）。

如需看完整窗口 frame（含 titlebar / toolbar / decoration）：

```swift
import AppKit

if let window = NSApplication.shared.windows.first {
    let size = window.frame.size  // 含 titlebar / decoration
}
```

但 Starcat 当前窗口下限用的是 `contentMinSize`，所以调试 overlay 显示 contentView 尺寸更贴近约束本身。

### 6.3 per-column 尺寸

若要单独显示三栏每栏的宽度，得在每个栏的根 View 里嵌 `GeometryReader` + `PreferenceKey`/`onGeometryChange` 上抛尺寸。当前 overlay 只测窗口 contentView 总宽，主要用途是验证窗口 min/ideal/max 约束生效，前者暂时够用。

## 8. FAQ

**Q：为什么不直接放个 `Config.json` 文件读？**
A：见 §1.2。对调试开关是过度设计；macOS 的"配置文件"标准就是 UserDefaults 后的那个 plist，已经满足需求。

**Q：Release 包真的完全关吗？我截图给用户看会不会泄露 overlay？**
A：完全关。`#if DEBUG` 在编译期决定，Release 二进制里没有读 `DebugLayoutOverlay` 这个 key 的代码。

**Q：team 里其他人不小心把 Scheme 配置提交进 git 怎么办？**
A：xcodegen 模板默认 `.gitignore` 了 `xcuserdata/`，Scheme 配置不会进 git。如果用 "Shared scheme"（在 `xcshareddata/` 里），那就要小心——目前 Starcat 不用 shared scheme。

**Q：可以在测试代码里开吗？**
A：`TestEnvironment.isRunning == true` 时**不要**开调试 overlay，避免影响 UI 测试快照/截图。如果未来确实需要在测试里读某个 flag，加 `&& !TestEnvironment.isRunning` 保护。
