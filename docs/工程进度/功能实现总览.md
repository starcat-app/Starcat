## 0. 使用约定（AI 协作前必读）

### 0.1 开工前

1. **每次实现新功能前**，先打开本文档检查：
   - 该功能是否已经在清单里？
   - 该功能的依赖是否已完成（看前置项是否打勾）？
   - 当前 Week 还有哪些未完成项？是否应该插队？
2. 如发现新功能未列入清单，先在对应章节追加为 `- [ ]` 并标注优先级，再开工。

### 0.2 完成后（强制：不仅勾选，还要写实现说明）

1. 把对应 `- [ ]` 改为 `- [x]`，并在行末追加 **完成日期** + **关联文件**。
2. **必须紧跟一行 `> 实现：...`**，简要描述（参考下方模板）：
   - **技术选择**：一句话写关键决策（"用了什么 / 拒绝了什么 / 为什么"）
   - **涉及文件**：列出主要新增 / 修改的文件（路径）
   - **已知约束 / 后续 TODO**：有就写，没有就省略
3. 顶部「2. 进度仪表盘」的统计数字同步更新。
4. 「10. 变更日志」追加一行。
5. 如发现该功能改变了下游某项的设计前提，去对应项加一行 `> 备注：...`。

#### 实现说明模板

```markdown
- [x] **功能名** — 简短描述 — `主要文件路径` — **YYYY-MM-DD 完成**
  > 实现：用了 X 方案（拒绝了 Y，因为 Z）。新增 `A.swift` / `B.swift`，改造 `C.swift`。约束：xxx。
```

> **关键约束**：仅打勾 `[x]` 不够，必须有 `> 实现：...` 行。这是 dong4j 在 2026-05-30 明确的硬性要求，所有 AI 协作者必须遵守。
>
> **已勾选项的处理**：约定从 2026-05-30 起对所有**新完成**的功能强制；W1-W3.1 早期已勾选项的实现说明留待 dong4j 决定是否需要回填（参考 `2026-05-30-代码评审与进度清单.md` 已有详细记录）。当前唯一已补全实现说明的样板：第 3.3 节"README WebView 渲染"和"README 抓取 + 缓存"。

  > - 根因：`ReadmeWebView.Coordinator.decidePolicyFor` 默认 `decisionHandler(.cancel)`，把 `loadHTMLString(_, baseURL: repo.htmlUrl)` 触发的**主框架首次导航**（url == baseURL，navigationType == .other）也 cancel 了。

  >
  > **经验教训**：macOS App Sandbox 下 WKWebView 会冒出一大堆 `pboard / launchservicesd / networkd / RunningBoard` 之类的连接错误日志，是 WebContent 进程访问受限服务被沙箱拒的**常规噪音**，不致命，不要被它带偏排查方向。**已确认无害的具体字符串清单**（持续追加，看到不要再排查）：
  >   - `Failed to change to usage state 2: (null)` — 每次切 repo / `loadHTMLString` 触发，WebContent 向 RunningBoard 申请 process state assertion 被拒（私有 entitlement `com.apple.runningboard.assertions.webkit` 一方独占，三方 app 加不上也不需要加）。**2026-05-30 18:48 已确认是 WebKit 静默吃下并打 debug log，README 渲染功能完全正常。**
  >   - `Could not create a sandbox extension for ...` — 同类，WebKit 内部 helper 进程申请 sandbox 扩展被拒。

  >   - `WebProcessProxy::didFinishLaunching: Invalid connection identifier` / `Failed to terminate process: ... No such process found` — WebContent 进程生命周期管理日志，App 退出时常见。
  >
  >   开发期想清净：Scheme → Run → Arguments → Environment Variables 加 `OS_ACTIVITY_MODE=disable`，可屏蔽所有系统 os_log 噪音，只保留 `AppLog.*` 业务日志。**不要把这个环境变量提交到 .xcscheme**——只是临时调试用，否则上 CI 时连真正的系统警告也看不见了。
  >
  > **回归 3（图片 broken + 右键 reload 把整页 GitHub 拉进来）—— 18:42 修复**
  > - **现象**：① `hamzamix/StarWise` README 里 `<img src="./logo.PNG">` 显示为 broken；② 在 README 区域右键"重新加载"→ 整个 GitHub 仓库页面被加载到 WebView 里。
  > - **根因 1（图片 404）**：GitHub `/repos/{}/{}/readme?accept=html` 端点对 **Markdown 图片** `![]()` 做 camo 代理重写，但对**原生 HTML `<img>` 标签**的相对 src 不做绝对化（原样吐回 `./logo.PNG`）。baseURL=`https://github.com/owner/repo` 解析 `./logo.PNG` → `https://github.com/owner/logo.PNG` → 404。
  > - **根因 2（reload 拉整页）**：`loadHTMLString(_, baseURL: repo.htmlUrl)` 会把 WebView 的 `URL` 字段设为 baseURL；用户右键"重新加载"→ `webView.reload()` 对 baseURL 发起真实网络请求 → 整个 GitHub 仓库页面被拉进来。"图片这时能加载"是假象（GitHub 自己的页面 + 已登录会话）。
  > - **修复 1（图片）**：`ReadmeWebView` 新增 `owner` / `repo` 参数 + `rewriteAssetURLs(in:owner:repo:)`，HTML 注入前用正则把 `<img src="相对路径">` 重写为 `https://raw.githubusercontent.com/{owner}/{repo}/HEAD/...`。绝对 URL / `data:` / 协议相对 `//` 不动；`HEAD` 自动指向 default branch，无需查询。
  > - **修复 2（reload）**：`Coordinator` 新增 `expectsInitialLoad` 标志；`loadIfNeeded` 在 `loadHTMLString` 前置 true，首次主框架导航消耗后置 false；后续所有主框架导航（含 `.reload` / meta refresh）一律 cancel。`about:` scheme 无条件放行（WebView 初始化噪音）。"真正的刷新" 由底栏"刷新"按钮调 `ReadmeViewModel.reload(repo:)` 走 ETag 缓存路径触发。
  > - **涉及文件**：改 `Shared/Components/ReadmeWebView.swift`（+ rewrite 逻辑 + expectsInitialLoad 拦截）、`Features/Home/RepoDetailView.swift`（透传 owner/repo 给 ReadmeStateView / ReadmeWebView）。47 项单测全绿。
  > - **已知约束**：① 重写策略只针对 `<img>` 标签的双引号 src；少数 README 用单引号或 `<source srcset>` 不覆盖（GitHub render 出来稳定用双引号 `src`，单引号案例极少，暂不引 SwiftSoup 类 HTML 解析依赖）。② `<a href="./xx">` 这种相对链接的解析仍交给 baseURL，点击后由 `.linkActivated` 跳系统浏览器，浏览器再走 GitHub 仓库页面解析（行为正确）。③ 图片重写正则的单元测试待 D-? 一起补（目前是字符串纯函数，新建独立测试 target 性价比待评估）。
