## 0. 使用约定

### 0.1 dong4j 的工作流

1. 想到一个问题（UI 小毛病 / 文案 / 操作不顺 / 性能可疑 / 文档错字 / 设计反悔 ...）→ 立刻在 §2 「问题清单」追加一条，按下面模板填。
2. 一句话说清"现象 + 期望"即可，不必预先设计方案。
3. 优先级用 `🔥 紧急` / `⚡ 高` / `🌊 中` / `🌱 低` 区分（或不填，AI 默认按 中 处理）。

### 0.2 AI 协作者的工作流

1. 每次开工前**先打开本文件**，从 §2 取一项未勾选条目开工（按优先级 + 出现顺序）。
2. 实现完成后：把条目 `- [ ]` 改 `- [x]`，**紧跟一行 `> 实现：...`**（参考 `docs/工程进度/功能实现总览.md` §0.2 模板，简述：技术选择 + 涉及文件 + 已知约束）。
3. 同步更新 §3 「进度仪表盘」。
4. 如发现该问题牵出更多分支问题，**新增子条目**到本文件而非埋头扩大原修复范围（Surgical Changes 原则）。
5. 全部勾完后：把本文件状态改为 ✅ 完成，归档摘要写入 `docs/工程进度/功能实现总览.md` §10 变更日志。

### 0.3 条目模板

```markdown
- [ ] 🔥 **问题标题（一句话）** — 出现位置（文件 / View / 操作路径） — 期望（一句话）
  > 现象：（dong4j 写：复现路径、截图链接、关键日志，可留空让 AI 复现）
  > 期望：（dong4j 写：想要的最终行为）
  > 备注：（可选；关联的设计文档章节、已经想过的方案等）
```

AI 完成后追加：

```markdown
  > 实现：用 X 方案（拒绝 Y 因为 Z）。改 `A.swift` / 新增 `B.swift`。约束：xxx。**YYYY-MM-DD 完成（commit hash 或简短描述）**
```

## 1. 范围与边界

本专项**只收**满足以下任一条件的条目：

- 已经做完的功能里发现的细节问题（UI 错位 / 边缘 case / 错误提示不友好等）
- 文档错字 / 跨文档不一致 / 已过时表述
- 影响日常使用但不构成新功能的"反人类"操作
- 小型重构机会（< 0.5 天工作量，不属于 D-? 重构债）

本专项**不收**（请走对应渠道）：

- ❌ 新功能 → 进 `docs/工程进度/功能实现总览.md` §3-5 对应位置 `- [ ]`
- ❌ 大重构 → 进 `docs/工程进度/功能实现总览.md` §6 取 D-? 编号
- ❌ 发布前清单（Apple Developer / 隐私政策等）→ 进同文档 §8
- ❌ 需要新设计文档的问题 → 在 `docs/详细设计/` 新建文档后再回填本文件
