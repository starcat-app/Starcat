# Starcat 版本迭代规范

> 适用范围：启动版本、维护版本范围与 Checklist、版本收口。项目 Skill：[`starcat-version-iteration`](../../skills/starcat-version-iteration/SKILL.md)。
> 决策：2026-11-20；日常交付先记录版本清单，发布前统一整理 Changelog。

## 1. 入口与授权

- “开始进行 X.Y.Z 的版本迭代”触发只读检查和功能收集；版本号采用 `X.Y.Z`，Beta 序号属于发布记录，不额外派生一套迭代计划。
- 展示检查结果、参与和排除的仓库、功能清单、渠道及拟执行分支操作。dong4j 明确说“开干 / 改吧 / GO / 实施”等后，才能创建或切换分支、写入版本计划。仅提供功能列表仍属于讨论。
- 一次授权覆盖已展示的初始化范围，不逐仓重复询问。已有授权仍有效时，后续明确要求增补、延期或登记完成可直接维护同一文件；不把讨论中的想法自动加入已确认范围。
- 初始化不授权执行清单内全部功能。业务开发、Changelog、功能总览、提交、推送、GUI、打包和发布继续遵守各自授权边界。

## 2. 开发前检查

先读取 `AGENTS.md`、`LESSONS.md`、`BRANCH.md`、本规范、Git 分支规范、Changelog 规范及相关已确认决策；只读检查 `docs/功能实现总览.md`，不得自动新增或修改条目。

| 项目 | 检查内容 |
|---|---|
| 仓库 | 主仓库、`supports/clone-all.sh` 登记项目及 supports 中额外发现的独立 Git 仓库；包含隐藏目录与 `.git` 文件形式的 worktree；缺失项目单列 |
| 工作区 | 当前分支、HEAD、暂存/未暂存/未跟踪文件、冲突及未完成的 merge/rebase/cherry-pick |
| Worktree | 各目录的分支和脏状态、目标版本分支归属；同一 Git common directory 的多个检出目录按同一仓库处理 |
| dev 基线 | 本地 dev、上游设置、缓存远端 refs 的领先/落后/分叉、dev 与 main 的关系、未合入 dev 的旧版本分支 |
| 远端事实 | 明确缓存与实时状态；只读 `ls-remote` 可核对远端 dev，不把过期缓存当最新基线；联网失败写未核实 |
| 版本 | 现有同版本计划、App 配置版本、本地目标 tag、四份 Changelog 的精确版本标题、重复标题与双语状态差异 |
| 环境 | 本地 Secrets 配置、`Configs/SwiftPackages.resolved`、Makefile 和所需工具是否存在；不读取或输出密钥内容 |

输出使用“通过 / 提醒 / 阻断 / 未核实”。有 worktree、本地 dev 领先远端、App 配置尚未升到新版本、Changelog 尚无目标节，均不单独构成阻断。目标版本已经发布、未解决冲突、未知脏修改、错误基线或目标分支被其他任务占用，需要先处理或确认具体处置方案。

只读检查脚本不自动 fetch、pull、stash、提交、切分支、清理或升级。涉及同步操作时遵循分支规范；发现差异先展示方案。启动迭代不默认构建、跑全量测试、查询全部上游最新依赖或执行 `clone-all.sh --pull`。

## 3. 收集范围并初始化分支

1. 检查后询问本版的新增、优化、修复、必须完成项与渠道；已有答案不重复问。不自动把旧计划的所有未完成项搬入本版。
2. 默认参与范围为主仓库和 supports 全部活跃自维护独立仓库；归档、第三方副本和其他排除项必须列明原因。额外发现的仓库先确认归属，不能仅凭目录名猜测。最终名单一次确认。
3. 获授权后，先重新核对全部参与仓库的状态，再逐仓从各自经过核实的 `dev` 创建并切换到 `feature/X.Y.Z`。共享分支名表示 App 迭代，不要求 CLI/API 产品版本号随之变化。
4. 缺少 dev 不擅自改用 main；已有目标分支先核对用途、提交关系及 worktree 后续用，不覆盖。重跑时续接已完成项；若中途失败，逐仓报告成功、失败及未执行项，不强行回滚或宣称全部成功。
5. 默认沿用现有工作目录，不因脏状态自行新建 worktree。确有并行需求时按 Git 规范另列方案；新 worktree 的本机配置、受控锁与登记要求不变。
6. 分支创建后再写计划，避免计划本身使 dev 变脏。主仓库同步 `BRANCH.md`，其他仓库遵循各自登记规则；报告每仓的分支、用途、dev 基线 commit、目录、状态及验收后合回 dev 的归宿。不自动 push。

## 4. 唯一版本 Checklist

- 路径：`docs/4-工程进度/版本迭代/X.Y.Z-迭代计划.md`；使用 [模板](../../skills/starcat-version-iteration/assets/迭代计划.md)。已有同版本清单必须续用；已有详细大版本规划保留并链接，不复制整篇。
- 头部记录状态、渠道、分支和 Changelog 归属。状态使用“规划中 / 开发中 / 待发布 / 已发布 / 已取消”；明确授权初始化后标记“开发中”，不因创建文档就开始全部业务开发。
- 按新增、优化、修复、常规任务分组；条目使用稳定 ID（例如 `V198-01`），写最终用户结果。仅在有歧义时追加一句验收条件，详细设计与证据只放链接。
- `[ ]` 表示尚未完成；代码实现但待验收时在原条目注明；`[x]` 表示已达到约定验收条件并有简短证据或链接，不能以测试/构建代替尚未完成的人工验收或部署。
- 新增功能在本版内的返工归并回原条目，避免堆过程记录。新增、延期、取消保留原 ID；延期/取消移入对应区并记录去向或原因，不打完成勾。
- 当前版本以用户明确指定为先，其次 `feature/X.Y.Z` 与计划头部；不匹配或多份活跃计划无法确定时先澄清，不按最大版本号猜测。版本计划是本轮范围基线；`docs/功能实现总览.md` 仍是全项目主进度索引，保留独立写入授权。
- 获授权的本版任务完成后，同批更新当前清单。没有当前版本计划时不擅自创建；继续执行原 Changelog 询问规则。Checklist 不替代 GitHub / Multica，链接现有任务，不自动创建或关闭远端任务。

## 5. 每轮必带的依赖检查

每个新版本自动加入且初始未完成：**第三方依赖、二进制与内嵌资源版本更新检查**。不继承上一轮勾选状态。

- 根据当前集成事实盘点，至少核对 CodebaseMemory、DeepSeek Harness 及配套工具、Codex CLI/App Server、SPM 受控锁、CodeFlow/Mermaid 与 vendored 资源；清单随实际集成变化，不限定为这几个示例。
- 执行该任务时再联网核对官方上游，记录当前版本/commit、可用版本、处理结论与证据。可结论为“已升级并验证”“无需升级”或“暂缓并说明原因与影响”；检查完成不等于全部升级到最新。
- 升级沿用既有渠道、架构、签名、校验和、索引兼容、本地补丁、致谢与许可证约束，参照[第三方依赖专项方案](../2-产品/需求讨论/正式方案/第三方依赖升级与兼容性验证方案.md)。不擅自下载、安装或替换。
- 版本收口必须再次核对该项；遗漏、未核实或实际升级后未验证时列为待处理，不能因上个版本完成过而跳过。

## 6. Changelog 与发版衔接

存在已确认且状态为“开发中 / 待发布”的当前版本计划时，日常维护 Checklist，不再逐任务询问 Changelog；dong4j 明确要求立即更新日志时执行该要求。单纯创建 Skill/规范不等于已有当前版本计划。

收口时，按 [Changelog 规范](Changelog-更新规范.md) 和 [`starcat-update-changelog`](../../skills/starcat-update-changelog/SKILL.md)：以已验收且属于本次实际交付的条目为主要素材，对照相关仓库从实际上一发布基线到本次交付提交的完整变更补漏；排除内部维护、未交付、延期和取消项；同主题归并为最终用户结果。若 Git 发现未登记内容，先报告并核实交付状态，不能静默漏掉或当成已验收。

获得 Changelog 授权后才写对应渠道的中英文 Markdown；目标版本/发布渠道与汇总版本分开记录，1.9.x → 2.0.0 过渡规则仍适用。Checklist 不直接作为发布资源，也不替代四份正式日志。封版审计转交 `starcat-release-readiness`；打包发布转交现行发布 Skill 和 SOP，遵守当前消息显式授权。真实发布成功后才更新计划发布状态，并记录未交付项去向；不凭完成 Checklist 宣称发布完成。
