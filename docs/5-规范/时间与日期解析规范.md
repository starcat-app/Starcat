# 时间与日期解析规范

本文档约束 Starcat 客户端中 ISO8601 时间字符串的解析与展示，避免外部 API 时间格式差异导致 UI 静默丢字段。

## 核心规则

1. 外部 API 返回的 ISO8601 时间字符串，禁止直接用 `ISO8601DateFormatter.shared.date(from:)` 解析。
2. GitHub REST、`starcat-discovery-api`、`starcat-weekly-api`、`starcat-trending-api` 等外部 / 自建服务返回的时间，统一优先用 `ISO8601DateFormatter.githubDate(from:)` 解析。
3. `ISO8601DateFormatter.shared` 只用于项目内部写入的标准化时间字符串，尤其是本地 SQLite 缓存字段、同步时间戳、内部 metadata。
4. UI 展示时间时必须先解析成 `Date`，再用显式 locale 格式化；不要直接展示原始 ISO8601 字符串。

## 原因

项目里的 `ISO8601DateFormatter.shared` 配置了：

```swift
formatter.formatOptions = [.withInternetDateTime, .withFractionalSeconds]
```

因此它只能稳定解析带 fractional seconds 的字符串，例如：

```text
2026-07-07T10:17:02.000Z
```

但 GitHub 和 discovery 后端常返回不带毫秒的时间，例如：

```text
2026-07-07T10:17:02Z
```

这种字符串用 `ISO8601DateFormatter.shared.date(from:)` 会返回 `nil`。如果 UI 代码用 `guard let date = ... else { return nil }`，就会出现“数据在后端和 SQLite 都存在，但界面不展示”的静默失败。

## 推荐写法

```swift
guard let date = ISO8601DateFormatter.githubDate(from: dto.latestReleaseAt) else {
    return nil
}

let text = date.formatted(
    .dateTime
        .month(.abbreviated)
        .day()
        .locale(locale)
)
```

`githubDate(from:)` 会先尝试带 fractional seconds 的格式，再尝试纯 `.withInternetDateTime` 格式，能兼容 GitHub 和 Starcat 自建后端常见返回。

## 禁止写法

```swift
let date = ISO8601DateFormatter.shared.date(from: apiTimestamp)
```

尤其禁止在以下场景使用：

- GitHub API 的 `created_at` / `updated_at` / `pushed_at` / `published_at`
- discovery repo 的 `latest_release_at`
- weekly / trending / recommend 等后端返回的事件时间
- 测试 fixture 中强解包无毫秒时间：`ISO8601DateFormatter.shared.date(from: "2026-07-07T10:17:02Z")!`

## 测试要求

涉及外部 API 时间解析的新逻辑，至少覆盖两种输入：

```text
2026-07-07T10:17:02Z
2026-07-07T10:17:02.000Z
```

测试不应依赖 `ISO8601DateFormatter.shared` 去构造无毫秒 fixture；需要固定时间时可以直接用 `DateComponents` 构造 `Date`，或用 `ISO8601DateFormatter.githubDate(from:)` 解析。
