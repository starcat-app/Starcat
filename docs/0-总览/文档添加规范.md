# Starcat 文档添加规范

> 创建:2026-06-28
> 适用范围:所有在 `docs/` 目录下新建 / 移动 / 删除文档的协作者
> 强制级别:**违反任一条 = 文档 review 不通过**

---

## 一、目录归属规则(按文档生命周期)

| 目录 | 适用文档 | 关键判断 |
|------|---------|---------|
| `0-总览/` | 入口、跨目录的导航与规范 | 文档本身不承载内容,只指向其他目录 |
| `1-立项/` | 立项期沉淀(需求、概要、调研、发展规划、问题清单) | 「项目为什么要做 / 怎么做」的源头,基本不改 |
| `2-产品/需求讨论/` | 需求池 + 讨论 + 方案 | 单点功能的产品文档 |
| `2-产品/里程碑/` | 阶段总结(版本化) | 涉及具体版本号(v1 / v2 / …)的快照 |
| `3-设计/详细设计/` | 详细技术设计(滚动维护) | 单一功能点的完整设计,带「适用版本」标注 |
| `4-工程进度/阶段性回顾/` | 阶段性总结(非里程碑) | 复盘 / 总结 / 反思 |
| `4-工程进度/踩坑与故障记录/` | 一次性的踩坑、故障、根因排查、临时方案 | 「以后再遇到能查到」的归档 |
| `4-工程进度/重构专项/` | R-xx 编号的重构任务专项 | 跟踪一个长期重构的进度 |
| `5-规范/` | **永久强制规范**(UI / i18n / 开源致谢 等) | 一旦写入,长期生效,变更需评审 |
| `6-发版与上架/` | 发版 SOP + 各版本上架 / 发布快照 | 涉及上架流程 |
| `7-工具与脚本/` | 工具型参考(Swift 学习、调试、脚本说明) | 不属于产品本身,纯工具性 |
| `8-原型设计/` | UI 原型 / SKILL / 设计系统参考 | |

## 二、版本号使用规则

**只允许**在以下场景使用版本号前缀(`v1-xxx.md` / `v2-xxx.md`):

1. 里程碑快照 — `6-发版与上架/v1-发布说明.md`
2. 阶段总结 — `2-产品/里程碑/2026-06-01-第一阶段总结与后续规划.md`
3. 阶段性回顾 — `4-工程进度/阶段性回顾/2026-05-30-现阶段问题修复.md`
4. 阶段规划 — `2-产品/需求讨论/v2-功能规划.md`

**禁止**给以下目录加 `v1/` `v2/` 子目录:

- `1-立项/`
- `3-设计/详细设计/`(用「适用版本」标注字段代替)
- `5-规范/`
- `7-工具与脚本/`
- `8-原型设计/`

## 三、命名规则

### 3.1 文件名

- **Markdown 文件**:用中文,空格保留(`v1-上架信息准备.md` / `CloudKit数据同步设计.md`)
- **Kebab-case 备选**:规范类用 kebab-case(`i18n-军规.md` / `UI-颜色规范.md`)
- **不要**:用驼峰、下划线、纯英文
- **里程碑 / 阶段总结**必须日期开头:`YYYY-MM-DD-xxx.md` 或 `YYYYMMDDHHMMSS-xxx.md`

### 3.2 子目录

- 中文(`调研报告/` / `正式方案/` / `agent/` / `推荐算法/`)
- 规范类目录用中文 + 编号前缀(`1-立项/` `2-产品/` `3-设计/` `4-工程进度/` `5-规范/` `6-发版与上架/` `7-工具与脚本/` `8-原型设计/`)
- **禁止**用 `v1/` `v2/` 作为顶层目录(见 §二)

## 四、图片 / 附件规范

**核心原则**:文档中的图片应放在**同级且同名**的目录中。

```text
# 正确示例
docs/1-立项/
├── 调研报告.md
└── 调研报告/                          ← 与 .md 同名,作为图片目录
    ├── image-20260523094230335.png
    └── image-20260523095041171.png

# 引用
![xxx](./调研报告/image-20260523094230335.png)
```

### 4.1 适用范围

| 场景 | 处理方式 |
|------|---------|
| 文档里要插入图片 | 在文档同级建同名目录,引用路径用相对路径 |
| 文档里只有少量图片(1-2 张) | 仍然按规范建目录,避免后续加图时打破规则 |
| 文档里完全没图片 | 不建空目录 |
| 复杂示意图(Sketch / Figma 导出) | 同样进同名目录,可加 `screenshots/` 等子目录区分 |

### 4.2 命名冲突 edge case

如果「文档名 + 同名目录」造成引用混乱(例:`调研报告.md` 与 `调研报告/` 同行看着怪),可以:

- 用 `xxx-images/` `xxx-pics/` `xxx-figs/` 等带后缀的同名前缀目录代替
- 例:`docs/1-立项/调研报告-images/` 替代 `调研报告/`

**优先级**:**同名前缀**(带后缀) > **严格同名**(无后缀)。

### 4.3 跨文档共享图片

- 禁止把图片放在根目录公用(散乱)
- 应该放在第一次使用的文档的同名目录
- 后续引用用 `../A/B/同名目录/xxx.png` 相对路径

## 五、文档移动 / 重命名流程

1. **优先用 `git mv`**(保留历史)
2. 移动后,**全工程搜索引用**:
   ```bash
   grep -rn "原文件名" --include="*.md" --include="*.swift" .
   ```
3. 更新所有引用(优先相对路径,绝对路径仅限 `AGENTS.md` 等配置入口)
4. 在 `功能实现总览.md` 变更日志追加一行

## 六、删除文档

1. `git rm` 删除文件
2. 检查是否被 `AGENTS.md` / 其他文档 / 代码引用,先改引用再删文件
3. 一次性过程性文档应进 `_archive/` 而非删除(留作可查)

## 七、AGENTS.md 引用原则

- **只引用,不复制正文** — 强制规范在 `5-规范/`,`AGENTS.md` 只放指向它的链接
- **入口位置**:`AGENTS.md`「文档导航」节 → 列出 `docs/` 各目录职责
- **单一信任源**:每条规则在 `docs/` 下只能有一个权威文档,其他位置都是引用
