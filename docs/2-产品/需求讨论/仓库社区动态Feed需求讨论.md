## 1. 我想做什么

在仓库详情页增加一个与当前项目强关联的「社区动态」入口。用户点击后，可以看到 GitHub 之外关于这个项目的讨论、文章、视频、发布报道和使用反馈，并可让 AI 基于当前 Feed 生成带来源的观点总结。

这个功能要补足 GitHub 仓库内容天然缺失的一面：

- GitHub README、Release、Issue 主要说明项目自己如何描述和维护自己。
- 外部社区更容易出现真实使用体验、争议、替代方案、迁移原因和踩坑记录。
- 对 Starcat 用户而言，“社区如何评价这个项目”往往比重复阅读 README 更能帮助理解、评估和回访。

因此，本专题的核心不是“搜索更多网页”，而是：

> 围绕一个确定的 GitHub 仓库，持续整理可追溯的外部社区证据，让用户快速理解项目在真实世界中的口碑、讨论焦点和变化。

## 2. 产品定位

### 2.1 名称

详情页对用户展示的功能名暂定为：

- 中文：**社区动态**
- 英文：**Community**

“Feed”只用于设计和技术文档，不作为主入口文案。“全网搜索”“舆情”“新闻”等名称均不采用：

- “全网搜索”强调查询动作，弱化了围绕当前仓库持续阅读的心智。
- “舆情”过于商业和监控化，不符合开发者工具语境。
- “新闻”无法覆盖讨论帖、使用心得、视频和问答。

### 2.2 与现有能力的边界

| 能力 | 回答的问题 | 本专题是否替代 |
|---|---|---|
| README / Repo Detail | 项目是什么、怎么用 | 不替代 |
| GitHub Activity / Release | 项目在 GitHub 内发生了什么 | 不替代 |
| 相似项目 | 还有哪些功能接近的仓库 | 不替代 |
| 知识库 | 我保存和整理了什么长期资料 | 不替代 |
| 全局 External Search | 用户主动搜索某个开放问题 | 不替代 |
| 社区动态 Feed | 外部社区如何讨论当前项目 | 新增 |

社区动态不是 GitHub Activity 的另一个视图，也不是把搜索中心嵌入详情页。它必须始终以当前仓库为对象，并对结果进行仓库身份确认、去重和内容分类。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 想在采用依赖前了解真实反馈的开发者。
- 需要快速形成项目判断的技术博主、媒体和研究者。
- 收藏较多项目、隔一段时间回来重新评估的 Starcat 用户。
- 正在比较迁移方案、替代品或技术路线的团队成员。

### 3.2 用户故事

| # | 作为 | 我想 | 以便 |
|---|---|---|---|
| U1 | 用户 | 在详情页一键打开当前项目的社区动态 | 不离开当前项目上下文 |
| U2 | 用户 | 按讨论、文章、视频、发布等类型浏览 | 快速找到我关心的信息形态 |
| U3 | 用户 | 看到来源、时间、摘要和原始链接 | 判断信息新鲜度并回到原文核实 |
| U4 | 用户 | 识别社区共识、好评、批评与常见对比 | 快速建立项目的外部认知 |
| U5 | 用户 | 让 AI 总结当前 Feed | 在信息较多时减少阅读成本 |
| U6 | 用户 | 从 AI 结论跳回对应来源 | 验证总结不是无依据生成 |
| U7 | 用户 | 网络失败时继续看到上一次结果 | 不因临时故障失去已有信息 |
| U8 | 私有仓库用户 | 不向外部服务发送仓库身份 | 避免泄露私有项目名称和上下文 |
| U9 | 同一 Starcat 用户 | 在同一设备或另一台设备重复查看同一项目 | 复用已有项目数据，不重复抓取社区来源 |
| U10 | 不同 Starcat 用户 | 查看其他人刚刚请求过的公开项目 | 复用项目级公共缓存，减少等待和上游请求 |

## 4. 内容范围

### 4.1 内容类型是主分类

Feed 顶层按内容价值分类，平台只作为来源标识。首期类型如下：

| 类型 | 典型内容 | 可能来源 |
|---|---|---|
| 讨论 | 使用体验、争论、评论串、Show HN 反馈 | Hacker News、X、Reddit、Lobsters、V2EX |
| 文章 | 教程、评测、迁移记录、踩坑与深度分析 | 独立博客、DEV、Medium、Hashnode、掘金、少数派 |
| 视频 | 演示、评测、教程、会议分享 | YouTube、Bilibili |
| 发布 | 产品发布、榜单、Launch 讨论 | Product Hunt、Hacker News、媒体 |
| 新闻 | 融资、收购、安全事件、重大版本报道 | 技术媒体、新闻站点 |

首期不把 Hacker News、Reddit、YouTube 等平台做成顶层导航。用户先关心“这是一篇讨论还是一段视频”，再关心它来自哪里。

### 4.2 首期来源优先级

| 阶段 | 来源 | 需求理由 |
|---|---|---|
| P0 | Hacker News、X、Reddit、公开 Web 文章 | 讨论和长文价值高；X 已验证可按 GitHub URL 找到热门帖子 |
| P1 | YouTube、Product Hunt | 补充演示、评测和发布反馈 |
| 后续 | Lobsters、Stack Overflow、V2EX、知乎、掘金、少数派、Bilibili | 按覆盖率、接口稳定性和合规条件逐步增加 |

来源清单不是永久承诺。任何需要专用 API 的平台，都必须在实现前重新核对授权、配额、商业使用条款和 App Store 合规性。

### 4.3 Feed 条目必须提供的信息

每条信息至少展示：

- 标题。
- 内容类型。
- 来源平台或站点域名。
- 发布时间；无法确认时明确显示未知，不推测时间。
- 一段可读摘要或搜索结果 snippet。
- 原文链接。
- 可用时显示讨论分数、评论数、作者或频道。

Feed 不保存第三方完整正文，也不把普通网页正文自动写入知识库或 RAG。

### 4.4 X 来源实测结论

2026-08-30 使用测试账号对 twitterapi.io 和 SocialData 进行了真实请求验证，样本覆盖高热项目 `openai/codex` 与长尾项目 `starcat-app/Starcat`：

- 两家均可使用 `url:github.com/<owner>/<repo>` 和 `queryType/type=Top` 搜索热门帖子。
- twitterapi.io 的 URL 查询精度更高，适合作为主来源，但短时间连续请求出现过 `429 Too Many Requests`。
- SocialData 返回量更大、连续请求稳定，适合作为补充召回和故障降级，但会混入 conversation 父帖和只有通用仓库名的内容。
- 仅搜索 `owner/repo` 会被搜索引擎拆词，不能作为强相关证据。
- URL 搜索仍可能发生前缀误匹配，例如目标 `/openai/codex` 命中 `/openai/codex-security`，必须按 host + path segment 做二次过滤。

因此 X 来源采用 twitterapi.io 主查、SocialData 补充 / 降级的双 Provider 模式，最终结果由 `starcat-community-api` 统一过滤、排序并按 Tweet ID 去重。

## 5. 交互需求

### 5.1 入口

入口位于仓库详情页现有 Hero 操作区，与 Wiki、相似项目、知识库同组，使用独立图标按钮。

建议顺序：

```text
Wiki → 社区动态 → 相似项目 → 知识库
```

需求约束：

- 入口只在存在有效公开仓库身份时可用。
- 图标建议使用 `dot.radiowaves.left.and.right`，表达围绕项目汇聚的外部信号。
- 视觉尺寸、hover、focus、VoiceOver 与同组按钮保持一致。
- 点击入口才允许发起社区动态请求；切换详情项目时不得自动预取。

### 5.2 Feed 容器

首期使用详情页按钮触发的 Popover，不新增独立窗口或一级导航。

Popover 应包含：

1. 标题、刷新状态和关闭当前上下文的自然交互。
2. “全部 / 讨论 / 文章 / 视频 / 发布 / 新闻”内容筛选。
3. 按时间与相关性组织的 Feed 列表。
4. AI 总结按钮。
5. AI 总结结果区，生成后固定在列表顶部并允许折叠。

### 5.3 状态反馈

必须覆盖以下状态：

- 首次加载。
- 命中缓存并后台刷新。
- 正在手动刷新。
- 无相关结果。
- 仅部分来源成功。
- 全部来源失败但存在旧缓存。
- 全部来源失败且无缓存。
- 私有仓库不可用。
- 社区数据服务未配置、不可达或暂时不可用。
- AI 总结证据不足。
- AI 总结失败，但原始 Feed 仍可继续阅读。

## 6. AI 总结需求

### 6.1 总结对象

AI 只总结用户当前看到的 Feed 快照，不在总结阶段重新联网搜索，也不读取现有 Repo AI Summary 代替社区证据。

### 6.2 输出结构

首期 AI 总结建议固定输出：

1. **一句话观察**：社区总体关注什么。
2. **主要共识**：多来源重复出现的判断。
3. **正面反馈**：被认可的能力或使用体验。
4. **批评与风险**：缺陷、争议、迁移阻力或维护风险。
5. **常见对比**：与哪些替代方案一起被讨论，以及对比维度。
6. **证据范围**：来源数量、时间跨度和明显缺口。

### 6.3 可信度约束

- 每个实质性结论必须引用当前 Feed 中的来源编号。
- 不得把单一来源写成“社区普遍认为”。
- 无法确认的内容必须表述为“某来源提到”或“现有样本中出现”。
- 最低生成门槛建议为 3 条有效信息、至少 2 个独立域名；不足时不生成结论性总结。
- 页面必须保留原始 Feed，AI 总结不能替代来源列表。

### 6.4 订阅边界

建议：

- 原始社区动态 Feed：所有满足条件的用户可读。
- AI 社区观点总结：复用现有 `AI Summary` Pro 权益和已配置模型。

这样可以先让用户确认外部信息本身有价值，再用 AI 降低阅读成本；不为本专题新增一套独立订阅枚举。

## 7. 相关性与质量需求

仓库名可能高度歧义，例如 `swift`、`gin`、`echo`、`delta`。不能把“搜索到同名词”直接视为与仓库相关。

### 7.1 身份证据优先级

相关性从强到弱：

1. 内容直接包含仓库 canonical GitHub URL。
2. 同时包含完整 `owner/name`。
3. 同时包含 repo 名和 owner、项目主页域名或独有 topic。
4. 只包含 repo 名，但上下文存在明确技术实体证据。
5. 只有通用名称，没有其他项目证据。

第 5 类默认过滤。高歧义名称必须提高门槛，宁可少展示，也不能把无关内容混入 Feed。

### 7.2 去重与保留

- 同一 canonical URL 只保留一条，合并更完整的标题、摘要和时间。
- 带跟踪参数、移动端路径或聚合跳转的同一文章应归一化。
- 不同社区中的独立讨论串必须保留，即使它们引用同一篇文章。
- 相同标题但不同 URL 不可仅凭标题强行合并。

### 7.3 排序

默认排序要同时考虑：

- 仓库身份匹配强度。
- 内容新鲜度。
- 来源多样性。
- 讨论热度（仅在来源提供可靠指标时使用）。
- 内容类型覆盖，避免首屏被同一站点或同一种内容占满。

首期不要求每次刷新调用 LLM 做 rerank。相关性必须首先由可测试、可解释的确定性规则保证。

## 8. 隐私、合规与成本边界

### 8.1 私有仓库

首期只支持公开仓库。私有仓库不显示可执行入口，也不得把 owner、repo 名、README、topic 或其他身份信息发送给 `starcat-community-api`、社区平台或 AI 总结链路。

这比现有“用户允许私有仓库参与外部搜索”的通用开关更严格，是社区动态首期的产品边界，不代表修改其他功能的既有策略。

### 8.2 明确联网

- 只有用户点击社区动态或手动刷新时，才发起外部请求。
- 仓库切换、列表滚动、详情预览不得隐式触发。
- UI 应明确显示数据来自 Starcat 社区数据服务及具体社区平台。

### 8.3 数据留存

允许客户端本地缓存：

- 标题、短摘要、URL、来源、时间、可选指标。
- 查询指纹、Provider、刷新时间、结果数量和错误摘要。
- AI 总结文本、引用关系、模型和 prompt 版本。

允许社区数据服务保存可重建的公共项目缓存：

- 标准化的公开仓库身份。
- Feed 条目的标题、短摘要、URL、来源、时间和公开指标。
- 来源刷新时间、查询版本、错误状态、ETag 和内容 hash。
- 用于请求合并、退避和限流的最小运行状态。

不保存：

- 第三方网页完整正文。
- Cookie、登录态或用户在外部站点的身份。
- 为了分析而采集的点击轨迹。
- 用户与仓库的长期浏览关系；首期社区数据服务不需要识别具体 GitHub / Starcat 用户。

### 8.4 独立后端与共享缓存

首期新增独立、可自部署的 `starcat-community-api`，作为 Starcat 客户端与 Hacker News、Reddit、公开 Web Search 等来源之间的唯一数据接口。

采用独立服务的原因：

- 社区数据属于 `owner/name` 对应的项目级公共数据，可以被同一用户的多台设备以及不同用户共享。
- Provider 密钥、限流、第三方条款和查询规则不应散落在每台客户端。
- 相关性过滤、去重和排序必须由服务端统一执行，避免不同客户端版本得到互相矛盾的 Feed。
- 同一项目的并发请求必须合并成一次上游抓取，不能因为多个用户同时打开而重复消耗配额。
- 服务端可以集中实现成功、空结果和错误的差异化 TTL，并为客户端提供 ETag。

缓存主键不得包含 Starcat 用户 ID，应使用：

```text
owner/name + sourceProfile + queryVersion + schemaVersion
```

首期接口沿用 Starcat 支持服务的 Client API Key 鉴权，不上传 GitHub access token，也不要求后端识别具体 Starcat 用户。Pro 权益仍由 App 本地链路判断；手动刷新至少执行项目级冷却。未来若 Starcat 建立独立的可验证账号 token，再增加用户级限流，但仍不得把用户 ID 放进 Feed 缓存主键。

重复请求规则：

- 同一设备重复打开：优先命中客户端缓存，并通过 ETag 验证。
- 同一 Starcat 用户换设备：访问后端项目缓存，不重复抓取上游。
- 不同用户查看同一项目：共享同一项目缓存。
- 同一项目缓存缺失且有多个并发请求：使用 singleflight / request coalescing，只执行一个抓取任务。

### 8.5 第三方条款

- Hacker News 可评估使用 [Algolia Search API](https://hn.algolia.com/api) 获取结构化讨论信息。
- twitterapi.io 使用 [`GET /twitter/tweet/advanced_search`](https://docs.twitterapi.io/api-reference/endpoint/tweet_advanced_search)，通过 `X-API-Key` 鉴权，支持 `Top` / `Latest` 和 X Advanced Search 查询语法。
- SocialData 使用 [`GET /twitter/search`](https://docs.socialdata.tools/reference/get-search-results/)，通过 Bearer Token 鉴权，支持 `Top` / `Latest` 和 cursor。
- YouTube 若改用专用接口，应遵循 [YouTube Data API `search.list`](https://developers.google.com/youtube/v3/docs/search/list) 的配额与展示要求。
- Product Hunt 的 [API 文档](https://api.producthunt.com/v2/docs) 对商业用途有额外限制，未获得许可前不得把直接 API 接入列为已确定能力。
- Reddit 等平台在实现专用接入前，必须重新核对当时有效的开发者条款和访问限制。

X 搜索资费（官方页面核对日期：2026-08-30）：

| 服务 | Search 资费 | 计费特点 | 首屏 20 条估算 |
|---|---:|---|---:|
| [twitterapi.io](https://twitterapi.io/) | `$0.00015 / 返回 Tweet`，即 `$0.15 / 1,000 Tweets` | Pay-as-you-go，无月度最低消费；余额充值与可选自动充值分开 | 约 `$0.003` |
| [SocialData](https://docs.socialdata.tools/getting-started/pricing/) | `$0.0002 / 返回 Tweet`，即 `$0.20 / 1,000 Tweets` | 需要账户保持正余额；失败请求不扣费；余额按官方说明不过期 | 约 `$0.004` |

若同一冷缓存刷新分别向两家请求一页、每家返回 20 条，理论数据成本约 `$0.007`。正常路径应先调用 twitterapi.io；只有结果不足、429 或来源故障时才调用 SocialData，不能每次无条件双查。空结果的实际最低扣费、批量折扣和未来价格变化以 Provider 账单为准。

以上外部条件核对日期为 2026-08-30，实施前必须复查，不能把当前条款视为长期不变。

## 9. 非目标

首期明确不做：

- 不做任意关键词的全网搜索页。
- 不抓取或镜像第三方站点完整内容。
- 不登录用户的 Reddit、X、YouTube 等第三方账号。
- 不把社区动态自动写入知识库、笔记、Repo AI Summary 或 RAG 索引。
- 不做实时监控、系统通知和后台定时轮询。
- 不做情感分数、舆情指数或“项目好坏”自动评分。
- 不为私有仓库生成脱敏搜索词后尝试搜索。
- 不在 Starcat 客户端新增 GRDB 表或修改已发布 migration；`starcat-community-api` 可以使用独立数据库保存可重建公共缓存。

## 10. 功能验收标准

### 10.1 Feed

- [ ] 公开仓库详情页出现“社区动态”图标入口，位置和视觉与相邻按钮一致。
- [ ] 点击入口后才发起请求，单纯选中或切换仓库不会联网。
- [ ] Feed 能按内容类型筛选，并展示标题、来源、时间、摘要和原文链接。
- [ ] 同一 canonical URL 不重复展示，不同社区的独立讨论串不被误合并。
- [ ] 通用同名项目的无关结果被过滤，无法确认身份的结果不进入正式 Feed。
- [ ] 单个来源失败时保留其他成功来源，并明确显示“部分来源不可用”。
- [ ] 有旧缓存时网络失败仍可阅读旧结果，并显示数据时间。
- [ ] 私有仓库不会产生任何社区动态外部请求。
- [ ] 同一项目在缓存有效期内被同一用户或不同用户重复访问时，不重复请求 Hacker News 等上游来源。
- [ ] 同一项目并发缓存未命中时只产生一个上游抓取任务，其余请求复用结果。
- [ ] 客户端携带 ETag，Feed 未变化时后端返回 `304 Not Modified`。
- [ ] X URL 查询结果经过 host + path segment 校验，不把同前缀仓库当作目标项目。
- [ ] twitterapi.io 返回 429 或有效结果不足时可按预算降级到 SocialData，两个来源按 Tweet ID 去重。
- [ ] X 查询限定首屏和成本预算，不进行无界 cursor 分页。

### 10.2 AI 总结

- [ ] AI 只消费当前 Feed 快照，不在生成时二次搜索。
- [ ] 证据不足时不生成结论性总结，并解释缺少的来源条件。
- [ ] 每个主要观点可跳回至少一个原始来源。
- [ ] AI 失败不影响原始 Feed 阅读。
- [ ] 新的社区总结不会覆盖或污染现有 Repo AI Summary。
- [ ] Feed 内容变化后，旧 AI 总结不会被错误复用。

### 10.3 体验与工程边界

- [ ] 支持浅色、深色、小窗口和 VoiceOver 基本操作。
- [ ] 所有用户可见文案进入 i18n，不在 Swift 代码中硬编码。
- [ ] 不新增第三方完整正文持久化，不新增私有仓库外发路径。
- [ ] 无需删除数据库或修改已发布 migration。

## 11. 已收敛决策与待确认项

### 11.1 已收敛

- 产品名使用“社区动态”，不使用“全网搜索”。
- 入口放在详情页 Wiki / 相似项目 / 知识库同组。
- 顶层按内容类型组织，平台只作为来源标识。
- 原始 Feed 和 AI 总结分层，AI 必须引用来源。
- 首期公开仓库限定、点击后联网、不自动写入知识库。
- 新增独立 `starcat-community-api`，统一完成社区来源抓取、相关性处理和项目级共享缓存。
- Starcat App 不直接调用 Hacker News、Reddit 或 Web Search Provider，只消费社区数据服务的稳定 Feed 接口。
- X 来源采用 twitterapi.io 主查、SocialData 补充 / 降级，并由服务端统一保管凭据和执行成本预算。
- 原始 Feed 按项目全局共享，不依赖后端识别具体用户；同一 Starcat 用户跨设备复用是项目级缓存自然产生的结果。
- AI 总结继续复用现有 AI Provider 与权益，不由社区数据服务代替用户的 AI 配置。

### 11.2 仍需在实施前确认

1. 首期是否把 YouTube 纳入 P0，还是只做 Hacker News、Reddit 和 Web 文章。
2. 原始 Feed 是否完全免费，或免费用户限制最近条数；当前建议为完全可读。
3. Popover 的最终宽高和小窗口降级，需要在真实 App 中视觉验收。
4. 是否在后续版本增加“加入知识库”的显式人工动作；本专题首期不做。
5. X 来源的单次刷新硬预算和月度告警阈值，需要结合上线后的项目命中率与 Provider 实际账单确定。
