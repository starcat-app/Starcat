# Starcat 相似仓库推荐：内容向量 vs 行为训练，以及用户行为数据获取方案

> 版本：v1.1
> 适用项目：Starcat macOS 应用  
> 主题：相似 GitHub 仓库推荐、SimRepo 类算法、自研推荐系统、用户行为数据采集

> 2026-08-22 修订：客户端前置数据贡献已收口为两个独立 opt-in，只上传公开 Star 全量快照和公开 repo 日级 Star 数观测。原文中的点击、AI 分析、加入对比等是早期候选信号，不属于当前获准上报范围。字段、隐私、删除和 outbox 契约以 [60-Starcat数据贡献与数据平台详细设计](../../../3-设计/详细设计/60-Starcat数据贡献与数据平台详细设计.md) 为准，训练算法以 [61-Starcat自研仓库推荐系统详细设计](../../../3-设计/详细设计/61-Starcat自研仓库推荐系统详细设计.md) 为准。

---

## 1. 背景问题

在前面的方案中提到了“训练推荐模型”，但这里容易产生误解：

> 如果只是下载/收集很多 GitHub 项目，提取 README、description、topics，然后做 embedding，写入 Qdrant / pgvector，再做向量查询，这个过程确实**不需要训练推荐模型**。

这条路线本质上是：

```text
GitHub Repo 文本数据
    ↓
使用已有 embedding 模型生成向量
    ↓
写入向量数据库
    ↓
查询时做 nearest-neighbor search
```

这里使用的是**已经训练好的 embedding 模型**，Starcat 自己不训练模型。

我之前说的“训练”，指的是另一条路线：

> 用 GitHub stars、Starcat 收藏、点击、AI 分析、加入对比等用户行为数据，训练出 repo 的“行为向量”。

这属于协同过滤推荐，不是简单文本向量检索。

---

## 2. 两类推荐路线的区别

| 方案 | 是否需要训练 | 核心输入 | 产物 | 解决的问题 |
|---|---:|---|---|---|
| 内容向量检索 | 不需要训练推荐模型 | README、description、topics、language | repo 内容向量 | 内容/语义相似 |
| star 共现统计 | 不一定需要训练 | GitHub stargazer 数据 | repo 共现边 | 被相同开发者关注 |
| 协同过滤训练 | 需要训练轻量推荐模型 | user-repo 行为矩阵 | repo 行为向量 | 开发者兴趣相似 |
| 混合推荐 | 可选训练 | 内容 + metadata + 行为 | 多路召回 + 排序 | 技术选型/项目发现 |

---

## 3. 第一阶段：内容向量检索，不需要训练

### 3.1 你的理解是正确的

Starcat 第一版完全可以这样做：

```text
收集 GitHub repo
    ↓
获取 repo metadata
    ↓
获取 README
    ↓
构造 embedding text
    ↓
调用 embedding 模型
    ↓
写入 Qdrant
    ↓
根据当前 repo 查询相似 repo
```

这里不存在“训练推荐模型”。

Qdrant 官方文档把这类能力称为 vector similarity search / k-NN search，也支持直接通过已存储向量做搜索。Qdrant 还支持 Recommendations，即提供 positive / negative examples 做推荐查询。参考 Qdrant Search 与 Explore/Recommend 文档：

- Qdrant Search: https://qdrant.tech/documentation/search/search/
- Qdrant Explore / Recommendation API: https://qdrant.tech/documentation/search/explore/
- Qdrant Recommend Points API: https://api.qdrant.tech/api-reference/search/recommend-points

### 3.2 内容向量输入

建议不要只用 README 全文，而是构造一个稳定的 repo profile：

```text
Repository: langchain-ai/langchain
Description: Build context-aware reasoning applications
Primary Language: Python
Topics: llm, agents, rag, prompt-engineering, ai
README Summary:
LangChain is a framework for building applications powered by large language models...
```

推荐字段：

| 字段 | 来源 | 说明 |
|---|---|---|
| repo id | GitHub REST API | GitHub 数字 ID |
| full_name | GitHub REST API | owner/repo |
| description | GitHub REST API | 简短说明 |
| topics | GitHub REST API | 主题标签 |
| language | GitHub REST API | 主语言 |
| README | GitHub REST API / raw | 核心语义来源 |
| stars / forks | GitHub REST API | 排序因子 |
| pushed_at | GitHub REST API | 活跃度因子 |
| license | GitHub REST API | 技术选型参考 |
| archived | GitHub REST API | 过滤因子 |

GitHub REST API 仓库接口文档：

- https://docs.github.com/rest/repos/repos

### 3.3 MVP 推荐公式

第一版可以使用简单规则排序：

```text
score =
  0.75 * content_vector_similarity
+ 0.10 * topic_overlap
+ 0.05 * language_match
+ 0.05 * activity_score
+ 0.05 * log_stars
```

这不是模型训练，只是手写排序规则。

### 3.4 适合解决的问题

内容向量检索适合：

- README 语义相似；
- 技术方向相近；
- topics 相近；
- 同类项目发现；
- 新项目冷启动；
- 技术选型候选扩展。

例如：

```text
langchain-ai/langchain
    ↓
run-llama/llama_index
microsoft/semantic-kernel
deep-set/haystack
crewAIInc/crewAI
```

## 4. “训练”到底指什么？

### 4.1 训练不是训练 LLM

这里说的训练不是：

```text
训练大语言模型
训练 embedding 模型
训练代码理解模型
```

而是训练一个轻量推荐模型，例如：

- implicit ALS；
- BPR；
- LightFM；
- Learning-to-Rank。

Python `implicit` 库官方定位就是 “Fast Python Collaborative Filtering for Implicit Datasets”，提供 ALS、BPR 等面向隐式反馈数据的协同过滤算法：

- https://benfred.github.io/implicit/
- https://benfred.github.io/implicit/api/models/cpu/als.html

### 4.2 训练的输入是 user-repo 行为矩阵

例如：

```text
userA star 了：langchain、llama_index、crewai
userB star 了：langchain、semantic-kernel、dspy
userC star 了：vue、react、svelte
```

构造成矩阵：

| user / repo | langchain | llama_index | semantic-kernel | vue | react |
|---|---:|---:|---:|---:|---:|
| userA | 1 | 1 | 0 | 0 | 0 |
| userB | 1 | 0 | 1 | 0 | 0 |
| userC | 0 | 0 | 0 | 1 | 1 |

训练后得到：

```text
repo_vector[langchain] = [...]
repo_vector[llama_index] = [...]
repo_vector[semantic-kernel] = [...]
repo_vector[vue] = [...]
repo_vector[react] = [...]
```

这些向量表示的是：

> 喜欢这个 repo 的用户，也喜欢哪些 repo。

这和 README 语义向量完全不是一回事。

---

## 5. 内容向量 vs 行为向量

### 5.1 内容向量

来源：

```text
README + description + topics + language
```

表示：

```text
这个 repo 在文本语义和技术方向上像什么？
```

例如：

```text
一个 RAG 项目的 README 写得很像 LangChain
    ↓
内容向量会接近 LangChain
```

### 5.2 行为向量

来源：

```text
GitHub stars + Starcat 收藏 + 点击 + AI 分析 + 加入对比
```

表示：

```text
喜欢这个 repo 的开发者，还喜欢什么？
```

例如：

```text
大量用户同时 star langchain 和 llama_index
    ↓
行为向量会让它们接近
```

### 5.3 两类相似性都重要

| 例子 | 内容向量可能 | 行为向量可能 |
|---|---|---|
| langchain vs llama_index | 接近 | 接近 |
| next.js vs shadcn-ui | 不一定很接近 | 可能接近 |
| vscode vs zed | 不一定很接近 | 可能接近 |
| tailwindcss vs radix-ui | 不一定很接近 | 可能接近 |

因此，Starcat 后期最好使用混合推荐：

```text
内容相似 + 行为相似 + topics + language + 活跃度 + 用户偏好
```

## 6. 用户行为数据怎么获取？

用户行为数据分为两大类：

1. **GitHub 外部公开行为**；
2. **Starcat 内部产品行为**。

---

## 7. GitHub 外部公开行为数据

### 7.1 Stargazers：某个 repo 被哪些用户 star

GitHub 提供 stargazers endpoint，可以列出 star 了某个仓库的用户。GitHub starring API 文档说明，如果使用特定 media type：

```http
Accept: application/vnd.github.star+json
```

可以包含 star 创建时间 `starred_at`。

文档：

- https://docs.github.com/rest/activity/starring

请求示例：

```bash
curl -L \
  -H "Accept: application/vnd.github.star+json" \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  "https://api.github.com/repos/langchain-ai/langchain/stargazers?per_page=100&page=1"
```

返回数据中可以获取：

```json
[
  {
    "starred_at": "2024-01-01T12:00:00Z",
    "user": {
      "id": 123456,
      "login": "some-user"
    }
  }
]
```

这类数据可以用于：

```text
repoA 和 repoB 是否被同一批用户 star？
```

### 7.2 Authenticated user starred repos：当前授权用户 star 过哪些 repo

如果用户在 Starcat 登录 GitHub 并授权，可以读取当前用户 star 过的仓库：

```http
GET /user/starred
```

同样可以使用：

```http
Accept: application/vnd.github.star+json
```

获取 star 时间。

用途：

- 个性化推荐；
- 用户兴趣画像；
- 初次登录后的冷启动推荐；
- 基于用户 GitHub stars 推荐项目。

注意：这需要用户授权，不能默认获取。

### 7.3 用户公开 star 列表

也可以通过公开接口获取某个用户 star 过的仓库：

```http
GET /users/{username}/starred
```

但不要盲目大规模抓取所有用户的 starred repos。更推荐从 Starcat 收录的 repo 反向抓 stargazers，再做局部图谱。

### 7.4 Watchers / subscribers

GitHub 有 watchers/subscribers 相关数据，但 star 是更强、更常见的“喜欢/关注”信号。早期建议优先使用 stargazers。

### 7.5 Forks

Fork 可以表示更强的开发意图：

```text
fork > star
```

但 fork 也可能只是临时修改、备份或自动化行为。因此可以作为辅助权重，不建议作为主要推荐信号。

### 7.6 Issues / PR / contributors

这些数据能表达更强参与度：

| 行为 | 推荐意义 |
|---|---|
| 提 issue | 关注/使用过 |
| 提 PR | 深度参与 |
| contributor | 技术相关性更强 |
| discussion | 使用社区重合 |

但这些数据采集成本更高，第一阶段不建议做。

## 8. GitHub API 限流与采集策略

GitHub REST API 有主限流和二级限流。GitHub 官方 rate limit 文档说明：

- 未认证 REST 请求主要限流通常是每小时 60 次；
- authenticated user / OAuth / PAT 请求通常有更高限额；
- GitHub App installation token 通常有基础 5,000 requests/hour，并会受安装规模等影响；
- GitHub 也有二级限流，例如并发、每分钟 point、CPU 时间等约束。

文档：

- https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api

因此，Starcat 不应该试图抓 GitHub 全站，而应该做“局部采集”。

### 8.1 推荐采集范围

优先采集：

| repo 来源 | 是否采 stargazers | 优先级 |
|---|---:|---:|
| 用户收藏 repo | 是 | P0 |
| 用户打开详情页 repo | 是 | P0 |
| GitHub Trending repo | 是 | P0 |
| Starcat AI 分类频道 repo | 是 | P0 |
| Show HN 中的 GitHub repo | 是 | P1 |
| Product Hunt 关联 GitHub repo | 是 | P1 |
| 普通搜索结果 repo | 视情况 | P2 |
| star 太低的新 repo | 暂缓 | P2 |

### 8.2 采集数量建议

不要所有 stargazers 全量抓。按 star 数分层：

| repo stars | 采集 stargazers 数量 |
|---:|---:|
| 100 ～ 1k | 最多 500 |
| 1k ～ 10k | 最多 2,000 |
| 10k ～ 100k | 最多 5,000 |
| 100k+ | 最多 10,000 |

### 8.3 采集任务要求

必须支持：

```text
队列
限速
断点续采
ETag / If-None-Match
失败重试
冷却时间
优先级
去重
```

## 9. Starcat 内部用户行为数据

> 当前范围修订：本节保留候选信号分析，不代表客户端可以采集或上传。首期只贡献匿名公开 Star 全量快照，不上传点击、浏览、AI 分析、标签、笔记、对比、搜索或停留时长。以后扩大字段必须重新完成产品确认、独立同意、隐私披露和删除设计，不能沿用现有开关静默增加。

Starcat 自己的数据比 GitHub stars 更重要，因为它直接反映 Starcat 用户的真实意图。

### 9.1 可以采集的内部行为

| 行为 | 含义 | 推荐权重建议 |
|---|---|---:|
| view_repo | 打开 repo 详情页 | 0.3 |
| preview_readme | 查看 README | 0.5 |
| favorite_repo | 收藏 repo | 3.0 |
| unfavorite_repo | 取消收藏 | -1.0 |
| ai_analyze_repo | 触发 AI 分析 | 2.0 |
| ask_repo_question | 对 repo 提问 | 2.5 |
| add_to_compare | 加入技术选型对比 | 4.0 |
| export_report | 导出报告 | 5.0 |
| click_similar_repo | 点击推荐结果 | 1.5 |
| hide_repo | 不感兴趣 / 隐藏 | -3.0 |
| open_github | 跳转 GitHub | 1.0 |
| open_deepwiki | 跳转 DeepWiki/Zread | 1.2 |

### 9.2 为什么内部行为很有价值？

GitHub star 是公开行为，但它有几个问题：

- 用户 star 可能只是收藏，不代表近期兴趣；
- 用户 star 数据有历史噪声；
- fake stars 会污染数据；
- 大项目会天然共现很多；
- 新项目数据稀疏。

Starcat 内部行为更贴近你的产品场景：

```text
用户不是随便 star，而是在做技术调研、AI 分析、对比和收藏。
```

所以 Starcat 应该把内部行为作为长期核心资产。

## 10. 用户行为数据表设计

> 实施修订：下列 `user_repo_events` 等表是早期通用行为平台草案，不用于当前客户端贡献实现。当前推荐原始表使用匿名 `recommendation_snapshots + recommendation_snapshot_items`，在线 Serving 不读取匿名身份；详见 60/61 文档。

### 10.1 user_repo_events

```sql
CREATE TABLE user_repo_events (
    id BIGSERIAL PRIMARY KEY,
    user_id TEXT,
    anonymous_id TEXT,
    repo_id BIGINT NOT NULL,
    event_type TEXT NOT NULL,
    event_weight DOUBLE PRECISION NOT NULL,
    source TEXT NOT NULL DEFAULT 'starcat',
    session_id TEXT,

CREATE INDEX idx_user_repo_events_user_time

CREATE INDEX idx_user_repo_events_repo_time
ON user_repo_events(repo_id, created_at DESC);

CREATE INDEX idx_user_repo_events_type_time
ON user_repo_events(event_type, created_at DESC);
```

字段说明：

| 字段 | 说明 |
|---|---|
| user_id | 登录用户 ID，可以为空 |
| anonymous_id | 匿名设备 ID，用于未登录用户 |
| repo_id | GitHub repo 数字 ID |
| event_type | 行为类型 |
| event_weight | 行为权重 |
| source | starcat/github/imported |
| session_id | 一次使用会话 |
| referrer_repo_id | 从哪个 repo 推荐点击过来 |
| metadata | 额外上下文 |
| created_at | 事件时间 |

## 11. 用户行为如何进入推荐算法？

### 11.1 第一种：不训练，直接加权排序

用户行为可以直接作为排序特征：

```text
score =
  0.65 * content_similarity
+ 0.10 * topic_overlap
+ 0.05 * language_match
+ 0.05 * activity_score
+ 0.05 * log_stars
+ 0.10 * starcat_behavior_score
```

其中：

```text
starcat_behavior_score =
  收藏次数
+ AI 分析次数
+ 加入对比次数
+ 推荐点击次数
- 隐藏次数
```

这仍然不需要训练。

### 11.2 第二种：co-star / co-favorite 共现统计

可以计算：

```text
repoA 和 repoB 被多少相同用户收藏/点击/分析过？
```

公式：

```text
co_behavior_score(A, B) =
  common_users(A, B) / sqrt(users(A) * users(B))
```

这也不一定叫训练，更像离线统计。

### 11.3 第三种：训练 ALS / LightFM

当行为数据足够多后，构建矩阵：

```text
user_id × repo_id = behavior_weight
```

示例权重：

```text
view_repo: 0.3
favorite_repo: 3.0
ai_analyze_repo: 2.0
add_to_compare: 4.0
hide_repo: -3.0
```

然后训练 implicit ALS：

```python
import implicit
from scipy.sparse import coo_matrix

matrix = coo_matrix((weights, (user_indices, repo_indices)))

model = implicit.als.AlternatingLeastSquares(
    factors=128,
    regularization=0.05,
    iterations=30,
    alpha=40
)

model.fit(matrix)
repo_vectors = model.item_factors
```

训练产物：

```text
每个 repo 一个行为向量
```

这些行为向量可以写入 Qdrant 的单独 collection：

```text
repo_behavior_als_v1
```

## 12. 用户行为数据的隐私与合规

Starcat 应该默认遵守最小采集原则。

### 12.1 建议采集原则

| 原则 | 做法 |
|---|---|
| 最小化 | 只采推荐需要的事件 |
| 可关闭 | 设置里提供关闭个性化推荐/匿名统计 |
| 可删除 | 用户可以清除本地行为和服务端行为 |
| 匿名化 | 未登录使用 anonymous_id，不采个人身份信息 |
| 聚合优先 | 推荐训练尽量使用聚合数据 |
| 明示用途 | 说明行为数据用于推荐和产品改进 |

### 12.2 不建议采集

不要采集：

- 用户本地私有仓库路径；
- 私有仓库代码内容；
- 私有 GitHub token；
- 用户输入给 AI 的完整敏感内容；
- 系统层面的无关行为；
- 精确地理位置。

### 12.3 GitHub 授权注意点

如果 Starcat 要读取用户 GitHub stars，应该：

- 明确说明用途；
- 使用最小 scope；
- 优先使用 GitHub OAuth / GitHub App；
- 不把 token 传给第三方服务；
- 支持用户撤销授权。

## 13. 推荐的落地路线

### 第 1 阶段：完全不训练

目标：最快上线。

```text
repo metadata
README summary
embedding
Qdrant search
Similar Repositories UI
```

特点：

- 不采 GitHub stargazers；
- 不训练推荐模型；
- 对新项目友好；
- 实现成本低。

### 第 2 阶段：采集 Starcat 内部行为，但不训练

目标：让推荐更贴近用户真实意图。

```text
view / favorite / analyze / compare / hide
    ↓
行为计分
    ↓
排序加权
```

### 第 3 阶段：采集局部 GitHub stargazers，做共现统计

目标：加入“开发者兴趣相似”信号。

```text
repo stargazers
    ↓
共同 stargazer
    ↓
repo_similarity_edges
    ↓
推荐结果增强
```

### 第 4 阶段：训练 ALS / LightFM

目标：接近 SimRepo 的行为向量推荐。

```text
GitHub stars + Starcat 行为
    ↓
user-repo matrix
    ↓
ALS / LightFM
    ↓
repo behavior vectors
    ↓
Qdrant behavior index
```

### 第 5 阶段：混合召回 + 排序模型

目标：成熟推荐系统。

```text
内容向量召回
行为向量召回
topic 召回
GitHub 共现召回
Starcat 个性化召回
    ↓
Learning-to-Rank
    ↓
最终推荐列表
```

## 14. 最终结论

你的理解没有错：

> 如果 Starcat 只是基于 README、description、topics 做 embedding，然后写入向量数据库查询相似 repo，确实不存在“训练推荐模型”。

我前面说的“训练”是指：

> 当 Starcat 想从“内容相似”升级到“开发者兴趣相似”时，首期只基于用户主动贡献的匿名公开 Star 集合和 GH Archive WatchEvent，训练轻量协同过滤模型，生成 repo 行为向量。点击、AI 分析、加入对比等信号不在当前采集范围。

因此，Starcat 推荐系统最合理的路线是：

```text
1. 内容向量检索：不训练，最快上线
2. 时间衰减 co-star：先得到高置信可解释边
3. Metric Learning：用 `EmbeddingBag(mean) + MultiSimilarityLoss` 学习全局行为向量
4. 内容向量：覆盖新 repo 和行为长尾
5. 动态混合：按行为置信度融合，并用 MMR 控制重复
```

这条路线既能快速落地，又不会浪费后续沉淀的用户行为数据。
