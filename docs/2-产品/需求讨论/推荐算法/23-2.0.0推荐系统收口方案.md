## 1. 交付目标与范围

2.0.0 的目标是把已有自研推荐能力收口为可持续更新的产品，而不是重新立项训练服务。

| 入口 | 用户问题 | 2.0.0 目标 |
| --- | --- | --- |
| 探索 → 为你推荐 | 我收藏的项目之外，还有哪些值得关注？ | 根据多个兴趣种子返回未 Star 的公开项目，支持分页、筛选与不感兴趣反馈 |
| 详情页 → 相似项目 | 有没有与当前项目用途接近的替代或关联项目？ | 使用当前公开仓库作为种子，完成第三方推荐源替换 |

两个入口共用候选库、模型发布、仓库元数据、推荐理由、缓存基础与错误处理；请求上下文和结果展示语义分别定义。

本期不做：

- 新建推荐 API 服务或第二份 Raw 数据湖。
- 把完整用户画像、私有仓库或行为日志上传到推荐服务。
- 把匿名训练贡献设为使用推荐的前提。
- 实时在线训练、复杂用户画像平台、自动 Star 或自动写入标签。
- 为等待 Metric Learning 而延后可用的自研首版。
- 将每日热点内容混入仓库相似度排序；热点另有内容接入方案。

## 3. 产品行为

### 3.1 为你推荐

- 在探索区域设置独立入口，使用现有仓库列表、详情页、Star 操作和全局筛选能力。
- 从本地已同步的公开 Stars 选择代表性种子，同时覆盖近期兴趣与长期兴趣。
- 默认排除完整已 Star 集合和本地不感兴趣集合；推荐结果不会自动加入知识库。
- 提供“换一批”，继续寻找尚未展示的候选；候选耗尽时明确说明，不将相同项目重新排序伪装为新一批。
- 卡片显示可核查的简短推荐理由，复用普通仓库卡片的布局和信息密度。
- 没有公开 Stars 时展示冷启动提示，可引导浏览发现分类；不能把热门列表标成个性化推荐。
- 有种子但模型覆盖不足时明确显示“暂时没有足够的推荐”，仍允许稍后重试。

### 3.2 详情页相似项目

- 只以当前公开仓库的 ID 请求相似候选；私有仓库不向推荐端发送 ID。
- 默认排除当前项目，标出候选中已 Star 的项目，保持“查看替代与关联项目”的用途。
- 若提供“隐藏已 Star”开关，复用与主推荐入口相同的完整本地排除逻辑；默认行为不混淆。
- 相似度不足或当前仓库尚未入模时显示明确空态，不静默调用旧第三方接口填满卡片。
- 自研结果验收前保留现有路由；完成切换后不把第三方请求当作长期兜底。

### 3.3 共同展示约束

- 空态、缓存状态、错误、候选不足分别表达，不把请求失败写成“没有相似项目”。
- 推荐理由说明依据；原始算法分数不显示为“匹配概率”或“百分之多少用户喜欢”。
- 新文案补齐全部 18 种语言，窄中栏下保持单行按钮和稳定工具栏。
- 分页继续使用项目统一的 `ListPaginationPolicy` 与 `automaticListPagination`。

## 4. 隐私：推荐查询与训练贡献分离

| 路径 | 允许的数据 | 约束 |
| --- | --- | --- |
| 推荐查询 | 当前仓库或少量代表性公开仓库 ID、分页和公共筛选条件 | 用于本次计算，不写入训练样本，不关联 GitHub 用户身份 |
| 匿名贡献 | 用户明确开启后，按 Collection 契约提交公开 Stars 快照 | 默认关闭，独立授权；关闭后停止后续贡献并清理本地待发送项，不影响推荐可用性，也不新增服务端历史删除能力 |
| 本地状态 | 全量 Stars、排除集合、兴趣分桶、反馈、账户缓存身份 | 留在本机，用于选种子、过滤及缓存失效 |

不上传 GitHub Token、GitHub 用户标识、私有或内部仓库、私人笔记、标签、搜索或点击日志、客户端 README / 代码内容、AI 对话与 RAG 内容。

推荐服务凭据只用于既有服务鉴权，不携带 GitHub 凭据，也不作为训练主体 ID。公开仓库 ID 的组合仍可能反映兴趣，请求体不写普通访问日志，不建立长期用户画像；个性化查询缓存使用 private 策略。

本期“不感兴趣”仅在本地过滤，不把反馈作为负种子上传。现有 negative seeds 能力保留为服务端接口事实，启用客户端上传需另行定义知情说明和数据边界。

服务器内容特征来自其独立获取的公开仓库元数据及允许使用的公开文本；这不构成读取客户端知识库或私有内容的授权。

## 5. 多兴趣种子选择

首版在客户端完成选择，不要求服务端知道“这个用户是谁”。

1. 读取当前账户完整已 Star 集合，只保留确认公开且 ID 有效的仓库；公开状态未知的不作种子。
2. 使用本地公开 metadata 的 topics、语言和 Star 时间形成兴趣分桶；不上传标签、笔记或分桶结果。
3. 分别保留近期与长期候选，从不同兴趣桶轮转取样，避免只取最近 20 个或 Stars 最高的 20 个。
4. 对近似重复的上游 / Fork 限制种子占比，保留有独立用途的 Fork，不全局删除 Fork。
5. 最多选 20 个不同公开 ID；不足时按实际数量请求，不用不相关仓库补足。
6. 固定输入下保持稳定选择；策略变更通过 `seed_policy_version` 使旧查询缓存失效。

初版采用分桶配额和稳定轮转，不先引入加权种子接口。近期窗口、分桶优先级、每桶上限和配额需在离线样例与小样本体验中确定，写入版本化策略后再上线。

协同候选缺失不等于仓库无价值：候选召回优先补内容相似信号；公开 metadata 不足时保留明确空态。

## 6. 候选库、模型与质量门禁

### 6.1 数据与职责

沿用三方职责：Collection 管匿名贡献，Trainer 管数据处理、训练和评估，Recommend API 只读 Serving 产物提供查询。

- 本地 Raw 继续原地保存，以 Artifact URI、Parquet 和 DuckDB 共享，不复制到新服务或云端。
- WatchEvent 提供公开兴趣行为；它缺少完整 Unstar 记录，不能当作实时 Stars 真值。
- PushEvent 可扩充候选目录，但观察时间不能替代 GitHub 仓库创建或更新时间。
- GitHub metadata 增强限于入选候选及需要补齐的公开仓库，不对全部仓库逐一爬取 Stargazers。
- 数据集保留来源、水位、覆盖区间、去重规则、校验和与质量报告；无法证明完整的数据不标成全量。
- GH Archive 主体与匿名贡献主体不通过真实身份关联；云端 Serving 不包含原始 actor 或用户级关系。

扩容实施遵循 22 号方案：先核对磁盘、内存、spill 与耗时预算，再分阶段放大；规划确认不代表获准执行大规模训练或搬动 Raw。

### 6.2 模型路线

| 阶段 | 方案 | 决策方式 |
| --- | --- | --- |
| 可比较基线 | Popular / SVD / 时间衰减 co-star | 同一数据、同一候选集合、同一时间切分比较 |
| 2.0.0 混合候选 | co-star + 内容向量 + 元数据规则 | 补长尾与无协同边仓库，验证覆盖和相关性 |
| 排序与多样性 | 来源分数校准、兴趣桶平衡、近重复去重 | 保留相关性，不用不相关项目凑满列表 |
| Metric Learning | 与已有基线比较质量、资源、训练和 Serving 成本 | 有实际收益再采用，不作为首版发布前置 |

内容向量模型、输入字段、语言支持、授权与资源预算尚未选定。至少需覆盖公开名称、描述和 topics；是否处理公开 README 另评估抓取、成本与文本安全边界。

无内容特征或内容相似度不足时返回候选不足，不能用 Popular 冒充个性化降级。Popular 用于基线比较及明确标为“热门”的独立发现入口。

### 6.3 评估与晋级

- 固定严格时序 train / validation / test 切分，去除未来信息；缺少可靠时间的记录不进入严格 next-Star 测试。
- 同时报告 Recall@K、NDCG@K、仓库覆盖、长尾覆盖、多样性和重复率，公开样本排除口径。
- 按热门 / 长尾、语言、协同行为充足 / 冷启动、单兴趣 / 多兴趣分别切片，不能只报告整体均值。
- 另做人工小样本相关性核查，记录明显不相关、Fork 重复和理由不成立案例；不引入用户逐项审核流程。
- 对比 Serving 延迟、产物大小、峰值内存和训练成本，先取基线再确定发布阈值。
- 具体数值门槛在实现阶段形成版本化评估配置；本文没有声称任何新模型已经通过门槛。

## 7. 接口、分页与本地完整过滤

### 7.1 现有与拟定契约

| 接口 | 当前契约 | 拟定扩展，待实现 |
| --- | --- | --- |
| `GET /api/v2/repos/{repo_id}/recommendations` | `limit/offset`、ETag、模型版本 | 补统一候选元信息、真实理由与覆盖状态；明确分页模型固定规则 |
| `POST /api/v2/recommendations/query` | 最多 20 个正种子、20 个负种子、500 个排除 ID，单次最多 100 条 | 增加可选 cursor、公共筛选、查询策略版本及批次身份，保留旧请求默认行为 |
| `/api/v1` 旧客户端推荐路由 | 自研结果的临时旧契约适配 | URL、参数、字段及分页语义保持兼容；下一次包含双渠道 v2 切换的 App 版本上线后删除 |

下述字段是拟定设计，不是已有 DTO：`batch_id`、`next_cursor`、`has_more`、`candidate_total`、`coverage_status`、`reason_codes` 和 `evidence`。实施时统一与现有 envelope、错误码和字段命名对齐。

`model_version` 已有；新分页必须同时固定模型版本、种子、过滤条件、排序与策略版本。cursor 是绑定这些条件的不透明校验令牌，不携带本地账户或完整排除集合。

首版无需服务端保存用户会话：可由不可变 Bundle 和确定性排序计算分页。请求条件与 cursor 不一致应明确报错，不能悄悄换查询继续翻页。

### 7.2 已 Star 与不感兴趣必须完整排除

500 是现有服务端请求限制，不是允许用户只有 500 个 Stars，也不是可以截断排除数据的依据。

1. 客户端按当前账户读取完整已 Star 和本地不感兴趣 ID 集合，包含不在当前列表分页中的仓库。
2. 请求代表性公开种子与候选页；不发送完整 Stars 或不感兴趣列表，也不发送私有仓库 ID。
3. 对收到的候选执行本地完整排除、页面内和批次内去重，再填入可见列表。
4. 本地过滤后不足一页且服务端 `has_more=true` 时继续读取下一候选页；必须推进 cursor。
5. 用请求数 / 时间预算约束一次补页循环，预算耗尽时保留已得到的项目并允许继续加载。
6. 服务端候选耗尽才显示当前批次结束；单页全部被过滤不能直接判定整个推荐为空。

不得把排除列表切成多次独立推荐请求再拼接：那会破坏全局排序、分页和去重，也无法证明所有已 Star 都被排除。

### 7.3 筛选与计数

- 语言、许可证等公共条件优先在服务端排序和分页前执行，沿用主窗口多选及未知值语义。
- 服务端没有某字段时，需先补候选 metadata 或明确该条件不可用；不能把“当前页过滤”冒充全量筛选。
- 若保留本地特有筛选，按同样的补页机制遍历候选，不能将局部结果总数标成精确总量。
- `candidate_total` 仅代表本批次服务端过滤后的候选数量，不等于排除全部已 Star 后的用户可见总量。
- 候选未遍历完时展示“已加载 N 项”，或只展示实际已加载数量；全部遍历后才能得到精确可见总数。
- 筛选、账户、种子、Stars 或反馈变化时重置分页身份，取消旧请求，迟到响应不得追加到新列表。

### 7.4 换一批

“换一批”优先从当前模型和查询条件下继续读取未消费的候选页，本地排除本轮已展示项目，完成后替换可见批次。候选耗尽时可按版本化规则轮转其他代表性公开种子，开始新的查询身份；不能把已耗尽的 cursor 重置后再次展示相同结果。

已展示集合仅用于当前推荐会话去重，不等于永久“不感兴趣”，也不上传服务端。换批与刷新分开：刷新重验证模型及数据，换批寻找新候选；新批次请求失败时保留上一批可读结果。没有足够新候选时如实展示数量和状态，不承诺无限换批。

## 8. 缓存与模型切换

既有单仓磁盘缓存、ETag 重验证和模型变化重载第一页继续复用，不能为多种子另造一套互不兼容的缓存状态机。

拟定缓存身份包括：

- 服务地址与 API 契约、入口类型、查询 / 排序策略版本。
- 单仓 ID 或规范化种子集合及种子策略版本。
- 公共筛选、排序、cursor / 批次身份及实际模型版本。
- 客户端账户作用域、Stars 修订号、反馈修订号及本地筛选版本。

本地账户身份与修订号只用于本机隔离，不发往服务端；key 不含 Token。展示理由采用可本地化代码，语言切换无需重训练。

Stars 或反馈发生变化时立即重新执行本地过滤，旧卡片不能继续显示刚 Star 或刚屏蔽的项目；同时使对应批次失效，新请求完成前可保留重新过滤后的快照。

服务端缓存按模型版本、规范化公开查询与分页条件隔离。多种子 POST 不依赖 HTTP 自动缓存，应由已有业务缓存统一管理，并限制容量及保留时间。

翻页中模型切换时：能继续读取原不可变模型则完成该批次；旧模型已退役则返回明确版本过期结果，客户端重载第一页。不得混入新模型后续页，也不得先清空可用缓存再发起请求。

离线或刷新失败保留同账户、同条件的旧缓存并标注状态；没有缓存时展示可重试错误。模型回滚同样以版本变化处理，不把回滚后的结果和旧批次拼接。

## 9. 推荐理由与证据

| 理由类型 | 可用证据 | 不允许的表达 |
| --- | --- | --- |
| 共同兴趣 | 当前种子与候选的真实共 Star 聚合信号 | 未计算过的“与你相似的用户都喜欢” |
| 内容相似 | 实际使用的公开描述 / topics 向量及相似度来源 | 根据项目名称凭空推断业务用途 |
| 多兴趣命中 | 命中的公开种子及其参与排序的信号 | 明明只有单一语言匹配却声称覆盖所有兴趣 |

返回可验证的种子 ID、信号类型和模型版本；涉及聚合行为时遵循数据最小化与现有隐私阈值，不返回原始用户信息。无足够证据则用中性的“相关项目”，不生成虚构理由。

新算法的展示分数需校准后沿用既有 `display_score` 语义，不能把不同来源 raw score 直接相加再展示成百分比。

## 10. 自动更新与替换第三方

### 10.1 更新编排

建议初始节奏为每日更新公开数据、每周训练候选模型；这是待实现的默认方案，之后根据实测成本和数据增量调整。

顺序固定为：输入校验 → 特征与候选生成 → 训练 → 离线评估 → Bundle 校验 → 上传 → 小流量验证 → 原子激活。

- Bundle 包含模型版本、数据水位、策略版本、校验和和评估摘要；Serving 只接收仓库级安全产物。
- 训练超时、评估未达门槛、下载不完整、校验失败或加载失败均保留当前活动模型。
- 激活成功后保留可回滚的旧版本；旧版本保留策略需覆盖分页生命周期，过期行为必须明确。
- 更新任务记录阶段、产物和失败原因；不向客户端泄露训练文件路径或原始数据。
- 不从客户端访问家庭训练机，不把训练和大规模特征计算放进在线请求。

### 10.2 双渠道与旧客户端

先以同一候选集验证 v1 适配与 v2 自研服务，再完成 App Store / Direct 客户端统一；Direct 已选 v2 不能代替两渠道验收。

旧客户端继续请求既有 `/api/v1` 地址，由服务端适配层转换自研结果。它是保留公开契约，不是长期维护两个推荐数据源。

**2026-11-03 收口授权**：dong4j 明确要求下一次包含双渠道 v2 切换的 App 版本上线之后删除 v1 推荐兼容逻辑。后端部署或本地构建不等于 App 已上线；删除范围是 v1 推荐路由、适配 Handler 及其兼容测试和统计说明，不包含 `/api/v1/ping` 等公共路由。执行清单登记于 `supports/starcat-recommend-api/TODO.md`。

完成质量、缓存、错误和旧客户端验证后移除 SimRepo Provider、配置与秘密依赖；以自研模型回滚作为恢复路径，不依赖第三方回切维持可用性。

## 11. 实施阶段与验收

| 阶段 | 工作 | 出口证据 |
| --- | --- | --- |
| A：现状核验 | 确认生产活动模型、输入水位、覆盖与资源预算 | 有版本和时间的运行证据，不复用历史数字冒充现状 |
| B：候选与模型 | 扩容、内容冷启动、基线比较、理由证据 | 同数据质量报告，冻结候选策略与门槛 |
| C：契约与客户端 | 稳定批次分页、多兴趣种子、完整本地排除、筛选计数和缓存 | API / 数据 / 状态测试与入口行为一致 |
| D：替换与运维 | 自动更新、原子激活、回滚、v1 适配、双渠道切换 | 旧客户端回归、失败演练、两渠道构建与界面验收 |

主要影响现有 `starcat-recsys-trainer`、`starcat-recommend-api`、`RecommendAPI`、`RecommendationContextService`、推荐入口与筛选状态。Collection 不承担在线推荐；仅在贡献契约需要调整时单独评估。

需要持久化本地反馈或批次状态时，实施阶段核对已发布 schema 并分配追加迁移；本文不预占迁移编号，不回写已发布建表 SQL。

| 场景 | 必须验证的结果 |
| --- | --- |
| 超过 500 个已 Star，含列表未加载项目 | 为你推荐中零已 Star 漏出，私有 ID 未上传 |
| 少量 / 无公开 Stars、只有私有 Stars | 合理选种子或明确空态，不伪造个性化推荐 |
| 多兴趣与长尾 / 新仓库 | 不被单一热门兴趣挤占；内容召回有依据，缺覆盖明确 |
| 整页候选被本地排除 | 推进 cursor 补页，有限预算，无无限循环或过早结束 |
| 换一批、候选耗尽与换批失败 | 不重复展示当前会话已见项目，不重排旧项目冒充新批次，失败保留上一批 |
| 许可证多选、语言切换筛选 | 分页重置，计数口径正确，无旧条件结果混入 |
| 翻页期间换账户、Star、取消 Star、屏蔽 | 完整集合及时更新，迟到响应隔离，缓存不串账户 |
| 翻页期间模型升级 / 回滚 / 退役 | 同批次版本一致，必要时回到第一页并保留可用快照 |
| 离线、服务失败、无活动模型 | 旧缓存可读或明确错误，不误报空列表 |
| 自动训练 / 上传 / 激活任一阶段失败 | 活动模型不变，恢复或回滚可执行 |
| 旧客户端 v1、Direct 与 App Store | DTO / 分页兼容，两渠道均验证自研来源 |
| 18 种语言与窄中栏 | 文案真实翻译，工具栏、按钮及理由布局稳定 |

本方案完成的是范围与实施约束。模型选择、阈值、资源预算、分页预算及缓存保留时间由实施证据确定；功能完成以以上验收结果为准。
