# 自研推荐后续优化计划

> 日期：2026-11-03。
> 性质：基于 v19 / v20 交付结果提出的后续实施建议。本文件不代表已启用自动训练、已实施新算法或已授权新的部署。
> 本轮仅整理计划和博客，不修改业务代码、模型、生产配置、总览或更新日志。

## 1. 当前基线

> 2026-11-10 实施补充：已新增 Studio 每周日 11:00 的本机训练编排与登录补跑，固定 v20 配方，满足同输入新旧模型质量、覆盖和接口门槛后自动发布；样本不足时保留线上模型并积累留出数据。原始规划与当时状态保留在下表，具体配置、5000 主体等门槛和恢复方式见 [每周自动训练运维指南](../../../../supports/starcat-recsys-trainer/docs/每周自动训练运维指南.md)。

| 能力 | 已验证状态 | 尚未解决 |
| --- | --- | --- |
| 行为推荐 | v19：时间衰减共现与内容排名融合，通过独立主体确认门槛 | 近期行为稀疏、热门偏置、事后 metadata 偏差 |
| 目标目录 | v20：18,839 个公开候选，保留 1,350,586 条预计算边 | 远未覆盖全部 GitHub；存在活跃度、语言和 Star 门槛偏差 |

质量数字固定引用 v19 确认集：8,395 个训练外主体，Recall@20 0.035086、NDCG@20 0.013851；相对同输入 support2 基线提升约 38.9% / 27.9%。这是已观察时间窗口上的新增主体确认，不是未知前瞻测试。生产最终重训版本引用重训前评估，v20 未新增行为质量结论。

## 2. 第一优先级：形成可持续的数据与训练闭环

### 2.1 先做增量数据与周期重训

建议初始节奏为每日补数据、每周训练候选、每月做一次完整对账。具体频率在记录耗时、扫描量、磁盘和收益后调整，不把日历到点等同于必须切模型。

1. 每日计算最新完整 UTC 日期，复用已有 WatchEvent `catch-up`。PushEvent 使用自己的 checkpoint 与预算检查，缺少的日常调度单独补齐，不能直接假定具备同名入口。
2. 校验分区 schema、行数、checksum、连续日期及事件身份。保留 Raw，只为新增或受影响分区生成新的 Canonical 快照；不能追加后直接修改旧实验的输入。
3. 分别记录 `raw_watermark`、Canonical 截止时间、metadata 快照时间、评估窗口与生产模型水位。上游缺日时保留旧 active，明确显示停在哪一层。
4. 每周冻结输入、配置、源码摘要和评估协议，构建候选；同输入重训基线，避免把新增数据收益全部算作算法收益。
5. 通过离线门槛、Bundle 校验、隔离 API 与生产影子验收后，才切活动版本。失败保留旧模型与失败证据，不自动放宽门槛。

下载涉及 BigQuery 时继续遵守扫描预算和额度检查。本计划不执行收费查询，也不建议重新下载全部历史。

### 2.2 暂不直接累加线上推荐边

数据增量、模型增量与 Bundle 增量是三个独立问题。

当前共现模型包含主体准入、仓库截断、时间衰减、支持度与 Top-K；新增 Star 可能改变主体入选记录和旧边排序。TF-IDF 的 IDF 又依赖整个拟合目录。仅将新边追加到当前 SQLite，不能保证等价于固定输入完整重训。

首期每周重训有界 Dataset，产出完整不可变 Bundle；线上继续只读模型。若以后成本成为瓶颈，再评估：

- 保存可重放的主体—仓库首次关系与边的充分统计；对受影响主体先撤销旧贡献，再计算新贡献，不能只加不减。
- 时间衰减采用固定参考时刻，明确旧贡献如何随时刻变化。
- 用相同截止时间的完整重训对照增量产物，检查边、排序、质量和耗时误差。
- 大模型只传输变化分片，但按完整版本原子激活；传输优化不改变训练语义。

只有证明等价或误差可接受，并确实节省资源后，才引入这些复杂度。

### 2.3 增加数据源质量监测

上游 GH Archive issue #320 有使用者报告近期 WatchEvent 采集率下降，分析基于两个项目；这是风险线索，本项目尚未独立验证其比例或全站代表性。不能用“本地分区连续”证明“上游已采到全部 Star”。

建议固定一批不同规模、语言和年龄的公开项目，按月对照事件量与公开 Stargazers 样本，记录差异和不可比因素。Stargazers 是当前仍保留 Star 的集合，历史事件包括后来取消 Star 的行为，两者不应要求逐条一致。监测目的是发现突变，不据此制造缺失事件或擅自重加权。

用户默认关闭的公开 Star 贡献保持独立 opt-in，不能因为数据稀疏而扩大收集范围。PushEvent 可补目录和活跃线索，不能直接把开发者 Push 当成用户喜欢某仓库的等价标签。

## 3. 第二优先级：分别扩大源覆盖与目标覆盖

### 3.1 可查询的源项目

建立固定验证集，覆盖目录内有边、目录内无边、目录外公开项目、中文描述、无 topics、新项目及不可用来源。分别报告有依据的非空率、弱关联率、错误率和延迟，禁止以“全部返回列表”为唯一目标。

目录外 metadata 缓存继续带内容快照身份；描述更新后，分页与 ETag 必须跟随实际快照。上游失败保持可重试错误，不写成永久空结果。

### 3.2 可被推荐的目标项目

建议先将候选预算由约 1.9 万扩大至 3 万，再依据质量与资源结果决定是否试 5 万；这些是实验预算，不是已完成数量或放行条件。

补充来源优先使用已采集的 PushEvent 目录、已有公开 metadata 缓存、合法的近期公开项目发现来源，以及单仓查询中暴露的候选缺口。按语言、年龄、支持度与活跃度分层，给低 Star 新项目独立配额，不统一要求更高 Star 数。

只保存公开项目级缺口统计，避免从查询日志重建用户完整 Stars。对每个候选保留来源、观察时间、metadata 快照和有效状态。

每次扩容要重测目录内/外真值损失、内容索引大小、构建耗时、在线 P95 和热门偏置。新增 metadata 候选不等于新增了足够的行为训练信号；行为目录扩容需独立对照。

## 4. 第三优先级：提高相关性并减少重复

### 4.1 先补可信的内容评估集

建议建立 200～500 个公开源项目的固定相关性评估集，区分替代方案、互补工具、同生态项目与不相关项目。兼顾语言、新旧项目和流行度，保留每个候选的标注理由；AI 可以辅助初筛，不能把它生成的标签直接作为唯一质量真值。

历史 Star 留出反映后续关注行为，并不直接等于“这个仓库的相似项目是否合适”。因此行为评估与单仓相关性评估分开。

### 4.2 比较语义内容表示

保持现有 TF-IDF 为可复现基线，离线比较多语言 embedding；只使用公开名称、描述、topics 等已允许字段，扩展 README 范围需另行确认。固定模型版本与文本摘要，按变化项目增量编码。

候选生成可比较共现、TF-IDF、embedding 及排名融合。不要默认所有查询统一增加内容权重；先看共现充足、稀疏和目录外切片，再在 validation 选定少量规则并冻结确认。

Metric Learning 或双塔放在这些基线之后。只有同预算、同数据与同评估下有稳定收益，才增加训练和部署复杂度。

### 4.3 重排与分数解释

先排除自身、重复 ID 和失效项目，再比较 Fork / 镜像识别、热门惩罚与 MMR 多样性。默认过滤不得错误删除真正不同的替代项目，每一步都要有消融。

共现、余弦相似度和展示分数不等于“用户喜欢概率”；不能将 99% 匹配度写成 99% 准确率。推荐理由只能来自实际使用的信号。

## 5. 评估与放行

后续训练前冻结新窗口与门槛，停止使用已经反复观察的 2026 年 10 月确认集调参。下一轮优先累积尚未用于选型的完整日期数据；数量不足时延后质量结论，不能把当前未完成月份称为完整测试集。

建议统一输出：

| 维度 | 指标 / 检查 |
| --- | --- |
| 行为质量 | Recall@20、NDCG@20、MRR、同主体配对区间 |
| 覆盖 | 源非空率、实际目标覆盖、目录外真值损失 |
| 分群 | 热门 / 长尾、新旧项目、语言、历史长度、训练主体内外 |
| 相关性 | 单仓标注集的相关比例、重复比例、明显不相关案例 |
| 工程 | 完整 / 增量耗时、资源、API P50/P95、冷缓存、错误率 |
| 可信度 | 输入与协议摘要、metadata 时点、refit 指标引用范围 |

具体阈值应在查看下一轮候选成绩前冻结。本计划不根据当前分数事后制定新放行条件。数据门禁失败不训练；质量证据不足不自动晋级；业务验收失败不激活。

## 6. 产品化与实施顺序

| 顺序 | 建议交付 | 完成判断 |
| --- | --- | --- |
| A | 增量水位、来源异常监测、每周候选编排 | 失败可恢复、不重下载已验证历史、旧模型持续可用 |
| B | 分层目录扩容与固定相关性评估集 | 扩容收益、目录损失、资源与弱关联均可量化 |
| C | 多语言内容候选与去重 / 多样性重排 | 同输入对照和新确认集通过，不牺牲主要分群 |
| D | 多 seed 内容补充与“为你推荐” | 有权重与排除规则、分页版本一致、账号缓存隔离 |
| 发版后 | 删除 v1 推荐兼容层 | 包含双渠道 v2 切换的新版 App 已实际上线 |

“为你推荐”保留代表性公开种子预算；完整 Stars 排除与不感兴趣反馈先在本地处理。新增点击或反馈上传不属于现有贡献授权，不能默认采集。
