Starcat 是我开发的一款原生 macOS GitHub Star 管理应用。整理收藏之外，我一直想补上一个能力：打开某个项目时，能顺手找到用途接近、值得继续了解的其他项目。

最初，这个功能接的是第三方相似项目接口。它能让我很快做出产品，但随着 Starcat 进入 2.0.0 的开发阶段，我需要回答更多问题：为什么推荐这几个项目？新项目什么时候能被收录？接口返回空结果，是项目缺少关联，还是根本不在数据目录里？

这篇文章记录我把推荐能力收回自己维护的过程。数据处理到 2026 年 10 月 31 日，本文记录的交付完成于 11 月 3 日：自研推荐 API 已部署，旧接口内部也已切换到同一套自研数据；Direct 和 App Store 的新代码统一使用 v2，但这次没有发布新版 App。

当前用的是时间衰减共现与 TF-IDF 内容推荐。原先设想过的 Metric Learning 还没有进入生产。

## 一、为什么要自己做推荐

第三方接口适合验证需求。相似项目入口、弹出列表、项目卡片和详情跳转，都可以先跑起来。真正让我决定自建的，是后续迭代需要掌握数据和排序。

首先是覆盖。用户打开一个仓库却看不到推荐，我需要知道问题出在数据采集、候选目录，还是排序。这些环节在外部服务里不容易核实，也无法由我直接修复。

其次是更新。GitHub 的项目变化很快，旧的行为可以帮助认识成熟生态，却不一定能及时反映一个最近才出现的工具。自建以后，我可以分别记录原始数据、元数据和生产模型的更新时间，知道新信息卡在哪一层。

还有产品方向。详情页的“相似项目”只需要一个源仓库；之后想做的“为你推荐”，需要组合多个兴趣种子，排除用户已经收藏的项目，并处理“不感兴趣”等反馈。我希望这两个入口共用推荐底座。

这也影响了隐私设计。推荐查询只需要代表性的公开仓库 ID，完整收藏排除和个人反馈可以先在本地处理。训练贡献则是独立、默认关闭的授权，不能因为用户点开推荐，就把他的收藏用于训练。

自建意味着要自己承担下载、清洗、训练、验收和运维成本。我的目标是让这套系统可以解释、复现，并且能根据 Starcat 的实际问题继续改。

## 二、系统怎样设计

### 用共同收藏建立项目之间的关系

行为模型的起点很朴素：如果很多人同时 Star 了 A 和 B，A 与 B 可能有某种关联。

它可能是替代关系，也可能是同一生态里的配套工具。例如，模型推理项目和推理服务框架经常出现在同一个人的收藏里，但两者用途并不相同。所以共现能提供推荐线索，不能直接当成严格的“功能相似”标签。

直接累计共同收藏次数也不够。热门仓库容易出现在所有列表中，收藏量特别大的账户还会产生大量项目配对。我给模型加了几项限制：

- 对旧行为做时间衰减，当前实验使用 365 天半衰期，让近期信号有更大影响。
- 对每个主体参与共现配对的仓库数量设置上限，相关对照中使用 cap100。
- 对低支持度关系做收缩，避免少数偶然共现得到过高分数。
- 设置严格的配对预算，只保留每个源仓库的 Top-K 结果。

这里的“主体”是训练数据里按来源区分的行为身份。不同来源的身份不能仅凭一个相同字符串就合并，线上模型也不需要携带这些身份。

训练侧用 Python、DuckDB 和 Parquet 处理数据，服务侧使用 Go。计算量大的部分离线完成，API 主要读取已经生成好的结果。

### 用公开内容补没有共现边的项目

共现模型有一个直接的限制：一个项目没有足够的行为，或者没有进入训练目录，就很难得到推荐。

为此，我加入了内容模型。它读取公开仓库的名称、描述、topics 和语言，将这些字段转换成 TF-IDF 向量，再检索相近项目。topics 和语言做了字段加权，向量归一化后用点积计算相似度。

TF-IDF 适合用作第一版基线：输入明确、训练便宜，也便于检查某个词为什么影响结果。它的不足同样明显，跨语言描述和用途接近但措辞不同的项目，未必能匹配好。

v19 的选型结果是共现与内容的排名融合，内容权重为 25%。这个比例用于排名融合，不表示“推荐有 25% 的概率来自内容”，也不是对用户喜欢概率的估计。

### 在线查询分成三条路径

v20 保留了 v19 已经验证的预计算结果，并补上内容冷启动。单仓接口按以下顺序处理：

1. 源项目有预计算推荐边，就返回这些结果。
2. 没有出边，但源项目在模型目录里，就使用目录中的 metadata 查询内容索引。
3. 源项目不在目录里，就由服务端按公开仓库数值 ID 补充 GitHub metadata，再检索已有候选。

第三条路径扩大的是“能拿来发起查询的项目”范围。推荐目标仍来自模型候选目录，不能据此说已经覆盖整个 GitHub。

如果项目私有、已删除、不可用，或者内容不足以形成有效查询，就不伪造推荐。上游临时失败也要返回可重试错误，不能保存成一个长期有效的空列表。

### 模型作为不可变产物发布

训练结束后，结果被封装成不可变 Bundle，包含清单、校验信息和 Serving 数据。线上服务读取 Bundle，不在用户查询时重新训练。

每次发布都对应明确的模型版本。分页和 ETag 绑定这个版本；对于目录外内容查询，还要加入源 metadata 的摘要。否则，用户翻页期间模型或描述发生变化，就可能看到重复、遗漏，或者错误命中旧缓存。

新版本先经过文件校验、隔离 API 验收，再激活。旧 Bundle 保留作回退，训练进程失败不会直接破坏正在服务的版本。

## 三、用了什么数据，规模有多大

### 主要行为来自 GH Archive WatchEvent

GH Archive 将公开 GitHub 事件按小时归档。Starcat 使用其中的 WatchEvent 作为公开 Star 行为主信号，因为它有事件时间，可以构建主体—仓库关系，也便于做按时间切分的评估。

这份数据只能代表被归档到的公开行为。Star 表示关注，不一定表示使用或认可；历史 Star 也不等于当前仍保留的收藏。不能把它解释成完整、无偏的用户偏好数据库。

本次还使用了另外几类信息：

| 数据 | 在系统里的用途 | 不能混淆的地方 |
| --- | --- | --- |
| GH Archive WatchEvent | 共现训练、历史留出标签 | 公开关注信号，不是人工相关性标注 |
| GH Archive PushEvent | 仓库发现、目录补充和活动线索 | Push 不等于某个用户喜欢这个项目，不能直接作为 Star 正例 |
| GitHub 公开 metadata | 有效状态过滤、内容特征、目录外查询 | 当前快照可能带来事后信息偏差 |
| 用户主动授权的公开 Star 贡献 | 独立的推荐训练来源 | 当前规模有限，不是本次训练的主要数据量 |

用户标签、笔记、私有仓库和 AI/RAG 内容没有被并入这次训练。

### 五亿条历史记录，最终为何只有两百万条训练关系

本次固定的 WatchEvent Canonical 快照覆盖 2016 年至 2026 年 10 月 31 日，共 511,284,530 行。这里的 Canonical 是标准化后的历史事件输入，不是最终训练样本，也不是五亿个用户。

从事件到模型，要经过身份去重、公开有效目录过滤、训练期支持度筛选、主体抽样、首次 Star 关系合并和历史量准入。修复后的 v18 Dataset 为：

| 层级 | 数量 |
| --- | ---: |
| Canonical 历史事件输入 | 511,284,530 |
| Dataset 主体—仓库关系 | 2,061,840 |
| 时间切分中的训练关系 | 2,060,069 |
| 训练主体 | 59,940 |
| v18 / v19 候选仓库 | 13,638 |

训练主体采用稳定的 2% 抽样，并对历史量设置准入范围。这是在资源预算内建立可重复实验的选择，代价是近期样本和长尾覆盖可能不足。它不是“用了全部历史用户做训练”。

此前 v12 的十年输入统计是 510,104,947 条互动，属于另一个输入快照，不能和本次的 511,284,530 混为同一批数据。

覆盖扩容后的 v20 又形成了另一组规模：

| 产物 | 数量 |
| --- | ---: |
| 可被推荐的公开候选 | 18,839 |
| 相比 v19 新增候选 | 5,201 |
| TF-IDF 词表特征 | 42,657 |
| 内容倒排项 | 278,169 |
| 保留的预计算推荐边 | 1,350,586 |

新增候选来自已有公开 metadata 缓存和有预算限制的 GitHub 公开查询。目录仍然存在语言、活跃度和 Star 门槛偏差；扩容后的 18,839 个候选没有全部获得新的行为训练信号。

## 四、训练了多少次，踩过什么坑

### 先说明“次数”的统计口径

按本次保留在本机的 `gharchive*` 实验产物清点，共有 31 个可审计工作区，其中 12 个留下了推荐边模型产物，合计 41 份推荐边文件；v20 另完成了 1 次内容索引训练。

41 份产物包含 Popular、SVD、co-star 和内容基线，参数消融、融合候选以及最终 refit。它不等于 41 个独立上线版本，也不代表完整记录了每一次中断的调试执行。纯数据重建和没有输出模型的工作区没有算作成功模型训练。

版本号也不能当训练次数：v18 主要修数据，v19 做独立评估与融合选型，v20 重点补覆盖。

### 第一个基线：共现有用，但覆盖很窄

早期在 2016 年全年数据上，我比较过全局热门 Popular、矩阵分解 SVD 和共现 co-star：

| 模型 | Recall@20 | NDCG@20 | 推荐目标覆盖率 |
| --- | ---: | ---: | ---: |
| Popular | 0.04748 | 0.02696 | 0.00421 |
| SVD | 0.03966 | 0.02313 | 0.74669 |
| co-star | 0.06009 | 0.03928 | 0.07074 |

Recall@20 衡量前 20 个结果找回多少留出项目；NDCG@20 还考虑命中项目的位置；覆盖率衡量评估中实际推荐到的不同目标占候选目录的比例。

这组结果让我保留了 co-star 作为行为基线，但也暴露了它的局限：找回行为的能力更好，不代表能推荐更多不同项目。SVD 的覆盖很高，召回却没有在这个实验里获胜。

这些是早期历史实验。后面近期评估的窗口、目录和主体都不同，不能把分数放在一起排总榜。

### 扩容会偷偷改变训练人群

我原本以为，增加候选仓库主要是在增加可推荐的项目。实际跑下来，主体历史量也随目录扩大而变化。

假如某个账户在旧目录里有 180 个项目，在扩容目录里变成 220 个，它就可能触发“最多 200 个”的准入上限，被移出训练。此时新旧模型的差异同时包含目录变化和人群变化，无法判断究竟是哪一项起作用。

后续消融固定了参考目录下的主体准入和权重，保留原关系，再追加新候选对应的记录；对照 cap、支持度等参数时，也尽量一次只变一个因素。

固定人群、cap100、support0.5 的一个消融候选，在两个独立 test 人群上的 Recall@20 分别达到 0.065319 和 0.050986，高于各自对应的 v15、v16。不过旧人群的 MRR 点估计略低于 v15，我没有把它写成全面获胜。

### v17 没过近期检验，停止发布

长窗口实验有收益，不代表近期表现一定更好。v17 用 validation 选定候选后，在 274 个 test 主体上得到：

| 模型 | Recall@20 | NDCG@20 |
| --- | ---: | ---: |
| 同输入 support2 基线 | 0.02189781 | 0.00588230 |
| validation 选出的候选 | 0.01459854 | 0.00445336 |

候选更差，未通过门槛。这次没有继续做最终 refit，也没有靠调整参数反复刷同一份 test，直到找到一组好看的数字。

随后我先查数据。10 月有 241,782 条 Canonical 记录，经过既有目录、支持度、2% 主体抽样和准入后，只剩 291 条 Dataset 关系。单纯把评估器的“最多主体数”调大，无法找回已经在前面被过滤掉的样本。

### 事件 ID 不能单独作为全历史唯一键

审计还发现了去重问题：不同年份出现相同原始事件 ID，但主体、仓库或时间不同。仅按来源与 ID 合并，会把不同事件误认为同一条，甚至让后来的记录覆盖训练期历史。

修复后的 WatchEvent 身份包含：

```text
来源 + 原始事件 ID + 来源内主体 + 仓库 ID + 事件时间
```

完全相同事件的重复观测仍然合并，其他来源和快照数据保持各自语义。我还补了回归，检查增加未来的无关同 ID 事件，不会改变已经冻结的训练历史。

重建后，事件层恢复了 33,209 条，最终 Dataset 却只净增 200 条，从 2,061,640 变成 2,061,840。原因是恢复的事件还要经过目录过滤、主体抽样和首次关系合并；其中一个主体的有效历史量从 200 恢复到 201，又按原规则被排除。

因此，“恢复三万条事件”不能写成“增加三万条训练样本”。这次修复证明的是数据语义更正确，推荐质量要重新评估。

### v19 把训练抽样与评估抽样拆开

训练可以受资源预算限制，但评估不能只能看到训练时那 2% 的人群。

v19 从 Canonical 单独构建评估 Artifact，排除全部训练主体，按冻结的规则抽样。先做容量盘点，再确定样本预算，最终获得 10,000 个 validation 主体，以及 8,395 个训练外确认主体。

每个查询最多使用 20 个代表种子，但排除完整已知历史。主指标保留可确认公开 metadata 中的目录外标签，不把模型无法推荐的目标悄悄删掉。零历史、短历史等群体单独统计，没有混入已经验证的暖启动结论。

候选包括 support2 基线、较低支持度共现、TF-IDF，以及少量固定权重的排名融合。validation 只选出一个候选后，再读取确认集。门槛事先冻结，包括有效人数、相对基线的 Recall/NDCG、同主体配对区间和空结果率。

### 最终确认效果怎样

validation 选中的是 `hybrid_25`，即内容权重 25% 的排名融合。8,395 个训练外主体的确认结果如下：

| 模型 | Recall@20 | NDCG@20 | MRR@20 | 推荐目标覆盖率 | 空结果率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| support2 基线 | 0.025261 | 0.010832 | 0.007035 | 0.046595 | 0.011793 |
| hybrid_25 | 0.035086 | 0.013851 | 0.008389 | 0.161359 | 0 |
| Popular | 0.011779 | 0.005903 | 0.004310 | 0.003669 | 0 |

相对同输入 support2 基线，Recall@20 提升约 38.9%，NDCG@20 提升约 27.9%。同主体配对的 90% bootstrap 区间中，Recall 差异为 `[0.007263, 0.012561]`，NDCG 差异为 `[0.001823, 0.004219]`，均没有穿过零，全部预设门槛通过。

38.9% 是相对提升，不是“推荐准确率 38.9%”。表中的零空结果也只适用于这批评估主体，不能推广成任意仓库都有推荐。

这份结果还有两个边界。10 月时间窗口此前已经观察过，因此它是新增训练外主体的确认，不是真正未知的前瞻测试；metadata 使用当前快照，也存在事后信息偏差。

确认后，我保持相同训练主体和准入权重，将其截至 10 月底的有效记录纳入最终 refit。生产 Bundle 明确标记引用重训前评估，不能把上述分数说成最终重训模型在未知数据上的实测成绩。

### API 可用以后，还要修真实项目的空结果

v19 上线后，一些项目能看到推荐，另一些项目仍然为空。这次主要是覆盖问题，继续调共现参数解决不了目录外源项目。

v20 因此保留全部 1,350,586 条旧边，扩充 metadata 候选并训练内容索引。冻结的 32 个原空结果源，在最终公网复验中全部得到非空结果；5 个旧源的条目、排序和分数保持不变。

这证明覆盖恢复，不证明相关性全面提升。只有名字、缺少描述和 topics 的项目，仍可能命中用途不同但词面相近的仓库。

首次公网验收还遇到过一次 metadata 上游 503，当时立即停止验收，保留失败记录；随后同源恢复，保持相同模型和参数完整复验通过。首次错误的具体原因没有确定，没有把它包装成已经定位并根治的问题。

工程上还处理过百万边 Bundle 构建中的展示分数查询性能问题：补充复合临时索引并检查查询计划，保持分数与排序定义不变。训练完成之外，还要确保产物能构建、能校验、能由 API 稳定读取。

### 这次实际交付到哪里

生产活动模型为 `gharchive-20261031-v20-coverage`。自研推荐 API 已部署，第三方 Provider 和凭据依赖已移除。旧客户端的 v1 只保留响应适配，底层读取同一套自研结果；双渠道新代码统一调用 v2。

验收覆盖单仓、多种子、排除、自推荐过滤、分页去重、模型版本、ETag/304 和鉴权；客户端推荐与缓存测试、双渠道构建也已通过。

这次没有发布新版 App。等包含双渠道 v2 切换的新版实际上线后，再删除 v1 兼容层。

## 五、后面怎样持续改进

### 先把数据更新和模型更新串起来

接下来建议采用每日补数据、每周训练候选、每月完整对账的节奏。这个调度尚未全部接通，不应把已有下载 checkpoint 当成自动重训已经完成。

我会分别记录 Raw、Canonical、metadata、评估窗口和生产模型的水位。某天下载失败，应该知道缺了哪个分区；候选训练失败，旧模型继续服务；指标未过门槛，不自动发布。

第一阶段仍然周期完整重训有界 Dataset，生成新的不可变 Bundle。共现涉及主体截断、时间衰减和 Top-K，TF-IDF 的 IDF 又依赖整个目录，直接向线上数据库追加新边并不等价于重训。

只有当重训成本确实成为瓶颈，再考虑维护可撤销的统计量、局部重算和分片传输，并用同一水位的完整重训验证误差。

数据源本身也要监测。GH Archive 的 issue #320 有使用者基于两个项目报告 WatchEvent 采集率下降。这是需要独立核查的风险线索，不能直接将其中的比例当作 Starcat 全站结论；本地文件连续，也不能证明上游采到了全部 Star。

### 覆盖分两件事做

源覆盖决定“哪些仓库可以拿来查询”，目标覆盖决定“哪些仓库有机会被推荐”。目录外内容查询主要改善了前者。

后续会为不同语言、项目年龄和流行度建立固定切片，再逐步扩大目标目录。可以先以 3 万候选作为实验预算，记录资源和质量变化后，再决定是否试 5 万。这些是待验证预算，不是上线承诺。

扩容要同时看弱关联、延迟和目录外真值损失。只统计返回了多少非空列表，很容易把质量问题藏起来。

### 用相关性评估指导更复杂的模型

历史 Star 留出回答的是“能否找回后续关注行为”，详情页还需要回答“这两个项目为什么相关”。我计划建立 200～500 个公开源项目的固定标注集，区分替代方案、互补工具、同生态和不相关结果。

有了这组基准，再比较 TF-IDF、多语言 embedding 和 Metric Learning。后两项目前都没有上线，是否采用取决于同输入、同预算下的收益。新一轮选型也要使用尚未用于调参的新数据，不能继续反复使用已经看过的 10 月确认集。

重排会逐项比较 Fork/镜像去重、热门偏置校正和 MMR 多样性。每项都保留消融，避免为了“看起来更多样”，把真正相关的结果挤出去。

等多种子内容补充、兴趣权重和本地排除规则完善后，再把这套底座用于“为你推荐”。详情页目前已经能使用自研 API；个性化推荐仍需要单独完成产品和质量验收。
