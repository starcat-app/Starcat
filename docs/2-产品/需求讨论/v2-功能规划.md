  > **v1 现状**：字段已落库；仅 toolbar 菜单项 `externalLinks.homepage` 可打开。

  > **v1 现状**：无；toolbar 仅有「去 Pull Requests 列表页」。
  > **v2 目标**（二选一，开工前拍板）：
  > - **推荐 A**：不单独占格，Issues chip 长按/菜单展开「Issues n · PR m」

  > **约束**：**禁止**塞进 Stars 同步流程；仅详情页 `.task(id: repo.id)` 按需拉取；评估 Search API 30/min 与主限流。
  > **涉及**：`GitHubAPIClient` + 可选 `repo_extra_stats` 缓存层 + hero UI

- [ ] **最新 Release 内联展示（未订阅可见）** — tag + 发布时间 + 可选摘要
  > **v1 现状**：`RepoReleaseStatItem` 仅在**已订阅**时第二行显示最新 `tagName`；未订阅为灰色 “Releases” 文案；toolbar 可跳 Releases 列表页。
  > **v2 目标**（二选一，开工前拍板）：
  > - **推荐 A（最小）**：扩展 `RepoReleaseStatItem`——未订阅也懒加载 `releases/latest`，第二行显示 `vX.Y.Z · 相对时间`（可点跳 GitHub）
  > - **B（完整）**：在 `metaLinksRow` 下方加 `releaseSummaryRow`：`tag · 时间 — body 首行截断`
  > **约束**：与 §4.1 Release 订阅共用 `ReleaseRepository` / 缓存，避免重复打 API；404 显示「无 Release」占位，不报错。
  > **涉及**：`RepoReleaseSection.swift` / `ReleaseRepository` + `RepoMetadataHeaderView.swift`

### 1.3 Hero 布局方案（v2 实施时遵循）

已定型的垂直结构（`RepoMetadataHeaderView`）：

```
header          avatar · full_name · badges · trailingActions
badgeRow        archived / fork / license
inlineTopicsRow
description     （可选）
metaLinksRow    ← Website；可选 Release 摘要第二行
statsSection    ⭐ Forks · ◯ Issues · Watchers · 日期 · 🔔 Release
```

设计原则：

1. **数字指标** → 只进 `statsSection`（与 Stars/Forks 同语言）。
2. **外链/身份**（Website）→ 不进 stats，放 description 与 stats 之间的 `metaLinksRow`。
3. **Release 长摘要** → 不进 stats 单行；优先扩 `RepoReleaseStatItem`，摘要过长时用 `metaLinksRow` 第二行。
4. **独立 PR 数** → 默认合并进 Issues 展示，避免 stats 行在窄窗口挤爆。

与 toolbar 分工：

| 位置 | 职责 |
|------|------|
| Toolbar `ExternalLinksMenu` | 熟练用户快捷跳转 GitHub 子页 |
| Hero 内联 | 扫一眼决策：活跃度、版本、官网 |

### 1.4 v2 最小增量建议（实施顺序）

若分期做，建议顺序：

1. Open Issues 数（数据已有，改动小）
2. Website `metaLinksRow`（纯 UI）
3. 最新 Release 扩展 `RepoReleaseStatItem`（复用 Release 层）
4. 独立 Open PR 数（视需求再定 A/B）

## 3. Weekly 多来源扩展（HelloGitHub、AI 情报与置顶）

### 3.1 最终定位

HelloGitHub 不再作为 Trending 的客户端直连数据源，而是与阮一峰周刊、ZRead、Show HN 一样，由 `starcat-weekly-api` 采集、持久化、调用 GitHub API 补全，再通过统一 Weekly bulk 提供给 Starcat。

本期同时纳入：

- `hellogithub`：crawler 来源，需回填历史月刊并持续增量；
- `ai_intelligence`：人工批量录入来源，由 repo-local skill 把文本解析成真实 `owner/repo` 后调用管理 API；
- Weekly 多项目置顶：通过 weekly-api 管理接口和 `pages/_local-admin` 维护有序置顶列表；
- Starcat Weekly 来源筛选、来源图标、通用来源详情与本地缓存扩展。

### 3.2 固定来源

| 来源代码 | 展示名 | 录入方式 | skill 可写 |
|---|---|---|---:|
| `weekly` | 阮一峰周刊 | crawler | 否 |
| `zread` | ZRead | crawler | 否 |
| `discovery` | Hacker News | crawler | 否 |
| `hellogithub` | HelloGitHub | crawler + 历史回填 | 否 |
| `ai_intelligence` | AI 情报 | batch API | 是 |

来源由 weekly-api 固定目录控制，不能由 skill 或管理请求自由创建。新增来源必须先完成 weekly-api、Starcat、图标、筛选和运维入口，再在后端启用。

### 3.3 后端方向

- 把当前三张来源专属表迁移为通用 `repo_source_events`；
- Collector 和 batch POST 只把候选项持久化入队，不同步调用 GitHub；
- transaction commit 后主动唤醒 Worker，Worker 启动时扫描一次并每 15 分钟兜底扫描；
- Worker 统一负责 GitHub enrich、租约恢复、最多 3 次重试和失败剔除；
- `/api/v1/repos/bulk` 升级为来源目录 + 通用 `source_entries` + 置顶字段；
- HelloGitHub 历史以官方 periodical volume 页面回填，featured API 用于日常增量；
- 管理端提供来源同步、批次状态、批量录入、仓库搜索和置顶原子替换接口。

### 3.4 Starcat 与控制台

- Weekly 来源筛选由 bulk 的来源目录动态生成，不再依赖固定三源 `CaseIterable enum`；
- HelloGitHub 与 AI 情报加入 Weekly 来源图标和详情来源链接；
- `weekly_bulk_repos` 通过下一可用 migration 增加通用来源、置顶字段，并新增来源目录缓存；
- 置顶先于用户选择的普通排序，但不能绕过来源、语言或仓库状态筛选；
- `_local-admin` 增加来源状态、HelloGitHub 回填进度和多项目置顶管理。

### 3.5 正式方案

完整 schema、接口、Worker、skill、客户端、控制台、迁移、发布顺序和验收标准统一以：

`docs/2-产品/需求讨论/正式方案/Weekly多来源扩展与AI情报采集正式方案.md`

为准。本文不再保留未拍板选项。

## 4. 导出 Starred 到 GitHub Awesome 仓库

### 4.1 背景

分享页面已支持生成用户分享卡片（PNG 导出 / X 分享）。本功能是另一种"分享"：**将用户已 Star 的项目列表同步到自己的 GitHub 仓库，自动生成一份 Awesome 风格的 README**。

### 4.2 参考实现

GitHub Action [simonecorsi/mawesome](https://github.com/simonecorsi/mawesome) 提供了核心思路：

- 读取用户 GitHub Stars 列表
- 按语言或分类自动生成 `README.md`
- 输出为 Awesome 风格的项目清单
- 提交到指定仓库（通常为 `awesome-stars` 或同名仓库）

Starcat 在此基础上增强：利用本地已缓存的 Stars 数据 + 用户标签分类 + AI 摘要，生成比原始 mawesome 更丰富的内容。

### 4.3 功能条目

- [ ] **Awesome 导出配置** — 用户选择导出范围（全部 / 按标签筛选 / 按语言筛选）、排序方式（Star 数 / 最近更新 / 自定义排序）、输出仓库
  > **涉及**：新增 `AwesomeExportConfigView`（设置页），配置落本地 SQLite
  > **约束**：首次导出前必须已通过 GitHub OAuth 授权 `public_repo` 写入权限；若 scope 不足引导重新授权

- [ ] **README 生成引擎** — 按模板生成 `README.md`：包含分类目录、项目列表（名称 + 描述 + 语言 + Stars）、AI 摘要摘要、最后更新时间戳
  > **涉及**：新增 `AwesomeReadmeGenerator`（模板引擎，Swift 内实现）
  > **模板变量**：`{{category}}` `{{repo_name}}` `{{description}}` `{{stars}}` `{{language}}` `{{ai_summary}}` `{{last_updated}}`
  > **约束**：模板可内置默认 + 用户自定义；每类上限 500 条避免 README 过大

- [ ] **GitHub 推送** — 将生成的 README 提交到用户指定仓库（自动创建或覆盖 `README.md`），可选 PR 模式或直接 push
  > **涉及**：复用 `GitHubAPIClient` 的 Contents API（`PUT /repos/{owner}/{repo}/contents/{path}`）
  > **约束**：仓库不存在时自动创建（`POST /user/repos`）；首次使用引导确认目标仓库名（默认 `awesome-stars`）
  > **冲突策略**：默认覆盖 `README.md`，可选"追加到已有文件末尾"

- [ ] **定时同步（可选）** — 支持按周期（每周 / 每月）自动拉取最新 Stars 并更新 Awesome 仓库
  > **涉及**：`NSBackgroundActivityScheduler` + 本地变更检测
  > **约束**：必须在 Starcat 运行期间触发；不跑后台 silent push

### 4.4 与已有分享功能的边界

| 功能 | 输出 | 用途 |
|------|------|------|
| 分享卡片（已有） | PNG 图片 | 一次性展示，社交分享 |
| Awesome 导出（本功能） | GitHub README | 持续维护的公开项目清单，SEO / 社区影响力 |

## 5. Trending 推荐栏目（基于 GitHub Issues）

### 5.1 背景

阮一峰的《科技爱好者周刊》通过 GitHub Issues 管理推荐内容，读者通过 Issue 评论互动。Starcat 参考此模式，在 Trending 模块中新增一个「推荐」栏目：**dong4j 维护一个独立的 GitHub 仓库，以 Issues 形式发布项目推荐，Starcat 客户端拉取该仓库 Issues 列表并以内嵌详情页展示**。

### 5.2 数据流

```
dong4j 创建 Issue（推荐某个仓库）
    ↓
GitHub Issues API（GET /repos/{owner}/{repo}/issues）
    ↓
Starcat 客户端拉取 → 缓存 → 渲染推荐列表 + 详情
```

与 Weekly 模块的关键区别：

| 维度 | Weekly（已有） | 推荐栏目（本功能） |
|------|---------------|-------------------|
| 数据源 | 四个后端 API（聚合源文章） | 单一 GitHub 仓库 Issues |
| 详情展示 | WebView 渲染源文章 | **原生详情页**，展示 dong4j 写的推荐语 + 仓库元数据 |
| 内容归属 | 第三方作者 | dong4j 原创推荐 |

### 5.3 功能条目

- [ ] **推荐仓库配置** — dong4j 创建专用 GitHub 仓库（如 `starcat-recommendations`），以 Issues 承载推荐内容
  > **Issue 模板**（使用 GitHub Issue Template）：
  > ```markdown
  > ---
  > name: 项目推荐
  > about: 推荐一个 GitHub 项目
  > title: '[推荐] {项目名}'
  > labels: ['recommendation', '{类别标签}']
  > ---
  > 
  > **仓库地址**: https://github.com/{owner}/{repo}
  > **推荐语**: （为什么推荐这个项目？解决了什么问题？适合谁用？）
  > **标签**: （逗号分隔，如：效率工具、开发框架、AI）
  > ```

- [ ] **Trending 推荐列表** — 在 Trending 模块新增「推荐」分类，拉取 Issue 列表并在 Trending 列表中以卡片展示
  > **涉及**：`GitHubAPIClient.getRepoIssues(owner:repo:)` + 新增 `RecommendationRepository` 缓存层
  > **排序**：默认按 Issue 创建时间降序
  > **TTL**：24h 缓存，与 Trending 共用刷新周期
  > **列表卡片**：显示 Issue title（即项目名） + dong4j 写的首行推荐语 + 类别标签

- [ ] **推荐详情页** — 点击推荐卡片进入详情页，**不跳转 GitHub WebView**，而是在 Starcat 内原生渲染：
  > - 顶部：被推荐仓库的元数据（name / description / stars / language / license）——复用现有 `RepoMetadataHeaderView`
  > - 中部：**dong4j 的推荐语**（从 Issue body 解析，去除模板标记，保留纯文本 + Markdown）
  > - 底部：被推荐仓库的 AI 摘要（若本地已有缓存）或 README 摘要
  > **涉及**：新增 `RecommendationDetailView`，复用 `RepoDetailView` 的 header 组件
  > **约束**：Issue body 解析需处理模板格式；表情 / 图片保留 Markdown 渲染

- [ ] **Issue 互动（可选，后期）** — 支持在 Starcat 内查看 Issue 评论区、点赞等
  > **约束**：v2 首版不做评论；详情页底部放"在 GitHub 查看"链接即可
