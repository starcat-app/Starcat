## 1. 版本目标与范围

2.0.0 在社区项目发现、设置重构与业务图标统一的原范围上，增加基于 Stars 的个性化推荐、自研详情页相似推荐收口和可回看历史的每日热点。两种推荐入口共用同一套推荐底座。同时开展第三方依赖升级专项，覆盖 Agent Runtime、二进制工具、Swift 依赖和内嵌资源，以兼容性验证作为发布条件。交互与性能继续先收集问题和证据，再按影响安排整改。

| 优先级 | 方向 | 本版本交付边界 |
|---|---|---|
| P0 | Linux.do 项目发现 | 采集、项目识别、独立分类、跨分类来源标识、原帖追溯形成完整链路 |
| P1 | 推荐底座与详情页相似推荐（已完成，2026-11-04） | 扩大自研候选覆盖，建立质量门禁，完成第三方推荐数据源替换 |

## 2. Linux.do 项目发现

### 2.1 用户可见行为

- 入口为“探索 → Linux.do”，侧栏位于“周刊”下方，提供独立的可折叠语言子分类。
- 收录“开源推广”标签公开主帖中实际推广的公开 GitHub 仓库；首版处理主帖及主帖编辑。
- 一篇帖子允许关联多个项目，一个项目允许关联多篇帖子，仓库按 GitHub repository ID 去重。
- 分类列表提供原有仓库浏览能力，并显示来源与关联帖子数；默认按推广时间排序，普通回复顶帖不改变推广时间。
- 仓库详情的 Linux.do 来源标签直接打开原帖；同仓库多帖选择最新发布的一篇，同时间按帖子 ID 稳定选择。
- Stars、知识库、其他发现来源等入口中，同一仓库均可呈现 Linux.do 来源标识。
- 收录只增加公共目录与来源事实；Star、标签、笔记、知识库状态继续由用户控制。

### 2.2 采集与运营边界

采集采用[标签 RSS](https://linux.do/tag/2234-tag/2234.rss)。2026-10-12 调研时，未登录的标签 JSON 请求返回 403，RSS 返回 200 且含 30 条帖子；该记录是当时的可行性证据，不代表当前所有运行环境均可访问。按 2026-10-18 决议，每轮完成后随机等待 5 分钟至 5 小时，首轮也等待；403 结束当轮，429 遵守 `Retry-After`。RSS 不保证完整历史、全部编辑与删除均可发现；已收录项目不会因离开滚动窗口而删除。

复用 `starcat-discovery-api` 的仓库元数据、调度和缓存能力，为 Linux.do 维护独立目录与来源关系。当前 Discovery、Awesome 的目录边界继续保留。

主帖中出现的所有 GitHub 链接都只是候选；依赖、竞品、示例、徽章和引用内容不能直接当作推广项目。按 2026-10-18 决议全自动识别并核验，归属不明的候选自动跳过、记录原因，规则或内容变化后重判，不设置人工审核环节。公开可访问与采用开源许可证是两项独立事实，许可证未知不阻断来源收录。

首版不包含评论区全量采集、非 GitHub 仓库适配、论坛内评论或登录操作，也不承诺完整历史回填。具体接入路径、识别规则、数据契约与验收用例见 [Linux.do 项目发现与来源标识接入方案](../../3-设计/详细设计/70-Linux.do项目发现与来源标识接入方案.md)。

## 3. 设置页面重构

### 3.1 当前问题与已有能力

2026-10-12 梳理时，[SettingsView](../../../Starcat/Features/Settings/SettingsView.swift)定义 20 个分类入口。用户反馈设置复杂，特别是普通搜索和 RAG 的向量相关配置难以区分；以下保留当时的需求与验收基线，后续实现不以旧分类数量为目标。

代码已通过 [resolveEmbeddingSelection](../../../Starcat/Features/AI/AIConfiguration.swift)统一解析向量模型；[语义搜索](../../../Starcat/Features/AI/SemanticSearchService.swift)和 [RAG 索引](../../../Starcat/Core/RAG/KnowledgeRAGIndexBuilder.swift)共用该选择。重构重点是配置归属和用途表达；不能把现有共享模型误写为两套独立模型。

| 配置层次 | 用途 | 目标呈现 |
|---|---|---|
| 向量模型 | 把文本转换成相似度匹配数据 | 统一配置，显示使用该模型的功能 |
| 仓库搜索索引 | 按含义找到仓库 | 展示仓库覆盖、更新状态和重建操作 |
| 知识库内容索引 | 为问答检索 README、笔记、摘要等证据 | 独立展示内容覆盖和处理状态 |
| 检索后端与参数 | 选择存储、召回、重排与预算 | 常用项有推荐值，专业参数按需展开 |

两类索引分别维护；换模型时说明影响范围与重建需求。没有向量模型时仍保留知识库关键词检索能力，遵循[开发前问题清单 §5.16](../../1-立项/开发前问题清单.md)。

### 3.2 信息架构草案

首轮按以下十组梳理所有现有配置。名称、页内层级和逐项归属在设置专项中进一步确认，不以压缩分类数替代可用性验证。

| 建议分类 | 主要归属 |
|---|---|
| 通用与外观 | 语言、主题、字号、Dock 与应用行为、渠道更新入口 |
| 通知与快捷键 | 通知策略、分类订阅、应用快捷键、输入行为 |
| 账户与隐私 | GitHub 权限、Pro 许可、数据贡献与隐私说明 |
| AI 与模型 | 供应商、凭据、本地模型、共享向量模型、任务模型分配 |
| 翻译 | 系统翻译、第三方翻译服务、AI 翻译的选择与状态 |
| 自动整理 | 标签整理、GitHub Lists 分组等后台能力 |
| 搜索与知识库 | 两类索引、知识库问答的检索与提示词、联网搜索；模型引用统一入口 |
| 扩展与连接 | 浏览器插件、MCP、CLI / 本地工具、自建服务地址 |
| 数据与存储 | 数据目录、缓存用量、已有维护与数据操作 |
| 诊断与实验 | 诊断导出、日志入口、Labs 与高级诊断能力 |

复杂能力通过页内分组或子页进入，设置搜索应能直接定位具体控件。模型、API Key 等基础配置只保留一个编辑归属，消费方展示有效配置和跳转入口。

### 3.3 分类说明卡片

每个分类顶部使用统一结构：分类图标、标题、一句话用途、影响范围，以及有意义的状态或相关入口。

示例文案：

> 搜索与知识库
>
> 配置仓库搜索和知识库问答使用的检索能力。
>
> 两项功能共用向量模型，仓库索引与知识库内容索引分别维护。

卡片遵循 [DESIGN.md](../../../DESIGN.md)的原生工具风格，使用紧凑间距、系统语义色和清晰表面层次。说明卡片是分类解释组件，其余控件继续沿用原生表单。具体样板确认后再同步相关 UI 规范。

### 3.4 交付与验收

- 全量设置项建立“旧位置 → 新位置 → 生效范围”映射，避免遗漏或重复编辑入口。
- 常用项优先展示；高级参数有默认值、用途解释和恢复路径。
- 延续自动保存，并区分保存成功、连接验证成功、配置生效时机。
- 保留既有配置、Keychain 凭据、深链跳转与渠道差异，不要求用户重新设置。
- 分类说明卡片、长文本、大字号、明暗主题和错误反馈完成样板验收。

## 4. 图标体系整理

> 状态：2026-11-04 完成——业务身份图标全量换用锁定版本 Lucide 1.67.0 模板资产（89 个 imageset，`BusinessIcon` 注册表统一 `BusinessIcon.Source` 分发），系统操作与状态按方案 A 保留 SF Symbols；推荐排序用 thumbs-up 与 AI sparkles 区分。本节保留选型与验收基线，2px 线宽光学校准随发版验收。

选型方向为 **SF Symbols + Lucide + 少量定制业务图标**。以下保留最初的选型与验收要求；截至 2026-10-22，已有业务图标补齐及 Fork 语义决议，后续以[开发前问题清单](../../1-立项/开发前问题清单.md)中的具体映射为准，不重复推翻已确认的样板。

| 图标类型 | 处理原则 |
|---|---|
| 系统操作 | 关闭、复制、刷新、删除、展开等继续复用现有共享组件和合适的 SF Symbols |
| 业务含义 | 核对 Awesome、自动整理、索引、工作台等入口，语义不准确时替换 |
| 品牌来源 | GitHub、Linux.do 等优先采用允许使用的官方标识，统一容器与尺寸 |
| 库中缺失的业务图形 | 列出缺口，按统一网格、线宽、圆角和视觉重量成批制作 |

最初的样板候选包括 Awesome 的 `eyeglasses` 对比 Lucide [library-big](https://lucide.dev/icons/library-big)，AI 自动整理的循环箭头对比 [workflow](https://lucide.dev/icons/workflow)。这些候选保留为调研记录；后续新增图标仍需检查是否与知识库、刷新等现有含义混淆，不能仅因图形更好看而替换。

Lucide [SVG 规范](https://lucide.dev/contribute/icons/code-conventions)使用 24×24 网格、默认 2px 描边与圆角端点。最终在 Starcat 的 13/15/18pt 场景做光学校准。缺失图标先生成同风格设计稿，经确认后整理为可维护的矢量资产，并验证明暗主题、字号缩放、选中与禁用状态。

交付物包括图标语义对照表、样板、缺失图标资产、集中语义映射与使用规范。同一功能在侧栏、设置、工具栏和空状态保持同一含义。引入资源必须按照 [Lucide 许可证](https://lucide.dev/license)及项目[开源致谢规范](../../5-规范/开源致谢同步-规范.md)登记；部分 Feather 衍生图标另有 MIT 声明。

### 7.3 实施边界与验收

- 先扩大数据与候选覆盖，建立同一数据切分下的基线对比，再增加内容冷启动与多样性排序。Metric Learning 是否进入首版由评估决定，不作为发版前置条件。

- 两入口复用版本化模型、推荐网络与缓存；个人缓存按账号、Stars / 反馈版本、筛选与模型版本隔离。切账号、Star / Unstar、模型更新与离线恢复均需验收。
- 训练与在线查询分离；建议每日更新数据、每周训练评估，通过门禁后原子切换，失败保留上一可用模型。这是待实施的运行节奏，不是现有每日任务已经涵盖的能力。
- 自研达到相关性、覆盖、长尾空结果率与稳定性门槛后，v1 在原契约下改用自研数据，完成旧客户端回归后移除 SimRepo Provider 和密钥，避免长期保留两套推荐来源。

### 7.4 每日推荐卡片（抽卡式今日推荐）

> 状态：2026-11-03 确认纳入 P2 探索项，概念设计阶段，待交互样板验证后实施

当天首次打开应用时，弹出覆盖整个应用的「今日推荐」覆盖层，以抽卡形式展示基于用户历史 Stars 推荐的 10 个项目卡片。本节为概念设计基线，不改变 7.1–7.3 首版「两个入口」的收口范围，实施排在推荐收口之后。

触发与入口：

- 当日首次启动且主窗口就绪后弹出；当天再次打开不重复弹出，跨重启同样只弹一次。
- 侧栏「探索 → 今日推荐」保留手动入口，可随时重看当日结果；设置提供「每日首次打开弹出今日推荐」开关（默认开）。
- 新用户冷启动、推荐服务不可用、离线且无缓存时不弹层、不显示错误，静默进入主界面。

卡片与抽卡交互（概念设计，待样板验证）：

- 覆盖层背景用磨砂材质加轻微暗色渐晕，主界面虚化可见；标题显示「今日推荐 · 当日日期」，副标题说明「根据你的 Stars 挑选了 10 个项目」。
- 中央为 3–5 张卡背的扇形卡堆，缓慢呼吸浮动；点击顶部卡背以 3D 翻转展示正面，翻开的卡片飞入底部 10 格卡槽（已抽点亮），并提供「全部翻开」跳过仪式感。
- 卡面只展示基础信息：owner 头像与 owner/repo、语言与 Star 数、AI 一句话总结（1–2 行）、推荐依据（来自哪个已 Star 项目或主题）；不展示 README。
- 单卡操作：打开仓库详情、快捷 Star（需确认）、不感兴趣（记入本地反馈并参与后续排除）。
- 抽完或点「跳过」进入结算视图：10 张卡片网格展开，可逐张查看，底部提供「稍后再看 / 完成」；关闭按钮遵循 SheetCloseButton 规范，支持 Esc。
- 动效遵循 DESIGN.md 原生工具风格，克制使用翻转、飞入与呼吸动画，不做过场视频式炫光；音效默认关闭（可选后续项）。

数据与约束：

- 每日 10 张由推荐底座多仓推荐生成，排除全部已 Star 与本地「不感兴趣」反馈；当日结果锁定并本地缓存，当天重开不换卡。
- AI 一句话总结优先服务端预生成缓存（与每日热点封面同思路），缺失时回退仓库描述，避免客户端每天 10 次实时 AI 调用。
- 推荐依据必须来自真实命中的种子或元数据，沿用 7.2 约束；卡片上的 Star 写入必须用户确认，反馈仅存本地。
- 新增文案覆盖全部 17 种语言；验收覆盖当日只弹一次、结果当日稳定、冷启动与离线不弹层、抽卡往返详情后卡槽进度保留，以及小窗口、大字号、明暗主题与键盘操作可用。

- 按来源、业务日期、报告类型、内容语言去重，以内容 hash / revision 更新同一期。永久保留已发布历史，上游目录变化或生成失败不清空旧内容。

- 首页、往期与阅读页统一使用本地程序化封面；以报告 ID 和分类确定构图与配色，同一报告跨语言、重启保持稳定，绘制细节按尺寸限额。当前不依赖图像模型、对象存储或 CDN，服务端封面 URL 不触发客户端图片请求。

- 打开页面后，以当前登录用户为起点，逐步展示「我 → 我关注的人 → 他们关注的人」两层有向关系。
- 点击任一用户节点，按需加载并展开该用户关注的人；按 GitHub 用户 ID 合并重复节点，保留共同关注与环路。
- 选中节点时，高亮从我出发到达该用户的一条路径；在已加载有向图内使用 BFS 查找最短路径，不宣称它是整个 GitHub 网络的全局最短路径。
- 支持旋转、缩放与拖拽；区分未加载、部分加载、不可访问和已完整加载，不能把截断或不可见数据解释为没有关注关系。

### 9.2 数据与规模边界

现有 GH Archive WatchEvent 数据记录用户与仓库之间的 Star 事件，不包含用户之间的 follow 边。图谱改从 GitHub following 接口获取当前可见关系，不依赖历史事件还原关注网络。

GH Archive 历史中虽存在过 `FollowEvent`，但该事件类型已于 2013 年停产；关注边必须通过 GitHub GraphQL `following` 嵌套查询或 REST `GET /users/{username}/following` 获取。现有 `read:user` scope 足够，可复用 `OwnerFollowService` / `UserAPI` 的请求能力。

优先评估 GraphQL `following` 分页与有限嵌套查询，公开关系也可通过 REST `GET /users/{username}/following` 获取。实施前核对现有凭据、接口权限、隐私限制与实际查询成本，不把上一轮讨论中的固定配额估算作为接口契约。私密资料或接口限制导致的空结果，不据此断言该用户没有关注任何人。

第二层每人限制加载前 N 个，设置全图节点、边数与请求预算，点击节点后再按需分页；初始 N 和全图上限由验证结果确定。不全量递归抓取，不用不完整数据推断全局共同关注排名。结果本地缓存并带 TTL 与采集时间，不写服务端、不进入推荐训练数据；明确这是分批采集的关系快照。

### 9.3 渲染与验收

采用 `WKWebView` 内嵌页面交付：图谱资源离线打包进 App，不走 CDN；GitHub 请求和凭据保留在原生侧，经 `WKScriptMessageHandler` 向页面注入展示数据并接收节点点击、展开等事件。通信方式参考 `ReadmeWebView.swift`；取数注入方式参考 CodeFlow 的 vendored HTML 模式，但改为 App 内渲染。新增第三方资源按项目规范登记开源致谢。

渲染分两步：探索期先用 `3d-force-graph`（three.js + d3-force-3d，MIT）快速验证产品交互；上游实测约 5,000 节点起明显卡顿，若两层展开规模超过该量级，则参照 CBM Lens（已内嵌）、lemonberrylabs/codegraph、graphier 等项目的共同做法，用纯 three.js 自写场景：单个 `InstancedMesh` 画全部节点、全部边合批为 `LineSegments`（`AdditiveBlending`、`depthWrite=false`）、力导向布局跑在 Web Worker 且已有节点位置钉住（增量展开不乱跳）、按相机距离分级 LOD、高亮节点经 Bloom 发光、路径高亮走独立线层并关闭深度测试、窗口隐藏时暂停渲染。护栏：边亮度随边数按 `1/sqrt(n)` 衰减、非高亮节点颜色压暗、超过约 5,000 节点关闭 Bloom、超过约 1 万节点降为点精灵。新增 three.js / 3d-force-graph / d3-force-3d 等第三方资源按项目规范登记开源致谢；若借用 CBM Lens 或 codegraph 片段另行登记。

验收包括两层逐步加载、节点点击展开、重复节点与环路、路径高亮、旋转缩放拖拽、分页截断提示、限流恢复、隐私限制及缓存刷新；图谱在 App Store / Direct 两渠道行为一致。以 500 个一级关注用户作为规模验证场景，在明确第二层上限、硬件与网络条件后测量首屏时间、完整加载时间、内存与交互流畅度；「两层加载小于 10 秒」仅作为待验证目标，不作为未经实测的承诺。验收增加「两层展开达到约 1 万节点时仍可旋转、点选、路径高亮」作为自写场景的触发与通过条件。

## 10. 第三方依赖升级与兼容性验证

### 10.1 升级范围与现有边界

| 类别 | 范围 | 当前约束与验收重点 |
|---|---|---|
| Agent Runtime | DeepSeek Harness、Codex App Server 及协议适配器 | 两者均为外部 Runtime，沿用 Direct 与架构限制；DeepSeek 的主程序、配套工具、Cordis 配置一同核对，Codex 核对 CLI / 独立 App Server 安装形态和版本能力 |
| 二进制工具 | CodebaseMemory 等实际集成程序 | App Store 内嵌 CodebaseMemory，Direct 使用外部安装；检查真实文件、版本、架构、校验和、签名及旧索引兼容，不把两个渠道改为同一种分发方式 |
| Swift 依赖 | `project.yml` 声明的远程与本地包，以及 `Package.resolved` 的传递依赖 | 包含 GRDB、MLX、OpenAI、MCP、Sparkle、ZIPFoundation 等；分支依赖也记录具体 commit，按业务关联分批升级 |
| 内嵌资源与源码 | CodeFlow、Mermaid、vendored 组件、图标和第三方生成数据 | 核对来源版本、Starcat 本地补丁、页面间接 CDN 依赖与致谢；代码和资源均纳入清单 |

当前 `Package.resolved` 位于被 Git 忽略的生成工程目录，32 个 pin 仅代表本机解析快照。专项需建立受版本控制、可由标准构建入口复用的锁定方式，并验证干净环境得到同一依赖集合；仅记录这份本机文件不能证明跨机器构建可复现。

RepoContextPacker 仍是 Starcat 自研 Swift 能力，本项检查其 ZIPFoundation 等依赖与行为，不新增 repomix 安装任务。CodeFlow 的 HTML 含 Starcat ZIP 注入补丁及外部 JS/WASM 引用，替换主文件时需一同验证这些依赖。当前依赖配置、实际资源和渠道行为的核查记录见[专项方案](正式方案/第三方依赖升级与兼容性验证方案.md)。

### 10.2 升级步骤

1. 建立可追溯清单：当前版本 / commit、来源、安装或内嵌位置、渠道与架构、本地补丁、候选目标、影响面和验证状态。当前值来自配置和实际文件，候选版本另查官方发布记录。
2. 确定候选版本：优先选择满足 Starcat 系统与协议约束的稳定版本；无稳定 tag 的项目锁定审查过的 commit。用户自行安装的 Runtime 先做版本与能力检查，不自动替换用户工具。
3. 按 Runtime、二进制、渲染资源和相关 SPM 依赖拆批升级。每批执行对应测试和必要构建，记录回退基线；本地适配补丁逐项重新应用并核对，不整包覆盖后默认兼容。
4. 完成真实运行与旧用户升级回归。模拟协议、路径解析和编译检查之外，还需记录指定 Runtime / 二进制版本的实际运行证据。
5. 发布前冻结依赖版本、commit 与资源校验和，完成全量回归。签名、公证及最终安装包验收在后续获授权的发布阶段执行。

### 10.3 兼容性验收

- Agent：握手、模型与推理选项、流式与最终正文、工具结果、超时、取消、异常退出和进程清理；新版本仍遵守工具权限与凭据隔离，不默认启用上游新增能力。
- 用户数据：从已发布 1.9.x 配置与数据库升级，标签、笔记、授权和知识库数据保留；工具旧索引可继续读取或按明确规则重建，用户数据不得以重建方式丢弃。
- 核心功能：数据库迁移 / 查询、AI 请求与本地模型、MCP、README / Mermaid、CodeFlow、代码索引与查询、图片 / ZIP、Direct 更新链路按受影响范围回归。
- 环境：App Store / Direct 分别构建与验证，覆盖最低支持系统和当前稳定系统；按组件实际支持架构验证，未支持的架构保持正确不可用状态。
- 资源与 UI：检查启动、内存、CPU、包体积及离线 / 加载失败表现；升级新增文案完成全部 18 种语言，长文案与窄窗口布局保持可用。

现有真实 Codex / DeepSeek 集成测试默认不启用，CodebaseMemory 和页面测试也含模拟实现；验收记录分别标明静态检查、自动化测试、真实运行与分发产物验证，不把某一层通过替代全部完成。

本轮只建立清单和验证方案，不运行升级脚本，不下载、替换或启动第三方 Runtime / 二进制，不做发布操作。

## 11. 实施顺序与版本验收

1. 每日热点主体已实现，继续回归分类切换、历史分页、固定修订阅读与项目往返；封面沿用本地程序化绘制，发布适配器沿用已接通的上游同步与自生成接管路径，不重复立项或等待推荐模型。
2. Linux.do 按已确认决议回归采集、目录、来源标识和详情追溯；已交付部分不重复立项。
3. 核对当前推荐模型和数据规模，完成扩容、可复现评估、长尾补召回与模型发布门禁。
4. 基于同一底座完成详情页自研替换和“为你推荐”，先补 API 候选补取与缓存契约，再接产品入口。
5. 第三方依赖清单与候选审查提前开展；涉及新功能的依赖在其集成前固定，随后分批升级并回归，避免临近发布集中替换。
6. 设置与图标按已确认方案继续收口，UI / 性能问题按证据分级。
7. 冻结依赖基线，完成 App Store / Direct 双渠道回归、真实 Runtime / 二进制验证、升级数据与配置保留、新增文案全语言检查及新增功能性能验收。渠道发布仍需单独授权。
8. 每日热点对话与关注关系图谱按 P2 排期，在每日热点首版和推荐收口之后开展，不阻塞 2.0.0 发布；纳入实际交付时仍须通过对应渠道、依赖与性能验收。
9. 每日推荐卡片与每周 AI 大事按 P2 排期，分别在推荐收口与每日热点首版之后开展；实施前需完成抽卡交互样板与报告生成链路验证，不阻塞 2.0.0 发布。

代码实施前另行确认方案；正式实施时遵循现有任务录入、分支与数据库追加迁移规则。本文不分配迁移版本号，不创建 GitHub / Multica 任务，也不代表发布授权。

本轮只维护规划、设计及必要导航。`docs/功能实现总览.md` 与 Changelog 保持原状；需要登记时再按其独立授权规则处理。
