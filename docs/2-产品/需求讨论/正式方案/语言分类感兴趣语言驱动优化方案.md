# 语言分类「感兴趣语言驱动」整体优化方案

> 日期: 2026-09-03
> 状态: 已实现（2026-09-03 验收通过）
> 范围: 星标模块（Manage）语言分类 + 探索栏目（Trending / Weekly / Discovery）语言分类

## 1. 背景与问题

Starcat 的语言分类存在三类问题，需要整体优化：

1. **筛选模式错误**：星标模块语言分类原本是「多选」，可同时选中多个语言；期望是「单选」。
2. **异常关联**：星标模块左侧语言分类与 toolbar 全局筛选语言共用同一状态，互相联动；期望两者独立。
3. **语言列表冗长**：语言分类直接展示所有语言（星标=本地 stars 聚合 / 探索=后端聚合），冷门语言刷屏。

目标：把语言分类统一收敛为「**感兴趣语言驱动**」——用户只关心自己设置的语言，其余有语言的项目归入「其他」，未分类单独列出。

## 2. 方案目标

1. 语言分类统一为「全部 → 未分类 → 感兴趣语言 → 其他」结构。
2. 语言分类为**单选**，且与 toolbar 全局筛选语言**解耦**（各自独立、互不联动）。
3. 候选名单统一来自设置页「感兴趣语言」（`AppSettings.interestedLanguages`）。
4. 「其他」分类 = 语言非空、且不在「感兴趣语言」里。

## 3. 分类语义定义

| 分类 | 定义 |
|---|---|
| 全部 | 清空语言筛选 |
| 未分类 | `language` 为空（NULL / 空串） |
| 其他 | `language` 非空、且不在「感兴趣语言」集合里 |
| 感兴趣语言 | 设置页「感兴趣语言」逐行展示（count=0 也显示） |

> 未分类 与 其他 的边界：未分类 = 语言为空；其他 = 语言非空但不在感兴趣语言列表。

## 4. 已实现：星标模块（Manage）

> 2026-09-03 已完成，`make build-direct` + 相关 96 单测通过。

### 4.1 单选 + 与全局筛选解耦

- `toggleLanguageFilterFromUser` 改为单选：只写 `repoLanguageFilter`（`.all / .uncategorized / .language / .other`），不再触碰全局多选 `globalFilterLanguages`。
- `setCategorizedLanguageFiltersFromUser` 只写全局多选 `globalFilterLanguages`。
- 拆分 `clearSidebarLanguageFilter()`（清左侧单选）/ `clearLanguageFiltersFromUser()`（清全局多选）。
- `selectSingleLanguageFilterFromUser`（旧版 `.language(...)` 深链恢复）改走左侧单选 `repoLanguageFilter`。
- `isManageLanguageFilterSelected` 只读左侧 `repoLanguageFilter`；`globalLanguageBinding` 只读全局 `globalFilterLanguages`。

### 4.2 左侧语言分类数据源重构

- 新增 `SidebarLanguageRow`（`.uncategorized / .other / .language`）枚举 + `sidebarLanguageRows` 派生属性。
- 基于 `languageStats`（DB 聚合）与 `interestedLanguages` 在内存重分组，不新增 SQL。
- 渲染顺序固定：全部（独立行）→ 未分类 → 感兴趣语言 → 其他；count=0 的感兴趣语言也保留显示。

### 4.3 数据层扩展（支持「其他」）

- `RepoLanguageFilter` 新增 `.other` 哨兵（持久化 `__starcat_other__`）。
- `RepoListFilters` 新增 `excludedLanguages: Set<String>`。
- SQL 层（`RepoRepository`）与内存层（`computeFilteredSorted`）改用 `switch` 处理 `.other`：`language IS NOT NULL AND language NOT IN (excludedLanguages)`。
- 转换层（`currentRepoListFiltersForDatabasePaging`）注入 `excludedLanguages`；snapshot key 纳入 `excludedLanguages`（避免改「感兴趣语言」后命中脏缓存）。
- 删除已无引用的 `queryLanguage`。

### 4.4 状态同步

- `HomeViewModel` 新增 `interestedLanguages` 镜像字段（`.other` 生效时 refilter）。
- `HomeView` 启动（`syncViewModelSettingsFromAppSettings`）+ `onChange` 从 `AppSettings.interestedLanguages` 同步。

## 5. 已实现：探索栏目（Trending / Weekly / Discovery）

### 5.1 现状排查

| 模式 | 语言机制 | 数据是否全量在客户端 | 后端接口 |
|---|---|---|---|
| Trending | 后端单语言导航查询（`lang`，limit 100） | ❌ 否（按「周期 × 语言」分桶查） | `GET /api/v1/repos?since&lang&limit` |
| Weekly | 本地筛选 | ✅ 是 | `/repos/bulk` 全量（~4000 条，无 query 参数） |
| Discovery | 本地筛选 | ✅ 是 | `fetchBulk` 全量 catalog（无 language 参数） |

- **Weekly**：`WeeklyContentView.swift` 头部注释明确「切 source/sort/lang 纯本地 filter + 分页，避免切筛选重新请求远端」。
- **Discovery**：`ExploreDiscoveryViewModel.swift:9-10` 注释明确「按 Weekly bulk 思路：本地缓存全量 catalog，筛选、排序、分页都在本地完成」。
- **Trending**：`TrendingViewModel.selectLanguage` → `reload` → 后端 `fetchTrending(since, language)`，客户端只做本地排序 + 本地分页（`visibleLimit`）。

**Trending 数据量证据**：`supports/starcat-trending-api/internal/handler/trending_cache.go:21-22` 注释原文「entry 量级 3 since × 几十 lang × ≤3 limit ≈ 几百」。Trending 语言只有「几十个」，每语言每周期约 25 条，**单周期全量 ≈ 几百到一千多条，比 Weekly 的 4000 还小**。后端 `repos.go:69-74` 当前 `limit` 硬上限 100。

**结论**：Trending 完全具备「全量拉到本地 + 本地筛选」的条件，当前「分桶查询」只是历史架构，不是技术限制。

### 5.2 方案设计

三模式统一成「**全量拉到本地 + 本地筛选**」，与星标模块同构：

1. **展示层聚合（三模式 SidebarView，纯客户端）**：三模式语言列表（`trendingLanguageStore.displayList` / `weeklyLanguageStore.displayList` / `exploreCatalogStore.displayLanguages`）统一按 `interestedLanguages` 重分组为「全部 → 未分类 → 感兴趣语言 → 其他」。
2. **Trending 全量化**：后端把 `limit` 上限从 100 提高（或新增全量读取接口）；客户端 `TrendingViewModel` 从「分桶查询」改为「全量拉取当前周期所有语言 + 本地按语言导航 + 本地过滤」，参考 Discovery 的 `applyFiltersLocally` 模式。
3. **Weekly / Discovery 本地过滤「其他」**：`deriveLocalItems` / `applyFiltersLocally` 新增「其他」分支——语言非空且不在感兴趣语言。
4. **「其他」选中态**：Trending 用 `TrendingLanguage` 新增哨兵；Weekly / Discovery 用保留哨兵字符串。
5. **count 与顺序**：count=0 的感兴趣语言显示 0；「其他」分组放语言分类最后。
6. **面包屑导航语言区分**：星标模块优先显示全局筛选语言（全局为空回退左侧语言）；探索模块在左侧语言导航后追加全局筛选语言，避免两套语言筛选在标题里混淆。

三者均用 `Set` 做 O(1) 包含判断，避免 repo 数 × 语言数退化成 O(n·m)。

## 6. 分阶段实施计划

1. **阶段 1 — Trending 后端全量**：提高 `limit` 上限 / 加全量接口（`go build ./... && go vet ./...` 验证）。
2. **阶段 2 — Trending 客户端重构**：全量化 + 本地语言导航 + 「其他」本地过滤。
3. **阶段 3 — Weekly / Discovery 本地过滤**：各加「其他」分支。
4. **阶段 4 — SidebarView 展示层聚合**：三模式语言列表统一重分组 + 「其他」行 + i18n key。
5. **阶段 5 — 单测与构建验证**：`make test`（相关 Suite）+ `make build-direct` + `jq empty` 校验 xcstrings。

## 7. 风险与约束

1. **分页正确性**：全量化后分页在本地完成，「其他」过滤在分页前做，total 准确（与 Weekly/Discovery 同语义）。
2. **缓存**：Trending 全量接口需对齐现有 `TrendingCache` 的 `since|lang|limit` key 规则（全量 = `lang` 为空 / 专用 key）。
3. **数据量**：Trending 全量（一两千条）+ gzip + TTL 与 Weekly 同量级，无新增压力。
4. **i18n**：`Localizable.xcstrings` 编辑遵循「只按行新增」军规，不整文件格式化。
5. **后端仓库边界**：`supports/starcat-trending-api` 是独立 Git 仓库，改动需按该仓库 `AGENTS.md` 规范（`go build ./... && go vet ./...`，禁止擅自 `fly deploy` / `git push`）。
