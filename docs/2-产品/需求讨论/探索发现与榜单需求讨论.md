# 探索发现与榜单需求讨论

> 日期: 2026-06-30
> 状态: 已形成方向, 已进入实现与补强
> 范围: Starcat「探索」入口、发现流、趋势 / 热门 / 新发布榜单、新增 discovery 后端服务

## 1. 背景

Starcat 当前已有 `Trending` 入口,主要服务 GitHub Trending 的今日 / 本周 / 本月榜单。随着产品进入「整理、理解、找回、评估」之外的主动发现阶段,单一 Trending 入口已经不能覆盖以下需求:

- 通过主题发现新项目,例如人工智能、隐私、网络、媒体、社交、阅读、工具。
- 保留现有趋势榜单,但把它纳入更大的「探索」入口。
- 增加热门榜单和新发布榜单,让用户能按不同价值维度找项目。
- 发现页需要平台维度,榜单页继续保留 Languages 子分类。
- 中栏顶部需要统一筛选组件,避免只有趋势有「今日 / 本周 / 本月」导致结构不一致。

## 2. komi-store 调研结论

调研对象: `kurikomi-labs/komi-store`、`kurikomi-labs/komi-store-backend`、`kurikomi-labs/komi-store-backend-data`。

komi-store 的发现 / 榜单不是客户端临时请求 GitHub 得到的,而是三层结构:

```text
客户端
  -> api.github-store.org
后端服务
  -> Postgres 中的 repos / repo_categories / repo_topic_buckets / feed_exposure
数据生成仓库
  -> GitHub Search API + GitHub Releases API
  -> 静态 JSON 缓存
  -> Postgres upsert
```

关键接口:

```text
GET /v1/feed?platform=&page=&limit=
GET /v1/categories/trending/{platform}
GET /v1/categories/new-releases/{platform}
GET /v1/categories/most-popular/{platform}
GET /v1/topics/{bucket}/{platform}
```

关键做法:

- 榜单数据通过定时任务预生成,请求路径只读数据库。
- 候选 repo 来自 GitHub Search API。
- 每个候选 repo 再查 GitHub Releases API,确认是否有对应平台可安装资产。
- `most-popular` 使用高星候选,并计算 `popularityScore = stars + forks * 2`。
- `feed` 使用 momentum、popularity、recency、cooldown 和 diversity 组合,避免每天只展示头部项目。
- 线上后端有 CDN 缓存,静态 JSON 作为后端不可用时的离线兜底。

对 Starcat 的启发:

- Starcat 不应在客户端直接复刻抓取逻辑,应该用后端预计算。
- `trending-api` 应保持现状,避免现有 Trending 回归。
- 新能力应抽成新的 `starcat-discovery-api`,承载发现、热门、新发布以及未来新版趋势。

## 3. 讨论后的产品方向

把当前 `Trending` 一级入口升级为「探索」。探索下有四个主模式:

```text
探索
├── 发现
├── 趋势
├── 热门
└── 新发布
```

各模式的子分类和筛选不同:

| 模式 | 左侧子分类 | 中栏顶部筛选 | 数据来源 |
|---|---|---|---|
| 发现 | 平台 + 主题 | 推荐 / 最新 / 热度等通用排序 | 新 `starcat-discovery-api` |
| 趋势 | Languages | 今日 / 本周 / 本月 | 首期继续用 `starcat-trending-api` |
| 热门 | Languages | 综合热度 / Stars / 活跃度 | 新 `starcat-discovery-api` |
| 新发布 | Languages | 最近发布 / 最近更新 / Stars | 新 `starcat-discovery-api` |

发现模式的主题分类初始为:

```text
全部 / 人工智能 / 隐私 / 网络 / 媒体 / 社交 / 阅读 / 工具
```

发现模式新增平台维度:

```text
全部 / macOS / iOS / CLI / Web / Server / Android / Windows / Linux
```

平台维度与主题维度都支持折叠。折叠后只展示「全部」入口,交互形态参考当前 Trending Languages 的折叠样式。

## 4. 后端边界讨论

有两个方案:

1. 扩展 `starcat-trending-api`
2. 新增 `starcat-discovery-api`

最终倾向新增独立服务:

- `starcat-trending-api` 语义清晰,只负责 GitHub Trending 单源数据。
- 发现 / 热门 / 新发布需要更多表、定时任务、排名算法、曝光冷却和静态缓存,职责已经超过 trending。
- 新服务可独立灰度,不影响当前 Trending。
- 未来如果新服务的趋势质量更好,再逐步迁移 Trending。

## 5. 需要注意的问题

1. 不要在 UI 上先放无法生效的筛选项。中栏统一筛选组件可以先统一容器,但具体选项必须与后端能力一致。
2. 发现流必须避免头部项目垄断。需要 cooldown / diversity,否则用户每天看到的都是相同 repo。
3. 后端请求 GitHub 需要 token pool、rate limit 退避和失败保留旧数据。
4. 数据服务应优先公开、可自部署,与现有 `weekly-api` / `trending-api` / `recommend-api` 规范一致。
5. 客户端不要直连 GitHub Search 兜底,避免把复杂查询、配额和字段漂移暴露到 macOS App。

## 6. 初步结论

本需求拆成三部分推进:

1. 产品信息架构: `Trending` 升级为「探索」,提供发现 / 趋势 / 热门 / 新发布四模式。
2. 后端能力: 新增 `starcat-discovery-api`,承载发现流和新榜单。
3. 客户端接入: 保留当前 Trending 调用链,新模式接入新服务;等新服务稳定后再评估是否迁移趋势。

## 7. 实施中补充讨论

首版方案漏掉了两个体验关键点:

1. **Sidebar 汇总数据**
   - 需求不是只展示子分类目录,而是探索 4 个子模式和每个子模式下的筛选项都要有 repo 数量。
   - 不能让客户端为了左侧数字分别请求列表分页,否则会造成请求放大和状态不一致。
   - 补充方案: `starcat-discovery-api` 新增 `GET /api/v1/discovery/summary`,一次返回发现 / 热门 / 新发布 / 新趋势候选的总量和 facet count。

2. **Starcat 本地缓存**
   - 旧 Trending 在客户端有 `trending_repos` / `trending_readmes` 本地缓存,探索如果只靠内存和网络,体验会不一致。
   - 补充方案: Starcat 新增 discovery 本地 SQLite 缓存表,缓存列表页和 summary。进入探索时先读本地缓存,再后台刷新远端。

最终实现边界:

- 发现 / 热门 / 新发布列表与 summary 使用 `starcat-discovery-api + Starcat 本地 SQLite 缓存`。
- 趋势中栏继续使用 `starcat-trending-api` 和原有 Trending 缓存。
- 探索模式行里的趋势总量优先取现有 `TrendingLanguageStore` 聚合,避免展示一个与当前趋势列表不一致的新服务候选数量。
