# SkillDeck 产品与源码分析

> 基线：`45a31373b0620a7c73f536f377271b9c6c82d235` / v0.2.0。核查日期：2026-11-14。方法：源码与 GitHub 元数据静态分析，未运行应用或测试。

## 1. 产品定位

SkillDeck 是原生 SwiftUI macOS 应用，目标是把分散在多个 AI 编程工具中的 Skill 放在一个界面内查看、安装、分配、编辑和更新。它把文件系统作为主要状态来源，以共享目录、各工具专用目录、软链接及 lock 文件连接生态。

它不是 Star 管理器，也不是运行 Skill 的 Agent。对 Starcat 最有价值的是本机管理流程、跨工具状态模型与长期维护中暴露的问题，不是界面外观。项目最低 macOS 14，使用 Observation、actor、Yams 与 swift-markdown；Starcat 已是 macOS 15+，无需为了参考它降低自己的技术基线。证据见 [SD01、SD02](11-证据索引与核查记录.md#skilldeck-源码)。

## 2. 能力地图

| 能力 | main 源码中可确认的实现 | 对 Starcat 的启发 |
|---|---|---|
| 本机发现 | 扫描共享及 Agent 目录，跟踪安装位置、broken 和 disabled 状态 | 应有独立本机扫描器及诊断 |
| Agent 分配 | 建立逐 Skill symlink，识别部分共享目录继承关系 | 安装、链接与继承要分开 |
| GitHub 安装 | 仓库内容获取、选择 Skill、记录来源和版本 | 复用 Starcat 现有固定 commit 下载能力 |
| 本地导入 | 拷贝 Skill 目录到共享库 | 导入前展示完整目录、大小和归属 |
| 来源浏览 | skills.sh 与 ClawHub | provider 隔离，不能把抓页面当稳定协议 |
| 更新 | 单项／批量检查与更新，stage、backup、恢复记录 | 更新事务值得研究；初装也要达到同等标准 |
| 停用 | v0.1.4 后新增共享 Skill 的 manifest 重命名方案 | 不等于所有 Agent 的通用禁用机制 |
| 编辑 | frontmatter 表单与正文编辑，编辑页所谓 Preview 为纯文本 | 正文预览与原始文本保存都要真实实现 |
| 使用证据 | 默认工厂注册 7 个本地日志 provider | 不能把 README 较旧的“三种工具”当现状 |
| 来源分组 | v0.2.0 按仓库分组、折叠、来源链接和 tooltip | 与个人标签、批量目标分配不是同一能力 |

## 3. 核心数据流

`SkillScanner → SkillManager.refresh → lock/cache 补充 → SwiftUI 列表／详情` 是读链路。`SkillManager` 还负责安装、删除、分配、编辑、更新、全局停用、watcher 与 usage 协调，约两千行，职责集中。

`Skill.id` 是目录名，`Hashable` 和相等比较也以该 ID 为准。扫描器按名称合并来自不同根目录的项，附加各个 Agent 的安装记录。这个模型省事，但无法可靠表达“两个仓库都提供同名 Skill”“同名本地副本已经分叉”“某 Agent 专用目录中的同名内容不同”。源码事实见 [SD03、SD04、SD06](11-证据索引与核查记录.md#skilldeck-源码)。

Starcat 应将上述对象拆为来源身份、受管条目、内容版本、物理安装实例、可见性证据；列表合并必须基于已证明的关系，不基于名字相同。

## 4. 值得借鉴的实现

### 4.1 更新流程已经考虑恢复

上游更新不是简单覆盖：它有 staging、backup、manifest、rename 和启动时恢复；更新前重新获取仓库，批量更新按来源聚合，减少同仓库重复下载。刷新还恢复瞬时更新状态，避免新数组覆盖更新按钮状态。

因此不能笼统断言“SkillDeck 没有事务或回滚”。真正的差异是：**更新路径已有恢复设计，初次持久化安装路径没有同等完整的保护**。Starcat 应让安装、替换、编辑发布和更新共用事务规则，而不是只修更新按钮。[SD06、PR32、PR56、PR57、PR69](11-证据索引与核查记录.md#变更与问题证据)

### 4.2 使用统计主动区分不完整

上游 usage 模型区分未扫描、扫描中、有结果、陈旧、失败与无来源，并保留部分读取失败时的旧缓存。这比“读不到就显示 0 次”更可信。适配器采用日志指纹，减少重复解析，部分服务还读取 SQLite / WAL。

应吸收它的“检测到调用证据”口径与覆盖信息；改进按目录名关联 Skill 的身份方式。不能因为某个工具有 provider 就宣称该工具所有版本、所有日志格式均受支持。[SD10](11-证据索引与核查记录.md#skilldeck-源码)

### 4.3 安装去重与来源匹配是持续修出来的能力

重名安装、Registry 的已安装判断、根目录 Skill 更新及更新按钮刷新问题都有独立修复。说明来源定位、内容 revision、扫描快照之间的映射应先建模、再做 UI；靠界面局部布尔值会重复踩坑。

## 5. 静态风险与约束

下表是源码审查结论，不代表本轮复现了用户数据丢失或崩溃。

| 发现 | 具体路径与依据 | 可发生的实际问题 | Starcat 对策 |
|---|---|---|---|
| 名称作为全局身份 | `Skill.swift`；`SkillScanner.scanAll` | 不同源同名项被合并，来源与操作目标不清 | 来源键、条目 UUID、物理位置分开 |
| 安装目录识别宽松 | `SymlinkManager.findInstallations` 可把同名实体目录视作安装 | 目录存在不证明内容一致或同源 | 显示 `conflictingDirectory`，核对 receipt／hash |
| 移除链接未比对预期目标 | `SymlinkManager.removeSymlink` | 被外部工具改指向后仍可能被移除 | 操作前 `lstat/readlink` 再校验目标 |
| 删除按 canonicalURL 操作 | `SkillManager.deleteSkill` | 若列表项指向外部 canonical 内容，删除范围可能超出用户认知 | 外部只读；删除与解除分配分开授权 |
| 初装先删再复制 | `persistInstalledSkillDirectory` | 拷贝失败时旧目录已被删除 | 同卷 stage、验证、备份、rename |
| 分配错误被忽略 | 同函数建立部分目标 symlink 使用 `try?` | 内容已安装但目标分配失败，用户难以判断 | 每目标成功／跳过／冲突／失败结果 |
| 已知字段重编码 | `SkillMDParser.serialize` | 未建模 frontmatter 字段和布局可能丢失 | 保存原始文本；独立解析和校验 |
| 扫描失败折叠为空 | 扫描中部分 `try?` / 默认值 | 无权限或损坏被看成没有 Skill | root coverage 与 parse diagnostics |
| watcher 双重 close | `stopWatching` 关闭 fd，cancel handler 再关同 fd | 重复关闭可能碰到已复用的描述符 | 唯一 owner、唯一关闭点 |
| watcher 层级有限 | 父目录 DispatchSource，没有递归内容覆盖保证 | 修改内部文件后界面不刷新 | 明确监听范围、补扫、手动刷新 |

证据对应 [SD03–SD08](11-证据索引与核查记录.md#skilldeck-源码)。其中 watcher 双重 close 也在未合入 PR #59 中被显式修正；不能把该 PR 的修复当作当前 main 已有行为。

这些是文件管理器的正常操作风险，不需要在 Starcat 中增加通用安全框架或扫描整个用户目录。约束精确到受管路径、目标链接、文件内容与操作顺序即可。

## 6. UI 可以学什么，应该换什么

可学：导航与详情分离、Skill 行中提供来源、目标分配集中呈现、导入与更新使用明确流程、批量操作给进度。

应该换成 Starcat 的方式：

- 用现有原生三栏、系统标题栏和共享 Header，不复制 SkillDeck 的导航布局、颜色、Dashboard 卡片和密集开关。
- 将“可读／受管分配／外部副本／继承”做成有说明的状态行，而非一排看起来都可独立控制的 Toggle。
- 详情优先展示 Skill 的用途与 Markdown，再展示文件、目标位置、来源和更新，减少满屏技术标识。
- 只有编辑模式显示编辑工具；只读浏览不能被表单占满。
- 与 #74 的教训对应：侧栏窄时控制按钮应折叠到菜单，不能依赖用户自行拉宽才能找到。
- 与 #51 对应：详情 Markdown 与编辑 Preview 分别验收；标签叫“预览”就必须渲染。

本轮没有运行上游 UI，上述评价基于源码、公开问题及用户明确不喜欢上游外观的要求，不冒充实机体验。

## 7. 互操作边界

上游读写 `~/.agents/.skill-lock.json`，结构版本为 3，使用 Codable 和原子文件写入。其结构仅建模特定字段；原子写入可以避免半文件，不能自动解决多安装器同时读改写的问题。

Starcat 首版应只读第三方 lock，作为来源线索；拥有完整目录、来源和内容校验的 Starcat receipt 才能授予写入权限。识别不出的 lock 版本应标记 `unsupportedVersion`，不能把解析失败当作“没有安装”。[SD09](11-证据索引与核查记录.md#skilldeck-源码)

skills.sh 排行读取包含 Next 页面数据提取，搜索使用独立接口；ClawHub 也有自己的列表、详情与下载流程。它们是具体服务适配，不是 Agent Skills 格式规范的一部分。初版通过 GitHub／本地目录完成闭环，市场作为后续 provider 接入。

## 8. 采用决策

| 级别 | 内容 |
|---|---|
| 借鉴 | 生命周期能力地图、来源聚合更新、更新恢复、日志覆盖状态、批量结果 |
| 改造后采用 | 软链接分配、共享目录关系、本地导入、完整 YAML 校验、来源浏览 |
| 不照搬 | 名字做 ID、共享目录自动接管、忽略目标失败、typed YAML 全文重写 |
| 另立范围 | 整项目目录同步、AGENTS/CLAUDE 等规则同步、MCP 服务管理 |
