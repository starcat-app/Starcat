# 领域模型、本机扫描与存储方案

> 状态：领域与服务契约。T04 已建立独立本机库与来源／条目／版本／根／位置记录，进度与验证见 [12](12-开发Checklist与实施记录.md)。尚未实施部分仍为目标契约；写操作以 [07](07-安装分配禁用与文件事务方案.md) 为准。

## 1. 为什么不能只有一个 Skill 结构

`foo` 可能来自不同仓库，也可能在 Claude、Codex、项目目录中各有一份。相同目录经 symlink 被多个工具看到，又不是多份内容。因此名称、来源身份、库条目、版本、物理位置、可见性不能共用一个 ID。

| 拟议类型 | 身份与关键字段 | 含义 |
|---|---|---|
| `SkillSource` | UUID；kind；canonicalLocator；subdirectory；defaultRef | 获取内容的逻辑来源 |
| `SkillLibraryEntry` | UUID；sourceID?；manifestName；displayName；managementKind | 一个持续存在的库条目 |
| `SkillRevision` | revisionID；entryID；contentDigest；upstreamCommit?；manifestDigest | 一份完整内容快照 |
| `SkillLocation` | UUID；rootID；lexicalPath；resolvedPath；resourceIdentifier? | 一个可定位的物理内容位置 |
| `SkillExposure` | entry/location；agentID；rootID；evidence；verification | 某 Agent 从何处可能读到内容 |
| `SkillAssignment` | UUID；entryID；destination；mode；desiredState；receiptID | Starcat 创建并拥有的分配关系 |
| `SkillRoot` | UUID；configuredPath；resolvedPath；scope；agentIDs；traversalPolicy | 一个明确配置的发现根 |

类型可以在实现中合并文件，不要求每个名词各造一个 service。关键是保持上述身份和所有权差异。

## 2. 身份与规范化规则

来源唯一键为 `kind + canonicalLocator + normalizedSubdirectory`。GitHub 的 owner/repo 比较按平台规则规范化；去掉无意义的 `.git`、结尾 `/`；分支与 commit 是版本选择，不能变成全新来源。重定向或仓库改名只在确认同一仓库身份后更新别名。

本地导入来源记录用户选中的目录身份与当时内容指纹；拷贝结果获得独立 entryID。相同 hash 只表示内容相同，不自动合并所有权。

物理去重使用解析后的路径，并在可用时辅以 volume／resource identifier。符号路径与真实路径都保留：前者用于解释读取入口，后者用于物理去重。inode/resource identifier 可复用，不作为跨时间永久 ID；条目 ID 不能随每次扫描变化。

外部条目首次发现生成稳定 UUID，并通过既有位置映射重识别。完整扫描确认消失后保留 `missing` 状态与用户标签；用户明确忘记后才移除元数据。受管条目以库 receipt 为主键来源。

Agent 可见性必须记录 `directRoot / sharedRoot / symlink / projectRoot / plugin / configuration` 证据，以及 `verified / inferred / unverified`。路径存在只能证明“发现”，不能保证运行中的 Agent 已加载。

## 3. 自有目录

建议位于现有应用支持根下、账号目录之外：

```text
<Application Support>/com.starcat.app/skill-library/
  library.sqlite
  managed/<entryID>/
    receipt.json
    content/<manifestName>/SKILL.md
    content/<manifestName>/...
  transactions/<operationID>/journal.json
  cache/
```

同卷 stage 与 backup 放在**被替换目录的父目录**，例如 `managed/<entryID>/.stage-<operationID>`；不能默认放系统 `/tmp` 后假设 rename 总是原子的。目标 Agent 的副本事务在其实际父目录暂存，链接操作只在目标父目录创建临时链接。

受管内容保留 manifest 所要求的父目录名，存储路径中的 UUID 不替代 `name`。库根不能是 `~/.agents/skills`，否则导入即自动暴露给多个工具，无法实现“仅入库、暂不分配”。

缓存可清理；数据库、receipt、用户标签、未完成操作记录与备份不属于普通缓存。

## 4. GRDB 表结构草案

使用独立 `SkillLibraryDatabase`，不复用随 GitHub 账号切换的 `DatabaseManager`。初次发布的库可有独立 `v1`；一旦发布，其后变化只追加迁移。不得修改已发布主库的 `v1-initial`。

T04 实际落点为 `Core/Skills/Library/SkillLibraryStore.swift`：actor 内惰性打开 GRDB DatabaseQueue，统一持有存储与关系读取，未机械拆出第二个数据库包装类。独立 `v1-skill-library` 先创建 sources／entries／revisions／roots／locations；assignments／operations 随 T09–T11 追加迁移，tags 留到 M4。以下表格仍是完整目标草案，不代表全部字段和表已存在。回执位于 `managed/<entryID>/receipt.json`，校验格式版本和条目身份，读取回执不授予外部内容所有权。

| 表 | 核心字段 | 约束／索引 |
|---|---|---|
| `skill_sources` | id、kind、canonical_locator、subdirectory、ref、metadata_json | 唯一来源键 |
| `skill_entries` | id、source_id?、manifest_name、display_name、management_kind、current_revision、is_hidden、created_at、updated_at | source／name／更新时间索引 |
| `skill_revisions` | id、entry_id、content_digest、manifest_digest、upstream_commit?、upstream_tree?、created_at | entry + digest 唯一 |
| `skill_roots` | id、configured_path、resolved_path、scope、agent_ids_json、traversal_json、enabled、last_success_at | 规范路径去重但保留逻辑归属 |
| `skill_locations` | id、entry_id、root_id、lexical_path、resolved_path、kind、observed_digest?、scan_state、last_seen_generation | root + lexical_path 唯一 |
| `skill_assignments` | id、entry_id、target_path、resolved_parent、agent_ids_json、mode、desired_state、observed_state、receipt_id | target_path 唯一，entry 索引 |
| `skill_operations` | id、kind、entry_id?、state、journal_path、result_json、created_at、updated_at | 未完成状态索引 |
| `skill_entry_tags` | entry_id、tag、created_at | M4 添加；entry + 规范化 tag 唯一 |

`exposures` 首版由 root、location、assignment 与适配规则派生，不必再存一张可能失效的真值表。完整正文不进 SQLite；可搜索摘要按文件指纹更新。初版普通筛选与关键词查询即可，性能证据不足时不预先增加向量、FTS 或复杂缓存系统。

`metadata_json`、操作结果 JSON 必须携带版本；这只服务可变外部描述，不用于绕开核心关系和约束。

## 5. 扫描输入与输出契约

拟议接口：

```swift
protocol LocalSkillScanning: Sendable {
    func scan(_ request: SkillScanRequest) async -> SkillScanReport
}
```

`SkillScanRequest` 至少包含 `generationID、roots、previousSnapshotToken、reason`。输出包含：

- 每根 `complete / missing / inaccessible / partial / cancelled / unsupported`；
- 已发现 candidate、解析诊断、逻辑与真实路径、遍历是否截断；
- 实际检查的目录／文件数、开始／结束时间；
- 只有 `complete` 或确认 `missing` 的根，才允许将此前未见位置转为 `missing`。

根缺失时：若能读取父目录且确认不存在，可以标 missing；若父目录无权限或挂载不可达，标 unavailable。权限错误不能因 `fileExists == false` 被当成不存在。

批量快照包含 `snapshotRevision`；UI 只接受当前 generation 的结果，避免旧扫描覆盖新配置。取消保留已发布结果，但根不能标 complete。

## 6. 遍历策略

首版只扫描明确配置的工具根和受管库，不遍历整个 Home。

推荐可验证的默认预算：深度 6、每根最多 5000 个目录／50000 个 entry、同一时刻最多 4 个根；这些是 Starcat 建议值，不是声称所有 Agent 的上限相同。适配器可采用更严格深度；超预算产生 partial 和诊断，绝不静默截断。

规则：

1. 查找确切 `SKILL.md`，解析 name／description 与 diagnostics。
2. 找到一个 Skill 后不把其 `references/assets/scripts` 内的文档继续当子 Skill；真正嵌套 Skill 标注并按策略处理。
3. 点目录默认跳过，工具明确的系统／插件根另配规则，不能因此漏掉作为根本身的 `.system` 等目录。
4. 读取目录 symlink 时记录路径、做循环检测与预算；外部解析目标只读发现，不获得写权限。
5. Skill 内部的附件 symlink 不跟随预览；用户选择导入时按现有安装约束阻断不受支持布局。
6. 损坏 frontmatter 保留原始文件、错误位置与候选项，不能伪造正常 metadata。
7. 错误根保留上一份成功快照并标 stale；成功根独立更新。

目录 symlink 与 Skill 内容中的 symlink 是不同问题：允许通过用户配置根发现内容，不代表允许把任意链接附件复制进受管包。

## 7. 内容指纹与文件状态

完整 digest 基于排序的相对路径、文件内容 SHA256、类型与执行位。忽略项只包括明确定义的 Starcat 自有事务／回执文件；不得笼统忽略所有点文件。

快速扫描先比较 file size／mtime／resource identity，打开详情或任何写入前再执行完整校验。mtime 不是内容相等的证明。文件树和预览使用 digest 缓存，外部变化后失效。

本地修改状态为 `unchanged / modified / missing / unreadable / unknown`；只有与已知安装基线完整对比后才能说 unchanged。扫描预算不足时不能批准覆盖或删除。

## 8. 监听与一致性

推荐系统递归 FSEventStream 作为变更提示源，串行拥有监听状态与生命周期；事件仅表示“需要重扫”，不是数据库事实。若实现阶段选择 DispatchSource，则必须明确其子目录覆盖范围，并补充已知内容目录监听，不能假装递归。

T06 使用 300ms 窗口合并事件，不反复重置计时，持续写入也会触发补扫。首版按一次完整对账合并 dirty 请求，扫描完成后再补扫一次，不能因“正在刷新”而丢弃事件。文件系统事件溢出／根重命名／挂载变化触发完整对账。

打开窗口、应用重新激活、用户手动刷新及操作完成后都进行适度补扫。首版窗口可见时启动 watcher，关闭窗口后停止非必要监听，app 级服务保留索引；已经确认的操作继续执行，并在完成后对受影响路径对账。再次打开完整核对配置根，因此不需要窗口关闭后持续高频扫描。

扫描与 watcher 不自动修复缺失分配，也不擅自重建被用户删除的链接。恢复写入只来自明确操作或可验证的未完成事务，不能把 desired state 当作常驻自动同步命令。

## 9. Swift 6 隔离

- ViewModel / scene coordinator：`@MainActor`，只组织 UI 与异步调用。
- 扫描、摘要和 hash：独立 actor／明确后台执行的 worker；返回 `Sendable` 值，不把可变 FileManager 状态传给多个任务。
- 操作 coordinator：按 entry／实际目标序列化写入；读取可并发，提交短区间不响应取消。
- 数据库：使用 GRDB writer 的隔离，不在 UI getter 中同步读盘。
- watcher：一个执行域管理创建、取消和资源释放；fd／stream 只释放一次。

`Task {}` 从 MainActor 创建并不自动让重 I/O 离开主线程。具体 executor 选型需按当前 Swift 工具链验证，不靠“写了 async”证明不卡顿。

学习关键词：`@Observable`、actor isolation、Sendable、structured concurrency、GRDB DatabaseWriter；入口见 [Swift 学习索引](../../../7-工具与脚本/Swift-学习索引.md)，项目参照 `RepoSkillInstaller`、`AIWorkspaceSceneCoordinator`、`DatabaseManager`。

## 11. 当前实施记录

T04／T05 已实现独立本机库及只读扫描，源码位于 `Starcat/Core/Skills/Library/`。来源、条目、版本、发现根与词法位置分别持久化；相同物理目录的多个入口关联同一条目，同名独立副本不合并。缺失保留条目身份，重现沿用原 ID。

扫描代次在独立库提交入口校验，失败、取消和预算截断只将未见位置标 stale；完整覆盖或确认不存在才标 missing。默认深度 6、每根 5000 目录／50000 条目、manifest 1 MiB、最多四根并发。目录列表先由 Foundation 取得，故工作量预算不能表述成严格内存预算。

当前复用的 frontmatter parser 仅覆盖 YAML 子集，解析失败诊断为“无效或不受支持”，不承诺完整 YAML 校验。OpenCode 根内独立 Markdown 尚未索引，对应根标 partial；新增解析依赖与更多格式不在本次自动扩展。受管写入由 M2 接续。

T06 已实现 `SkillLibraryEnvironment` 与 `SkillRootWatcher`。仅显式开窗后探测工具及扫描；关闭停止索引资源，重开保留快照后对账。FSEvents 在独立队列递归监听实际根与父目录；父目录用于发现根创建和替换，普通事件过滤邻接数据库写入，避免受管根缺失时自触发刷新循环。每次对账重建句柄，30 秒定时、重新激活和手动刷新提供漏事件补扫。UI 生命周期 `runID` 与存储 generation 分别隔离旧会话和旧提交；取消只撤销匹配代次。

监听的 C 上下文由 retain／release 配对管理，stream 创建与停止用锁串行，目录元数据探测放在锁外；已取消的重启请求先检查取消状态，不能停止当前新会话的 stream。69 项定向回归在 Address Sanitizer 下通过，双渠道标准 build-only 通过；不据此宣称实际 GUI 验收完成。

T07 新增 `SkillContentReader` 与 `SkillContentView`：选中条目才读取物理位置，文件预览逐段检查相对路径和符号链接；读取上限 1 MiB，目录预算 2000 条目／6 层，超限保留部分目录。文件以既有 `RepoFileSourcePreview` 只读显示，二进制／超限单独提示。MarkdownUI 的两类图片 provider 均被替换，不自动读取本机图片或请求远端；只有明确点击的 HTTP(S) 链接交给浏览器。后台读取结果按详情请求隔离，失败保留既有内容和警告。55 项定向回归、双渠道标准 build-only、累计 40 key × 17 语言编译资源校验通过；译文仍为 `needs_review`。
