# Starcat 发展规划

> 本文档整理 dong4j 与 AI 协作者在 2026-06-01 围绕 Starcat 后续方向的一轮完整讨论。
>
> 文档目的不是写一份简短 roadmap，而是保留讨论中的背景、原始想法、产品判断、技术取舍和 UI 落地建议，供后续继续深入研究、拆分需求、更新详细设计和工程进度清单。

---

## 0. 核心定位调整

### 0.1 本轮讨论确认的产品方向

Starcat 后续不应只停留在“GitHub Star 收藏夹”，而应发展成：

> 面向开发者的本地优先开源项目知识库、项目情报订阅器与技术决策辅助工具。

这个定位包含四层含义：

1. **本地优先**：用户的 stars、标签、笔记、摘要、向量索引、技术选型报告、安全扫描结果默认存储在本机。
2. **第三方接口集成**：Starcat 可以集成 GitHub API、OSV API、GitHub Advisory Database、OpenAI-compatible API、Gemini、DeepSeek、Ollama、LM Studio 等，但不默认依赖 Starcat 自建服务端。
3. **围绕 GitHub 开源项目**：Starcat 可以轻量吸收 RSS / 周刊 / awesome list / GitHub Search 结果，但核心对象仍然是 GitHub repo。
4. **辅助工程判断**：AI 不只是生成摘要，而应帮助用户做项目理解、技术选型、安全风险判断、维护活跃度判断和后续研究整理。

### 0.2 明确不做的方向

本轮讨论明确收敛掉一个方向：

> 不默认设计 Starcat 官方服务端、AI Proxy、配额服务或内容推送服务。

dong4j 的原始判断：

> “前面说的关于服务端相关的功能，我并不建议，因为 Starcat 应用的定位是用户本地应用，更多是集成第三方接口，我并不打算自己服务器来提供服务，首先是成本不可控，另外是没有时间维护，所以更推荐使用本地服务。”

这个判断会影响此前文档中若干设计：

- `docs/AI代理API设计.md` 应降级为可选参考方案，而不是默认路线。
- `docs/概要设计.md` 中 “Starcat Pro 内置 AI 配额，通过自有服务转发” 需要重新评估。
- `docs/开发前问题清单.md` 已在 2026-06-13 按当前实现修订为“本地向量检索 + 用户自带 embedding provider”。
- `docs/详细设计/11-Phase2-AI与Release详细设计.md` 中服务端与本地向量路线冲突，需要统一。

### 0.3 推荐总架构

推荐架构：

```text
Starcat macOS App
├── 本地数据层
│   ├── SQLite / GRDB
│   ├── README 缓存
│   ├── AI 摘要缓存
│   ├── Embedding 向量缓存
│   ├── 安全扫描结果缓存
│   └── Discover 订阅结果缓存
├── 第三方接口层
│   ├── GitHub REST / GraphQL API
│   ├── GitHub Global Security Advisories
│   ├── OSV API
│   ├── 用户配置的 AI Provider
│   └── GitHub / RSS / Markdown 内容源
├── 本地分析层
│   ├── README / manifest 解析
│   ├── 语义搜索
│   ├── 项目健康度评分
│   ├── 技术选型分析
│   ├── 安全雷达
│   └── 周刊 / awesome list 项目提取
└── UI 工作流
    ├── Manage：管理已有 Stars
    ├── Trending：GitHub 热榜
    ├── Discover：项目情报订阅
    ├── Search：语义搜索与技术选型
    ├── Security：漏洞与风险
    └── Insights：健康度、维护活跃度、License、贡献机会
```

## 1. AI 功能 UI 设计

### 1.1 功能是什么

本轮讨论最初围绕 “Starcat 中 AI 相关功能应该怎么设计 UI” 展开。核心问题不是 AI 能做什么，而是 AI 应该如何嵌入 Starcat 的使用流程。

讨论结论：

> AI 不应被设计成一个独立聊天机器人，而应作为嵌入式助手，出现在用户阅读 repo、打标签、搜索、整理、技术选型和看推荐的上下文中。

Starcat 的主干仍然是三栏管理器：

```text
左栏：Manage / Trending / Search / Discover / Security / Insights
中栏：repo 列表、搜索结果、订阅结果、漏洞列表
右栏：repo 详情、AI 摘要、笔记、报告、风险详情
```

AI 的角色：

- 帮用户快速理解一个 repo。
- 帮用户推荐标签和分类。
- 帮用户解释搜索命中原因。
- 帮用户生成技术选型报告。
- 帮用户总结 release notes、周刊内容和项目风险。

### 1.2 价值

AI UI 的价值不在于 “有一个聊天框”，而在于降低已有工作流成本：

- 阅读 README 前，先获得一句话摘要和适用场景。
- 打标签时，不需要手动想标签体系。
- 搜索时，不只返回关键词匹配，还能解释为什么相关。
- 做技术选型时，不需要从几十个 Star 项目中手动拼对比表。
- 看开源项目推荐时，可以快速判断是否值得收藏或稍后研究。

### 1.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 独立 AI Chat 页 | 实现直观，用户容易理解 | 偏离 Starcat “项目管理”主题，容易变成泛聊天工具，聊天上下文和 repo 数据关系弱 | 不推荐作为主入口 |
| 详情页嵌入式 AI Tab | 和 repo 上下文强绑定，用户在阅读时直接使用 | 需要设计多个状态：未生成、生成中、失败、缓存、重新生成 | 推荐第一阶段实现 |
| 搜索页 AI 问答 | 适合自然语言搜索和技术选型 | 如果没有候选 repo 约束，容易生成泛泛答案 | 推荐作为 Search 的高级模式 |
| 批量整理 AI Wizard | 适合处理 Untagged、大量 stars | 成本、等待、失败重试复杂 | 推荐第二阶段实现 |
| 全局 AI Command Palette | 高级用户效率高 | 学习成本较高，初期价值不明显 | 后续增强 |

### 1.4 推荐技术方案

第一版推荐实现三个 UI 能力：

1. **右侧详情页 `AI 摘要` Tab**
   - 单仓 AI 摘要。
   - 推荐标签。
   - 平台识别。
   - 优缺点和风险。
   - 最小示例。

2. **标签推荐确认 Popover**
   - 出现在详情页 Tags 区域旁边。
   - 每个推荐标签显示置信度和原因。
   - 用户逐个确认或全部应用。

3. **Search 页混合搜索解释**
   - 搜索结果显示 “命中原因”。
   - AI 不直接替用户决定，只解释为什么这些 repo 相关。

技术上：

- 本地组装 prompt。
- 用户配置 AI Provider。
- 结果写入本地 SQLite。
- 生成状态和错误状态都保存在 ViewModel 内，不要阻塞主界面。

### 1.5 UI 落地建议

右侧详情页建议结构：

```text
Repo Detail
├── 顶部元信息
├── Tags / Notes / Status
└── Tab
    ├── README
    ├── AI 摘要
    └── Notes
```

`AI 摘要` Tab：

```text
一句话总结
这个项目是什么？

适合场景
- ...

推荐标签
[Swift +] [macOS +] [Local-first +]

优点
- ...

风险
- ...

最小示例
[展开]

由 deepseek-chat 生成 · 2026-06-01 · 重新生成
```

未生成状态：

```text
尚未生成 AI 摘要
将读取 repo 元数据、README、topics 和用户笔记。

[生成摘要]
预计消耗 1 次 AI 调用
```

设计约束：

- 不自动批量生成所有 repo。
- “重新生成”弱化，避免误触消耗额度。
- AI 标签永远不直接落库，必须用户确认。
- AI 结果必须显示生成时间、模型和缓存状态。
- AI 视觉应克制，不要整页紫色或过度使用 sparkle 风格。

## 2. AI 与本地服务架构

### 2.1 功能是什么

本轮讨论中曾提到自建 AI 代理、服务端语义搜索和配额服务，但 dong4j 明确否定了这个方向。

原始想法：

> Starcat 应用的定位是用户本地应用，更多是集成第三方接口，不打算自己服务器提供服务。原因是成本不可控，也没有时间维护，所以更推荐使用本地服务。

因此，Starcat 的 AI 能力应采用本地优先方案：

- AI Key 存本地。
- Prompt 在本地组装。
- 直接调用用户配置的第三方 API 或本地模型。
- 结果本地缓存。
- 向量索引本地保存。
- 不维护 Starcat 官方用户系统、quota 系统和代理服务。

### 2.2 价值

本地优先架构对 Starcat 很重要：

- **隐私**：用户 stars、笔记、技术选型报告、AI Key 不经过 Starcat 服务器。
- **成本可控**：不需要维护 AI 代理、数据库、Redis、监控、计费。
- **维护简单**：Starcat 只维护客户端逻辑和第三方接口适配。
- **定位清晰**：Starcat 是本地知识库，而不是 SaaS。
- **可扩展**：高级用户可接 OpenAI-compatible、Ollama、LM Studio、DeepSeek、Gemini、OpenRouter。

### 2.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| Starcat 自建 AI Proxy | 可统一模型、统一计费、隐藏模型 Key | 运维成本高，需要账户、配额、风控、日志、服务稳定性；与本地应用定位冲突 | 不推荐默认路线 |
| BYOK 第三方 API | 成本由用户承担，Starcat 无需维护服务端；适合隐私敏感和重度用户 | 配置门槛高；不同 Provider API 差异需要适配 | 推荐主路线 |
| 本地模型 Ollama / LM Studio | 数据不出本机，适合离线和隐私场景 | 模型质量、速度、硬件要求不稳定 | 推荐作为可选高级模式 |
| Apple 本地模型能力 | 原生体验好，未来潜力大 | 当前能力边界和可用性需按系统版本评估 | 后续观察 |
| MCP / 本地 CLI 工具链 | 适合接 Repomix、Gitingest、OSV Scanner | 工具安装和路径管理复杂 | 后续增强 |

### 2.4 推荐技术方案

推荐设置页支持：

```text
AI Provider
├── 本地模型
│   ├── Ollama
│   └── LM Studio / OpenAI-compatible localhost
├── 第三方 API
│   ├── OpenAI-compatible
│   ├── DeepSeek
│   ├── Gemini
│   └── OpenRouter
└── 嵌入模型
    ├── 本地 embedding
    └── 第三方 embedding API
```

统一抽象：

```swift
protocol AIServiceProtocol {
    func summarizeRepo(_ request: RepoSummaryRequest) async throws -> RepoSummary
    func recommendTags(_ request: TagRecommendationRequest) async throws -> [AITagRecommendation]
    func generateEmbedding(_ request: EmbeddingRequest) async throws -> [Float]
    func compareProjects(_ request: ProjectComparisonRequest) async throws -> ProjectComparisonReport
}
```

存储：

- API Key 继续复用现有加密凭证存储。
- AI 设置进入 `AppSettings` 或单独 `AISettingsRepository`。
- AI 结果进入本地 SQLite。

### 2.5 UI 落地建议

设置页新增 `AI` Tab：

```text
[OpenAI Compatible v]
```

## 3. 开源项目分析工具集成

### 3.1 功能是什么

dong4j 提出：

> “我记得是有专门用于分析 GitHub 开源项目的一些开源项目，比如我知道的就有 CodeFlow 这个开源项目。我在考虑是否可以引入一些开源项目来分析用户已经 star 的项目。”

这个功能的本质是：Starcat 不仅保存用户 star 的项目，还能借助现有开源工具对这些项目做结构化分析。

可分析内容包括：

- README 摘要。
- 技术栈识别。
- 目录结构。
- 依赖图。
- 项目健康度。
- 安全风险。
- 架构图。
- 可用于技术选型的优缺点。

### 3.2 价值

Starcat 的用户通常 star 了很多项目，但问题是：

- 收藏时觉得有用，之后很难找回。
- 看 README 成本高。
- 不知道项目是否还活跃。
- 不知道是否适合引入生产项目。
- 不知道同类项目之间怎么选。

开源项目分析工具可以把 “收藏项目” 转化为 “可检索、可比较、可决策的知识资产”。

### 3.3 可参考开源项目

| 项目 | 主要能力 | 适合 Starcat 的用途 | 集成判断 |
|---|---|---|---|
| CodeFlow | 架构图、依赖图、blast radius、安全扫描、模式检测、健康分 | 深度分析单个 repo | 可研究，不建议第一版直接嵌入 |
| Repomix | 将 repo 打包成 LLM 友好文本，支持远程 repo、Secretlint、Tree-sitter 压缩 | AI 摘要、技术选型、深度分析前的上下文生成 | 推荐优先试点 |
| Gitingest | 将 GitHub repo 转成 prompt-friendly digest，CLI / Python 包 | 快速生成 repo digest | 推荐轻量试点 |
| RepoLens | AI repo 分析、代码浏览、问题扫描、架构图、文档生成 | 产品形态参考 | 借鉴 UX，不作为第一阶段依赖 |
| CodeBoarding | 静态分析 + LLM 架构图、组件文档、Mermaid | 大型项目架构理解 | 后期深度分析可研究 |
| RepoMind | repo chat、架构图、安全扫描 | “对 repo 提问”体验参考 | 不作为第一阶段依赖 |
| OpenSSF Scorecard | 开源项目安全与维护实践评分 | 健康度 / 安全基础指标 | 可以直接集成 |

### 3.4 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 直接集成完整开源项目 | 快速获得完整能力 | 依赖重、语言栈复杂、UI/数据模型难以融合、维护风险高 | 不推荐第一版 |
| 调用本地 CLI | 边界清晰，不侵入 Swift 代码；工具可独立升级 | 需要处理安装、路径、权限、错误输出 | 推荐可选增强 |
| 只借鉴算法和输出格式 | 可控、符合 Starcat 架构 | 初期开发量较大 | 核心能力可逐步自研 |
| 远程服务调用 | 用户无安装负担 | 与本地优先定位冲突 | 不推荐 |

### 3.5 推荐技术方案

采用分层分析：

```text
Level 1：元数据分析
├── GitHub API
├── License
├── Community Profile
├── Releases
├── Issues / PR 活跃度
└── 不 clone 代码，默认可批量跑

Level 2：README + Manifest 分析
├── README
├── package.json / go.mod / Cargo.toml / Package.swift / pom.xml
├── 技术栈识别
├── AI 摘要
└── 可对较多 repo 按需跑

Level 3：完整代码图谱分析
├── Repomix / Gitingest / CodeFlow
├── 目录结构
├── 依赖图
├── 安全扫描
├── 架构图
└── 只对用户手动选择的 repo 跑
```

第一版推荐：

1. 先用 GitHub API + README + manifest 做轻量分析。
2. 再提供 “深度分析这个仓库” 按钮。
3. 深度分析优先试点 Repomix 或 Gitingest。
4. CodeFlow 作为后续深度能力研究对象。

### 3.6 UI 落地建议

右侧详情页新增 `Analysis` 或并入 `AI 摘要`：

```text

基础信息

```

```text

```

## 4. 技术选型助手

### 4.1 功能是什么

dong4j 提出：

> “我觉得还有几个功能可以做：技术选型分析，比如我们要开发某个系统，需要用到某个技术时，可以先借助 Starcat 语义搜索给出建议的项目，然后再使用 AI 对这些项目或技术做技术选型。”

这是本轮讨论中最具差异化的功能之一。

它不是简单的 “问 AI 用什么技术”，而是基于用户自己的 Stars、Discover 订阅源、Trending、GitHub Search 和项目分析结果，生成有依据的技术选型建议。

典型场景：

```text
我要开发一个 macOS 本地优先应用，需要选择本地数据库和云同步方案。
```

Starcat 可以先找出候选项目：

- GRDB.swift
- SQLite.swift
- SwiftData 示例项目
- Core Data / CloudKit sample
- Realm Swift
- Supabase Swift

然后生成对比报告。

### 4.2 价值

这个功能把 Starcat 从 “项目收藏工具” 推进到 “工程决策辅助工具”：

- 用户不需要从头搜索资料。
- 用户已有的 Stars 成为技术选型素材。
- AI 结论有 repo、README、release、issue、license、健康度作为依据。
- 选型报告可以保存，后续作为 ADR 或项目文档草稿。

它比泛 AI 答案更可信，因为分析范围可控，候选项目可见，依据可追溯。

### 4.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 直接让 AI 回答选型问题 | 实现简单 | 容易泛化、不可追溯、和用户 stars 关系弱 | 不推荐 |
| 先语义搜索候选 repo，再 AI 分析 | 有事实依据，符合 Starcat 数据优势 | 需要语义搜索和候选确认 UI | 推荐 |
| 纯规则评分 | 稳定、成本低 | 难处理复杂需求语义 | 可作为辅助 |
| 深度代码分析后选型 | 结果更细 | 成本高、速度慢，不适合默认流程 | 作为高级模式 |

### 4.4 推荐技术方案

推荐流程：

```text
用户输入目标
```

## 5. 安全雷达：Star 项目漏洞监控

### 5.1 功能是什么

dong4j 提出：

> “我记得 GitHub 有一个通知功能，用于报告哪些库又有什么漏洞了。是否可以集成到 Starcat，用于报告用户 star 的项目的漏洞？”

这里要区分两类能力：

1. **GitHub Dependabot Alerts**
   - 主要面向用户拥有、维护或有安全权限的仓库。
   - 不能简单读取所有 starred repo 的 Dependabot alert。

2. **Starred repo 安全风险监控**
   - 使用 GitHub Global Security Advisories、OSV、manifest / lockfile 分析，自己做公开漏洞匹配。
   - 更适合 Starcat。

### 5.2 价值

Starcat 用户 star 项目的原因往往是未来可能使用或参考。安全雷达可以帮助用户判断：

- 某个项目是否近期有高危漏洞。
- 某个依赖是否长期存在安全问题。
- 某个项目是否适合进入技术选型候选。
- 已收藏项目中哪些需要关注。

这比 “AI 周报” 更刚需，也更贴合开发者工具属性。

### 5.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| Dependabot Alerts API | 官方、准确 | 权限受限，只覆盖用户有权限的 repo | 用于自有仓库，不覆盖普通 stars |
| GitHub Global Security Advisories | 官方公开漏洞库，可查 GHSA / CVE | 需要自己关联 repo / package / version | 推荐 |
| OSV API | 聚合多生态漏洞源，支持 batch query | 仍需解析依赖和版本 | 推荐 |
| 本地 OSV Scanner CLI | 能直接扫 manifest / lockfile | 需要安装工具，运行成本高 | 可选增强 |
| 自建漏洞数据库 | 查询可控 | 维护成本高，违背本地优先 | 不推荐 |

### 5.4 推荐技术方案

分三层：

```text
Layer 1：公开漏洞关联
├── GitHub Global Security Advisories
├── 按 package / ecosystem / severity 查询
└── 适合轻量扫描

Layer 2：依赖清单扫描
├── package-lock.json
├── pnpm-lock.yaml
├── yarn.lock
├── requirements.txt
├── poetry.lock
├── pyproject.toml
├── go.mod / go.sum
├── Cargo.lock
├── Package.resolved
├── pom.xml
└── 调 OSV querybatch

Layer 3：自有仓库告警聚合
├── Dependabot Alerts API
├── Code scanning
├── Secret scanning
└── 仅用户有权限时展示
```

第一版推荐：

- 先接 OSV API + GitHub Global Security Advisories。
- 只扫 repo 根目录 manifest / lockfile。
- 没有 lockfile 时标注 “版本不确定”。
- 支持 high / critical 筛选。
- 支持忽略、稍后提醒。

### 5.5 UI 落地建议

左侧顶层新增：

```text

```

中栏：

```text

[Critical] [High] [Medium] [Recently Published]

```

右侧：

```text

Fixed: 4.17.21

- 在 package-lock.json 中发现 lodash 4.17.20
- 该版本匹配 OSV 漏洞范围

操作
[打开 Advisory] [忽略] [稍后提醒]
```

设计约束：

- 不要制造恐慌，漏洞不等于可利用。
- 必须显示 “影响依据”。
- 不默认 clone 全仓库。
- 扫描结果要本地缓存。
- 默认只提示 high / critical，避免噪音。

## 6. GitHub API 可扩展功能

### 6.1 功能是什么

讨论中进一步追问：

> “GitHub 还开放了哪些 API，可以用于 Starcat 集成的，用于开发更多围绕 Starcat 这个应用主题的实用功能？”

这个问题的核心是：Starcat 可以借助 GitHub 官方 API，从 Star 管理扩展成开源项目情报工具。

### 6.2 可用 API 与功能方向

| API / 数据源 | 可做功能 | 价值 |
|---|---|---|
| Repository metadata | 基础 repo 信息、stars、forks、archived、pushed_at | Starcat 基础数据 |
| README / Contents API | README、manifest、配置文件读取 | 摘要、技术栈识别、安全扫描 |
| Releases API | Release 时间线、订阅、资产过滤 | 版本跟踪 |
| Issues / Pull Requests API | 活跃度、维护响应、贡献机会 | 健康度和贡献机会 |
| Repository statistics | commit 活跃度、贡献者、代码频率 | 维护活跃度 |
| Community Profile API | README、License、CONTRIBUTING、Code of Conduct 完整度 | 项目健康度 |
| Topics / Languages | 分类、语义搜索、技术栈识别 | 标签和推荐 |
| Search API | 外部候选项目发现 | 技术选型、Discover 搜索任务 |
| Notifications / Watching API | GitHub 通知聚合、watch 管理 | 轻量通知中心 |
| Global Security Advisories | GHSA / CVE 漏洞查询 | 安全雷达 |
| Dependency Graph / SBOM | 依赖清单、安全风险 | 高级安全分析 |
| Code scanning / Secret scanning | 自有仓库安全扫描结果 | 自有仓库风险聚合 |
| Licenses API | License 合规判断 | 技术选型和商用风险 |

### 6.3 功能优先级建议

第一批，低成本高价值：

1. 项目健康度评分。
2. Release 订阅增强。
3. License / 社区完整度检查。
4. 维护活跃度雷达。

第二批，差异化强：

1. 安全雷达。
2. 技术选型助手。
3. AI 项目对比报告。
4. 贡献机会发现。

第三批，高级能力：

1. SBOM / 依赖图。
2. 自有仓库安全告警聚合。
3. GitHub 通知中心。
4. 开源项目风险评分模型。

### 6.4 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 只使用 REST API | 实现简单，和现有网络层一致 | 批量查询字段多时请求数较高 | 第一阶段推荐 |
| 引入 GraphQL | 可一次查多类字段，适合复杂列表 | 查询语句、分页和错误处理更复杂 | 后续优化 |
| 定时全量同步所有扩展数据 | 数据完整 | API 配额压力大，耗时长 | 不推荐 |
| 按需抓取 + 本地缓存 | 成本低，符合本地应用 | 首次打开详情可能有加载过程 | 推荐 |

### 6.5 推荐技术方案

使用 “按需抓取 + 本地缓存 + 局部批量刷新”：

```text
打开 repo 详情
  ↓
读取本地缓存
  ↓
缓存缺失或过期时请求 GitHub API
  ↓
写入本地 SQLite
  ↓
UI 无感更新
```

对于列表级指标：

- Stars / forks / pushed_at 已在基础 sync 中获取。
- 健康度、release、security 等延迟加载。
- 用户可在设置中配置后台刷新频率。

## 7. 热门项目推荐与轻量项目情报订阅

### 7.1 功能是什么

dong4j 提出：

> “我还想到一个功能：热门项目推荐，不是现在的 Trending 项目。因为我发现其实现在的很多自媒体博主也在走这条路：会自己去发现一些项目，然后拍视频推荐这个项目。现在的一些 AI 自动化工具，也会提供这个订阅热门开源项目的定时任务，每天推送一次。Starcat 其实也可以做一个专栏，可以是 AI 定时搜索总结的结果，也可以是通过某种方式来接受推送结果的。比较流行的是 weekly，GitHub 上也有开源仓库，一些爱好者收集一些比较有趣的应用或开源项目，每周定时推送一次，比如 ruanyf/weekly。那 Starcat 就相当于一个轻量级的 RSS 客户端，必须是轻量级，主要用于收集 GitHub 开源项目。”

这个功能可以定义为：

> Discover：面向 GitHub 开源项目的轻量情报订阅器。

它和现有 Trending 的区别：

| 维度 | Trending | Discover |
|---|---|---|
| 来源 | GitHub 热度榜 | 周刊、awesome list、GitHub Search、个人精选源 |
| 逻辑 | 热度排序 | 人类精选 + 用户偏好 + AI 整理 |
| 内容 | 当前流行项目 | 有解释、有来源、有推荐理由的项目 |
| 使用方式 | 浏览 | 订阅、已读、稍后看、收藏、研究 |

### 7.2 价值

这个功能非常契合 Starcat：

- 用户不只是管理已有 stars，还能发现新项目。
- 周刊和 awesome list 本来就是 GitHub 项目发现的重要来源。
- Starcat 可以统一去重、摘要、打标签、收藏、稍后看。
- 不需要自建内容平台，只需订阅公开 GitHub 仓库或用户自定义源。
- 对 dong4j 自己也有价值：可以维护一个公开 GitHub feed repo，让 Starcat 用户订阅。

### 7.3 订阅源类型

第一类：GitHub 周刊源

示例：

```text
ruanyf/weekly
```

Starcat 定时读取：

- README 期数索引。
- `docs/issue-xxx.md`。
- issue 投稿区。
- Markdown 中的 GitHub repo URL。

第二类：Awesome / Curated List 源

示例：

```text
awesome-selfhosted/awesome-selfhosted
public-api-lists/public-api-lists
awesome-mac/awesome-mac
```

Starcat 扫描 README，提取 GitHub 链接，并记录来源。

第三类：GitHub Search 任务源

示例：

```text
关键词：macOS SwiftUI local-first
语言：Swift
Star 增长：最近 7 天 > 50
排除：tutorial, toy, archived
频率：每天一次
```

第四类：自定义 Starcat Feed

dong4j 可以维护一个公开 GitHub 仓库：

```text
dong4j/starcat-feeds
```

每周提交一个 Markdown 或 JSON：

```text
feeds/2026/week-23.md
```

Starcat 用户订阅这个 repo，本地定时拉取。

第五类：主题频道（Topic Channels）

dong4j 进一步补充：

> “既然都可以推荐优质的开源项目了，那是不是可以做一个分类，比如 Skill / MCP 等，这 2 个应该算现在比较火的了，可以独立出来。”

这意味着 Discover 不应该只是按来源分组，也应该按技术主题分组。来源回答“从哪里来”，主题频道回答“这个项目属于什么方向”。

首批可以内置两个热点频道：

```text
Skill
MCP
```

原因：

- **Skill**：围绕 AI Agent 的可复用能力包、工作流、提示词、工具调用封装正在快速增长，适合单独收集。
- **MCP**：Model Context Protocol 已成为 AI 工具连接外部系统的重要协议，MCP server / client / registry / SDK / integration 项目增长快，值得独立订阅和研究。

主题频道不是固定死的分类，而是一套可配置规则：

```text
TopicChannel
├── Skill
│   ├── keywords: skill, agent skill, codex skill, claude skill
│   ├── githubTopics: ai-agent, skill, prompt-engineering
│   └── feeds: skill registry / awesome skill list
├── MCP
│   ├── keywords: mcp, model context protocol, mcp server
│   ├── githubTopics: mcp, model-context-protocol
│   └── feeds: mcp registry / awesome mcp servers
├── AI Agent
├── Local-first
├── macOS Apps
└── Developer Tools
```

频道内的项目可以来自多种来源：

- GitHub Search 定时任务。
- Discover feed 中解析出的项目。
- awesome list。
- anysearch / Jina Search 的网络搜索结果。
- 用户手动加入。
- Starcat AI 根据 README / topics / description 自动归类。

频道的关键价值是让 Discover 从“信息流”变成“可研究的专题库”。

### 7.4 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 完整 RSS 客户端 | 通用性强 | 容易偏离 Starcat，变成 Reeder / NetNewsWire 竞品 | 不推荐 |
| 只订阅 GitHub repo Markdown | 简单、稳定、贴合 GitHub 项目 | 对非 GitHub 内容支持弱 | 推荐第一版 |
| 支持 RSS，但只抽取 GitHub 链接 | 可接更多内容源 | 需要 RSS 解析和去噪 | 第二阶段 |
| 自建推送服务 | 可控、体验好 | 运维成本高，违背本地优先 | 不推荐 |
| 公开 GitHub feed repo | 无服务器、可版本化、用户可 fork | 更新依赖 GitHub 拉取 | 推荐 |
| 内置主题频道 | 对热点方向有更强组织能力，适合 Skill / MCP 这类快速变化主题 | 需要维护频道规则，可能随热点变化过时 | 推荐 |
| 完全 AI 自动分类 | 可扩展性强 | 分类不稳定，解释性差 | 作为辅助，不作为唯一依据 |

## 8. 混合语义搜索与本地向量索引

### 8.1 功能是什么

dong4j 在阅读本节后进一步补充：

> “语义搜索不只是从已 star 的项目中搜索，而应该结合网络搜索结果，比如使用 anysearch 这个工具，返回的结构化数据很适合 LLM 总结，还有比如 Jina 提供的 API 等。我的意思是这个功能可以做得更优化，因为用户想了解某个技术或技术选型时，他还没有 star 项目，那就肯定搜索不到，所以肯定要结合网络结果来给出结果，结果展示也需要优化，可以让用户直接 star 操作入库。”

因此，Starcat 的语义搜索不应被理解成“只在本地 Stars 中搜索”，而应升级为：

> 混合语义搜索：同时搜索本地知识库、Discover 已收集项目和网络搜索结果，并把可用项目沉淀进 Starcat。

它是多个高级功能的基础：

- 技术选型助手需要先找候选项目。
- Discover 需要找相似项目。
- AI 摘要需要被检索。
- 用户希望用自然语言搜索 stars。
- 用户研究一个新技术时，可能本地没有任何相关 Star，需要从网络发现候选项目。
- 网络搜索结果可以被 LLM 总结、筛选、去重，再进入 Starcat 的候选池。

示例：

```text
找适合做 macOS 菜单栏工具的 Swift 项目
```

Starcat 不应只匹配关键词 `macOS` 或 `Swift`，而应理解：

- 菜单栏应用。
- SwiftUI / AppKit。
- MenuBarExtra。
- macOS utility。
- 本地应用。

同时，它也应该能在本地没有命中时继续向外查找：

```text
本地 Stars：没有找到足够候选
Discover 缓存：找到 2 个候选
网络搜索：找到 8 个 GitHub 项目和 3 篇技术选型文章
```

搜索结果不应只展示网页链接，而要尽量转化为 Starcat 可操作的项目卡片：

- 这是 GitHub repo 吗？
- 是否已经 Star？
- 是否已在本地数据库？
- 能否一键 Star 入库？
- 是否适合加入技术选型候选？
- 来源是本地、Discover、GitHub Search、anysearch 还是 Jina Search？

### 8.2 价值

对于拥有大量 stars 的用户，关键词搜索不足以解决问题：

- repo 名称不一定包含用途。
- README 里可能用不同表述。
- 用户笔记和 AI 摘要是更好的检索材料。
- 技术选型场景需要“意图搜索”。

但只查本地也不够。很多真实场景是：

- 用户正准备了解一门新技术，本地还没有收藏相关项目。
- 用户要做技术选型，需要补充自己 stars 之外的候选项目。
- 用户只记得一个技术方向，不知道具体 repo 名称。
- 用户想比较生态现状，需要结合网络搜索、GitHub Search 和周刊推荐结果。

混合语义搜索的价值是：

- **找回已有知识**：从本地 Stars、笔记、标签、AI 摘要中找回项目。
- **发现未知项目**：从网络搜索和 GitHub Search 中发现尚未 Star 的项目。
- **形成候选池**：搜索结果可直接进入技术选型、Discover 或 Stars。
- **沉淀用户资产**：外部结果经过 Star / 稍后看 / 加入候选后进入本地数据库，不再只是一次性网页搜索。
- **提升 AI 报告质量**：技术选型报告不局限于用户已经收藏的项目，能补充外部生态信息。

### 8.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 纯 FTS5 | 本地、快、无需 AI | 只能关键词匹配，不理解语义 | 保留作为基础 |
| 只查本地 embedding | 隐私好、可离线、结果可控 | 对新技术和未收藏项目无能为力 | 作为基础能力，不应是唯一来源 |
| GitHub Search API | 官方、直接返回 repo，可 Star 入库 | 搜索语义有限，排序偏关键词和 GitHub 热度 | 推荐接入 |
| anysearch / 搜索聚合工具 | 返回结构化结果，适合 LLM 总结和 rerank | 依赖第三方接口或本地工具可用性，需要抽象适配层 | 推荐作为可选 Web Search Provider |
| Jina Reader / Search API | 可把网页或搜索结果转成 LLM-friendly Markdown，适合总结和 grounding | 外部服务，需考虑速率、成本和隐私；结果仍需过滤 GitHub repo | 推荐作为可选 Provider |
| Jina Embeddings / 第三方 Embedding API | 多语言语义效果好，接入成本低 | 文本会发给第三方；模型维度和价格会变化 | 可作为 embedding provider 之一 |
| 本地生成 embedding + 内存 Top-K | 实现简单，几千 stars 足够 | 大数据量性能一般 | 推荐第一版 |
| SQLite + sqlite-vec | 本地索引能力强，可扩展 | 引入 native extension、打包和兼容性复杂 | 第二阶段 |
| 外部向量数据库 | 功能完整 | 过重，不适合本地轻应用 | 不推荐 |
| Starcat 自建搜索服务 | 体验可控 | 违背本地优先，维护和成本不可控 | 不推荐 |

### 8.4 推荐技术方案

推荐把搜索范围拆成三层：

```text
Search Scope
├── Local
│   ├── 已 Star 仓库
│   ├── README 缓存
│   ├── 用户笔记
│   ├── 标签
│   ├── AI 摘要
│   └── 本地 embedding
├── Library
│   ├── Discover 已收集项目
│   ├── 周刊 / awesome list 解析结果
│   ├── 稍后看
│   └── 已忽略项目（默认不展示，可恢复）
└── Web
    ├── GitHub Search API
    ├── anysearch Provider
    ├── Jina Search / Reader
    └── 用户后续配置的其他搜索 Provider
```

第一版推荐做 “Local + GitHub Search”：

```text
用户输入自然语言 query
  ↓
Local Search
  ├── FTS5 关键词搜索
  ├── 本地 embedding Top-K
  └── RRF 融合
  ↓
若结果不足 / 用户选择扩展到网络
  ↓
GitHub Search API
  ├── search/repositories
  ├── language / stars / pushed / license 过滤
  └── 返回 repo 候选
  ↓
结果归一化为 SearchResultItem
  ↓
LLM rerank / summarize（可选）
  ↓
展示并允许 Star / 稍后看 / 加入技术选型候选
```

第二版加入 Web Search Provider 抽象：

```swift
protocol WebSearchProvider {
    func search(_ request: WebSearchRequest) async throws -> [WebSearchResult]
}
```

Provider 类型：

```text
GitHubSearchProvider
AnysearchProvider
JinaSearchProvider
CustomSearchProvider
```

搜索结果统一成两类：

```text
RepoCandidate
├── owner
├── name
├── htmlURL
├── description
├── language
├── starsCount
├── license
├── source
├── isStarred
├── isInLocalDatabase
└── matchReason

ReferenceCandidate
├── title
├── url
├── snippet
├── source
├── extractedRepoURLs
└── summary
```

第三版加入 Jina / anysearch / Reader 类能力：

- anysearch 负责返回结构化 web 搜索结果，适合交给 LLM 总结和 rerank。
- Jina Search 可用于 grounding 查询，把搜索结果转成 LLM 友好的文本。
- Jina Reader 可用于读取外部技术文章、README、awesome list 页面。
- Jina Embeddings 可作为用户可选 embedding provider。

本地向量索引仍然保留：

```text
Embedding 生成
├── 用户配置 Provider
├── 对 repo description / README 摘要 / notes / tags 生成向量
├── 对 Discover 已收集项目生成向量
└── 存入 SQLite BLOB

本地检索
├── FTS5 得到关键词结果
├── 内存计算 query embedding 与 repo embedding cosine similarity
├── RRF 融合排序
└── 返回命中原因
```

后续优化：

- 如果 stars 数量明显增长，再引入 `sqlite-vec`。
- 向量生成队列支持暂停、失败重试和增量更新。
- 网络搜索结果只有用户执行 Star、稍后看、加入候选、保存来源时才正式入库，避免污染本地库。
- 对同一个 `owner/repo` 做全局去重，避免本地、Discover、GitHub Search、Web Search 重复展示。

### 8.6 入库与状态设计

网络搜索结果进入 Starcat 时要区分几个状态：

```text
未入库
├── 只展示本次搜索结果

稍后看
├── 存入 Discover / Saved for Later
├── 不调用 GitHub Star
└── 可生成 AI 摘要和 embedding

Star 入库
├── 调用 GitHub star API
├── 写入本地 repos / starred_repos
├── 拉取 README / metadata
└── 可打标签、写笔记、进入常规管理流

加入技术选型候选
├── 存入当前技术选型 session
├── 不一定 Star
└── 报告生成后可选择是否收藏
```

推荐 UI 规则：

- `[Star 入库]` 是明确动作，会调用 GitHub API。
- `[稍后看]` 只存本地，不污染 GitHub Stars。
- `[加入技术选型]` 是临时研究动作，不等于收藏。
- 已 star 的网络候选显示 `[已 Star] [打开详情]`。
- 网络结果默认不生成 embedding，只有用户保存后才生成。

### 8.7 与技术选型助手的关系

技术选型助手不应该只依赖本地 Stars。推荐流程更新为：

```text
用户输入技术选型目标
  ↓
先查本地 Stars / Discover
  ↓
若候选不足，提示扩展网络搜索
  ↓
GitHub Search / anysearch / Jina Search 补候选
  ↓
用户确认候选项目
  ↓
Starcat 拉取 README / metadata / release / license
  ↓
AI 生成对比报告
  ↓
用户可 Star 入库或仅保存报告
```

UI 提示：

```text
本地只找到 2 个候选项目，可能不足以完成技术选型。

[扩展到网络搜索]
将使用 GitHub Search / anysearch / Jina 查找更多候选项目。
```

这样 Starcat 的 Search 不只是 “找回已有收藏”，而是完整支持：

- 找回。
- 发现。
- 研究。
- 收藏。
- 技术决策。

## 9. 项目健康度、维护活跃度与 License 风险

### 9.1 功能是什么

这个功能来自 GitHub API 扩展讨论。Starcat 可以为每个 repo 提供基础风险画像：

- 项目是否仍活跃。
- 文档是否完整。
- 是否有 License。
- 是否长期没有 release。
- issue 是否积压。
- 是否单维护者风险。

### 9.2 价值

用户 star 项目时往往只看当时是否有趣，但技术选型时需要更多事实依据。

健康度指标可以服务：

- 详情页快速判断。
- 技术选型对比矩阵。
- Discover 推荐排序。
- Security 风险解释。

### 9.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| 只展示 GitHub 原始字段 | 简单透明 | 用户仍需自己判断 | 基础能力 |
| Starcat 本地规则评分 | 可解释、成本低 | 分数模型需要迭代 | 推荐 |
| AI 生成健康度结论 | 表达自然 | 可能不稳定，必须有依据 | 作为解释层 |
| OpenSSF Scorecard | 专业、公开标准 | 对部分 repo 支持和调用成本需评估 | 可选增强 |

### 9.4 推荐技术方案

使用规则评分 + AI 解释：

```text
Health Score
├── 活跃度：最近 push / commit / release
├── 文档：README / license / contributing / issue template
├── 社区：issues / PR 响应
├── 风险：archived / no license / stale release
└── 安全：known advisories / scorecard
```

AI 只用于生成说明：

```text
该项目维护活跃，但 release 频率低。适合作为参考或内部工具依赖，生产引入前建议检查 issue 响应速度。
```

### 9.5 UI 落地建议

详情页顶部指标：

```text
Health 82
Maintenance Active
License MIT
Security No critical known
Latest Release 3 days ago
```

Insights 页面：

```text
Insights
├── 最近恢复活跃
├── 长期无人维护
├── 无 License
├── Issue 积压严重
└── 适合贡献
```

> 实施拆分见 [详细设计 17：项目健康度与维护活跃度设计](详细设计/17-项目健康度与维护活跃度设计.md)（HOM-92 父任务沉淀），6 个子任务覆盖：扩展数据缓存、评分规则、维护指标、License 风险、Insights UI、AI 解释。

## 10. Release 订阅追踪

### 10.1 功能是什么

Release 订阅原本已经在 Starcat P1 规划中，本轮讨论把它进一步放到本地优先架构下确认：

- 用户订阅某些 repo 的 release。
- Starcat 本地定时轮询 GitHub Releases API。
- 有新 release 时显示时间线和本地通知。
- 可按平台 / 文件类型过滤 release assets。

### 10.2 价值

Release 订阅是 Starcat 区别于普通 Star 列表的重要能力：

- 用户不需要 watch 所有 repo。
- 只关注自己真正使用或研究的项目。
- 可以过滤 macOS / arm64 / dmg / zip 等资产。
- 可结合 AI 总结 release notes。

### 10.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| GitHub Notifications | 官方通知体系 | 噪音大，watch 语义和 star 不同 | 可选补充 |
| 本地轮询 Releases API | 可控、只关注订阅 repo | 需要处理频率、ETag、后台调度 | 推荐 |
| 自建推送服务 | 实时性好 | 运维成本高 | 不推荐 |
| RSS / Atom release feed | 简单 | 字段和过滤能力有限 | 可作为 fallback |

### 10.4 推荐技术方案

```text
release_subscriptions
├── repo_id
├── is_subscribed
├── last_check_at
├── last_version
├── notify_enabled
└── etag

releases
├── id
├── repo_id
├── tag_name
├── name
├── body
├── prerelease
├── published_at
├── html_url
└── assets_json
```

本地调度：

- 使用 `NSBackgroundActivityScheduler`。
- 手动刷新按钮。
- ETag 条件请求。
- 默认低频轮询，例如 4-6 小时。

### 10.5 UI 落地建议

Sidebar：

```text
Releases
├── Timeline
├── Unread
├── Subscriptions
└── Assets
```

详情页按钮：

```text
[订阅 Release] / [取消订阅]
```

Release 时间线：

```text
owner/repo v1.2.0
3 hours ago

变更摘要
- 修复 ...
- 新增 ...

Assets
[macOS arm64 dmg] [copy link]
```

## 11. 贡献机会发现

### 11.1 功能是什么

贡献机会发现是 GitHub API 扩展中提出的后续能力：

- 在用户已 star 或 Discover 项目里查找 `good first issue`。
- 查找 `help wanted`。
- 查找长期无人处理但适合贡献的问题。
- 结合用户技术偏好推荐开源贡献任务。

### 11.2 价值

很多开发者 star 项目不只是为了使用，也可能为了学习和参与。Starcat 可以帮助用户从收藏走向参与。

### 11.3 技术选型对比

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| Issues API 按 label 查询 | 简单直接 | label 不规范 | 推荐第一版 |
| Search Issues API | 可跨 repo 搜索 | 有速率限制 | 可选 |
| AI 判断 issue 是否适合 | 更智能 | 成本高，结果不稳定 | 后续增强 |

### 11.4 推荐技术方案

第一版：

- 只在用户手动打开 `Contribution` 页面时拉取。
- 默认查 starred repo 中含 `good first issue` / `help wanted` 的 open issues。
- 本地缓存结果。

issue card：

## 13. 推荐实施顺序

### 13.1 第一阶段：本地 AI 与单仓智能化

目标：让 Starcat 详情页具备 AI 理解能力。

1. AI 设置页：Provider、Base URL、API Key、模型、测试连接。
2. `AIServiceProtocol` 与 OpenAI-compatible 最小实现。
3. 单仓 AI 摘要。
4. AI 标签推荐确认流。
5. AI 结果本地缓存。

**2026-06-04 落地记录**：

- AI 设置页与 OpenAI-compatible 最小实现已完成，见 `docs/详细设计/14-AI集成落地记录.md §1`。
- 单仓 AI 摘要已落地为详情页正文区 `README / AI 摘要` segmented tab，默认仍打开 README；AI 摘要读取 repo 元数据与本地 README 缓存，调用 BYOK chat model，结果写入 `ai_summaries`。
- AI 标签推荐确认流已落地在 `RepoAIInsightPanel`：每个推荐标签显示置信度和原因，用户点击“应用”或“全部应用”后才创建/绑定标签。
- AI 结果本地缓存使用 `AISummaryRecord` / `GRDBAISummaryRepository`，以 `(repo_id, model)` 为主键，`source_hash` 判断缓存是否仍匹配当前 repo 上下文。
- **需审计确认，但已按最佳方案实现**：第一阶段没有做建议态标签持久化表，确认流直接写入现有 `tags` / `repo_tags`。批量整理或可撤销建议队列进入后续阶段再补。

### 13.2 第二阶段：语义搜索与技术选型

目标：让用户能通过自然语言找 repo，并生成技术选型报告。

1. Embedding 生成队列。
2. 本地向量缓存。
3. FTS5 + cosine similarity + RRF。
4. Search 页面语义搜索。
5. 技术选型助手。
6. 报告保存与 Markdown 导出。

### 13.3 第三阶段：Discover 轻量项目情报订阅

目标：从 “管理已有 stars” 扩展为 “发现新项目”。

1. GitHub Markdown feed source。
2. Markdown 中 GitHub URL 提取。
3. Discover 列表和来源管理。
4. 一键 Star / 稍后看 / 不感兴趣。
5. AI 摘要和推荐理由。
6. GitHub Search 定时任务。

### 13.4 第四阶段：安全雷达与项目健康度

目标：帮助用户判断项目风险和长期可用性。

1. License / Community Profile / Releases / Issues 指标。
2. 本地健康度评分。
3. OSV API / GitHub Advisory 集成。
4. manifest / lockfile 轻量扫描。
5. Security 页面。
6. 技术选型报告接入风险指标。

### 13.5 第五阶段：深度项目分析

目标：对重点 repo 做结构、依赖、架构和风险分析。

1. Repomix / Gitingest 本地工具检测。
2. “深度分析这个仓库”按钮。
3. 分析结果缓存。
4. 架构图 / 模块说明。
5. 技术选型深度模式。
