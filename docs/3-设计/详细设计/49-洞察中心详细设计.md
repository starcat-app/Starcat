## 1. 目标

洞察中心解决两个不同层级的问题：

1. **我的洞察**：从全部收藏或知识库范围观察整理进度、技术分布、项目状态与待处理事项。
2. **仓库洞察**：针对当前选中的单个仓库，观察近期协作活动、贡献者、项目健康度、社区规范与安全信号。

这不是照搬 GitHub Insights，也不是增加一个独立的 Web Dashboard。实现必须继续遵守 Starcat 的 Finder / Xcode Organizer 式三栏框架：

- Sidebar 负责全局入口和范围。
- 中栏负责分类与待处理集合。
- Detail 负责统计内容和操作。
- 使用系统语义色、紧凑间距和原生控件，不使用渐变背景、巨型营销卡片或多层嵌套卡片。

原型中的数字、占比、活动内容均为视觉占位，不构成数据口径或接口契约。本设计文档中的指标定义才是实施依据。

## 2. 范围与非目标

### 2.1 本期范围

- 新增顶级入口“洞察”，实现“我的洞察”三栏页面。
- 在 Manage 仓库详情中增加 `README / 洞察` 内容切换。
- 复用现有本地 SQLite 聚合、项目健康度、OpenSSF 与 RAG 索引状态。
- 对当前选中的单仓库按需请求 GitHub 活动数据。
- 所有统计项都给出明确口径、空态、错误态和下钻行为。

### 2.2 本期不做

- 不复制 GitHub 的完整 Insights 左侧菜单。
- 不对全部收藏仓库批量抓取 GitHub 远端统计。
- 不做跨日期的个人收藏历史趋势；当前数据库没有可靠的历史快照。
- 不展示 Traffic、Views、Clones、Referrers。GitHub Traffic 只适用于用户有写权限的仓库，且只提供最近 14 天，不适合作为通用仓库洞察。
- 不新增后端服务，不上传用户洞察数据，不参与 CloudKit 同步。
- 不把项目健康度现有四维模型改回旧设计文档中的历史模型。

## 5. 我的洞察

### 5.1 范围

```swift
enum InsightsScope: String, CaseIterable, Sendable {
    case starred
    case knowledge
}
```

UI 文案：

- `starred`：全部收藏
- `knowledge`：知识库

范围必须贯穿每个指标，禁止一个卡片统计收藏、另一个卡片暗中统计“收藏 ∪ 知识库”而不说明。

唯一例外是现有项目健康度覆盖查询。如果第一版直接复用 active scope，标题必须明确写为“活跃仓库健康度（收藏 ∪ 知识库）”；后续补齐按范围查询后再跟随范围切换。

### 5.2 指标口径

#### 顶部 KPI

| 指标 | 全部收藏 | 知识库 | 点击行为 |
|---|---|---|---|
| 项目数 | `repos.is_starred = 1` | `repo_notes.library_state = in_library` | 切回 Manage，应用对应范围 |
| 近 30 天新增 | `starred_at` 在滚动 30 天内 | `library_updated_at` 在滚动 30 天内 | 按范围 + 时间过滤 |
| 正在使用 | 范围内 `status = using` | 范围内 `status = using` | 按范围 + 状态过滤 |
| 已整理 | 范围内满足“有标签或有笔记或状态非未读”的去重仓库数 | 同左 | 打开“整理情况” |

“已整理”是产品派生指标，不能存库。第一版定义为：

```text
有至少一个标签
OR private_note 非空
OR ai_generated_note 非空
OR status IN (read, using)
```

#### 整理情况

以范围内仓库总数为分母：

- 未读
- 已读
- 正在使用
- 已打标签 / 未打标签

状态统计必须使用 `LEFT JOIN repo_notes`。没有 note 行的仓库视为 `unread`，否则收藏总数会与三种状态之和不一致。

#### 技术分布

- 语言来源使用仓库的 `language` 主语言。
- “全部收藏”复用收藏语言聚合。
- “知识库”复用 `knowledgeLanguageStats()` 的知识库范围。
- 空语言统一归类为“未知”，不从分母中静默删除。
- 默认展示前 8 名，其余合并为“其他”。
- 点击语言切回 Manage，应用范围 + `globalFilterLanguages`。

#### 需要处理

| 项目 | 适用范围 | 数据来源 | 下钻条件 |
|---|---|---|---|
| 未打标签 | 两个范围 | Repo 与 Tag 关联 | scope + untagged |
| 未读 | 两个范围 | `RepoStatus` | scope + `status = unread` |
| 无 README | 知识库 | RAG metadata snapshot | knowledge + `readme = missing` |
| 无可索引内容 | 知识库 | RAG source coverage | knowledge + `indexableSource = missing` |
| 索引失败或过期 | 知识库 | RAG index health | knowledge + `ragIndex IN (failed, stale)` |
| 健康度待计算 | 活跃仓库 | Health coverage | `healthAvailability = missing` |

范围不适用时不显示零值噪音。例如“全部收藏”下不展示知识库专属的 RAG 项，改为一行提示“切换到知识库查看索引状态”。

#### 项目健康度覆盖

第一版只显示覆盖进度，不对全库分数做平均：

- 已计算：存在有效 `repo_health_snapshots` 的候选仓库数。
- 待计算：候选总数 - 已计算。
- OpenSSF 已覆盖 / 待覆盖单独显示，不能与 Starcat Health 混为同一分数。

不展示“平均健康度”的原因：

- 四维权重与候选仓库类型并不完全一致。
- 一个平均数会掩盖少数高风险仓库。
- 现阶段“需要处理”和覆盖率比平均分更可操作。

### 5.3 Snapshot

```swift
struct MyInsightsSnapshot: Equatable, Sendable {
    let scope: InsightsScope
    let generatedAt: Date
    let totalCount: Int
    let addedInLast30DaysCount: Int
    let organizedCount: Int
    let statusCounts: [RepoStatus: Int]
    let taggedCount: Int
    let untaggedCount: Int
    let languageItems: [InsightsDistributionItem]
    let actionItems: [InsightsActionItem]
    let healthCoverage: RepoHealthCoverageSummary
    let openSSFCoverage: OpenSSFCoverageSummary
}
```

数据层不应从 ViewModel 拼散落查询。新增 `MyInsightsSnapshotProvider`，在一次数据库读取中获取一致视图：

```swift
protocol MyInsightsSnapshotProviding: Sendable {
    func load(scope: InsightsScope) async throws -> MyInsightsSnapshot
}
```

实现策略：

1. 优先提取并复用 `KnowledgeBaseMetadataSnapshot` 已验证的 SQL 与口径。
2. RAG Prompt 继续通过适配器获取其需要的字段，不让 UI 直接依赖 Prompt 专用模型。
3. 与 `HomeViewModel.refreshSidebar()` 共用 Repository 层查询，禁止复制一套“看起来相同”的计数。
4. 先做实时 SQLite 聚合。没有真实历史趋势需求前，不建 summary 表、不跑定时任务。

### 5.4 下钻筛选扩展

现有 `GlobalRepoFilterState` 已覆盖：

- `statusFilter`
- `starFilter`
- `libraryFilter`
- `globalFilterLanguages`
- `healthAvailabilityFilter`


- 切换到 Manage 后保留“返回洞察”上下文；清除临时筛选时恢复点击前状态。
- 不用搜索关键字模拟结构化筛选。

## 6. 仓库洞察

### 6.1 内容结构

按从“快速判断”到“深入查看”排列：

1. 时间范围：1 周 / 1 月 / 3 月 / 1 年。
2. 活动 KPI：新建 PR、已合并 PR、新建 Issue、已关闭 Issue。
3. Commit 活动：按周柱状图。
4. 主要贡献者：头像、登录名、贡献次数。
5. 项目健康度：当前四维雷达图或四条横向刻度。
6. 社区与安全：Community Profile、License、OpenSSF。
7. 最近活动：Release、合并 PR、关闭 Issue 的统一时间线。

窄窗口下不强行保持两列卡片。Detail 内容按可用宽度在一列与两列间自适应，不设置固定 Detail 最小宽度；窗口下限继续由 `MainWindowFrameModifier` 统一负责。

### 6.2 时间范围

```swift
enum RepositoryInsightsRange: String, CaseIterable, Sendable {
    case week
    case month
    case quarter
    case year
}
```

区间统一使用 `[start, now]`：

| UI | 起点 |
|---|---|
| 1 周 | `now - 7 days` |
| 1 月 | `now - 30 days` |
| 3 月 | `now - 90 days` |
| 1 年 | `now - 365 days` |

Commit activity 的 GitHub endpoint 固定返回最近 52 周。客户端只截取选中区间，不为每个区间重复请求。

### 6.3 GitHub 数据源

| 数据 | 建议端点 | 处理 |
|---|---|---|
| 新建 / 合并 PR | Search Issues API，`is:pr created:` / `merged:` | 返回 `total_count`；搜索限额单独处理 |
| 新建 / 关闭 Issue | Search Issues API，`is:issue created:` / `closed:` | 返回 `total_count` |
| Commit 活动 | `GET /repos/{owner}/{repo}/stats/commit_activity` | 处理 `202 Accepted` |
| 贡献者 | `GET /repos/{owner}/{repo}/stats/contributors` | 处理 `202`、空仓库和超大仓库限制 |
| Community | `GET /repos/{owner}/{repo}/community/profile` | fork 不支持时显示“不可用” |
| 最近 Release | 现有 Release 数据或 Releases API | 优先本地缓存 |
| 最近 PR / Issue | Search Issues API | 限制数量，只做时间线 |
| Health / OpenSSF | Starcat 本地缓存 | 不重复访问 GitHub |

GitHub Repository Statistics 属于高成本缓存端点。未生成时会返回 `202`，客户端必须短暂等待后重试；默认分支 SHA 变化时 GitHub 会使其统计缓存失效。实现必须遵循 [Repository statistics 官方说明](https://docs.github.com/en/rest/metrics/statistics)。

Community Profile 可返回文档、行为准则、License、Issue/PR Template、README 与健康百分比，详见 [Community metrics 官方说明](https://docs.github.com/en/rest/metrics/community)。

Traffic 端点要求仓库写权限并只覆盖最近 14 天，因此本期明确排除，详见 [Repository traffic 官方说明](https://docs.github.com/en/rest/metrics/traffic)。

### 6.4 类型化 Client

不得从洞察 UI 调用 `GitHubRAGRemoteContextProvider`，也不得解析它面向 LLM 生成的文本。应把其中已验证的 URL、认证和状态码处理提取到共享的类型化客户端：

```swift
protocol GitHubRepositoryMetricsClient: Sendable {
    func loadActivityCounts(
        repository: RepoIdentity,
        range: RepositoryInsightsRange
    ) async throws -> RepositoryActivityCounts

    func loadCommitActivity(repository: RepoIdentity) async throws -> [WeeklyCommitActivity]

    func loadContributors(repository: RepoIdentity) async throws -> [RepositoryContributor]

    func loadCommunityProfile(repository: RepoIdentity) async throws -> RepositoryCommunityProfile

    func loadRecentActivity(
        repository: RepoIdentity,
        range: RepositoryInsightsRange
    ) async throws -> [RepositoryActivityItem]
}
```

RAG Remote Context 改为此 Client 的消费者之一，从类型化结果生成文本；洞察 ViewModel 直接消费类型化结果。这样认证、API version、Rate Limit、重试与测试桩只有一个实现。

### 6.5 加载状态

每个远端区块独立加载，不能因为 contributors 失败而让整个页面报错：

```swift
enum InsightsSectionState<Value: Equatable>: Equatable {
    case idle
    case loading(cached: Value?)
    case ready(Value)
    case generating(cached: Value?)
    case unavailable(reason: RepositoryInsightsUnavailableReason)
    case failed(message: String, cached: Value?)
}
```

状态映射：

| 情况 | UI |
|---|---|
| 首次加载 | 区块内 skeleton / ProgressView |
| `202` | “GitHub 正在生成统计数据”，有限次数自动重试 |
| `403 / 429` 且 Rate Limit 耗尽 | 显示恢复时间，不继续请求 |
| Secondary Rate Limit | 尊重 `Retry-After`，停止并发请求 |
| `404 / 422` 或 endpoint 不支持 | “此仓库暂无该统计” |
| 有旧缓存但刷新失败 | 保留旧数据，标注更新时间和刷新失败 |
| 用户未登录 | 本地 Health/OpenSSF 仍显示；远端区块提示登录 |

远端请求经 actor 串行或低并发执行，不能在切换仓库时同时发起一批搜索与统计请求。GitHub 对认证用户通常提供 5,000 次/小时的 primary limit，但 Search 与 secondary limit 另有约束，恢复时间以响应头为准，详见 [REST API Rate Limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

### 6.6 缓存与迁移

#### 我的洞察

- 只读实时 SQLite。
- 可使用数据库 revision + 最多 60 秒的内存缓存。
- 不新增表，不新增后台任务。

#### 仓库洞察

第一实现建议增加本地快照缓存，避免每次切换 `README / 洞察` 重打 GitHub：

```text
repo_insights_snapshots
├─ repo_id               INTEGER NOT NULL
├─ dataset               TEXT NOT NULL
├─ range_key             TEXT NOT NULL
├─ payload_json          BLOB NOT NULL
├─ default_branch_sha    TEXT
├─ fetched_at            DATETIME NOT NULL
├─ stale_after           DATETIME NOT NULL
├─ response_etag         TEXT
└─ PRIMARY KEY (repo_id, dataset, range_key)
```

数据集与 TTL：

| dataset | TTL | range_key |
|---|---:|---|
| activityCounts | 15 分钟 | week / month / quarter / year |
| recentActivity | 15 分钟 | week / month / quarter / year |
| commitActivity | 24 小时 | all |
| contributors | 24 小时 | all |
| communityProfile | 24 小时 | all |

迁移约束：

- 当前迁移已到 `v15`；实施时使用当时真实的下一顺序版本，本文不锁死为某个编号。
- 只追加 `registerVN`，禁止回写 `v1-initial`。
- 缓存是可重建数据，不进入 CloudKit，不影响用户标签、笔记和状态。
- repo 被物理清理时通过外键级联或清理流程删除快照。

如果实施时确认已有通用 HTTP 缓存能够完整表达 `dataset + range + repo`，可复用现有缓存而不建表，但必须在开工审计中给出等价的 TTL、陈旧数据和离线行为证明。

## 7. ViewModel 与并发

### 7.1 我的洞察

```swift
@MainActor
@Observable
final class MyInsightsViewModel {
    private(set) var state: LoadableState<MyInsightsSnapshot>
    var scope: InsightsScope

    func loadIfNeeded() async
    func refresh() async
    func selectAction(_ action: InsightsAction)
}
```

- scope 变化时取消旧任务。
- Snapshot 返回后再次校验 scope，旧结果不得覆盖新范围。
- 数据库 revision 未变化且缓存未过期时直接复用。
- 刷新只重读本地数据库，不触发全量 Stars 同步。

### 7.2 仓库洞察

```swift
@MainActor
@Observable
final class RepositoryInsightsViewModel {
    private(set) var snapshot: RepositoryInsightsSnapshot
    var range: RepositoryInsightsRange

    func load(repo: Repo) async
    func refresh(repo: Repo) async
    func cancel()
}
```

- 以 `repo.id + range + generation` 作为结果归属。
- 快速切换仓库、切换范围或切回 README 时取消无用任务。
- 本地 Health/OpenSSF 先显示，远端区块渐进更新。
- 默认显示未过期缓存；过期缓存先显示并后台刷新。
- 手动刷新使用 `SyncIconButton`，同一仓库 10 秒内防重复点击。
- View 消失不自动清除 ViewModel 缓存，但必须取消网络请求。

## 10. 实施切片

### M1：我的洞察本地闭环

目标：

### M3：仓库洞察本地信息

### M4：仓库远端活动与缓存

目标：

## 12. 验收标准

功能完成必须同时满足：

1. “我的洞察”所有数字都有唯一且可测试的数据口径。
2. 顶级洞察完全复用 Starcat 主窗口三栏导航，不出现独立 Dashboard 框架。
3. 仓库洞察复用 `RepoDetailScaffold`，只扩展 Manage 内容插槽。
4. 本地洞察不新增汇总表或后台任务。
5. 远端统计仅对当前仓库按需加载，有缓存、取消、Rate Limit 与 `202` 处理。
6. 原型里的每个首期区块都有真实数据源；没有真实数据的区块不以模拟值上线。
7. 点击“需要处理”后，列表条数与入口数字一致。
8. 自动化测试通过；明暗主题、最小窗口、快速切仓和登录状态由人工完成截图验收。

## 13. 开工前确认项
