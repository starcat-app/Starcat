## 1. 目标

洞察中心解决两个不同层级的问题：

1. **我的洞察**：从全部收藏或知识库范围观察整理进度、技术分布、项目状态与待处理事项。
2. **仓库洞察**：针对当前选中的单个仓库，观察 Star 增长历史、近期协作活动、贡献者、项目健康度、社区规范与安全信号。

这不是照搬 GitHub Insights，也不是增加一个独立的 Web Dashboard。实现必须继续遵守 Starcat 的 Finder / Xcode Organizer 式三栏框架：

- Sidebar 负责全局入口和范围。
- 中栏负责分类与待处理集合。
- Detail 负责统计内容和操作。
- 使用系统语义色、紧凑间距和原生控件，不使用渐变背景、巨型营销卡片或多层嵌套卡片。

原型中的数字、占比、活动内容均为视觉占位，不构成数据口径或接口契约。本设计文档中的指标定义才是实施依据。

## 5. 我的洞察

### 5.1 范围

```swift
enum InsightsScope: String, CaseIterable, Sendable {
    case starred
    case knowledge
}
```

UI 文案：

- `starred`：全部收藏
- `knowledge`：知识库

范围必须贯穿每个指标，禁止一个卡片统计收藏、另一个卡片暗中统计“收藏 ∪ 知识库”而不说明。

唯一例外是现有项目健康度覆盖查询。如果第一版直接复用 active scope，标题必须明确写为“活跃仓库健康度（收藏 ∪ 知识库）”；后续补齐按范围查询后再跟随范围切换。

### 5.2 指标口径

#### 顶部 KPI

| 指标 | 全部收藏 | 知识库 | 点击行为 |
|---|---|---|---|
| 项目数 | `repos.is_starred = 1` | `repo_notes.library_state = in_library` | 切回 Manage，应用对应范围 |
| 近 30 天新增 | `starred_at` 在滚动 30 天内 | `library_updated_at` 在滚动 30 天内 | 按范围 + 时间过滤 |
| 正在使用 | 范围内 `status = using` | 范围内 `status = using` | 按范围 + 状态过滤 |
| 已整理 | 范围内满足“有标签或有笔记或状态非未读”的去重仓库数 | 同左 | 打开“整理情况” |

“已整理”是产品派生指标，不能存库。第一版定义为：

```text
有至少一个标签
OR private_note 非空
OR ai_generated_note 非空
OR status IN (read, using)
```

#### 整理情况

以范围内仓库总数为分母：

- 未读
- 已读
- 正在使用
- 已打标签 / 未打标签

状态统计必须使用 `LEFT JOIN repo_notes`。没有 note 行的仓库视为 `unread`，否则收藏总数会与三种状态之和不一致。

#### 资产清理、高价值待整理与节奏

- 资产清理把“未读、无标签、无笔记”拆成独立计数，不把三个条件的交集伪装成总待办。
- 高价值待整理只从当前范围中筛选尚未整理的仓库，再按当前 Stars 降序取前 5；它是行动优先级，不是质量评分。
- 近十二周节奏使用 `starred_at`（全部收藏）或 `library_updated_at`（知识库）按自然周聚合；没有新增的周仍返回零点，保证折线和柱形图时间轴稳定。
- 以上数据均在 `GRDBMyInsightsSnapshotProvider` 的同一数据库读取中生成，不增加 summary 表或后台任务。

#### 技术分布

- 语言来源使用仓库的 `language` 主语言。
- “全部收藏”复用收藏语言聚合。
- “知识库”复用 `knowledgeLanguageStats()` 的知识库范围。
- 空语言统一归类为“未知”，不从分母中静默删除。
- 默认展示前 8 名，其余合并为“其他”。
- 点击语言切回 Manage，应用范围 + `globalFilterLanguages`。

#### 需要处理

| 项目 | 适用范围 | 数据来源 | 下钻条件 |
|---|---|---|---|
| 未打标签 | 两个范围 | Repo 与 Tag 关联 | scope + untagged |
| 未读 | 两个范围 | `RepoStatus` | scope + `status = unread` |
| 无 README | 知识库 | RAG metadata snapshot | knowledge + `readme = missing` |
| 无可索引内容 | 知识库 | RAG source coverage | knowledge + `indexableSource = missing` |
| 索引失败或过期 | 知识库 | RAG index health | knowledge + `ragIndex IN (failed, stale)` |
| 健康度待计算 | 活跃仓库 | Health coverage | `healthAvailability = missing` |

范围不适用时不显示零值噪音。例如“全部收藏”下不展示知识库专属的 RAG 项，改为一行提示“切换到知识库查看索引状态”。

#### 项目健康度覆盖

第一版只显示覆盖进度，不对全库分数做平均：

- 已计算：存在有效 `repo_health_snapshots` 的候选仓库数。
- 待计算：候选总数 - 已计算。
- OpenSSF 已覆盖 / 待覆盖单独显示，不能与 Starcat Health 混为同一分数。

不展示“平均健康度”的原因：

- 四维权重与候选仓库类型并不完全一致。
- 一个平均数会掩盖少数高风险仓库。
- 现阶段“需要处理”和覆盖率比平均分更可操作。

#### 知识沉淀与索引覆盖

- 全部收藏范围显示已入库、已有笔记、已有标签三个覆盖计数。
- 知识库范围额外显示 README、可索引内容、当前 embedding model 已就绪三个覆盖计数。
- embedding model 变化后，旧模型索引不计为“已就绪”；不能只凭存在任意 embedding 记录宣告覆盖。
- 覆盖条只表达当前范围内的事实数量，不将“已入库”或“有标签”误称为内容质量。

### 5.3 Snapshot

```swift
struct MyInsightsSnapshot: Equatable, Sendable {
    let scope: InsightsScope
    let generatedAt: Date
    let totalCount: Int
    let addedInLast30DaysCount: Int
    let organizedCount: Int
    let statusCounts: [RepoStatus: Int]
    let taggedCount: Int
    let untaggedCount: Int
    let languageItems: [InsightsDistributionItem]
    let actionItems: [InsightsActionItem]
    let healthCoverage: RepoHealthCoverageSummary
    let openSSFCoverage: OpenSSFCoverageSummary
}
```

数据层不应从 ViewModel 拼散落查询。新增 `MyInsightsSnapshotProvider`，在一次数据库读取中获取一致视图：

```swift
protocol MyInsightsSnapshotProviding: Sendable {
    func load(scope: InsightsScope) async throws -> MyInsightsSnapshot
}
```

实现策略：

1. 优先提取并复用 `KnowledgeBaseMetadataSnapshot` 已验证的 SQL 与口径。
2. RAG Prompt 继续通过适配器获取其需要的字段，不让 UI 直接依赖 Prompt 专用模型。
3. 与 `HomeViewModel.refreshSidebar()` 共用 Repository 层查询，禁止复制一套“看起来相同”的计数。
4. 先做实时 SQLite 聚合。没有真实历史趋势需求前，不建 summary 表、不跑定时任务。

## 6. 仓库洞察

### 6.1 内容结构

按从“快速判断”到“深入查看”排列：

1. 协作活动时间范围：1 周 / 1 月 / 3 月 / 1 年。
2. 活动 KPI：新建 PR、已合并 PR、新建 Issue、已关闭 Issue，并派生 PR / Issue 吞吐比与 Issue 净变化。
3. Star 趋势：当前 Stars、30 天 / 1 年增长、日均 / 月均增长速度、长期估算段与 Starcat 精确快照段。
4. Commit 活动：按周柱状图，并比较最近四周与此前四周的维护脉搏。
5. 主要贡献者：头像、登录名、贡献次数，以及前 12 位样本内的 Top 1 / Top 3 集中度。
6. 发布节奏：复用本地 Release 历史，展示近一年发布数、最近最多 12 次发布的平均间隔和最近发布日期；两个范围分别写入标题，不能暗示全历史平均。
7. 项目健康度：当前四维雷达图或四条横向刻度。
8. 社区与安全：Community Profile、License、Issue / Pull Request 模板、OpenSSF 与近期 Security Advisories。
9. 最近活动：Release、合并 PR、关闭 Issue 的统一时间线。

窄窗口下不强行保持两列卡片。Detail 内容按可用宽度在一列与两列间自适应，不设置固定 Detail 最小宽度；窗口下限继续由 `MainWindowFrameModifier` 统一负责。

Star 趋势是仓库洞察的一部分，但数据层继续保持独立：

- `RepositoryInsightsView` 负责页面编排。
- `StarHistorySection` 负责图表、来源说明和自己的范围选择。
- `StarHistoryViewModel` 负责本地快照、Discovery API、精度合并与状态。
- 不把 Star 历史塞进 `GitHubRepositoryMetricsClient`，因为它来自 Starcat Discovery API 与本地快照，不是单一 GitHub Metrics endpoint。

### 6.2 时间范围

```swift
enum RepositoryActivityRange: String, CaseIterable, Sendable {
    case week
    case month
    case quarter
    case year
}
```

区间统一使用 `[start, now]`：

| UI | 起点 |
|---|---|
| 1 周 | `now - 7 days` |
| 1 月 | `now - 30 days` |
| 3 月 | `now - 90 days` |
| 1 年 | `now - 365 days` |

Commit activity 的 GitHub endpoint 固定返回最近 52 周。客户端只截取选中区间，不为每个区间重复请求。

Star 趋势使用独立范围，不被页面活动范围强行裁剪：

```swift
enum StarHistoryRange: String, CaseIterable, Sendable {
    case quarter
    case year
    case all
}
```

原因：

- 一周或一个月通常只有零至一个本地精确快照，不能形成有意义的长期曲线。
- `all` 只适用于 Star 历史，不适用于 Search Issues API。
- 两个范围选择器分别放在“协作活动”和“Star 趋势”区块标题行，避免一个控件暗中改变不同口径的数据。

### 6.3 GitHub 数据源

| 数据 | 建议端点 | 处理 |
|---|---|---|
| Star 长期历史 | `starcat-discovery-api /api/v1/repos/{owner}/{repo}/star-history` | GH Archive 估算；处理构建中 `202`、ETag 与 24h 缓存 |
| Star 精确快照 | repo metadata 同步后的本地每日快照 | 不额外请求 GitHub；允许真实下降 |
| 新建 / 合并 PR | Search Issues API，`is:pr created:` / `merged:` | 返回 `total_count`；搜索限额单独处理 |
| 新建 / 关闭 Issue | Search Issues API，`is:issue created:` / `closed:` | 返回 `total_count` |
| Commit 活动 | `GET /repos/{owner}/{repo}/stats/commit_activity` | 处理 `202 Accepted` |
| 贡献者 | `GET /repos/{owner}/{repo}/stats/contributors` | 处理 `202`、空仓库和超大仓库限制 |
| Community | `GET /repos/{owner}/{repo}/community/profile` | fork 不支持时显示“不可用” |
| Security Advisories | `GET /repos/{owner}/{repo}/security-advisories?per_page=100` | 只把成功空响应显示为 0；无权限 / 不支持必须显示不可用 |
| 最近 Release | 现有 Release 数据或 Releases API | 优先本地缓存 |
| 最近 PR / Issue | Search Issues API | 限制数量，只做时间线 |
| Health / OpenSSF | Starcat 本地缓存 | 不重复访问 GitHub |

GitHub Repository Statistics 属于高成本缓存端点。未生成时会返回 `202`，客户端必须短暂等待后重试；默认分支 SHA 变化时 GitHub 会使其统计缓存失效。实现必须遵循 [Repository statistics 官方说明](https://docs.github.com/en/rest/metrics/statistics)。

Community Profile 可返回文档、行为准则、License、Issue/PR Template、README 与健康百分比，详见 [Community metrics 官方说明](https://docs.github.com/en/rest/metrics/community)。

Traffic 端点要求仓库写权限并只覆盖最近 14 天，因此本期明确排除，详见 [Repository traffic 官方说明](https://docs.github.com/en/rest/metrics/traffic)。

GitHub 已宣布 `/repos/{owner}/{repo}/stargazers` 的列表访问将限制为管理员和协作者，因此不能用该端点为用户收藏的任意仓库生成历史曲线。Star 趋势的数据来源、归一化公式、私有仓库边界和后端契约以 [仓库星标历史整体落地方案](50-仓库星标历史整体落地方案.md) 为准。

### 6.4 类型化 Client

不得从洞察 UI 调用 `GitHubRAGRemoteContextProvider`，也不得解析它面向 LLM 生成的文本。应把其中已验证的 URL、认证和状态码处理提取到共享的类型化客户端：

```swift
protocol GitHubRepositoryMetricsClient: Sendable {
    func loadActivityCounts(
        repository: RepoIdentity,
        range: RepositoryActivityRange
    ) async throws -> RepositoryActivityCounts

    func loadCommitActivity(repository: RepoIdentity) async throws -> [WeeklyCommitActivity]

    func loadContributors(repository: RepoIdentity) async throws -> [RepositoryContributor]

    func loadCommunityProfile(repository: RepoIdentity) async throws -> RepositoryCommunityProfile

    func loadRecentActivity(
        repository: RepoIdentity,
        range: RepositoryActivityRange
    ) async throws -> [RepositoryActivityItem]
}
```

RAG Remote Context 改为此 Client 的消费者之一，从类型化结果生成文本；洞察 ViewModel 直接消费类型化结果。这样认证、API version、Rate Limit、重试与测试桩只有一个实现。

Star 历史继续使用 `StarHistoryAPI + RepoStarHistoryRepository`：

- `StarHistoryAPI` 访问 `starcat-discovery-api`。
- `RepoStarHistoryRepository` 合并 GH Archive 估算、Discovery 快照和本机快照。
- `StarHistoryViewModel` 作为 `RepositoryInsightsView` 的子状态，不与活动指标共用 range 或 loading。

### 6.5 加载状态

每个远端区块独立加载，不能因为 contributors 失败而让整个页面报错：

```swift
enum InsightsSectionState<Value: Equatable>: Equatable {
    case idle
    case loading(cached: Value?)
    case ready(Value)
    case generating(cached: Value?)
    case unavailable(reason: RepositoryInsightsUnavailableReason)
    case failed(message: String, cached: Value?)
}
```

状态映射：

| 情况 | UI |
|---|---|
| 首次加载 | 保持区块稳定高度，不在内容中央显示 `ProgressView`；数据返回后原位更新 |
| `202` | “GitHub 正在生成统计数据”，有限次数自动重试 |
| `STAR_HISTORY_BUILDING` | Star 区块显示“正在准备长期历史”，保留本地快照 |
| `403 / 429` 且 Rate Limit 耗尽 | 显示恢复时间，不继续请求 |
| Secondary Rate Limit | 尊重 `Retry-After`，停止并发请求 |
| `404 / 422` 或 endpoint 不支持 | “此仓库暂无该统计” |
| 有旧缓存但刷新失败 | 保留旧数据，标注更新时间和刷新失败 |
| 用户未登录 | 本地 Health/OpenSSF 仍显示；远端区块提示登录 |

远端请求经 actor 串行或低并发执行，不能在切换仓库时同时发起一批搜索与统计请求。GitHub 对认证用户通常提供 5,000 次/小时的 primary limit，但 Search 与 secondary limit 另有约束，恢复时间以响应头为准，详见 [REST API Rate Limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

### 6.6 缓存与迁移

#### 我的洞察

- 只读实时 SQLite。
- 可使用数据库 revision + 最多 60 秒的内存缓存。
- 不新增表，不新增后台任务。

#### 仓库洞察

两个需求一起实施时，追加一次统一迁移 `v16-repository-insights`，包含两类可重建缓存：

```text
repo_insights_snapshots
├─ repo_id               INTEGER NOT NULL
├─ dataset               TEXT NOT NULL
├─ range_key             TEXT NOT NULL
├─ payload_json          BLOB NOT NULL
├─ default_branch_sha    TEXT
├─ fetched_at            DATETIME NOT NULL
├─ stale_after           DATETIME NOT NULL
├─ response_etag         TEXT
└─ PRIMARY KEY (repo_id, dataset, range_key)

repo_star_history_points
├─ repo_id               INTEGER NOT NULL
├─ observed_on           TEXT NOT NULL
├─ stars_count           INTEGER NOT NULL
├─ source                TEXT NOT NULL
├─ precision             TEXT NOT NULL
├─ fetched_at            TEXT NOT NULL
└─ PRIMARY KEY (repo_id, observed_on, source)
```

数据集与 TTL：

| dataset | TTL | range_key |
|---|---:|---|
| activityCounts | 15 分钟 | week / month / quarter / year |
| recentActivity | 15 分钟 | week / month / quarter / year |
| commitActivity | 24 小时 | all |
| contributors | 24 小时 | all |
| communityProfile | 24 小时 | all |

Star 历史表不使用 TTL 删除历史点：

- `gh_archive / discovery_snapshot` 由 24 小时远端刷新替换。
- `local_snapshot` 按日幂等追加，远端刷新不得删除。
- 同日同时存在估算与精确点时，展示层优先精确点。

迁移约束：

- 当前迁移已到 `v15`；两个需求同批开工时追加一次 `registerV16`，迁移名为 `v16-repository-insights`。
- 只追加 `registerVN`，禁止回写 `v1-initial`。
- 缓存是可重建数据，不进入 CloudKit，不影响用户标签、笔记和状态。
- repo 被物理清理时通过外键级联或清理流程删除快照。

如果实施时确认已有通用 HTTP 缓存能够完整表达 `dataset + range + repo`，可复用现有缓存而不建表，但必须在开工审计中给出等价的 TTL、陈旧数据和离线行为证明。

## 7. ViewModel 与并发

### 7.1 我的洞察

```swift
@MainActor

final class MyInsightsViewModel {
    private(set) var state: LoadableState<MyInsightsSnapshot>

    func refresh() async
```

- scope 变化时取消旧任务。
- Snapshot 返回后再次校验 scope，旧结果不得覆盖新范围。

### 7.2 仓库洞察

```swift

    func refresh(repo: Repo) async
```

- 以 `repo.id + range + generation` 作为结果归属。

## 14. 性能优化实现回填

### 14.1 请求数变化

仓库洞察仍按当前仓库按需加载，不做收藏仓库批量预取。完整冷加载的 GitHub 请求构成如下：

| 数据 | 优化前 | 优化后正常路径 | 说明 |
|---|---:|---:|---|
| Activity | 4 REST Search | 与 Recent 共用 1 GraphQL | 四个 aliases 返回 PR / Issue 计数 |
| Recent Activity | 2 REST Search | 与 Activity 共用 1 GraphQL | 同一响应返回最近 PR / Issue |
| Commit Activity | 1 | 1 | 支持 ETag / 304 |
| Contributors | 1 | 1 | 支持 ETag / 304 |
| Community | 1 | 1 | 支持 ETag / 304 |
| Security | 1 | 1 | 支持 ETag / 304 |
| 合计 | 最多 10 | 最多 5 | GraphQL 不可用时回退原 REST 路径 |

Star History 不计入上表：它继续使用独立 Discovery API 覆盖判断、24 小时远端缓存和有限 `202` 轮询，不与 GitHub Metrics 串行队列混用。

### 14.2 三层缓存

1. ViewModel 层：同一仓库、同一刷新入口在 10 秒内只执行一轮手动刷新；刷新中保留已上屏内容。
2. 进程层：普通 GitHub Metrics 请求按 URL、ETag、认证身份和请求类型合并 in-flight；SQLite payload 解码后进入固定 48 条 LRU。
3. SQLite 层：`repo_insights_snapshots` 仍是跨启动真源；Activity / Recent 为 15 分钟，Commit / Contributors 为 24 小时，Community 为 3 天，Security 为 6 小时。

缓存有效期内再次进入同一仓库不会发 GitHub 请求；A → B → A 返回时优先命中解码 LRU，避免重复 SQLite 读取与 JSON 解码。`store`、`remove`、损坏隔离和 304 touch 都同步精确更新热点条目。

### 14.3 条件请求与失败缓存

- Commit、Contributors、Community、Security 从 SQLite 读取 ETag 并发送 `If-None-Match`。
- 304 只续期 `fetched_at / stale_after / response_etag`，保留原 payload；若 payload 在请求期间被删除，则无条件重拉一次。
- 404 / 422 对相同 endpoint 负缓存 24 小时；403 只在当前认证身份下短期缓存；401 不缓存。
- 普通 HTTP / 解码 / 传输失败使用 2、4、8、16、30 秒有界指数退避。
- 403 / 429 继续严格遵守 `Retry-After` 或 `X-RateLimit-Reset`，认证身份变化不会继承旧账号退避。

### 14.4 切库与并发边界

`AppDependencies.switchUserDatabase(to:)` 使用 begin / end 屏障覆盖整个 `DatabaseManager.reopen` 窗口：begin 先阻止新请求读取 Token，再取消并等待旧账号普通洞察 in-flight；reopen 成功或失败后都 end，等待者随后重新读取当前 Token。切库同时清空解码热点、Rate Limit 和 endpoint failure 状态。页面加载身份包含 `repoID + databaseScopeRevision`，切库时让旧 generation 失效并清空手动刷新冷却。

RAG observer 请求不参与普通洞察请求合并和 endpoint 失败缓存，确保每次调试调用仍对应一组真实 request / response / failure 事件。

### 14.5 本地读取与非目标

Release、Release cadence、Health、OpenSSF、Community 使用同一个 GRDB read transaction 形成本地 Snapshot；单字段读取失败只降级该字段，不影响其余区块。

本轮没有新增 migration、后台任务、页面加载提示、中央进度环或动画，也没有改变“我的洞察”的 revision + 60 秒缓存、README 的既有 SWR、Repo List 的 account-scoped prepared snapshot / LRU。
