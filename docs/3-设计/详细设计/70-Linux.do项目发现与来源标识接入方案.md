# Linux.do 项目发现与来源标识接入方案

> 适用版本：Starcat 2.0.0。
> 状态：客户端接入与缓存已实现；2026-10-18 的实施／验证记录保留，不能将其当作当前生产状态。
> 调研日期：2026-10-12；主仓库基线：`dev` / `c2525c46`。
> 2026-10-12 为文档调研阶段；初版记录见第 9 节，全自动调整见第 10 节。历史阶段的授权边界不代表当前生产状态。

> 现状核对（2026-11-12）：`Starcat/Core/Sync/LinuxDoRepository.swift` 已按 Provider 身份与资源路径隔离内存／磁盘快照，TTL 为 30 分钟；强制刷新绕过 TTL 但保留 ETag，304 更新新鲜度，拒绝 revision 倒退。客户端不应再按“等待建立缓存层”重新实施。本轮未检查采集运行日志或生产部署，服务端状态需在 `supports/starcat-discovery-api` 单独核对。

## 1. 结论与范围

建议由 `starcat-discovery-api` 统一采集 Linux.do“开源推广”标签，为客户端提供独立项目目录、轻量来源索引和原帖链接。客户端不直接爬论坛，不要求用户提供论坛账号或 Cookie。

接入分成三个独立问题：

| 问题 | 建议方案 | 关键约束 |
|---|---|---|
| 如何采集 | 先验证公开标签 RSS；需要完整性时使用站方允许的分页 API / 导出 | RSS 已实测可读，但不是完整历史库，也不是授权证明 |
| 如何识别项目 | 自动提取主帖候选、判断主项目角色并核验公开 GitHub 身份；不确定项自动跳过 | 不收依赖 / 引用，不将来源收录等同于许可证背书 |
| 如何跨分类显示 | 下载公共来源索引，按 `gh_repo_id` 在本地匹配所有仓库入口 | 不依赖打开 Linux.do 分类，不上传用户 Stars 清单，不逐行联网 |

已确认方向来自 [2.0.0 版本规划](../../2-产品/需求讨论/v2.0.0-版本规划.md)：Linux.do 优先级最高，入口暂定“探索 → 发现 → Linux.do”，详情可追溯原帖，其他分类显示来源标识。

2026-10-18 已明确取消人工审核；识别与许可证政策以第 4、10 节为准。初版频率、缓存与来源过期窗口见第 9 节；历史回补及采集通道扩展不在本轮范围。

首版范围：公开主帖及可获取的主帖编辑、公开 GitHub 仓库、一帖多仓库与一仓库多帖。首版不做评论区全量抓取、非 GitHub 平台、论坛登录 / 评论、不经确认的用户数据写入，也不为本功能引入通用采集平台。

## 2. 现有架构与接入边界

### 2.1 服务端

当前 [Discovery 服务装配](../../../supports/starcat-discovery-api/server/server.go)已有 GitHub 元数据获取、SQLite、调度、缓存、公共查询鉴权和管理鉴权，并承载 Awesome 来源管理。Linux.do 可复用这些能力，无需新建独立服务。

[SQLite Store](../../../supports/starcat-discovery-api/internal/store/sqlite.go)已区分共享仓库事实与 `discovery_catalog_repos` 成员关系：Discovery bulk / 排行查询按目录成员过滤，Awesome 独立维护来源。Linux.do 应沿用这一边界：

- 仓库名称、描述、语言、Stars 等事实继续按 GitHub ID 复用。
- Linux.do 收录关系独立保存；不能把所有新识别仓库自动插入普通 Discovery 成员表。
- 现有热门、新发布、主题和平台计数不因 Linux.do 入库自动扩大。
- 同一仓库可以同时属于 Discovery、Awesome、Weekly、Linux.do；展示 Linux.do 标识不要求它从其他来源移出。

`supports/starcat-discovery-api` 是独立 Git 仓库。后续服务端和主 App 的提交、发布、部署须分别管理，本次没有修改任何一个的业务代码。

## 3. 采集方式

### 3.1 本次可用性证据

| 检查项 | 2026-10-12 观察 | 能证明 / 不能证明 |
|---|---|---|
| [开源推广标签](https://linux.do/tag/2234-tag/2234) | 网页检索可读取公开列表；当前 tag ID 为 `2234` | 可定位目标标签；不能证明生产服务器可持续访问 |
| `GET /tag/2234-tag/2234.json` | 本机无登录态请求返回 `403`、`text/html` | 此访问环境下 JSON 不可直接用；不外推为所有身份 / 所有端点均不可用 |
| [标签 RSS](https://linux.do/tag/2234-tag/2234.rss) | 无 Cookie 请求返回 `200`、`application/rss+xml`；有效 RSS 根节点，30 个 item，响应约 329 KiB | 有可用的结构化公开输入；未验证分页、稳定容量与编辑 / 删除通知 |
| RSS 内容抽查 | 前三条 `description` 含 HTML 和 GitHub 链接，同一链接会重复；也出现 `/releases/latest` 深链接 | 可做候选提取；不能把重复次数当置信度，也不能默认摘要完整 |
| [robots.txt](https://linux.do/robots.txt) / [站点条款](https://linux.do/tos) | robots 有若干路径限制；条款页面包含自动访问限制，也存在模板化表述 | 正式接入前须确认站方许可与内容使用范围；可读、未被 robots 禁止都不等于已获许可 |

本次只做少量探测，没有尝试 Cookie 复用、验证码处理、代理轮换或绕过 403。公开网页检索结果也不作为生产采集管道。

### 3.2 通道选择

| 通道 | 用途 | 首版建议 |
|---|---|---|
| 公开标签 RSS | 发现窗口内帖子，并从可用正文摘要提取候选 | 优先做许可与覆盖验证；适合有限增量，不能独立保证完整收录 |
| 站方允许的 Discourse API | 标签分页、主帖正文、更新时间与可见性复核 | 完整性优先方案；需实际验证端点、凭据范围、限流和正文权限 |
| 站方导出 / 授权清单 | 一次性历史回填，提供可追溯 topic ID | API 不便开放时的补充；使用相同识别与发布流程 |
| 人工提交公开帖子 URL | 少量补漏或运营复核入口 | 只补录已允许访问的内容；不能把人工补录宣传为自动采集完成 |
| HTML 页面解析 | 结构化通道不足时的候选 | 仅在站方允许且接口不足时评估，不作为默认方案 |

[Discourse 官方 RSS 文档](https://meta.discourse.org/t/finding-discourse-rss-feeds/264134)支持带 tag ID 的 RSS 地址；通用文档中的 API / RSS 能力不等于 Linux.do 已向当前身份开放。官方 Latest RSS 会受回复活动影响，不能把排序经验直接当作本站标签源的增量契约。

建议分两档验收：

- **RSS 有限覆盖档**：明确标注“已收录项目”，只承诺实际抓到并核验的项目；历史、窗口外编辑和删除需要补录 / 撤销渠道。
- **完整性增强档**：站方允许分页与主帖复核后，再承诺特定起止范围的回填和编辑收敛。没有验证前不得显示“全部项目”。

若版本要求“所有主帖编辑、删帖、去标签都能自动及时同步”，RSS 单通道不满足发布条件，不能用提高轮询频率代替完整性通道。

### 3.3 同步流程与断点

1. 读取目标标签 RSS / 已批准的标签分页，校验状态、内容类型、XML / JSON 结构和来源身份。
2. 将发现的 topic ID 与内容版本保存到待处理队列，再推进该轮扫描检查点。正文获取失败的任务保留重试，不因扫描结束丢失。
3. 若 RSS 正文足够，直接提取候选；摘要不足时，仅通过已批准的主帖读取方式补齐。没有正文权限时进入待补证据，不猜测项目。
4. 获取 GitHub 仓库事实，执行角色与许可证判定，保存识别结果 / 人工复核任务。
5. 只发布已通过的仓库—帖子关系，重新生成目录及来源索引版本。采集失败不能清空已发布目录。

RSS 逐 item 按 `topic_id + content_hash` 去重；hash 基于规范化的标题和可见正文，排除站点附带的阅读链接、回复计数等变化。不能按“遇到已见 topic ID”立即停止，也不能只保留最大 topic ID 或 `pubDate`：旧帖可能重新进入窗口。

取得 API 权限后，使用服务端返回且通过同源校验的下一页地址 / cursor，不臆造分页上限。首次回填与日常增量使用不同任务和进度；限制每轮工作量，未处理完继续排队，不以部分结果替换全目录。

主帖身份使用 topic ID 与 `post_number == 1`，不把回复流的第一条可见记录、最后活跃时间或某次摘要当作主帖编辑的权威证据。RSS 中缺失的更新时间 / post ID 保持为空，不能编造字段。

### 3.4 频率、失败与覆盖

以下是待许可确认的保守起点，不是线上配置：RSS 每 30 分钟一次并带少量抖动；同站并发 1；需要补取时请求至少间隔 2 秒；单轮有请求数和时长上限，超出留待下轮。最终以站方限制为准。

- 支持时使用 `ETag` / `Last-Modified` 条件请求；`304` 是未变化，不是空目录。
- `429` 遵循 `Retry-After`，网络 / `5xx` 有界退避；`401/403` 暂停对应通道并提示配置 / 授权问题，不循环重试挑战页。
- `200 + HTML 挑战页`、解析失败、超大正文、异常条目数量视为失败输入；不发布空快照。
- RSS 窗口外消失不代表删除或撤回；源暂不可达也不能直接撤销所有关系。
- 确认删帖、转私有、去掉目标标签或运营撤回时，移除对应公开关系；仍有其他有效帖子的仓库保留标识。
- RSS-only 模式缺少上述确认能力时，对旧关系定期复核或人工处理。快照同时记录采集检查时间与关系最后核验时间，不能靠每次拉 RSS 把旧关系“刷成最新”。

首次只处理当前可用窗口和经授权提供的历史种子。是否回填最近 30 天或更早，待取得可分页来源后按实际成本决定。记录接入起点、覆盖模式、未完成回填和窗口遗漏风险。

## 4. 项目识别与发布

### 4.1 候选提取

RSS/XML 和主帖 HTML 作为不可信输入，仅解析、不执行。XML 禁止外部实体；HTML 不执行 JavaScript，不下载图片 / 附件，不抓取正文任意外链。

用 HTML 解析器读取正文链接并保留段落 / 小标题上下文；排除代码块、引用块、徽章、头像、图片链接和重复预览。相同链接在正文、onebox、自动摘要中重复出现只算一条证据。

URL 处理规则：

- 只接受解析后 host 精确为 `github.com` 的仓库候选，拒绝相似域名、userinfo、异常端口和路径伪装；GitHub 元数据请求固定发往官方 API。
- 规范化 `.git`、尾斜杠、query / fragment、大小写；组织 / 用户主页、`search`、`topics`、`collections` 等不当作仓库。
- `/owner/repo/tree/...`、`blob/...`、`releases/...`、`issues/...` 可还原仓库候选，但深链接本身不证明该仓库是推广对象。
- 短链和项目官网首版不递归追踪。无直接仓库链接时自动跳过，不按名称猜测绑定，也不引入人工补充流程。
- 候选数量、正文长度、解析时间均设上限；超限作为采集失败保留旧快照，不无限扩展采集面。

本次 RSS 样本中，帖子 [3009797](https://linux.do/t/topic/3009797)出现同一仓库的重复链接；帖子 [2704761](https://linux.do/t/topic/2704761)同时包含仓库根地址和 Release 深链接。这些只证明去重 / 规范化需求，尚未被本任务判定为正式收录项目。

### 4.2 GitHub 身份与开源状态

通过 [GitHub Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository)核验 `id`、`full_name`、`html_url`、可见性和许可证字段。采用响应中的数值 `id` 作为长期仓库主键，`owner/repo` 只作可变显示名与查找入口。

重命名 / 转移后跟随受限的官方跳转并更新名称；同名重建但 ID 不同的仓库不得继承旧关系。Fork 不自动排除，是否是帖子推广对象仍按上下文判断。仓库内容不下载、不执行。

收录政策：明确的推广对象及公开可访问的真实 GitHub 仓库是必要条件。`license == null`、`NOASSERTION` 或自定义许可只保留为元数据，不阻断来源收录，不转人工复核；来源标识不承诺该项目通过了开源许可、代码质量或安全性核实。

GitHub 临时限流 / 网络错误保留待核验状态；`404` 也可能涉及可见性，不能直接写“项目已删除”。已收录仓库明确变为非公开时停止对外发布该仓库及其关系，且不影响用户本地持有的数据。

### 4.3 推广角色判定

| 情况 | 建议处理 | 原因 |
|---|---|---|
| 唯一有效仓库，不在依赖 / 引用语境，且通过公开身份核验 | 自动收录 | 标签是推广来源，不要求恰好写出少数固定关键词 |
| 标题 / 段落明确分别介绍前端、后端等多个项目，并逐一对应链接 | 分别自动识别并收录 | 多仓库不再一律拦截 |
| 依赖、致谢、竞品、示例工程、引用或模板来源 | 排除对应候选 | 与推广对象角色不同 |
| 多个链接角色不清且没有标题 / 局部说明支持 | 自动跳过并保存原因 | 帖子或规则变化后自动重判，不等待人工 |
| 没有仓库链接，仅有官网或名称 | 自动跳过 | 不按名称搜索结果自动绑定 |

首版采用可解释规则，不依赖客户端 BYOK，也不把 LLM 放在必经链路。后续若引入模型，只辅助给出候选与理由；论坛内容不能控制工具调用、读取凭据或写用户数据。

候选诊断只读展示原帖 ID、最小上下文、仓库 ID、许可证、规则版本、自动判定与原因；不提供批准、拒绝或撤回的人工审批入口。Onebox 取卡片目标，不把卡片复制的 README 中的依赖链接当作正文推广对象。

### 4.4 变更与防止误恢复

候选只保留待机器核验（`pending`）、已发布（`published`）、自动跳过（`skipped`）。帖子内容 hash 或规则版本变化后自动重跑识别：

- 同一推广关系证据仍明确：自动更新证据版本并核验发布。
- 已观察候选的推广角色明确改变：自动跳过并移除该关系，不删除其他有效帖子的关系。
- RSS 缺席、摘要不完整或获取失败：保留最后有效发布；不等同于确认链接移除或仓库私有。
- 新增候选：独立自动核验，不继承同帖其他仓库的发布结果。

发布仅使用机器识别并验证公开身份的关系。规则升级绕过旧 RSS ETag，同时按帖子重判已有最小证据，不伪造历史帖子的最近可见时间。跨帖按 `gh_repo_id` 去重，帖子按 topic ID 去重；普通回复不会增加推广次数。

## 5. 数据、接口与缓存契约

### 5.1 最小逻辑模型

| 数据 | 核心字段 / 约束 | 用途 |
|---|---|---|
| `linuxdo_topics` | topic ID、原帖 URL、标题、创建时间、可用时的主帖 ID / 更新时间、content hash、最近见到 / 核验时间、可见性 | 论坛来源事实；不保存用户 Cookie 或回复全文 |
| `linuxdo_candidates` | 候选 ID、topic ID、规范化仓库 URL、可空 GitHub ID、角色判定、许可元数据、自动状态、规则版本、证据 hash、最小上下文 | 未核验链接也可排队；同帖同 URL 幂等，核验后按 ID 合并别名 |
| `linuxdo_repo_topics` | `(gh_repo_id, topic_id)` 唯一、推广时间、关系核验时间、发布状态 | 仅保存批准后的公开关系；目录与来源索引的共同事实源 |
| 同步任务与运行记录 | 任务身份、检查点、重试时间、计数、错误分类、发布时间 | 复用已有适用的调度 / 记录能力；持久任务不能只存在内存 |

以上是逻辑职责，不要求为每种状态新增一张表或引入消息队列。正式 DDL 根据服务端当前迁移机制确定；候选状态、公开关系更新与新快照发布需保持事务一致性。

推广时间优先使用经确认的帖子创建时间，未知时使用首次收录时间并注明口径；不能把最后回复时间当作项目发布 / 更新时间。多帖仓库的默认排序取最近一篇有效推广帖时间，再以仓库 ID 稳定打散同时间项。

只保留识别与复核必要的短上下文，不向客户端分发论坛全文或论坛图片；原帖阅读交给浏览器。正文临时副本建议处理后清理，失败 / 复核样本设置短期保留上限，具体期限随站方许可确定。来源撤回后移除公开标题与链接，可保留不含正文的必要审计状态。

### 5.2 拟议公共接口

沿用现有 Discovery 服务的鉴权与部署入口，先增加三个独立端点；不改变旧客户端的 Discovery DTO 语义。

| 端点（拟议） | 主要返回 | 客户端触发 |
|---|---|---|
| `GET /api/v1/discovery/linuxdo/bulk` | 完整已发布仓库目录、目录 summary、revision、覆盖信息 | 进入 Linux.do 分类或主动刷新；本地筛选、稳定排序与分片显示 |
| `GET /api/v1/discovery/linuxdo/provenance` | 紧凑的仓库 ID → 帖子数量 / 最近推广与核验时间映射、revision、ETag | 公共来源后台刷新，不依赖该分类是否打开 |
| `GET /api/v1/discovery/linuxdo/repos/{gh_repo_id}/topics` | 该仓库的有效帖子标题、URL、时间、revision，必要时分页 | 点击详情来源标签且没有可用帖子缓存时按需加载 |

`bulk` 与 `provenance` 是同一批公开关系的两种投影，来自同一发布版本。`provenance` 不含长正文 / 仓库完整信息，避免为了给 Stars 显示徽章先下载全部项目详情。目录 summary 同 bulk 返回，避免额外请求造成计数与列表版本不同。

首版采用完整、可条件刷新、可压缩的来源快照，先量化体积；没有规模证据前不做复杂增量协议。若体积超出预算，应在上线前改为可验证的分片快照，而不是逐行查询。帖子详情的 cursor 绑定 revision，版本失效时要求重取，不能混接不同时刻的分页。

快照至少含 `schema_version`、`revision`、`generated_at`、`source_checked_at`、`coverage_mode`、关系数与内容完整性校验信息。`generated_at` 只是 Starcat 发布时间，不表示每篇帖子都刚复核过。

管理接口另走现有 admin 鉴权，只提供触发同步与只读候选诊断；重判、重试和明确私有时的撤回由自动流程完成，不向普通 App 或运营后台增加人工审核任务。

### 5.3 客户端公共来源缓存

建议增加应用级 `RepoProvenanceStore`，首版只实现 Linux.do，不顺便重构全部既有来源。持久化内容以数据提供方身份、来源和 schema 版本隔离；仓库键固定为 GitHub.com 的数值 ID。

启动后先读取磁盘快照，非阻塞地按过期策略刷新；建议首版刷新间隔 30 分钟，在前台恢复、手动刷新等时机合并请求。多个窗口复用同一请求，来源刷新失败不阻塞启动或 Stars 浏览。服务地址变化时失效旧提供方缓存。

缓存必须能保存“尚未出现在用户本地 repos 表中的公共仓库 ID”，不能依赖本地 Stars 外键，否则无法提前知道其他分类中的项目来源。是否用独立可重建缓存表或现有磁盘缓存机制，在实施时决定；如进入已发布数据库，必须追加 `registerVN`，不得改历史迁移。

应用新快照前完成结构、版本、数量 / 完整性校验，再原子替换。每个提供方的发布 revision 应可比较先后，过期请求不能覆盖较新版本；目录响应也不能用旧来源摘要回写较新的全局索引。HTTP 失败、挑战页、半包、部分分页均保留旧快照。正常的完整空快照与失败必须可区分；移除关系通过成功发布的新版本传播，不能永远保留旧 badge。

没有快照时状态是“尚未获取”，不是“此项目从未被推广”；成功快照中未命中只表示“不在当前收录目录”。来源暂不可达时允许展示缓存记录并在 tooltip / 详情注明核验时间。建议连续 7 天无法刷新后停止展示肯定性列表 badge，在详情提供“来源记录待核验”；具体窗口在发布前确认。

RSS-only 模式还需单独处理关系核验过期：持续成功抓 RSS 不能为窗口外旧关系续期。建议超过 30 天未核验的关系进入待复核状态；是否保留历史来源说明由运营确认，不能冒充当前有效推广关系。

## 6. 跨分类来源标识与详情

### 6.1 身份与状态分离

Linux.do 标识表示“当前收录目录有此仓库的有效推广帖”，不是用户自定义 tag、Star 状态、知识库状态或本次列表来源。不得修改这些用户数据，也不得因此把论坛内容自动加入 RAG 索引。

所有入口按 `gh_repo_id` 查本地来源索引。已 Star 项目即使在本功能上线前就存在，也能命中；仓库改名后不丢来源。同一仓库经不同入口打开时来源关系一致，但原有 Weekly / Awesome / Activity 等上下文继续保留。

列表数据装配阶段批量投影来源摘要，视图只渲染，不在 `body`、`onAppear` 或每个 row 的 task 中请求网络。来源 revision 变化时只更新受影响的可见仓库，不能为一个 badge 重新查询用户全部仓库。

### 6.2 页面覆盖矩阵

| 场景 | 来源 badge | 原帖入口 / 约束 |
|---|---|---|
| Stars、标签、语言、Lists、智能集合 | 命中同一公共 ID 即显示 | 不要求访问 Linux.do 分类，不改变当前筛选 |
| 知识库 / 我的项目的公开仓库 | 与 Stars 相同 | 来源不等于已入知识库；当前私有仓库不展示公共推广标识 |
| 发现、热门、新发布、Trending、Weekly、Awesome | Linux.do 与既有来源并存 | 各自目录成员与计数不变 |
| 搜索中心的仓库结果 | 有可核验数值 ID 时显示 | 普通网页结果不按标题猜测关联；不为缺 ID 的单行补抓论坛 |
| Activity 中关联仓库的卡片 | 使用该仓库 ID 显示 | 活动类型图标保持原含义 |
| 各入口仓库详情 | 统一来源区 | 关联多篇帖子，不覆盖当前来源链接 |

紧凑选择器、Agent / RAG 的仓库卡片也需盘点：复用完整行时继承同一摘要；空间有限时只显示紧凑标识与 tooltip，不新增论坛正文。它们的全量组件清单在 UI 接入阶段核验，不以本表代替代码覆盖检查。

### 6.3 展示与点击

- 列表使用小尺寸 Linux.do 标识，tooltip 为“收录于 Linux.do · N 篇推广帖”；文字帮助与 accessibility label 同步，不仅依赖颜色。
- 标识样式沿用 Starcat 的紧凑行内元信息。官方品牌资源使用范围未确认时先使用文字标识，不用 Linux 企鹅图标冒充站点品牌。
- 来源较多时保留可识别入口并收起超出项，不覆盖 Stars、知识库、Fork、健康度等不同语义的标记；窄窗口下不挤掉仓库名。
- 列表来源标签只展示来源；详情页点击 Linux.do 标签直接用默认浏览器打开原帖，不再弹出讨论浮层，不自动切换当前分类或替换 README。
- 多帖按实际发布时间选最新一篇，同一时刻按帖子 ID 稳定选择，不依赖接口数组顺序。复用已核验的安全 URL 与缓存，无缓存才按需加载；切换仓库或取消请求后不执行迟到跳转。
- 来源详情加载失败保留 badge 与重试入口，不让来源服务故障阻止 README / 笔记 / Star 操作。收到权威撤回版本时同步更新数量和内容。

遵循 [DESIGN.md](../../../DESIGN.md)、[分页规范](../../5-规范/UI-列表分页加载规范.md)、[颜色规范](../../5-规范/UI-颜色规范.md)、[Focus Ring 规范](../../5-规范/UI-Focus-Ring-规范.md)及 i18n 规则。这里定义的是信息和行为，不是已验收的视觉样板。

### 6.4 分类、排序与分页

“发现 → Linux.do”与现有主题 / 平台属于不同筛选维度。建议来源选择显式建模为 `default / linuxdo`，Linux.do 保持独立目录；来源切换重置游标、筛选兼容性和选择身份，不能沿用普通 Discovery 的上一页结果。

首版 Linux.do 提供项目名 / 描述过滤、语言筛选，以及“最近推广 / Stars”排序；默认最近推广。现有 Discovery 主题 / 平台计数不自动复用，缺乏可靠分类数据时不展示对应空壳筛选。

2026-10-20 确认接入侧栏语言子分类：复用探索语言区的图标、可折叠标题和“全部 / 未分类 / 感兴趣语言 / 其他”分组。按 Linux.do 独立缓存聚合主语言，空白语言归未分类，其他为非空语言中感兴趣语言的补集；来源内单选与全局语言筛选独立叠加，不回写普通 Discovery 或 Weekly 状态。切换语言同步更新面包屑、实际列表数量及分页身份，不额外请求后端。

目录总数按唯一仓库计，帖子数另列。当前可见计数按本目录实际筛选结果计算；不让父级普通 Discovery 总数变成未去重的“旧目录 + Linux.do”相加。

目录快照与来源索引可能分次到达：每份响应按 revision 单独应用，不把不同版本拼成一个计数。当前目录的一轮筛选 / 分页固定快照，后台新版本准备好后整体刷新；使用现有 `ListPaginationPolicy` / `automaticListPagination`，剩余 10 个可见项时预取，快速滚动不得丢加载需求。

## 7. 验收与实施顺序

### 7.1 测试清单

| 范围 | 必测样例 / 验收点 |
|---|---|
| 采集 | RSS 含 HTML、空合法 feed、损坏 XML、`200` 挑战页、`304`、`403`、`429`、超时；失败不覆盖已发布快照 |
| 覆盖 | 窗口中旧帖重现不重复；窗口消失不误删；RSS-only 窗口外编辑不可见的限制被正确呈现 |
| 识别 | 一帖一仓库、多仓库、无仓库、依赖 / 竞品 / 引用、重复 onebox、Release 深链接、短链、伪 GitHub 域名 |
| 开源与身份 | 许可证缺失 / 不明、私有或不可访问、Fork、改名转移、同名新 ID；失败状态不伪装成已确认删除 |
| 自动判定 | 规则或帖子变化自动重判；依赖跳过不反复请求 GitHub；旧待审项迁移后自动处理；失败保留旧发布 |
| 目录隔离 | Linux.do 入库不改变普通 Discovery / Awesome / Weekly 成员语义；多帖仓库只计一个项目 |
| 跨分类 | 已有 Stars 在未打开 Linux.do 分类时显示；切换标签、语言、知识库、发现、搜索后匹配一致 |
| 缓存 | 离线启动、半包、陈旧缓存、空快照、服务地址变化、schema 不支持、后台新版本到达与正在分页并发 |
| 详情 | 一仓库多帖、窄窗口、大字号、明暗主题、长标题、键盘 / accessibility、原帖链接与撤回状态 |
| 请求成本 | 渲染 100 / 1,000 行不会产生对应数量的来源请求；来源索引更新不触发全库重新组装 |
| 数据安全 | 不写 Star / tags / notes / library，不把论坛全文同步到 CloudKit 或 RAG；数据库升级保留旧数据 |

识别规则用合成 fixture 和公开样本结构建立离线预期结果，覆盖上述正反例；发现依赖 / 竞品误收时修正规则并加入回归测试，而非引入运行期人工审批。不承诺未经评估的准确率百分比。GUI 验收需另行获得屏幕操作授权。

### 7.2 工作包与门禁

| 阶段 | 交付 | 进入下一步的条件 |
|---|---|---|
| LD-0 接入验证 | 许可范围、通道样本、正文完整性、覆盖模式与频率 | 明确 RSS 有限覆盖是否满足首版；需要时取得 API / 导出通道 |
| LD-1 服务端识别 | 自动候选识别、GitHub 核验、自动跳过 / 重判、幂等任务 | 正反例通过，原因可追溯，无人工审批依赖 |
| LD-2 公共查询 | 独立目录、来源索引、帖子端点、版本与缓存 | 目录隔离、快照原子发布、失败恢复通过 |
| LD-3 客户端来源 | 启动期非阻塞缓存、共享匹配与覆盖矩阵 | 未访问新分类的已有 Stars 也能显示，且无逐行联网 |
| LD-4 分类与详情 | 来源导航、筛选 / 排序、详情标签直接回链 | 两类来源不混淆，多帖选择、分页、错误与离线行为通过 |
| LD-5 联合验收 | App Store / Direct、升级、样本复核、请求与内存预算 | 客户端与服务端分别验证；部署与正式发布另行授权 |

实施前尚需确认三项：

1. **数据覆盖**：接受 RSS 有限覆盖先上线，还是要求取得分页 / 编辑核验通道后再上线？推荐先完成 LD-0，再据结果决定。
2. **许可证政策**：2026-10-18 已确认未知许可只记录、不阻断来源收录；标识不替项目背书开源许可。
3. **陈旧关系**：建议快照不可达 7 天、关系未核验 30 天后降级显示；应结合 RSS / API 能力与运营负担校准。

2026-10-12 规划阶段交付到方案文档为止；2026-10-15 之后按第 9 节授权开展本地实现。部署、正式发布、功能实现总览与 Changelog 仍需单独授权。

## 9. 初版实施边界

**授权**：2026-10-15，dong4j 确认开始实施，并明确后端和 Starcat 都必须缓存。本节记录实现选择，不代表线上采集已启用或 GUI 已验收。

### 9.1 后端

- 继续使用 `supports/starcat-discovery-api`。追加 `2026-10-15-linuxdo-provenance` 迁移，保留原库；共享仓库事实不改变 Discovery / Awesome 目录归属和既有评分，普通目录清理也保护 Linux.do 引用。
- 固定公开标签 RSS、无 Cookie、拒绝重定向、限制响应体/候选数/执行时间；首帖候选持久化后才推进 ETag。默认 `LINUXDO_COLLECTION_ENABLED=false`；启用后单并发采集，首轮及每轮完成后在 5 分钟至 5 小时之间随机等待，见第 11 节。
- 2026-10-15 初版曾采用单仓库、许可白名单和人工审核；2026-10-18 已由第 4、10 节的全自动规则替代。RSS 为空、缺席或解析失败仍不会自动撤回。
- 三个公共端点采用完整快照与递增 revision；目录单独返回 `promotion_dates`。来源关系按 `(gh_repo_id, topic_id)` 去重。管理接口沿用 Admin API key，与客户端只读 key 分离。
- SQLite 为持久缓存；独立响应缓存复用已有有界 LRU/inflight 实现，30 分钟 TTL、64 项/32 MiB、ETag/304/gzip，发布与撤回后换代。
- 操作契约与限制见 [Discovery API README](../../../supports/starcat-discovery-api/README.md#linuxdo-discovery)。

### 9.2 客户端
