## 1. TL;DR

Starcat 主列表搜索栏背后是**两条并行**的检索管线：

- **关键词模式（默认）**：SQLite **FTS5** 倒排索引 + **BM25** 排序，毫秒级、零网络成本，适合精确字符串。
- **AI 模式（可选）**：Embedding **向量语义**搜索 + **A 经验区间归一**+**B 字面命中 boost**+**C FTS hit 排序加权**，秒级、有 API 成本，适合自然语言意图。

两条管线**索引不同的字段**、**评分单位不同**、**排序信号互相注入**，解决三个核心问题：

1. **召回够不够全**——FTS5 加 `full_name` 让 owner 名也能被索；新建 `notes_fts` 把私有笔记纳入；向量保住"同义不同字面"的纯语义召回。
2. **排序对不对**——FTS5 用 BM25 替代 `starred_at DESC` 让真正相关的排第一；向量在 cosine 之上叠 B（字面 boost）+ C（FTS hit 加权）让"用户复制 description 都才 68%"这种反直觉 case 直接置顶。
3. **数字直不直观**——把 cosine 经验区间 `[0.30, 0.95]` 重标定到 `[0, 1]` 显示，UI 阈值滑杆与列表显示百分比同语义；同时给 1-4 档星标（★1 / ★2 / ★3 / ★4）替代精确数字，避免对小数点位的过度解读。


## 2. 双引擎概览

### 2.1 入口与切换

`SmartSearchField` 把用户输入交给 `HomeViewModel`，由 `smartSearchMode`（`.keyword` / `.semantic`）决定走哪条路径。设置项 `aiSemanticEnabled = false` 时 AI 模式被强制隐藏，强制走 `.keyword`。

```swift
// HomeViewModel.swift（节选）
if self.smartSearchMode == .semantic {
    let candidates = try await self.repository.fetchAllStarred()
    let ftsHits    = try await self.repository.searchFTS(query: self.searchQuery)
    let ftsHitIDs  = Set(ftsHits.map(\.id))
    let hits = try await semanticSearchService.search(
        query: self.searchQuery,
        candidates: candidates,
        ftsHitIDs: ftsHitIDs
    )
    return (repos: hits.map(\.repo), semanticHitMap: ...)
} else {
    return (repos: try await self.repository.searchFTS(query: self.searchQuery),
            semanticHitMap: [:])
}
```

注意：**AI 模式下 FTS5 也会跑一次**，结果作为 C 加权信号注入语义搜索（不做硬过滤）。

### 2.2 双引擎对照

| 维度 | FTS5 关键词 | 向量语义 |
|---|---|---|
| 引擎 | SQLite `fts5` 倒排表 | Embedding API（OpenAI / BGE / GTE）+ Swift cosine |
| 索引存储 | 主库 `repos_fts` / `notes_fts` 虚拟表 | `repo_embeddings.vector` BLOB |
| 索引字段 | `name` / `full_name` / `description` / `language` / `topics`（repos）+ `content`（notes） | `IndexedSnapshot`：自然语言主体 + 元数据尾巴 + 用户笔记 |
| 评分 | BM25（IDF + TF + 长度归一）；返回**负数**，越小越相关 | cosine `[-1, 1]`，文本 embedding 实测 `[0.30, 0.95]` |
| 时延 | 毫秒级（本地 SQL） | 秒级（首次需调 embedding API 算 query vector） |
| 成本 | 零 | 1 次 embedding API call / 搜索 + 全表内存 cosine |
| 短词支持 | 部分支持（`unicode61`）；笔记列不支持（`trigram`，≥3 字符）| 任意长度（取决于 embedding tokenizer） |
| CJK 中缀 | 笔记列支持（`trigram`）；repo 列不支持（`unicode61` 不切 CJK） | 不分词，整段编码，自然支持 |
| 同义词识别 | 不支持（必须字面匹配） | 自然支持（"compose" / "composer" / "撰写" 同向量空间） |
| 触发 | 默认入口 | `smartSearchMode == .semantic` 且 `aiSemanticEnabled` |

### 2.3 设计原则

- **召回不互斥**：FTS5 命中 ID 注入语义搜索作为加权信号，而不是用 FTS 命中过滤后再做 cosine——这样保留"语义同义但字面没匹"的纯向量召回。
- **评分不混算**：`displayScore` 只受 cosine 与字面 boost 影响，**不**包含 FTS 加权（FTS 是召回信号，不是相似度本身）；FTS 加权只进 `sortScore`，影响排序不影响数字。
- **阈值与显示同语义**：UI 阈值滑杆（`aiSemanticSearchScoreThreshold`，默认 0.75）过滤的就是 `displayScore`，列表上看到的百分比也是 `displayScore`，两者数字与单位严格一致。


## 3. FTS5 关键词检索

### 3.1 索引数据 — `repos_fts`

```sql
CREATE VIRTUAL TABLE repos_fts USING fts5(
    name,
    full_name,            -- 2026-06-14 新增，让 owner / "owner/repo" 都可搜
    description,
    language,
    topics,
    content      = 'repos',
    content_rowid= 'id',
    tokenize     = 'unicode61 remove_diacritics 2'
);
```

**5 个文本列**：

| 列 | 数据来源 | 典型字面 |
|---|---|---|
| `name` | `repos.name` | `swift-markdown-ui` |
| `full_name` | `repos.full_name`（**新增**） | `gonzalezreal/swift-markdown-ui` |
| `description` | `repos.description` | `Display and customize Markdown text in SwiftUI` |
| `language` | `repos.language` | `Swift` / `Go` / `Rust` / `R` |
| `topics` | `repos.topics`（JSON 字符串原样进 FTS）| `["swiftui","markdown"]` |

**外部内容模式（`content='repos'`）**：FTS 表不存原始内容，倒排表里只保留指针指向 `repos.id`，省掉一份冗余拷贝。代价是必须用触发器维护倒排索引一致性。

**触发器（3 个）**：

| 名称 | 时机 | 作用 |
|---|---|---|
| `repos_ai` | `AFTER INSERT ON repos` | 把新 repo 字段写进 FTS 倒排表 |
| `repos_ad` | `AFTER DELETE ON repos` | 用 `INSERT INTO repos_fts(repos_fts, ...) VALUES('delete', ...)` 删掉对应行 |
| `repos_au` | `AFTER UPDATE ON repos` | 先 delete 旧值再 insert 新值，保倒排表与主表对齐 |

> **决策日志**：`full_name` 列是 2026-06-14 加上的（dong4j 反馈"搜 owner 名搜不到"）。原 schema 没有 `full_name`，这次为了避免新建 V2 migration（项目未上线无线上数据，AGENTS.md 铁律 #1），直接改 V1 的 `createReposFTS` 与 3 个触发器。

### 3.2 索引数据 — `notes_fts`

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(
    content,
    content      = 'repo_notes',
    content_rowid= 'repo_id',
    tokenize     = 'trigram'
);
```

**索引 1 个列**：`repo_notes.content`（用户私有笔记 markdown 原文）。

**`content_rowid='repo_id'` 设计**：`repo_notes.repo_id` 已经是主键（每个 repo 最多一条笔记，PK = repo_id INTEGER），直接当 fts5 的 rowid 桥接，无需新增中间关联表。`UNION` 后两侧 `rowid` 都对齐到 `repos.id`，跨表去重 by `repo_id` 自然成立。

**触发器（3 个，与 repos_fts 同模式）**：

```sql
CREATE TRIGGER repo_notes_au AFTER UPDATE ON repo_notes
WHEN OLD.content IS NOT NEW.content   -- ← 守门：只在内容变化时才重建索引
BEGIN
    INSERT INTO notes_fts(notes_fts, rowid, content)
        VALUES('delete', OLD.repo_id, OLD.content);
    INSERT INTO notes_fts(rowid, content)
        VALUES(NEW.repo_id, NEW.content);
END;
```

> **`WHEN OLD.content IS NOT NEW.content`**：`repo_notes` 同时承载笔记内容 + 状态（`status` 列），状态变化（如 "Active → Archived"）触发的高频 UPDATE 不应该重建 FTS 倒排表。守门子句把这种 UPDATE 短路掉。

### 3.3 异构 tokenizer 决策

`repos_fts = unicode61` + `notes_fts = trigram` 是刻意的**异构**配置。

**`unicode61 remove_diacritics 2`**（fts5 内置）：

- 按 Unicode 属性切词，连续 ASCII alphanum / 单个汉字各成一个 token
- `remove_diacritics 2`：去除组合重音符（café → cafe）
- 短词（"Go" / "AI" / "C"）按整词索引，可命中
- **缺陷**：连续 CJK 字符（"试过部署失败"）被当作**单个 token**，搜中间词（"部署失败"）必命不中

**`trigram`**（SQLite 3.34+ 内置）：

- 按 3-字符滑动窗口切词，"hello" → `hel` / `ell` / `llo`
- CJK 中缀友好："试过部署失败" → `试过部` / `过部署` / `部署失` / `署失败` 等，搜 "部署失败" 三 trigram 全匹中
- **缺陷**：≤ 2 字符的 query 完全无法命中（短词索引失效）

**为什么不一刀切**：

| | repos_fts 用 trigram | repos_fts 用 unicode61 |
|---|---|---|
| 短英文 / 短缩写（Go / C / R / AI / ml） | ✗ ≤2 字符 query 必失 | ✓ |
| `language` 列搜 "Go" | ✗ | ✓ |
| `topics` 列搜 "ai" / "ml" | ✗ | ✓ |
| 中文 description 中缀（实测占比低，repo 元数据 95%+ 是英文） | ✓ | ✗ |
| 索引体积膨胀 | ~3× | 1× |

repos 元数据列是**短英文密集型**，必须保 `unicode61`；笔记列是**中文长文 + 长英文短语密集型**（≥3 字符词为主），切 `trigram` 收益高、缺陷低。两个列各取所需，对外是同一个 `searchFTS(query:)` 接口，每张 fts 表用各自 tokenizer 重新 tokenize query 字符串。

### 3.4 查询管线

```
用户输入
   ↓ trim + 空判
   ↓ FTSQuery.sanitize
MATCH 字符串
   ↓
SQL CTE：repos_fts MATCH OR notes_fts MATCH
   ↓
按 repo_id GROUP BY，取 MIN(bm25)
   ↓
JOIN repos
   ↓
ORDER BY best_score ASC, starred_at DESC
   ↓
[Repo]
```

**`FTSQuery.sanitize` 转义规则**（`Starcat/Shared/Utilities/FTSQuery.swift`）：

| 用户输入 | sanitize 输出 | 说明 |
|---|---|---|
| `swift ui` | `"swift" "ui"*` | 多词默认 AND，末词加 `*` 前缀通配 |
| `react.js` | `"react.js"*` | 单词包双引号防 `.` 被当成元字符 |
| `c++ template` | `"c++" "template"*` | `+` 在双引号里是字面 |
| `kubernetes 部署` | `"kubernetes" "部署"*` | 中文与英文混合按空白切 |
| `部署失败` | `"部署失败"*` | 单 token，`unicode61` 看到整段 CJK 是单 token，`trigram` 看到 3 个 trigram |
| `   ` | `""`（空） | 调用方负责短路，搜索退化为全量 |
| `"hello` | `""hello"*`（双引号转义为 `""`）| FTS5 规范：双引号内的 `"` 用 `""` 转义 |

#### 3.4.1 普通搜索 AND 与 RAG 专用 OR 的边界

`FTSQuery.sanitize` 只服务于主窗口中由用户直接输入的短关键词搜索，多词继续采用 AND，
以精确筛选为优先。知识库 RAG 不复用这条输入协议：Planner 的 `semanticQuery` 是面向
embedding 的完整自然语言，如果直接按空白转成 AND，任一介绍性词汇缺失都会让整个分片
无法召回。

RAG 使用独立的 `RAGKeywordQueryBuilder`：Planner Prompt 目标给出 3～8 个高信息量
`keywordQueries`，执行层再把每项作为不可信字面文本转义，生成显式 OR：

```text
"配置"* OR "构建目标"* OR "configuration"* OR "build target"*
```

- 每个关键词或短语独立加引号并转义内部双引号，模型输出的 `AND` / `OR` / `NOT` 等只按
  字面搜索，不能成为 FTS5 操作符。
- 中文问题应同时保留中文概念词和常见英文技术表达；FTS5 本身不翻译，跨语言覆盖来自
  双语关键词，跨语言语义仍由向量分支负责。
- 空 `keywordQueries` 只用于兼容旧自定义 Planner Prompt，此时从 `semanticQuery` 提取
  最多 8 个有界 token 并以 OR 降级，不回到旧 AND。
- repo 范围始终由候选 `repo_id` 强制限定，仓库名不加入关键词，也不是分片命中的必要条件。
- 本地硬上限为 8 项；过滤低信息项后允许少于 3 项，不为满足数量下限补造词。

因此两种语义必须长期并存：普通搜索 AND 保证精度，RAG 关键词 OR 扩大召回，再由 BM25、
Hybrid Fusion、可选 Rerank 和最终证据上限控制噪声。

**核心 SQL**（`searchFTS`，`Starcat/Core/Sync/RepoRepository.swift`）：

```sql
WITH hits(repo_id, score) AS (
    SELECT rowid, bm25(repos_fts) FROM repos_fts WHERE repos_fts MATCH ?
    UNION ALL
    SELECT rowid, bm25(notes_fts) FROM notes_fts WHERE notes_fts MATCH ?
)
SELECT r.* FROM repos r
JOIN (
    SELECT repo_id, MIN(score) AS best_score
    FROM hits
    GROUP BY repo_id
) m ON r.id = m.repo_id
WHERE r.is_starred = 1
ORDER BY m.best_score ASC, r.starred_at DESC
```

**关键点**：

- `bm25()` 必须在 fts5 表上下文调用，所以两路命中各自带 BM25 分进 CTE，不能在外层 `hits` 上再调 `bm25()`
- `UNION ALL` + `GROUP BY repo_id` + `MIN(score)`：同一 repo 两表都命中时，取**更相关的来源分数**（BM25 越小越相关）
- 外层 `ORDER BY best_score ASC, starred_at DESC`：先按相关度排，相关度相同时按收藏时间倒序

### 3.5 BM25 评分简要

SQLite fts5 内置 `bm25(table)` 函数返回当前匹配行的 BM25 分数。算法核心：

```
BM25 = Σ ( IDF(term) × TF_norm(term, doc) )
TF_norm = freq × (k1+1) / (freq + k1 × (1 - b + b × |doc|/avgdl))
IDF     = log( (N - n + 0.5) / (n + 0.5) + 1 )
```

| 符号 | 含义 |
|---|---|
| `freq` | term 在 doc 中出现次数 |
| `\|doc\|` | doc 长度（token 数） |
| `avgdl` | 平均 doc 长度 |
| `N` | 文档总数 |
| `n` | 含 term 的文档数 |
| `k1` | TF 饱和参数（fts5 默认 1.2）|
| `b` | 长度归一参数（fts5 默认 0.75）|

**重要：fts5 的 `bm25()` 返回值乘了 -1**——所以 SQLite 里 BM25 是**负数，越小（越接近负无穷）越相关**。这就是为什么 `ORDER BY ... ASC` 是把最相关排第一。

**未做的优化**：fts5 支持给不同列加权（`bm25(repos_fts, 2.0, 1.0, 0.5)`），当前未启用。等 5.x 看效果决定要不要给 `name` / `full_name` 列更高权重。

### 3.6 已知边界

| 场景 | 行为 | 备注 |
|---|---|---|
| repo description 中文中缀 | 命中不上（`unicode61` 不切 CJK） | 走 AI 模式语义搜索可命中 |
| 笔记 ≤ 2 字符 query | 命中不上（`trigram` 最小窗口 3） | 极少见（用户笔记搜短词意义不大）|
| 多词 phrase order | 不要求顺序，只要求都出现 | "swift ui" 与 "ui swift" 等价 |
| 不支持否定 / OR | sanitize 屏蔽了 `-` / `OR` 等元字符 | 故意：保用户感知简单 |
| 重音符 | 已去除（`remove_diacritics 2`） | café = cafe |
| 大小写 | 不敏感 | fts5 默认行为 |


## 4. 向量语义搜索

### 4.1 索引数据 — `IndexedSnapshot` 三段式

详细背景见 `26-向量搜索改进.md`。这里给摘要。

`IndexedTextBuilder.build(repo:body:noteContent:)` 把每个 repo 摊平成 `IndexedSnapshot`：

```swift
struct IndexedSnapshot {
    let body: String        // 自然语言主体（决策三级降级）
    let notes: String?      // 用户私有笔记
    let metadata: Metadata  // 6 个保留元数据字段
}

struct Metadata {
    let fullName, description, language, topics, license, homepage: String?
}
```

**主体 `body` 三级降级**（`chooseBody`）：

```
AI 摘要（aiSummaries.summary）  ──优先
  ↓ 缺
README 纯文本（readmes.content，已 ReadmePreprocessor.sanitize 过）
  ↓ 缺
description + topics 拼成自然语言段（不带 "Description:" 前缀）
  ↓ 都缺
""（空字符串，全靠 metadata 承担）
```

**元数据保留 6 项**（决策 D，详见 `26-向量搜索改进.md` §2 决策表）：

| 字段 | 保留理由 |
|---|---|
| `fullName` | owner/repo 字面信号（用户搜 owner 名时有用）|
| `description` | 一句话核心 |
| `language` | 主语言信号 |
| `topics` | tag 化的方向标签 |
| `license` | 偶尔是搜索意图（"MIT"）|
| `homepage` | 偶尔含产品名 |

**剔除字段**：`stars` / `forks` / `owner` / `name` / 时间戳。

- `stars / forks`：数值类对自然语言 embedding 无语义贡献，且高频变化会让 hash 不停变，触发无谓的向量重建
- `owner / name`：拆开后碎片化，已包含在 `fullName` 里
- 时间戳：同上，纯噪声

**最终拼出的 indexedText 结构**（用户在 Settings 可改模板，默认）：

```
{fullName}

{body}

{description}
Language: {language}
Topics: {topics}
License: {license}
Homepage: {homepage}

Notes:
{notes}
```

### 4.2 索引建立流程

```
ensureIndexed(candidates:model:client:force:)
   ↓
对每个 candidate：build IndexedSnapshot
   ↓
查 repo_embeddings.snapshot_json（上次索引时的快照）
   ↓
IndexedTextDiff.shouldRebuild(old:new:thresholds:)
   ├─ body 行级 diff   > body 阈值（严格 5 / 标准 10 / 宽松 20%）
   ├─ notes 行级 diff  > notes 阈值（严格 10 / 标准 20 / 宽松 30%）
   └─ metadata 任一字段变化 → 重建
   ↓ 任一触发
embedding 批量调用（batch size 32）
   ↓
upsert repo_embeddings.{snapshot_json, vector, model, dim}
```

**触发时机**：

- **后台慢速预拉**：`SemanticIndexCoordinator` 在空闲时按 starredAt DESC 顺序补全
- **按需懒补全**：`search()` 入口看到候选 repo 没向量时优先补，再做 cosine
- **README 加载完毕 / AI 摘要更新 / 用户保存笔记**：相关 repo 单条触发 `refreshIndexIfChanged`

> 单一事实：当前候选集是**全量 starred**（不限 sidebar 分类），与 FTS 路径全局搜索语义一致。

### 4.3 查询管线

```
用户输入 query
   ↓
HomeViewModel
   ↓ 并行：
   ├─ candidates  = repository.fetchAllStarred()
   └─ ftsHitIDs   = Set(searchFTS(query).map(\.id))     ← FTS5 在这里被消费
   ↓
SemanticSearchService.search(query, candidates, ftsHitIDs:)
   ↓ ensureIndexed（缺向量的 candidates 现场补）
   ↓ embedding(query) → queryVector
   ↓
对每个 repo（candidates × stored）：
    cosine          = cosineSimilarity(queryVector, vector)
    literalHit      = hasLiteralMatch(repo, query)
    effectiveScore  = literalHit ? max(cosine, 0.95) : cosine          # B
    sortScore       = effectiveScore + (ftsHit ? 0.15 : 0)              # C
    displayScore    = clamp((effectiveScore - 0.30) / 0.65, 0, 1)       # A
    tier            = bucket(displayScore)                              # ★1-4
   ↓
sort by sortScore DESC
   ↓
take limit (默认 80)
   ↓
[SemanticSearchHit] {repo, score, displayScore, tier, reason}
```

### 4.4 三段加权详解

#### A — 显示层经验区间归一

文本 embedding 模型（OpenAI / BGE / GTE 等）实测：

- **完全无关**两段文字 cosine 普遍在 `0.30 ~ 0.50`（远高于 0）
- **同一字符串**两次 embedding cosine 也很少 1.0，多在 `0.95 ~ 0.99`

直接把原始 cosine 当百分比展示会让用户看到："我搜的词字面就在 description 里，结果只有 68%"。

**解法**：经验区间 `[0.30, 0.95]` 线性归一到 `[0, 1]`：

```swift
nonisolated static let displayScoreLowAnchor:  Double = 0.30
nonisolated static let displayScoreHighAnchor: Double = 0.95

nonisolated static func normalizeDisplayScore(_ raw: Double) -> Double {
    guard raw.isFinite else { return 0 }
    let span = displayScoreHighAnchor - displayScoreLowAnchor   // 0.65
    let normalized = (raw - displayScoreLowAnchor) / span
    return max(0, min(1, normalized))                            // clamp
}
```

| 原始 cosine | displayScore |
|---|---|
| 0.30 | 0.00（0%） |
| 0.50 | 0.31（31%） |
| 0.625 | 0.50（50%） |
| 0.75 | 0.69（69%） |
| 0.85 | 0.85（85%） |
| 0.95 | 1.00（100%） |
| < 0.30 | 0（clamp）|
| > 0.95 | 1（clamp）|
| NaN | 0（短路）|

#### B — 字面命中 boost

query 完整字符串（不分词，case-insensitive）出现在以下任一位置时，effectiveScore 强制抬到 `≥ 0.95`：

```swift
nonisolated static func hasLiteralMatch(repo: Repo, query: String) -> Bool {
    let q = query.localizedLowercase
    if repo.fullName.localizedLowercase.contains(q)                 { return true }
    if let d = repo.description, d.localizedLowercase.contains(q)   { return true }
    if let t = repo.topics,      t.localizedLowercase.contains(q)   { return true }
    return false
}

let effectiveScore = literalHit ? max(cosine, 0.95) : cosine
```

**字段选择**：`fullName` / `description` / `topics` —— 都是用户显式定义的核心元数据，命中这三个里任一即视为"该 repo 与 query 强相关"。**有意不查 README 全文 / 笔记**：那些命中由 C 走 FTS hit 路径，避免 boost 信号过密。

**修复的核心 case**：用户复制 description 字符串去搜，或搜的就是 owner 名 / 仓库名 / 一个 topic 标签。这种"字面就摆在那"的搜索，原本 cosine 因为短 query × 长 doc 稀释问题只给 60-70%，B 短路直接置顶。

#### C — FTS hit 排序加权

```swift
nonisolated static let ftsBoostWeight: Double = 0.15

let ftsBoost: Double = ftsHitIDs.contains(repo.id) ? ftsBoostWeight : 0
let sortScore = effectiveScore + ftsBoost
```

**为什么是 0.15**：≈ 经验区间跨度（0.65）的 23%，足够让 FTS 命中越过 1-2 档非命中候选，但不至于完全压过明显更高的语义相关。

**为什么只进 sortScore，不进 displayScore**：FTS 命中是**召回信号**（这个 repo 的某字段含字面），不是**相似度本身**。混进 displayScore 会让"明明语义相关但字面差点"的 repo 在 UI 上反而显示更低分，反直觉。

**联合排序**：

```
sortScore = max(cosine, literalBoostFloor=0.95 if literalHit) + 0.15 if ftsHit
                ↑ B                                            ↑ C
displayScore = normalize(max(cosine, 0.95 if literalHit))
                          ↑ B 影响显示
                                      ↑ C 不影响显示
```

#### tier 档位

```swift
nonisolated static func tier(forDisplayScore score: Double) -> Int {
    if score >= 0.85 { return 4 }
    if score >= 0.65 { return 3 }
    if score >= 0.45 { return 2 }
    return 1
}
```

UI 在 `SemanticScoreBadge` 显示 1-4 颗 ★ + 数字百分比双信号。档位边界（0.85 / 0.65 / 0.45）刻意比阈值滑杆默认值（0.75）更细，让 0.45 ~ 0.85 区间也能感受到视觉差。

### 4.5 评分单位速查

| 字段 | 类型 | 用途 | 范围 |
|---|---|---|---|
| `score` | `Double` | 原始 cosine（调试 / 测试） | 文本 embedding 实测 `[0.30, 0.95]` |
| `displayScore` | `Double` | UI 百分比展示 + **阈值过滤** | `[0, 1]` |
| `sortScore` | `Double` | 内部排序 | `[0, 1.10]` 极端情况（`1.0 + 0.10` clamp 后还能再 +0.15） |
| `tier` | `Int` | UI ★ 档位 | `1, 2, 3, 4` |

**阈值过滤位置**（`HomeViewModel.applyView`）：

```swift
if let hit = semanticHitMap[repo.id], hit.displayScore < threshold { continue }
//                                       ↑ 用 displayScore，不是原始 score
```

`threshold = settings.aiSemanticSearchScoreThreshold`，默认 `0.75`。滑杆改值**本地实时生效**，不重新调 embedding API（candidates / hits 已缓存，filter 在内存里跑）。

### 4.6 reason 文案派发

`reason()` 按字面命中位置 + ftsHit 派发：

| 条件 | 文案 |
|---|---|
| `fullName` 含 query | "仓库名直接相关，语义相似度 X%" |
| `description` 含 query | "描述包含相关概念，语义相似度 X%" |
| `topics` 含 query | "Topics 命中相关方向，语义相似度 X%" |
| 以上都不命中 + `ftsHit == true` | "笔记 / 字段关键词命中，语义相似度 X%" |
| 全部不命中（纯向量召回） | "AI 向量相似度 X%" |

百分比始终是 `displayScore`，**不是**原始 cosine。

### 4.7 已知边界

| 场景 | 行为 | 备注 |
|---|---|---|
| 短 query × 长 doc 的稀释 | A 重标定后视觉对齐 | 经验区间归一是缓解，不是根治 |
| 字面 boost 是子串匹配 | "java" 也命中 "javascript" | 故意，因为分词需要选语言 / 库，复杂度高 |
| query embedding 每次调 API | 1 次 / 搜索 | candidates 向量已落库，不重 embed |
| candidate 没向量 | 现场补全（ensureIndexed）| 首搜可能慢；后续走 SWR 缓存 |
| 阈值滑杆改值 | 内存 filter 实时生效 | 不重 embed，零 API 成本 |
| 私仓向量 | 与公仓共用 embedding API | 由用户在 BYOK 时知情同意（隐私边界详见 `14-AI集成落地记录.md`）|


## 5. 双引擎协同

### 5.1 默认路径

普通用户：默认 `.keyword`（FTS5），毫秒级、零成本。SettingsView 把"AI 语义搜索"放在 toggle 后面，未开启时 `SmartSearchField` 不显示模式切换胶囊。

### 5.2 AI 模式下的协同流程

```
                 query
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
 searchFTS(query)        embedding(query)        candidates = fetchAllStarred
       │                       │                       │
       └────────┬──────────────┘                       │
                │                                       │
                ▼                                       ▼
          ftsHitIDs                              [Repo] ← ensureIndexed
                │                                       │
                └──────────────┬───────────────────────┘
                               ▼
              SemanticSearchService.search
                │
                ├─ cosine(queryVector, repoVector)
                ├─ B: literalHit ? max(cosine, 0.95) : cosine
                ├─ C: + 0.15 if ftsHit                       (sortScore)
                └─ A: normalize → displayScore → tier
                               ↓
                         排序 + 限流（80）
                               ↓
                    [SemanticSearchHit]
                               ↓
                  HomeViewModel.applyView
                               ↓
                     displayScore ≥ threshold
                               ↓
                            UI 列表
```

### 5.3 单次搜索成本

| 模式 | SQL 调用 | API 调用 | 内存计算 | 时延 |
|---|---|---|---|---|
| FTS（关键词）| 1 次 fts5 MATCH（含 UNION 两表） | 0 | 0 | ms 级 |
| Semantic | 1 次 fts5 MATCH（拿 ftsHitIDs）+ 1 次 embeddings 表 fetch | 1 次 embedding（query）| 全表 cosine（数百 repo） | s 级 |

### 5.4 阈值与排序的解耦

- 排序由 `sortScore` 决定（含 FTS C 加权）
- 显示与过滤由 `displayScore` 决定（不含 FTS C 加权）

**用户可见的现象**：

- 同一 repo 在不同阈值下显示数字不变（只是被过滤掉或保留）
- FTS 命中的 repo 即使 cosine 略低，也能"挤"到列表前几（因为 sortScore 加分）
- FTS 命中的 repo 数字不会因此虚高（因为 displayScore 不算 FTS）

### 5.5 数据共用：FTS5 不重复存原文

`repos_fts.content='repos'` / `notes_fts.content='repo_notes'` 是 fts5 的 [external content table](https://www.sqlite.org/fts5.html#external_content_tables) 模式。倒排表只存 token → docid 映射，不复制原始文本。

体积估算（按 1810 repo + 平均 1k 字符 description / topics + ~200 笔记 × 平均 500 字符）：

| 表 | 估算大小 |
|---|---|
| `repos`（原始） | ~3-5 MB |
| `repos_fts`（倒排） | ~2-3 MB（unicode61 索引）|
| `repo_notes`（原始） | ~100 KB |
| `notes_fts`（倒排） | ~300 KB（trigram ~3× 膨胀）|
| `repo_embeddings.vector` | 1810 × 1536 dim × 4 byte = ~11 MB（OpenAI embedding-3-small）|

向量是大头。FTS 倒排表相比向量小一个数量级，配合 SWR 启动加载策略不会成为性能瓶颈。


## 6. 示例走查

下面 5 个场景每条都给出"FTS 模式怎么走"+"AI 模式怎么走"的对比。所有示例假设候选库里至少包含以下 repo：

```
1. gonzalezreal/swift-markdown-ui     description="Display and customize Markdown text"
                                       language="Swift"  topics=["swiftui","markdown"]
2. ghostty-org/ghostty                 description="Fast, native, GPU-accelerated terminal"
                                       language="Zig"    topics=["terminal","gpu"]
3. tw93/Pake                           description="Turn any webpage into a desktop app"
                                       language="Rust"   topics=["webview","tauri"]
4. user 私有笔记 on tw93/Pake          content="试过部署失败，需要在 macOS 14 上签名问题"
5. apple/swift                         description="The Swift Programming Language"
                                       language="Swift"
```

### 6.1 「swift」（短词，单 token）

**FTS 模式**：

- `sanitize("swift")` → `"swift"*`
- `repos_fts MATCH '"swift"*'` 命中 1 / 5（`name`、`full_name`、`description`、`language` 多列含 swift）
- `notes_fts MATCH '"swift"*'` 命中 0（笔记内容里没 "swift"）
- BM25 排序：repo 1 因为 name + full_name 都含 "swift"，BM25 最负（最相关），排第一

**AI 模式**：

- ftsHits = {1, 5}（含 swift 的两个 repo）
- query embedding 生成，候选全表 cosine
- repo 1 字面命中 description → B boost effectiveScore = max(0.78, 0.95) = 0.95，displayScore = 1.0，★4
- repo 5 字面命中 fullName → 同上 0.95，★4
- repo 2 / 3 没字面，cosine 可能 0.40 / 0.45，displayScore ~ 15-23%，★1
- 都过 0.75 阈值的：repo 1 + 5

### 6.2 「webview tauri」（多词 AND）

**FTS 模式**：

- `sanitize("webview tauri")` → `"webview" "tauri"*`
- `repos_fts MATCH '"webview" "tauri"*'` 命中 repo 3（topics 含两词）
- `notes_fts` 命中 0
- 列表只有 repo 3

**AI 模式**：

- ftsHits = {3}
- repo 3 字面命中 topics → B boost 0.95，C 加权 +0.15，sortScore = 1.10，displayScore = 100%
- 其他 webview / 桌面化相关 repo 可能 cosine 0.55 ~ 0.65，displayScore 38-54%，★2，可能被 0.75 阈值滤掉
- 用户拖低阈值看到完整语义召回

### 6.3 「部署失败」（CJK 中缀，仅笔记列匹中）

**FTS 模式**：

- `sanitize("部署失败")` → `"部署失败"*`
- `repos_fts MATCH '"部署失败"*'` 命中 0（unicode61 不切 CJK，且 repos 列里没人写中文 description）
- `notes_fts MATCH '"部署失败"*'` 命中 repo 4（trigram 切出 `部署失` / `署失败` 两个 trigram，全匹中）
- 列表只有 repo 4（即 tw93/Pake，因为它的笔记命中）

**AI 模式**：

- ftsHits = {3}（来自笔记）
- repo 3 (tw93/Pake) 字面命中？fullName/description/topics 不含"部署失败"四字 → literalHit = false
- 但 ftsHit = true → +0.15 sortScore；displayScore 来自 cosine（笔记参与了向量索引）
- 假设 cosine = 0.62（笔记里"部署失败"+"签名问题" 与 query 强相关），displayScore = 49%，★2，过不过阈值看用户设置
- 关键观察：**FTS C 加权让这个 repo 排到比仅靠 cosine 更前**，但 displayScore 没虚高到 100%

### 6.4 「Go 后台任务框架」（混合 query：短英文 + 长中文）

**FTS 模式**：

- `sanitize("Go 后台任务框架")` → `"Go" "后台任务框架"*`
- `repos_fts MATCH ...`：
  - `"Go"` 命中所有 `language='Go'` 的 repo（unicode61 整词索引）
  - `"后台任务框架"*` 命中 0（CJK 单 token，几乎没 description 写这个完整词）
  - 因为是 AND，最终命中是 `language=Go` AND `description / topics 含完整中文短语`，几乎都不命中
- 列表为空 / 极少

**AI 模式**：

- ftsHits = []（同上）
- query embedding 把整段意图编进 vector
- 任何"Go 写的、做后台任务"的 repo 都会有较高 cosine（即使字面没匹）
- 比如 `hibiken/asynq`（Redis-backed task queue in Go），description = "Simple, reliable, and efficient distributed task queue in Go" → cosine ~ 0.72，B literalHit = false（query 没字面在 description 里），displayScore = (0.72-0.30)/0.65 = 0.65，★3
- 用户感受到"AI 真的懂我意图"

这是 **AI 模式相对 FTS 的核心价值**：CJK 中缀 + 同义词 + 意图概括。

### 6.5 「kubernetes 部署」（混合，FTS 部分命中 + 笔记命中）

**FTS 模式**：

- `sanitize("kubernetes 部署")` → `"kubernetes" "部署"*`
- `repos_fts`：含 "kubernetes" 的 repo（`description` / `topics` / `name`）AND 含 "部署"——AND 之后几乎为空（"部署" 中文很少在英文 repo 元数据里出现）
- `notes_fts`：用户在某个 k8s 相关 repo 笔记里写"试过部署"——trigram 命中"部署"
- 由于 fts5 MATCH 是按 fts 表内的字段做 AND，跨表匹配走 UNION，所以 repos_fts 单表 AND 不命中、notes_fts 单表只搜了"kubernetes 部署"在笔记列里——笔记里如果只有"部署"没有"kubernetes"，AND 也不命中

实际行为：**FTS5 MATCH 是按表内 AND**，不跨字段补全。这是 FTS5 的本质限制，AI 模式下能跨字段语义合并。

**AI 模式**：

- ftsHits 可能为空（FTS 单表 AND 不命中）
- query embedding 把"kubernetes" + "部署" 编进同一向量
- 任何 k8s 部署相关的 repo / 用户笔记里提到部署的 repo，cosine 都会比较高
- 关键：**ftsHits 为空时，C 加权失效，纯靠 A+B**——但仍能召回，只是排名不再有 FTS 加分


## 7. 后期优化空间

按"价值 × 实现成本"排序，编号 D 起延续 `26-向量搜索改进.md` 的决策表命名。

### 7.1 D — Chunk-level Embedding（核心优化）

**问题**：当前 1 个 repo 1 个向量。`indexedText` 长度从几百字到 1 万 +（README 全文截断到 12000 token）都打成同一向量，长文档语义被严重稀释。用户搜 "Hooks 文档"，React 仓库的 README 写了几十个章节，"Hooks 章节" 的语义信号被 useState 等其他章节稀释成 cosine 0.55。

**方案**：把 README / AI 摘要按 markdown header（`##` / `###`）切段，每段独立 embedding，落到新表 `repo_chunks(repo_id, chunk_index, section_path, content, vector, token_count)`。查询时：

```
对每个 candidate_repo：
    chunks = fetch repo_chunks where repo_id = ?
    cosine_per_chunk = [cosine(queryVector, chunk.vector) for chunk in chunks]
    repo_score = max(cosine_per_chunk)         # 或 top-3 平均
    best_chunk = argmax(cosine_per_chunk)
    UI 高亮 best_chunk.section_path
```

**收益**：

- 长 README 不再稀释
- 多主题 repo（如 awesome-list）每个主题单独打分
- "AI 引用具体段落" 能力的基础设施（→ 后续做本地 RAG）

**代价**：

- 索引膨胀：1810 repo × 平均 5 chunks = ~9000 embeddings，存储 ~50 MB
- 查询计算量：cosine 数从 1810 → 9000+，纯 Swift 内存矩阵运算秒级仍可接受
- README 改一行，行级 diff 触发 chunk 切分变化时重建哪些 chunk 是新问题
- chunk 拆分策略需要选（按 header / 滑窗 / 语义切分）

### 7.2 E — Hybrid Scoring（RRF / Weighted Fusion）

**问题**：当前 C 加权（FTS hit +0.15 固定）粒度太粗。FTS 命中"在 fullName 第一位"和"在 topics 第七项"，两者权重应不同。

**方案**：用 **Reciprocal Rank Fusion (RRF)** 把两路结果按排名融合：

```
RRF_score(repo) = Σ ( 1 / (k + rank_in_path(repo)) )    # k 默认 60
              path ∈ {FTS, semantic}
```

或加权融合：

```
final = α × normalize(BM25) + β × cosine + γ × literalBoost
```

**收益**：理论上排序更精细。
**代价**：调参成本（α/β/γ），且对用户不可解释（reason 文案变复杂）。

> **决策预判**：先做 D，再决定 E。E 的边际收益低，可能不优先。

### 7.3 F — Query Expansion（同义改写）

**问题**：用户搜 "部署"，我们的 embedding 模型没把 "部署" / "deploy" / "deployment" / "ship" 学到很近时，纯向量召回可能失效。

**方案**：

- 离线词表（中英对照同义词）扩展 query：`query_set = ["部署", "deploy", "deployment"]`，多次 embedding 取 max-cosine
- 或调便宜 LLM（Haiku / Flash）生成 3 个改写 query

**收益**：跨语言、跨术语召回。
**代价**：词表维护 / LLM 成本，且改写错可能引入噪声。

### 7.4 G — 短词向量路径

**问题**：FTS5 笔记列 trigram 不能搜 ≤2 字符的 query；但用户可能就想搜 "AI" / "Go" / "ML"。

**方案**：

- 短 query 走纯向量，不走 FTS
- 或在 FTSQuery.sanitize 里检测短 query → 跳 trigram 表只查 unicode61 表

**收益**：兜底极端短 query。
**代价**：分支代码 + 多 / 单 token 边界判断。

### 7.5 H — 重排序 Reranker

**问题**：cosine 召回 top-N 后，前 10 名内排序不一定准。

**方案**：cosine 拿 top-30，再用 cross-encoder（如 bge-reranker-base）做精排。本地 CoreML 部署成本高，云端 API 调用单次 query 排 30 个 pair 也可承受。

**收益**：top-K 排序准确度提升明显。
**代价**：再多一次外部依赖；cross-encoder 模型大（几百 MB）。

### 7.6 I — Embedding 模型升级

**问题**：当前推荐 OpenAI embedding-3-small（1536d, $0.02/1M tokens）。embedding-3-large（3072d, $0.13/1M tokens）效果更好。

**方案**：UI 给"质量优先 / 成本优先" 两档，文档说明重建索引的成本（1810 repo × ~12k tokens = ~22M tokens，large 约 $2.86，small 约 $0.44）。

**收益**：召回 / 排序质量普遍提升。
**代价**：用户重建索引时间成本 + API 成本。

### 7.7 J — 个性化信号

**问题**：用户的 tag / 状态 / 最近浏览 / 笔记编辑频次都是个性化信号，当前完全没用。

**方案**：

- "最近 30 天浏览过的 repo" 排序加分
- 与查询 tag 重合的 repo 加分
- `status = "in-use" / "archived"` 影响权重

**收益**：feed-style 的"最相关 + 最熟悉"双重相关。
**代价**：信号源采集 + 调参 + 隐私边界。

### 7.8 K — FTS 列权重 / 多 phrase 搜索

**问题**：fts5 支持给列加权（`bm25(repos_fts, 2.0, 1.5, 1.0, 1.0, 1.0)`），当前未启用。

**方案**：给 `name` / `full_name` 高于 `description` 的权重。

**收益**：精确 repo 名搜索更准。
**代价**：调参 + 测试。

### 7.9 优化路线建议

```
P2-Q1   D（chunk-level）         ← 核心，是后续 RAG 基础
P2-Q1   K（FTS 列权重）          ← 低成本，先调出最佳 BM25 配置
P2-Q2   I（embedding 模型升级）   ← UI 让用户选
P2-Q2   F（query expansion 同义）← 中文场景刚需
P3      H（reranker）            ← 高复杂度，看 D 后是否还需要
P3      E（RRF / Hybrid Fusion）  ← 看 K 调权重后是否还需要
P3      G（短词向量路径）        ← 边角 case
P3      J（个性化信号）          ← 与 starred-RAG 入口同场景
```

详细的"已 starred 项目本地 RAG 落地"见 `30-本地RAG设计.md`。
