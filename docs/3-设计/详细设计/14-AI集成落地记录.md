## 1. BYOK 设置与 MacPaw/OpenAI Adapter

### 1.1 技术选型过程

- 继续采用 `docs/3-设计/详细设计/12-AI库选型调研.md` 的结论：第一版使用 `MacPaw/OpenAI`。
- 接入方式选择 `branch: main`，原因是调研文档已说明当前阶段按 main 接入；本次 `xcodebuild -resolvePackageDependencies` 实际解析到 `c9342438e70e6c9a93d09220a8855459deaba00a`。
- Provider 产品路线收敛为 OpenAI-compatible：OpenAI / DeepSeek / OpenRouter / Ollama / LM Studio 都通过 Base URL + API Key + 模型名配置表达，不引入 Starcat 自建 AI 代理。

### 1.2 落地方案

- `project.yml` 增加 `OpenAI` SwiftPM 包，并重新执行 `xcodegen generate`。
- 新增 `Features/AI/AIClient.swift`，定义 Starcat 自己的 `AIClientProtocol` 和 `AIClientConfiguration`。
- 新增 `Features/AI/OpenAIClient.swift`，内部使用 MacPaw/OpenAI 的 `OpenAIProtocol`，对外只暴露 `chat` / `embedding` / `testConnection`。
- `AppSettings` 增加 AI 偏好：
  - `aiProvider`
  - `aiBaseURL`
  - `aiChatModel`
  - `aiEmbeddingModel`
  - `smartSearchMode`
- `AISettingsView` 从临时 `@State` 占位改为真实 BYOK 设置页：
  - API Key 读写 `KeychainManager.storeAIKey/loadAIKey/deleteAIKey`
  - Base URL / 模型 / 搜索模式写入 `AppSettings`
  - `测试连接` 发起一次短 embedding 请求验证 Key、Base URL 和 embedding 模型

### 1.3 最终实现方式

- API Key 不进入 `UserDefaults`，继续走项目已有 AES-GCM 本地加密文件 `credentials.json`。
- MacPaw/OpenAI 的 `Configuration` 不直接接收完整 Base URL，本次在 `OpenAIClient.makeSDKConfiguration` 中把用户输入拆成 `scheme` / `host` / `port` / `basePath`。
- 实测 MacPaw/OpenAI 当前 main 的 `EmbeddingsQuery` 签名与 README 示例不同，最终按源码使用 `EmbeddingsQuery(input: .string(input), model: model)`。
- 设置页 Provider 切换会自动填充默认 Base URL 和模型，但用户仍可手动覆盖。

## 2. AI 语义搜索与 SQLite 向量缓存

### 2.1 技术选型过程

- 入口延续 `docs/3-设计/详细设计/13-智能搜索栏交互设计.md` 的系统 `.searchable(..., placement: .toolbar)` 方案，不重新自绘搜索框。
- 结果展示选择“中栏列表内联展示”，不弹独立窗口：
  - 优点：不破坏 Starcat 现有三栏工作流，选中结果后右侧 README / 详情仍然复用；
  - 优点：列表过滤、状态筛选、多选等能力不用为弹窗重做；
  - 代价：无法像 Spotlight 一样展示长解释，但仓库管理场景更需要连续浏览和对比。
- 向量存储选择 SQLite BLOB + Swift cosine：
  - 不用 sqlite-vss / sqlite-vec 动态扩展，避免 macOS 沙盒签名、extension 加载路径和分发风险；
  - Starcat MVP 规模在几千个 starred repo，内存 cosine 排名足够；
  - 后续若达到 10k+ 或需要 ANN，再把 `RepoEmbeddingRepository` 替换为 sqlite-vec / 独立向量索引。
- 向量计算选择 BYOK provider 调用 OpenAI-compatible embeddings，而不是 Starcat 自建服务端。这样与“本地优先、不自建 AI 代理默认路线”一致。

### 2.2 落地方案

- 数据库新增 v5 migration：
  - `repo_embeddings(repo_id, model, content_hash, dimensions, embedding, indexed_text, updated_at)`
  - `ai_summaries(repo_id, model, source_hash, summary_json, generated_at)` 先随 v5 建好，供单仓智能化复用
- 新增 `RepoEmbedding` 模型，把 `[Float]` 编码为 Float32 BLOB。
- 新增 `GRDBRepoEmbeddingRepository`，提供按 repo ids 读取和批量 upsert。
- `AIClientProtocol` 增加 `embeddings(inputs:model:)`，`OpenAIClient` 通过 MacPaw/OpenAI 的 `.stringList` 批量生成向量，避免逐仓库发请求。
- 新增 `SemanticSearchService`：
  - repo 元数据转稳定索引文本；
  - SHA256 `content_hash` 判断缓存是否过期；
  - 缺失 / 过期向量按 32 条一批生成并写入 SQLite；
  - 查询时生成 query embedding，加载候选 repo 向量后用 cosine similarity 排名。
- `HomeViewModel` 增加 `smartSearchMode`、`isSemanticIndexing`、`semanticHitMap`：
  - keyword 模式继续走原 FTS5；
  - semantic 模式先取全量 starred repos，再由 `SemanticSearchService` 返回排序结果；
  - 搜索结果不写入 sidebar list cache，避免污染 All Stars / Tags 等分类缓存；
  - semantic 排名不再套用户 sortOption，避免破坏 cosine 排序。
- `RepoListView` toolbar 增加搜索模式菜单和语义索引刷新按钮；`RepoRowView` 在 compact/card 两种密度显示 AI 分数与命中说明。

### 2.3 最终实现方式

- 搜索入口：仍使用右上角系统搜索框，旁边 `sparkles` 菜单切换 Keyword / AI Semantic。
- 搜索结果：
  - 直接渲染在中栏 repo list；
  - compact 行显示 `sparkles + 百分比分数`；
  - card 行显示“命中原因 + 分数”；
  - 选中后右栏详情不变。
- 索引刷新：
  - 搜索时自动补缺失 / 过期 embedding；
  - AI 模式下 toolbar 额外提供手动刷新索引按钮，适合切换 embedding model 或大量同步后使用。
- 命中说明第一版采用本地轻量解释：仓库名 / 描述 / topics 直接命中时给出对应原因，否则显示 AI 向量相似度。没有让 LLM 为每条结果生成解释，避免一次搜索触发大量 chat 调用。

### 2.4 验证

- `xcodegen generate` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' build` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' -only-testing:StarcatTests/SemanticSearchTests -only-testing:StarcatTests/AppSettingsTests test` 通过：
  - `AppSettings` 9 项；
  - `Semantic Search` 2 项。

### 2.5 待 dong4j 审计确认

- **需审计确认，但已按最佳方案实现**：语义搜索结果不弹独立窗口，而是复用中栏列表展示。理由是 Starcat 的核心任务是“浏览、筛选、打开详情、继续管理”，内联结果最少破坏现有工作流。
- **需审计确认，但已按最佳方案实现**：第一版不用 sqlite-vss / sqlite-vec，使用 SQLite BLOB + Swift cosine。理由是 MVP 数据规模可控，动态扩展分发风险高于收益。
- **需审计确认，但已按最佳方案实现**：命中说明不调用 LLM 逐条生成，先做本地解释。理由是每次搜索都生成 LLM explanation 会显著增加延迟和 BYOK 成本。

## 3. 本地 AI 与单仓智能化第一阶段

### 3.1 技术选型过程

- 继续遵守 `docs/发展规划.md §13(详见 `docs/3-设计/详细设计/23-Chrome-插件方案.md`).1` 第一阶段目标：
  1. AI 设置页；
  2. AI service protocol；
  3. 单仓 AI 摘要；
  4. AI 标签推荐确认流；
  5. AI 结果本地缓存。
- UI 采用详情页嵌入式 AI Tab，而不是独立 Chat 页。原因与发展规划一致：AI 摘要和当前 repo 上下文强绑定，不把 Starcat 做成泛聊天工具。
- 缓存复用第二阶段已建的 `ai_summaries` 表，避免再开一张 `repo_ai_analysis` 表造成概念重复。
- 标签推荐使用现有 `TagRepository` / `RepoTagRepository`，用户点击“应用”后才创建/绑定标签，不引入“建议态标签”新表。

### 3.2 落地方案

- 新增 `AISummaryRecord` / `GRDBAISummaryRepository`：
  - 主键 `(repo_id, model)`；
  - `source_hash` 判断 repo 元数据或 README 变化后缓存是否过期；
  - `summary_json` 保存结构化 AI 输出。
- 新增 `RepoAIInsightService`：
  - 读取 repo 元数据和 `ReadmeRepository` 本地 README 缓存；
  - 对 rendered HTML 做轻量去噪；
  - 调用 BYOK chat model；
  - 要求模型返回严格 JSON；
  - 解析后写入 SQLite 缓存。
- 新增 `RepoAIInsightViewModel`：
  - 加载缓存；
  - 生成 / 重新生成；
  - 单个应用标签；
  - 全部应用标签；
  - 标签落库后通知 HomeViewModel 刷新 Sidebar 计数和当前列表。
- 新增 `RepoAIInsightPanel`：
  - 未生成状态；
  - 生成中状态；
  - 错误状态；
  - 已生成摘要；
  - 推荐标签确认区。
- `RepoDetailView` 将原 README 正文区改为 `README / AI 摘要` segmented tab，默认仍展示 README。

### 3.3 最终实现方式

- AI 输出结构：
  - `oneLiner`
  - `summary`
  - `platforms`
  - `suitableFor`
  - `strengths`
  - `risks`
  - `minimalExample`
  - `suggestedTags`
  - `model`
  - `generatedAt`
- Prompt 明确要求简体中文、JSON only、标签 3-8 个、`model/generatedAt` 留空由 Starcat 本地填充。
- 标签确认流：
  - 已存在同名标签：直接复用；
  - 不存在：创建普通用户标签（`icon = tag`，颜色为空走 UI 默认）；
  - 关联 repo：`RepoTagRepository.addTag`，幂等；
  - 不自动应用任何 AI 标签。
- README / AI 摘要 tab 设计：
  - 默认 README，避免 AI 抢占原阅读路径；
  - AI 摘要作为正文 tab，不放进会随滚动折叠的 metadata panel；
  - 生成模型和生成时间在底部显示。

## 4. AI 设置与调用链重构

### 4.1 技术选型过程

- 继续使用 `MacPaw/OpenAI`，不换 SDK。原因：当前 SDK 已支持 `models()` / `chatsStream()` / `embeddings()`，重构重点是 Starcat 自己的配置抽象，而不是 provider adapter 选型。
- 多服务商配置先使用 `UserDefaults` JSON，API Key 继续走 `KeychainManager` 本地 AES-GCM 加密文件。原因：profile / 模型启用 / Prompt 是偏好数据，第一版不需要数据库查询能力；API Key 仍不能进 UserDefaults。
- 模型列表测试走 OpenAI-compatible `/models` 族接口，解析只强依赖 `data[].id`。原因：OpenAI / DeepSeek / OpenRouter / LM Studio / Ollama 都有模型列表能力，但 capability 元数据不统一。

### 4.2 落地方案

- 新增 `AIConfiguration.swift`：
  - `AIProviderProfile` 表达一个可调用服务商；
  - `AIModelDescriptor` 表达模型、启用状态和能力；
  - `AIModelTaskConfiguration` 把摘要 / 标签 / Embedding 三个任务拆开；
  - `AIModelParameters` 保存 temperature / topP / topK / max tokens / timeout / stream；
  - `AIPromptConfiguration` 保存 system prompt 和 user prompt template。
- `AppSettings` 增加 `aiProviderProfiles`、`aiSummaryTask`、`aiTagsTask`、`aiEmbeddingTask`，启动时从旧版 provider/baseURL/chatModel/embeddingModel 迁移默认 profile。
- `KeychainManager` 增加 provider-scoped API Key：`storeAIKey(_:forProvider:)` / `loadAIKey(forProvider:)` / `deleteAIKey(forProvider:)`，并保留旧全局 Key fallback。
- `AIClientProtocol` 增加参数化 chat、流式 chat 和模型列表：
  - `chat(request:)`
  - `chatStream(request:)`
  - `listModels()`
- `OpenAIClient`：
  - Chat 请求写入 temperature / topP / maxCompletionTokens / JSON mode；
  - `chatStream` 汇总 delta，并在结束时发 `.completed`；
  - `listModels` 使用标准 HTTP GET 解析 provider 返回模型；
  - 对 `finish_reason == length` 抛 `responseTruncated`，避免继续误报“空内容”。
- `AISettingsView` 重写为四段：
  1. AI 服务商：新增 / 删除 profile、保存 Key、测试并获取模型；
  2. 已发现模型：启用 / 禁用 / 修正 Chat 或 Embedding 能力；
  3. 模型设置：摘要、推荐标签、Embedding 分别选择 provider + model，支持自定义模型名；
  4. 参数与 Prompt：按任务编辑参数和默认 Prompt。
- `RepoAIInsightService` 将摘要和标签拆成并行调用：
  - 摘要走 `aiSummaryTask`，优先流式；
  - 标签走 `aiTagsTask`，只解析 JSON；
  - 标签失败只返回 `tagErrorMessage`，不丢弃已生成摘要。
- `SemanticSearchService` 改为只读取 `aiEmbeddingTask`，允许 Embedding 与摘要/标签使用不同 provider。

### 4.3 最终实现方式

- 摘要默认 Prompt 不再要求 JSON，改为结构化 Markdown 中文摘要，减少 LM Studio / Qwen reasoning 模型卡在 JSON 输出上的概率，同时恢复旧版摘要的信息密度。
- Markdown 摘要固定输出 `一句话总结 / 这个项目是什么 / 平台生态 / 适合场景 / 优点 / 风险与注意点 / 最小示例` 七块内容。
- `RepoAISummaryMarkdownView` 使用 `gonzalezreal/swift-markdown-ui` 渲染摘要；README 仍保持 WebView/GitHub HTML 路线，不混用。
- `AIModelListView` 把设置页的模型列表封装为固定高度内部滚动组件，支持过滤、启用 / 禁用和能力修正。
- 标签默认 Prompt 仍要求 JSON，只解析 `suggestedTags` envelope 或数组。
- `RepoAIInsightPanel` 展示两块内容：
  - 第一块：AI 摘要，生成时显示流式草稿；
  - 第二块：推荐标签，失败时显示独立错误，不影响摘要。
- AI 结果缓存仍复用 `ai_summaries`，cache key 从单 model 升级为 `summary:{provider}/{model}|tags:{provider}/{model}`。

### 4.4 验证

- `xcodegen generate` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' build` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' test` 通过，Swift Testing：233 tests / 35 suites。

### 4.5 待 dong4j 审计确认

- **需审计确认，但已按最佳方案实现**：模型能力只做启发式推断，并允许用户在模型列表中手动修正。理由是 OpenAI-compatible provider 没有统一 capability schema。
- **需审计确认，但已按最佳方案实现**：`topK` 当前只保存配置，不发送到 MacPaw/OpenAI。理由是 Chat Completions 标准字段不含 `top_k`，强发会破坏远端 provider 兼容性。
- **需审计确认，但已按最佳方案实现**：摘要改为自然语言流式输出，标签保留 JSON 输出，两者并行。理由是摘要的用户价值是“尽快可读”，标签的用户价值是“可结构化确认落库”，两者失败边界应该分离。
- **需审计确认，但已按最佳方案实现**：AI 摘要引入 MarkdownUI 渲染短 Markdown，不复用 README WebView。理由是 README 需要完整 GFM 兼容，AI 摘要只需要 Starcat Prompt 控制下的标题、列表、段落和可选代码块，独立 SwiftUI 组件更轻。
- **需审计确认，但已按最佳方案实现**：模型列表用固定高度内部滚动，不继续把每个模型平铺到 Settings Form。理由是模型数量由 provider 决定，不能让外部设置页承担无限增长的滚动成本。
