# AI 用量统计面板设计

> 状态: 已实现
> 日期: 2026-07-19
> 参考: [mm7894215/TokenTracker](https://github.com/mm7894215/TokenTracker)

## 1. 目标

Starcat 的知识库 RAG、语义搜索、仓库摘要、标签推荐、README 翻译、Agent 和 MCP 都会调用用户配置的 AI Provider。该面板回答三个问题：

1. Starcat 发起了多少次 AI 请求？
2. 已知的输入、输出和总 token 分别是多少？
3. 用量主要来自哪个功能、Provider 和模型？

本期只统计功能上线后的新请求，不扫描 Provider 账单，也不猜测历史用量。

## 2. 视觉参考与 Starcat 化

已核对 TokenTracker 的 Dashboard light / dark 截图及 README。参考其高信息密度卡片、时间范围切换、总量指标、趋势图、模型分布和明细表结构，但不照搬 Web 侧栏、品牌色或费用模块：

- Starcat 使用独立 macOS 原生窗口、系统材质、语义色和紧凑间距。
- 首屏以 5 张 KPI 卡片建立总览，再展示输入 / 输出趋势。
- 功能、模型和最近调用使用 segmented detail 区，避免一个窗口同时堆满三张大表。
- 入口复用全局状态 popover，并在 Actions 菜单提供可发现的辅助入口。
- 本期不展示费用。BYOK、自定义 OpenAI-compatible、本地 Ollama / LM Studio 模型缺少统一且可靠的价格真相源，显示 0 美元会误导用户。

## 3. 统计口径

### 3.1 一次调用

一次 Chat Completions 或 Embeddings HTTP 请求记为一次 API 调用。Embedding 批量传入 N 段文本仍是一次调用，并单独记录 `item_count = N`。

成功、失败和取消都会落一条事件。失败只保存错误分类，不保存完整服务端错误文本。

### 3.2 Token 字段

| 字段 | 语义 |
|---|---|
| `input_tokens` | Provider 返回的 prompt / input token |
| `output_tokens` | Provider 返回的 completion / output token |
| `total_tokens` | Provider 返回的请求总 token |
| `cached_input_tokens` | 输入 token 的子集，不再加到总 token |
| `reasoning_output_tokens` | 输出 token 的子集，不再加到总 token |

统计面板直接求和 `input_tokens`、`output_tokens`、`total_tokens`，不使用 `input + output` 反推总量，避免不同 Provider 的计费细节造成二次修正。

### 3.3 Usage 来源

- `provider`: Provider 明确返回，面板标记为“精确”。
- `estimated`: 预留给未来本地估算；v1 不主动生成估算值。
- `unavailable`: Provider 未返回，或流在最终 usage chunk 到达前中断；token 字段保持 `NULL`，绝不写 0。

“用量可用率” = `total_tokens IS NOT NULL` 的请求数 / 全部请求数。总 token 只对已知值求和，调用次数始终包含未知 token 的请求。

## 4. 功能归因

| feature | phase 示例 | 调用来源 |
|---|---|---|
| `rag` | `planning` / `query_embedding` / `answer` / `compression` / `title` | 知识库问答 |
| `knowledge_indexing` | `chunk_embedding` | 知识库 child chunk 向量化 |
| `semantic_search` | `query` / `indexing` | 主界面语义搜索与 repo 向量索引 |
| `repo_summary` | `generation` | 仓库摘要 |
| `repo_tags` | `recommendation` | 标签推荐 |
| `repo_chat` | `conversation` | 仓库 AI 对话 |
| `readme_translation` | `translation` | README 翻译 |
| `agent` | `generation` | Agent 文本生成 |
| `mcp` | `semantic_search` | MCP 语义搜索 |

`feature` 是面向用户的稳定一级维度，raw value 已持久化，禁止随意改名；`phase` 是功能内部的稳定阶段，便于后续诊断和更细筛选。

## 5. 数据结构

正式版后新增迁移 `v14-ai-usage-events`，不修改已发布 `v1-initial`。

```text
ai_usage_events
├── id / started_at / completed_at / duration_ms
├── provider_id / provider_kind / model
├── feature / phase / operation
├── input_tokens / output_tokens / total_tokens
├── cached_input_tokens / reasoning_output_tokens
├── item_count / usage_source / status / error_category
└── correlation_id
```

索引覆盖 `completed_at`、`(feature, completed_at)` 和 `(model, completed_at)`。v1 保留原始请求级事件，用实时 SQL 聚合，不增加日报表或后台汇总任务；只有真实数据量证明聚合成为瓶颈后，才考虑追加 rollup 表。

数据库按 GitHub 用户物理隔离。`AIUsageRecorder` 持有可切换的 `DatabaseManaging` 门面，不缓存 writer，账号切换后自动写入新用户库。

## 6. 采集链路

`OpenAIClient` 是统一采集边界：

- 非流式 Chat 读取 `ChatResult.usage`。
- 流式 Chat 设置 `stream_options.include_usage = true`，读取最终 `ChatStreamResult.usage`。
- Embedding 读取 `EmbeddingsResult.usage`，同时记录输入 item 数。
- 消费端终止流时取消底层 Task，记录 `cancelled`。
- Provider 明确拒绝 `stream_options` / `include_usage` 且尚未收到任何 chunk 时，无 usage 重试一次；已开始输出后绝不重试，避免重复扣费或拼接两段回答。
- SQLite 写入是旁路能力，写入失败只记本地诊断，不改变 AI 请求结果。

业务层通过 `AIUsageContext` 传归因，不让 adapter 根据 prompt 或调用栈猜功能。

## 7. 查询与 UI

时间范围支持今天、7 天、30 天和全部。筛选支持功能、Provider 和模型。一次查询返回：

- 总 token、输入 token、输出 token、API 调用、Embedding item、成功率和用量可用率；
- 按本地自然日聚合的输入 / 输出趋势；
- 功能分布、模型分布；
- 最近 80 条调用明细；
- 全历史 Provider / 模型筛选选项。

完整窗口通过一次 GRDB 只读事务获得以上一致快照。全局状态 popover 只需要今日总量和调用次数，因此走单独的单 SQL `summary` 查询；它和完整快照复用同一汇总实现及统计口径，不执行趋势、分布、明细或全历史筛选选项查询，避免轻量入口随事件量增长而变慢。

点击功能或模型分布行会直接下钻筛选。日期和数字格式显式使用 SwiftUI `locale`，独立窗口 hosting root 挂载 `.appLocaleEnvironment()`。

## 8. 隐私与同步边界

只落统计元数据。严禁加入：

- system / user prompt、对话历史、模型 response；
- API Key、GitHub Token、Base URL；
- 完整错误文本、HTTP body、请求 JSON；
- README、代码、笔记或附件内容。

`ai_usage_events` 不进入 CloudKit，也不进入匿名遥测。用户切账号后读取对应账号的本地库。
