# 数据库设计

> 本文档定义 Starcat 的本地数据库 Schema（GRDB / SQLite）。
>
> **代码真相**：`Starcat/Core/Database/Migrations/DatabaseMigrationsV1.swift`
> 是 schema 的**单一信任源**；本文档跟随其更新，主要用于阅读理解 + 跨表关系讨论。

---

## 一、设计原则

### 1.1 数据分类

| 类型 | 说明 | 示例表 |
|------|------|------|
| 用户数据 | 用户创建，不能丢失 | `tags` / `repo_notes` / `repo_tags` / `saved_searches` |
| 可重建数据 | 可从 GitHub API 重新拉取 | `repos` / `releases` / `starred_repos` |
| 缓存数据 | 可按需重新生成 | `readmes` / `trending_repos` / `trending_readmes` / `readme_translations` / `repo_embeddings` / `ai_summaries` |
| 状态机 | 进程级状态 | `sync_state` / `tag_stats_cache` |

### 1.2 性能

- 为最热查询路径建复合索引（如 `(is_starred, language, starred_at)`）
- 支持分页 + `LIMIT`
- 批量写入用 GRDB 事务，1810 条 starred repo 入库 < 1s
- FTS5 全文搜索 with `unicode61 remove_diacritics 2` tokenizer（中文友好）

### 1.3 schema 演进策略（2026-07-12 起：正式版已发布）

**正式版之后（当前阶段）**：所有 schema 演进**必须追加** `registerVN(into:)` 迁移
（`ALTER TABLE` / `CREATE TABLE` / 索引），由 GRDB `DatabaseMigrator` 按版本顺序执行。

**禁止**：
- 直接修改已落地的 `v1-initial` 建表 SQL，指望用户删 sqlite 重建
- 把新字段只写进 `ensurePrelaunchRAGSchema` / `repairPrelaunchDevelopmentSchema` 这类开发期补丁

**允许**：
- 新建表、加列、加索引的追加迁移
- 在迁移里做一次性数据搬迁（明确写清原因与回滚不可用约束；本项目仍不支持降级）

> **背景**：2026-05-29 到 2026-06-11 曾把 v1~v9 摊平进 `v1-initial`（上线前策略）。
> 正式版发布后该策略废止；v2 / v3 / v4… 以追加形式保护已发布用户本地数据。
> 代码入口：`Starcat/Core/Database/Migrations/DatabaseMigrationsV1.swift` 的 `registerAll`。

## 二、用户数据 + 仓库核心表

### 2.1 `repos`（仓库主表，28 列）

```sql
CREATE TABLE repos (
    -- 标识
    id INTEGER PRIMARY KEY,                -- GitHub repo ID (Int64)
    owner TEXT NOT NULL,
    name TEXT NOT NULL,
    full_name TEXT NOT NULL UNIQUE,

    -- 元数据
    description TEXT,
    language TEXT,
    stars_count INTEGER NOT NULL DEFAULT 0,
    forks_count INTEGER NOT NULL DEFAULT 0,
    watchers_count INTEGER NOT NULL DEFAULT 0,
    topics TEXT,                           -- JSON 数组字符串，如 `["ai","swift"]`

    -- URL
    license TEXT,
    homepage TEXT,
    html_url TEXT NOT NULL,
    clone_url TEXT,
    ssh_url TEXT,

    -- 标志（SQLite 0/1 Bool）
    is_private  INTEGER NOT NULL DEFAULT 0,
    is_fork     INTEGER NOT NULL DEFAULT 0,
    is_archived INTEGER NOT NULL DEFAULT 0,
    is_starred  INTEGER NOT NULL DEFAULT 1,

    -- 时间戳（ISO8601）
    pushed_at  TEXT,
    created_at TEXT,
    updated_at TEXT,
    starred_at TEXT,

    -- 缓存
    cached_at TEXT,

    -- StarcatRepoCardDTO v1.2 hero 区扩展字段（R-01）
    owner_avatar      TEXT,
    subscribers_count INTEGER,
    default_branch    TEXT,
    open_issues_count INTEGER
);

CREATE INDEX idx_repos_language        ON repos(language);
CREATE INDEX idx_repos_stars           ON repos(stars_count);
CREATE INDEX idx_repos_starred_at      ON repos(starred_at);
CREATE INDEX idx_repos_owner_language  ON repos(owner, language);

-- HOM-46 性能优化：sidebar 列表查询热路径（1810 行 400~700ms → ms 级）
CREATE INDEX idx_repos_is_starred_starred_at          ON repos(is_starred, starred_at);
CREATE INDEX idx_repos_is_starred_language_starred_at ON repos(is_starred, language, starred_at);
```

**关键设计决策**：

- `topics` **存 JSON 数组字符串**而非关联表：topics 数量稳定 ≤ 20、只在卡片显示用，
  关联表会引入 N+1 + cascade，性价比低。
- `owner_avatar / subscribers_count / default_branch / open_issues_count` **不分子表**：
  来自 `StarcatRepoCardDTO` v1.2（R-01 三场景共用架构 §6.1），与 stars/forks/topics
  是同一抽象层级；分子表会让 SELECT 变 JOIN，得不偿失。全部 nullable 容 GitHub API 偶发漏返。
- `is_starred` **默认 true**：本地 repos 表只存「当前或曾经 star 过」的仓库；
  `(is_starred, ...)` 复合索引用 `is_starred = 0` 表达软删除（取消 star 但保留 tags / notes）。

### 2.2 `starred_repos`（用户 star 关系表）

```sql
CREATE TABLE starred_repos (
    repo_id      INTEGER PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE,
    user_id      INTEGER NOT NULL,
    starred_at   TEXT    NOT NULL,
    sync_status  TEXT    NOT NULL DEFAULT 'synced',  -- synced / pending / failed
    last_sync_at TEXT
);

CREATE INDEX idx_starred_repos_user       ON starred_repos(user_id);
CREATE INDEX idx_starred_repos_starred_at ON starred_repos(starred_at);
```

独立于 `repos` 缓存维度；`sync_status` 跟踪与 GitHub 的双向 star 同步态。

### 2.3 `tags`（用户标签）

```sql
CREATE TABLE tags (
    id         TEXT PRIMARY KEY,                                  -- UUID
    name       TEXT NOT NULL UNIQUE,
    color      TEXT,                                              -- hex，如 `#FF5722`
    icon       TEXT,                                              -- SF Symbol 名称
    sort_order INTEGER NOT NULL DEFAULT 0,
    is_preset  INTEGER NOT NULL DEFAULT 0,                        -- 1 = 系统预设
    parent_id  TEXT REFERENCES tags(id) ON DELETE SET NULL,       -- 二级嵌套
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE INDEX idx_tags_parent ON tags(parent_id);
```

- `is_preset = 1`：Languages / Tools / Frameworks 等系统预设，不可删。
- `parent_id`：自引用外键，支持二级嵌套（如 "Web" → "React" / "Vue"）。

### 2.4 `repo_tags`（repo ↔ tag 多对多关联）

```sql
CREATE TABLE repo_tags (
    repo_id    INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    tag_id     TEXT    NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    created_at TEXT    NOT NULL,
    PRIMARY KEY (repo_id, tag_id)
);

CREATE INDEX idx_repo_tags_tag ON repo_tags(tag_id);
```

### 2.5 `repo_notes`（用户私有笔记 + 阅读状态）

```sql
CREATE TABLE repo_notes (
    repo_id         INTEGER PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE,
    content         TEXT,
    status          TEXT    NOT NULL DEFAULT 'unread',  -- unread / reading / using / deprecated
    is_ai_generated INTEGER NOT NULL DEFAULT 0,
    edited_at       TEXT
);
```

`status` 用于 UI 侧排序 / 筛选。

### 2.6 `saved_searches`（用户保存的搜索条件）

```sql
CREATE TABLE saved_searches (
    id           TEXT PRIMARY KEY,
    name         TEXT NOT NULL,
    query        TEXT NOT NULL,        -- 搜索过滤参数 JSON 序列化
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL,
    last_used_at TEXT
);
```

### 2.7 `sync_state`（同步状态机）

```sql
CREATE TABLE sync_state (
    user_id             INTEGER PRIMARY KEY,
    last_sync_at        TEXT,                     -- 上次全量同步完成
    last_incremental_at TEXT,                     -- 上次增量同步完成
    starred_count       INTEGER NOT NULL DEFAULT 0,
    synced_count        INTEGER NOT NULL DEFAULT 0,
    failed_count        INTEGER NOT NULL DEFAULT 0,
    sync_status         TEXT    NOT NULL DEFAULT 'idle',  -- idle / syncing / failed
    error_message       TEXT,
    stars_etag          TEXT                      -- /user/starred?page=1 ETag (W4-4 C2)
);
```

- `stars_etag`：用于 `/user/starred?page=1` 的 ETag 304 短路；下次同步先 conditional GET，
  未变（304）则跳过整轮 starred 列表拉取，省 ~50KB 网络流量并避免触发 GitHub rate limit。
  NULL = 首次同步语义。

### 2.8 `tag_stats_cache`（tag 关联 repo 计数缓存）

```sql
CREATE TABLE tag_stats_cache (
    tag_id     TEXT PRIMARY KEY REFERENCES tags(id) ON DELETE CASCADE,
    repo_count INTEGER NOT NULL,
    cached_at  TEXT    NOT NULL
);
```

避免每次 sidebar 渲染都跑 `SELECT COUNT(*) FROM repo_tags WHERE tag_id = ?`。

## 三、`readmes`（GitHub 原 README 缓存）

```sql
CREATE TABLE readmes (
    repo_id       INTEGER PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE,
    content       TEXT,                  -- 原始 Markdown
    rendered_html TEXT,                  -- 渲染后的 HTML（可选）
    etag          TEXT,                  -- 用于 ReadmeAPI 304 短路
    last_modified TEXT,                  -- Last-Modified header
    cached_at     TEXT    NOT NULL,
    size          INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_readmes_cached ON readmes(cached_at);
```

由 ReadmeAPI 的 ETag 流程**独占管理**；与翻译表 `readme_translations` 完全独立（详见 §7）。

## 四、FTS5 全文搜索

> **Tokenizer 选择**：统一使用 `unicode61 remove_diacritics 2`，原因：
> - `unicode61` 对 CJK 字符按字切分（适合中文笔记 / 描述）
> - `remove_diacritics 2` 处理重音符号（如 `café` → `cafe`），方便英文搜索
> - **不使用 `porter`**：porter 是英文词干算法（`running → run`），对中文反而切碎语义
> - 长期方向：若中文搜索体验不够，可后续替换为 `simple` + jieba 分词或集成 sqlite-vec

```sql
-- 与 repos 表通过外部内容模式零冗余同步（FTS 不存原始内容，节省 100KB+ 存储）
CREATE VIRTUAL TABLE repos_fts USING fts5(
    name,
    description,
    language,
    topics,
    content='repos',
    content_rowid='id',
    tokenize = 'unicode61 remove_diacritics 2'
);

-- 3 个触发器保持 FTS 与 repos 表同步（AFTER INSERT / DELETE / UPDATE）
CREATE TRIGGER repos_ai AFTER INSERT ON repos BEGIN
    INSERT INTO repos_fts(rowid, name, description, language, topics)
    VALUES (new.id, new.name, new.description, new.language, new.topics);
END;

CREATE TRIGGER repos_ad AFTER DELETE ON repos BEGIN
    INSERT INTO repos_fts(repos_fts, rowid, name, description, language, topics)
    VALUES('delete', old.id, old.name, old.description, old.language, old.topics);
END;

CREATE TRIGGER repos_au AFTER UPDATE ON repos BEGIN
    INSERT INTO repos_fts(repos_fts, rowid, name, description, language, topics)
    VALUES('delete', old.id, old.name, old.description, old.language, old.topics);
    INSERT INTO repos_fts(rowid, name, description, language, topics)
    VALUES (new.id, new.name, new.description, new.language, new.topics);
END;
```

`repo_notes` 的全文搜索如未来支持，单独建 `notes_fts` 虚拟表（不污染 `repos_fts`）。

## 五、Trending 缓存（与 repos / readmes 完全隔离）

### 5.1 `trending_repos`

```sql
CREATE TABLE trending_repos (
    -- 榜单维度（PK）
    period          TEXT    NOT NULL,    -- daily / weekly / monthly
    language_filter TEXT    NOT NULL,    -- "" 表示全部语言
    rank            INTEGER NOT NULL,    -- 0-based

    -- repo 标识
    gh_repo_id INTEGER,                  -- R-01 v1.2 跨场景 ✓ 标记用（不是 PK）
    full_name  TEXT NOT NULL,
    owner      TEXT NOT NULL,
    name       TEXT NOT NULL,

    -- 基础元数据
    description    TEXT,
    language       TEXT,
    stars_count    INTEGER NOT NULL DEFAULT 0,
    forks_count    INTEGER NOT NULL DEFAULT 0,
    watchers_count INTEGER,
    topics         TEXT,                 -- JSON 数组字符串

    -- URL / 许可
    license  TEXT,
    homepage TEXT,

    -- 状态标志（SQLite 0/1 Bool）
    is_archived INTEGER,
    is_fork     INTEGER,
    is_private  INTEGER,

    -- StarcatRepoCardDTO v1.2 hero 区扩展字段（R-01）
    owner_avatar      TEXT,
    subscribers_count INTEGER,
    default_branch    TEXT,
    open_issues_count INTEGER,

    -- trending 特有
    stars_in_period   INTEGER NOT NULL DEFAULT 0,
    contributors_json TEXT,              -- JSON [{username, avatarURL, profileURL}]

    -- 时间戳
    pushed_at  TEXT,
    created_at TEXT,
    updated_at TEXT,
    cached_at  TEXT NOT NULL,

    PRIMARY KEY (period, language_filter, rank)
);

CREATE INDEX idx_trending_repos_full_name ON trending_repos(full_name);
```

**设计决策**（dong4j 2026-06-02 选型 scope_b + schema_a + readme_pk_c + ttl_c）：

- **`scope_b`**：列表 + README 两块都做持久化。
- **`schema_a`**：独立表与 `repos` / `readmes` 完全隔离 —— trending 没有真实 GitHub repo id
  （HTML scrape 出来的），强制复用 `repos.id` PK 会触发"何时从外部 API 补 id"的链式问题。
  注意 `gh_repo_id` 列是 R-01 v1.2 跨场景 ✓ 标记需要的辅助字段，**不是 PK**（PK 仍是榜单
  维度三元组 `(period, language_filter, rank)`）。
- **`ttl_c`**：列表与 README 都不设 TTL，每次进 Trending 都强制走网络重拉，本地缓存只承担
  「离线兜底 + 快速首屏 SWR」角色。
- **字段命名与 `repos` 表对齐**（`topics` / `is_archived` / `pushed_at` 等），便于
  toDomain / makeEphemeralRepo 转换函数代码风格统一。

### 5.2 `trending_readmes`

```sql
CREATE TABLE trending_readmes (
    full_name     TEXT PRIMARY KEY,
    rendered_html TEXT,
    etag          TEXT,
    last_modified TEXT,
    cached_at     TEXT    NOT NULL,
    size          INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_trending_readmes_cached ON trending_readmes(cached_at);
```

- PK 用 `full_name` 而非 `repo_id`：trending 只有 `owner/repo`，没 Int64 id。
- 字段语义与 `readmes` 完全对齐，让 ReadmeAPI 复用同一套 SWR + ETag 304 逻辑。
- **不挂 FTS5 触发器**：trending 是榜单切换型，不需要全文搜索。

## 六、AI 智能化缓存

### 6.1 `repo_embeddings`（语义搜索向量存储）

```sql
CREATE TABLE repo_embeddings (
    repo_id       INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    model         TEXT    NOT NULL,
    content_hash  TEXT    NOT NULL,        -- 参与向量化的 repo 文本 SHA256
    dimensions    INTEGER NOT NULL,
    embedding     BLOB    NOT NULL,        -- Float32 向量
    indexed_text  TEXT    NOT NULL,
    updated_at    TEXT    NOT NULL,
    PRIMARY KEY (repo_id, model)
);

CREATE INDEX idx_repo_embeddings_model_hash ON repo_embeddings(model, content_hash);
```

**为什么不用 sqlite-vss / sqlite-vec 动态扩展**：macOS 沙盒分发动态 SQLite extension
引入签名 / 加载路径 / App Review 风险；Starcat MVP 规模在几千条 starred repo 内，
Swift 内存 cosine 排名足够稳定。

PK `(repo_id, model)`：让后续换 embedding model 时不会误用旧向量。

### 6.2 `ai_summaries`（单仓 AI 智能化结果）

```sql
CREATE TABLE ai_summaries (
    repo_id      INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    model        TEXT    NOT NULL,
    source_hash  TEXT    NOT NULL,           -- README / 元数据指纹
    summary_json TEXT    NOT NULL,           -- AI 结构化输出
    generated_at TEXT    NOT NULL,
    PRIMARY KEY (repo_id, model)
);

CREATE INDEX idx_ai_summaries_repo ON ai_summaries(repo_id);
```

**只缓存 JSON，不自动写标签** —— 标签应用必须用户显式确认（产品策略：AI 保守，
用户先看后用）。`source_hash` + `model` 用于判断 README / repo 元数据变更后是否需要重新生成。

## 七、Release 订阅追踪（HOM-47）

### 7.1 `release_subscriptions`

```sql
CREATE TABLE release_subscriptions (
    repo_id               INTEGER PRIMARY KEY REFERENCES repos(id) ON DELETE CASCADE,
    is_subscribed         INTEGER NOT NULL DEFAULT 1,
    notify_enabled        INTEGER NOT NULL DEFAULT 1,
    last_known_release_id INTEGER,
    last_known_tag_name   TEXT,
    last_polled_at        TEXT,
    created_at            TEXT    NOT NULL,
    modified_at           TEXT    NOT NULL    -- CloudKit LWW 同步用
);

CREATE INDEX idx_release_subscriptions_active ON release_subscriptions(is_subscribed);
```

- `notify_enabled` 与 `is_subscribed` 解耦：未来可支持"订阅但静默"（MVP 默认 true）。
- `last_known_release_id` / `last_known_tag_name`：上次轮询见过的最新 Release 游标，
  下次轮询判断"出现了哪些新 Release 需要通知"。
- 索引 `(is_subscribed)`：时间线视图查询路径"所有 is_subscribed = 1 的订阅"。

### 7.2 `releases`

```sql
CREATE TABLE releases (
    id                INTEGER PRIMARY KEY,                          -- GitHub Release ID
    repo_id           INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    tag_name          TEXT    NOT NULL,
    name              TEXT,
    body_markdown     TEXT,                                         -- GitHub Release notes 完整 Markdown 原文
    html_url          TEXT    NOT NULL,
    is_prerelease     INTEGER NOT NULL DEFAULT 0,
    is_draft          INTEGER NOT NULL DEFAULT 0,
    published_at      TEXT,
    created_at_remote TEXT,
    assets_json       TEXT,                                         -- 资产数组直接存 JSON
    is_read           INTEGER NOT NULL DEFAULT 0,
    fetched_at        TEXT    NOT NULL
);

CREATE INDEX idx_releases_repo_published ON releases(repo_id, published_at);
CREATE INDEX idx_releases_published      ON releases(published_at);
```

- `assets_json` 不开 release_assets 关联表：assets 数量稳定 ≤ 10 条、只在时间线展示用，
  没有"按平台筛选所有 release 资产"的查询场景；关联表会引入 N+1 + cascade，性价比低。
- `body_markdown`：保存 GitHub 返回的完整 Release notes Markdown；列表摘要由 UI 层截断，
  数据库层不截断，确保活动页发行版详情可完整渲染。
- 索引设计：时间线主查询按 `published_at DESC` 排所有订阅 repo 的 releases，
  `(repo_id, published_at)` 复合 + `(published_at)` 单列覆盖两条热路径。

## 八、README 翻译缓存（HOM-68）

### 8.1 `readme_translations`

```sql
CREATE TABLE readme_translations (
    repo_id          INTEGER NOT NULL REFERENCES repos(id) ON DELETE CASCADE,
    target_language  TEXT    NOT NULL,        -- BCP-47 风格 raw，如 `zh-Hans` / `en` / `ja`
    model            TEXT    NOT NULL,
    source_hash      TEXT    NOT NULL,        -- 参与翻译的 README HTML 的 SHA256 指纹
    translated_html  TEXT    NOT NULL,
    size             INTEGER NOT NULL DEFAULT 0,
    created_at       TEXT    NOT NULL,
    PRIMARY KEY (repo_id, target_language)
);

CREATE INDEX idx_readme_translations_repo ON readme_translations(repo_id);
```

**为什么独立表而不是把翻译塞进 `readmes` 表**：

- `readmes` 是「GitHub 原 README 缓存」，由 ReadmeAPI 的 ETag 流程独占管理；
  塞翻译会让 ETag 304 命中时既要 `touchCachedAt` 又要保留 translation 字段，写入逻辑
  容易踩进「翻译被原 README 304 路径误清」之类的坑。
- 一个 repo 可能存多个目标语言（中/英/日同时缓存），独立表用复合 PK 更直观。
- `source_hash` 失配 → 自动重新翻译（README 被作者更新后旧译文失效）。
- 翻译表 schema 完全独立于 ETag/Last-Modified 流程，未来要加分块翻译进度
  或质量评分字段时不影响 readmes。

## 九、表创建顺序与外键依赖

`DatabaseMigrationsV1.swift::registerV1` 按以下顺序建表（被外键引用方先建）：

```
repos (无依赖)
  ├─ starred_repos          → repos
  ├─ repo_tags              → repos, tags
  ├─ repo_notes             → repos
  ├─ readmes                → repos
  ├─ tag_stats_cache        → tags
  ├─ repo_embeddings        → repos
  ├─ ai_summaries           → repos
  ├─ release_subscriptions  → repos
  ├─ releases               → repos
  └─ readme_translations    → repos

tags (无依赖，被 repo_tags / tag_stats_cache 引用)

saved_searches / sync_state / trending_repos / trending_readmes (独立无外键)

repos_fts (FTS5 虚拟表，AFTER repos 建好；+ 3 触发器)
```

## 十、GRDB 模型代码示例

### 10.1 Repo 模型

```swift
import GRDB

struct Repo: Codable, FetchableRecord, PersistableRecord, Identifiable {
    static let databaseTableName = "repos"

    var id: Int64
    var owner: String
    var name: String
    var fullName: String

    var description: String?
    var language: String?
    var starsCount: Int
    var forksCount: Int
    var watchersCount: Int
    var topics: String?

    var license: String?
    var homepage: String?
    var htmlUrl: String
    var cloneUrl: String?
    var sshUrl: String?

    var isPrivate: Bool
    var isFork: Bool
    var isArchived: Bool
    var isStarred: Bool

    var pushedAt: String?
    var createdAt: String?
    var updatedAt: String?
    var starredAt: String?

    var cachedAt: String?

    // StarcatRepoCardDTO v1.2 hero 字段
    var ownerAvatar: String?
    var subscribersCount: Int?
    var defaultBranch: String?
    var openIssuesCount: Int?

    // 关联（GRDB association API）
    static let starredRepo = hasOne(StarredRepo.self)
    static let note = hasOne(RepoNote.self)
    static let aiSummary = hasOne(AISummary.self)
    static let tags = hasMany(Tag.self, through: hasMany(RepoTag.self), using: RepoTag.tag)
}
```

### 10.2 批量写入模式

```swift
// 批量插入：比单条插入快 10-100 倍
try await dbPool.write { db in
    try Repo.insertAll(db, repos, onConflict: .replace)
}

// 显式事务（多表写入或自定义错误处理）
try await dbPool.write { db in
    try db.inTransaction {
        for repo in repos {
            try repo.save(db)
        }
        return .commit
    }
}
```
