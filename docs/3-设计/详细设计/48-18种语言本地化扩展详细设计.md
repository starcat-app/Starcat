# Starcat 18 种语言本地化扩展详细设计

> 状态：方案已确认，待开发
> 适用版本：后续多语言版本，具体版本号由排期决定
> 最后更新：2026-07-24
> 现行规范：[`docs/5-规范/i18n-军规.md`](../../5-规范/i18n-军规.md)

## 1. 文档目标

本文档把 Starcat 从现有英语、简体中文双语扩展到 18 种常用语言，给出可以直接实施的代码边界、仓库边界、数据格式、脚本契约、翻译状态、CI 门禁、分阶段任务、测试命令与验收标准。

本文档是本次 18 语言扩展的实施单一入口。开发者仍须遵守现有 i18n 强制规范；如本文与旧版 [`10-国际化(i18n)设计.md`](10-国际化(i18n)设计.md) 的历史示例冲突，以 `docs/5-规范/i18n-军规.md` 和当前代码为准。

本次目标不是“创建 16 个空语言包”，而是让 18 种语言都满足以下用户可见结果：

1. App 构建产物包含对应 `.lproj`。
2. 用户能在“设置 → 通用 → 语言”中识别并切换语言。
3. SwiftUI、独立窗口、sheet、popover 和 `String.l10n` 查表结果一致。
4. AI 摘要、AI 标签、AI 对话和 RAG 输出语言跟随 Starcat Display Language。
5. 翻译通过 key、占位符、状态、完整度和人工 UI 验收后才对用户开放。

## 3. 范围边界

### 3.1 本次包含

- Starcat App 内的静态 UI 文案。
- `LocaleStore`、`String.l10n`、`LocalizedBundle` 对 18 种语言的运行时支持。
- AI 与 RAG 输出语言映射。
- `Localizable.xcstrings` 中 18 种语言的翻译内容。
- `supports/starcat-localization` 公开协作仓库中的 18 个 `.xcloc`。
- 主仓库导入导出脚本、公开仓库校验脚本和 CI。
- 阿拉伯语 RTL、长文本和多文字系统 UI 验收。
- README、贡献说明、语言状态与审核工作流。

### 3.2 本次不包含

- App Store Connect 商品页标题、描述、关键词、宣传文本和截图本地化。
- `starcat.ink` 官网、公开文档站和更新日志的 18 语言翻译。
- GitHub README 内容的 AI 翻译目标语言功能；该功能与 App UI 本地化是两套概念。
- 把所有 macOS 系统菜单在运行时无重启切换语言。系统 `NSMenu` 和部分 AppKit 对话框仍受现有平台限制。
- 数据库 schema 变更。本功能不需要数据库迁移。
- 接入付费机器翻译 API 或在仓库中保存翻译服务密钥。

### 3.3 “支持一种语言”的定义

只有同时满足以下条件，语言才能在 Starcat 正式语言选择器中出现：

- 语言包与当前 String Catalog key 集合一致。
- 除明确登记的字面量外，没有缺失 target。
- 没有 `needs-translation`、`new` 或 `needs-review-translation`。
- 占位符、换行、Markdown/HTML 结构校验通过。
- 至少一名母语或高熟练度审核者完成语义审核。
- 指定 UI 验收矩阵通过。
- 构建产物中存在对应 `<locale>.lproj`。

创建 `.xcloc`、生成 AI 初稿或依赖英语 fallback，都不能单独算“已支持”。

当前代码链路：


### 4.1 已确认的当前缺口

1. `AppLocale` 只声明 `en`、`zh-Hans`。
2. `aiOutputLanguageDescriptor` 只覆盖部分语言。
3. `zh-Hant` 只有 script、没有 region 时，旧逻辑可能误判为 Simplified Chinese。
4. `starcat-localization.py export --locale ...` 会先删除整个 `Translation Packages/`。
5. 导出会覆盖公开包中尚未导回 Catalog 的在途翻译。
6. 导入脚本忽略 XLIFF target state，并把所有非空 target 直接标记为 `translated`。
7. 公开仓库 CI 只验证 JSON/XML 可解析，无法阻止错 locale、错 key、占位符损坏和未审核翻译。
8. 公开 `.xcloc` 已明显落后于主 Catalog。
9. 旧设计文档仍有 `String(localized:)`、`NSLocalizedString` 示例，与现行军规冲突。

## 6. 目标架构

```text
Starcat/Resources/Localizable.xcstrings
        │
        │ export（保留在途翻译）
        ▼
supports/starcat-localization/
├── locales.json
├── nontranslatable-keys.json
└── Translation Packages/
    ├── en.xcloc
    ├── zh-Hans.xcloc
    ├── zh-Hant.xcloc
    ├── ja.xcloc
    └── ... 共 18 个
        │
        │ 翻译 + review
        ▼
starcat-localization.py import
        │
        │ 只接受已审核 state
        ▼
Localizable.xcstrings
        │
        │ Xcode 编译
        ▼
Starcat.app/Contents/Resources/<locale>.lproj
```

核心原则：

1. `Localizable.xcstrings` 是 App 运行时翻译的单一来源。
2. `.xcloc` 是公开协作交换格式，不是 App 运行时来源。
3. 公开仓库可以保存未完成语言；主 App 不能提前暴露未完成语言。
4. 任何导出都必须保留公开包里的在途 target，不能把贡献者成果清空。
5. 任何导入都必须尊重审核状态，不能把 AI 草稿伪装成已翻译。

## 7. 公开语言清单

### 7.1 新增 `locales.json`

文件：

```text
supports/starcat-localization/locales.json
```

建议结构：

```json
{
  "schemaVersion": 1,
  "sourceLocale": "en",
  "locales": [
    {
      "id": "en",
      "englishName": "English",
      "nativeName": "English",
      "direction": "ltr",
      "releaseStatus": "released"
    },
    {
      "id": "zh-Hans",
      "englishName": "Simplified Chinese",
      "nativeName": "简体中文",
      "direction": "ltr",
      "releaseStatus": "released"
    },
    {
      "id": "ar",
      "englishName": "Arabic",
      "nativeName": "العربية",
      "direction": "rtl",
      "releaseStatus": "draft"
    }
  ]
}
```

完整文件必须包含第 2 节确认的 18 个 locale，顺序与 App 语言选择器顺序一致。

允许的 `releaseStatus`：

| 状态 | 含义 | App 是否可见 |
| --- | --- | --- |
| `draft` | 未翻译或 AI 初稿阶段 | 否 |
| `review` | 翻译完成，等待母语审核/UI 验收 | 否 |
| `released` | 所有门禁通过，可以进入正式构建 | 是 |

`releaseStatus` 是人工发布决策，不得仅根据“非空字符串比例”自动提升。

### 7.2 新增 `nontranslatable-keys.json`

文件：

```text
supports/starcat-localization/nontranslatable-keys.json
```

用途：显式登记无需翻译的产品名、技术名、纯格式字符串和符号，避免将“缺翻译”与“故意保持字面量”混在一起。

建议结构：

```json
{
  "schemaVersion": 1,
  "keys": {
    "Starcat": "产品名",
    "GitHub": "产品名",
    "%@ MB": "仅格式与单位，不需要翻译"
  }
}
```

约束：

- 每个 key 必须提供非空原因。
- Catalog 删除 key 后，CI 必须报告 stale allowlist。
- 不能用通配符掩盖一批缺失翻译。
- 普通 UI 句子不能进入此清单。

## 8. XLIFF 翻译状态契约

本项目统一使用以下状态语义：

| XLIFF target state | 含义 | 可导回 Catalog | 可正式发布 |
| --- | --- | --- | --- |
| `needs-translation` | 尚无翻译 | 否 | 否 |
| `new` | 新增、尚未处理 | 否 | 否 |
| `needs-review-translation` | AI 初稿或源文案变化后待复核 | 否 | 否 |
| `translated` | 已由翻译者完成并审核 | 是 | 是 |
| `final` | 维护者终审完成 | 是 | 是 |
| `signed-off` | 已签署/发布确认 | 是 | 是 |

规则：

1. AI 生成 target 必须写成 `needs-review-translation`。
2. 人工打开 `.xcloc` 修改，不代表自动完成终审；提交者必须在 PR 中声明审核范围。
3. 源字符串变化时，即使 target 非空，也必须降级为 `needs-review-translation`。
4. 默认 import 只接受 `translated`、`final`、`signed-off`。
5. 如维护者确需导入未审核内容，只能使用显式危险参数，并且不能把对应语言加入 `AppLocale`。

## 9. 主仓库导入导出脚本改造

目标文件：

```text
supports/scripts/starcat-localization.py
```

### 9.1 命令面保持兼容

继续保留：

```bash
supports/scripts/starcat-localization.py export
supports/scripts/starcat-localization.py export --locale ja
supports/scripts/starcat-localization.py import --package <path>
supports/scripts/starcat-localization.py import-all
```

新增：

```bash
supports/scripts/starcat-localization.py audit
supports/scripts/starcat-localization.py report
```

### 9.2 `export` 行为

无 `--locale`：

1. 读取 `locales.json`。
2. 导出全部 18 个语言包。
3. 校验 Catalog `sourceLanguage == locales.json.sourceLocale`。
4. 对每种语言合并 Catalog 现有 target 与旧 `.xcloc` 在途 target。
5. 使用临时目录完成写入和校验后，再原子替换目标包。
6. 不在构建失败时破坏现有语言包。

带 `--locale`：

1. 只重建指定 locale。
2. 不删除 `Translation Packages/`。
3. 不改其他 `.xcloc` 的时间戳和内容。
4. locale 不在 `locales.json` 时立即失败。

target 合并优先级：

```text
Catalog 中已审核 target
  > 旧 .xcloc 中的在途 target
  > 空字符串
```

源字符串变化检测：

```text
旧 XLIFF <source> != 当前 Catalog source
  且旧 target 非空
  -> 保留 target
  -> state = needs-review-translation
```

### 9.3 `import` 行为

导入单包前必须检查：

- `contents.json.targetLocale` 与目录名一致。
- XLIFF `target-language` 与 `targetLocale` 一致。
- XLIFF `source-language` 与 Catalog `sourceLanguage` 一致。
- key 在 Catalog 中存在。
- target state 属于允许集合。
- 占位符与 source 相容。

默认行为：

```text
translated / final / signed-off -> 写回
needs-translation / new / needs-review-translation -> 跳过并报告
空 target -> 跳过
未知 key -> 失败，不静默跳过
```

不能沿用当前“导入任何非空 target 并统一写成 translated”的行为。

### 9.4 `import-all` 行为

- 只处理 `locales.json` 中存在的语言包。
- 按 manifest 顺序输出结果。
- 任意包结构错误时整体不写 Catalog。
- 所有包预检成功后才开始一次性写入。
- 保持 String Catalog 的 `"key" : value` 格式，禁止用普通 `json.dump` 重排整个文件。

现有 `save_catalog()` 会全文件序列化为 `"key": value` 风格，与 i18n 军规冲突。实现时必须复用 `scripts/xcstrings_patch.py` 的最小补丁策略，或新增专门保持 Xcode String Catalog 格式的 writer，并用格式测试锁定。

### 9.5 `audit` 行为

`audit` 是只读门禁，至少输出：

- Catalog source locale 与 key 数。
- manifest locale 数与重复项。
- 每个包的 key 总数。
- 每个状态的数量。
- 缺失 key、未知 key、重复 key。
- 占位符错误。
- stale `nontranslatable-keys`。
- `released` 语言是否达到零阻断项。

有阻断项时返回非 0。

### 9.6 `report` 行为

默认输出人类可读表格：

```text
Locale   Total  Translated  Review  Missing  Completion  Release
en       4198   4144        0       0        100.00%     released
de       4198   3800        120     224      90.52%      draft
```

完成度分母排除 `nontranslatable-keys.json` 登记项，但报告必须单独显示 excluded 数量。

支持机器格式：

```bash
supports/scripts/starcat-localization.py report --format json
```

## 10. 占位符与结构校验

### 10.1 必须识别的占位符

- Foundation/printf：`%@`、`%d`、`%ld`、`%lld`、`%f`。
- 位置参数：`%1$@`、`%2$d`。
- 百分号转义：`%%`。
- Prompt token：`{targetLanguage}`、`{outputLanguage}`、`{readmeHTML}` 等。
- String Catalog 复数或 substitution token。

校验规则：

1. source 与 target 的 token 种类、数量必须一致。
2. 非位置 printf token 的顺序必须一致。
3. 使用 `$` 的位置参数允许按语言语序调整，但索引集合必须一致。
4. `%%` 不能被误判为普通占位符。
5. target 不得新增 source 中不存在的花括号 token。

### 10.2 必须保护的结构

- `\n` 与段落边界。
- Markdown code span、链接和列表结构。
- HTML tag 和 attribute。
- URL scheme、环境变量、命令、文件路径。
- `Starcat`、`GitHub`、`OpenSSF`、`CodeFlow`、`CodebaseMemory` 等登记术语。

CI 不能只用“target 非空”判断翻译有效。

## 11. 公开仓库校验器与 CI

### 11.1 文件落点

在 `starcat-localization` 独立仓库新增：

```text
scripts/validate_packages.py
tests/test_validate_packages.py
```

`.github/workflows/ci.yml` 只负责调用已提交的 validator，不继续维护大段 inline Python，保证本地与 CI 使用同一实现。

### 11.2 校验顺序

1. 解析 `locales.json` 和 `nontranslatable-keys.json`。
2. 断言 manifest 恰好包含确认的 18 个 locale。
3. 断言 `Translation Packages/` 与 manifest 一一对应。
4. 校验 `.xcloc/contents.json`。
5. 校验 XLIFF 和嵌入式 `.xcstrings` 可解析。
6. 校验所有包使用相同 source snapshot。
7. 校验每个 XLIFF 的 key 集合与 source snapshot 一致。
8. 校验 locale、target state、重复 key。
9. 校验占位符与结构。
10. 对 `released` locale 执行零缺失、零待审核门禁。
11. 输出 completion report。

### 11.3 CI 触发

### 11.4 PR 贡献约束

语言 PR 默认只允许修改：

- 自己负责的 `<locale>.xcloc`。
- 对应 glossary（如存在）。
- 必要的语言状态说明。

禁止语言 PR 顺手更新其他语言包、README 推广区块或 CI。

## 12. App 运行时改造

### 12.1 `AppLocale`

目标文件：

```text
Starcat/Core/Settings/LocaleStore.swift
```

最终枚举：

```swift
enum AppLocale: String, CaseIterable, Identifiable, Sendable {
    case system
    case english = "en"
    case simplifiedChinese = "zh-Hans"
    case traditionalChinese = "zh-Hant"
    case japanese = "ja"
    case korean = "ko"
    case german = "de"
    case french = "fr"
    case spanish = "es"
    case brazilianPortuguese = "pt-BR"
    case italian = "it"
    case russian = "ru"
    case dutch = "nl"
    case polish = "pl"
    case ukrainian = "uk"
    case turkish = "tr"
    case vietnamese = "vi"
    case indonesian = "id"
    case arabic = "ar"
}
```

不要在 16 种新增语言仍为 `draft/review` 时一次性合入全部 case。运行时 PR 应在全部目标语言通过发布门禁后合入；若业务决定分批发布，则只加入当批 `released` locale。

### 12.2 原生语言名

建议把语言名改成字面 `String`：

```swift
var nativeDisplayName: String {
    switch self {
    case .system:
        return String.l10n("settings.general.language.system")
    case .english:
        return "English"
    case .simplifiedChinese:
        return "简体中文"
    // ...
    }
}
```

设置页使用：

```swift
Text(verbatim: option.nativeDisplayName)
```

`system` 是唯一跟随当前 UI 翻译的选项；其余语言名使用原生字面值。

### 12.3 `effectiveLocale`

除 `system` 外可以统一使用 raw value：

```swift
var effectiveLocale: Locale {
    rawValue == AppLocale.system.rawValue
        ? .autoupdatingCurrent
        : Locale(identifier: rawValue)
}
```

实现时可选择显式 switch 或统一构造，但必须有覆盖全部 case 的单测。

| `ja` | `Japanese` |

| `fr` | `French` |

```text

```

### 12.5 `String.l10n` 与 `LocalizedBundle`

现有按 raw locale 查找 `<locale>.lproj` 的逻辑可以复用，不需要为每种语言增加 switch。

需要更新其中“raw 只能是 `en` / `zh-Hans`”的过时注释，并增加测试确认：

- `pt-BR` 能命中 `pt-BR.lproj`。
- `zh-Hant` 能命中 `zh-Hant.lproj`。
- 找不到 bundle 时回退到 development language，而不是空字符串。

### 12.6 用户已有设置兼容性

`AppLocaleOverride` raw value 保持不变：

- 现有 `system`、`en`、`zh-Hans` 无迁移。
- 异常或已移除值继续回落 `.system`。
- 不增加数据库 migration。

## 13. 翻译生产与审核流程

### 13.1 推荐策略

采用：

```text
英语 source
  -> AI 或翻译者初稿
  -> needs-review-translation
  -> 母语审核
  -> translated
  -> UI 验收
  -> releaseStatus = released
```

AI 只能提高初稿速度，不能替代审核。

### 13.2 翻译批次

建议按 UI 与市场优先级分批生产内容，但最终里程碑仍是 18 种全部完成。

| 批次 | Locale | 目的 |
| --- | --- | --- |
| A | `zh-Hant`、`ja`、`ko`、`de`、`fr`、`es`、`pt-BR` | 主要 Mac 市场与 CJK |
| B | `it`、`ru`、`nl`、`pl`、`uk` | 欧洲与 Cyrillic |
| C | `tr`、`vi`、`id`、`ar` | 新兴开发者市场与 RTL |

英语和简体中文先作为基线刷新，不进入新增翻译批次。

### 13.3 翻译上下文

每个翻译任务至少提供：

- key。
- English source。
- comment。
- 所属功能前缀。
- placeholder 清单。
- glossary 链接。
- 允许的最大长度或 UI 场景（已知时）。

不能只把脱离 key/comment 的英文字符串列表交给模型或翻译者。

### 13.4 审核要求

审核者至少检查：

- 术语一致。
- UI 语气一致。
- GitHub、macOS、AI 技术名没有错误翻译。
- 按钮与菜单文案足够简洁。
- 占位符未改变。
- 否定、删除、购买、隐私和安全文案语义准确。
- 文案与对应 UI 场景匹配。

高风险文案必须人工逐条检查：

- 删除、清空、取消 Star。
- 登录、Token、API Key、权限和隐私。
- 订阅、购买、恢复购买和授权。
- 数据导入导出。
- AI 内容外发提示。
- 错误恢复和诊断。

## 14. RTL 与布局验收

阿拉伯语不能只检查字符串是否显示。

### 14.1 必须验证

- `layoutDirection == .rightToLeft`。
- Sidebar、列表和详情栏的阅读顺序。
- 返回、前进、展开、收起箭头的语义方向。
- `leading` / `trailing` 是否正确，避免固定 `.left` / `.right`。
- AppKit window toolbar 和 traffic-light/control 布局。
- 数字、百分比、日期、时间、URL、代码和仓库名的双向文本。
- TextField 光标和 placeholder。
- Markdown、README、RAG 引用和代码块保持技术内容 LTR。
- 图表、时间线和排序箭头不因镜像改变数据语义。

### 14.2 禁止做法

- 通过全局 `.environment(\.layoutDirection, .leftToRight)` 规避 RTL。
- 为 Arabic 单独复制整套 View。
- 把所有 SF Symbol 无条件镜像。
- 用空格手工修正双向文本。

必要时只对代码、URL、hash、命令等技术内容局部指定 LTR。
