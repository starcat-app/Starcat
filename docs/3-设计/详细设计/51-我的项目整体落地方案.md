## 1. 结论

在“星标”模块下新增一等分类“我的项目”，展示当前 GitHub 用户：

1. 个人账号拥有的仓库；
2. 通过组织成员身份可访问的组织仓库；
3. 以上范围内经用户额外授权的 Private / Internal 仓库。

“我的项目”不是 Smart Collection，也不是“是否已 Star”的别名。它代表 GitHub 上的项目归属关系，因此必须拥有独立数据来源、关系表和同步状态；Repo 元数据、列表行、详情 Scaffold、README、洞察和 Star History 继续复用现有实现。

授权采用双通道：

- 现有 GitHub OAuth 保持不变，继续负责登录、公开 Stars 和公开仓库 Star / Unstar。
- 新增可选 GitHub App 连接，使用细粒度只读权限访问用户明确安装的个人或组织仓库。
- 禁止为实现 Private 仓库直接把现有 OAuth 扩大为 `repo` scope。GitHub OAuth 的 `repo` 会获得私有仓库广泛读写能力，无法把源码权限限制为只读。

首版最终完成定义包含 Public、Private 和组织项目；只有 Public 项目可见的中间版本不能被描述为需求已完成。

## 2. 背景与当前事实

### 2.1 当前代码基础

| 能力 | 当前事实 | 本方案处理 |
|---|---|---|
| Sidebar | `SidebarRootPage.manage` 下已有固定分类、Tags、Languages、GitHub Stars Lists | 新增 `SidebarItem.myProjects`，放在“全部仓库”之前 |
| Repo 模型 | `repos` 已能保存 `is_starred = 0` 的外部或知识库仓库 | 继续复用，不创建第二套 Project Repo 模型 |
| 列表 | `RepoListScope` + `RepoListFilters` + GRDB 分页承担 Manage 主路径 | 新增项目 scope 和项目筛选，不回退到全量内存过滤 |
| 详情 | `RepoDetailScaffold` + `ManageDetailContent` 统一承载 README / 洞察 | 原样复用，只增加项目权限和可见性元数据 |
| 仓库洞察 | 已有活动 KPI、Commit、贡献者、Release、Health、OpenSSF、社区与安全信号 | 按 token 能力加载；权限不足显示 unavailable，不伪造为 0 |
| Star History | v16 已支持公开远端历史、本机每日快照和 Private 本地拦截 | 项目同步成功后接入现有本机快照链路 |
| 数据库 | 最新已发布迁移为 `v16-repository-insights` | 必须追加 `v17-my-projects`，禁止修改 `v1-initial` 或 v16 |

### 2.2 当前授权边界

产品决策仍是 `read:user + public_repo`；当前代码常量还包含历史 `user` 项，实施 Phase 0 必须先核对并收口实际授权头，但本方案不在设计阶段改写现有登录链。

当前授权无法读取 Private 仓库。GitHub 官方同时明确：

- OAuth `repo` scope 对 Public / Private 仓库具有广泛读写能力；
- OAuth App 目前无法把源码访问限制为只读；
- GitHub App 使用细粒度权限，并允许用户只选择部分仓库；
- 桌面应用可以使用 GitHub App Device Flow 获取 user access token。

参考：

- [GitHub OAuth scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)
- [List repositories for the authenticated user](https://docs.github.com/en/rest/repos/repos?apiVersion=2026-03-10#list-repositories-for-the-authenticated-user)
- [Generating a user access token for a GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)
- [Installing a GitHub App from a third party](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)

### 2.3 关键语义

以下关系相互独立：

```text
已 Star
我的项目
已加入知识库
```

同一 Repo 可以同时命中任意组合。例如：

- 用户拥有但未 Star 的个人项目：只属于“我的项目”；
- 用户 Star 了自己的项目：同时属于“全部仓库”和“我的项目”；
- 用户取消 Star：仍保留在“我的项目”；
- 组织 Private 项目加入知识库：同时属于“我的项目”和“知识库”，但 Private 数据仍服从本方案隐私门禁。

## 3. 产品范围

### 3.1 首版包含

- 星标 Sidebar 固定分类“我的项目”及真实计数。
- 个人项目、组织项目、Public / Private / Internal 范围。
- 复用现有 Repo 列表、选择、多选、搜索、排序、Tags、状态和知识库操作。
- 复用现有 Repo 详情、README、AI 摘要入口和仓库洞察。
- 项目专属筛选：全部、个人、组织、具体组织、可见性。
- 项目专属元数据：归属账号、可见性、当前权限、授权来源。
- 每次项目元数据成功同步后记录当天 Star 精确快照。
- GitHub App 安装、组织审批、部分仓库授权、撤销和失效状态。
- Private 项目不进入 Discovery、External Search、公开分享或默认云同步。

### 3.2 首版不包含

- 不把外部个人协作者仓库纳入“我的项目”；首版只接受 `owner` 和 `organization_member`。
- 不显示用户无权访问的组织仓库。
- 不复制 GitHub Insights 的完整菜单。
- 不展示 Traffic / Views / Clones / Referrers。
- 不在列表阶段逐仓请求 Commit、Issue、PR、Contributor 或 Security API。
- 不为“我的项目”新增独立详情页或第三种 Repo DTO。
- 不新增 Starcat 后端，不把 GitHub App private key 放入客户端。
- 不使用 Classic PAT 作为普通用户的主产品流程；PAT 仅保留现有高级用户入口。
- 不把 Private 仓库身份发送给 `starcat-discovery-api`。
- 不承诺补全 Private 项目在接入 Starcat 以前的完整 Star 历史。

### 3.3 延后项

- 外部个人协作者仓库。
- 多组织聚合洞察。
- 项目 Star 增长榜、跨仓库对比和导出。
- GitHub App 的 Starring write 权限。
- Private 仓库 Issues / Pull Requests / Security Advisories 的额外授权。
- Private RepoContext 自动进入 AI；首版只允许用户主动触发并遵守既有 Provider 提示。

## 5. 授权架构

### 5.1 双凭据职责

```text
Existing GitHub OAuth Token
├─ 登录身份
├─ Public Stars 同步
├─ Public Star / Unstar
└─ Public 项目 fallback

Optional GitHub App User Access Token
├─ 用户明确安装的个人仓库
├─ 用户明确安装或获批的组织仓库
├─ Private / Internal metadata
└─ Private README / Contents（只读）
```

禁止把两个 token 混为“谁最新就覆盖谁”。调用方必须按 purpose 选择凭据：

```swift
enum GitHubCredentialPurpose {
    case publicStars
    case publicRepository
    case projectMetadata
    case privateContents
}
```

### 5.2 GitHub App 最小权限

首版申请：

| 权限 | 级别 | 用途 |
|---|---|---|
| Repository metadata | Read | 列表、名称、可见性、Stars、Forks、权限等基础元数据 |
| Repository contents | Read | Private README、默认分支和用户主动打开的源码上下文 |

首版不申请：

- Contents write；
- Administration；
- Issues write；
- Pull requests write；
- Repository hooks；
- Starring write；
- Organization administration。

如果后续希望 Private 项目完整显示 PR / Issue / Security 区块，应按 endpoint 单独审计并新增只读权限，不允许一次性扩大权限。

### 5.3 安装与授权流程

```text
用户点击“连接私人项目”
  → 打开 GitHub App 安装页
  → 选择个人账号或组织
  → 选择 All repositories 或 Only select repositories
  → 组织场景可能进入等待审批
  → Starcat 发起 GitHub App Device Flow
  → token 写入独立 Keychain namespace
  → 拉取授权范围并执行首轮项目同步
```

GitHub App 的授权状态不能复用 `AuthSession.state.isAuthenticated`：

- 用户可以已登录 Starcat，但尚未连接私人项目；
- 某个组织可以已授权，另一个组织仍待审批；
- GitHub App token 失效不应把现有 Public Stars 登录态清空。

建议新增独立 `ProjectAccessSession`：

```swift
enum ProjectAccessState {
    case disconnected
    case connecting
    case connected(ProjectAccessSummary)
    case partiallyAuthorized(ProjectAccessSummary)
    case awaitingApproval([String])
    case expired
    case failed(ProjectAccessError)
}
```

### 5.4 Token 存储

- GitHub App token 与现有 OAuth token 使用不同 Keychain service/account。
- 如启用 expiring user access token，同时保存 refresh token 和过期时间。
- 切换 Starcat GitHub 用户时，必须按 GitHub user ID 选择对应项目凭据，禁止跨账号复用。
- Reset / Sign out 需分别说明删除现有登录凭据和项目访问凭据的影响。
- 日志禁止输出 token、refresh token、安装 URL 参数或 Private repo full name。

## 6. GitHub API 契约

### 6.1 项目列表

使用：

```http
GET /user/repos
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2026-03-10
```

为准确区分归属，执行两条独立分页链：

```http
GET /user/repos?visibility=all&affiliation=owner&sort=pushed&direction=desc&per_page=100&page=N
GET /user/repos?visibility=all&affiliation=organization_member&sort=pushed&direction=desc&per_page=100&page=N
```

当前 OAuth fallback 固定 `visibility=public`。GitHub App token 使用 `visibility=all`，结果仍受用户权限、App 安装账号、App permission 和 selected repositories 的共同限制。

不把 `collaborator` 加入首版，避免把“别人邀请我协作的仓库”混入“我的项目”。

### 6.2 DTO

扩展 `GitHubRepoDTO` 或增加紧邻 API 的项目包装 DTO，但共享 Repo 字段仍只保留一份：

```swift
struct GitHubProjectDTO {
    let repo: GitHubRepoDTO
    let affiliation: ProjectAffiliation
    let accountLogin: String
    let visibility: ProjectVisibility
    let permission: ProjectPermission
}
```

`GitHubRepoDTO` 需确认并映射：

- `visibility`
- `private`
- `owner.type`
- `permissions.pull`
- `permissions.triage`
- `permissions.push`
- `permissions.maintain`
- `permissions.admin`

权限取最高有效等级，不依赖字段顺序。

### 6.3 分页、ETag 与 Rate Limit

- `per_page=100`。
- 遵循 Link Header，不用“返回 100 条”推断存在下一页。
- 每条 affiliation 链独立保存 ETag / last success。
- 304 只能复用该 affiliation 的完整成功快照。
- 任意一页失败，本轮不得清理旧关系。
- 统一复用现有 GitHub RateLimitInfo 和 401 / 403 / 404 诊断。
- 首次连接允许立即同步；后续后台同步建议 6 小时一次，手动刷新可强制执行。
- 同一账号的 Stars 全量同步与 Projects 全量同步串行或共享有界调度，避免同时打满 GitHub 配额。

## 7. 数据库设计

### 7.1 迁移

追加：

```text
v17-my-projects
```

禁止：

- 修改 `v1-initial`；
- 修改 `v16-repository-insights`；
- 要求用户删库；
- 用启动期 `ensure*` 永久旁路迁移。

### 7.2 `user_projects`

```sql
CREATE TABLE user_projects (
    user_id            INTEGER NOT NULL,
    repo_id            INTEGER NOT NULL,
    affiliation        TEXT NOT NULL,
    account_login      TEXT NOT NULL,
    visibility         TEXT NOT NULL,
    permission         TEXT NOT NULL,
    credential_source  TEXT NOT NULL,
    sync_generation    TEXT NOT NULL,
    last_seen_at       TEXT NOT NULL,
    synced_at          TEXT NOT NULL,
    PRIMARY KEY (user_id, repo_id),
    FOREIGN KEY (repo_id) REFERENCES repos(id) ON DELETE CASCADE
);

CREATE INDEX idx_user_projects_user_affiliation
ON user_projects(user_id, affiliation);

CREATE INDEX idx_user_projects_user_account
ON user_projects(user_id, account_login);

CREATE INDEX idx_user_projects_user_visibility
ON user_projects(user_id, visibility);
```

字段约束：

- `affiliation`: `owner | organization_member`
- `visibility`: `public | private | internal`
- `permission`: `read | triage | write | maintain | admin`
- `credential_source`: `oauth_public | github_app`

`credential_source` 只表示本次成功观察该关系使用的能力来源，不存 token 或 installation ID。

### 7.3 `project_sync_state`

```sql
CREATE TABLE project_sync_state (
    user_id                 INTEGER PRIMARY KEY,
    last_full_sync_at       TEXT,
    last_success_generation TEXT,
    repo_count              INTEGER NOT NULL DEFAULT 0,
    status                  TEXT NOT NULL,
    last_error_code         TEXT
);
```

只保存稳定、非敏感的诊断状态。详细错误文本进入内存 UI state 和受控日志，不长期落库 Private repo name。

### 7.4 Repo Upsert 约束

新增项目专用 Repository 方法，不能直接复用会强制写 `is_starred = false` 的路径：

```swift
func upsertProjects(
    _ projects: [GitHubProjectDTO],
    userID: Int64,
    generation: String,
    syncedAt: Date
) async throws
```

同一事务必须：

1. upsert Repo metadata；
2. 保留数据库已有 `is_starred`；
3. 保留 Tags、Notes、LibraryState、Pin；
4. upsert `user_projects`；
5. 写入当天 `local_snapshot` Star 历史点；
6. 更新数据库 revision。

### 7.5 全量对账

```text
开始同步 → 生成 generation UUID
  → owner 全部分页成功
  → organization_member 全部分页成功
  → 单事务 upsert 新 generation
  → 删除该用户旧 generation 的 user_projects 关系
  → 更新 project_sync_state
```

任意分页、解码或写库失败：

- 保留上一轮全部关系；
- 不更新 last success generation；
- UI 显示 stale；
- 不把 repo 标记为 unstarred；
- 不删除用户笔记、标签或知识库状态。

## 8. 查询与状态层

### 8.1 RepoListScope

```swift
enum RepoListScope {
    case allStars
    case myProjects
    case library
    // 其余现有 scope 保持
```

项目 scope SQL：

```sql
JOIN user_projects up_scope
  ON up_scope.repo_id = r.id
 AND up_scope.user_id = ?
```

### 8.2 项目筛选

建议在 `RepoListFilters` 增加：

```swift
struct RepoProjectFilters: Equatable, Sendable {
    var affiliation: ProjectAffiliationFilter
    var accountLogin: String?
    var visibility: ProjectVisibilityFilter
    var minimumPermission: ProjectPermission?

```

只有 scope 为 `.myProjects` 时应用；离开该 scope 时保留用户会话偏好，但不能影响全部 Stars、知识库或 Smart Collections。

- `myProjectsCount`
- `projectAccounts`
- `projectFilter`
- `projectSyncPresentation`

`refreshSidebar()` 从本地关系表读取计数和组织列表，不触发网络。

- 数据库分页；
- 搜索；
- 排序；
- selection generation；
- 多选；

### 8.4 搜索

Manage 快速搜索在 `.myProjects` scope 内只搜索项目关系命中的 Repo。全局 Search Center 维持现有范围，首版不新增“My Projects”顶级 Search scope。

## 9. Star History 与更多数据

### 9.1 Star History

直接复用 v16：

| 项目类型 | 历史来源 |
|---|---|
| 当前用户拥有或协作的项目 | 使用关系表记录的 OAuth / GitHub App 凭据直连 GitHub Stargazers，按 `starred_at` 重建当前 Stargazers 曲线，并叠加本机 snapshot |
| 普通 Public 仓库 | GH Archive 估算（若生产已 GO）+ Discovery snapshot + 本机 snapshot |
| 无有效项目凭据的 Private / Internal | 仅本机 snapshot |

GitHub Stargazers 只返回当前仍在 Star 的用户及其 Star 时间，不能还原已经 Unstar 用户造成的历史峰值，因此 UI 必须标注为“当前 Stargazers 重建”，不得表述为完整事件历史。客户端只在内存中读取 `starred_at` 并聚合为按日数量，禁止保存 Stargazer 用户身份。

GitHub 已将 Stargazers 列表限制为仓库管理员和协作者读取。没有 `.githubStargazers` 来源时，Star History 在图表或空态下方显示问题式短链接，并跳转到 [GitHub 官方访问限制公告](https://github.blog/changelog/2026-06-30-upcoming-access-restrictions-to-public-api-endpoints-and-ui-views/)；完整说明只放在 help 和 VoiceOver hint，且必须说明普通仓库仍可能使用 Discovery / GH Archive 估算，只有远端历史不可用时才退回本机 snapshot。

Star History footer 不显示动态读数，图表选中日期只更新图内浮层，避免 footer 高度变化造成窗口上下抖动。图例与“日期范围 · 更新时间”固定同排：图例靠左，元数据靠右；单一精度隐藏图例，两种以上精度才展示图例。限制短链接按需占用第二行，完整说明继续保留在 help 和 VoiceOver hint。

Private / Internal 必须在构造 Discovery 请求前拦截，但可使用用户已授权的 GitHub App 凭据直连 GitHub；组织审批、项目同步或详情加载都不能把仓库信息发送到 Starcat 公共服务。

本机 snapshot 从“项目首次成功同步”开始积累。两个快照之间只连接观察点，不声称掌握每次 Star / Unstar 的准确时间。

### 9.2 列表可展示数据

首版只使用一次项目列表响应和本地缓存：

- Stars / Forks / Watchers；
- Open Issues；
- 最近 Push；
- 创建时间；
- 默认分支；
- 归档 / Fork；
- 可见性；
- 当前权限；
- 本地 30 天 Star 增长。

### 9.3 详情可展示数据

现有仓库洞察按能力加载：

- Star 增长和增速；
- Commit activity；
- PR / Issue 活动；
- Contributor 分布；
- Release 节奏；
- Community Profile；
- Security Advisory；
- Health / OpenSSF。

首版 GitHub App 只申请 Metadata + Contents read，因此需要额外权限的区块必须显示 unavailable。不要为了“详情完整”提前扩大授权。

## 10. Private 数据边界

### 10.1 默认禁止出站

Private / Internal 项目的以下信息不得发送给 Starcat 公共服务：

- owner / repo name；
- repo ID；
- README；
- Commit、Issue、PR、Contributor；
- Star History；
- Tags、Notes、LibraryState；
- 用户访问顺序。

明确禁止的服务：

- `starcat-discovery-api`
- `starcat-sharing-api`
- AnySearch / External Search
- 公开 Wiki provider
- 公共推荐、Trending、Weekly ingest

### 10.2 本地存储

- Repo metadata、README cache、洞察缓存和 Star snapshot 保存在当前用户数据库或现有本机缓存目录。
- `user_projects` 和项目同步状态是可重建远端投影，不进入 CloudKit。
- JSON 导出默认不包含 `user_projects`、GitHub App token 或 Private 仓库远端缓存。
- 用户创建的 Tags、Notes、LibraryState 继续遵守现有用户数据保护策略。

### 10.3 AI 与 RAG

- Private 项目不会因为出现在“我的项目”就自动加入知识库。
- 用户主动加入知识库后，索引仍在本机。
- 发送给 BYOK Chat Provider 前必须明确提示将使用 Private 项目内容，并遵循用户选择的 Provider。
- Private 项目永远不进入 External Search query。
- 批量 AI 自动整理首版跳过 Private 项目，后续单独设计授权。

### 10.4 撤销访问

当 GitHub App 不再返回某个 Private 项目：

1. 从 `user_projects` 移除关系；
2. 不再显示在“我的项目”；
3. Repo `access_state` 标记 unavailable；
4. 停止远端刷新；
5. 保留用户创建的标签、笔记和知识库归属；
6. Private README / source cache 的清理策略在实施前单独确认，首版至少提供“清除已失效私人项目缓存”操作。

## 11. 同步与刷新

### 11.1 触发时机

| 触发 | 行为 |
|---|---|
| 首次连接 GitHub App | 全量 Projects sync |
| App 启动 | 读取本地；距上次成功超过 6 小时才后台同步 |
| 点击“我的项目” | 只读本地，不阻塞首屏 |
| 手动刷新当前列表 | 执行 Projects sync，再重载当前分页 |
| GitHub App 授权返回 | 强制同步 |
| Stars 全量同步 | 不自动触发 Projects 全量同步 |

### 11.2 刷新入口

使用现有 `SyncIconButton` 和全局刷新命令路由，不新增第二个图标体系。

刷新中：

- 保留旧列表；
- 按钮旋转和 Accent 状态；
- 成功后原位刷新；
- 失败显示非阻塞 stale / error；
- 不清空 selection。

### 11.3 并发

- 同一用户只允许一个 Projects full sync。
- Stars sync 与 Projects sync 共享 GitHub 请求预算。
- Repo metadata upsert 分批写入，但旧关系清理只能在全量成功后执行。
- 快速切换 Sidebar 不取消已经安全进入后台的 full sync；只取消当前列表加载任务。

| 场景 | 预期 |
|---|---|
| 仅现有 OAuth | 展示可见 Public 个人和组织项目，不声称包含 Private |

## 16. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| OAuth `repo` 权限过重 | 用户信任和隐私风险 | 使用独立 GitHub App 细粒度只读权限 |
| 组织安装需审批 | 数据不完整 | 显示组织级授权状态，不把未授权误报为空组织 |
| 双 token 路由错误 | Private 泄露或登录被误清空 | purpose-based credential router + 独立 session / Keychain |
| Project upsert 覆盖 Star | 用户列表错误 | 专用 upsert，数据库回归覆盖交叉关系 |
| 分页中途失败误删 | 大量项目瞬间消失 | generation 全量成功后才对账清理 |
| 列表逐仓补洞察 | Rate Limit 和滚动卡顿 | 列表只用批量响应与本地聚合 |
| Private 内容进入公共服务 | 严重隐私问题 | 请求构造前拦截 + 服务路由测试 + 日志脱敏 |
| 权限撤销后缓存残留 | 本机隐私风险 | access unavailable + 停止刷新 + 缓存清理入口 |
| 组织很多 | Sidebar 膨胀 | 单一 Sidebar 入口，组织放 Toolbar 筛选 |
| Star History 被误解为完整历史 | 产品误导 | 来源、精度、覆盖起点固定展示 |

## 17. 完成定义

必须同时满足：

1. “我的项目”是独立 Repo scope，不依赖 Star 状态。
2. 个人 Public / Private 和已获授权组织项目均可展示。
3. 未安装或未获批的仓库不会被伪装成已同步的空结果。
4. 同 Repo 在 Star / Project / Library 间关系正确。
5. 列表、搜索、分页、排序、筛选、多选和详情复用现有 Manage 体系。
6. Public / Private Star History 来源和精度明确。
7. Private / Internal 项目不访问 Starcat 公共服务。
8. 失败、断网、撤销和 token 过期保留明确且安全的降级。
9. v17 迁移不修改任何已发布 migration，不要求删库。
10. 自动化与人工验收矩阵完成。

以下不算完成：

- 只加 Sidebar 入口；
- 只展示当前 OAuth 能看到的 Public 项目；
- 用 `repos.owner == currentLogin` 推断全部项目；
- 把组织仓库或 Private 仓库当成普通 Star Repo；
- 直接给现有 OAuth 增加 `repo` scope；
- Private 项目打开详情时仍把 owner/name 发给 Discovery；
- 未获 dong4j 确认就改写 `docs/功能实现总览.md`。

## 18. 已采用决策

1. “我的项目”放在星标模块下，属于固定一等分类。
2. 首版范围是个人拥有仓库 + 组织成员仓库，不含外部个人协作者仓库。
3. 复用现有 Repo、RepoList、RepoDetailScaffold、ManageDetailContent、Insights 和 Star History。
4. 新增 `user_projects` 关系表，不新增 `repos.is_owned`。
5. 追加 `v17-my-projects`，不修改已发布 migration。
6. 现有 OAuth 保持原职责；Private / Internal 使用可选 GitHub App。
7. GitHub App 首版只申请 Metadata read + Contents read。
8. 组织不展开到 Sidebar，使用中栏 Toolbar 筛选。
9. 列表不发逐仓洞察请求，30 天 Star 增长只读本地历史。
10. 项目使用授权凭据直连 GitHub 重建当前 Stargazers 历史；Private 无有效凭据时只使用本机 snapshot，且始终不访问 Discovery。
11. `user_projects`、同步状态和 Private 缓存不进入 CloudKit / 默认 JSON 导出。
12. 专项代码、自动化测试、原五轮审查和七轮补充复审均已完成；真实 GitHub App 与 macOS 实机矩阵保留为发布前外部 Gate。
