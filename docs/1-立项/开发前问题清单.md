### 1.2 数据库循环外键依赖

**问题**：`repos.id → starred_repos.repo_id` 形成循环外键，SQLite 无法创建。

**解决方案**：移除 `repos.id → starred_repos.repo_id` 这个不合理的外键。

```sql
-- repos 表：移除循环外键
CREATE TABLE repos (
    id TEXT PRIMARY KEY,                    -- GitHub repo ID (唯一标识)
    ...
    cached_at TEXT                          -- 移除：FOREIGN KEY (id) REFERENCES starred_repos
);

-- starred_repos 表保持
CREATE TABLE starred_repos (
    repo_id TEXT PRIMARY KEY,             -- 关联 repos.id
    ...
    FOREIGN KEY (repo_id) REFERENCES repos(id) ON DELETE CASCADE
);
```

**已更新**：`01-数据库设计.md`

### 1.3 OAuth 权限范围与功能矛盾

**问题**：`public_repo` scope 是否支持删除 Star 操作？

**解决方案**：经查证 GitHub 文档，`public_repo` scope **已包含**对公开仓库的 star/unstar 操作权限。

```swift
// GitHub OAuth Scope
let scopes = ["read:user", "public_repo"]
```

> **说明**：GitHub 官方文档明确指出 `public_repo` scope "Also required for starring public repositories"，即已包含 star/unstar 权限。

### 2.2 语义搜索架构

**问题**：SQLite 原生不提供项目可直接依赖的向量相似度能力，同时 Starcat 已明确采用本地优先、BYOK、不自建 AI 代理的产品路线。

**最终方案（2026-06-13 按当前实现修订）**：embedding 由用户配置的 OpenAI-compatible Provider 生成，repo 向量缓存在本地 SQLite；搜索时只生成 query vector，并在 Swift 内存中计算 cosine similarity 和 Top-K。第一阶段不引入 pgvector、sqlite-vss 或 Starcat 自建语义搜索服务。

```
┌─────────────────────────────────────────────────────────────┐
│                    语义搜索架构                             │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Starcat 本地：                                             │
│  ├── 存 repo 向量与 IndexedSnapshot（SQLite）               │
│  ├── 生成 query vector 后在 Swift 内存计算 cosine            │
│  └── 排序并展示 Top-K                                       │
│                                                              │
│  用户选择的 Embedding Provider：                            │
│  └── 仅负责生成 repo / query embedding                      │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**已更新**：相关文档保持一致

### 2.4 增量同步没有真实方案

**问题**：GitHub Stars API 不支持增量查询，文档中的"增量同步"实际是全量拉取。

**解决方案**：定期全量对比 + **手动刷新**功能。

```
┌─────────────────────────────────────────────────────────────┐
│                    同步策略                                 │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  首次同步：全量拉取，存 last_sync_at                    │
│                                                              │
│  增量同步：                                                │
│  ├── 按 starred_at DESC 排序，只拉前 N 条（N = 你 star 数）│
│  ├── 对比本地数据，更新新增的                           │
│  └── 检测删除（本地有 remote 没有）→ 软删除           │
│                                                              │
│  手动刷新：                                                │
│  └── 用户主动触发完整同步                              │
│                                                              │
│  定期全量同步（如每周一次）：                             │
│  └── 凌晨低峰期做，检测"取消 star 但本地还显示"        │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 三、🟠 关键设计缺失（已补充）

### 3.1 Release 订阅通知

**问题**：功能清单中 Release 订阅追踪是 P2，但用户要求必须做。

**解决方案**：Release 订阅移到 **P1**，使用轮询方案监测。

```swift
/// Release 发布通知监测管理器
/// 使用 NSBackgroundActivityScheduler 在 macOS 后台定期执行（建议每 4-6 小时一次）
@MainActor
@Observable
class ReleaseMonitor {
    var newReleases: [ReleaseNotification] = []

    /// 检测所有订阅的仓库是否有新 Release
    func checkForNewReleases() async -> [ReleaseNotification] {
        let subscriptions = database.getActiveSubscriptions()
        var notifications: [ReleaseNotification] = []

        for subscription in subscriptions {
            if let notification = await checkRepo(subscription) {
                notifications.append(notification)
            }
        }

        return notifications
    }
}
```

### 4.4 双分发渠道

**决定（2026-06-27）**：Starcat 支持 App Store 与 Direct 两种分发渠道，但支付 / 授权机制分离。

| 渠道 | 分发 | 支付 / 授权 | 约束 |
|------|------|-------------|------|
| App Store | Mac App Store | StoreKit 2 / Apple IAP | App Store build 不展示 Lemon Squeezy、授权码或外部购买入口 |
| Direct | 官网 DMG | Lemon Squeezy / License Key | Direct build 单独展示授权码激活与官网订阅管理入口 |

**实现原则**：双渠道、单权益。业务层继续只依赖 `EntitlementGate` / `isPro`，购买与授权 Provider 按构建渠道分叉。

## 五、🟢 启动期决议（已确认）

以下问题在 MVP 启动会议（2026-05-30）确认，写入此处作为基线，开发过程中如需调整需要更新本节。

### 5.1 测试策略

| 项 | 决议 |
|---|---|
| 测试框架 | **Swift Testing**（`import Testing` / `@Test` / `#expect`） |
| MVP 覆盖率目标 | 不强制百分比，但 Core 层（Database/Network/Sync/Keychain）必须有单测 |
| 数据库集成测试 | 用内存数据库（`DatabaseQueue(path: ":memory:")`），跑 Migration + CRUD + FTS5 |
| UI 测试 | MVP 阶段不写 |

### 5.2 数据 Migration 方案

| 项 | 决议 |
|---|---|
| 版本号策略 | GRDB `DatabaseMigrator`，使用语义化字符串标识（`"v1-initial"`, `"v2-undo-star"`, ...） |
| 降级支持 | **不支持降级**，新版本只允许向上迁移 |
| 失败提示 | 迁移失败时弹窗提示用户，提供"导出当前数据库 + 联系支持"选项；不允许静默重置 |
| **正式版后（2026-07-12 起）** | **禁止直接改 `v1-initial` 建表 SQL**；加字段 / 建表一律追加 `registerVN`（`ALTER TABLE` / `CREATE`），保护已发布用户本地数据 |
| MVP v1 范围 | repos / starred_repos / tags / repo_tags / repo_notes / readmes / saved_searches / sync_state / tag_stats_cache + repos_fts |
| 后续版本 | 以 `DatabaseMigrations.registerAll` 中已注册的 v2+ 为准；详见 `docs/3-设计/详细设计/01-数据库设计.md` §1.3 |

### 5.3 依赖注入架构

| 项 | 决议 |
|---|---|
| DI 方案 | **SwiftUI Environment + Protocol**，不引第三方 DI 库 |
| 实现模式 | 每个 Service 定义 `protocol`（如 `GitHubAPIServiceProtocol`），通过 `EnvironmentKey` 注入；Mock 实现用于单测和预览 |
| 单例 | 仅 `DatabaseManager` / `KeychainManager` / `Logger` 这类无状态基础设施允许单例 |

### 5.4 CloudKit 开发环境

| 项 | 决议 |
|---|---|
| MVP 阶段 | **不接入 CloudKit**，所有数据本地 SQLite |
| 数据层抽象 | UserData repository protocol（`TagRepository` / `NoteRepository` 等），CloudKit 实现在 v1.1+ 落地 |
| 同步开关 | 设置页"iCloud 同步"开关默认关闭，未实现前显示"即将上线" |

### 5.5 AI 成本设计（P1 才生效）

| 项 | 决议 |
|---|---|
| 缓存过期 | AI 摘要默认 **30 天不过期**，用户可手动重新生成 |
| 配额显示 | 设置页显示本月 AI 调用次数 + 剩余配额（自建服务模式），BYOK 模式不显示 |
| 批量预估 | 批量操作前预估"将调用 X 次 AI"，用户确认后才执行 |

### 5.6 导入导出兼容性

| 项 | 决议 |
|---|---|
| MVP 导出格式 | Starcat 自有 JSON（含 repo metadata + tags + notes + status）|
| 第三方导入 | MVP 仅支持 Starcat JSON 导入；OhMyStar/Astral 兼容延后到 v1.1 |
| 冲突策略 | 导入时检测重复 repo_id，按"保留本地 / 用导入文件覆盖 / 合并字段"三选项让用户决定 |

### 5.7 国际化策略

| 项 | 决议 |
|---|---|
| UI 语言 | 跟随系统语言；MVP 首发支持**简体中文 + 英文** |
| 字符串管理 | 使用 String Catalog (`.xcstrings`)，Xcode 15+ 原生支持 |
| AI 摘要语言 | 设置页提供"AI 输出语言"选项，默认跟随 UI 语言 |
| README 渲染 | 不翻译原文（除非用户启用 README 翻译功能，见功能清单 2.x） |

### 5.8 工程基础设施

| 项 | 决议 |
|---|---|
| 包管理 | Swift Package Manager（SPM） |
| 图片库 | **Kingfisher 7.0+**（纯 Swift、API 简、避免 OC 依赖） |
| Keychain 封装 | **KeychainAccess 4.2+**（避免裸写 Security framework） |
| 日志 | **OSLog 原生**，不引 swift-log；按 category 拆分（network/database/sync/auth/ai/ui） |
| Lint | **SwiftLint** 作为可选 Build Phase，违规不阻断编译，先用 warning |
| Git Hooks | 暂不强制 pre-commit hook |

### 5.9 品牌/标识

| 项 | 决议 | 备注 |
|---|---|---|
| 应用名 | Starcat | |
| Bundle ID | `com.starcat.app.store` | App Store target；Direct target 使用 `com.starcat.app.direct` |
| URL Scheme | `starcat://callback` | OAuth 回调 |
| OSLog subsystem | `com.starcat.app` | |
