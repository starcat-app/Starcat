# 洞察中心性能优化审查报告 03：切库并发窗口复核

> 审查日期：2026-07-29
>
> 审查范围：`1cb05e7b..47093522`
>
> 结论：发现 1 个 P1；先记录，再修复。

## 1. 已确认

- 旧账号已经存在于 Metrics in-flight tracker 的普通请求会被取消并等待到终态。
- 网络 await 后的取消检查能阻止已取消响应继续解码。
- 热点、Rate Limit、endpoint failure 和页面冷却均会在切库时清理。
- 完整冷加载请求预算测试已补齐：正常路径 5 次请求，六类缓存全部写入。
- Checklist 已按自动化证据回填，未执行的 test host 和人工验收没有伪造完成。

## 2. P1：清理结束到 reopen 完成之间仍可插入新请求

当前顺序是：

1. `repositoryMetricsClient.clearTransientState()`；
2. `database.reopen(userId:)`；
3. 推进 `databaseScopeRevision`。

第 1 步会取消当时已经登记的普通请求，但方法返回后到第 2 步完成前，Metrics Client 没有保持“切库中”状态。若 SwiftUI / RAG 在这个窗口发起新请求，它可能使用旧数据库或旧/新 Token 的不一致组合，并在 reopen 后返回。

## 3. 修复要求

1. Metrics Client 增加切库 begin / end 屏障。
2. begin 先阻止新请求进入 in-flight，再取消并等待已有普通请求。
3. `AppDependencies` 在 reopen 成功或失败后都必须 end，避免永久挂起。
4. 普通洞察和新发起的 observer 请求在屏障期间等待，reopen 完成后重新读取当前 Token。
5. 增加自动化测试：切库屏障期间请求不出站，end 后才读取新 Token 并继续。
