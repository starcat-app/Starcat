>
> 审查范围：`310b2f76..ca454f6d`

> 结论：发现 1 个 P1、2 个 P2；先记录，再修复。

## 1. 已确认

- 普通 Metrics GET 以 URL、ETag、认证身份和请求类型合并 in-flight；RAG observer 请求保持独立审计。
- Activity 与 Recent Activity 在完整冷加载中复用同一个 GraphQL Bundle，正常路径最多 1 次请求，失败时回退原 REST 查询。
- Commit、Contributors、Community、Security 已贯通 ETag、`If-None-Match`、304 touch 和 payload 丢失后的无条件重拉。
- SQLite 解码热点缓存容量固定为 48 条，Key 包含 writer 身份、用户、仓库、数据集、范围和解码类型。
- 手动刷新保留可见内容，并按入口执行 10 秒冷却；没有新增中央加载环或新动画。
- Activity / Recent、Commit / Contributors、Community、Security 的 TTL 已按 15 分钟、24 小时、3 天、6 小时分层。
- Star History 未被本轮通用缓存改造侵入，仍沿用既有覆盖判断、远端缓存和 202 轮询策略。

## 2. 发现的问题

### P1：切换用户数据库时只隔离、未主动清理瞬时状态

当前热点 Key 和失败 Key 能阻止跨账号命中，但 `AppDependencies.switchUserDatabase(to:)` 没有主动：

- 清空已解码热点值；
- 清空 Rate Limit / endpoint failure 状态；
- 取消并等待旧账号普通洞察 in-flight；
- 清空页面 ViewModel 的手动刷新冷却。

旧请求若在 `database.reopen` 之后才完成，存在把旧账号响应写入新数据库作用域的理论窗口。必须在切库前取消并等待普通洞察任务终止，再清热点与退避状态。

### P2：缺少切库清理的自动化证据

现有测试覆盖了热点 Key 隔离和 Token 切换不继承限流，但没有直接验证：

- 主动清空热点后下一次读取重新访问 SQLite；
- 主动重置 Metrics 瞬时状态后同一认证可以重新出站；
- 页面切库后手动刷新冷却被清空。

### P2：Checklist 尚未回填真实状态

功能与测试提交已形成，但 Checklist 仍显示 `0 / 63`。应在修复完成、验证证据稳定后逐项回填；人工体感、真实 GitHub 配额和 Instruments 项继续保持未勾选。

## 3. 修复要求

1. 为洞察缓存和 Metrics Client 增加显式瞬时状态清理契约。
2. `switchUserDatabase(to:)` 在 `database.reopen` 前取消并等待旧普通洞察任务，清空热点与退避状态。
3. 页面以 `databaseScopeRevision` 作为加载身份的一部分，并清空 ViewModel 冷却。
4. 分别补缓存、Metrics Client、ViewModel 的账号切换测试。
5. 修复完成后进行第二轮代码、测试、文档、Checklist 与提交一致性审查。
