# 支付对接专项审查报告 01

> 审查时间：2026-07-04
> 审查范围：支付抽象、Direct License API、Creem 首期适配、支付专项文档与 checklist
> 结论：发现 2 个一致性问题，需先修复再进入下一轮审查。

## 1. 发现问题

### P1：支付 provider 抽象在文档和 checklist 中已声明，但后端代码仍直接由 handler 读取 URL

- 现象：`docs/4-工程进度/支付对接专项/checklist.md` 写明 `DirectPaymentProvider` 已落地，但 `supports/starcat-license-api/internal/handler/payment.go` 仍直接持有 `checkoutURL` / `customerPortalURL`。
- 风险：后续接 Creem 以外 provider 时会把 provider 选择逻辑压到 HTTP handler，和“handler 只做协议边界，provider 负责供应商差异”的设计不一致。
- 修复方向：新增 `PaymentProvider` 接口和首期静态 URL provider，handler 只依赖接口。

### P1：支付正式方案和详细设计仍包含计划态表述，与首期实现不一致

- 现象：正式方案仍使用 `StoreKitEntitlementProvider`、`DirectPaymentProvider / DirectLicenseProvider` 等计划名，且 Phase / 验收标准仍是未勾选状态；部分需求讨论仍写 Creem “待实现”和 7 天离线宽限。
- 风险：后续协作会误判当前状态，以为支付抽象、License API、Direct 设置入口仍未实现。
- 修复方向：同步为实际实现名与首期约束：`SubscriptionManager` 作为 StoreKit provider、`CompositeProEntitlementProvider` 聚合、`DirectLicenseManager` 负责 Direct 权益，首期不启用离线宽限放行。
