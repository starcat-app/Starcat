# 探索发现与榜单设计实现一致性审计

> 日期: 2026-06-30
> 范围: `starcat-discovery-api`、Starcat Explore、三份产品/设计文档

## 本次已修正

- 热门 / 新发布不再复用同一批 385 个 catalog 数据。后端 ranking 生成时先执行分类资格过滤,再写 `category_rankings`。
- `bulk` 增加 `categories` 与 `category_ranks`,Starcat 本地缓存新增 `discovery_bulk_category_memberships`,客户端按归属过滤热门 / 新发布。
- 新发布资格补齐稳定 release、180 天窗口、真实 release asset、非 archived、非 fork 条件;默认排序改为 `latest_release_at DESC, release_score DESC`。
- 热门资格补齐非 archived、非 fork、高 star 或高 popularity score 条件。
- 分类接口显式排序时仍限定在该分类候选集内,例如 `/most-popular?sort=stars` 不会回到全量 catalog。
- `summary` 的热门 / 新发布计数不再在 ranking 缺失时回退全量 `repos`,避免把数据管道异常伪装为有效分类数据。
- `starcat-discovery-api` 的 full sync 已从普通 upsert 升级为候选集清理:轻同步保留旧 catalog,全量同步在本轮 GitHub 候选非空后删除不再命中的公开仓库缓存。
- `bulk` 进程内缓存已按 `CACHE_TTL_SECONDS` 生效；2026-06-30 审计时默认 900 秒，2026-07-18 已调整为 10800 秒（3 小时），与默认轻量同步及 Starcat 客户端 freshness 窗口一致。
- 趋势候选接口已从公开路由收敛到 Admin 鉴权的 `/internal/discovery/trending-candidates`,正式趋势仍只走 `starcat-trending-api`。
- SQLite 已补齐 `search_score/stars/updated/created/lower(full_name)` 等排序索引和 category bucket 辅助索引。

## 仍未完全匹配设计

- 发现 feed 的“曝光冷却 / 多样性 / 动态 momentum”只落了 `feed_exposure` 与快照表,当前排序仍主要依赖静态 score。后续需要把曝光次数、主题去重、增长快照纳入 feed 排序。
- `repo_daily_snapshots` 已采集,但 stars / forks / downloads 的增长率还没有进入 `trending_score` 或 `discovery_score`。
- 平台识别已基于 release asset / topic / language,但设计里的 asset quality 分没有独立建模,目前只通过 release score 和 downloads 间接影响。
- 静态 JSON snapshot / 离线兜底未实现。当前后端依赖 SQLite 数据和 Fly volume,没有导出可公开托管的只读 snapshot。
- Discovery 详情页已按后续产品决策改为 README 渲染,不再展示原设计中的推荐原因 / 判断信号 / 版本发布 / 关键指标详情块。若 README 方案确认长期保留,正式方案和详细设计需把详情页章节改成 README 为主、推荐信号仅保留为列表/排序解释。
- 文档中部分算法描述仍偏目标态,例如“多样性与冷却策略”已写入阶段目标但尚未完整落地;需要在下一轮算法调优中把目标态拆成可验证规则和测试。

## 后续建议

1. 先用本次部署后的线上数据观察热门 / 新发布数量和质量,确认分类边界是否过窄。
2. 再补 feed 的曝光冷却与主题多样性,避免一次性把排序算法复杂度拉满。
3. 如果 README 详情页方向稳定,同步重写详细设计 §7.5,删除已经不采用的 Discovery 自绘详情描述。
