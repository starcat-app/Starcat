# 探索发现与榜单总结报告

> 日期: 2026-06-30
> 范围: Starcat 探索入口、`starcat-discovery-api`、现有 `starcat-trending-api` 边界、客户端本地缓存与线上部署

## 1. 背景

本次需求起点是参考 `kurikomi-labs/komi-store` 的发现与榜单能力,把 Starcat 原有单一 Trending 入口升级为更完整的「探索」入口。目标不是简单复制一个榜单页面,而是让 Starcat 在不破坏现有 Trending 稳定性的前提下,具备发现新仓库、查看热门仓库、查看新发布仓库的能力。

最终信息架构确定为:

- 探索
- 发现
- 趋势
- 热门
- 新发布

其中「趋势」继续使用现有 `starcat-trending-api`,保持今日 / 本周 / 本月和语言筛选逻辑不变；「发现 / 热门 / 新发布」由新增的 `starcat-discovery-api` 提供数据,并由 Starcat 客户端落本地 SQLite 后完成筛选、排序和分页。

## 2. komi-store 调研结论

komi-store 的关键价值有两点:

1. 它把发现页和榜单页分开组织,发现页支持平台与分类筛选,榜单页支持趋势、新发布、热门等不同榜单语义。
2. 它的热门、新发布不是前端简单排序全量数据,而是后端先生成某个业务语义下的候选集,再给客户端消费。

调研后 Starcat 没有照搬 komi-store 的接口形态,而是保留了更适合本项目的本地优先策略:

- 后端负责采集 GitHub 公开数据、归类、生成 ranking。
- 客户端优先读取本地 SQLite 缓存。
- 远端主要提供全量公开 catalog 快照和 summary。
- 趋势先不迁移,避免把现有稳定链路和新服务质量绑在一起。

## 3. 方案演进

本次需求经历了几次重要修正。

第一版方案把现有 Trending 改为「探索」,并把发现 / 趋势 / 热门 / 新发布作为探索下的主模式。随后明确这 4 个模式应该出现在左侧导航,而不是中栏顶部 tab。中栏顶部只保留当前模式需要的筛选和排序。

第二次修正是汇总数量。探索左侧不仅要显示目录,还要像 Manage / Activity 一样显示每个模式和每个筛选项下的 repo 数量。因此新增了 summary 能力:

- 发现总量、主题计数、平台计数来自 discovery summary。
- 热门总量和语言计数来自 discovery summary。
- 新发布总量和语言计数来自 discovery summary。
- 趋势总量和语言计数继续来自现有 trending 本地缓存与 `starcat-trending-api`。

第三次修正是本地优先。发现 / 热门 / 新发布不能每次筛选都依赖后端分页接口,否则与 Starcat 一贯的本地优先承诺不一致。最终改为后端提供 `/api/v1/discovery/bulk`,客户端把公开 catalog、summary、分类归属落入本地 SQLite,再在本地完成筛选、排序、分页。

第四次修正是 discovery 与 trending 的边界。`starcat-discovery-api` 中可以保留内部趋势候选诊断能力,但 Starcat 正式「趋势」必须继续只走 `starcat-trending-api`。因此公开 discovery trending 路由被移除,只保留 Admin 鉴权的 `/internal/discovery/trending-candidates`。

第五次修正是热门 / 新发布的数据归属。曾经出现发现、热门、新发布数量都接近 385 的问题,本质是客户端按全量 catalog 或 score 推断分类。最终改为后端写入 `category_rankings`,bulk 返回 `categories` 和 `category_ranks`,客户端只按后端归属判断热门 / 新发布。

## 4. 最终实现概况

### 4.1 后端服务

新增独立后端 `starcat-discovery-api`,作为 discovery 相关能力的边界服务。它负责:

- 从 GitHub Search / Repository / Release API 采集公开仓库数据。
- 识别主题分类,包括人工智能、隐私、网络、媒体、社交、阅读、工具。
- 识别平台分类,包括 macOS、iOS、CLI、Web、Server、Android、Windows、Linux。
- 生成发现、热门、新发布所需的 score 与 ranking。
- 提供 summary、bulk、metadata、分页诊断接口。
- 提供 Admin 同步接口和内部趋势候选诊断接口。
- 使用 SQLite + Fly volume 持久化公开 catalog。

同步策略分为两类:

- 轻同步: 定时 upsert 本轮命中的仓库,刷新 ranking,不删除旧数据。
- 全量同步: 在本轮 GitHub 候选非空后,删除不再命中的公开 catalog 数据,再刷新 ranking。

GitHub token 使用多 token 池轮换。token 低于 `RATE_LIMIT_FLOOR` 时会临时禁用到 reset 时间；401 token 会标记为 dead；403 / 429 / 5xx 会切换 token 重试。

### 4.2 客户端接入

Starcat 客户端新增 Explore 能力:

- 原 Trending 一级入口升级为「探索」。
- 左侧主模式为发现 / 趋势 / 热门 / 新发布。
- 发现下支持主题分类和平台分类,并支持折叠。
- 热门 / 新发布下使用语言分类。
- 趋势下沿用现有语言分类和今日 / 本周 / 本月。
- 中栏顶部统一引入排序 / 筛选入口,趋势保留时间范围筛选。
- 发现 / 热门 / 新发布详情页改为 README 渲染,与 Starcat 其他 repo 详情体验统一。

客户端本地缓存包括:

- discovery bulk repo 快照。
- discovery summary。
- discovery category membership。
- discovery list page 降级缓存。

这样做的结果是:网络可用时后台刷新远端,网络不可用时仍可展示本地旧数据；筛选和排序不会因为后端接口延迟影响交互。

### 4.3 运维与部署

`starcat-discovery-api` 已纳入 supports 目录规范:

- 补齐 `.env.example`、Fly 配置、README、部署文档、开源说明。
- 接入 `supports/start-all.sh`。
- 接入 `supports/Makefile`。
- 接入 secrets 同步、备份、恢复、清理等脚本。
- 使用 Fly.io 部署,生产 SQLite 路径为 `/data/discovery.db`,本地默认路径为 `./discovery.db`。

线上已部署并验证:

- app: `starcat-discovery-api`
- 地址: `https://starcat-discovery-api.fly.dev`
- 当前 summary: `discover=385`、`popular=351`、`new_releases=104`
- 旧公开 trending 路由返回 404
- internal trending candidates 需要 Admin 鉴权
- `manual-full` 同步成功,本轮 `repos_pruned=0`

## 5. 关键决策

### 5.1 新建 discovery-api,不改 trending-api

现有 Trending 是已经可用的稳定链路。新需求涉及 GitHub 搜索、release、平台识别、榜单 ranking、bulk、本地缓存、summary 等多项新增能力。如果直接扩展 `starcat-trending-api`,风险会集中到现有趋势功能上。

因此最终选择新增 `starcat-discovery-api`,让新能力独立演进。趋势仍保留原服务,只有内部候选诊断可以在 discovery-api 中做质量对比。

### 5.2 客户端本地优先

Starcat 的核心承诺是本地优先。发现 / 热门 / 新发布如果完全依赖远端分页,会造成筛选慢、离线不可用、状态不可控。最终采用 bulk 快照 + 本地 SQLite 的方案。

后端负责生成可信 catalog 和 category membership；客户端负责本地读取、筛选、排序、分页。

### 5.3 热门 / 新发布由后端归属决定

热门和新发布不是全量数据的不同排序方式。它们必须先有后端候选集和业务资格过滤:

- 热门需要排除 archived / fork,并满足 star 或 popularity 门槛。
- 新发布需要稳定 release、真实 asset、180 天窗口、非 archived、非 fork。

客户端不能用 score 自行推断分类,只能消费后端返回的 `categories` 和 `category_ranks`。

### 5.4 README 详情优先

最初 Discovery 详情页展示推荐原因、判断信号、版本发布、关键指标等自绘信息。后来改为 README 渲染,与 Starcat 中星标、趋势、活动等模块的详情体验保持一致。

推荐原因和信号仍可作为列表解释或后续排序调优依据,但详情页主体验以 README 为准。

## 7. 遗留问题

当前仍有几项与目标态不完全一致:

1. 发现 feed 的曝光冷却、多样性、动态 momentum 还没有完整进入排序算法。已有 `feed_exposure` 和每日快照基础,但排序仍主要依赖静态 score。
2. `repo_daily_snapshots` 已采集,但 stars / forks / downloads 增长率还没有进入 `trending_score` 或 `discovery_score`。
3. 平台识别已有基础规则,但 asset quality 还没有独立建模。
4. 静态 JSON snapshot / 离线兜底还没有实现,当前后端依赖 SQLite 和 Fly volume。
5. 详细设计中的 Discovery 自绘详情页描述需要后续按 README 详情页方向重写。
6. 需要继续观察线上热门 / 新发布质量,确认候选规则是否过窄或过宽。

## 8. 后续建议

下一阶段建议按优先级推进:

1. 先观察线上数据质量,重点看热门 / 新发布是否符合直觉,是否需要调整资格门槛。
2. 再补 feed 排序算法,把曝光冷却、主题多样性和增长快照纳入可验证规则。
3. 补充静态 snapshot 方案,降低 Fly volume 或 SQLite 单点异常对公开 catalog 的影响。
4. 同步重写详细设计中详情页章节,把 README 渲染确定为正式方案。
5. 继续保留趋势双轨观察,只有当 discovery-api 的趋势候选质量明确优于或不低于现有 trending-api 时,再讨论迁移。

## 9. 结论

这次需求已经从单纯“参考 komi-store 的发现和排行榜”演进为 Starcat 的一套独立探索体系。当前实现保住了三个关键边界:

- 现有趋势链路不受影响。
- 新增发现 / 热门 / 新发布走独立后端。
- Starcat 客户端仍坚持本地优先。

从产品侧看,用户现在可以在探索入口下按发现、趋势、热门、新发布浏览仓库,并看到对应分类数量。从工程侧看,后端服务、客户端缓存、部署脚本、文档和进度记录已经形成闭环。剩余工作主要集中在算法质量调优和文档目标态收敛,不再是基础能力缺失。
