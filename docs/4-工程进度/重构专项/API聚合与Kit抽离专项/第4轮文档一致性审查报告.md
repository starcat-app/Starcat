## 1. 当前事实基线

- Starcat 六个业务 `productionURL` 均为 `https://starcat-api.fly.dev`。
- 业务请求和 `/api/v1/ping` 使用 `X-SC-Svc` 分流；聚合 `/healthz` 不带服务头。
- 聚合网关按 `X-SC-Svc` 优先、旧头兼容、Host 回退进行路由；维护模式只开放 `status=maintenance` 的 `/healthz`。
- 服务配置按 `Apply → FromEnv → restore` 隔离，仅 wiki 四个运行期 `CACHE_*` 显式 Pin。
- `fly-secrets-sync.sh starcat-api` 读取一把 `STARCAT_SHARED_API_KEY` 并生成六个 Fly `*_API_KEYS`；本地 `go run` 仍需六个前缀 Key。
- 2026-08-08 已创建 Fly `starcat-api` App 与 nrt Volume，并以维护模式完成首次部署；六个独立 App 仍在运行且 health check 通过。
- 本地聚合 `.env` 已生成独立 `DISCOVERY_ADMIN_API_KEYS`，格式/唯一性/权限/Git 忽略校验通过，并已同步到 Fly；明文未写入文档或日志。

旧独立 App 的 `fly-restore-data.sh` 会先启动 Machine 以获得 SSH/SFTP，再清空整个 `/data`。文档已经如实标注其破坏范围，但该流程本身仍存在业务进程重新打开 SQLite 的窗口；若继续把它作为生产恢复工具，应另立脚本修复任务，不能仅凭本轮文档同步视为风险关闭。
