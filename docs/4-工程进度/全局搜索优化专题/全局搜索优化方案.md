## 1. 目标与成功标准

用户记不清项目名称时，可以直接描述用途、特点、作者线索或近期热度，Starcat 理解查询后主动检索，最终返回可打开、Star、加入知识库的 GitHub 仓库卡片。

核心验收问题：

> 帮我查一下 github 最近比较火的 linux 发行版，我搞忘叫什么名字了。

期望行为：

1. 输入不包含 `Omarchy`，本地数据库也没有这个仓库。
2. 系统识别“根据模糊线索找回项目”，使用近期信息辅助查找，并区分时间线索与明确时间限制。
3. 搜索公开资料、发现候选、核验 GitHub 身份与描述。
4. 在相关证据支持的测试场景中，把 Omarchy 放进前三条仓库结果。
5. 展示简短匹配理由和证据入口；Star 数、规范仓库名等事实取自实际响应。

该问题作为回归样本，不建立“Linux + 热门 → Omarchy”的特例。其他忘名、用途描述、替代品和中文查询同样进入评测集。实时搜索随时间变化，不能把某个项目永久规定为“最近最火”。

### 1.1 已确认的产品决策

以下七项来自本轮逐项确认，是后文流程、预算和验收的共同约束。

| 决策点 | 已确认行为 |
|---|---|
| 自动触发 | 普通关键词优先快速搜索，保留主动“智能查找”；自然语言描述自动启动智能发现 |
| 联网控制 | 智能发现的网页检索复用“AI 外部上下文”开关；“全部”中是否附带网页资料卡独立控制 |
| 结果排序 | 智能发现按相关性统一排序，外部项目可以领先本地收藏；相关性接近时优先本地已收藏项目 |
| 决策失败 | 搜索中的分类失败或超时，由已配置的 Planner 接手；不自动切换 Jev / Laya，不改变分组与标签策略 |
| 等待时间 | 首轮暂定 15 秒总预算，结果渐进展示；超时保留结果，用户主动“继续查找”可追加一轮有界检索 |
| 候选识别 | 必要时增加一次 LLM 调用，从已取得的网页内容提取项目名，再定位、核验仓库；与其他阶段共享首轮预算 |
| 模糊时间 | 忘名查询中的“最近很火”作为辅助线索；用户明确指定时间、增长指标等条件时严格执行 |

分类阈值、候选数量、缓存期限及冷 / 热态耗时，通过源码核查与评测确定。后文列出的初始参数仍需验证，不把产品决策确认当成性能验收通过。

## 2. 当前实现与问题定位

以下结论来自本地源码检查。尚未进行本轮运行时性能测量，不能据此宣称具体提速幅度。

| 环节 | 已确认的当前行为 | 本专题要解决的问题 |
|---|---|---|
| 提交与编排 | `SearchCenterViewModel.submit()` 提交；`SearchCoordinator` 按 scope 并发执行 Provider | 保留即时反馈、独立失败、generation 隔离和已有来源快照 |
| 全部范围 | 本地关键词、本地语义、GitHub 并发；Web 由 `externalSearchIncludeInAll` 控制 | 不能把现状误解成“本地未命中才搜索远端” |
| 本地关键词 | `searchAllLocalFTS` 查询本地全部缓存仓库 | 保留精确名称和关键词搜索的速度 |
| 本地语义 | 对本地候选计算 embedding 相似度 | 无法发现未缓存仓库；口语查询也缺少意图规划 |
| 索引维护 | `SemanticSearchService.search()` 先等待 `ensureIndexed`；逐仓拼快照，缺失或过期项分批生成向量 | 搜索可能等待全库内容检查和索引补建 |
| 语义过滤 | cosine 经经验区间归一，再使用展示阈值过滤；默认阈值为 0.75 | 展示分不等于相关概率，硬阈值可能损失候选 |
| GitHub 搜索 | 原始 query 加结构化筛选后发送 | 没有去除口语、跨语言改写和任务相关查询生成 |
| Web 搜索 | 外部命中统一生成 `ReferenceCandidate` | 网页发现的项目没有被解析、核验为仓库候选 |
| 合并排序 | 按关键词、语义、GitHub、Web 顺序重建并去重 | 来源优先级不能表达自然语言相关性 |

## 3. 范围与既有约束

本专题包含：

- 搜索查询与索引维护解耦。
- 复用 Jev / Laya 对查询进行封闭式判断。
- LLM 查询规划、多来源召回、仓库核验和证据重排。
- 复用现有仓库卡片、详情和操作，补齐状态、证据及取消行为。
- 质量评测、阶段耗时、请求预算与失败回退。

首版不新增后端服务、向量数据库或数据库 schema，不迁移 RAG 索引，不重做 Agent 工作台，也不把完整 RAG 问答流程塞进搜索框。MCP、CLI、Alfred、Raycast 等外部入口继续保持现有协议，后续可复用发现服务，但不在本轮扩大接口范围。

现有 Web tab 保持单 Provider 的网页检索。新增智能发现仍只使用用户选定的一个外部搜索 Provider；同一 Provider 可以执行有限条改写查询。网页资料不自动写入数据库；核验后的仓库候选也仅存在于搜索会话，持久化沿用用户明确操作的现有流程。

智能发现查询网页由 `externalContextEnabled` 控制，并沿用现有 Provider 配置、凭据与隐私约束，不新增联网总开关。`externalSearchIncludeInAll` 继续控制“全部”范围中的独立网页资料卡，不能用它阻断 AI 已获允许的网页检索。该展示开关关闭时，仍可借助网页发现仓库、展示匹配理由及证据链接；AI 外部上下文关闭时，智能发现仅使用本地和 GitHub 等可用来源。

上述两个开关独立生效：AI 外部上下文关闭不等于关闭用户主动使用的 Web tab；“全部”范围按其网页展示设置提供普通网页结果，也不因此获得 AI 网页检索权限。此时普通网页结果不送入 Planner、候选提取或 Ranker 充当外部上下文。

[外部搜索服务专项](../外部搜索服务专项/外部搜索服务专项进度.md)中“不做 LLM rerank、不把网页自动转成仓库”的条目属于当时第一版交付范围。本专题新增“全部”范围的受控发现流程，保留手动 Web tab 与不自动入库的约束，不把历史交付记录改成已经实现本方案。

## 4. 决策引擎复用结论

### 4.1 已有接口足以承担查询分流

当前通用接口为 `DecisionEngineProviding.evaluate(DecisionEvaluationRequest)`：

- `DecisionState.text` 已支持文本输入，无需伪造 `Repo`。
- `questions` 可在一个业务请求中携带多个 `DecisionNoulQuestion`。
- 每个问题返回 `DecisionNoulAnswer.probability`。
- `DecisionEngineRegistry` 根据用户选择取得 Jev 或 Laya。
- Jev 把问题转换成 TypeSafe `noul`；Laya 使用本地 MLX runtime 执行同类判断。

因此，新增搜索领域服务即可接入。复用通用协议、注册表、模型生命周期及传输，不把查询分类塞进负责仓库分组和标签复用的 `RepositoryDecisionService`。

当前抽象只开放 `noul`，不依赖尚未开放的 `choice` 或 `score`。多个问题的数值是各自判断的输出，不是互斥类别的 softmax，不要求相加等于 1，也不能把它们当成已经在搜索场景校准的置信度。

源码依据：[DecisionEngine.swift](../../../Starcat/Features/AI/DecisionEngine.swift)、[JevDecisionEngine.swift](../../../Starcat/Features/AI/JevDecisionEngine.swift)、[LayaDecisionEngine.swift](../../../Starcat/Features/AI/LayaDecisionEngine.swift)、[DecisionSuggestionRouters.swift](../../../Starcat/Features/AI/DecisionSuggestionRouters.swift)。

### 4.2 分工

| 层 | 职责 |
|---|---|
| 确定性解析 | 识别完整 GitHub 仓库 URL、完整 `owner/repo`、明确搜索限定符及用户选择的范围 |
| Decision Engine | 判断是否需要语义规划、是否依赖时效证据 |
| LLM Planner | 提取线索，生成本地、GitHub、网页查询及候选假设 |
| 可选 LLM 候选提取 | 从已取得的网页正文或摘要识别项目名，并返回对应原文证据 |
| 检索与核验代码 | 执行请求、限制预算、校验身份、去重、保留来源与真实元数据 |
| LLM Ranker | 根据有限候选及证据选择顺序，给出可追溯的匹配理由 |

决策引擎只判断固定问题，不生成英文搜索词、GitHub 地址、项目简介或热度事实。明确名称和普通字面查询先走快速路径，减少无收益的模型调用。决策引擎用于优化分流；它的关闭、不可用或失败，不能阻止已识别的自然语言查询进入智能发现。

### 4.3 一次请求中的两个问题

| question ID | 判断目标 | true / false 判据 |
|---|---|---|
| `needs_intent_planning` | 是否需要解释模糊线索、用途或关系才能构造有效查询 | true：忘记名称、描述能力、寻找替代品或组合条件；false：主要是直接名称、普通字面检索 |
| `needs_fresh_evidence` | 正确回答是否依赖近期、当前或某一时间范围内的外部事实 | true：最近热门、目前维护、近期增长等；false：只要求名称或静态用途匹配 |

问题与判据固定并带版本；用户原文及 scope 作为被判断的数据传入，不能拼进规则字段。决策输入只包含完成分流所需的查询上下文，不携带全库目录、笔记或 README。

`needs_fresh_evidence` 为正表示需要尝试取得时效证据，不等于给所有候选施加硬时间过滤；辅助线索与明确时间限制由 Planner 按第 6.2 节区分。

对“忘记名字的热门 Linux 发行版”，预期两个问题都得到正向判断；这是待评测预期，不是已经测得的模型结果。不能用“中文 / 长句 / 出现最近”单一规则替代整个判断，也不能把普通关键词默认认定为精确项目名。

### 4.4 路由策略与启用方式

新增拟定配置 `decisionSearchRoutingEnabled`，放在 Labs 现有“作用范围”中，默认关闭。使用现有 `decisionEngineEnabled` 和 `decisionEngineID`，不新增搜索专属 Jev Key 或独立 Laya 模型副本，不借用分组 / 标签开关。

独立开关的原因：已有用户开启决策引擎时，已知作用范围是分组与标签；搜索查询进入远端 Jev 属于新增用途，需要可见、可关闭。Laya 保留本地执行，Jev 明示会把当前查询交给所选服务判断。

| 条件 | 行为 |
|---|---|
| 空查询 | 清空或维持现有空态，不发模型请求 |
| 完整仓库身份或明确 GitHub 搜索语法 | 确定性快速路径；含项目 URL 的整句描述不能误判为单独 URL |
| 明确的普通字面查询，如 `react`、`redis` | 优先快速搜索，不默认调用 Planner；保留主动“智能查找”的入口 |
| 决策总开关或搜索范围开关关闭 | 普通关键词继续快速搜索；识别到自然语言意图时自动进入 Planner，不能把所有剩余输入统一发送给 LLM |
| 所选引擎未注册、凭据不可用或本地模型未安装 | 普通关键词继续快速搜索；自然语言查询使用 Planner，不下载模型、不更换引擎 |
| 决策正常返回，明确属于普通字面查询且无时效要求 | 快速检索；结果区保留用户主动“智能查找”的入口 |
| 决策正常返回，需要规划、需要时效证据，或结果落在不确定区 | 进入 LLM Planner，并传入已取得的决策信号 |
| 决策已开始后出现网络、加载、解析、推理错误或阶段超时 | 记录分类失败，在剩余总预算内由一次 Planner 接手意图理解与规划；不重试分类，不切换 Jev / Laya |
| 用户显式选择“智能查找” | 直接进入 Planner，跳过分类；仍遵守联网开关、模型配置与权益 |

轻量识别先区分明确的普通关键词和自然语言意图；对仍需判断的查询，可使用已启用的决策引擎。不能仅因本地有命中就阻止自然语言发现，也不能因为关闭决策引擎而让 `react`、`redis` 全部进入 Planner。具体识别边界用中文、英文和混合查询集校准，误分流仍可由用户主动“智能查找”纠正。

“正常返回但不确定”和“调用失败后接手”分别记录，二者都可进入一次 Planner。后者是 dong4j 明确确认的搜索专属降级：不修改通用决策引擎的错误语义，不改变分组、标签既有的调用失败处理，也不隐式尝试另一个决策引擎。没有可用 Planner 或总截止时间已到时，保留基础结果，给出配置或继续查找入口。

按引擎和模型版本校准正向、负向及不确定区阈值。首轮评测前不写死通用 0.5 分界，不复用标签分类阈值。缺失字段、NaN、越界数值属于无效响应，必须记录为分类失败，再按上述搜索专属策略降级，不能冒充有效的不确定分数。

### 4.5 性能与生命周期

Laya 的 `availability` 当前只确认模型安装，不保证 runtime 已驻留。冷启动还可能等待内存准入、加载权重，不能直接引用上游热态延迟作为 Starcat 的路由耗时。

分别测量 Laya 冷 / 热态和 Jev 网络耗时，并与“直接让 Planner 完成分类和规划”比较。决策分流应在减少不必要规划请求、控制费用或改善端到端体验方面产生可测收益；达不到门槛时保持实验性可选，不强制插入所有查询。

复用当前 runtime 准入与释放机制。超时只意味着停止本次结果采纳并请求取消，不能宣称 GPU 推理已立即结束；资源释放以底层操作真实退出为准。总截止时间不得等待不可及时取消的任务才结束 UI 加载态。

分类阶段应留出 Planner 和检索的时间，不能独占首轮 15 秒预算。分类超时后启动 Planner 仍需遵守共享 runtime 准入与剩余截止时间，不能为降级绕过现有资源管理。阶段阈值由冷 / 热态实测确定。

## 5. 完整搜索执行流程

1. **提交快照**：冻结原始查询、scope、筛选、账号、模型和外部搜索设置，创建 generation；原文用于输入框和历史，不被改写查询替换。
2. **即时本地结果**：启动原始 FTS，与分类 / 规划并行。任何远端阶段都不能阻塞这批结果。
3. **查询分流**：确定性解析优先，普通关键词快速搜索，自然语言描述自动发现；可选决策引擎失败时由 Planner 接手。
4. **生成计划**：Planner 提取意图、实体线索、语义查询及时间条件的软硬约束，生成有预算的检索计划。
5. **并行召回**：执行计划中的本地关键词、已有向量、GitHub、Web 查询；相同任务共享结果，避免 Provider 各自规划和重复计费。
6. **候选解析**：优先识别 GitHub URL 与明确项目名；必要时调用一次 LLM，从已取得的网页内容提取项目名及原文证据，再在共享预算内定位仓库。模型记忆中的候选只当待核验假设。
7. **身份和内容核验**：取得规范名称、GitHub ID、元数据，并保留描述 / README / 网页证据。
8. **结果重排**：把有限的已核验候选与证据交给 Ranker；输出候选 ID、次序、简短理由和证据 ID。
9. **渐进展示**：已取得的基础结果和已核验候选先显示，最终相关性顺序集中更新一次，按仓库身份保持选中项。
10. **限时收束与继续**：首轮总预算到期时结束等待并保留结果；用户主动继续时复用已有线索与有效结果，追加一轮有界检索。

首版采用有界流程，可选候选提取不是无限搜索循环。原始 GitHub 查询与改写 GitHub 查询由同一编排器决定，不能在智能路径中把整句口语和改写词重复发到相同端点。用户主动继续的行为按第 9.4 节单独计量。

## 6. 查询计划、候选与证据契约

以下为拟定职责和字段，实施时优先复用现有模型，不为每个步骤单独建设框架。

| 契约 | 最小内容与约束 |
|---|---|
| `SearchIntentDecision` | 快速 / 发现路由、时效需求、来源为规则 / 决策 / Planner、引擎与问题版本；判断分数仅供诊断 |
| `RepositoryDiscoveryPlan` | 原始查询、规范化意图、本地关键词与语义查询、GitHub 查询、Web 查询、时间解释及软硬约束、允许来源与预算 |
| `SearchEvidence` | 来源类型、URL、原始摘录、关联候选、获取时间、可得的发布时间；缺失日期不补造 |
| 现有 `RepositoryCandidate` 的增量字段 | 发现来源、证据引用、匹配理由、重排位置；不把 LLM 自报分数放进 `semanticScore` |
| 会话状态 | 分类 / 规划 / 搜索 / 候选提取 / 核验 / 排序阶段、各来源状态、预算、generation、继续查找轮次及已用线索 |

约束：

- JSON 输出仍需代码校验；`jsonObject` 不能替代字段、数量、枚举、候选身份和引用校验。
- Planner 不能增加用户未允许的来源，也不能放宽手动筛选；计划与筛选冲突时说明没有符合条件的结果。
- 无法核验身份的网页保持资料身份，是否显示独立资料卡遵守 scope 与网页展示开关，不能伪装成仓库卡。无法确认关联的文章不能给仓库附加“已证实”标签。
- 可选候选提取必须返回已提供资料中的项目名、原文片段与证据 ID；代码校验名称和片段确实出现在对应资料中，再调用 GitHub 搜索。提取名称不等于仓库身份或用途已核验。
- Ranker 只能返回输入候选中的 ID，引用只能来自提供的证据；排序失败保留候选与检索顺序。
- 基础事实和匹配理由分开保存。项目简介、Star 数、仓库名取自实际数据，LLM 只补充匹配解释。
- 默认只把公开候选和公开证据交给发现链路的远端模型；本地私仓结果仍可显示，但不因此自动进入远端规划或重排。未满足既有隐私条件时保留其本地排序。
- 重排候选预算需保留外部已核验项目的名额，再补充本地和其他来源；不能按旧的“本地在前”顺序直接截取前 20 条，导致新发现的项目进不了重排。
- 智能发现按相关性统一排序，未收藏的外部项目可以排在本地已收藏项目之前；相关性接近时再优先本地已收藏项目，不设置本地来源固定置顶。同一仓库合并全部来源，保留已收藏、已入库及笔记等状态。

### 6.1 身份核验

复用 [RepoAPI.swift](../../../Starcat/Core/Network/GitHubAPI/RepoAPI.swift) 获取仓库元数据。处理规范 GitHub 仓库 URL，不能把组织首页、搜索页、Issue 链接直接当成仓库身份。

重定向或更名后采用实际响应中的数字 ID 和规范名称；历史名称只保留为线索。同一仓库合并来源和本地状态，Star、笔记、知识库状态以本地操作的最新快照为准。

GitHub API 成功仅证明仓库存在。判断“是不是 Linux 发行版”“是否具备用户描述的用途”，还需要实际描述或内容证据。网页与 README 都作为不可信资料处理，不执行其中的指令。

### 6.2 “最近”和热度

Planner 根据查询提交时的日期、时区解释相对时间；绝对时间范围与原文一起保留。对未明确具体天数的“最近”，采用可解释的检索窗口，同时保留至少一条较宽查询，避免遗漏最近走红的老项目。

对“最近很火的 Linux 发行版，我忘了名字”，找回项目是主要目标，“最近很火”作为辅助线索。用途或特征高度匹配的候选，即使只取得较早资料或缺少近期热度证据，也可保留；匹配理由明确说明已确认的特征与尚未证实的近期热度，不能因模糊时间线索直接剔除候选。

对“过去 7 天 Star 增长最快”等明确时间、指标约束，严格按条件检索与排序。缺少相应数据时说明无法确认，不擅自改成累计 Star 排名或扩大时间窗口。软硬时间条件进入计划、证据解释和评测标签，不能仅由 `needs_fresh_evidence` 一个分数决定。

累计 Star 数、最近 push、创建时间分别表达不同事实，不能单独证明“最近很火”。需要带日期的相关讨论、实际榜单或已取得的增长证据；缺少证据时只陈述已确认的属性，不生成排名和增长数字。

首版不新增榜单采集或历史分析后端。未来接入已有 Trending / History 能力需要另行核对数据覆盖和时效。

## 7. 语义检索性能修正

### 7.1 索引维护退出查询关键路径

`SemanticSearchService.search()` 改为读取兼容的已存在向量、生成或复用 query vector、计算候选相似度。禁止在该路径逐仓重建内容快照或等待 repo embeddings 写入。

缺失和过期索引交给现有 `SemanticIndexBuilder` 与已有内容变更触发点维护；索引状态在后台更新。查询期间不下载本地模型、不自动全量重建。无兼容向量时该来源返回“索引未就绪”，不能把它包装成确定的零命中。

保持模型 / 配置身份和向量维度校验，不混用不同模型的向量。复用 query embedding 缓存时，核对 Provider、模型、相关配置版本和账号边界，避免只因模型显示名相同就命中错误缓存。

这是共享服务改动，需审查本地列表等调用者。先从查询路径剥离维护职责，不顺带迁移 RAG 数据或改变其索引体系。

### 7.2 召回阈值与展示阈值分开

智能发现从语义侧取有界 Top-K 候选，用作后续相关性判断；不先套用面向展示的 75% 门槛把候选永久丢掉。独立的现有本地语义展示仍保留用户阈值语义，避免无说明改变设置行为。

与 FTS 合并时区分原始相似度、字面命中、来源次序和 LLM 重排位置，不把不同量纲分数直接相加。不将模型判断分数展示成“命中概率”。

先记录全库读取、query embedding、相似度计算和合并耗时，再决定是否需要批量读取或计算调度调整。避免未经测量就引入新的向量存储和复杂并发。

## 8. 结果交互与范围

| 范围 | 首版行为 |
|---|---|
| 全部 | 普通关键词快速搜索，自然语言自动发现；AI 查网页由 `externalContextEnabled` 控制，独立网页资料卡由 `externalSearchIncludeInAll` 控制 |
| 本地 | 仅返回本地仓库，使用现有关键词与优化后的向量检索；不自动扩展成远端仓库发现 |
| GitHub | 保留现有直接查询、筛选与分页，不偷偷改成网页聚合 |
| 网页 | 保留单 Provider 资料结果及现有筛选，不改变手动 Web tab 契约 |

“本地”仍可能使用配置的远端 embedding 服务生成 query vector，不等同于承诺完全离线。首版用户主动“智能查找”的入口位于“全部”范围，其他范围不通过该按钮隐式切换来源。

沿用当前 Search Center 的搜索框、scope、仓库行、详情和操作。新增行内阶段提示，例如“理解查询”“搜索项目”“核验项目”“整理结果”，不展示模型原始推理、不把搜索界面改造成聊天页。

每个发现结果最多增加简短匹配理由和可展开证据入口。不把多个来源命中数简单相加冒充不同仓库数。网页来源失败、核验失败和确实无命中分别表达；错误文案提供模型或搜索设置入口，技术细节放入诊断。

基础结果与核验完成的仓库逐步进入统一列表，不等待 Ranker 结束才显示。智能重排允许高相关外部项目排在本地收藏前面，最终顺序每轮集中更新一次。网页资料卡关闭时，仓库匹配理由与证据链接仍可展示。

首轮暂定 15 秒总预算，到期结束等待状态并保留结果。未找到可靠匹配或尚有线索可扩展时提供“继续查找”；点击后复用当前线索和有效结果追加一轮，用户也可直接修改查询。首轮超时不自动触发下一轮，取消或切换查询后不自动恢复旧任务。

结果排序或流式补充期间，以 `RepoIdentity` 维持键盘选中，不沿用已经指向另一行的旧数组下标。重复提交、清空、scope 变化和旧响应到达继续受请求身份约束；重新打开浮层沿用现有会话恢复语义。

所有新增 UI 按 [DESIGN.md](../../../DESIGN.md) 和现有 UI 规范实施；新增文案需完成届时全部支持语言，AI 初稿状态如实标记。

## 9. 请求预算、缓存与失败行为

### 9.1 首轮预算草案

| 项目 | 初始上限 / 目标 | 说明 |
|---|---|---|
| 决策评估 | 每次智能提交至多 1 次，批量携带 2 个问题 | 精确路径与用户主动智能查找跳过 |
| LLM | 常规至多 2 次：Planner + Ranker；必要时总计至多 3 次 | 仅增加一次网页候选提取；分类降级复用同一次 Planner，不额外调用 LLM 分类 |
| Web | 同一 Provider 至多 2 条查询，每条至多 10 个命中 | 不跨 Provider 聚合 |
| GitHub 仓库搜索 | 至多 2 次 | 一次类别召回；必要时一次从规则或 LLM 提取的项目名定位仓库，共享预算 |
| 单仓库核验 | 至多 5 个远端候选 | 已有可信 GitHub 响应可复用；不对本地全部命中逐一联网 |
| README 补充 | 仅在已有摘要不足时，至多 3 个候选 | 与身份核验及总截止时间共享预算 |
| 重排输入 | 去重后至多 20 个候选及截断证据 | 不提交完整数据库或全文网页集合 |
| 本地首屏 | 热态 P95 目标不超过 200ms | 评测报告必须注明库规模与机器 |
| 智能首批结果 | 目标约 3～6 秒 | 依模型和网络测量，不能作为已达成指标 |
| 首轮智能发现 | 初始总预算 15 秒 | 分类、规划、检索、候选提取、核验及排序共用截止时间；超时保留结果并结束等待 |

请求数量指业务调用；需要核对底层客户端已有重试，使实际网络尝试同样受剩余时间与尝试上限控制。缓存命中不计为新的远端调用，但记入诊断。手动分页属于用户新动作，不得偷偷重新执行整套 Planner 和 Ranker。

常规的两次 LLM 调用分别负责规划和排序。已有足够仓库候选时无需增加调用；只有相关文章而缺少仓库线索时，可在排序前增加一次候选提取，从已取得的有限正文或摘要中返回项目名与原文证据，再交给代码定位、核验 GitHub 仓库。候选提取属于按需步骤，不默认再抓取完整网页，也不循环调用模型寻找地址。

可选提取与其他步骤共享 15 秒及 GitHub 请求预算，不能因为多一次 LLM 就重置截止时间或增加搜索次数。剩余时间不足或定位预算已用完时，保留已有线索供用户继续查找；提取失败仍可展示已有仓库，原网页按展示设置保留为资料。15 秒为已确认的初始设计参数，后续按真实耗时评测调整。

### 9.2 缓存身份

复用已有 `SearchSessionCache` 和 `DiskExternalSearchCache` 的能力，不建立跨账号、永久保存模型猜测的结果库。

- 规划 / 路由缓存包含 query、scope、引擎 / 模型配置、问题 / prompt 版本及相关设置。
- 时效查询包含解析后的时间窗口和时间桶，不能用旧缓存断言当前热度。
- 检索缓存包含实际改写 query、筛选和 Provider；凭据或配置改变后失效。
- 会话结果核对 AI 外部上下文、网页展示设置及时间条件策略；继续查找可复用仍有效的计划、证据和候选，不重复执行已完成的相同检索。
- 带本地结果的会话缓存按账号隔离；退出、切号、库变化和 Star / 知识库操作及时失效或覆盖状态。
- 缓存候选不能覆盖当前本地操作；错误或未完成结果不伪装成成功缓存。

### 9.3 分阶段失败

| 失败阶段 | 用户可见结果与后续 |
|---|---|
| 决策调用开始前不可用 | 普通关键词快速搜索，自然语言进入已配置的 Planner；没有模型时保留普通搜索并给配置入口 |
| 决策运行中失败或阶段超时 | 基础结果保留，在剩余总预算内由一次 Planner 接手；不重试分类或自动切换 Jev / Laya |
| Planner 失败或计划无效 | 保留本地结果，按原有直接搜索能力降级，不执行无法校验的查询计划 |
| 某个检索源失败 | 其他来源继续，独立记录失败；不伪装成该来源无命中 |
| 可选候选提取失败或证据无效 | 保留已有候选，不使用无依据项目名补查，不追加提取重试；原网页按展示设置保留为资料 |
| 仓库核验失败 | 排除其“已核验仓库”身份，原网页按展示设置保留为资料 |
| Ranker 失败或引用无效 | 保留已核验候选和确定性顺序，不显示无依据的匹配理由 |
| 总预算到期 | 结束本轮等待并停止采纳迟到响应，保留已成功结果和有效线索，提供主动继续查找；取消底层任务，资源按真实退出释放 |
| 用户取消或切换查询 | 终止当前 generation 的后续采纳，不自动追加轮次；底层资源按真实退出释放 |

分类失败后由 Planner 接手是搜索业务明确允许的降级，不属于切换决策引擎。禁止实现 Jev → Laya → LLM 的连锁尝试，也不修改分组、标签模块调用失败后直接上抛的既有约定。降级、候选提取和用户继续查找都需分别记录调用归因。

### 9.4 用户主动继续查找

“继续查找”属于同一查询下的用户新动作，每次点击最多追加一轮，沿用第 9.1 节的单轮调用上限和初始时间预算，不自动续轮。

复用当前会话中仍有效的意图、已取得证据、已核验候选及尚未执行的线索；根据已有资料调整下一轮查询，避免整套流程从头重跑。已有足够证据时跳过无必要的规划或候选提取，所有实际新增调用仍计入本轮预算，候选按身份合并并保留用户最新操作。

以现有请求身份和明确轮次区分本轮响应，上一轮超时或已取消的响应不能因继续查找重新获得写入资格。query、scope、账号或相关模型 / Provider 设置变化时按新请求处理，不继承失效上下文。诊断分别报告首轮与继续轮次的耗时、用量、缓存复用和新增命中，不能把多轮结果计为一次首轮成功。

## 11. 实施阶段与交付门槛

| 阶段 | 工作内容 | 完成证据 |
|---|---|---|
| P0 基线与契约 | 建立查询集、记录当前结果与耗时，冻结范围、计划、证据、预算接口 | 第 1.1 节七项产品决策进入验收；技术参数有可复现基线与标注规则 |
| P1 查询性能 | 查询不再等待 repo 索引维护，诊断已存在 / 缺失向量 | 缺索引搜索不会生成 repo embeddings；现有索引维护仍可工作 |
| P2 决策分流 | 普通关键词快搜、自然语言发现、所选 Jev / Laya 及搜索专属 Planner 降级 | 冷 / 热态评测、误分流分析、失败后接手且无隐式引擎切换；分组标签不受影响 |
| P3 仓库发现 | 规划、检索、可选候选提取、GitHub 核验、相关性重排与时间条件解释 | 固定回放和实时查询分别验证；按需第三次 LLM 在单轮预算内；非特例查询同样改善 |
| P4 UI 与回归 | 联网与展示开关分离、渐进结果、限时收束、继续查找、稳定选中、全部语言 | 定向测试、标准渠道构建与授权后的实际界面验收 |

开始代码实施前，按仓库现行任务规范建立或复用唯一 GitHub 主关联及 Multica 对应关系，再明确分支与 worktree。当前仅归档文档，没有创建这些关联，也没有完成实施或验收。

## 12. 验收与评测

### 12.1 数据与指标

初始人工标注 30～50 条真实查询，包含中文、英文、混合输入、明确名称、忘名、用途、替代品、时间线索和无答案情况。候选答案由人工及可追溯资料确定，不用模型输出给模型自身打分。

为每条样本记录原文、允许范围、期望仓库集合、可接受别名、判断依据和采样日期。保留独立验证集；Jev 与 Laya 使用相同人工标签评估，不使用 Jev 输出训练或蒸馏另一引擎。

至少报告：

- 路由：需要发现的请求被误送快速路径的比例、普通关键词无必要 Planner 调用比例、不确定率、分类失败后 Planner 接手情况。
- 召回：期望仓库进入重排前候选集的比例，以及可选网页候选提取带来的新增有效候选。
- 排序：Top-1 / Top-3 命中率、首个正确结果位置。
- 事实：虚构仓库、无依据热度 / 排名陈述、无效证据引用数量。
- 性能：本地首屏、决策冷 / 热态、规划、检索、候选提取、核验、排序及端到端 P50 / P95；首轮超时是否及时结束等待。
- 成本：模型调用、搜索调用、实际重试、缓存命中和 token 用量，首轮与用户主动继续的轮次分别报告。

需要直接比较“启用决策引擎”和“未启用决策引擎”的真实查询结果：是否减少不必要的 Planner 调用，以及自然语言端到端延迟是否明显增加。不能仅以分类接口可调用证明它对搜索有收益。

区分固定证据回放与实时联网评测。前者验证可复现行为，后者验证当前供应商和数据源实际可用性；固定测试通过不能代替实时结果，也不能证明 GUI 已验收。

### 12.2 必须覆盖的场景

| 场景 | 预期 |
|---|---|
| 忘名 Linux 发行版，本地无目标项目 | 固定证据支持时 Omarchy 进入前三；不要求查询包含项目名 |
| 仓库改名 / 转移组织 | 通过响应 ID 和规范名称合并；不写死历史 owner |
| 完整 GitHub URL / `owner/repo` | 无决策、无 Planner，直接检索；口语中夹 URL 仍保留完整意图 |
| 关键词与自然语言边界 | `react`、`redis` 默认快速搜索；“终端里管理容器的工具”等自动发现；模糊边界分别评测，误分流可主动智能查找 |
| 决策双问题同时为正、结果不确定 | 正常进入一次 Planner，不把独立分数当作互斥分类 |
| 决策缺字段 / NaN / 阶段超时 | 记录分类失败，在剩余总预算内由一次 Planner 接手；不重试分类或切换 Jev / Laya；分组标签策略不变 |
| 决策总开关关闭 / 搜索作用范围开关关闭 / Laya 未安装 | 普通关键词仍快速搜索，自然语言由 Planner 处理；不自动下载或改变引擎 |
| Laya 冷启动和内存准入等待 | 本地结果正常显示；按真实执行结束释放资源 |
| 本地已有向量 / 部分缺失 / 完全未就绪 | 查询不生成 repo embeddings；索引缺失与无命中区分 |
| AI 外部上下文开启，网页资料卡关闭 | 可查网页发现仓库并展示证据链接，不混入独立网页资料卡 |
| AI 外部上下文关闭，网页资料卡开启 | 智能发现不查网页；普通“全部”网页结果按展示设置提供，不自动用作 AI 外部上下文 |
| AI 外部上下文关闭 / 凭据不可用 / GitHub 限流 | 智能发现保留可用来源并说明受限，不越权开启来源 |
| 外部项目比本地收藏更相关 | 外部项目可以排在前面；相关性接近时优先本地收藏，同仓库只显示一条并保留本地状态 |
| 只有介绍文章，未直接给出 GitHub 地址 | 必要时增加一次 LLM 提取名称及原文证据，再定位核验；证据伪造或预算不足时不继续自动补查 |
| 已有足够仓库候选 | 无额外提取调用，常规至多两次 LLM；按需提取时首轮总计至多三次 |
| 首轮 15 秒到期 | 及时结束等待，保留已取得结果与线索，提供主动继续查找，不自动续轮 |
| 用户主动继续查找 | 复用有效线索与结果追加一轮，独立计量；旧轮迟到响应无效，改查询后不继承失效上下文 |
| 搜索结果含无关项目或文章指令 | 无内容证据不进入高相关结果，不执行网页指令 |
| 模型返回不存在的候选 ID / 证据 ID | 拒绝无效输出，保留核验候选 |
| 快速连续提交 / scope 切换 / 排序更新 | 旧响应不覆盖新结果，选中身份与操作对象一致 |
| Star 或入库后迟到结果返回 | 用户操作后的最新本地状态保持 |
| 账号切换 / Provider 或模型变更 | 相关缓存失效，无跨账号本地候选泄漏 |
| 最近热门但只有累计 stars | 不生成“近期第一”“近期暴涨”等无证据结论 |
| 忘名查询的用途匹配，但近期热度未证实 | 保留可能匹配的候选，说明已确认特征及热度证据不足，不因模糊时间线索硬过滤 |
| 明确要求过去 7 天 Star 增长最快 | 严格按时间和增长指标执行；缺数据时说明无法确认，不替换成累计 Star 排名 |
| 没有明确答案 | 如实展示候选或未找到，不强行给出一个确定项目 |

### 12.3 自动化与人工验证

扩展现有 Search Coordinator、ViewModel、SemanticSearch、GitHub 和 External Search 测试；新增路由、搜索专属降级、开关联动、候选提取证据、总预算与继续查找轮次的有意义测试。模型质量使用人工标注评测，不用 Mock 成功代替真实准确率。

测试通过项目 `make test TEST_ARGS="..."` 定向入口执行，按项目约定先确认 Xcode IDE 未占用测试环境；构建使用 `make build-appstore`、`make build-direct`。这些属于后续代码实施验证，本次文档归档不执行。

实际界面验收与构建通过分别记录；需要 Computer Use 时另行取得明确授权。实现后再核对当时的完整语言集合及长文案布局。
