# 严重故障诊断与状态面板摘要方案

> 状态：方案待实施；dong4j 已确认严重故障准入原则，本轮仅授权文档落档
> 创建：2026-11-12
> 适用范围：Starcat macOS App 的 App Store / Direct 渠道
> 关联基线：[诊断日志优化方案](诊断日志优化方案.md)、[开发前问题清单](../../1-立项/开发前问题清单.md)

本文规定诊断日志的写入边界、故障记录格式、上下文保留方式和状态面板展示字段。文中的新增字段、界面示例、实施步骤和验收项均为拟议方案，不代表已经修改代码或通过验收。

## 1. 目标与决策边界

dong4j 已明确：诊断日志只写入出现严重问题、导致某项功能无法正常使用的错误。导出的诊断材料需要包含足够的上下文，供开发者排查；状态面板只展示用户能够理解的问题摘要。

一条故障记录同时服务于这两个用途：

- 状态面板回答“什么功能发生了问题、何时发生、发生几次”。
- 导出材料回答“在哪个版本和环境中，哪个操作经过哪些阶段，在何处因为什么失败，尝试过什么恢复，最终影响是什么”。

正常阶段不独立写成诊断问题。最终严重故障发生时，将本次操作必要的阶段和状态一起附入该条记录，避免收紧采集范围后丢失排障线索。

2026-11-10 方案允许可恢复错误与取消作为独立 `context` 事件落盘。本次调整收紧的是实际写入范围，不能仅将 `visibility` 从 `issue` 改为 `context`。既有后台写入、轮转、导出快照和脱敏能力继续复用。

本方案不增加自动重试、远端上传、业务修复或 GUI 操作，也不改变独立本地 AI 运行日志的采集与清理规则。

## 3. 严重故障准入

### 3.1 判断依据

只有业务事实能够确认严重故障时，才生成持久化诊断记录：

1. 故障实际阻断了当前功能或关键操作，或使关键用户数据无法正确保存、恢复、清理。
2. 当前操作已经得出失败结果；已有业务重试或回退未能完成用户原本请求的功能。
3. 不是主动取消、正常业务拒绝、缺少可选配置等预期状态。

功能影响按具体请求判断。例如，代码分析无法执行时，“普通聊天仍能使用”不能自动算作代码分析成功回退；同样，刷新失败但用户请求的内容仍可从有效缓存正常使用，也不能只因发生异常就上报严重故障。

不根据异常类型、HTTP 状态或日志级别单独判定准入。网络故障和服务错误是否达到严重程度，沿用具体模块已有的业务判定，不为日志新增自动重试或统一等待阈值。

### 3.2 分类示例

| 场景 | 处理规则 |
| --- | --- |
| 启动依赖、数据库打开或迁移失败，相关功能无法工作 | 记录严重故障及失败阶段 |
| 关键凭据或用户数据无法读写、恢复出厂清理未完成 | 按实际功能影响或数据风险记录 |
| 必需的内置 Runtime 损坏，功能无法启动 | 记录最终失败与已执行的检查 |
| 请求重试成功、候选程序检测后找到可用程序 | 不生成独立严重故障记录 |
| 缓存刷新失败，但有效缓存能完成当前请求 | 不生成严重故障记录，普通日志可保留 |
| 重新 Star 成功后清理旧撤销记录失败 | 不直接视为 Star 功能阻断；按撤销能力实际影响判断 |
| 单项设置解析失败后可使用有效默认值 | 不一律上报；关键配置丢失应单独判断 |
| Spotlight 单仓库更新失败或索引重建失败 | 判断具体搜索能力与可用索引，不能统一视为整体不可用 |
| RAG、语义索引或代码上下文构建部分失败 | 判断用户请求是否实际无法完成，不能仅按异常类型决定 |
| 缺少 API Key、授权过期、购买取消、可选程序未安装 | 使用对应用户提示或配置指引，不自动作为严重程序故障 |
| 401、404、429、5xx、超时或响应解码异常 | 在业务层结合重试、回退和最终影响判断 |
| 成功、正常空结果、取消、跳过、健康检查结果、普通进度 | 不作为独立诊断事件持久化 |

`level` 描述技术严重程度，`outcome` 描述结果，`impact` 描述实际影响。新持久化故障使用与事实一致的 `error` / `critical` 和 `blocked` / `dataRisk`；不能通过自动补成这些值来绕过准入判断。

## 4. 故障记录格式

### 4.1 字段职责

继续使用 JSONL，每行一个 JSON 对象。拟将事件格式升级到 `schemaVersion = 3`，以下新增字段不代表当前已支持。

| 字段 | 用途 | 面板展示 |
| --- | --- | --- |
| `schemaVersion`、`eventID`、`sequence` | 格式版本、事件身份与写入顺序 | 不展示 |
| `summaryKey`（新增） | 固定问题类型对应的本地化摘要 key | 渲染为主要摘要 |
| `timestamp`、`firstSeen`、`lastSeen` | 记录时间及聚合时间范围 | 展示简短时间 |
| `occurrenceCount` | 本条记录新增的发生次数 | 汇总后展示次数 |
| `level`、`impact`、`outcome`、`visibility` | 严重程度、实际影响、结果与提醒用途 | 用于状态判断，不展示内部枚举 |
| `category`、`operation`、`phase`、`durationMs` | 模块、操作、失败阶段与耗时 | 模块可按需本地化展示 |
| `message` | 固定技术描述，不能拼接任意用户内容或响应正文 | 不展示 |
| `errorCode`、`underlying`、`errorChain` | 稳定错误分类、安全底层摘要与受控错误链 | 不展示 |
| `fields` | 当时的重试次数、缓存与回退状态等白名单标量 | 不展示 |
| `breadcrumbs`（新增） | 本次操作必要的有界阶段记录 | 不展示 |
| `breadcrumbsTruncated`（新增） | 阶段上下文是否因容量限制被截断 | 不展示；导出报告说明 |
| `sessionID`、`environmentID` | 关联运行会话及环境快照 | 不展示 |
| `operationID`、`parentOperationID` | 关联根操作与子操作 | 不展示 |
| `requestID`、`serverTraceID`、`service`、`statusCode` | 按实际可用信息关联请求、服务端和响应 | 不展示 |
| `sourceFile`、`sourceFunction`、`sourceLine` | 定位内部代码，不含开发机器绝对路径 | 不展示 |

新故障必须提供固定的 `summaryKey`。摘要由本地化资源生成，不从 `message` 或任意异常文本截取，也不通过生成式摘要补写根因。本轮不增加任意字符串插值参数。

`message` 继续使用固定技术描述。错误类型、结果码和必要的解码路径放入现有安全错误字段，不能将任意 `localizedDescription` 直接作为可导出的完整错误。

新严重故障使用 `visibility = issue`。`visibility` 不作为采集权限开关，不能通过写成 `context` 持久化不符合准入的普通事件。

### 4.2 合成示例

以下为“聊天数据库损坏，最终无法打开”的合成示例，不对应真实用户数据。为阅读展开显示，落盘时为单行 JSON。

```json
{
  "schemaVersion": 3,
  "eventID": "example-event",
  "timestamp": "2026-11-12T01:00:00+08:00",
  "level": "error",
  "visibility": "issue",
  "impact": "blocked",
  "category": "chat-history",
  "operation": "chatHistory.openDatabase",
  "summaryKey": "diagnostics.issue.chatHistoryUnavailable",
  "message": "Chat history database initialization failed",
  "phase": "openDatabase",
  "outcome": "failed",
  "errorCode": "database.openFailed",
  "errorChain": [
    { "type": "GRDB.DatabaseError", "code": 11 }
  ],
  "sessionID": "example-session",
  "operationID": "example-operation",
  "environmentID": "example-session",
  "occurrenceCount": 1,
  "fields": {
    "attempt": 1,
    "cacheFallback": false,
    "outputAvailable": false
  },
  "breadcrumbs": [
    {
      "phase": "resolveDatabaseLocation",
      "outcome": "succeeded",
      "elapsedMs": 2
    },
    {
      "phase": "openDatabase",
      "outcome": "failed",
      "elapsedMs": 8
    }
  ],
  "breadcrumbsTruncated": false
}
```

示例中的 `summaryKey` 为拟议 key，尚未添加到本地化资源。请求或服务端 trace 未提供时直接省略，不生成虚构关联值。

## 5. 操作上下文的保留

### 5.1 采集与落盘时机

复用现有 `DiagnosticOperation` 和操作 ID：

1. 操作执行时，在该操作的内存上下文中保留关键阶段和安全统计。
2. 子操作通过已有操作关系传递必要的错误与阶段，不各自重复生成同一根故障。
3. 用户取消、正常完成或有效回退时，不生成严重故障记录，释放本次上下文。
4. 最终确认为严重故障时，生成一条记录，附带相关步骤、错误链、尝试次数和回退结果。

诊断不能增加业务请求，也不能为了获得完整过程而重复执行用户操作。

### 5.2 上下文内容与容量

`breadcrumbs` 只接受固定阶段、结果、相对操作开始的耗时，以及必要的白名单标量和请求关联标识。失败前成功的缓存检查、初始化或请求可以作为这条故障的上下文保留。

拟将每次操作的阶段记录上限设为 16 条，保留最近的必要阶段，并受现有载荷预算约束；截断时设置 `breadcrumbsTruncated`，报告明确说明证据不完整。具体接入不能形成全局无界操作历史，也不为该上限新增用户设置。

会话与环境资料继续保存为必要的元数据，不能以减少事件数量为由丢失构建与会话关联，也不能借元数据重新保存所有成功操作轨迹。

### 5.3 环境与恢复事实

版本、构建、渠道、系统等信息通过 `environmentID` 关联现有环境资料。影响本次故障的关键配置状态在故障发生时保存为受控字段，区分当时状态与导出时快照。

后续是否恢复，仅在已有业务状态能够明确关联并证明时说明。没有对应证据时标记为未知；本轮不为恢复判断新增一套持久化状态系统。

## 6. 状态面板展示

### 6.1 展示内容

现有诊断入口继续保留，主要内容改为 `summaryKey` 对应的本地化摘要，时间与次数作为辅助信息：

```text
聊天记录读取失败
最近发生于 01:00 · 发生 1 次
```

多项故障时，概览可显示“2 项诊断问题 · 最近：聊天记录读取失败”。问题项数按故障分组计算，不能把发生 20 次直接称为 20 个不同问题。分组至少结合模块、操作、稳定错误分类和必要作用范围，不能只根据翻译后的摘要合并。

`occurrenceCount` 沿用每条新增次数的语义，避免把累计次数重复相加。不同操作中的关键差异仍应能在导出材料中追踪。

面板不展示原始英文 `message`、异常堆栈、源码位置、JSON 或内部 ID，也不扩展为完整日志查看器。

### 6.2 历史、确认与恢复

- 使用“最近发生”的事实描述，不凭历史错误断言当前功能仍不可用。
- 沿用现有最近 24 小时和已确认提醒的范围，不将其称为全部未恢复故障。
- 清除提醒表示用户确认，不删除诊断证据，也不证明功能恢复。
- 导出成功仅表示生成了本地材料，不确认提醒、不宣称已上传。
- 无合格故障时表达“没有诊断问题记录”，不能据此保证所有功能正常。
- 诊断存储或采集不可用时明确显示记录不可用，不能伪装成没有故障。

摘要新增文案使用现有本地化流程，按实施时实际支持语言集合完成覆盖与校验，AI 译文保持真实审核状态。

## 7. 导出材料与隐私

### 7.1 导出内容

继续复用 `events.jsonl`、`report.md`、`manifest.json`、会话与环境资料、现有状态快照和允许的相关附件。

`report.md` 展开同一条故障的技术字段与 `breadcrumbs`，让开发者能够先看摘要，再看具体阶段、错误链、配置状态、缓存与回退结果、代码位置，以及可用的请求关联。

报告必须区分：

- 故障发生时记录的事实与导出时采集的状态。
- 已执行的重试或回退与尚未执行的建议。
- 已确认原因、规则推断和未知信息。
- 完整上下文与已截断、缺失或无法关联的证据。

独立本地 AI 运行日志维持原采集和清理语义；诊断包按所选严重故障关联筛选有界的安全投影，不再无条件附带与故障无关的最近过程。缺少可靠关联时说明证据不足，不能按时间接近就宣称来自同一请求。

收到 MetricKit 通知本身不生成严重故障事件。实际可用于排查严重问题的系统诊断仍可作为相关安全附件，由清单说明来源和采集结果。

### 7.2 无故障与增强复现

没有严重故障记录时，导出仍可提供允许的环境资料、状态快照、采集结果和用户主动填写的现象说明。报告明确说明未取得对应故障证据，不能为了产生内容而创建虚假错误。

既有增强复现入口可提高本操作安全上下文的采样密度，但仍不把成功、取消或已恢复的普通过程变成独立严重故障。内存上下文不承诺跨进程终止后完整恢复；系统诊断或其他来源能提供多少证据，就如实报告多少。

### 7.3 数据边界

沿用现有白名单、匿名关联、落盘前脱敏和导出校验。不采集凭据、用户输入输出、聊天与笔记正文、完整请求响应、完整 URL 或私人文件路径。数据库异常不附 SQL 绑定参数。

新增摘要与阶段记录同样经过边界校验。诊断写入失败不能递归生成更多诊断错误，继续复用现有存储健康统计。

## 8. 实施范围与顺序

| 顺序 | 涉及位置 | 预期变化 |
| --- | --- | --- |
| 1 | `DiagnosticEvent`、现有格式读写与诊断测试 | 增加摘要和有界过程字段，定义版本与安全边界 |
| 2 | `DiagnosticOperation`、`DiagnosticHTTP`、`UserFacingError`、`DiagnosticLogStore` | 普通过程留在操作上下文；严重故障才持久化；移除失败一律等于阻断的推断 |
| 3 | 各业务故障入口 | 根据实际结果接入准入规则，保留真正的数据库、凭据、关键数据和运行故障 |
| 4 | `AppStatusToolbarButton`、本地化资源 | 面板读取摘要，正确展示时间、问题项数与次数 |
| 5 | `DiagnosticBundleExporter`、`DiagnosticArchiveBuilder`、现有解析工具 | 输出完整技术证据与过程，调整附件关联与历史格式说明 |
| 6 | 单测、双渠道构建、文案与界面验收 | 分别记录代码验证和人工验收结果 |

业务审查覆盖启动与数据库、凭据、设置、Star 与撤销历史、Release 监控、仓库解析、Spotlight、内容刷新、AI、RAG、语义索引、Runtime、MCP、浏览器插件、README 和恢复出厂清理。不能只收紧通用入口而遗留显式 `DiagnosticLogStore.record` / `enqueue` 写入。

历史 JSONL 保留，不删库、不要求用户重建数据，不为旧事件伪造摘要、过程或影响。新写入统一使用新格式；旧日志在导出时标注历史证据限制。面板只将能够符合新准入规则的记录计入严重问题提醒，证据不足的旧事件不因原有 `issue` 标记继续点亮；合格记录遇到缺失或无法识别的摘要 key 时，显示本地化通用摘要。

旧方案保留为历史与已落地能力基线，实施后再依据真实变更更新对应使用手册、解析说明与验证记录。功能实现总览、Changelog、分支操作、提交与发布继续按各自授权处理。

## 9. 验收标准

以下均为待验证项，文档落档不代表通过。
