# 诊断日志优化方案

> 状态：方案已落档，实施待确认
> 创建：2026-11-10
> 审计基线：2026-11-10 的本地工作区代码，包含当时尚未提交的相关改动
> 适用范围：Starcat macOS App 的 App Store / Direct 渠道
> 执行清单：[诊断日志优化Checklist.md](诊断日志优化Checklist.md)

本文记录诊断日志专题的目标、代码审计结论、拟议架构、接入范围和验收标准。当前授权范围为方案落档，不代表代码实施、正式版本归属或发布已经确认。容量、时长和字段名称属于初始设计建议，须在实施与测量后收口。

## 1. 背景与目标

用户在应用报错、功能不可用、数据显示异常或应用无响应时，需要主动导出诊断包交给开发者。开发者应能够依靠这个包还原问题过程，减少反复询问用户、临时开启调试和再次复现的成本。

现有诊断已具备结构化事件、基础脱敏、文件轮转和 ZIP 导出，但采集范围较窄，缺少操作关联和故障现场。用户看到错误，不代表对应证据已经进入可导出的诊断日志。

本专题以用户故障排查为交付目标。普通用户无需提前开启调试开关，问题发生后的常规导出应尽可能回答：

1. 问题发生于哪个版本、构建、渠道、系统和运行会话
2. 用户执行了什么操作，操作使用了哪些有效配置
3. 操作经过哪些阶段，最后停留在哪一步
4. 是请求、认证、解析、存储、业务状态还是渲染阶段异常
5. 影响范围是什么，是否重试，后续是否恢复
6. 当前证据能够证明什么，缺少什么，还需要怎样复现或补充

诊断包不保证一次确定所有问题的根因。证据不足时，应明确记录限制和下一步取证方向，不生成没有证据支持的确定结论。

## 2. 现状审计

### 2.1 核心代码依据

现有存储串行化已经能够避免文件追加互相交错。这里提出的入队顺序和快照改造，是补齐导出证据完整性；尚无证据证明本次样本缺少信息就是由写入时序造成。

### 2.2 真实样本说明

用户提供的样本是事件 JSONL，不是完整导出 ZIP，共 22 条事件，时间范围为 2026-10-23 至 2026-11-10：

| 内容 | 数量 | 当前能够证明的事实 |
| --- | --- | --- |
| `starredRegistry.reload` 数据库错误 | 4 | 底层摘要均为 `Swift.CancellationError`，不能仅凭这些记录认定数据库损坏 |
| CodebaseMemory 程序检测失败 | 3 | 检测没有成功，缺少候选程序失败原因和当时的功能配置 |
| 服务健康检查成功 | 8 | 对应检查成功，不能代表用户操作的所有业务环节正常 |
| MetricKit 收到通知 | 7 | 收到了 payload，字节数无法用于定位具体问题 |

现有 ZIP 已包含简单版本、系统和设置资料，不能描述成“完全没有环境信息”。主要缺口是事件发生时的环境、用户动作、执行阶段和模块状态没有关联。

专题文档只保存汇总事实，不复制客户原始日志、附件的本机路径、账号身份或生产 trace。

### 2.3 已确认的分类问题

- [StarringSubsystem.swift](../../../Starcat/Core/Sync/StarringSubsystem.swift) 的 registry 重建将所有 catch 统一记录为数据库 issue，没有区分主动取消、任务替换和真正读取失败
- [CodebaseMemoryBinaryResolver.swift](../../../Starcat/Features/CodeGraph/CodebaseMemory/CodebaseMemoryBinaryResolver.swift) 将检测失败统一记录为 critical，候选程序的拒绝原因主要留在 OSLog
- 现有“是否计入故障提示”的窄规则同时限制了证据采集，导致可恢复但反复影响用户的故障可能没有对应诊断

## 3. 决策基线与范围

### 3.1 沿用的已确认约束

实施须遵循 [开发前问题清单](../../1-立项/开发前问题清单.md) 中的既有决策：

- 使用原生 OSLog，不引入 swift-log
- 本地 AI 日志保留阶段和统计，不保存输入、输出或思考原文
- 本地 AI 日志已有独立队列、容量和清理语义，不得因本专题破坏
- Direct 授权仅暴露安全错误码、HTTP 状态和经格式校验的 trace；不改变权益判断，不增加自动激活重试
- 已发布数据库 schema 变更须追加迁移；本专题的诊断存储设计不依赖业务库，也不要求用户删库

### 3.2 待确认的诊断边界调整

[功能实现总览](../../功能实现总览.md) 当前记录的旧边界是“仅记录用户不可自行恢复的程序、数据与打包故障”。本专题提议扩展故障取证范围，同时保持用户提醒克制。

本方案落档不直接覆盖旧决议。代码实施前，应确认新边界并在决策文档中记录；对功能实现总览的任何写入，继续遵循单独确认要求。

### 3.3 本专题范围

- 统一安全事件、操作关联、错误分类与后台存储
- 接入主要功能的执行边界、关键状态和恢复结果
- 生成可读报告、结构化文件和安全附件
- 完善常规导出、相关故障导出、增强复现和启动失败降级
- 配套开发者分析工具、隐私校验和性能验收

本专题不默认增加远端上传、第三方故障平台、用户行为全量录制、原始网络抓包或业务数据库导出。后端缺少关联字段时，先报告证据限制，具体服务改造作为独立范围确认。

## 4. 诊断规则

### 4.1 证据采集与用户提醒分离

| 场景 | 证据规则 | 提醒规则 |
| --- | --- | --- |
| 用户主动取消、页面切换替换任务 | 记录取消终态和已知取消原因 | 通常不点亮全局故障 |
| 网络断开、超时、401、429、5xx | 保留请求结果、尝试次数、恢复过程 | 按当前操作是否受阻提示 |
| AI 配置缺失、可选程序未安装 | 记录配置/依赖状态和不可用原因 | 提供对应配置或安装指引 |
| 解码失败、数据读取失败、未知异常 | 保留结构化错误和关联阶段 | 按影响范围和严重程度提示 |
| 人数差异、渲染未完成、状态未推进 | 记录观测值、来源和判定依据 | 区分业务限制、暂时差异与不可用 |
| 重试成功、重新连接成功 | 关联此前失败并记录恢复 | 更新当前状态，保留历史证据 |

有些 404、缓存未命中、304 或权限拒绝属于特定业务中的预期分支，应按实际语义记录为跳过、缓存命中或预期不可用，不能统一升级为故障。

### 4.2 独立表达三个维度

- 严重程度：保留 debug / info / warning / error / critical 等技术级别
- 操作结果：成功、失败、取消、部分完成、跳过
- 用户影响：无影响、功能降级、功能受阻、数据风险

critical 应由实际影响支撑。可选依赖未安装不能仅因“功能需要它”就被当成整个应用的严重故障。

### 4.3 导出、忽略与恢复

导出成功只表示诊断包生成成功。用户忽略提醒只影响提醒展示。故障恢复需要后续成功事件或有效状态作为依据，三者不得互相替代。

## 5. 事件与操作关联设计

### 5.1 字段组

| 字段组 | 拟议内容 | 约束 |
| --- | --- | --- |
| 格式与身份 | `schemaVersion`、`eventID`、写入序号、毫秒级时间戳 | 格式显式版本化；耗时使用单调时钟计算 |
| 会话与环境 | `sessionID`、`environmentID` | 环境快照保留当时版本、构建、渠道和必要运行条件 |
| 操作关系 | `operationID`、`parentOperationID`、模块、固定操作名 | 根操作与子操作可关联，不使用用户输入作为操作名 |
| 执行状态 | 阶段、结果、耗时、触发来源、尝试次数 | 开始与结束可对应，明确是否实际重试 |
| 请求关系 | 客户端 `requestID`、服务端 `traceID` | 两者分开；服务端标识按协议校验，缺失时如实记录 |
| 错误 | 稳定错误码、类型、domain/code、受控原因链 | 不把任意错误对象或原始响应直接序列化 |
| 上下文 | 整数、布尔、数值、受控字符串等有类型字段 | 有白名单、长度和数量上限 |
| 代码位置 | 内部文件标识、函数、行号 | 避免开发机器绝对路径 |
| 对象关系 | 账号、仓库、任务等匿名引用 | 在允许的诊断范围内一致；不使用明文身份作为默认关联键 |

### 5.2 执行链

一次根操作贯穿用户动作及其必要子阶段。例如图谱展开关联缓存读取、分页请求、合并、快照提交和渲染确认。

Swift 任务上下文可参考现有 [LocalAILogEvent.swift](../../../Starcat/Features/AI/LocalAI/LocalAILogEvent.swift) 中的 `LocalAILogContext`。跨回调、独立任务和 Swift/JavaScript 边界需显式携带关联信息，不能假设上下文总能自动传播。

根操作与关键子操作必须有明确终态。导出时仍未结束的任务列出当前阶段、持续时间和最后更新时间；没有结束事件只能说明状态未闭合，不能直接认定崩溃。

### 5.3 错误与文案

诊断使用稳定错误码和固定技术描述，用户提示继续本地化。`DecodingError` 保留安全 codingPath，数据库错误保留类型和结果码，不附带 SQL 绑定参数。

同一底层失败可被多个层级观察，但应使用关联错误身份，避免在报告里被计算成多个独立根故障。

## 6. 模块接入矩阵

| 模块 | 必须采集的内容 |
| --- | --- |
| 启动与数据库 | 启动阶段、打开/切库/迁移结果、迁移版本、失败位置、是否保留旧状态 |
| GitHub 登录 | 登录、恢复和刷新阶段，权限状态，Keychain 操作结果，刷新后请求结果 |
| Direct 授权与订阅 | 操作类型、安全业务错误码、HTTP 状态、服务端 trace、冷却/尝试结果、上次验证状态 |
| GitHub 与自建 API | 服务类别、方法与路径模板、请求尝试、耗时、状态码、业务结果、解码位置、限流信息 |
| Stars 同步 | 触发来源、分页进度、拉取/合并/新增/删除数量、失败阶段、取消原因、最终结果 |
| 关注与关注者图谱 | 接口总数、缓存数、去重数、分页状态、展示预算、渲染数、按钮判定、快照版本 |
| README 与 WebView | 内容来源、缓存年龄、加载阶段、导航错误、脚本安全错误摘要、渲染确认、内容进程状态 |
| AI 与本地模型 | Provider 类别、请求阶段、首个输出等待、流式结束原因、模型加载/下载/推理结果 |
| RAG 与 Agent | 索引与检索阶段、命中数量、执行阶段、工具结果、权限拒绝、Runtime 退出原因 |
| 每日热点、Linux.do、推荐、周刊等 | 来源、缓存年龄、刷新阶段、响应/展示数量、过滤原因、解析结果 |
| MCP、CLI 与扩展连接 | 启用状态、启动/连接阶段、协议版本、端口与权限结果、断连原因 |
| 设置与文件访问 | 关键安全设置状态、授权目录是否可访问、保存失败阶段，不记录完整路径或秘密值 |

网络采集接入已有客户端和传输入口，保持鉴权、重试和流式语义。不能为了记录日志额外发起授权激活、业务写入或重复计费请求。

HTTP 成功不等于业务成功，必须覆盖 GraphQL errors、业务 envelope 和解码失败。网络分段耗时按当前系统、会话和协议实际提供的字段采集，缺失值标记为未知，不能填零。

状态快照优先复用已有状态和缓存，携带来源、采集时间及更新时间。导出不隐式启动全量同步、业务修复、全库扫描或远端健康检查；主动检查应由独立用户动作触发。

## 7. 重点故障证据标准

### 7.1 图谱人数与按钮状态

对“总数 87、只显示 78、没有更多按钮”的验收样例，应能够查询：

- 接口总数及来源时间，关系缓存的来源与新鲜度
- 接口是否还有下一页，分页游标是否存在，不导出原始敏感游标
- 本次获取数量、合并与去重后数量
- 展示预算、节点容量、裁剪数量及限制原因
- Swift 快照提交数量、JavaScript 收到版本和绘制确认数量
- 当前选择版本、按钮显示状态、禁用或隐藏原因
- 是否刷新，刷新后的结果和人数差异

87 与 78 的差异先作为观测事实保留。只有结合来源、分页和渲染阶段，才能区分接口口径、缓存、分页、容量限制与绘制问题。

### 7.2 授权与服务端异常

关联客户端操作、请求、HTTP 状态、安全业务错误码、服务端 trace 和后续结果。报告准确区分“请求失败”“收到业务拒绝”和“本地权益仍保留”等状态。

客户端未收到的上游根因不得推测为确定事实。服务端 trace 缺失或无法关联时，将其作为证据缺口列出；本专题不自行部署后端变更。

### 7.3 外部程序不可用

区分未配置、路径失效、不可执行、渠道不提供、版本不支持、版本探测超时和异常退出。候选路径以类别或匿名引用表示，记录拒绝原因汇总。

stdout / stderr 不自动原样打包；仅允许提取受控错误码和有界安全摘要，过滤内容型输出。

### 7.4 功能卡住但没有报错

通过开始/结束事件和当前操作快照，展示任务阶段、持续时间、最后进度和必要资源状态。超时判断沿用具体业务约束，避免用统一时长把所有长任务判为故障。

## 8. 存储、聚合与留存

### 8.1 后台串行写入

统一入口同步完成轻量入队与序号分配，后台单一写入者负责编码、落盘和轮转。队列设置条数与载荷上限，避免每条事件独立创建无限量 Task。

可以借鉴 [LocalAILogStore.swift](../../../Starcat/Features/AI/LocalAI/LocalAILogStore.swift) 的有界队列和 FIFO 屏障；不要求把已有独立日志存储全部合并。

### 8.2 重复聚合

重复错误保留发生次数、首次与最后时间、有界原因样本和操作关联。不同原因不能只因文案相同就被合并。

每次用户操作的关键开始、结束和请求结果仍需保留，避免聚合后失去因果链。故障分组统计与原始事件保留策略分别定义。

### 8.3 初始参数

| 项目 | 建议值 |
| --- | --- |
| 常规留存 | 最长 14 天，同时受容量限制 |
| 新诊断存储及自管附件 | 合计最多 50 MB |
| 增强复现 | 15 分钟自动结束，额外数据最多 20 MB，计入上述总额 |
| 默认导出范围 | 最近 24 小时事件，加实际留存范围内的故障汇总 |
| 精确导出 | 指定故障或时间段，补入保留范围内的关联操作 |

以上为建议值，不是已经测量得到的性能结论。既有本地 AI 等独立日志仍遵循原容量与清理约束；导出只读取有界窗口，不让新存储替其他模块清理源文件。

容量不足时优先淘汰低价值记录，保留可用的故障证据；无法保留的内容必须计数并说明。到达上限可能使实际覆盖少于 14 天。

### 8.4 采集健康

单独维护队列丢弃、文件写入失败、磁盘不足、轮转失败及最近成功写入状态。日志系统不能递归记录自身失败形成风暴，也不能把写入失败吞掉后输出“无异常”。

## 9. 诊断包设计

### 9.1 文件布局

```text
starcat-diagnostics/
  report.md
  manifest.json
  events.jsonl
  sessions.json
  environment.json
  state/
    database.json
    sync.json
    services.json
    follow-graph.json
    ai-runtime.json
  attachments/
    local-ai/
    system-diagnostics/
  user-feedback.json
```

文件按实际采集项生成，可选反馈不存在时不创建空附件。manifest 对未生成内容说明原因。

### 9.2 可读报告

`report.md` 是开发者首读文件，包含：

1. 可选的问题描述、模块、发生时间和复现步骤
2. App 版本、构建、渠道、系统、会话及实际日志覆盖范围
3. 故障汇总、发生次数、首次/最后时间及恢复状态
4. 相关操作的时间线和最后阶段
5. 关键状态差异、重试和未闭合任务
6. 可用于继续查询后端的安全 trace
7. 证据缺失、截断、未知状态和建议补充的复现步骤

报告优先展示可证明事实。规则推断必须明确标为推断，不用生成式内容替代缺失证据。

### 9.3 完整性清单

`manifest.json` 记录格式版本、导出 ID、请求与实际覆盖范围、快照截点、文件清单和各采集项结果。

采集项状态至少区分已采集、不适用、尚未采集、权限不足、失败、超时和截断。空结果不等于无故障，缺失字段不等于零。

### 9.4 导出流程

1. 获取必要的安全状态快照，每个模块记录自己的采集时间与版本
2. 等待截点前已入队事件完成写入，生成日志一致快照
3. 在后台生成报告、manifest、附件和压缩临时产物
4. 完整生成后替换目标文件，避免预先删除已有 ZIP
5. 返回导出结果，仅清理本次临时目录

日志截点保证到某个序号的记录完整，不承诺所有业务状态全局原子一致。导出同时产生的新事件继续进入正常存储。

单个采集器有时间预算，失败不阻止其他内容导出。压缩失败时尽可能提供基础文本报告；不能宣称已经生成完整 ZIP。

## 10. 用户入口

### 10.1 常规导出

保留设置和已有菜单入口。问题模块、发生时间与现象可选填写，不因用户无法准确描述而阻止导出。

默认范围自动选择，更多时间范围和附件信息放在必要的补充选项中。用户界面不暴露内部事件 schema 等实现细节。

### 10.2 导出相关诊断

在合适的错误入口带入当前操作和失败信息，减少用户定位问题时间的负担。可提供报告编号或复制安全摘要，编号只能用于定位本地报告，不能暗示文件已上传。

### 10.3 增强复现

提供“记录一次问题复现”，开始后提高安全阶段记录与状态采样密度。用户可手动结束并导出，到期自动停止。

增强模式沿用相同隐私规则，不增加输入、回答或原始网络正文采集。用户没有开启增强模式时，常规证据仍应可用。

### 10.4 原生交互与本地化

沿用 [DESIGN.md](../../../DESIGN.md) 和现有设置页模式，独立操作按钮右对齐，复用关闭与复制反馈组件。导出进度与取消结果明确，文件处理不阻塞主线程。

新增文案按实施时实际支持语言集合完成覆盖、占位符和资源检查，AI 译文保留真实审核状态。

## 11. 隐私与数据边界

### 11.1 默认允许

版本与构建、渠道、系统类别、必要配置状态、数量、耗时、稳定错误码、缓存来源、受控技术诊断字段和匿名对象关系。

配置采用显式白名单，不导出整个 UserDefaults、进程环境或全部设置对象。关联所需的匿名标识不能作为跨用户跟踪用途。

### 11.2 默认禁止

- Token、API Key、Cookie、License Key 和授权头
- AI 提问、回答、思考、完整会话和工具正文
- 私有笔记、README 正文、原始数据库和 SQL 绑定参数
- 未经筛选的请求、响应、Provider 调试交换和进程输出
- 完整用户目录、文件路径、邮箱及默认明文账号/仓库身份

自定义 endpoint 默认保留协议、端口、路径模板和匿名服务引用等必要特征；需要完整地址时由用户明确补充。截图由用户自行选择提供，不自动截屏。

### 11.3 两道校验

生产点先限制字段并在落盘前脱敏，导出阶段再做完整性与敏感内容校验。URL、数据库错误、服务端 envelope、系统附件分别制定安全提取规则，正则仅作为补充。

既有 AI HTTP 调试、RAG 和 Agent Trace 不直接加入默认包。优先提取阶段、数量、结果码和耗时，避免正文通过 detail 或 error message 进入附件。

## 12. 系统诊断与降级能力

### 12.1 系统附件

对实际收到且允许导出的系统诊断，保留有效的异常、时间范围和调用栈等技术字段，经过专门的路径和隐私处理。关联对应构建信息，供开发者配对符号文件分析。

按当前最低系统与 SDK 能力实现并验证，不依赖用户机器一定交付某类报告。未收到、未支持或处理失败时，在包中明确说明。

### 12.2 启动与异常结束

尽早初始化基础诊断，不依赖业务数据库、登录或 Keychain 成功。保留启动阶段和现有启动失败导出入口。

上次会话没有正常结束记录时标记“结束原因未知”，附最后阶段；不能仅凭结束标记缺失就认定发生崩溃。

### 12.3 应急导出

应用无法进入界面时，提供有明确使用说明的本地应急导出工具，只收集本 App 允许的诊断目录和基础资料，不要求打开业务数据库。

App Store / Direct 的容器、路径和访问限制分别验证。访问不到的内容需提示用户选择相关文件或说明缺失，不绕过系统权限。

## 14. 实施批次与格式切换

| 批次 | 交付范围 | 批次验收 |
| --- | --- | --- |
| 第一批 | 事件与上下文、错误规则、后台写入、聚合、快照基础 | 一次模拟用户操作完整还原，取消/失败/恢复正确分类 |
| 第二批 | 启动/数据库、登录/授权、网络、Stars 同步、图谱与 AI 请求 | 主要故障具有请求、阶段、状态和恢复证据 |
| 第三批 | 可读报告、manifest、其余模块、状态快照、统一导出入口 | 普通用户可导出，开发者可读并按关联查询 |
| 第四批 | 系统附件、应急导出、增强复现、隐私与性能收口 | 特殊故障可取证，缺失与能力边界明确 |

每批应包含必要测试和可审查结果，不能等到第四批才检查隐私或数据完整性。完整专题交付须满足全部保留范围与最终验收，第一批底座完成不代表专题完成。

新格式显式版本化，新事件统一写入新格式。历史 JSONL 保留为旧格式证据，在导出时标注其字段和关联能力限制，不伪造历史会话或操作信息，不长期双写两套事件 API。

实施前按 [Git 分支与 Worktree 规范](../../5-规范/Git-分支与Worktree规范.md) 核对实际工作区，保留其他任务改动；按 [任务录入规范](../任务录入规范.md) 核对正式任务关联。本文内的清单编号仅用于专题追踪，不代表已经创建远端任务。

## 15. 验收与交付

### 15.1 真实故障场景

| 场景 | 诊断包必须提供的结果 |
| --- | --- |
| 图谱 87/78 | 总数来源、分页、缓存、展示限制、渲染确认和按钮判定依据 |
| 连续授权 502 | 每次实际请求、汇总次数、安全错误码、服务端 trace、后续恢复状态 |
| 页面切换导致取消 | 记录已知取消原因，不误报为数据库损坏 |
| CodebaseMemory 不可用 | 区分未安装、路径/执行权限、版本和探测失败 |
| README 空白 | 判断内容获取、文档组装、导航、脚本或渲染确认停在哪个阶段 |
| AI 无输出 | 请求是否发出、是否收到首个输出、结束/取消/超时的实际阶段 |
| 部分采集失败或磁盘不足 | 其余证据可用，缺失和丢弃情况明确 |
| 导出期间持续写入 | 截点前事件完整，截点后事件继续正常记录 |
| 启动失败或异常结束 | 可用的启动阶段、上一会话最后状态及未知原因边界 |

### 15.2 必要验证

- 规则与关联：未知错误、业务失败、取消、嵌套操作、请求尝试和恢复归属
- 存储：并发、有界队列、聚合、轮转、跨会话、截点、写入失败和部分损坏
- 导出：文件契约、报告引用、采集状态、超时降级、失败不破坏已有文件
- 隐私：敏感样本不进入落盘记录、报告、设置快照和附件
- 性能：常开开销、长时间运行、日志风暴、有界内存和磁盘、导出期间界面响应
- 渠道：App Store / Direct 的路径、权限、功能差异和最低系统能力
- 界面与本地化：导出、取消、失败、增强到期和长文案布局

单测与双渠道构建统一使用项目 Makefile；新增 Swift 文件遵循 xcodegen 流程。跑测前确认 Xcode IDE 已关闭，保留测试环境对 Keychain 和系统授权调用的门控。真实 GUI 验收单独记录证据，使用 Computer Use 前仍须明确授权。

最终交付包括代码与针对性测试、可读示例诊断包、开发者分析工具、应急导出说明、实测结果和已知限制。专题关闭时按当前项目规范处理主进度与任务状态，写入功能实现总览仍须事先确认。
