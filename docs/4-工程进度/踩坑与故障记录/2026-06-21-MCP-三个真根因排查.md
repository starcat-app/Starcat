# MCP 三个真根因排查（2026-06-21）

> **本文是 30s timeout 修复后的下一棒排查文档**。30s timeout 修了之后，端到端
> 模拟 + Claude 客户端实测发现：MCP 协议层有 3 个独立 bug 让 Claude **完全无法使用工具**。
> 本文**只做根因分析 + 实测证据**，不写修复方案——修复方案是下一棒。
>
> 30s timeout 修复的过程见 `功能实现总览.md` §0.3「MCP 30s timeout 修复
> （macOS 26 IPv4/IPv6 listener mismatch）」。

---

## 0. TL;DR

修完 30s timeout 后，**MCP 客户端能连上、能 initialize、能收到 serverInfo**。但端到端
模拟 4 步（initialize / notifications/initialized / tools/list / tools/call）暴露
**3 个独立根因**：

| ID | 根因 | 实测证据 | 严重度 |
|----|------|----------|--------|
| D-33 | `tools/list` 返回 0 tools | HTTP 200 + `{"result":{"tools":[]}}` | 中（Claude 看不到任何工具） |
| D-34 | `tools/call` 返回 "MCP registry is unavailable" | HTTP 200 + `isError: true, "MCP registry is unavailable."` | 中（即使看到工具也调不通） |
| D-35 | 重连时 -32600 "Server is already initialized" | 第二次 initialize 收到 -32600 + data.detail="Server is already initialized" | 低（单次连接能通，重连失败） |

D-33 + D-34 **同源**（都是 `StarcatMCPToolRegistry` 被 ARC 释放导致 handler 闭包 `[weak self]` 拿不到）。D-35 独立（SDK `Server` 状态机问题，私有状态没法重置）。

## 1. D-33 根因：`tools/list` 返回空数组

### 1.1 实测证据

```bash
curl -X POST http://127.0.0.1:5551/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer <token>" \
  --data-raw '{"jsonrpc":"2.0","id":99,"method":"tools/list"}'
```

实测响应（2026-06-21 02:25，Starcat PID 96212）：

```json
{"id":99,"jsonrpc":"2.0","result":{"tools":[]}}
```

**应该返回 12 个 tool**（`starcat.search_repos` / `starcat.semantic_search` /
`starcat.get_repo` / `starcat.get_readme` / `starcat.list_tags` /
`starcat.get_repo_note` / `starcat.upsert_repo_note` / `starcat.set_repo_status` /
`starcat.create_tag` / `starcat.add_repo_tags` / `starcat.remove_repo_tags` /
`starcat.set_repo_tags`），见 `Starcat/Features/MCP/StarcatMCPToolRegistry.swift:67-196`
的 `private var tools: [Tool] { [...] }` 静态计算属性。

### 1.2 代码定位

**handler 注册**（`StarcatMCPToolRegistry.swift:24-30`）：

```swift
func register(on server: Server) async {
    await server.withMethodHandler(ListTools.self) { [weak self] _ in
        guard let self else { return .init(tools: []) }   // ← 关键
        return await MainActor.run {
            .init(tools: self.tools)
        }
    }
    // ... 其他 handler 也都是 [weak self] 模式
}
```

**handler 被 SDK 持久化在 `Server.methodHandlers` 字典**（SDK `Server.swift:341-345`）：

```swift
public func withMethodHandler<M: Method>(
    ...
) {
    methodHandlers[M.name] = TypedRequestHandler { (request: Request<M>) -> Response<...> in
        // 闭包被存进 methodHandlers，后续每次 dispatch 都查这个 dict
    }
}
```

### 1.3 根因链（按时间线）

1. 用户在设置页**打开** MCP 开关
2. `StarcatMCPService.refreshForCurrentSettings()` 调 `start()`（`StarcatMCPService.swift:98-163`）
3. `start()` 在 `Task { @MainActor in ... }` 里**局部构造** registry（`StarcatMCPService.swift:132`）：
   ```swift
   let registry = StarcatMCPToolRegistry(facade: facade, writeFacade: writeFacade)
   ```
4. `await registry.register(on: server)` 把 handler 闭包（持有 `[weak self]` 指向
   registry 实例）注册到 `server.methodHandlers`
5. **Task 闭包返回** —— `let registry` 这个**局部变量**的强引用**消失**
6. registry 实例的引用计数**归零**（除了 handler 闭包里的 `[weak self]` 弱引用）
7. **ARC 立即释放 registry 实例**
8. 后续每次 `tools/list` 请求到达：
   - SDK 通过 `methodHandlers["tools/list"]` 找到 handler
   - handler 闭包内 `[weak self]`（指 registry）**拿到 nil**
   - 进 `guard let self else { return .init(tools: []) }` 短路
   - 返回**空数组**

**关键证据**：`StarcatMCPService` 类的**字段列表里没有 `registry`**——

```
$ grep -n "registry" StarcatMCPService.swift
132:let registry = StarcatMCPToolRegistry(facade: facade, writeFacade: writeFacade)   ← 局部变量
141:await registry.register(on: server)                                                ← 函数内使用
```

整个 `StarcatMCPService` 类（line 17-216）只有 `server` / `transport` /
`httpServer` 三个 `var` 字段（line 32-34），**没有任何地方把 `registry` 存进字段**。
所以 Task 闭包返回后，registry 唯一的强引用消失，ARC 立即回收。

### 1.4 旁证

`StarcatMCPService.swift:43-54` 的 `init()` 参数列表**有** `facade` 和
`writeFacade`，但**没有** `registry`：

```swift
init(
    settings: AppSettings,
    entitlementGate: EntitlementGate,
    tokenStore: StarcatMCPTokenStore = StarcatMCPTokenStore(),
    facade: StarcatMCPFacade,
    writeFacade: StarcatMCPWriteFacade,
    notificationService: ReleaseNotificationService? = nil
)
```

`init` 收到 `facade` / `writeFacade` 后立刻存进 `self.facade` / `self.writeFacade`
（line 28-29），但 `registry` 没在 init 构造、也没在 init 收到——再次证明
registry 是**有意识设计成"start 时按需构造、Task 结束就释放"**的临时对象。

### 1.5 反证（如果根因是其他）

- **不是** SDK 拒请求（HTTP 200 + 合法 JSON-RPC response，handler 走到了）
- **不是** validator 拒（实测带 `Accept: application/json, text/event-stream`
  跟 SDK 默认 `AcceptHeaderValidator(mode: .jsonOnly)` 兼容，line 101-111
  `case .jsonOnly: guard hasJSON` 满足）
- **不是** 字段名错（`tools` 是 SDK 标准的 `ListTools.Result.tools`，跟
  `StarcatMCPToolRegistry.tools` 同名但作用域不同）
- **不是** JSON 序列化失败（响应合法 JSON）

## 2. D-34 根因：`tools/call` 返回 "MCP registry is unavailable"

### 2.1 实测证据

```bash
curl -X POST http://127.0.0.1:5551/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer <token>" \
  --data-raw '{"jsonrpc":"2.0","id":99,"method":"tools/call","params":{"name":"starcat.search_repos","arguments":{}}}'
```

实测响应（2026-06-21 02:25）：

```json
{
  "id": 99,
  "jsonrpc": "2.0",
  "result": {
    "content": [{"text": "MCP registry is unavailable.", "type": "text"}],
    "isError": true
  }
}
```

### 2.2 代码定位

`StarcatMCPToolRegistry.swift:32-37`：

```swift
await server.withMethodHandler(CallTool.self) { [weak self] params in
    guard let self else {
        return .init(content: [.text(text: "MCP registry is unavailable.", annotations: nil, _meta: nil)], isError: true)
    }
    return await self.callTool(params)
}
```

**"MCP registry is unavailable." 这串文案是精确匹配**——直接证明 `[weak self]`
拿到 nil 触发了 `guard let self else` 分支。

### 2.3 根因链

**与 D-33 完全同源**——同一份 `[weak self]` 模式、同一份 Task 闭包结束释放
registry 局部变量。D-33 / D-34 实际是**同一个 bug 的两个症状**：
- `tools/list` handler 返回空数组（D-33 症状）
- `tools/call` handler 返回 "MCP registry is unavailable"（D-34 症状）

### 2.4 旁证

`ListResources` / `ReadResource` 两个 handler 也都是 `[weak self]` 模式（line
39-64），按同样逻辑**也会失效**——但这两个没有 D-33 那种"空数组也能响应"的退化
路径，会直接走 `guard let self else { throw MCPError.internalError(...) }` /
`return .init(resources: [])`，实测应该是空数组 + 抛错。

## 3. D-35 根因：重连时 -32600 "Server is already initialized"

### 3.1 实测证据

第一次 initialize（成功，HTTP 200）：

```json
{"id":1,"jsonrpc":"2.0","result":{
  "capabilities":{"resources":{"listChanged":false},"tools":{"listChanged":false}},
  "instructions":"Expose Starcat starred repository context to local agents. ...",
  "protocolVersion":"2025-03-26",
  "serverInfo":{"name":"starcat","title":"Starcat","version":"0.1.0"}
}}
```

第二次 initialize（被拒，HTTP 200 + JSON-RPC error）：

```json
{
  "id": 1,
  "jsonrpc": "2.0",
  "error": {
    "code": -32600,
    "data": {"detail": "Server is already initialized"},
    "message": "Invalid Request: Server is already initialized"
  }
}
```

Claude 客户端的体感错误：

```
Failed to reconnect to Starcat: -32600 at http://127.0.0.1:5551/mcp
```

### 3.2 代码定位（SDK 内部）

**字段定义**（SDK `Server.swift:174-175`）：

```swift
/// Whether the server is initialized
private var isInitialized = false
```

**状态机入口**（SDK `Server.swift:923-958`，`Server.start(transport:)` 内部
`registerDefaultHandlers` 调用）：

```swift
withMethodHandler(Initialize.self) { [weak self] params in
    guard let self = self else {
        throw MCPError.internalError("Server was deallocated")
    }

    guard await !self.isInitialized else {
        throw MCPError.invalidRequest("Server is already initialized")    // ← 关键
    }
    // ...
    await self.setInitialState(...)                                       // ← 把 isInitialized 置 true
    return Initialize.Result(...)
}
```

**状态写入**（SDK `Server.swift:960-970`）：

```swift
private func setInitialState(
    clientInfo: Client.Info,
    clientCapabilities: Client.Capabilities,
    protocolVersion: String
) async {
    self.clientInfo = clientInfo
    self.clientCapabilities = clientCapabilities
    self.protocolVersion = protocolVersion
    self.isInitialized = true                                             // ← 单向递增，无 reset
}
```

### 3.3 根因链

1. 第一次 `initialize` 请求到达
2. SDK `Server.swift:928` 检查 `!self.isInitialized` —— 第一次是 `false`，通过
3. `setInitialState` 把 `isInitialized` 置 `true`（**单向递增，无 reset 入口**）
4. **第二次** `initialize` 请求到达（同一 server 进程内）
5. SDK `Server.swift:928` 再次检查 `!self.isInitialized` —— 这次是 `true`
6. **直接抛** `MCPError.invalidRequest("Server is already initialized")`
7. SDK 把错误包成 JSON-RPC `-32600` 响应

### 3.4 根因性质：SDK 设计层限制

`Server` 是 `public final actor`（SDK `Server.swift:48`），其内部状态机字段
**全部是 `private`**：

```
$ grep -n "isInitialized\|clientInfo\|clientCapabilities\|protocolVersion" SDK/Server.swift
174:/// Whether the server is initialized
175:private var isInitialized = false
176:private var clientInfo: Client.Info?
177:private var clientCapabilities: Client.Capabilities?
178:private var protocolVersion: String?
```

`Server` **不暴露任何 reset / restart / reconnect 入口**——

```
$ grep -n "func reset\|public func.*reset\|reset.*state\|unregisterHandler" SDK/Server.swift
（0 matches）
```

**可用的关闭接口**：

- `Server.stop()`（SDK `Server.swift:278-293`）：**只取消 `task` + 清空
  `pendingRequests` + 调 `connection?.disconnect()`，**不动 `isInitialized`**
- `Server.waitUntilCompleted()`（line 295-297）：只 await 现有 task
- **没有** `Server.reset()` / `Server.restart()` / 任何把 `isInitialized` 置 false 的方法

### 3.5 旁证：Server 是 actor 且方法全是 actor-isolated

`Server` 是 `actor`，所有方法默认 actor-isolated。Starcat 即使想用 `Task` + 反射
强行写 `isInitialized`——Swift 反射 API 不支持写 `private` 字段，**编译器层面
就没法绕过**。

### 3.6 用户影响

- **单次连接**（Claude 启动后第一次连）：能 initialize、能列工具、能调工具
- **断线重连**（Claude 切网络 / 切代理 / idle 超时 / 主动 reconnect）：被拒
  -32600
- **MCP 服务重启**（用户在设置页关→开 MCP 开关）：因为 `StarcatMCPService.stop()`
  → `start()` **会重新构造** `server` 实例（line 122 `let server = Server(...)`）
  → 新 server 实例 `isInitialized = false` → 重连成功

所以 D-35 的用户体感是：**Claude 偶发报 "reconnect failed"**，需要用户在
Starcat 设置页关→开 MCP 开关才能恢复。

## 5. 与之前猜测的差异

### 5.1 Accept header 头问题（已排除）

之前怀疑 D-33 / D-34 是 SDK `AcceptHeaderValidator` 太严导致请求被拒。
**实测排除**：补齐 `Accept: application/json, text/event-stream` 头后，请求
正常进入 handler（HTTP 200 + 合法 JSON-RPC response），但 handler 返回 0 tools。
**SDK 默认的 `AcceptHeaderValidator(mode: .jsonOnly)` 兼容 `application/json`
和 `application/json, text/event-stream` 两种 Accept 头**（SDK
`HTTPRequestValidation.swift:101-111`），不是问题。

### 5.2 MCP 规范对 Accept 的要求

MCP Streamable HTTP 规范要求客户端**必须**发
`Accept: application/json, text/event-stream`。SDK `jsonOnly` 模式只校验
`hasJSON` 兼容性，**比 spec 宽松**——这是 SDK 的实现选择，不是 bug。Starcat
不需要改。

### 5.3 Pro 门控漏开（已排除）

之前怀疑 D-33 / D-34 / D-35 是 Pro 没开导致 `validate()` 403 拒。**实测排除**：
- Pro 门控**只影响 `StarcatHTTPServerError.forbidden` 响应**（HTTP 403 + JSON body
  含 "Pro subscription required"），不会让 handler 拿到空列表
- 实测响应是 HTTP 200 + 合法 JSON-RPC + tools:[] / "MCP registry is unavailable"
  / "Server is already initialized"，**全部合法 JSON-RPC 响应**，不是 403

## 6. 修复方向（不写具体方案）

> ⚠️ **本文只做根因分析 + 证据收集**。具体修复方案涉及 trade-off（重建 server vs
> 改造 SDK vs 改 wrapper），需要 dong4j 拍板。下一棒文档再做。

### D-33 + D-34（同源）修复方向

核心矛盾：`StarcatMCPToolRegistry` 实例必须在 `server` 生命周期内**一直存活**，
否则 handler 闭包里的 `[weak self]` 拿不到。

候选方向：
1. 把 `registry` 从 `start()` 局部变量提升为 `StarcatMCPService` 实例字段（最简）
2. 改 handler 闭包用强引用（破坏 `weak self` 模式，权衡 ARC 风险）
3. 把 registry 改 `actor` / `static singleton`（生命周期脱离 service 实例）

### D-35 修复方向

核心矛盾：SDK `Server` 是 `actor`，`isInitialized` 是 `private var`，**SDK 不
暴露 reset 入口**。

候选方向：
1. 每次新连接**重建 server + transport**（简单但每次连接开销大）
2. 改用 `StatefulHTTPServerTransport`（SDK 提供，但设计不同）
3. **绕过 SDK**——自建一层 handler 注册抽象，自己管理 `isInitialized` 状态
4. **fork SDK** 改 `isInitialized` 为 `internal`（不推荐，破坏升级路径）
5. **D-35 接受现状**——D-35 实际影响小（用户重连失败时引导其重启 MCP 开关）
