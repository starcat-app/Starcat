## 1. D-33 + D-34 修复策略

### 1.1 根因回顾

`StarcatMCPToolRegistry` 是 `start()` 内的**局部变量**（`StarcatMCPService.swift:132`）。
`Task { @MainActor in ... }` 闭包返回后，registry 实例的强引用消失，ARC 立即
回收。handler 闭包里的 `[weak self]` 永远拿 nil，导致：
- `tools/list` → 返回空数组
- `tools/call` → 返回 "MCP registry is unavailable"

### 1.2 策略矩阵

| 方案 | 描述 | 改动范围 | 优点 | 缺点 |
|------|------|----------|------|------|
| **A** ⭐ | 把 `let registry` 局部变量提升为 `StarcatMCPService` 实例字段 | 1 文件改 ~5 行（init + start） | 最简、最直接、与现有 `server` / `transport` / `httpServer` 字段同款模式 | registry 跟 service 同生命周期，service 释放时 registry 才释放（正确） |
| **B** | 改 handler 闭包用强引用（删除 `[weak self]`） | 1 文件改 ~4 处闭包签名 | 改动小 | 破坏 ARC 平衡模式；如果未来 StarcatMCPToolRegistry 变重会内存泄漏；跟 codebase 其他 `[weak self]` 模式不一致 |
| **C** | 把 `StarcatMCPToolRegistry` 改成 `actor` 或 static singleton | 1 文件改结构体定义 + 持有方 | 生命周期脱离 service 实例 | 改动最大；引入 `actor` 隔离会让现有 `@MainActor` 闭包迁移成本高；singleton 难测试 |

### 1.3 推荐：方案 A

**理由**：
1. **改动最小**：5 行代码（`StarcatMCPService.swift` 1 个文件）
2. **模式一致**：`StarcatMCPService` 已经有 `server` / `transport` / `httpServer`
   三个实例字段（line 32-34），加 `registry` 字段是**延续现有模式**
3. **生命周期正确**：registry 在 service 生命周期内持续存活，handler 闭包里的
   `[weak self]` 不会变 nil
4. **风险最低**：不破坏 ARC 模式、不引入 actor 隔离、不需要全局 singleton

### 1.4 改动 shape

**文件**：`Starcat/Features/MCP/StarcatMCPService.swift`

**字段区**（line 26-37 附近，新增 1 个字段）：

```
+ private let registry: StarcatMCPToolRegistry
```

**init 区**（line 39-54 附近，新增 1 行构造）：

```
+ self.registry = StarcatMCPToolRegistry(facade: facade, writeFacade: writeFacade)
```

**start() 区**（line 132 改局部变量，line 141 引用方式不变）：

```
- let registry = StarcatMCPToolRegistry(facade: facade, writeFacade: writeFacade)
+ // registry 现在是 self.registry，由 init 构造
```

`init` 收到 `facade` / `writeFacade` 时序需要保证早于 `self.registry` 构造——
按当前 init 顺序（line 28-29 先存 facade / writeFacade），构造 `self.registry`
放在 init 末尾即可。

### 1.5 验证

| 步骤 | 命令 / 操作 | 期望结果 |
|------|------------|----------|
| 1 | 编译 | `xcodegen generate` + `xcodebuild build` BUILD SUCCEEDED |
| 2 | 重启 Starcat（设置页关→开 MCP 开关） | 无 crash / MCP state = .running |
| 3 | `curl tools/list` | HTTP 200 + `{"result":{"tools":[12 个 tool]}}` |
| 4 | `curl tools/call starcat.list_tags` | HTTP 200 + `isError: false` + JSON 内容 |
| 5 | Claude 客户端实测 | Claude 能列出工具 + 能调用工具 + 返回结果正确 |

### 1.6 风险与回滚

- **风险**：registry 跟 service 同生命周期，service 释放时 registry 才释放。
  如果未来 registry 持有大量资源（如缓存、数据库连接），可能延长释放时间——
  但当前 registry 只是 `facade` / `writeFacade` 两个引用，无额外资源
- **回滚**：恢复 line 132 局部变量 + 删除 `self.registry` 字段即可，1 个文件改回来

## 2. D-35 修复策略

### 2.1 根因回顾

SDK `Server.swift:175` `private var isInitialized = false`，单次置 true 后**无
reset 入口**（`grep "func reset"` 0 matches）。第二次 initialize 走到
`Server.swift:928` `guard await !self.isInitialized else { throw ... }` 被拒。

SDK 私有字段 + actor 隔离 + 无 reset API = **SDK 层不可绕过**。

### 2.2 策略矩阵

| 方案 | 描述 | 改动范围 | 优点 | 缺点 |
|------|------|----------|------|------|
| **A** | 每次新 TCP 连接**重建 server + transport** | `StarcatMCPLoopbackHTTPServer.swift` 改 accept handler；`StarcatMCPService.start` 把 server 构造移到 accept 路径 | 每个连接 fresh `isInitialized`；彻底解决 | 每次连接构造 Server actor + 注册 handler，开销 ~ms 级；架构改动较大 |
| **B** ⭐ | 接受现状：MCP service 启动时建 server，单 service 生命周期内 server 不重建；单连接重连失败需用户重启 MCP | 0 文件改 | 0 改动；当前架构已天然支持（settings 切换触发 stop+start） | 用户切 Claude 网络 / idle 超时重连时会报 -32600 |
| **C** | Fork SDK 改 `isInitialized` 为 `internal` + 加 reset 方法 | fork SDK 包；改 SDK 1 文件 | 真正根本解决 | 破坏 SDK 升级路径；维护负担重 |
| **D** | 换 `StatefulHTTPServerTransport` | `StarcatMCPService.swift` 改 transport 类型 | SDK 官方支持 | 需要 session 管理；改动范围大；未验证是否解决 isInitialized 问题 |

### 2.3 推荐：方案 B

**理由**：
1. **0 改动**：当前架构已天然支持——settings 切换 → `StarcatMCPService.stop()`
   → `start()` → 新 `Server` 实例 + `isInitialized = false`
2. **MCP 使用场景契合**：Claude 启动后**单次连接**能完成所有工具调用；重连
   是边缘场景（切网络 / idle 超时）
3. **重连失败可恢复**：用户在 Starcat 设置页**关→开 MCP 开关**即可（已存在
   `restartForCurrentSettings()` 方法，`StarcatMCPService.swift:93-96`）
4. **无架构风险**：避免方案 A 的"每连接重建"开销，避免方案 C 的 fork 维护

**已知限制（需文档化给用户）**：
- Claude 切网络 / 长时间 idle 后重连会失败一次
- 失败时引导用户在 Starcat 设置页关→开 MCP 开关
- 长期方案：等 SDK 上游提供 reset API（可提 issue / 等版本升级）

### 2.4 改动 shape

**方案 B 0 文件改**——只需在文档里写清楚"重连失败时的用户引导"，并在
**未来用户反馈"频繁重连失败"**时升级到方案 A 或方案 C。

### 2.5 验证

| 步骤 | 命令 / 操作 | 期望结果 |
|------|------------|----------|
| 1 | 方案 B 无需代码改动，跳过编译 | — |
| 2 | Claude 第一次连接 | HTTP 200 + 工具列表 + 工具调用全部成功 |
| 3 | Claude 切网络 / 模拟重连 | 报 -32600（已知限制） |
| 4 | Starcat 设置页关→开 MCP 开关 | service 重建，新 server，Claude 重连成功 |

### 2.6 风险与回滚

- **风险**：用户偶发遇到 -32600 重连失败，需要**手动去设置页重启 MCP**
- **缓解**：未来在 Claude 报 -32600 时，给出明确引导文案"请在 Starcat 设置页
  关→开 MCP 开关"（属于 UX 层增强，不在本期范围）
- **回滚**：方案 B 无代码改动，"回滚"=升级到方案 A / C（需要后续决策）
