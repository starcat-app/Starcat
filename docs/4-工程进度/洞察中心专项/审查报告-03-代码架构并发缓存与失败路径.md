## 3. Findings

### R03-F01：旧仓库本地加载返回后可打断新仓库远端状态

- 等级：P1
- 状态：已修复
- 证据：
  - `load(repo:isAuthenticated:)` 在 `await load(repoId:)` 后没有检查 `Task.isCancelled` 或当前 `activeRepoID`。
  - `load(repoId:)` 的 generation 只阻止旧本地结果写回，不会阻止调用方继续执行后续远端阶段。
  - 五个远端加载方法进入后会先递增独立 generation 并写入 `.loading`，之后才通过 repo ID guard 丢弃缓存或网络结果。
- 触发路径：
  1. 仓库 A 的本地 Provider 较慢。
  2. 用户快速切换到仓库 B，SwiftUI 取消 A task 并开始 B。
  3. A Provider 不合作响应 cancellation，A 的 `load(repoId:)` 最后返回。
  4. A 继续启动五个远端方法，使 B 已在执行的 generation 失效，并可能把区块留在 loading。
- 修复要求：
  1. 让本地阶段返回其 generation 所有权结果，或在生产入口远端阶段前执行等价的 repo / generation / cancellation guard。
  2. 保持测试用 `load(repoId:)` 的既有 API 与本地区块隔离语义。
  3. 增加一个故意吞掉 cancellation 的旧仓库 Provider 回归测试，验证旧 task 不能启动远端请求或覆盖 B 状态。
  4. 运行 Repository Insights 定向测试和相关洞察矩阵。
- 修复 commit：`7b55c4de`（`fix(insights): 隔离快速切仓库的远端加载`）
- 验证结果：
  - `RepositoryInsightsViewModelTests` 7 项通过，新增测试使用不响应 cancellation 的 continuation 精确复现旧请求迟到。
  - Repository Insights、Star History、Metrics Client 和 My Insights 相关矩阵共 7 个 Suite、34 项测试通过。
  - 测试构建成功，`git diff --check` 通过。

## 4. 无问题项

- `MyInsightsViewModel` 用单快照协调中栏和详情栏，scope / revision / embedding model 变化由 generation 隔离；刷新失败保留旧快照。
- Repository Insights 五个远端区块各自拥有 generation、缓存和状态，单一区块失败不会清空其它区块。
- `RepositoryInsightsCache` 的 TTL 固定在 dataset 枚举，损坏 payload 只删除对应 repo / dataset / range。
- `StarHistoryViewModel` 同时使用 task cancellation 与 repo generation，Star range 独立于活动 range。
- Star History `202` 最多自动轮询三次且单次等待不超过 10 秒，之后停在 building 等待人工刷新。
- Star History Repository 保留 stale 曲线、ETag 与本地精确快照；私有仓库不调用公共 API。
- `DefaultGitHubRepositoryMetricsClient` 用显式 gate 覆盖网络 await，避免 actor 可重入导致区块并发击中 secondary rate limit。
- RAG 与洞察共用同一 Metrics Client 协议及生产实现，但各自持有独立实例；洞察缓存不进入 RAG 会话、Debug Trace 或上下文持久化。
- Repository Insights cache 与 Star History cache 使用不同表、类型和 ViewModel generation，不共享远端状态。
