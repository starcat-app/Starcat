# 审查报告 09：星标历史扫描成本复核

> 审查日期：2026-07-28
>
> 审查范围：Discovery 星标历史查询起点、BigQuery 成本护栏、专项设计、M0 与 Checklist
>
> 结论：发现并关闭 1 个 P1；真实 BigQuery M0 继续保持待授权

## 1. 发现

### R09-F01（P1）：所有仓库统一从 GH Archive 覆盖起点扫描

修复前，`starhistory.Service.build` 固定使用 `2011-02-12` 作为查询起点。HTTP handler 已经通过服务端 GitHub 请求获得 Repository `created_at`，但 `StarHistoryBuildRequest` 没有携带该字段，导致新仓库也扫描创建前的全部日表。

该行为不会影响曲线结果，却会无意义增加 BigQuery 扫描字节。仓库 Stars 数量不是计费裁剪条件，不能用“小仓库结果少”推断查询便宜。

## 2. 修复

- handler 严格解析服务端 GitHub Repository `created_at`，解析失败时不进入构建队列。
- `StarHistoryBuildRequest` 使用强类型 `time.Time` 传递可信创建时间，不新增客户端日期参数。
- worker 查询起点调整为 `max(repository.created_at UTC 日期, GH Archive 覆盖起点)`。
- 缺少创建日期的内部构建请求直接拒绝，避免未来调用方静默退回全历史扫描。
- API、README、部署配置、50 号方案、M0、追踪矩阵和 Checklist 同步记录日期边界。

## 4. 剩余边界

本轮没有执行 BigQuery dry run 或真实查询，也没有修改 `STAR_HISTORY_ENABLED=false` 的默认值。按创建日期裁剪解决单仓无效扫描，但约 2000 个收藏仓库仍可能产生大量逐仓重复查询；M0 必须对逐仓与批量方案分别估算，成本不可接受时不得开启生产 Provider。
