# 知识库 RAG 代码审查报告（第 3 轮）

> 状态: 静态复审与定向自动化验证完成；正确性、资源上界和架构技术债待按 checklist 整改。
> 日期: 2026-07-16
> 基线: `main` / `61090a7c`

## 1. 审查范围与结论

本轮重新核对索引构建、chunk Repository、Meilisearch/Qdrant 同步、附件入口、Planner/Service、会话持久化、会话切换缓存、Debug 文件存储与工作台运行态。重点确认 2026-07-15 大量会话和流式性能改动后，上一轮 checklist 是否仍与当前代码一致。

当前没有发现可由静态代码直接确认的新增 P0 数据损坏或必现崩溃。会话切换、历史窗口化和流式渲染已有明显改善，Meilisearch SQL 缺陷也已修复；但 Embedding 旧请求覆盖新内容的正确性风险仍未关闭，索引构建和会话缓存仍存在明确的资源上界问题，因此不能跳过正确性整改直接宣布 RAG 收尾完成。

## 2. 已确认完成或失效的旧项

- `RAGChunkRepository.fetchKeywordSearchableChunks` 已正确展开 SQL placeholders，`KnowledgeRAGCoreTests.keywordSearchableChunksExpandRepositoryPlaceholders` 覆盖批量 repo 回归；SQL 缺陷关闭，`fallbackToSQLite` 开关语义拆为独立测试补口。
- 会话选择已使用 generation 门闩和容量为 24 的 LRU 展示缓存，历史 UI 只投影最近轮次；旧的“切换会话等待 Debug/完整历史布局”问题不再按原路径成立。
- v10 `pinned_at` 通过独立 migration 增量落地，没有回写已发布的 `v7-knowledge-rag`。
- 当前真实文件选择器仅接受文本、Markdown、JSON 与源码。PDF/图片仍存在于底层处理器的未接入分支，但不是当前产品能力，也不再作为收尾验收项。

## 3. P1：正确性与能力边界

| 编号 | 问题与证据 | 风险 | 整改方向 |
|---|---|---|---|
| P1-01 | `KnowledgeRAGIndexBuilder` 异步请求 Embedding 后，`markEmbeddingReady` 只按 chunk id 更新，没有同时校验 `content_hash` 与 pending 状态。 | 内容在请求期间变化时，旧向量可能被写成新内容的 ready 向量。 | 增加串行化或分片 claim；写回以 id、hash、状态作条件，并补可稳定复现的并发测试。 |
| P1-02 | UI 只允许文本类附件，但专项进度、详细设计、测试方案和旧 checklist 仍宣称支持 PDF/图片。 | 验收范围错误，后续协作者可能把未接入底层分支误判为已交付能力。 | 正式范围收口为文本、Markdown、JSON、源码；PDF/图片保留为未来能力，不纳入当前 DoD。 |
| P1-03 | `RAGUserVisiblePlan`、Planner 与 Service 的固定兜底仍有硬编码中文。 | 英文环境可能泄漏固定中文，违反项目 i18n 规范。 | 固定产品文案统一走 `Localizable.xcstrings`；模型生成内容不翻译。 |
| P1-04 | 外部搜索与索引同步已按 `fallbackToSQLite` 分支，但缺少开关开启/关闭时的错误语义回归测试。 | 后续重构可能把显式失败吞掉，或在允许回退时错误中断本地链路。 | 分别覆盖 Meilisearch/Qdrant 查询与同步失败；开启时回退本地，关闭时保留外部错误。 |

## 4. P2：性能与资源上界

| 编号 | 问题与证据 | 整改方向 |
|---|---|---|
| P2-01 | Embedding 队列仍以 `limit: Int.max` 一次读取全部正文，并循环 `removeFirst`。 | 按 batch 分页读取或 claim，单独统计总数，消除数组头部搬移。 |
| P2-02 | 缺失 README 仍逐仓库串行拉取。 | 改为 2～4 个任务的有界并发，保留限流、超时、取消与稳定进度。 |
| P2-03 | `KnowledgeRAGIndexBuilder` 为 `@MainActor`，Markdown 解析和 chunk build 等纯计算仍可能占用主线程。 | 将纯计算移出主线程，只在主线程发布状态与进度。 |
| P2-04 | Meilisearch/Qdrant 同步仍按全量 `replaceAll`，Metadata-only 更新也可能触发无关向量重建。 | 合并短时间变更并按 chunk upsert/delete 增量同步。 |
| P2-05 | 单 source 刷新仍可能读取全库 Summary 或与当前 source 无关的数据。 | 按 repo/source 读取最小输入，避免单仓库刷新放大全库 I/O。 |
| P2-06 | 本地向量检索仍需扫描候选向量，缺少 1 万+ chunk 的 P50/P95、内存与取消基线。 | 先固定真实基线，再决定本地上限、索引或 Qdrant 引导；不得凭感觉改 schema。 |
| P2-07 | 回答完成、失败或取消后仍会重载完整会话及全部关联数据。 | 成功路径直接追加本轮持久化结果；全量重载只保留给切换会话与错误恢复。 |
| P2-08 | Debug 内存缓存有容量限制，但首次读取仍会枚举并解码会话全部历史 JSON，磁盘也无文件数或字节保留上限。 | 增加磁盘保留上限和分页/有界读取，保持导出与删除语义。 |
| P2-09 | 最近会话预取最多缓存 24 个完整消息、引用、大纲和远程审计快照，只有条目数上限。 | 增加总字节/消息数预算，或只预取轻量投影；以长会话记录启动 I/O 与峰值内存。 |
| P2-10 | `@repo` picker 与元数据快照仍有全量投影、重复归一化和快照过期风险。 | picker 使用轻量投影与阈值分页；元数据快照按数据修订版本缓存。 |

## 5. P2：架构与复用技术债

- `KnowledgeRAGWorkspaceViewModel` 约 3,399 行，会话运行态由多组并行字典维护；先收敛为 `[UUID: RAGConversationRuntimeState]`，保持现有 ViewModel 是唯一可观察协调器。
- `KnowledgeRAGService.ask` 继续同时承担 Planner、Retrieval、Remote Context、Prompt 与 Generation；应在 Service 内部分阶段并单测，不把 `runQuestion` 抽成第二个 God Object。
- TEI/Cohere rerank 可共享候选编号、HTTP、认证和结果映射，但保留协议 DTO，避免抽成含大量条件分支的万能 Provider。
- 工作台与知识库浏览器应共享轻量索引状态读模型，不共享各自的 UI 状态机。

先完成 P1-01 的 Embedding 写回一致性，再关闭附件/i18n 边界；随后先做可量化的资源上界与增量路径，最后收敛运行态和 Service 架构。每项必须先有失败测试或可重复基线，优化后不得改变知识库边界、隐私语义、召回结果和取消行为。
