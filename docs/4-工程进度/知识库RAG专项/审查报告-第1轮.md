# 知识库 RAG 代码审查报告（第 1 轮）

> 状态: 已完成静态审查与相关自动化测试；以下为待整改项，不代表已修改产品代码。

## 审查范围与结论

本轮覆盖 RAG 工作台、会话持久化、检索、远程上下文、附件、Prompt、Markdown 渲染及知识库浏览器。通过阅读实现及运行 `KnowledgeRAGCoreTests`、`RAGChunkRepositoryTests`、`StreamingMarkdownSnapshotTests` 完成核对，命令退出码为 0。

未发现可由静态代码直接确认的 P0 数据损坏或必现崩溃；但当前长会话、慢网络、快速切换和大知识库场景存在 7 项 P1 风险。它们足以造成卡顿、会话内容错位、无效等待或用户问题丢失，建议纳入 RAG 收尾的前置整改。静态审查与相关测试不能替代真实大数据和长时间流式问答压测。

## 已确认的正向基础

- Query Plan 有结构化解码、字段校验与范围裁剪；本地检索保持知识库边界。
- 远程上下文必须经用户确认，取消与缓存隔离已有基础；失败结果不会被写入缓存。
- keyword/vector 召回已并行，parent context 已使用批量读取，避免了该路径的 N+1。
- 调试轨迹与正常会话数据分离，Prompt 不会被持久化进普通历史。
- 已有 `StreamingMarkdownSnapshot` / `StreamingMarkdownAssembler`，具备可复用的增量 Markdown 能力。

## P1：收尾前整改

| 编号 | 问题与触发条件 | 风险 | 整改与验收 |
|---|---|---|---|
| P1-01 | `KnowledgeRAGWorkspaceViewModel.runQuestion` 每个流式 delta 都拼接完整 `String`；`RAGAssistantMessageBlock` 每次又以完整文本重建 `Markdown`。长回答会反复解析不断增长的全文。 | 主线程渲染成本接近二次增长，长回答可能明显掉帧、卡顿，放大现有布局压力。 | 抽取 RAG/AI 共用的流式 Markdown 展示器，复用 `StreamingMarkdownSnapshot`，按时间或字符阈值提交快照。以长回答压测确认滚动、取消和最终 Markdown 一致。 |
| P1-02 | `GRDBRAGConversationStore.loadConversation` 读取一批消息后，对每条消息分别读取 citation 和 remote audit。 | 长会话产生 N+1 数据库查询，切换历史和自动滚底的时序更不稳定。 | 以 message IDs 批量读取两类关联行并内存分组；为 100/200 条消息增加查询数或耗时回归测试。 |
| P1-03 | 会话列表与知识库浏览器的 `selectConversation` / `selectRepository` 均在异步加载结束后直接写 UI 状态，没有最新请求标记。快速点击 A、B 时，较慢的 A 可覆盖已经选中的 B。 | 展示错误会话或错误分片，进而让滚动、引用和用户操作指向错误对象。 | 采用可取消的 selection task 加 generation/token，只允许最新选择提交结果；延迟 mock 覆盖“先 A 后 B、A 最后返回”。 |
| P1-04 | Query Plan 对单个 remote request 有范围裁剪，但未对 request 列表去重/总量封顶；远程 provider 逐请求、逐候选串行调用，单次超时为 8 秒。 | 多资源、多仓库、慢网络时可在生成前等待很久，取消反馈和进度也不可信。 | 在确认前规范化、去重并限制总工作量；用有界并发抓取并保持输出顺序，展示真实进度与可取消状态；补慢 client、重复 request、超时测试。 |
| P1-05 | `KnowledgeRAGQueryPlanner.plan` 将认证、网络、配置等所有非取消错误都当作格式错误，重试后退化为 `semanticFallback`。 | 用户拿不到“检查 API Key/网络/模型设置”的原因；后续仍可能做无效检索，最终只得到泛化失败。 | 仅对 JSON/协议格式错误重试或降级；传输、认证、超时和配置错误转为类型化 RAG 错误，并提供重试/打开 AI 设置等明确动作；分别覆盖 401、断网和坏 JSON。 |
| P1-06 | 正常失败分支会清除刚加入内存的用户问题且已清空输入框；只有取消路径会保留/落盘。 | 附件、Provider 或生成失败后，用户需要重新输入问题，且无法直接重试。 | 失败时持久化用户问题或恢复草稿，提供“重试”“编辑后重试”；将可在前置完成的附件校验放到耗时规划前。 |
| P1-07 | 语义候选可读取最多 100,000 条 chunk；ready 检查和 vector search 都会加载完整 chunk/vector，且 repository ID 直接展开为 SQL `IN` 参数。PDF 亦会先提取所有页面文本再截断。 | 大知识库或大 PDF 下存在高内存、长等待和数据库参数规模风险；是否达到 SQLite 参数上限取决于构建配置，当前未验证。 | ready 检查改 `SELECT 1 LIMIT 1`；扫描只读取必要向量并以有界 Top-K 后再 hydrate，repo IDs 分批；PDF 边提取边累计至上限并检查取消。以 1万+ chunk、超长 PDF 压测确认峰值内存和 P95。 |

## P2：质量、可维护性与组件复用

| 编号 | 问题 | 整改方向 |
|---|---|---|
| P2-01 | Debug trace 保存完整 Prompt、历史、远程块与响应，仅在关闭/清理时释放；长调试会话会增长内存，导出也可能包含敏感内容。 | 对条数和总字节实施 FIFO 上限；导出前提示敏感内容，并提供脱敏选项。 |
| P2-02 | `RAGMarkdownText` 的 citation linkify 与间距调整是全局文本替换，未排除 fenced/inline code；与 Prompt 侧已有的 Markdown 安全扫描不一致。 | 提取共享的 Markdown 安全范围扫描器，只对可见正文做 citation 变换；补代码块、链接、转义 marker 测试。 |
| P2-03 | `RAGWorkspaceErrorSheet` 隐藏了技术细节是正确的，但所有错误几乎共用同一文案和邮件入口。 | 以类型化错误提供用户可执行的下一步：重试、打开设置、移除附件、检查网络；技术详情留在可复制的诊断信息而非正文。 |
| P2-04 | 已有 AI 流式 Markdown 组件，但 RAG 使用另一套全量重绘实现；选择请求的防竞态机制也应为 RAG 两个窗口共用。 | 在不改变视觉设计的前提下，将流式快照和 selection generation 提炼为小型共享组件/协作对象，避免双处修复后再次漂移。 |

## 测试补口与落地顺序

1. 先处理 P1-01、P1-03、P1-06：它们直接影响对话卡顿、选错会话和用户输入丢失。
2. 再处理 P1-02、P1-04、P1-05、P1-07：建立数据库、远程调用和大数据的可测上界。
3. 完成 P2 组件收敛与错误文案；随后再实施 Context Usage/语义压缩，避免在不稳定的请求链路上继续加复杂度。
4. 新增单测后关闭 Xcode，运行相关 Suite 与全量 `xcodebuild test`；最后以长会话、快速切换、断网、401、慢远程、1万+ chunk 和大 PDF 做人工压测，并记录 P50/P95、峰值内存与取消响应时间。

## 本轮边界

本报告没有修改 RAG 产品代码、数据库 schema 或用户数据。问题为代码路径审查结论；性能项须在固定设备、固定模型和脱敏真实数据集上量化后再写入具体阈值。
