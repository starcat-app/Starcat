# 精选发布台技术设计

## 1. 设计结论

精选发布台采用「AI 甄别会话 + Weekly 发布会话 + 独立管理员 API client + 单实例 Window」四层结构。实现参照 `.claude/skills/starcat-weekly-import`：先让 AI 拆分自然语言并基于开放网络证据判断，再用 GitHub 数据做事实核验；人工确认完成后，才激活 weekly-api 分类与批量导入。

客户端与后端职责保持清晰：Starcat 负责甄别、证据审阅和人工选择，weekly-api 负责管理员鉴权、动态分类、批次处理和同来源仓库去重。

## 2. 模块与职责

Agent 识别的逐阶段 Prompt、工具预算、防幻觉、人工复核和隐私边界详见 [`Agent-项目识别机制详解.md`](Agent-项目识别机制详解.md)。

```text
Weekly toolbar
    └─ CuratedPublisherAccessPolicy（入口权限）
        └─ Window(id: curated-publisher)
            └─ CuratedPublisherView（三栏编排）
                ├─ CuratedProjectIdentificationSession（输入、AI 进度、复核、入选集合）
                │   └─ CuratedProjectIdentificationService
                │       ├─ DefaultCuratedProjectAIReasoner
                │       ├─ ExternalSearchWebProvider
                │       └─ DefaultCuratedRepositoryEvidenceProvider
                │           ├─ GitHubRepositorySearchProvider
                │           └─ GitHubAPIClient（canonical + README）
                └─ CuratedPublisherSession（Weekly 连接、分类、批次与轮询）
                    ├─ CuratedPublisherAPIClient
                    ├─ CuratedPublisherCredentialStore
                    └─ UserDefaultsCuratedPublisherBatchTracker
```

### 2.1 访问策略

- 当前 allowlist 只保存稳定的 GitHub 数字用户 ID `20341123`。
- Toolbar 可见性、连接、创建分类和发布执行层都调用同一 policy。
- policy 不接触管理员密钥；未来可替换为服务端角色。

### 2.2 AI 甄别服务

- 第一阶段要求 AI 输出结构化项目项：原始文本、标题、实体类型、来源 URL、显式仓库和检索式。
- 第二阶段逐项执行开放网络检索与 GitHub Search，读取候选 README，建立可追溯证据包。
- 第三阶段由 AI 输出 `confirmed` / `needs_review` / `not_found`、仓库与理由。
- 防幻觉守卫只接受本轮已由 GitHub 核验的候选；AI 返回未知仓库时降级为 `needs_review`。
- 手工仓库地址仍走 `verify(repositoryURL:)` 的 GitHub canonical 核验，成功后才升级为 `confirmed`。
- `CuratedProjectIdentificationSession` 不持有 weekly-api client 或管理员密钥。

### 2.3 Weekly 发布会话

- `CuratedPublisherSession.bootstrap` 只读 Keychain，不访问 Weekly。
- AI 成功后，View 调用 `activatePublishing(findings:currentUserID:)`，此时才允许读取分类和恢复批次。
- `preparedFindings` 只接收已确认且被勾选的项目；发布前再次校验全部 finding。
- 状态流：`idle → connecting/creatingSource/publishing/polling → idle`。
- UserDefaults 只保存最近 batch ID；管理员密钥由独立 Keychain namespace 保存。
- 瞬时查询错误最多连续重试 3 次，达到上限后保留批次并允许手动恢复。

### 2.4 管理员 API client

- `GET /internal/sources?manual_import=true`：读取动态分类。
- `POST /internal/sources`：创建人工分类，请求包含 `code`、`display_name_zh`、`display_name_en`。
- `POST /internal/imports`：一次提交全部已确认仓库。
- `GET /internal/imports/{batch_id}`：查询批次。
- 所有请求使用 `Authorization: Bearer <admin-key>`，错误类型不得携带或打印请求 header。

### 2.5 weekly-api 去重

- 新分类落库为 `ingest_mode=manual`、`manual_import_enabled=true`、`enabled=true`，创建后可立即导入。
- 人工来源的事件键固定为 `manual:<source_code>:<owner/repo>`。
- 同一来源同一仓库即使 title、source URL 或 batch idempotency key 不同，也更新同一事件；不同来源保持独立。
- 客户端无需在识别阶段查询 Weekly 是否存在同名项目。

## 3. UI 结构

- `Window("精选发布台", id: "curated-publisher")`：单实例，三栏桌面布局。
- 左栏「收集项目线索」：AI 模型、自然语言多行输入、分阶段识别进度。
- 中栏「审阅甄别结果」：汇总指标、紧凑结果卡、证据、候选确认与手工 URL 核验；结果列表和证据区独立滚动，批量结果不会把当前证据挤出窗口。
- 右栏「分类与推送」：本机凭据状态、管理员连接、动态分类、新增分类 Sheet、批量预览和批次状态。
- 三栏将主要宽度留给审阅区；顶部只展示管理员 API 状态，模型入口固定在左栏，避免同一状态重复出现。
- AI 甄别与确认发布使用自然宽度的 `regular` 原生按钮并在栏内右对齐；异步进度和已选数量作为独立辅助状态展示，禁止用全栏宽胶囊按钮承载状态。
- 结果卡的勾选与详情切换是独立点击区，避免嵌套 `Button`。
- 文字/图标使用语义颜色；plain Button 禁用 focus ring；Sheet 使用 `SheetCloseButton`。

## 4. 数据契约

### 4.1 新增分类

```json
{
  "code": "developer_tools",
  "display_name_zh": "开发工具",
  "display_name_en": "Developer Tools"
}
```

### 4.2 批量提交

```json
{
  "source_code": "developer_tools",
  "idempotency_key": "starcat-curated-<sha256>",
  "repositories": [
    {
      "owner": "owner-a",
      "repo": "repo-a",
      "title": "项目 A",
      "source_url": "https://example.com/a"
    },
    {
      "owner": "owner-b",
      "repo": "repo-b",
      "title": "项目 B",
      "source_url": null
    }
  ]
}
```

幂等键对 `source_code + 排序后的 owner/repo 集合` 做 SHA-256，不包含输入文案与仓库顺序。

### 4.3 终态

- `success`：全部处理成功。
- `partial_success`：部分成功，必须展示 item 错误。
- `failed`：批次失败，展示服务端安全错误。
- `pending` / `processing`：继续轮询。

## 5. 测试策略

- AI 服务：自然语言拆分、外部证据、GitHub 核验、防幻觉降级、无官方仓库、非法 JSON。
- 甄别会话：确认项默认入选、候选升级、手工地址核验。
- API：admin header、来源列表、创建分类、批量提交、批次终态、401。
- 发布会话：bootstrap 零 Weekly 请求、AI 成功后激活、权限、批量提交、创建分类、轮询重试。
- 后端：分类创建校验/冲突/认证、动态分类立即导入、稳定事件键与跨来源隔离。
- UI 视觉与生产 weekly-api 真实发布属于人工验收，不用单元测试冒充。

## 6. 安全与演进

- 不在构建产物中内置 admin key。
- 不把 admin key 放入 `AppSettings`、UserDefaults、analytics 或 Logger metadata。
- 当前 allowlist 是客户端运营入口边界；weekly-api admin key 仍是服务端最终认证边界。
- 若未来面向所有用户开放，应新增服务端角色/短期令牌，不能把共享 admin key 分发给用户。
