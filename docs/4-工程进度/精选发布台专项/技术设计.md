# 精选发布台技术设计

## 1. 设计结论

精选发布台采用「现有搜索能力 + 独立管理员 API client + App 级会话 + 单实例 Window」的最小闭环。weekly-api 已具备来源目录、管理员认证、幂等导入、异步 enrich 和批次查询，本期客户端只编排这些能力，不增加后端接口。

## 2. 模块与职责

```text
Weekly toolbar
    └─ CuratedPublisherAccessPolicy（入口权限）
        └─ Window(id: curated-publisher)
            └─ CuratedPublisherView（输入、候选、预览、发布状态）
                └─ CuratedPublisherSession（状态机、执行权限、恢复与轮询）
                    ├─ CuratedProjectResolver
                    │   ├─ GitHubRepositorySearchProvider
                    │   └─ ExternalSearchWebProvider（可选降级）
                    ├─ CuratedPublisherAPIClient
                    └─ CuratedPublisherCredentialStore
```

### 2.1 `CuratedPublisherAccessPolicy`

- 当前 allowlist 只保存稳定的 GitHub 数字用户 ID `20341123`。
- Toolbar 可见性和 `Session.publish` 都调用同一 policy。
- policy 不接触管理员密钥；未来可用服务端角色实现替换。

### 2.2 `CuratedProjectResolver`

- 纯解析层先识别 `https://github.com/{owner}/{repo}` 与 `{owner}/{repo}`。
- 直接地址使用 GitHub Search 精确核验，不因 URL 形似 GitHub 就视为存在。
- 普通线索优先从 Web Search 提取 GitHub 候选，并与 GitHub Search 结果合并、按 `owner/repo` 去重。
- Web Search 不可用时捕获错误并只使用 GitHub Search。
- 最终可发布对象必须包含 GitHub API 返回的 repository candidate。

### 2.3 `CuratedPublisherAPIClient`

- base URL 复用 Weekly 自定义服务设置，否则使用 production URL。
- `GET /internal/sources?manual_import=true` 读取动态分类。
- `POST /internal/imports` 提交单仓库批次。
- `GET /internal/imports/{batch_id}` 查询批次。
- 所有请求使用 `Authorization: Bearer <admin-key>`，错误类型不得携带或打印请求 header。

### 2.4 `CuratedPublisherSession`

- 由 `AppDependencies` 持有，生命周期不依赖窗口 View。
- 状态流：`idle → resolving/verifying → idle(已核验) → publishing → polling → idle(终态或暂停)`；核验结果由 `verifiedCandidate` 单独表达。
- 任何线索、最终 URL 或候选变化都使旧核验与人工确认失效。
- 发布前依次校验用户权限、管理员连接、动态来源、官方仓库核验、人工确认。
- 幂等键对 `source_code + owner/repo + 原始线索` 做 SHA-256，避免网络重试重复入库。
- UserDefaults 只保存最近 batch ID；管理员密钥由 `CuratedPublisherCredentialStore` 保存。
- 提交成功即保存 batch ID，窗口关闭后轮询任务继续；下次打开会恢复查询。
- 瞬时查询错误最多连续重试 3 次；达到上限后保留非终态批次，由状态卡片显式恢复查询，避免服务长期不可用时无限请求。

## 3. UI 结构

- `Window("精选发布台", id: "curated-publisher")`：单实例、默认约 `1080 × 720`。
- 左栏：原始线索、识别按钮、候选列表、最终 GitHub URL、仓库预览、人工确认。
- 右栏：管理员连接、动态来源 Picker、发布预览、风险提示、主操作按钮、批次状态。
- 文字与图标只使用 `.primary` / `.secondary`；plain icon button 必须禁用 focus ring。
- 使用系统 material、Form/GroupBox/Divider 和语义色，不增加自绘窗口 chrome。

## 4. 数据契约

### 4.1 提交

```json
{
  "source_code": "ai_intelligence",
  "idempotency_key": "starcat-curated-<sha256>",
  "repositories": [
    {
      "owner": "owner",
      "repo": "repo",
      "title": "可选展示标题",
      "source_url": "https://example.com/original"
    }
  ]
}
```

### 4.2 终态

- `success`：全部处理成功。
- `partial_success`：部分成功，必须展示 item 错误。
- `failed`：批次失败，展示服务端安全错误。
- `pending` / `processing`：继续轮询。

## 5. 测试策略

- 地址解析：GitHub URL、`.git`、`owner/repo`、保留路径、非法 host。
- Resolver：直接地址精确核验、普通线索合并去重、Web Search 失败降级。
- API：admin header、路径/query、编码、成功 envelope、401 与错误 envelope。
- 权限：允许/拒绝用户，以及 publish 执行层二次校验。
- Session：编辑失效、发布守卫、幂等键稳定、提交/轮询/恢复、partial success。
- UI 视觉与真实 weekly-api 凭据验证属于人工验收，不用单元测试冒充。

## 6. 安全与演进

- 不在构建产物中内置 admin key。
- 不把 admin key 放入 `AppSettings`、UserDefaults、analytics 或 Logger metadata。
- 当前 allowlist 是客户端运营入口边界；weekly-api 的 admin key 仍是服务端最终认证边界。
- 若未来面向所有用户开放，应新增服务端角色/短期令牌，不能把共享 admin key 分发给用户。
