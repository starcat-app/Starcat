# Weekly 多来源采集专项第一轮审查报告

> 审查时间：2026-07-16
> 审查类型：功能完整性与最终方案逐条对照
> 结论：发现 7 项缺口，修复前不进入一致性审查

## 1. 审查范围

- `supports/starcat-weekly-api`：schema migration、通用来源查询、入队/Worker、HelloGitHub、人工录入、置顶、管理路由与 README；
- Starcat：bulk v2 DTO、GRDB v11、来源筛选、排序、详情、图标、i18n 与测试；
- `.claude/skills/starcat-weekly-import`：来源能力、核验、幂等、提交与密钥边界；
- `pages/_local-admin`：来源状态、回填恢复、增量同步、置顶编辑与浏览器行为；
- 正式方案、详细设计、专项 checklist 与 `docs/功能实现总览.md`。

已确认基础验证：weekly-api 83 个测试、race、vet、build 通过；Starcat 完整 `xcodebuild test` 通过；local-admin JavaScript 静态检查和 mock API 浏览器主流程通过。

## 2. 发现项

| ID | 级别 | 发现 | 影响 | 修复要求 |
|---|---|---|---|---|
| R1-01 | P1 | `WeeklyRepoDetail.events` 虽已解码，但 `WeeklyDetailScaffoldShell.loadDetail` 只使用 repo，通用来源事件未进入详情时间线。 | 最终方案 §7.3 的 `title / summary / rank / occurredAt` 通用详情没有落地，HelloGitHub 与 AI 情报只能看到一个来源跳转。 | 在详情中展示通用来源事件；切换项目时清空旧事件，并补解码/展示模型测试。 |
| R1-02 | P1 | `WeeklySourceDescriptor.localizedTitle` 使用 `Locale.current`，忽略 Starcat 的 `AppLocaleOverride`；显示名与图标 switch 仍放在 wire model。 | 用户在设置中强制 English/简体中文时动态来源标题可能跟随系统语言；来源扩展边界仍未达到 presentation resolver 设计。 | 新增独立来源 presentation resolver，按应用语言选择服务端中英文名，并补语言覆盖测试。 |
| R1-03 | P1 | Skill 输入未给 `idempotency_key` 时每次运行生成随机 UUID；dry-run 与正式提交、超时重放得到不同 key。 | 网络结果未知后重跑可能创建新批次，违背“唯一且可复用”的幂等要求。 | 对相同规范化 payload 生成稳定 key，显式 key 继续优先，并补脚本测试。 |
| R1-04 | P1 | 人工录入的 `source_url` 在 Skill 和服务端均未限制 scheme。 | 不可信文本可把任意 scheme 写入公开来源事件，客户端详情跳转边界不够严格。 | Skill 与 weekly-api 双层仅允许绝对 `http/https` URL；增加非法 scheme 测试。 |
| R1-05 | P2 | local-admin 来源行未展示 `processing` 与 `discarded`；仅有 count、pending、retrying 和 latest progress。 | 最终方案 §8.1 的队列可观测字段不完整，多次失败剔除无法直接看到。 | 补齐 processing/discarded 显示并做浏览器状态断言。 |
| R1-06 | P2 | HelloGitHub incremental/reconcile 管理响应只有临时 `task_id/status`，local-admin 仅在拿到 `batch_id` 时轮询；立即刷新可能发生在 Collector 入队之前。 | 增量与对账操作无法稳定展示实际持久化批次，页面反馈可能长期停在旧批次。 | local-admin 在无 batch_id 时短期轮询来源状态，发现新 latest batch 后转入批次轮询。 |
| R1-07 | P2 | 后端 README 仍保留“LLM 未配置时分类 pending”的已删除逻辑；bulk 文件头仍示例 schema v1；ADMIN 日志仍只称 Discovery sync。 | 文档、注释和运行日志与当前两阶段通用来源实现不一致。 | 修正文档、代码注释和日志，并重新执行文档/API 契约检查。 |

## 3. 已确认无问题项

- POST/Collector 入队事务内没有 GitHub 调用，commit 后才非阻塞唤醒；
- Worker 启动扫描、15 分钟兜底、30 分钟租约和 15/30 分钟退避符合方案；
- HelloGitHub 回填 controller checkpoint 可重启恢复，活动 controller 不会被子批次遮蔽；
- 旧三源停止双写，公开列表、facet、详情和 bulk 查询以通用来源事件为真源；
- Starcat v11 为追加 migration，没有修改已发布 migration；
- 置顶先经过筛选，再按 position 与用户排序稳定排序；
- 管理接口全部挂在独立 admin middleware，Starcat 客户端不读取 admin key；
- 未引入需登记的新三方依赖或品牌图片，HelloGitHub/AI 情报使用 SF Symbol fallback。

## 4. 本轮结论

主体架构与异步链路正确，但详情通用事件、应用内语言、Skill 幂等与 URL 安全属于必须修复项。本轮报告提交后逐项修复，每个小功能单独提交；修复并回归通过后才能勾选第一轮审查并进入第二轮跨仓库一致性审查。
