# Weekly 多来源采集专项第二轮审查报告

> 审查时间：2026-07-16
> 审查类型：跨仓库 API 契约、产品文案与工程进度一致性
> 结论：发现 6 项一致性缺口，修复前不进入最终审查

## 1. 审查范围

- 正式方案、详细设计、专项 checklist 与 `docs/功能实现总览.md`；
- weekly-api 实际路由、管理响应模型、README / README-ZH；
- Skill 主流程、API reference 与提交脚本；
- Starcat Weekly 网络层、缓存模型、详情展示、设置文案和源码注释；
- `pages/_local-admin` Weekly API Console 与专用运营面板。

本轮以实际路由和响应模型为真源，逐项对照所有消费端和文档，不重复第一轮已关闭的功能完整性问题。

## 2. 发现项

| ID | 级别 | 发现 | 影响 | 修复要求 |
|---|---|---|---|---|
| R2-01 | P1 | local-admin Weekly API Console 没有 `POST /internal/imports` 与 `GET /internal/imports/{batch_id}`，虽然专用面板和 Skill 已覆盖其他管理流程。 | 最终方案要求通用 API Console 可直接验证批量录入契约，目前运营人员无法在控制台构造和查询 AI 情报批次。 | 增加创建与查询 endpoint、默认 body 和 path 参数，并做静态契约检查。 |
| R2-02 | P1 | 详细设计仍写“来源状态优先返回 controller”和“刷新从 latest_batch 恢复活动任务”；实际响应已拆分 `latest_batch` 与 `active_backfill`。 | 文档会指导后续消费端错误覆盖最近采集批次，回退第一轮修复的状态语义。 | 明确两个字段职责以及页面恢复的选择顺序。 |
| R2-03 | P2 | Starcat 多处网络层、模型和页面注释仍称“三源聚合”，设置页描述仍只说阮一峰周刊。 | 代码阅读、设置说明与当前五个固定来源/后续动态来源能力不一致。 | 将本次涉及链路统一改为“多来源”，设置文案说明 Weekly 聚合来源。 |

## 3. 已确认一致项

- weekly-api 实际路由、正式方案与 Skill 对人工来源目录、批量提交和批次查询的路径一致；
- `SourceStatus` 已同时返回完整队列计数、`latest_batch` 和 `active_backfill`；
- bulk v2 的来源目录、通用条目与置顶字段在后端、Starcat DTO 和 GRDB 缓存中命名一致；
- 未知来源仍按 raw value 解码，客户端 presentation resolver 不依赖固定 enum；
- Starcat 客户端和公开 API key 路径均未接触 `ADMIN_API_KEYS`；
- 第一轮 7 项修复提交和回归证据均已回填。

## 4. 本轮结论

核心运行链路没有新增功能缺失，但运营控制台、详细设计、README、客户端说明和工程进度存在可验证的一致性偏差。本报告先独立提交，随后按发现项拆分修复和提交；全部回归通过后再关闭第二轮审查。
