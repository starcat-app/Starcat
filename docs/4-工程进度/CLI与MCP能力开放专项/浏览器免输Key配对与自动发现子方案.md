> 状态：需求已纳入 CLI 与 MCP 能力开放专项；以下为完善后的建议方案，实施与分批范围待确认
> 创建：2026-11-15
> 父方案：[CLI与MCP能力开放总体方案.md](CLI与MCP能力开放总体方案.md)
> 任务清单：[Checklist §6.1](CLI与MCP能力开放Checklist.md#61-浏览器配对子任务)

## 1. 需求与推荐结论

dong4j 提出：保留服务地址和 Key 的现有连接方式，新增浏览器发起配对、两端展示相同六位数字、用户在 Starcat 确认后自动取得认证凭据的方式。App 记录配对浏览器，支持单独取消配对；进一步探索自动发现，减少手动填写地址。

建议分两批：

| 批次 | 用户得到的体验 | 实现边界 |
| --- | --- | --- |
| B1：免输 Key 与本机发现 | 点击连接，优先找到本机 Starcat，核对六位码后完成连接；高级选项保留地址和 Key | 使用现有 loopback Companion 通道，增加设备级凭据、配对与有限地址发现 |
| B2：原生桥接与 CLI 接入 | 在配套桥接安装完成后免填地址，支持实际端口定位，并向外部统一经过 CLI 的目标收敛 | 单独验证 Chrome Native Messaging、Safari 原生宿主与 App Store / Direct 分发；通过后确认实施 |

这里“复用 Key 认证”建议解释为复用 `Authorization: Bearer ...` 验证方式，**新配对为每个浏览器实例签发独立 token**。自动把全局 Key 复制给每个浏览器，无法满足真正独立撤销：删除设备名称后，持有同一 Key 的客户端仍能访问。

B1 能减少默认配置下的手填；自定义端口未被发现时仍保留手动地址入口。完整免地址体验以 B2 的原生定位为目标，不能把有限端口探测宣传为能找到任意配置。

## 3. 推荐交互

### 3.1 浏览器端

1. 插件设置提供“连接 Starcat”作为主要入口，“手动设置”收起保存地址与 Key。
2. 点击连接后检查已保存地址和明确的本机候选地址；多个 Starcat 实例时显示渠道与实例标识，由用户选择。
3. 在扩展自己的设置标签页中进入“等待 Starcat 确认”，显示六位码，例如 `482 915`、请求有效期以及取消操作。
4. 提示切换到 Starcat 核对数字；用户在 App 确认后，扩展自动完成凭据保存和已认证连接验证。
5. 保存成功且验证通过才显示已连接；下一次按已配对配置重连，无需重复确认。

核对过程使用稳定的扩展标签页，避免依赖切到 App 时会消失的工具栏弹层。六位码和配对控制不放在 GitHub / Google 页面中的注入 UI，页面内容不能代替用户发起或批准配对。

首次只需在 Starcat 点一次“数字一致，允许配对”。如数字不一致，用户拒绝并重新发起；不要求手抄六位码，也不在两端重复弹确认框。

### 3.2 App 端

显示请求来源类型、浏览器名称、用户可填写的设备备注、请求时间、六位码，以及连接后可使用的现有浏览器能力；按钮为“拒绝”和“数字一致，允许配对”。

浏览器名称与备注是提示信息，不当作已经认证的身份。App 未在前台时如何提示，沿用既有 MCP 配对交互并在实施前确认，不为了自动弹窗默默增加通知权限。

只有用户明确点击连接才请求配对。App 不为每次后台发现弹窗；短时间重复请求合并，并限制待确认数量与频率，避免新增免 Key 接口造成反复弹窗。

## 4. 六位码、请求与 token

六位码是本次请求的人工核对标识，不是 API Key，也不是用它就能取得凭据的密码。参考 RFC 8628 对短用户码、长设备码、有效期与轮询的分工，但不宣称实现了 OAuth Device Flow。

建议使用以下状态与契约，具体路由名在实施设计时确定：

| 操作 | 要求 |
| --- | --- |
| 发现服务 | 只返回产品、协议支持、渠道和实例标识等最小公开信息；无 Key、账号、仓库或设备列表 |
| 发起配对 | 校验扩展来源、内容类型、请求结构和本机范围；返回请求标识、高熵领取凭据、六位码及过期时间 |
| 等待确认 | 扩展持领取凭据按服务约定间隔查询；普通网页不能凭请求 ID 或六位码读取结果 |
| App 批准 | 绑定正在展示的那一份请求和浏览器实例，签发设备专属 token；保存失败不宣称批准成功 |
| 领取结果 | 只有该请求的领取凭据可以换取结果；终态、消费与过期规则明确，防止另一个请求领走 |
| 完成连接 | 扩展保存到本地凭据存储，使用新 token 进行认证检查；失败如实提示并可重新配对 |
| 拒绝 / 取消 / 过期 | 进入终态，之后不能批准或领取；需用户重新发起 |

建议请求有效期约两分钟；具体数值与轮询间隔属于待确认参数。多个请求不得复用正在生效的显示码，重试产生新请求；请求 ID、领取凭据与六位码分别生成并绑定，展示码不承载全部认证信息。

未领取成功的短期配对结果不能永久保留可兑换状态。首版优先采用一次领取、失败重新配对的简单契约，并允许用户从设备列表删除残留记录；是否增加短期重取，需有实际恢复需求后再决定。

这是一套同机配对方案。单纯比较服务返回的六位码不能证明传输已加密，也不提供密码学意义上的中间人防护。若未来开放局域网，须先确认 TLS 与服务身份校验，不能把 loopback HTTP 原样扩到 `0.0.0.0`。

## 5. 浏览器身份与取消配对

### 5.1 身份模型

“浏览器指纹”建议落实为**浏览器配置内的扩展实例身份**，不采集 Canvas、字体列表或硬件特征。

- 扩展首次使用时生成随机实例 ID，保存在当前配置的本地存储中，不通过浏览器同步复制。
- 浏览器正常更新保留该身份；卸载扩展、清除本地存储或新建配置后重新配对。此身份不提供防止整份配置被复制的硬件绑定能力。
- App 为批准后的连接生成独立设备 ID 和 token；实例 ID 仅用于识别，不作为认证凭据。
- 列表显示浏览器类型、可编辑名称、配对时间、最近访问时间、授权范围和短设备标识。
- 如果以后使用客户端公钥，再把公钥摘要称为密钥指纹；首版随机设备 ID 的缩写不能包装成密码学指纹。
- 不同浏览器配置原则上独立配对；Safari 配置隔离及隐私浏览须实测，无法隔离时明确不支持该组合，不能共享身份后声称独立撤销。

### 5.2 撤销规则

1. App 取消配对后，拒绝该 token 的新请求，并主动终止属于该设备的事件订阅。
2. 其他浏览器和 MCP 设备继续工作，撤销不触发全局 Key 轮换。
3. 插件收到凭据失效响应后停止自动重试，显示需要重新配对，不自动退回旧 Key。
4. 插件内“取消配对”应先请求服务端撤销当前设备，再删除本地凭据。离线时只能报告“已清除本地连接，App 中的授权仍需取消”，不能谎报服务端已撤销。
5. 浏览器 token 只允许 Companion 范围，不能因共用设备存储而自动获得 MCP 全部工具权限；MCP token 也不因此自动成为浏览器凭据。

### 5.3 保留手动 Key

保留“地址 + Key”作为用户明确选择的高级连接方式。两种方式共用业务接口和认证中间层，由认证结果携带连接类型、设备身份与范围。

历史全局 Key 无法可靠区分使用它的各个浏览器，不能伪造可逐个撤销的设备记录。该模式要失效，仍需更换 Key；设备级配对的撤销仅撤销相应 token。旧用户可以主动切换新方式，切换成功后清除插件本地的旧 Key，不影响其他旧客户端。

## 6. 自动发现的选择

| 方案 | 能解决的问题 | 代价与限制 | 建议 |
| --- | --- | --- | --- |
| 已保存地址 + 有限 loopback 候选 | 默认安装和历史端口配置免手填 | 任意自定义端口无法保证发现 | B1 实施 |
| 原生桥接定位 | 不靠端口扫描，可由本机组件获取配置并接入 CLI | 需要宿主安装、浏览器适配与分发验证 | B2 优先评估 |
| App 发起的一次性连接链接 | 可携带实际地址，作为自定义配置的辅助入口 | 扩展入口、回传与渠道选择要设计；不能把长期 Key 放进链接 | 可选补充，不作为 B1 前置 |
| Bonjour / mDNS | 未来可列出局域网设备 | 发现不等于认证；跨浏览器发现能力、系统权限和远端安全通道均需验证 | 首版暂缓 |

B1 只探测当前配置、App 默认端口与必要旧端口，去重、超时并限制数量；不扫描全部端口或网段。发现请求不携带 token，也不自动接受重定向到其他主机。现有 `ping` 要求 Key，因此需要专门的最小发现接口，不能把业务 `ping` 无条件改成公开查询。

发现成功只代表找到候选服务。若已配对端口发生变化，未经认证的实例名称或 ID 不能诱使插件把旧 token 发到新地址；B1 可要求重新确认配对，B2 再通过可信原生路径处理地址更新。

App 未运行、服务未开启和端口未找到，在仅靠 HTTP 时未必能可靠区分，页面应提示可检查的步骤，不能虚构精确原因。多个 App Store / Direct 实例同时存在时让用户选择；浏览器的本地网络权限提示也应纳入真实环境验证。

## 7. 原生桥接如何与 CLI 总体架构衔接

目标链路为：浏览器扩展 → 浏览器原生适配 → CLI 连接与能力层 → App。

Chrome 官方 Native Messaging 需要注册宿主与允许的扩展来源，扩展页面 / background 调用宿主；协议是长度前缀 JSON，不能把当前按行输出的 `starcat mcp` 原样配置为宿主。建议在 CLI 中提供专用适配入口，复用连接和能力模块，不执行任意 Shell 命令。

Safari 原生消息到达其 containing app 的原生扩展，不能照搬 Chrome 的宿主注册方式。官方提供 App Groups 和按浏览器 profile 区分的原生消息信息；这些只是实现基础，不能据此认定沙盒中可以直接启动任意 CLI。

B2 在代码实施前给出 Chrome / Safari × App Store / Direct 的可行性矩阵，至少验证宿主安装与升级、App 移动路径、端口定位、签名与沙盒、配置隔离、卸载和事件流生命周期。Safari 若不能在相同约束下接入 CLI，应明确记录尚存的通道例外并确认取舍，不声称已经完成所有外部流量统一。

B1 保留现有 Companion 业务通道，是有记录的阶段边界。它复用同一设备授权思路，但不把六位码改造包装成浏览器已经经 CLI 调用 App。后续迁移也不能因 MCP 服务的 Pro 门槛改变浏览器当前可用权益。

## 8. 最小实现范围

- App：抽取或复用设备批准与存储逻辑，增加浏览器类型和权限范围；保留 MCP 邀请流程和既有设备数据。
- Companion：最小发现、待确认请求与领取、设备 token 鉴权、当前设备撤销以及事件流撤销。
- 两端插件：稳定配对页、来源受控的 background 消息、有限发现、凭据存储、自动重连与取消配对。
- 密钥只在受信任的扩展页面 / background 处理，content script 只传递受限业务动作；不能把新的长效 token 返回网页、URL、页面日志或任意消息调用方。
- 持久化沿用适当的 Keychain / 扩展存储机制；若需要改已发布 schema，追加迁移，不重写历史表定义。
- App 配对界面遵守项目 DESIGN、Sheet 与动效规范，文案按实际语言集合补齐；本子方案不扩展为全局 UI 改造。

## 9. 验收场景

| 场景 | 验收要求 |
| --- | --- |
| 默认地址 / 旧默认端口 | 无需输入 Key，有限发现可找到预期服务；有效保存配置不被覆盖 |
| 自定义端口 / 多个 App | 手动地址仍能配对；多候选可选择，不误连 |
| 批准 / 拒绝 / 不一致 / 过期 | 两端状态一致，错误或终态不能取得有效 token |
| 并行请求 / 重放 / 冒领 | 确认与领取绑定原请求；仅知道六位码不能取得 token |
| 切换到 App / 刷新配对页 | 配对页可持续查看；状态恢复符合约定，不错误显示成功 |
| 浏览器多配置 | 独立身份与凭据，不依赖客户端自报名称进行认证 |
| 单设备撤销 | 新请求和已有 SSE 停止，其他浏览器与 MCP 设备不受影响 |
| 保留手工 Key | 旧路径按原语义可用；撤销后不偷偷回退旧 Key |
| 取消配对时离线 | 区分本地清除与服务端撤销，提供真实下一步 |
| 任意网页发起请求 | 不能静默取得 Key、读取配对结果或批准请求；待配对提示有数量与频率约束 |
| 发现伪响应 / 地址变化 | 不向未经确认的新地址发送旧凭据，不把发现当成认证 |
| 渠道与权益 | 浏览器原权益不变，复用 MCP 组件不附带新的服务门槛 |
| 原生桥接 | 只有在各渠道与浏览器验证通过后才标记免地址和 CLI 接入完成 |

当前仅进行源码与官方文档核对、方案落档及文档检查，未执行配对、GUI、写入或构建。
