## 2. 一次读取生成图

`TagGraphQuery.snapshot(in:)` 在调用方提供的同一个 GRDB 读取事务中执行以下两条查询。节点从标签表出发，所以无当前仓库的标签也有一行。画布通过 `TagGraphFrame.read` 观察这份快照，公共工具在一次 `reader.read` 中调用相同的查询。[图谱查询](../../../Starcat/Core/Sync/TagGraphQuery.swift) · [画布与交集的同次读取](../../../Starcat/Core/Sync/TagGraphFrame.swift)

```sql
SELECT t.id, t.name, t.color, t.icon, COALESCE(c.n, 0) AS repo_count
FROM tags AS t
LEFT JOIN (
    SELECT rt.tag_id, COUNT(*) AS n
    FROM repo_tags AS rt
    JOIN repos AS r ON r.id = rt.repo_id AND r.is_starred = 1
    GROUP BY rt.tag_id
) AS c ON c.tag_id = t.id
ORDER BY t.id;

SELECT a.tag_id AS left_id, b.tag_id AS right_id, COUNT(*) AS shared_count
FROM repo_tags AS a
JOIN repos AS r ON r.id = a.repo_id AND r.is_starred = 1
JOIN repo_tags AS b ON b.repo_id = a.repo_id AND a.tag_id < b.tag_id
GROUP BY a.tag_id, b.tag_id
ORDER BY shared_count DESC, left_id, right_id;
```

`a.tag_id < b.tag_id` 排除自环并固定端点顺序。复合主键使每个仓库对每个标签对恰好贡献一行，因此此处的 `COUNT(*)` 就是去重仓库数。假设仓库有 k 个标签，它贡献 `k × (k−1) / 2` 个标签对，性能采样需要记录每仓标签密度。首版从现有表计算，查询过程无写入，也不需要数据库迁移。

输出 `nodes[{id, name, color, icon, repo_count}]` 和 `edges[{left_id, right_id, shared_count}]`。Swift 与 JS 都用 ID 或有序 ID 对作键，名称只用于展示。筛选阈值作用于可见边，节点计数和边权保留原始整数。初次绘图仅传节点和边，仓库明细在选中后读取。

## 3. 从一条边进入仓库列表

`RepoTagIntersection.page(in:tagIDs:limit:offset:)` 与既有的不分页入口共用一个 AND 条件。去重后的标签 ID 绑定到 `rt.tag_id IN (…)`。查询限定 `r.is_starred = 1`，按仓库 ID 分组，只有 `COUNT(DISTINCT rt.tag_id)` 等于请求的不同标签数才算匹配。在同一 `db` 中先求 `total`，再按 `starred_at DESC, id ASC` 取一页。节点详情传一个标签 ID，边详情传两个。[交集查询](../../../Starcat/Core/Sync/RepoTagIntersection.swift)

选中连线后，右侧先显示两个标签名、交集总数和最多三个仓库。「查看全部」按每页 20 个仓库展示。点仓库打开独立详情窗口，原图保留所选标签、当前页和视角。返回时的键盘焦点列入实机验收。图谱的查询范围只取决于这组标签和当前 Stars。样例中，首页按并集勾选 `Agent` 和 `Python` 能看到 r1、r2、r3，图中两者的交集只有 r1。[关系与仓库详情](../../../Starcat/Features/TagGraph/TagGraphInspector.swift)

## 4. 画布、选择与刷新

1. 打开图谱时，`TagGraphViewModel` 绑定当前账户的数据库，用 GRDB `ValueObservation.tracking` 读取快照。选中标签或边后，同一观察事务一并读取交集总数和当前页，因此边权与仓库列表来自同一次读取。[会话与选择](../../../Starcat/Features/TagGraph/TagGraphViewModel.swift)
2. 标签或关联增删、合并、已应用的 AI 建议和 Star 状态落库后，由观察到的表变化触发重读。更名只更新名称。所选边消失时收起交集详情并给出原因，节点仍在时可返回节点详情。即使边权没变，也要更新已打开的仓库列表，因为可能换了成员。分页越界时回到有效页。
3. 更换选中项或页码时重新订阅，关闭图谱或切号时取消订阅。每次订阅绑定账户会话和本次选择序号，回调发布前比对两者。切号立即清空原生详情和 WebView，拒绝旧会话的 JS 消息。只有同账户刷新才可保留上次成功内容并提供重试。
4. 原生层承载搜索、阈值、关联标签和仓库列表。Canvas 以标签色绘制节点，将原生传入的 SF Symbols PNG 按底色明暗着色。图标缺失时显示标签首字。边权同时控制线宽和不透明度。悬停时仅突出当前阈值下的直接邻居与连线，移开后恢复原选择。[原生工作区](../../../Starcat/Features/TagGraph/TagGraphWorkspace.swift) · [离线画布](../../../resources/follow-graph/tag-graph-entry.mjs)
5. WebView 就绪后用 `callAsyncJavaScript` 的参数传入结构化数据。JS 上报节点 ID 或两个端点 ID，原生仅接受当前会话和快照中存在的选择。权重、文案、阈值或选中变化尽量沿用已有节点坐标与视角，只在初次打开或点「恢复全览」时自动适配。减少动态效果时直接落到稳定布局，画布之外提供可由键盘与 VoiceOver 操作的同等入口。

## 5. 公共读取契约

两个工具均已登记为 `read`，沿用现有连接权益与授权，仅访问当前账户的本地数据库。通用 CLI `starcat tools call` 与 MCP `tools/call` 调用同一 App 执行器。可以从公共目录查看输入 Schema，再到执行器核对返回字段。[公共目录](../../../Starcat/Features/MCP/StarcatMCPPublicCatalog.swift) · [执行器](../../../Starcat/Features/MCP/StarcatMCPPublicFacade.swift) · [CLI 与 MCP 规范](../../5-规范/CLI与MCP能力暴露规范.md)

| 动作 / 工具 | 输入 | 输出及约束 |
| --- | --- | --- |
| 读图 `starcat.get_tag_graph` | `min_shared_repos` 默认 1，`limit`、`offset` 对边分页 | 每页给完整 `nodes` 和当前页 `edges`，附筛选前 `total_edges`、筛选后 `matching_edges` 以及 `limit`、`offset`、`has_more`、`next_offset`。边按第 2 节顺序返回 |
| 读交集 `starcat.list_repos_by_tags` | `tag_ids` 为非空 ID 数组，去重后作 AND，另传 `limit`、`offset` | 返回 `items`、去重全量 `total` 和同样的分页字段。`limit=1` 查 `Agent ∩ RAG` 时第一页有 1 项、`total=2`，翻完应恰有 r1 和 r2 |
| 平移、缩放、拖动、聚焦 | 原生和画布事件 | GUI 展示状态，公共接口不需要这些动作 |

两项分页默认 `limit=20`，取值 1～100，`offset` 从 0 起，末页 `next_offset=null`。空数组、非字符串 ID、非法阈值及分页参数返回 `INVALID_ARGUMENTS` 并标出参数路径。合法但已删除或当前账户未拥有的 ID 查询返回空交集。公共工具每次调用读取当时的快照，跨次翻页核对需固定数据。接口无文件输入输出、后台任务或隐式刷新。

## 6. 验证与实施顺序

先在隔离数据库跑通固定样例、分页以及切号，再接原生详情和离线画布，最后核对公共目录、CLI/MCP 与两渠道。性能先记录冷开聚合、首个可读画面、选择后的列表加载、稳定画布 CPU，给出设备、仓库数、标签数、边数及每仓标签数。建议用 17 标签的典型收藏和「单仓含 40 个标签、应产生 780 条边」的密集样本，另做多仓重叠测试。对慢样本用 `EXPLAIN QUERY PLAN` 定位，自测结果用于确定正式门槛。

2026-11-19 在内存 SQLite 库执行了第 2 节两条 SQL。需求样例返回 5 个节点、3 条边。按第 3 节的交集条件每页查一个仓库，`Agent ∩ RAG` 两页分别返回 r1 和 r2，取消 r2 的 Star 后边权与交集总数均从 2 降到 1。单仓 40 个标签得到 780 条边，每条权重为 1。

验收时对照 [V2-TG-01～06 的任务与证据](checklist.md)，分别记录 SQLite 结果、Swift／渲染器测试、真实公共调用、两渠道构建和经授权的 GUI 验收。产品待定项见[需求说明](需求说明.md)。

### 5,000 个 Star 的数据读取实测

2026-11-20 在 Mac Studio（Apple M2 Ultra、64 GB）用 Debug 配置采样。每组创建一个独立的临时账户库，写入 5,000 个 Star，然后在同一进程和数据库连接池中依次开启三个新的图谱会话。图数据从开始订阅计到主线程收到完整快照，共同仓库从选中权重最高的边计到主线程收到首批 20 项。每隔 1 ms 检查一次。表内依次为三轮实际耗时，单位为 ms。

| 样本 | 标签 / 边 | 每仓标签数 | 所选边的共同仓库数 | 图数据就绪 | 共同仓库首批就绪 |
| --- | ---: | --- | ---: | --- | --- |
| 典型收藏 | 17 / 34 | 0～3 | 222 | 389.1 / 7.5 / 7.0 | 11.6 / 11.4 / 11.7 |
| 密集收藏 | 40 / 780 | 首个仓库 40，其余 8 | 876 | 80.6 / 80.3 / 78.9 | 86.0 / 85.3 / 84.6 |

复测运行 `make test TEST_ARGS="-only-testing:StarcatTests/TagGraphScaleTests"`，查看 `TAG_GRAPH_SAMPLE` 行。构造样本、WKWebView 绘制和 SwiftUI 列表显示都在计时区间外。首个可读画面、列表可见时间和画布稳定后 10 秒的 CPU 与重绘次数留待实机记录。

实机复测沿用表中两个样本，各用独立测试账户。计时从点击侧栏图谱按钮到首个标签名称与计数可读，再从选中权重最高的边到共同仓库列表首行可见。用典型样本的 222 和密集样本的 876 核对所选关系。布局稳定后移开指针，连续 10 秒记录画布实际重绘次数及 Starcat、对应 WebContent 进程的 CPU。将每轮观测值与[首版性能参考线](需求说明.md#首版实施口径)对照。
