# AI 个人笔记审查报告 12：Hero 区域溢出滚动

> 审查时间: 2026-07-22 12:25 CST
> 审查基线: `032de5b`
> 需求证据: dong4j 反馈笔记扩展后 Hero 区域无法滚动，正文详情被挤出可视区域
> 结论: 自动化审查通过，0 个未关闭代码问题；真实窗口滚动手感待人工验收

> 后续说明（2026-07-22）: 本报告只验证了 Hero 内部滚动与纯高度计算，未覆盖 AI 面板增高后尺寸向 `NavigationSplitView` 根容器传播的真实布局回归；该遗漏已在 `审查报告-14-最小窗口三栏裁切回归.md` 修复并补充 39 / 39 联合回归。

## 1. 根因

`RepoDetailScaffold` 原先使用固定的纵向布局：上方 `metadataPanel` 按自然高度占位，下方才是 README / Release 正文。Hero 内包含标签、个人笔记和 AI 生成面板，但自身不是滚动容器；当笔记扩展到 480pt，或 AI 步骤与草稿同时展开时，Hero 会继续增长并压缩正文，只有下方正文自己的 `WKWebView` / `ScrollView` 能滚动，因此指针停在 Hero 区域时无法滚动整个超高内容。

## 2. 修复设计

`RepoDetailScaffold` 为 Hero 增加始终存在的纵向 `ScrollView`，并按详情可用高度计算可见上限：

```text
Hero 可见高度 = min(Hero 自然高度, 详情高度 - 160pt 正文保留高度)
```

- Hero 未溢出时保持自然高度，不额外占满详情页。
- Hero 溢出时只在 Hero 内部滚动，README / Release 正文至少保留 160pt。
- 外层 Hero `ScrollView` 始终存在，不因溢出状态切换而重建 `RepoNotesSection`，避免中断编辑状态或 repo 级 AI 生成会话。
- Hero 折叠资格和折叠位移改用实际可见高度，窗口缩放后重新计算，避免按不可见的自然高度过度折叠。
- 沿用 `detailScrollViewStyle()`，滚动条行为与详情页已有滚动区域一致。

## 3. 代码审查

- 高度计算集中在 `cappedMetadataPanelHeight(...)`，输入未完成测量、可用高度不足或保留高度无效时返回 `nil`，首帧沿用自然布局。
- `minimumBodyViewportHeight` 固定为 160pt，是本次唯一新增布局常量，没有引入配置项或 AppKit bridge。
- `restoreExpandedHeroIfNeeded(...)` 在 Hero 内容或窗口高度变化时恢复合法状态，避免缩放后保留无意义的折叠偏移。
- 没有修改个人笔记保存、AI 流式任务、README 加载、数据库或 i18n。
- 工作区中同文件的其它并行改动未进入提交。
