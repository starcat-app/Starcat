# AI 个人笔记审查报告 14：最小窗口三栏裁切回归

> 审查时间: 2026-07-22 13:10 CST
> 审查基线: `8224909`
> 需求证据: dong4j 截图显示最小主窗口启动 AI 笔记生成后，左、中、右三栏顶部同时越过窗口边界并被裁切
> 结论: 修复后代码与自动化审查通过，0 个未关闭代码问题；真实窗口待人工复验

## 1. 纠正问题边界

此前把截图误判为 Hero 内部滚动位置变化，后续放大裁图明确显示：左栏头像、中栏整理卡片和右栏仓库头像同时被裁切，问题发生在整个 `NavigationSplitView` 根容器。

按 dong4j 的复现时间线，问题在加入 AI 个人笔记生成后出现。直接触发条件是 `RepoNoteAIGenerationPanel` 插入后抬高右栏自然高度；Hero 滚动不是问题起点，只是后续实现仍未把超高详情内容与三栏根布局彻底隔离。

## 2. 根因

旧实现存在一条循环尺寸链路：

```text
AI 步骤面板增高
  -> CollapsibleRepoMetadataPanel 固定读取完整自然高度
  -> RepoDetailScaffold 布局完成后测量自己的高度
  -> 自测高度反过来决定 Hero 可见上限
  -> 右栏尺寸压力传到 NavigationSplitView
  -> 最小窗口中三栏根容器高于窗口并被上下裁切
```

`ContentView` 的主窗口 content 下限是 1440×763，当前运行窗口 frame 实测为 1440×815。问题不应通过继续增大窗口下限解决，否则只能掩盖详情子树尺寸泄漏。

## 3. 修复

`RepoDetailScaffold` 改为由外层 `GeometryReader` 先读取 `NavigationSplitView` 提议的父级 viewport：

- Hero 可见高度在同一布局轮次直接使用 `proxy.size.height` 计算；
- 详情根 `VStack` 固定为 `proxy.size`，不再由 AI 面板自然高度决定；
- 固定 viewport 增加最终裁切边界，异常自然尺寸只能留在右栏内部；
- `detailViewportHeight` 仅保留给 README 折叠资格计算，不再参与当前布局轮次的父级尺寸发现；
- AI 状态机、流式请求、repo 会话、主窗口最小尺寸和三栏列宽均未修改。

## 4. 自动化证据

## 5. 审查边界

- `GeometryReader` 读取的是父级 proposal，不是 window frame 或子树布局后的尺寸；符合 SwiftUI split-view 子视图应服从父级 viewport 的约束。
- README 仍至少保留 160pt，Hero 内部滚动和按可见高度折叠逻辑保留。
- 详情底部 AI 浮层仍位于固定右栏 viewport 内，不会跨栏绘制。
- 没有新增 Swift 文件，不需要重新执行 `xcodegen generate`。
- `docs/功能实现总览.md` 只读核对，未修改；未 push，未执行打包、发布或上传脚本。
