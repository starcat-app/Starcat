## 0. 范围与口径

dong4j 的原始诉求：页面流畅不卡顿（合理动画不算卡顿）。对应审查口径：

1. **主线程占用**：该异步的没有异步；主 actor 上的重 IO / 重计算 / 重复计算。
2. **缓存复用**：该用缓存的没用缓存；写入路径放大（全量 reload、整会话重写）。
3. **重复计算与请求**：同一数据在相邻路径重复取数、重复构造；无变化仍全量重建。
4. **外部 API**：超时设置、异常处理、失败降级。
5. **UI 重复布局**：`.task(id:)` 身份误用导致的无谓副作用、列表逐项 O(n) 查找、双层提取。

不改动现有动画与交互语义；凡是「有保护但构成可感卡顿的证据不足」的一律降级为观测项（第 4 节），不直接修。

## 1. P0 数据安全（会丢用户数据，优先修复）

### P0-1 聊天 SQLite 后端 LRU 淘汰会删光全部会话

- **位置**：`Starcat/Shared/Services/DiskChatHistoryStore.swift:1156`（基线行号；`lruSweep`）。
- **现象**：SQLite 后端的 `lruSweep` 用 `dbQueue` 对应的 **db / wal / shm 物理文件大小**做 `while` 循环的停止条件。
- **根因**：SQLite 事务内的 `DELETE` 只把页标记为空闲、**不缩文件**（WAL 模式下甚至先变大）；`VACUUM` 又不能在事务内执行。于是「物理大小 > 配额」在事务内恒真，循环唯一的自然出口是 `fetchOne` 取不到会话——即把全部会话删到 0 条。
- **触发条件**：聊天历史使用 SQLite 后端（默认后端为 JSON，见 `AppSettings.swift:2162`）且累计超过 100 MiB 配额。默认配置不触发，但 SQLite 是正式可选路径，构成数据安全隐患。
- **影响**：用户全部聊天会话（含消息正文与 carried-over summary）在无任何确认的情况下被清空，不可恢复。
- **方案**：与 JSON 后端既有语义对齐（`:653`，逐条 `bytes -= entry.size`）：
  - 计量改用**逻辑字节**——会话 `title`、`carried_over_summary` 与全部消息 `content` / `reasoning` 的 UTF-8 字节数（`LENGTH(CAST(x AS BLOB))`），随删除逐条扣减，删到达标即停；
  - 门禁上的物理 `totalBytes` 只做预筛，逻辑字节复核未超配额直接返回（避免碎片 / WAL 虚高触发无意义空扫与 VACUUM）；
  - `VACUUM` 仅在确有删除时执行，且留在事务外；
  - 淘汰语义与 JSON 后端一致：`updated_at` 最旧优先、删到达标即停，不引入「保留最后一条」新语义。
- **验收**：新增回归测试——小配额多会话按最旧优先删到达标即停（断言保留集，旧实现会删光）；save 隐式 sweep 路径同验；默认配额 no-op。已通过：`DiskChatHistoryStoreTests` 28/28（2026-11-22），双渠道构建通过。详见 checklist P0-1。

## 2. P1 主线程卡顿（构成可感卡顿的确定性来源）

### P1-1 聊天落盘阻塞主线程且整会话重写

- **位置**：`RepoAIChatViewModel.swift:531,548,653,688,738,873`（主 actor 同步保存）；`DiskChatHistoryStore.swift:579,741`（JSON 后端重写当前会话全部分块 + 遍历全库目录统计）、`:1085`（SQLite 后端删全消息重插）。
- **问题**：聊天是流式场景，每个 token / 事件批次都会触发保存；保存发生在主 actor 上，JSON 后端每次重写当前会话的**全部分块**，还要遍历全库目录重算字节统计；SQLite 后端每次删光该会话消息再全量重插。
- **影响**：长会话（200 条消息量级）下每轮流式事件都做 O(会话大小) 的同步 IO，主线程出现可感顿挫；会话越长越明显。
- **方案**：保留「先存用户消息」的崩溃恢复语义；JSON 后端改增量写受影响分块，全库字节统计移出保存热路径；SQLite 后端按 ordinal 增量 upsert（新增插入、已有更新，不整段重插）。
- **验收**：200 条消息会话的写入量对比；成功 / 取消 / 失败路径回归；落盘不再造成可感主线程卡顿。

### P1-2 README 翻译缓存写后全量 reload

- **位置**：`DiskReadmeTranslationCache.swift:58`（`@MainActor`）、`:192`（upsert 后 reload）、`:301`（同步遍历解码全部译文）。
- **问题**：翻译缓存是主 actor 单例；每写入**一条**译文就触发全量 reload，reload 同步遍历解码全部译文文件。
- **影响**：缓存条目越多，单条写入的主 actor 占用越长；批量翻译（首次翻译一篇 README 的全部段落）时按段落次数重复付出全库解码成本。
- **方案**：普通写入只更新单条缓存与聚合统计（对照 `RepoContextStorage` 等 summary-first 路径）；sweep / 淘汰 / 旧格式清理 / 强刷各自做最小必要 reload。
- **验收**：普通写入不再解码无关译文（目标 0 次）；sweep、淘汰、强刷行为不变；既有测试通过。

### P1-3 语义搜索打分在主 actor

- **位置**：`SemanticSearchService.swift:176,272-317`；候选来源 `LocalSemanticSearchProvider.swift:42`、`HomeViewModel.swift:2616`；`RepoEmbeddingRepository.swift:37`（单条 IN 全量取向量）。
- **问题**：取回候选向量后在主 actor 上逐条做余弦相似度、排序、截断；向量取数 SQL 每次按 repo IN 列表全量取。
- **影响**：候选规模大（数千仓）时，每次搜索的主 actor 长占用直接顶住 UI；输入防抖后仍有一次可见卡顿。
- **方案**：余弦打分 / 排序 / 截断调度出主 actor；向量取数核对分块（对照 `:55` 的计数实现）。
- **验收**：5k 候选排名与现实现一致；主 actor 连续占用与总耗时采样下降；取消行为不变。

### P1-4 README WebView 正文双路翻译提取

- **位置**：`ReadmeWebView.swift:2134,2141`（常规正文同时触发两套提取）；`:1836` 深克隆、`:1895` TreeWalker、`:1926` 桥传；条数 / 字符上限在 `:2217` 接收端才执行。
- **问题**：常规正文模式下两套提取路径同时跑（深克隆遍历 + TreeWalker 遍历），各自把段落桥传到主线程；条数 / 字符截断发生在接收端，Web 进程白做被丢弃的工作。
- **影响**：长 README 首次渲染的翻译提取成本翻倍；Web 进程 CPU 与桥接流量无谓放大。
- **方案**：按消费者与模式触发提取；上限前移到 JS 侧，Web 进程不再生成会被截断丢弃的数据。
- **验收**：提取次数与桥接字节数下降可测；切仓后文档与译文对应正确；字号 CSS 旁路不受影响。

### P1-5 搜索合并在主 actor 逐个 firstIndex（最坏二次复杂度）

- **位置**：`RepoRepository.swift:559,582,595`（非空 FTS 相关性查询无限量）；`LocalKeywordSearchProvider.swift:35`；`RepositorySearchMerger.swift:24,54`；`SearchCoordinator.swift:168,196,239`（来源交付与追加页时在主 actor 重建）。
- **问题**：合并器对每个新结果在既有数组里 `firstIndex` 线性查找；FTS 查询无 LIMIT，来源多、追加页频繁时每个来源交付都要在主 actor 重建整个合并数组。
- **影响**：搜索词命中面大时合并成本最坏 O(n²)，主 actor 上表现为键入后的可感延迟。
- **方案**：仓库身份字典索引化合并；保持排序、去重与来源归并语义；交付批次结构暂不动，后续另行评估。
- **验收**：固定样本对拍合并结果与现实现一致；合并工作量从最坏二次降为线性。

### P1-6 智能集合逐规则重复查询

- **位置**：`SmartCollectionsOverviewView.swift:365,435`；`HomeViewModel.swift:2182` 起（每条规则重复取候选 / 状态 / 非空笔记 ID）；`IndexedSnapshot.swift:38`。
- **问题**：N 条规则各自独立取候选集、状态、非空笔记 ID；同一刷新周期内同一份数据被重复查询 N 次。
- **影响**：规则多 + 仓库多的组合下，智能集合刷新出现可感等待；快照同时携带摘要与 README，内存占用偏大。
- **方案**：同一刷新、同 scope 内共享查询与规则上下文；快照是否同时携带摘要与 README，先测字节量再决定缩减。
- **验收**：N 条规则的查询次数从 O(N) 次独立取数收敛为共享；刷新结果与现实现一致；`SmartCollectionPerformanceTests` 防线保持。

### P1-7 Trending / Activity / Explore 的 `.task(id:)` 身份携带候选构造

- **位置**：`TrendingView.swift:157`、`ActivityView.swift:323`、`ExploreView.swift:262`。
- **问题**：`.task(id:)` 的 `id` 求值发生在 guard（筛选开关）之前——筛选**关闭**时也要构造 skillCandidates（筛选、临时 Repo 构造、查 starred registry）。
- **影响**：三个页面在不需要候选的形态下每次身份变化都白白构造候选；列表刷新期出现无谓开销。
- **方案**：筛选关闭用常量任务身份；开启用覆盖候选、筛选与分页变化的身份；候选构造移入任务体。
- **验收**：筛选关闭时候选构造 0 次；开启时补扫正常；Activity 池上限（200 / 120 / 100）不变。

### P1-8 每日推荐命中判断前全量取已收藏列表

- **位置**：`DailyRecommendationStore.swift:122`；宿主监听 `DailyRecommendationHost.swift:77`。
- **问题**：复用路径在判断「候选是否已收藏」前 `fetchAllStarred()` 全量取列表；宿主监听使该路径被频繁触发。
- **影响**：每次激活推荐都要付出全量取数，仓库多的用户下重复成本可观。
- **方案**：复用路径改为仅查询已收藏 ID（EXISTS / 限定投影）；保留 `DailyRecommendationPreparation.swift:28` 的同 key 单飞与异 key 取消。
- **验收**：同日重复激活不重复全量取数；手动换批、新 Star 排除行为不变。
