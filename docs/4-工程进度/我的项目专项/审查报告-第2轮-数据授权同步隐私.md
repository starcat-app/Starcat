>
> 审查范围：数据库、Repository、授权、同步、隐私和失败语义
>
> 审查结论：**不通过，发现 2 个必须修复的数据边界问题**

## 1. 已确认通过

1. `v17-my-projects` 为追加迁移，未改写任何已发布 migration；v16 → v17 升级测试保留原数据。
2. `repos` 继续作为可重建元数据缓存，`user_projects` 只保存用户—项目关系；Star、Tags、Notes、Status、LibraryState、Pin 与洞察不会被项目 upsert 覆盖。
3. owner / organization_member 分链保存 ETag 和同步状态；分页完整成功才做 generation 对账，中途失败保留旧关系。
4. OAuth 固定 `visibility=public`，GitHub App 固定 `visibility=all`；同轮同步凭据来源固定，启动/手动/后台触发共享 in-flight task。
5. 两条 affiliation 全失败才发布失败；单链成功返回部分摘要。GitHub App 的 organization_member 403 映射为待组织审批，其它单链失败映射为部分授权。
6. 401 只撤销项目凭据，不删除主 OAuth token；数据库和日志只保存稳定错误码，不保存 GitHub response body。
7. Private README、公共服务、分享、Universal Link、Discovery、推荐、Wiki、Repository Insights、CloudKit 和默认导出边界均有代码或可执行策略。

## 2. 发现的问题

### R2-01：Internal visibility 没有强制投影为 Repo 私密标记

- 级别：P1
- 证据：
  - `/user/repos` DTO 已正确解析 `visibility = internal`。
  - `GRDBUserProjectRepository.upsertPage` 通过通用 `repoFromDTO` 写入 `Repo.isPrivate`，没有用项目 visibility 纠正。
  - 全部公共出口与 Private README 凭据路由都以 `Repo.isPrivate` 为门禁。
  - GitHub 官方将 Internal 作为独立可见性，并在隐私语义上视为非公开仓库；不能依赖 REST payload 的 `private` 布尔值替代 `visibility`。
- 影响：当 REST payload 返回 `visibility=internal`、`private=false` 时，Internal 仓库可能进入 Public README token、公开服务、分享或 External Search 路径。
- 修复要求：
  1. 项目 upsert 时用 `visibility != public` 强制设置 `Repo.isPrivate = true`。
  2. 添加 DTO + Repository 回归测试，覆盖 `internal + private=false`。
  3. 文档明确公共出口以项目 visibility 归一化后的 Repo 私密标记为准。

### R2-02：撤销 GitHub App 时会先删除全部 App 来源关系，Public fallback 依赖下一次网络刷新

- 级别：P1
- 证据：
  - `user_projects` 的主键为 `(user_id, repo_id)`，同一项目只保留当前权威凭据来源。
  - GitHub App 全量同步会把 Public 项目的 `authorization_source` 更新为 `github_app`。
  - `deleteRelations(userID:authorizationSource:.githubApp)` 当前直接删除全部 GitHub App 来源关系。
  - 随后的 OAuth fallback 刷新若断网或限流，原本已缓存且 OAuth 可访问的 Public 项目也会暂时消失。
- 影响：不满足“撤销只移除不可访问关系，Public fallback 与旧列表在网络失败时仍可用”的失败保旧值语义。
- 修复要求：
  1. 撤销/401 清理时，把 GitHub App 来源的 Public 关系降级为 OAuth fallback。
  2. 只删除 Private / Internal 的 GitHub App 关系及 GitHub App 同步状态。
  3. 保留 Repo、Star、Tags、Notes、LibraryState、Pin 与缓存。
  4. 添加选择性清理测试，证明断网前 Public 项目仍可见。

## 3. 本轮结论

授权、分页、代际和失败状态主体实现正确，但 Internal 私密归一化与撤销后的 Public fallback 仍有数据泄漏/可用性风险。必须先关闭 R2-01、R2-02，再进入 UI 与交互审查。
