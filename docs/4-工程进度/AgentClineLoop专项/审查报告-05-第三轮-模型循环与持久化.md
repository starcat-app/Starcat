# 审查报告 05:第三轮模型循环与持久化

> 审查时间: 2026-07-11
> 审查范围: LLM Adapter、流式事件、Loop Runtime、预算、取消竞争、GRDB 事务和 pending approval 恢复
> 审查结论:主循环闭环完整,发现 2 项取消与恢复时长边界

## 1. 已核对证据

- OpenAI-compatible Adapter 同时覆盖流式和非流式 Provider,完整映射 text、reasoning、tool-call、usage 与 completed。
- tool-call-only 响应不会被当作空响应;多 choice 流式增量按 choice/index/callID 隔离。
- `LoopAgentRuntime` 每轮执行 Message Contract 校验,模型返回的每个 tool-call 都生成关联 tool-result 后进入下一轮。
- Runtime 强制 maxIterations、maxToolCalls、maxTokens、maxDuration、单工具超时、全局工具超时上限和只读工具重试策略。
- Run、message、approval 和 artifact 使用 GRDB 持久化;消息追加和 run 状态更新位于同一事务。
- completed/failed/cancelled 终态由 actor 状态机竞争,不会重复覆盖。

## 2. 发现项

### P1-1 模型 Adapter 没有向 Provider 传播流消费者取消

`OpenAIAgentLoopModelClient.stream` 在 `AsyncThrowingStream` 内创建独立 `Task`,但没有在 continuation 终止时取消该任务。Runtime 或 UI 停止消费外层 stream 后,内部任务仍可能继续等待 `AIClientProtocol.chatStream`,造成已取消 run 保留网络请求和事件生产。

修复:保存 producer task,在外层 continuation 的 `onTermination` 中取消;补充测试证明取消 Adapter 消费后底层 Provider stream 收到 cancellation。

### P1-2 pending approval 恢复错误计入用户离线等待时长

`AgentRunSession(restoring:)` 把 `startedAt` 设为原 run 的 `createdAt`。如果用户数小时后重启应用并批准工具,恢复后的下一轮会立即触发 `durationLimit`,不符合“重启后继续待确认调用”的验收语义。

修复:恢复 session 时以当前时间开启新的活跃执行时长窗口;消息、迭代、工具和 token 预算仍从持久化快照恢复。补充旧 run 恢复后仍可进入下一轮的测试。

## 3. 无问题项

- Provider/Keychain/模型参数全部复用现有设置,没有第二套配置。
- 非法工具参数、未知工具、Provider 能力错误和缺配置都有明确失败或 error tool-result。
- tool-result 与 run status 的持久化顺序可恢复,终态不会生成假 artifact。
- 单工具超时、重试尝试和错误摘要可从消息事实审计。

## 4. 修复顺序

1. 修复 Adapter 取消传播并补测试。
2. 修复恢复 session 的活跃时长起点并补测试。
3. 运行模型适配、Session、Loop 和持久化相关测试。
