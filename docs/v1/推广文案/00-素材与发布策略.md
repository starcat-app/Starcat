# Starcat 推广素材与发布策略

> 用途: 统一保存 Starcat v1 首发阶段的跨平台推广口径、截图素材和后续路线。每个平台文档可以独立发布,但不要把还没完成的路线写成已上线能力。
> 最后更新: 2026-07-21

## 项目组织

Starcat 不是一个孤立 App，它由 [starcat-app](https://github.com/starcat-app) 组织下的多个支撑项目共同构成：

| 项目 | 说明 |
|---|---|
| `starcat-app/Starcat` | macOS 主应用 |
| `starcat-app/starcat-pro` | 问题追踪与 feature requests |
| `starcat-app/starcat-cli` | Go 跨平台 CLI 与 MCP 协议适配器 |
| `starcat-app/starcat-skill` | Agent 工作流定义 |
| `starcat-app/starcat-recommend-api` | 相似仓库推荐服务 |
| `starcat-app/starcat-trending-api` | GitHub Trending 数据服务 |
| `starcat-app/starcat-weekly-api` | GitHub Weekly 数据服务 |
| `starcat-app/starcat-sharing-api` | 仓库分享链接与 OG 预览 |
| `starcat-app/starcat-wiki-api` | Wiki 元数据聚合 |
| `starcat-app/starcat-discovery-api` | 探索发现数据服务 |

用户在 `starcat-app/starcat-pro` 提交 issues 和功能请求。所有后端服务版本通过 `/ping` 契约统一注入，确保客户端与服务的版本一致性。

## 统一定位

一句话 (英文):

> Starcat is a native macOS app that turns GitHub Stars into a local-first, AI-readable knowledge base — with cross-repo RAG Q&A, repo research agents, and MCP-powered AI toolchain integration.

一句话 (中文):

> Starcat 是一款 macOS 原生的 GitHub Stars 管理与开源项目研究工具。它把散落的收藏变成可搜索、可问答、可研究的本地知识库，并通过 RAG 跨仓库问答、Agent 工作台和 MCP 服务桥接，让开发者的 AI 工具链真正读懂自己的开源项目库。

## 当前可直接讲的能力

### 基础工作流
- GitHub Stars 本地同步、增量更新、三栏原生 macOS 管理。
- README 本地缓存与原生渲染，支持离线阅读。
- 标签、笔记、阅读状态，支持 Smart Collections 自动分组。
- 全文搜索 (FTS5) + 语义搜索 (本地 embedding + cosine 检索)。
- Release 订阅、Activity 跟踪、Trending / Weekly 信息流。

### AI 能力（围绕 repo 上下文，非泛聊天）
- AI 摘要：单仓库 README 摘要，快速判断项目做什么、适合什么场景。
- AI 标签建议：基于 repo 元数据和内容推荐标签，用户确认后写入。
- README 翻译：中英双语快速切换。
- AI 对话：在 repo 详情页内围绕当前仓库上下文问答。

### v1.1.0 重点：知识库 RAG（跨仓库问答）
- **知识库问答工作台**：独立 RAG 工作台窗口，基于用户私有知识库（`in_library` repo）进行自然语言问答。
- **Local-First Hybrid RAG**：本地 FTS5 全文检索 + 本地向量语义检索默认可用，外部重排服务为高级选项。
- **Chunk-Level 索引**：对 README、笔记、AI 摘要做细粒度分片索引，每个回答带可追溯引用，能定位到具体段落。
- **GitHub 远程临时上下文**：可选的 issues / PRs / releases / security advisories 联网补充，但不进入本地 RAG 索引。
- **vDSP 加速向量扫描**：本地 1.8 万+ 向量余弦相似度计算提速 23 倍。
- **RAG 只读原则**：不自动写入 tags、notes、status，所有写入须用户确认。

### AI 工具链集成
- **MCP Service**：本地 MCP 服务，让 Claude、Codex 等外部 Agent 能查询 Starcat 的 repo 数据、搜索和知识库上下文。
- **RepoContextPacker**：将 repo 元数据、README、笔记、标签打包为 AI 可消费的结构化上下文。
- **CodeFlow**：代码级上下文追踪与提取。
- **AnySearch**：统一搜索入口，聚合本地 + GitHub + 外部搜索源的结果。
- **starcat-cli**：Go 跨平台 CLI，提供 `starcat mcp` 命令行桥接，让终端和 Agent 工作流直接调用 Starcat 能力。

### 发现与推荐
- 相似仓库推荐入口，首版由 `starcat-recommend-api` 中转 SimRepo，客户端消费稳定 `/api/v1/repos/{repo_id}/recommendations` 接口，后续可替换为自研内容向量/行为混合推荐。
- Trending / Weekly 多源聚合，由独立后端服务提供结构化数据。

## 发布节奏

**第一波**先要真实反馈，不要追求声量。建议先发 V2EX、即刻、Reddit r/macapps / r/SideProject，用 "我做了一个工具，想听听开发者怎么看" 的语气，重点收集对 RAG 问答体验和知识库工作流的反馈。

**第二波**做内容沉淀。少数派、掘金、知乎、公众号/博客更适合写完整文章：
- 少数派讲 "从收藏到知识库 — RAG 如何让 GitHub Stars 可以问答"。
- 掘金讲技术实现：本地 Hybrid RAG 架构、vDSP 向量加速、chunk 索引设计、recommend-api 边界、MCP 桥接。
- 知乎用问题型回答，讲 "GitHub Stars 太多怎么办"。
- 公众号讲个人故事和产品理念。

**第三波**做海外正式发布。Hacker News 讲技术 tradeoff 和 RAG 本地优先设计；Product Hunt 讲一句话价值和视觉。

**第四波**做长期 SEO。AlternativeTo、SaaSHub、BetaList、AI Tool Directories、GitHub Awesome lists 提供长尾入口。

## 评论区回复底稿

**为什么不是直接用 GitHub 网页?**

GitHub 网页适合看单个仓库，但不适合管理一个越来越大的个人 stars 库。Starcat 的重点不是替代 GitHub，而是把 stars 变成本地可搜索、可标注、可问答的知识库。特别是 RAG 工作台，你可以用自然语言问 "我收藏的 SwiftUI 项目中，哪些用了 Core Data"，这在 GitHub 网页上做不到。

**AI 会不会乱改我的标签?**

不会。Starcat 的 AI 策略是建议先行，用户确认后才写入。摘要、标签建议、笔记草稿、Agent 报告都必须可预览、可引用、可撤回。RAG 问答只读，不写入任何内容。

**RAG 会读取我所有的 stars 吗?**

不会。RAG 默认只基于你的知识库（已入库 repo）回答，不是全部 stars。知识库是你主动筛选过的项目集合，RAG 在这个边界内工作，每个回答都带可追溯引用。资料不足时会明确说明，不会编造。

**隐私怎么处理?**

Starcat 是本地优先应用。stars、标签、笔记、缓存、AI 结果、RAG 索引默认都在本机。AI key 走本地配置或用户选择的 provider（支持 OpenAI-compatible、DeepSeek、OpenRouter、Ollama）。推荐服务和外部重排是可选的，即使开启也不会把你的知识库变成 SaaS 后端。

## 不要过度承诺

- 所有 "已上线" 能力都能在当前 app 或文档中找到事实依据。
- 所有 "后续" 能力都写成 roadmap / planned / exploring。
- 每个平台至少配一张截图。
- 英文平台不要使用中文截图说明作为唯一素材。
- RAG 第一版只支持知识库范围问答，不要暗示能搜全网 GitHub。
