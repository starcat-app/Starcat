## 发布节奏

第一波先要真实反馈,不要追求声量。建议先发 V2EX、即刻、Reddit r/macapps / r/SideProject,用"我做了一个工具,想听听开发者怎么看"的语气,把反馈收回来改产品。

第二波做内容沉淀。少数派、掘金、知乎、公众号/博客更适合写完整文章,讲为什么 GitHub Stars 会变成信息负债,Starcat 怎么把它变回可以搜索、可以理解、可以继续研究的知识库。

第三波做海外正式发布。Hacker News 和 Product Hunt 的文案要更克制。HN 讲技术选择、本地优先、GitHub API、README 渲染、AI 不自动写入; Product Hunt 讲一句话价值和视觉。

第四波做长期 SEO。AlternativeTo、SaaSHub、BetaList、AI Tool Directories、GitHub Awesome lists 不一定当天带来用户,但长期会给 Starcat 一个"开发者工具/AI repo research/macOS GitHub app"的入口。

## 统一定位

一句话:

> Starcat is a native macOS app that turns GitHub Stars into a searchable, AI-readable knowledge base.

中文口径:

> Starcat 是一个 macOS 原生的 GitHub Stars 管理和开源项目研究工具。它把散落的收藏、README、标签、笔记、Release、周报和 AI 摘要放回同一个工作流里,让开发者真正找得到、看得懂、用得上自己 star 过的项目。

## 不要过度承诺

当前可以直接讲:

- GitHub Stars 同步、本地缓存、三栏管理。
- README 阅读、标签、笔记、阅读状态。
- AI 摘要、AI 标签建议、AI 对话、README 翻译、语义搜索。
- Trending / Weekly / Activity / Release 订阅。
- 相似仓库推荐入口,首版由 `starcat-recommend-api` 中转 SimRepo,后续可替换自研推荐。
- MCP Service、CodeFlow、RepoContextPacker、AnySearch 等面向 AI 工具链的能力。

可以讲为路线,但必须标清"正在规划/后续":

- Agent 中心: 整理、发现、消化三条主线。
- 技术选型 Agent、替代品发现 Agent、Stars 周报 Agent、Unread 激活、回忆搜索。
- Show HN Discovery 客户端、HelloGitHub 数据源、GitHub Issues 推荐栏目。
- CloudKit 多端同步、JSON 导入导出、Awesome README 导出。
- 自研内容向量/行为混合推荐。

## 评论区回复底稿

**为什么不是直接用 GitHub 网页?**

GitHub 网页适合看单个仓库,但不适合管理一个越来越大的个人 stars 库。Starcat 重点不是替代 GitHub,而是把 stars 变成本地可搜索、可标注、可分析的知识库。

**AI 会不会乱改我的标签?**

不会。Starcat 的 AI 策略是建议先行,用户确认后才写入。摘要、标签、笔记草稿、Agent 报告都应该是可预览、可引用、可撤回的。

**隐私怎么处理?**

Starcat 是本地优先应用。stars、标签、笔记、缓存和 AI 结果默认在本机。AI key 走本地配置或用户选择的 provider;路线里即使加入推荐服务,也会把推荐服务限定在发现体验,不把用户知识库变成 SaaS 后端。
