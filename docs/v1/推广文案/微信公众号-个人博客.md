# 一、微信公众号

## 标题

我 star 了快两千个仓库，后来才承认：收藏并不能变成理解

### 备选

- 翻了二十分钟 Stars，我开始怀疑「以后再看」
- 做 Starcat 的这一年：我想把吃灰的收藏变成还能问得动的东西

## 正文

去年有一阵，我卡在一个 macOS 小功能上。隐约记得自己 star 过一个 Swift 写的剪贴板工具，README 干净，架构也清楚，很适合拿来对照。

我打开 GitHub 的 Stars，开始翻。

翻到后来有点可笑。名字想不起来，关键词也拼不准，只剩一些没用的印象：Swift、菜单栏、大概和剪贴板有关。GitHub 的搜索框在那里，我却不知道该敲什么。二十分钟后找到了——与其说是搜索成功，不如说是靠耐心把列表又刷了一遍。

那天晚上我不是在恨 GitHub。GitHub 把收藏这件事做得足够轻：一眼、一键、列表还在。轻，才是问题本身。轻到你会对自己说谎，谎话说出来都一样：「以后再看。」

以后很少来。

我把自己的行为回想了一遍，并不高等。好用的库，先 star。火的项目，先 star。README 写得漂亮的，也 star。别人在群里安利一句，手比脑子快。几年下来，我的 Stars 过了一千八。数字看起来像履历，打开却像一间从没收拾过的杂物间：东西都在，你就是说不清自己到底有什么。

有一阵我试过正经整理。建 list，加备注，用浏览器书签，甚至导出过 JSON。大多坚持不了两周。不是工具不够多，是我高估了自己维护第二套系统的意愿。人会 star，是因为 star 几乎不费劲；人不会整理，是因为整理费劲，而且一时半会看不出收益。

所以后来做 Starcat，起点其实很自私：我想给自己一个，在 Mac 上打开就能继续翻自己收藏的地方。原生界面，本地数据，README 不用每次跳回浏览器。标签和笔记写在仓库旁边，而不是写在某个我三个月后就不会再打开的笔记软件里。

```
【截图 1｜管理主视图｜三栏、大库感】
落盘：wechat-01-manage.webp（可复用 zhihu-01）
```

做着做着，问题换了形。

把列表搬到本地，只能说明「找得到入口」。真正让我烦的，是另一种找不着：我想起一种能力、一种写法、一种取舍，却对应不到具体仓库。记忆是语义的，Stars 是列表的。两者中间缺了一层。

也是在那时候，我越来越不信任「再做一个更强的搜索框」这种答案。搜索假设你知道自己在找什么。我经常不知道。我知道的是一种模糊的需求，接近聊天时随口一问：「我收藏过的 SwiftUI 项目里，哪些正经用了 Core Data？」

这句话丢给 GitHub，它会按关键词给你一堆结果。丢给普通的全文检索，也常常只会把含这两个词的段落捞上来。我要的其实更刁：在我自己的材料里，做一次有出处的综合，而不是再生成一篇网上都能搜到的科普。

v1.1 里的知识库问答，是冲着这个别扭去做的。

它不搜全网。默认也不扫你全部 Stars。你得自己把仓库「入库」——这个动作有点烦，我故意留着。随手 star 和愿意放进知识库，本来就不是一回事；如果 AI 对两者一视同仁，回答会开始显得勤快而不可信。我宁可它在材料不够时直说不够，也不要它为了完整去外面借内容来凑。


做 RAG 的人爱谈效果。我更早卡住的是边界。索引放哪，答到哪一层，错了谁负责。个人 Stars 看着像公开信息，拼起来却是一张兴趣图谱：你在追什么，准备转什么，对哪些方向手痒。我没有兴趣把这张图默认交给某家云端知识库代管。所以检索先放本地，模型用你自己的 key 或本地模型；Starcat 更像工作台，不是又一个要你先搬家的平台。

还有一件事，我从第一版就写进自己的规矩里：AI 可以建议，不可以擅自改我的库。

不是做不到自动打标签。是我怕。标签乱了可以重建，信任没了很难捡回来。你花几年慢慢形成的分类习惯，不该在某次「智能整理」之后变得不像你自己。所以摘要能给，标签能提，问答能做——写入仍要经过你。


```
【截图 5｜仓库详情与私人笔记】
落盘：wechat-05-repo-detail.webp（可复用 zhihu-02）
```

后面还有 MCP、命令行，那些是给已经把 Agent 嵌进工作流的人用的。公众号里不展开。我只想留一句：如果人要能问自己的库，Agent 迟早也要能读同一份库，否则你又会养出两套互不通气的上下文。

代码在 starcat-app 组织下开源，主应用和一堆小服务拆开维护。bug 和骂声可以去 `starcat-pro`。我把它拆开，部分是工程原因，部分是我不想假装「一个 App 解决开源世界的一切」。

前面的路我自己也没走完。批量整理、替代品比较、周报和「去年那个 SSR 框架叫什么」这类回忆，都还在规划里。能写进文章的，只有已经能用的部分；其余的，我宁愿写「还没有」，免得读者按宣传来验收现实。

我仍不确定 Starcat 对不对所有人。Stars 只有几十个、并且真的会回去看的人，也许根本不需要它。它更像写给已经感到负累、又不愿把负累交给又一个云同步笔记的人。

如果你也有过对着 Stars 发呆的时刻，可以试试：https://starcat.ink

更想听的其实是回信。你现在还星吗？星完还会回去吗？如果有一个只能问「你亲手入库」的那些仓库、不能问全部 Stars 的问答，你会觉得安全，还是觉得碍手？

# 二、个人博客

## 标题

收藏是一种遗忘的方式：我为什么做 Starcat

### 备选

- 「以后再看」失效之后  
- 一张兴趣图谱该放在谁的硬盘上

## 摘要

开发者很容易星仓，却很难在几个月后找回当时的判断。本文记录我做 macOS 应用 Starcat 的动机：把 GitHub Stars 从列表变成可标注、可追问的本地知识库，以及我在「知识库边界 / 本地优先 / AI 不擅自写入」上为什么不愿让步。

## 正文

### 从一次丢人的翻找开始

我不愿把产品故事开场写成神话。Starcat 的起点更接近一次丢人：我找自己的收藏，找不到。

具体情节乏善可陈。做一个 macOS 功能时，想起某款 Swift 剪贴板工具，曾认真读过它的 README。名字忘了。Stars 页面很长。我像在旧硬碟里找一张没写文件名的照片，只能靠缩略图式的记忆去碰。找到的时候没有成就感，只有一种被自己的习惯捉弄的感觉。

在那之前，我并不觉得 Stars 有问题。它甚至有点叫人上瘾。公共场所里最礼貌的技术姿态之一，大概就是 star：我看见了，我认可了，我可能回头。动作轻，道德成本也低。你很少因为星得太多而被指责；你只会在某天需要它们时，才单独受罚。

罚金是时间，还有一种更隐晦的东西：你开始不信任自己的「以后」。

### 收藏为什么常常等于推迟理解

我后来花了些时间想这件事，倒不是为了把 Starcat 抬高成方法论。

软件圈有一种勤快的贫穷：输入极多，消化极少。信息流、周报、Awesome List、别人的 star 列表，都在训练我们获取。GitHub 把「获取」做成了社交货币，却几乎不帮你承担「保质期」。README 会变，项目会死，你的问题域也会变。星仓的那一刻，你以为自己保存的是仓库；多数时候你保存的只是一个未完成的判断。

未完成的判断堆在一起，看起来像库，摸起来像雾。

我也曾试图用更勤快的方式对抗雾：Lists、本地笔记、Spreadheet、定期回顾。失败原因非常普通——第二套系统的维护成本，高于 star 的快感。任何需要我变得更勤快才能运转的方案，最后都会输给我自己。

所以我要的不是又一处「提醒你整理」的地方。我想降低的是：在已经星过的前提下，回看和追问的摩擦。

### 一年里真正转过的几个弯

如果把这一年写成功能路线图，会很像发版说明，读的人也会很快睡着。我更愿意按自己想通的顺序写。

最先做的是搬家。Stars 同步到本地，三栏，README 缓存，标签和笔记贴在仓库旁。决定做原生 macOS，而不是套一层网页，有一半是口味，有一半是自私：我每天已经够多网页了，工具本身我不想再是一个浏览器标签。

```
【截图 B1｜主界面三栏】
落盘：blog-01-manage.webp
```

搬完家，我以为自己会开心一阵子。开心了很短。列表更清楚了，我却更频繁地碰到那种「说得出感觉、说不出名字」的时刻。本地搜索能加快已知关键词的找回，却救不了语义含混的需求。人问自己的收藏时，很少从准确的专有名词起手，更多是从场景和约束起手。

于是弯转到 AI。摘要、翻译、标签建议、对着当前仓库问两句。这些功能好展示，也容易做成聊天玩具。我自己用下来，真正有用的几乎都不是「多聊两句」，而是「少读一点也知道自己要不要深挖」。它节省的是注意力，不是陪伴。


再往后，才是知识库问答。我说「才是」，是因为如果一上来就做 RAG，我大概率会做一个更热闹、也更假的东西：对着两千个随手 star 的仓库夸夸其谈，引文华丽，信心满满，用户心里却清楚——这些仓库里有一半自己从未认真看过。那种智能，像有人翻了你的垃圾桶后开始分析你的生活品味。

所以我把「入库」留成显式动作。知识库是子集。问答默认发生在子集上。你可以用临时的远程上下文补一轮，但我不把那些补丁写进长期索引。这个设计让演示变笨一点，也让我睡觉踏实一点。

```
【截图 B4｜RAG 问答】
落盘：blog-04-rag-qa.webp
```

```
【截图 B5｜引用回到段落】

```

有人会问：为什么不直接开放「搜全部 Stars」？我没有宗教式的反对。我只是觉得默认值应该保守。宽松的默认会训练用户容忍幻觉和噪音；收紧的默认会逼用户做一次所有权确认——这些材料，我是否愿意为它们的答案负责？工具可以帮忙检索，责任不该被界面偷走。

### 本地优先对我来说不只是隐私口号

把索引放在本地，当然有隐私上的考虑。个人 Stars 聚合起来，接近一份兴趣与判断的底稿。底稿交给谁，是产品问题，也是政治问题，哪怕规模很小。

但还有一层更实际：我希望没网时也能翻自己的库，希望换模型时不必搬家，希望工具挂了之后数据仍是普通文件意义上的「还在」。本地优先不是复古，是我不想把个人研究环境做成又一种订阅型记忆。

实现上有很多可以写长的东西：混合检索、向量加速、chunk 怎么切、引用怎么回跳。那些更适合单独的技术文。放在这篇里，我只保留一个判断——先问数据是否该离开机器，再问模型有多聪明。顺序反了，产品会跟着歪。

### 我害怕自动化的那一部分

自动打标签、自动写笔记、自动「整理完你的一生收藏」，演示效果通常更好。我仍做得克制，近乎固执。

原因很个人。我维护过乱掉的标签体系，也见过被插件改得面目全非的笔记库。AI 一旦拥有静默写入权，短期效率上升，长期你无法分辨：这套结构到底是你的认知，还是模型的平均品味。Starcat 面向的是长期资产。长期资产上，我愿意牺牲一点酷。

所以问答只读。建议要确认。这条规矩如果哪天被我自己打破，希望是因为想清楚了，而不是因为竞品列表里多了一行「全自动」。

### 人和 Agent 共用一份上下文

我自己用 Agent 越多，越讨厌上下文分裂：人在 A 处收藏，模型在 B 处猜测，笔记在 C 处腐烂。MCP 和 CLI 对我而言，不是功能拼盘上的装饰，而是同一件事情的另一半——既然知识库在本地，就该允许可信的工具链来读它。

读，仍不等于写。这个对称我还想保持一阵子。

### 开源、拆仓，以及我尚未做完的事

项目放在 github.com/starcat-app。主应用和推荐、Trending、CLI 等拆开，有版本与发布上的现实考量，也有我不想把所有叙事塞进一个仓库的脾气。issue 去 `starcat-pro` 即可，表扬和拍砖都比沉默有用。

没做完的事一堆。批量整理、替代品与选型、周报、回忆式搜索——我可以在路线图里写得很齐，但齐的路线图常是一种文案技巧。它们仍在探索，不保证形态，更不保证时间表。你今天下载到的，应以能点开的界面为准。

### 收束，但不想升华

我没有一句话真理要送。若硬说有收获，大概是：

收藏很容易冒充学习。列表很容易冒充体系。智能很容易冒充可靠。

Starcat 只是我在这三层冒充之间，给自己钉的一个小钉子：把 Stars 放回本地，允许标注，允许追问，同时逼自己承认——不是每一个 star 都配进入知识库，也不是每一次模型输出都配直接写入我的结构。

它肯定不是人人需要的东西。若你的 Stars 仍少而清，GitHub 原版就好。若你已感到那间杂物间在呼吸，并且你愿意为「问得动」多负一点责任，再到 https://starcat.ink 看一眼。

我更期待的反馈不是「很酷」，而是你哪里不信任它。不信任默认比夸赞接近真相。
