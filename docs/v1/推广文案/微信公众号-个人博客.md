# 微信公众号 / 个人博客

## 文章标题

当 GitHub Stars 变成信息负债，我花了一年做了个能问答的知识库

## 正文草稿

### 一个你很可能也有的问题

去年秋天，我在做一个 macOS 效率工具。写到一半，想起自己年初 star 过一个 Swift 写的剪贴板管理器——那个项目的架构很清晰，我想参考它的实现。

打开 GitHub，点进 Stars 页面。找了 20 分钟。不是 GitHub 的问题，是我根本想不起那个项目的名字。只记得它是 Swift 写的，大概和剪贴板有关，可能叫 Clip-something。

最终找到了。但这个过程让我意识到一个问题：GitHub 给了我们"收藏"这个动作，但从来没帮我们解决"找回"和"理解"。

我回想了一下自己 star 项目的行为模式：

- 看到一个有用的库 → star
- 看到一个有意思的 AI 项目 → star
- 看到一篇 README 写得很好的工具 → star
- 看到别人推荐的框架 → star

每次 star 都是一句 "以后再看"。然后 "以后" 永远不会来。

这不是一个搜索技术的问题。GitHub 的搜索很强大。问题是：你不知道该搜什么。你只知道那个项目大概和剪贴板有关，印象中是 Swift 写的，好像还有菜单栏图标。这些模糊记忆填不进搜索框。

这是**知识管理**的问题。你的收藏不再是列表，而是一个没有被组织的知识库。

### 我做了什么

所以我做了一个 macOS 原生应用，叫 **Starcat**。

![Starcat 管理视图](assets/01-manage-ungrouped.png)

它的第一版很简单：把你的 GitHub Stars 同步到本地，用三栏界面管理。你可以给项目打标签、写笔记、标记阅读状态。AI 可以帮你快速理解一个 README——总结内容、建议标签、翻译文档。

但真正让我觉得这个东西值得做的，是 v1.1.0 加上的**知识库 RAG 问答**。

### 当你的收藏可以回答你的问题

想象一下这个场景：你想知道"我收藏的 SwiftUI 项目中，哪些用了 Core Data 做本地存储？"

这在以前，你得一个一个打开 repo 看 README。如果在 GitHub 上，你只能搜关键词 "Core Data"，然后逐个筛。

Starcat 的 RAG 工作台做的事是：

1. 理解你这句话的意思——你想找的是"用 Core Data 做本地存储的 SwiftUI 项目"。
2. 在你自己的知识库里做本地检索——全文搜索找关键词，向量搜索找语义相关的段落。
3. 把检索到的 README 片段、笔记、AI 摘要组织成上下文。
4. 发给 AI，生成一个带引用的回答。
5. 每个结论后面都有一个可点击的引用链接，直达原文段落。

整个过程，除了最后一步 AI 生成需要调一次 API，其他全在本地完成。你的数据没有离开你的 Mac。

![AI Assistant](assets/04-ai-assistant-window.png)

### 为什么 RAG 必须本地优先

这里有一个我很在意的设计选择：**知识库和 stars 是两回事**。

你可能 star 了 2000 个项目，但真正研究过、写过笔记、值得长期跟踪的可能只有 300 个。RAG 要回答的是基于你真正了解和关心的项目，而不是基于你随手点过 star 的全部内容。

所以 Starcat 的 RAG 默认只在"知识库"——你主动筛选入库的那些仓库——里检索。如果资料不够，它会明确告诉你"这个问题你的知识库回答不了"，而不是去网上凑一个似是而非的答案。

这个设计比"检索全部 stars"更保守，但也更可信。用户知道 AI 给的信息来自自己筛选过的数据。

### AI 不能替你做决定

另一个从第一天就坚持的原则：AI 只能建议，不能替用户写。

标签建议需要你确认，笔记草稿需要你手动保存，RAG 问答只读。这不是技术上做不到自动化——而是如果 AI 可以静默修改你的知识结构，你对整个系统的信任就没了。

### 不只是人用的，也是给 AI 工具链的

除了人用的界面，Starcat 还提供了一套给 AI 工具用的能力：

- **MCP Service**：让 Claude、Codex 或其他本地 Agent 能查询你的 stars 和知识库。
- **RepoContextPacker**：把 repo 元数据、README、标签、笔记打包成结构化的 AI 上下文。
- **starcat-cli**：命令行工具，`starcat mcp` 就能桥接所有能力。
- **AnySearch**：统一搜索入口，一次搜索同时覆盖本地 + GitHub + 外部源。

这些功能面向的是在用 AI 工具链做开发的 power user。Starcat 在这个图景里的角色是**本地 repo context hub**——不是替代你的 AI 工具，而是让你的 AI 工具能读懂你的开源项目库。

### 这个项目怎么组织的

Starcat 不是一个孤立 App。代码放在 [github.com/starcat-app](https://github.com/starcat-app) 组织下，主应用和支撑服务分开维护。

除了主应用（`starcat-app/Starcat`），还有独立的推荐服务、Trending/Weekly 数据服务、分享链接服务、CLI 工具、Agent 工作流定义。所有服务通过 `/ping` 契约统一注入版本号。

遇到 bug 或有功能建议，可以在 `starcat-app/starcat-pro` 提 issue。

### 接下来做什么

Starcat 还在早期。接下来的路线分三条线：

**整理**：让混乱的收藏先变清楚。批量处理未分类项目，自动发现近义标签（如 `cli-tool` 和 `cli-tools`）并建议合并，扫描功能重复或长期不维护的仓库。

**发现**：不只是看 Trending，而是从你自己的知识库出发去发现。相似仓库推荐已经有了第一版，后面会做替代品发现和技术选型 Agent——输入"我需要一个轻量的本地向量数据库"，它能从你的知识库和 GitHub 里找候选，输出对比报告。

**消化**：收藏的终点不是"已读"，而是被理解和应用。Stars 周报总结本周新增并聚类，Release 升级建议在 breaking change 时特别提醒，回忆搜索让你用自然语言找回"去年 star 的那个 SSR 框架"。

### 一个小结

如果让我用一句话概括 Starcat，我会说：

**它把 "以后再看" 的 GitHub Stars，变成了能搜索、能问答、能持续研究的本地知识库。**

它不适合所有人。如果你只有几十个 stars，GitHub 网页就够了。但如果你已经积累了成百上千个收藏，不想让它们继续躺在那里吃灰，也许你会觉得这个东西有用。
