# 微信公众号 / 个人博客

## 文章标题

当 GitHub Stars 变成信息负债,我做了 Starcat

## 正文草稿

GitHub Stars 是开发者最常用、也最容易被误用的功能之一。

看到一个不错的项目,点一下 star。看到一个以后可能用到的库,点一下 star。看到一篇 README 写得很好的工具,也点一下 star。

这个动作太轻了。轻到几年之后,你打开自己的 stars 列表,发现里面有几百上千个项目,但真正能找回、能复用、能说清为什么收藏的,可能只剩一小部分。

Starcat 就是从这个问题开始的。

它不是想重新做一个 GitHub,而是想补上 GitHub Stars 后面的那一段: 收藏之后,怎么整理? 怎么阅读? 怎么找回? 怎么判断这个项目还值不值得用?

![Starcat 管理视图](assets/01-manage-ungrouped.png)

Starcat 是一个 macOS 原生应用。它会把 GitHub Stars 同步到本地,然后用三栏界面管理。左侧是语言、标签、集合和用户信息;中间是 repo 列表;右侧是详情。

详情页里可以看 README,也可以看到标签、笔记、阅读状态、Release 和 AI 入口。

![Starcat 详情页](assets/02-repo-detail-readme.png)

我最开始想解决的是"找回"。比如我知道自己去年 star 过一个 macOS 自动化工具,但不记得名字。单靠 GitHub 网页,这件事并不顺手。Starcat 通过本地缓存、全文搜索、语义搜索、标签和笔记,让这种找回变得更自然。

后来加 AI,也不是为了做一个聊天机器人。AI 在 Starcat 里的位置应该很克制: 它围绕当前 repo 工作,帮你总结 README、建议标签、翻译文档、回答项目相关问题。

![AI Assistant](assets/04-ai-assistant-window.png)

Starcat 的 AI 有一个边界: 可以建议,不能擅自写入。标签必须用户确认,笔记草稿必须用户保存,后续 Agent 报告也应该有来源和预览。

接下来我会把 Starcat 往三个方向推进。

第一是整理。让 AI 帮你处理 untagged,找相似标签,扫描重复或长期不用的仓库,生成 Smart Collections。

第二是发现。相似仓库推荐已经有第一版入口,后面会继续做替代品发现、短名单对比和技术选型报告。

第三是消化。收藏之后不能就结束了。Starcat 后续会做 Stars 周报、Release 升级建议、回忆搜索和笔记草稿,帮助用户把 star 过的项目真正用起来。

如果用一句话概括 Starcat,我会说: 它是一个本地优先的开源项目知识库。

它面向的是那些经常在 GitHub 上研究项目、比较工具、收藏灵感,但又不想让 stars 变成信息垃圾堆的开发者。
