## 正文草稿

这篇不是单纯介绍产品,而是记录我做 Starcat 时遇到的几个设计问题。

Starcat 是一个 macOS 原生应用,目标是把 GitHub Stars 从"收藏夹"变成"本地开源项目知识库"。它同步用户 stars,缓存 README,支持标签、笔记、全文搜索、语义搜索、AI 摘要、Release 订阅和相似仓库推荐。

![管理视图](assets/01-manage-ungrouped.png)

## 问题一: Stars 数据不是只有列表

很多工具把 GitHub Stars 当成列表展示。但当数量上来以后,列表不是最重要的问题。真正的问题是:

- 怎么快速找到以前 star 过的项目?
- 怎么知道一个 repo 是否还活跃?
- 怎么给项目建立自己的分类体系?
- 怎么在选型时比较多个相似项目?

所以 Starcat 的数据层不只缓存 GitHub API 返回的 repo 元数据,还把 README、用户标签、笔记、状态、AI 摘要、Release 状态都放进本地模型里。这样搜索和筛选才有意义。

## 问题二: README 阅读要像本地文档,但内容来自 GitHub

README 是 repo 理解的入口。Starcat 里直接在详情页渲染 README,并做缓存和刷新状态。

![详情页](assets/02-repo-detail-readme.png)

这里的关键不是"把 Markdown 展示出来",而是处理几个边界:

- GitHub README 的图片、相对链接和 GFM 兼容性。
- 缓存命中时要先展示,再后台刷新。
- 翻译和 AI 摘要不能阻塞正常阅读。
- 失败状态不能把整个详情页搞崩。

## 问题三: AI 功能不要做成泛聊天

Starcat 里的 AI 只围绕 repo 上下文工作。它可以总结 README、建议标签、翻译内容、回答当前 repo 相关问题。

![AI Assistant](assets/04-ai-assistant-window.png)

我比较坚持的一点是: AI 不能自动写入用户知识库。标签建议必须确认,笔记草稿必须用户保存,后续 Agent 输出也应该有预览和引用。因为 stars、标签和笔记是用户长期维护的知识资产,不是一次性聊天记录。

## 问题四: 推荐服务要留稳定边界

相似仓库推荐第一版没有直接在客户端接第三方上游,而是加了一个 `starcat-recommend-api` 中转。原因很简单:

- 上游接口和 key 不应该暴露在客户端。
- 客户端只需要稳定消费 `/api/v1/repos/{repo_id}/recommendations`。
- 后续从 SimRepo 换成自研内容向量或行为推荐时,不需要改客户端 UI。

这也是本地优先应用和自建服务之间的平衡: 推荐服务服务于"发现",不是把用户的整个 stars 库搬到服务端。

## 后续: Agent 化但不做聊天壳

我现在更想把 Starcat 往三个方向推进:

- 整理: 批量整理 untagged、合并相似标签、生成 Smart Collections。
- 发现: 替代品发现、技术选型报告、相似仓库推荐。
- 消化: Stars 周报、Release 升级建议、回忆搜索、笔记草稿。

底层会逐步抽一个只读 Agent loop,复用 GitHub API、AnySearch、RepoContextPacker、CodeFlow 和 AI Provider。它不应该变成通用聊天机器人,而应该围绕用户自己的 stars 库产出可引用、可保存、可确认的结果。
