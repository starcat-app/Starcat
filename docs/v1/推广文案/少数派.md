## 正文草稿

### 你 star 过的项目，后来怎么样了？

去年我在做一个 macOS 自动化工具时，想起自己曾经 star 过一个用 Swift 写的剪贴板管理器。那个项目的 README 写得很好，架构也很清晰。我想回头看看它的实现思路。

然后我在 GitHub Stars 页面翻了 20 分钟。没找到。

不是 GitHub 的搜索不行 — 我甚至不记得那个项目的名字，只记得它是 Swift 写的，大概和剪贴板有关。GitHub 的 Stars 页面给了我一个列表，但没有给我"找回"的能力。它知道我被哪些项目吸引过，却不知道我当时为什么 star、后来有没有真的用过、现在还想不想继续关注。

这不是一个搜索问题，这是一个**知识管理问题**。

GitHub Stars 的动作太轻了。看到一个不错的项目，点一下。看到一个以后可能用的库，点一下。看到一个 README 写得很好的工具，也点一下。这个动作轻到没有成本，但几年下来，几百上千个 star 累积的信息负债是有成本的 — 你失去了对自己收藏的掌控。

我做 Starcat 的起点就是这个问题。但在做的过程中，我发现另一个更根本的问题：**收藏只是第一步，真正有价值的是"理解"和"找回"**。

### 不只是管理，是可以问答的知识库

Starcat 的第一版做了基础整理：把 GitHub Stars 同步到本地，用三栏原生界面管理，支持标签、笔记、阅读状态、全文搜索和语义搜索。AI 可以帮你总结 README、建议标签、翻译文档。

![Starcat 管理视图](assets/01-manage-ungrouped.png)

但真正让我兴奋的是 v1.1.0 加上的**知识库 RAG 工作台**。

场景是这样的：你在 Starcat 里打开 RAG 工作台，问一句 "我收藏的 SwiftUI 项目中，哪些用了 Core Data 做本地存储？"。Starcat 不会去搜 GitHub 全网，而是从你自己的知识库 — 你主动筛选入库的那些 repo — 里检索相关片段，生成带引用的回答。每个结论都链接回具体的仓库和段落，你可以点进去验证原文。

![Starcat 详情页](assets/02-repo-detail-readme.png)

为什么这是质的区别？因为传统的 GitHub 搜索只能做关键词匹配。你想找 "用 Core Data 做本地存储的 SwiftUI 项目"，这本身就不是一个搜索词能表达的。你需要的不是一个列表，而是一个能理解你问题、在你自己的项目库里找到答案的工具。

再举一个例子。你正在做技术选型，想比较几个状态管理方案。你把几个候选项目加进知识库，然后在 RAG 工作台里问："这几个项目中，哪些支持 Swift 6 并发？哪个维护最活跃？授权协议分别是什么？"RAG 会跨仓库检索，把这几个项目的信息放在一起比较。这不是"搜一个 repo 的 README"，而是"在你自己的知识库里做跨项目问答"。

### 本地优先，不是口号

Starcat 把 RAG 索引完全放在本地。它用 SQLite FTS5 做全文检索，用本地 embedding 做语义向量检索，两个通道的分数融合后排序。即使你没有网络，知识库问答也能正常工作。

这里有一个我比较坚持的设计原则：**RAG 默认只基于你的知识库回答，不是全部 stars，更不是 GitHub 全网**。

知识库和 stars 是两个概念。你可能有 2000 个 stars，但真正研究过、加了标签和笔记、值得纳入知识库的可能只有 300 个。RAG 在这个边界内工作，每个回答都有来源。资料不足时它会明确说 "你的知识库里没有足够的信息回答这个问题"，而不是去网上凑答案。

这个边界对隐私也很重要。你的知识库在本地，embedding 向量在本地，AI 调用走你自己配置的 provider。Starcat 不需要把任何知识库内容上传到服务端。

### AI 只能建议，不能替你写

另一个约束是：**Starcat 的 AI 不会自动修改你的知识库**。

这不是技术上的做不到，而是产品上的刻意选择。标签体系是你长期维护的知识结构，笔记是你自己的理解，阅读状态反映你的进度。一旦 AI 可以静默修改这些，你对整个系统的信任就没了。

所以 Starcat 的 AI 设计原则是"建议先行，确认后写入"：标签建议必须手动确认，笔记草稿必须手动保存，RAG 问答只读，Agent 报告必须有来源引用和预览。

听起来保守，但对于一个本地知识库来说，这个边界比"自动化"更重要。

### 让 AI 工具链也能读懂你的项目库

除了人用，Starcat 也面向 AI 工具链。它内置了一个本地 MCP Service，可以让 Claude、Codex 或其他本地 Agent 查询你的 stars 库、搜索 repo、获取知识库上下文。

同时还有几个配套能力：
- **RepoContextPacker**：把 repo 的元数据、README、标签、笔记打包成结构化上下文，直接喂给 AI。
- **CodeFlow**：代码级上下文追踪。
- **AnySearch**：统一搜索入口，同时搜本地 + GitHub + 外部源。
- **starcat-cli**：Go 跨平台 CLI，终端里 `starcat mcp` 就能桥接所有能力。

这些功能面向的不是"普通用户"，而是已经在用 AI 工具链做开发的 power user。Starcat 在这个场景里的定位是**本地 repo context hub** — 它不替代你的 AI 工具，而是让你的 AI 工具能读懂你自己的开源项目库。

### 接下来

Starcat 不是完成态产品，它是我自己管理 GitHub Stars 的方式工具化的结果。接下来的路线分三条线：

**整理线**：让混乱的大库先变清楚。批量处理未分类 stars，自动发现近义标签 (如 `cli-tool` 和 `cli-tools`) 并建议合并，扫描功能重叠或长期不维护的仓库簇，用自然语言一句话生成 Smart Collection 筛选规则。原则不变：AI 建议，用户确认。

**发现线**：从 "被动收藏" 到 "主动发现"。相似仓库推荐已经有了第一版，通过独立的 `starcat-recommend-api` 中转，客户端不直连上游推荐接口。后续可以替换为自研的内容向量混合推荐。再下一步是做替代品发现 Agent 和技术选型 Agent — 输入 "我需要一个轻量的本地向量数据库"，它从你的知识库和 GitHub 里找候选，输出带引用和对比表的调研报告。

**消化线**：让收藏真正用起来。Stars 周报总结本周新增项目并按主题聚类，Release 升级建议在 breaking change 时特别提醒，回忆搜索让你用自然语言找回 "去年 star 的那个 SSR 框架"。最终目标是：收藏的终点不是 "已读"，而是被理解、被应用、被沉淀。

### 关于 starcat-app 组织

Starcat 本身是开源的，代码在 [github.com/starcat-app](https://github.com/starcat-app) 组织下。除了主 App，还有几个独立的支撑项目：推荐服务、Trending/Weekly 数据服务、CLI 工具、Agent 工作流定义。如果你遇到 bug 或有功能建议，可以在 `starcat-app/starcat-pro` 提交 issue。

这个组织形式也反映了我的想法：Starcat 不是一个孤立的 App，而是一组围绕 "开源项目研究" 这个问题的工具集合。macOS App 是主要入口，但后续的 CLI、MCP 桥接、Agent 工作流都会是独立的、可组合的模块。
