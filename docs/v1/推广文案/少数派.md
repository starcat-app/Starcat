# 少数派

## 文章角度

少数派适合写完整产品故事,不要像发版公告。重点讲"为什么 GitHub Stars 需要被重新整理",再讲 Starcat 的设计取舍、macOS 原生体验和后续路线。

## 标题备选

- 我做了一个 macOS 上的 GitHub Stars 知识库
- 当 GitHub Stars 从收藏夹变成信息负债,我是怎么整理它的
- Starcat: 把 GitHub Stars 变成能搜索、能阅读、能理解的开源项目知识库

## 正文草稿

我做 Starcat 的起点不是 AI,也不是想重新做一个 GitHub 客户端。

真正的问题是: GitHub Stars 很容易被用坏。

开发者看到一个有意思的项目,点一下 star,告诉自己"以后会看"。这个动作太轻了,轻到几个月后回头看,收藏夹里已经有几百、几千个项目。它们有些是工具,有些是框架,有些是学习材料,有些只是当时觉得名字不错。GitHub 提供了收藏动作,但没有真的帮你把这些收藏变成知识。

Starcat 想解决的是这个问题。

它是一个 macOS 原生应用,会把你的 GitHub Stars 同步到本地,再围绕"整理、阅读、找回、评估"重建一个工作流。左侧是个人资料、语言、标签和集合;中间是 repo 列表;右侧是 README、标签、笔记、Release 和 AI 入口。

![Starcat 管理视图](assets/01-manage-ungrouped.png)

我希望它首先是一个安静的工具。你打开它,不是被一个巨大的 AI 聊天框接管,而是能看到自己的 stars 库: 哪些语言最多,哪些还没分类,哪些项目最近更新,哪些值得继续读。

详情页是 Starcat 的核心。

![Starcat 详情页](assets/02-repo-detail-readme.png)

在这里,README 直接渲染,标签和笔记贴在项目旁边,Release 可以订阅,AI 摘要和对话也都围绕当前 repo 工作。AI 的角色不是替你决定,而是帮你更快进入状态: 这个项目做什么、适合什么场景、有哪些风险、应该打什么标签。

我给 Starcat 设了一个很重要的约束: AI 不能自动改你的知识库。标签建议、笔记草稿、Agent 报告都必须先预览,用户确认后才写入。对于一个本地知识库来说,这个边界比"自动化"更重要。

## 为什么要做成本地优先

GitHub Stars 某种意义上是一张个人兴趣图谱。它透露了你关注什么技术、正在学什么、可能在做什么项目。所以 Starcat 的基本方向是本地优先: stars、标签、笔记、缓存、AI 结果默认都放在本机。

AI provider 也尽量走用户自己的配置。你可以接 OpenAI-compatible、DeepSeek、OpenRouter、Ollama 或本地模型。Starcat 不是想把用户的阅读列表收走再做一个 SaaS,而是尽量把外部能力接回本地工作流。

## 接下来

后续路线会分成三条线。

第一条是整理。比如批量整理 untagged,发现相似标签,扫描重复或长期不用的 repo,用自然语言生成 Smart Collection。很多人不是缺少发现工具,而是已有收藏已经乱到不敢整理。

第二条是发现。Starcat 已经开始做相似仓库推荐,第一版通过自建 `recommend-api` 中转,后续会替换成更稳定的自研推荐。更远一点,我想做替代品发现和技术选型 Agent: 输入一个问题,它从 GitHub、网页和你的本地 stars 里找候选,输出带引用的对比报告。

第三条是消化。收藏不是结束,真正有价值的是后续使用。Stars 周报、Release 升级建议、回忆搜索、笔记草稿,这些功能都在同一个方向上: 让 star 过的东西能被重新看见。

Starcat 现在还不是一个完成态产品。它更像我把自己管理 GitHub Stars 的方式做成了一个工具,再慢慢把"开源项目研究"这个工作流补完整。如果你也经常在 GitHub 上收藏项目,但很少真的回去整理和使用,Starcat 可能会适合你。
