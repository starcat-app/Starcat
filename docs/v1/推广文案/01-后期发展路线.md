# Starcat 后期发展路线

这份文档给推广时解释"Starcat 接下来会往哪里走"。它不适合原封不动贴到所有平台,但可以拆成 Product Hunt maker comment、Indie Hackers build log、少数派文章结尾、HN 评论补充。

## 从 Stars 管理器到开源项目知识库

Starcat v1 先解决一个很具体的问题: GitHub Stars 越积越多以后,它不再是收藏夹,而是一堆"以后再看"的负债。

所以第一阶段做的是整理和找回: 同步 stars,本地缓存 README,用标签、笔记、阅读状态和 Smart Collections 把仓库重新组织起来。AI 摘要和标签建议不是为了炫技,而是为了让用户少打开几个网页,更快判断一个 repo 是什么、适不适合自己、以后怎么找回来。

接下来 Starcat 会更明确地走向三个方向: 整理、发现、消化。

## 整理线: 让大库先变清楚

很多开发者不是没有好工具,而是已经 star 了太多东西。Starcat 后续会围绕"整理线"做更多 AI 辅助:

- Untagged 批量整理: 对未分类仓库生成标签建议,用户预览后分批确认。
- Tag 体系优化: 找出 `tool` / `tools` / `cli-tools` 这种近义标签,给出合并建议。
- 重叠扫描: 找到功能高度相似、长期不用或已经 archived 的仓库簇,帮助用户清理。
- Smart Collection 自然语言生成: 让用户用一句话生成筛选规则,例如"最近半年还活跃的 Swift/macOS 工具"。

这里的原则不会变: AI 可以建议,但不能替用户直接写入标签、删除收藏或改规则。

## 发现线: 不只是 Trending

Starcat 不想只做"今天 GitHub 上什么火"。大众 Trending 有价值,但对个人来说更重要的是: 这个项目和我已有的技术栈有什么关系? 有没有更适合的替代品? 我该不该把它放进下一个项目?

已落地的相似仓库推荐是第一步。现在的 `starcat-recommend-api` 先作为稳定中转,客户端不直连上游推荐接口,后续可以替换为自研内容向量、用户行为和本地 stars 画像的混合推荐。

后续计划包括:

- 替代品发现 Agent: 在单个 repo 详情页里找同类项目,输出对比表。
- 技术选型 Agent: 面向一个技术问题搜索 GitHub、网页和本地 stars,生成带引用的调研报告。
- 短名单对比: 多选几个候选 repo,比较维护活跃度、生态、许可证、集成成本。
- Show HN / HelloGitHub / GitHub Issues 推荐栏目: 把社区发现源接进 Starcat,但仍然回到 repo 这个核心对象。

## 消化线: 让收藏真正用起来

很多 repo 被 star 后就再也没打开过。Starcat 的第三条线是"消化": 帮用户把收藏变成知识和行动。

后续会探索:

- Stars 周报: 总结本周新增 stars,按主题聚类,写出为什么值得看。
- Activity 解读: 已收藏项目发版、归档、安全公告时,给出可读的摘要。
- Release 升级决策: 对 using 状态的仓库重点提醒 breaking changes 和升级风险。
- 回忆搜索 / 本地 RAG: 用户用自然语言问"去年 star 的那个 SSR 框架是什么",Starcat 返回带引用的答案。
- Note 起草和学习路径: AI 可以起草笔记或阅读路线,但保存仍由用户确认。

## Agent 不是聊天壳

Starcat 后续的 Agent 不会定位成通用聊天机器人。它应该围绕用户的 GitHub Stars 知识库工作,能调用 Starcat 已有的本地数据、GitHub API、AnySearch、RepoContextPacker、CodeFlow 和 MCP 能力。

长期 IA 可以收束为一个 Agent 中心,里面是三条线:

- Organize: 整理 stars、标签、Smart Collections。
- Discover: 找替代品、做技术选型、扩展候选项目。
- Digest: 周报、Release 解读、回忆搜索、笔记草稿。

这个方向的关键不是"多一个 AI 按钮",而是让每次 AI 输出都有来源、能沉淀、能回到用户自己的 repo 库里。
