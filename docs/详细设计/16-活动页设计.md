# 活动页设计

> 创建：2026-06-04
> 状态：第一版实施中；已结合 main 分支 HOM-47 Release 订阅实现修订

---

## 1. 背景

GitHub iPhone 端 Explore / 探索页不是一个可由官方 API 直接复刻的成品推荐流。GitHub 官方公开的是 Activity / Releases / Starring / Watching 等底层 REST API，而不是移动端 Explore 的完整数据源和排序算法。

Starcat 当前已经有：

- `Manage`：本地 GitHub Stars 管理、标签、笔记、状态、搜索。
- `Trending`：通过独立 `starcat-trending` 服务获取 GitHub Trending 数据，并有 `trending_repos` / `trending_readmes` 本地缓存。
- `SmartSearchField`：搜索能力已经收敛到 Manage 中栏 toolbar，不再依赖左侧顶栏的 `Search` 入口。
- `Release` 订阅追踪（HOM-47）：main 分支已实现 `ReleaseRecord` / `ReleaseSubscription`、`ReleasesAPI`、`ReleaseMonitor`、`ReleasePoller`、`ReleaseRepository`、`ReleaseTimelineView`、`RepoReleaseSection`。

因此本设计采用：

> 用 `活动` 替换左侧顶栏的 `搜索`，新增 Starcat 自己的 Activity 聚合页。它体验上接近 GitHub Explore / Activity Feed，但数据来源只使用官方 API、Starcat 本地缓存和本地推荐算法。

---

## 2. 产品目标

活动页用于聚合用户关心的项目变化：

- Starcat 公告。
- 仓库 Release。
- 最近 Star。
- 仓库活跃变化。
- 关注用户 / Watching 仓库动态。
- Starcat 本地推荐。

第一版目标：

1. 左侧顶栏从 `管理 / 趋势 / 搜索` 改为 `管理 / 趋势 / 活动`。
2. 点击 `活动` 后，左栏显示固定分类：
   - 全部分类
   - 公告
   - 发行版
   - 星标
   - 仓库
   - 关注
   - 建议
3. 每个分类前使用圆形颜色图标，直接复用 Manage 中 Languages 分类里的 `LanguageIconView`。
4. 中栏显示活动卡片，视觉接近现有 repo card，但字段按活动类型重新设计。
5. 点击活动卡片后，右侧详情页根据活动类型展示不同内容。
6. 支持上次活动分类恢复。切走再切回时恢复本次会话内选择；跨启动可通过 `AppSettings` 保存。

2026-06-04 结合 main 评估后的落地边界：

1. 不重复创建 Release 订阅基础设施，直接复用 HOM-47 已有的 release 表、仓储、轮询和详情页订阅段。
2. Activity 第一版不新增 `activity_items` / `activity_sources` 数据库表，先做本地聚合 ViewModel。
3. 中栏 Activity 卡片独立于 `RepoRowView`，但复用 `RemoteAvatar`、`LanguageBadge`、`StarsBadge`、`MetaBadge`、`RelativeDateBadge` 等共享视觉组件。
4. 右侧新增 `ActivityDetailView`，按 `ActivityKind` 分支展示；不把 Activity 伪装成 Repo 塞回 `RepoDetailView`。
5. 手动刷新 Activity 时只触发 `ReleasePoller.runNow()` 扫描已订阅 Release，不扫描全部 Stars。

非目标：

1. 不复刻 GitHub Mobile Explore 的内部推荐算法。
2. 不使用 GitHub 未公开接口。
3. 第一版不接 GitHub Notifications API。
4. 第一版不做实时消息流。GitHub Events API 官方说明不是实时用途，事件延迟可能从几十秒到数小时。

## 3. 左侧导航设计

### 3.1 Root Page 调整

现有 `SidebarRootPage`：

```swift
enum SidebarRootPage: String, CaseIterable, Identifiable {
    case manage
    case trending
    case search
}
```

建议改为：

```swift
enum SidebarRootPage: String, CaseIterable, Identifiable {
    case manage
    case trending
    case activity
}
```

对应文案与图标：

| Root | 文案 | SF Symbol |
|---|---|---|
| `manage` | 管理 | `folder` |
| `trending` | 趋势 | `chart.line.uptrend.xyaxis` |
| `activity` | 活动 | `bell.badge` 或 `tray.full` |

约束：

- 现有 Search 能力已经由 `SmartSearchField` 承担，替换 root entry 不会丢失搜索能力。
- `activity` 与 `manage` / `trending` 一样是一组左栏分类结构，不应该塞进 `SidebarItem`。

### 3.2 活动分类模型

新增：

```swift
enum ActivityCategory: String, CaseIterable, Identifiable, Sendable {
    case all
    case announcement
    case release
    case star
    case repository
    case following
    case suggestion
}
```

显示建议：

| Category | 中文 | 固定颜色图标来源 |
|---|---|---|
| `all` | 全部分类 | `LanguageIconView(language: "Swift")` |
| `announcement` | 公告 | `LanguageIconView(language: "JavaScript")` |
| `release` | 发行版 | `LanguageIconView(language: "Go")` |
| `star` | 星标 | `LanguageIconView(language: "Python")` |
| `repository` | 仓库 | `LanguageIconView(language: "Rust")` |
| `following` | 关注 | `LanguageIconView(language: "Java")` |
| `suggestion` | 建议 | `LanguageIconView(language: "TypeScript")` |

这里故意使用固定语言色，不新增色板，原因是：

- 视觉上与 Manage 的 Languages 分类保持一致。
- 不新增设计 token。
- 第一版分类数量固定，不需要动态配色。

### 3.3 选择恢复

参考 `HomeView` 当前 Manage / Trending 状态保存方式：

```swift
@State private var selectedActivityCategory: ActivityCategory = .all
@State private var savedActivityCategory: ActivityCategory = .all
```

切换 root page 时：

- 从 Activity 切走：保存 `selectedActivityCategory` 到 `savedActivityCategory`。
- 切回 Activity：恢复 `savedActivityCategory`。
- 跨启动：在 `AppSettings` 增加 `lastActivityCategoryRaw`，解码失败回落 `.all`。

关键约束：

- Activity 选中状态不污染 `HomeViewModel.selection`。
- 切到 Activity 时要清空 `viewModel.selectedRepoID`、`selectedTrendingRepoID` 等其他详情选择，避免右侧详情残留。

## 4. 数据来源

### 4.1 官方 API 能力边界

| 能力 | API | 备注 |
|---|---|---|
| Release | `GET /repos/{owner}/{repo}/releases/latest` / `GET /repos/{owner}/{repo}/releases` | 可拿 tag、name、body、published_at、assets、html_url |
| Repository Events | `GET /repos/{owner}/{repo}/events` | 返回 PushEvent、WatchEvent、ForkEvent、IssuesEvent、PullRequestEvent、ReleaseEvent 等 |
| Received Events | `GET /users/{username}/received_events` | 关注用户 / Watching 仓库收到的活动，非实时 |
| Starred Repos | `GET /user/starred` | Starcat 已经用它做 Stars 同步 |
| Watched Repos | `GET /user/subscriptions` | Watch 才是订阅通知语义 |
| Starring | `PUT /user/starred/{owner}/{repo}` / `DELETE ...` | Starcat 已经有 star / unstar 能力 |

重要边界：

- Stars 是 bookmark 语义，不影响 notifications 或 activity feed。
- Watch / subscription 才是“关注仓库通知”的语义。
- Events API 不是实时 feed，不能承诺即时到达。

参考：

- [GitHub REST Activity API](https://docs.github.com/en/rest/activity)
- [GitHub REST Events API](https://docs.github.com/en/rest/activity/events)
- [GitHub REST Releases API](https://docs.github.com/en/rest/releases/releases)
- [GitHub REST Starring API](https://docs.github.com/en/rest/activity/starring)
- [GitHub REST Watching API](https://docs.github.com/en/rest/activity/watching)

### 4.2 Starcat 第一版数据源

| 分类 | 数据源 | 是否必须登录 | 第一版建议 |
|---|---|---:|---|
| 公告 | 本地 bundled JSON / Markdown | 否 | 先做，保证活动页空库也有内容 |
| 发行版 | Releases API + 本地 release 订阅 / 最近 Star 仓库 | 是 | 先做核心能力 |
| 星标 | 本地 `starred_repos.starred_at` + Stars 同步结果 | 是 | 先做，零额外 API |
| 仓库 | 本地 repo 元数据 + Trending 缓存 | 否 / 是 | 先做，复用现有缓存 |
| 关注 | `received_events` / repo events | 是 | 第二步接入 |
| 建议 | 本地推荐算法 | 否 / 是 | 第二步接入 |

第一版不建议接 `Notifications API`，原因：

- 它会引入更敏感的通知权限与已读 / 完成语义。
- Starcat 当前 OAuth scope 和产品定位主要围绕 stars 管理、Trending、Release。
- Notifications 更接近“收件箱”，而本需求是“活动聚合页”。

## 5. 领域模型

### 5.1 ActivityKind

```swift
enum ActivityKind: String, Codable, Sendable {
    case announcement
    case release
    case star
    case repository
    case following
    case suggestion
}
```

### 5.2 ActivityItem

```swift
struct ActivityItem: Identifiable, Equatable, Sendable {
    let id: String
    let kind: ActivityKind
    let category: ActivityCategory

    let repoID: Int64?
    let repoFullName: String?
    let actorLogin: String?
    let actorAvatarURL: URL?

    let title: String
    let subtitle: String?
    let body: String?
    let htmlURL: URL?

    let createdAt: Date
    let fetchedAt: Date
    let payloadJSON: String?
    let isRead: Bool
}
```

设计说明：

- `id` 使用来源稳定 ID：
  - Release：`release:{releaseID}`
  - Event：`event:{eventID}`
  - Star：`star:{repoID}:{starredAt}`
  - Announcement：`announcement:{slug}`
  - Suggestion：`suggestion:{repoFullName}:{reasonHash}`
- `payloadJSON` 保存原始结构，便于后续扩展详情页字段，避免每次加字段都迁移。
- `repoID` 可空，因为 Trending / 外部 Event 可能只有 `owner/repo`，没有本地 `repos.id`。

## 6. 数据库设计

### 6.1 activity_items

```sql
CREATE TABLE activity_items (
    id TEXT PRIMARY KEY,
    kind TEXT NOT NULL,
    category TEXT NOT NULL,

    repo_id INTEGER,
    repo_full_name TEXT,
    actor_login TEXT,
    actor_avatar_url TEXT,

    title TEXT NOT NULL,
    subtitle TEXT,
    body TEXT,
    html_url TEXT,

    created_at TEXT NOT NULL,
    fetched_at TEXT NOT NULL,
    payload_json TEXT,
    is_read INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_activity_category_created
ON activity_items(category, created_at DESC);

CREATE INDEX idx_activity_repo
ON activity_items(repo_id);
```

### 6.2 activity_sources

```sql
CREATE TABLE activity_sources (
    source_key TEXT PRIMARY KEY,
    etag TEXT,
    last_modified TEXT,
    last_success_at TEXT,
    last_error TEXT
);
```

用途：

- 记录每个 API source 的 ETag / Last-Modified。
- 记录最后成功刷新时间。
- 网络失败时保留错误，UI 可在 toolbar 或状态区提示。

`source_key` 示例：

| source_key | 含义 |
|---|---|
| `releases:repo:apple/swift` | 某个 repo 的 releases |
| `events:received:dong4j` | 当前用户 received events |
| `events:repo:owner/name` | 某个 repo events |
| `announcements:bundled` | 本地公告数据 |

main 分支已经落地 v6 migration：

- `release_subscriptions`

## 7. 网络层设计

### 7.1 ReleasesAPI（main 已实现）

main 分支已新增 `Starcat/Core/Network/GitHubAPI/ReleasesAPI.swift`：

```swift
extension GitHubAPIClient {
    func releases(owner: String, repo: String, perPage: Int = 10) async throws -> APIResponse<[GitHubReleaseDTO]>

当前实现只拉第一页，`perPage` 默认 10，不带 ETag。这符合 HOM-47 Release 订阅追踪的目标：后台巡检只关心最近版本，不做全量历史同步。

```

### 7.2 EventsAPI

extension GitHubAPIClient {

## 8. Repository 与聚合器

### 8.1 ActivityRepository

新增：

- `ActivityRepositoryProtocol`
- `GRDBActivityRepository`
- `ActivityItemRecord`
- `ActivitySourceRecord`

职责：

1. 读取缓存活动列表。
2. 按分类读取。
3. upsert 一批 activity items。
4. 保存 source ETag / Last-Modified。
5. 标记已读。

接口草案：

```swift
protocol ActivityRepositoryProtocol: Sendable {
    func fetch(category: ActivityCategory, limit: Int, offset: Int) async throws -> [ActivityItem]
    func upsert(_ items: [ActivityItem]) async throws
    func markRead(id: String) async throws
    func sourceState(key: String) async throws -> ActivitySourceState?
    func updateSourceState(_ state: ActivitySourceState) async throws
}
```

第一版暂不实现本节。原因：

- main 已有 `releases` 缓存，Release 活动不需要再写一份 activity cache。
- 星标 / 仓库 / 建议可以从本地 `repos` 直接派生。
- Events API 尚未接入，第一版没有必须持久化的外部 activity source。

待接入 `received_events` / `repository_events` 后，再按本节补 `activity_items` / `activity_sources`。

### 8.2 ActivityAggregator

第一版新增 `ActivityViewModel`，先承担轻量聚合职责：

- `refreshAnnouncements()`
- `refreshRecentStars()`
- `refreshReleases()`
- `refreshRepositories()`
- `refreshSuggestions()`

后续接 Events API 后，再拆出 `ActivityAggregator` actor，负责把多个来源归一化成 `ActivityItem`。

```swift
actor ActivityAggregator {
    func refreshAnnouncements() async throws
    func refreshRecentStars(userID: Int64) async throws
    func refreshReleases(userID: Int64) async throws
    func refreshReceivedEvents(username: String) async throws
    func refreshSuggestions(userID: Int64?) async throws
}
```

设计约束：

- 聚合器不直接更新 UI。
- 聚合器只写数据库；`ActivityViewModel` 再从 `ActivityRepository` 读。
- 每个 source 独立失败，不让一个 API 失败清空整个活动页。
- 使用 ETag / Last-Modified 时，304 表示保留旧缓存，不生成错误态。

### 8.3 Release 刷新范围

不能对用户所有 Stars 全量轮询 Release。即使 OAuth 有 5000 req/hour，1800+ repo 全扫也太浪费。

第一版建议优先级：

1. 用户显式订阅 Release 的 repo。
2. GitHub Watch / subscriptions 中的 repo。
3. 最近 Star 的前 50 个 repo。
4. 当前正在详情页查看的 repo 懒加载 latest release。

后台轮询周期：

- 4-6 小时一次。
- 用户主动点击刷新时只刷新当前分类相关 source。

## 9. ViewModel 设计

新增 `ActivityViewModel`：

```swift
@MainActor
@Observable
final class ActivityViewModel {
    private(set) var items: [ActivityItem] = []
    private(set) var isLoading: Bool = false
    private(set) var isRefreshing: Bool = false
    private(set) var loadError: String?
    private(set) var lastRefreshedAt: Date?

    var selectedCategory: ActivityCategory = .all
    var selectedItemID: String?

    func loadCached() async
    func refresh(forceNetwork: Bool) async
    func select(_ item: ActivityItem)
}
```

加载策略：

1. 进入 Activity 页：先读缓存，立即上屏。
2. 如果无缓存：显示 skeleton / loading。
3. 用户点击刷新：后台刷新当前分类相关 source。
4. 刷新失败但有缓存：保留当前列表，只显示轻量错误提示。
5. 刷新失败且无缓存：显示 error state。

这与 Trending / README 的 SWR 思路保持一致。

## 10. UI 设计

### 10.1 左栏分类

`SidebarView` 新增：

```swift
@Binding var selectedActivityCategory: ActivityCategory
```

渲染：

```swift
List(selection: $selectedActivityCategory) {
    Section {
        activityCategoryRow(.all)

        if activityCategoriesExpanded {
            ForEach(ActivityCategory.allCases.filter { $0 != .all }) { category in
                activityCategoryRow(category)
            }
        }
    } header: {
        Button {
            activityCategoriesExpanded.toggle()
        } label: {
            HStack {
                Text("activity.category.section")
                Spacer()
                Text("6")
                disclosureChevron(isExpanded: activityCategoriesExpanded)
            }
        }
        .buttonStyle(.plain)
        .focusEffectDisabled()
    }
}
.listStyle(.sidebar)
```

实现口径：

- header 文案为 `activity.category.section`（活动分类），必须进 String Catalog。
- `全部分类` 行常驻在 header 下方，具体分类随 header 折叠 / 展开。
- header 右侧数量只统计具体分类数，不把 `全部分类` 算进去；这个口径与 Trending 的 Languages 一致。
- 分类行本身不显示数量，避免把静态分类误读成动态活动条数。

早期最简结构如下，第一版 UI 优化后不再采用：

```swift
List(selection: $selectedActivityCategory) {
    Section {
        ForEach(ActivityCategory.allCases) { category in
            activityCategoryRow(category)
        }
    } header: {
        Text("activity.categories")
            .font(.headline)
    }
}
.listStyle(.sidebar)
```

注意：

- 如果 root page 是 Activity 且未登录，仍可展示 `公告 / 建议`，但 `发行版 / 关注 / 星标` 可显示登录提示或空态。
- 活动页不强制登录。公共公告和 Trending-derived 建议可离线显示。

### 10.2 中栏活动卡片

新增 `ActivityRowView`，不要直接复用 `RepoRowView`，因为活动不是 repo，字段结构不同。

但应复用视觉组件：

- `RemoteAvatar`
- `LanguageBadge`
- `StarsBadge`
- `MetaBadge`
- `RelativeDateBadge`
- `ListRowRevealModifier`
- 现有 row selected / hover 的视觉语言

卡片布局：

```text
头像 / 类型图标    title                              时间
                  subtitle
                  body 摘要（1-2 行）
                  chips: Release / v1.2.0 / Swift / unread
```

不同类型展示建议：

| 类型 | title | subtitle | chips |
|---|---|---|---|
| 公告 | Starcat 公告标题 | 功能说明 / 版本说明 | `公告` |
| 发行版 | `owner/repo 发布了 v1.2.0` | release name / body 首段 | `Release` / `Prerelease` / asset 数 |
| 星标 | `你 Star 了 owner/repo` | repo description | language / stars |
| 仓库 | `owner/repo 有新变化` | pushed / metadata 摘要 | language / stars / forks |
| 关注 | `actor 在 owner/repo ...` | event payload 摘要 | event type |
| 建议 | `推荐 owner/repo` | 推荐理由 | language / score |

### 10.3 右侧详情页

新增 `ActivityDetailView`，按 `ActivityKind` 分支。

不要把所有逻辑塞进 `RepoDetailView`，原因：

- `RepoDetailView` 已经承担 Manage repo 与 Trending repo 两套详情。
- Activity 详情有 announcement / following / suggestion 这类非 repo 内容。
- 继续加分支会让详情页职责失控。

详情分支：

| 类型 | 详情内容 |
|---|---|
| 公告 | 标题、发布时间、完整 Markdown / Text、相关入口 |
| 发行版 | repo、tag、name、published_at、body、assets、打开 GitHub Release |
| 星标 | repo 摘要、starred_at、打开 repo、跳到 Manage 详情 |
| 仓库 | repo 元数据、README 入口、外链 |
| 关注 | actor、event type、payload 摘要、跳 GitHub |
| 建议 | 推荐理由、匹配语言 / topics、来自 Trending / 本地行为的证据 |

交互约束：

- 详情顶部面板需要与 Manage / Trending 详情页保持同款渐变背景：优先使用关联 repo 的主语言色；如果活动卡片没有 repo 或 repo 没有语言标识，则使用当前 Activity 分类色。
- 左侧头像卡背景同样要跟随当前 Activity 选中卡片变化。`ActivityItem.accentColor` 是单一取色入口，已经收口“repo 语言色优先、分类色兜底”的规则；`HomeView → SidebarView → SidebarHeaderView` 只透传最终 `Color`，避免 sidebar 反向理解 Activity 的数据模型。
- 星标 / 仓库 / 建议这三类 repo-backed 详情必须和 Manage repo 详情同构：顶部 repo 元信息面板按自然高度展开，不在顶部面板里再套固定高度滚动；README WebView 是主滚动区，向下滚动时通过公共 `CollapsibleRepoMetadataPanel` 折叠顶部面板，回到顶部再展开。
- repo-backed 详情的头像、stats、Watchers、分享、AI 入口等交互必须复用 `RepoMetadataHeaderView` 里的公共实现，保持 `.buttonStyle(.plain) + .focusEffectDisabled() + .pressableHover()`、tooltip 和确认弹窗行为一致。不要在 Activity 里再维护一份简化版 repo header。
- 右上角不额外放“打开 GitHub”链接按钮；与 Manage / Trending 详情页一致，左上角头像 / 类型图标承载打开对应页面的动作。
- 头像点击使用 `Button { NSWorkspace.shared.open(url) }`，并保持 `.buttonStyle(.plain) + .focusEffectDisabled() + .pressableHover()`，让 hover / focus 行为与现有详情页头像一致。
- 发行版 assets 的复制动作复用 `CopyFeedbackButton`，与 AI 摘要 / 对话中的复制反馈一致：复制后 icon 切换为 `checkmark.circle.fill`、颜色切绿色、1.5s 后回退。
- 星标 / 仓库 / 建议这三类 repo-backed 详情复用现有 `ReadmeViewModel` + `ReadmeStateView` + `ReadmeWebView` 展示 README。Activity 详情自持独立 `ReadmeViewModel`，不能复用 HomeView 中给 Manage / Trending 的实例，避免污染主详情页 README 状态。

## 14. 实施顺序

推荐拆成 5 个小步：

1. 文档确认
   - 本文档确认后再实现。
   - 不先做 GitHub API 内部接口逆向。
2. 导航与静态 UI
   - `Search` root 改 `Activity`。
   - 左栏分类列表落地。
   - 中栏 / 右栏先用本地 mock activity。
3. 数据库与 Repository
   - 新增 `activity_items` / `activity_sources`。
   - 如同步 Release，则同时落 `release_subscriptions` / `releases`。
4. 接入第一批真实数据
   - 本地公告。
   - 最近 Star。
   - Release latest / releases。
5. 接入第二批聚合
   - `received_events`。
   - repo events。
   - 本地 suggestion。

第一版最小可交付：

- 左侧 Activity 分类可选。
- 中栏有公告、最近 Star、Release 三类活动。
- 右侧能显示 announcement / star / release 三种详情。
- 数据可缓存，重启后仍能看到上次活动。
