### 问题与解决方案

#### Q-01 `@MainActor` Coordinator 的 deinit 隔离错误

- **问题**：`SearchCoordinator.deinit` 读取 `activeTask` 时，Swift 编译器报“main actor-isolated property can not be referenced from a nonisolated context”。
- **影响**：P1-03 首次构建失败；不影响搜索运行期逻辑。
- **采用方案**：删除 deinit 中的兜底 cancel；由每次新搜索和 `reset()` 显式取消旧 Task，generation 继续阻止迟到结果写回。
- **未采用方案**：没有把 Coordinator 改成独立 actor，也没有为一个析构兜底引入锁或 `nonisolated(unsafe)`。
- **后续可调整点**：如果未来 Coordinator 生命周期脱离主窗口，可改为由持有者在 disappear / close 时显式调用 `reset()`。

#### Q-02 Swift 6 将测试 Suite 的静态 helper 推断为 MainActor 隔离

- **问题**：`@MainActor` 测试 Suite 内的纯数据构造方法被继承为 actor 隔离，传入 `@Sendable` Provider 闭包时编译器拒绝跨隔离调用。
- **方案**：将不读取任何 UI / actor 状态的 `makeRepo`、`makeCandidate` 明确标记为 `nonisolated`，保留测试主体在 MainActor 上验证 `SearchCoordinator`。
- **影响**：仅约束测试辅助代码的并发语义，不改变生产实现。

#### Q-03 MainActor 类型不能作为 initializer 默认参数直接构造

- **问题**：`SearchHistoryStore()` 写在 `SearchCenterViewModel.init` 的默认参数表达式中时，默认参数按 nonisolated context 求值，Swift 6 拒绝调用 MainActor initializer。
- **方案**：参数改为 optional，在已经明确为 MainActor 的 initializer body 内构造默认实例。
- **影响**：依赖注入能力不变，测试仍可传入独立 HistoryStore。

#### Q-04 GitHubAPIClientProtocol 新端点会使全部旧 Mock 失去 conformance

- **问题**：直接增加 `searchRepositories` requirement 会要求所有历史测试 Mock 实现与自身场景无关的方法。
- **方案**：协议 extension 提供明确抛出 `NetworkError.invalidRequest` 的默认实现，生产 actor 提供真实覆盖；搜索测试需要 Mock 时再显式覆盖。
- **影响**：旧测试零修改，误用未实现搜索的 Mock 会立即失败而不是返回伪数据。

#### Q-05 定向测试在 LaunchServices 阶段等待 worker materialize

- **问题**：`GitHubRepositorySearchTests` 已完成 App 与测试 target 编译签名，但 test runner 长时间停在 `waiting for workers to materialize`，与项目已记录的 Xcode IDE / `testmanagerd` 竞争症状一致。
- **方案**：终止无输出的挂起运行，不清理 DerivedData、不杀用户进程；以测试 target 编译成功作为当前小任务门禁，最终验收阶段统一重试全量测试。
- **影响**：当前没有断言执行结果；不是代码编译失败，保留到 F-02 明确复核。

## 1. 最终结论

Starcat 的搜索应拆成两个边界清晰、互不替代的入口：

1. **Manage 快速过滤**：保留当前 toolbar `SmartSearchField`，继续提供本地关键词搜索和本地 AI 语义搜索，结果内联覆盖 Manage 中栏。
2. **全局搜索中心**：基于 `d9bd9f7` 的 Spotlight / Command Palette 交互演进，使用 `⌘K` 或独立 toolbar 按钮打开，聚合本地仓库、GitHub 全站仓库和 AnySearch 网页资料。

不把 GitHub / Web / AI Ask 全部继续塞进 `SmartSearchMode`。toolbar 搜索是“缩小当前库”，搜索中心是“跨来源发现与行动”，两者解决的问题不同。

```text
Manage SmartSearchField
├── Keyword  -> GRDB FTS5
└── Semantic -> BYOK embedding + SQLite vector cache + Swift cosine

Global Search Center (Cmd+K)
├── Local    -> FTS5 / optional semantic rerank
├── GitHub   -> GitHub REST Search API
└── Web      -> AnySearch REST API (opt-in)
```

## 2. 现状判断

### 2.1 当前主线已有能力

- `SmartSearchField` 已支持 `.keyword` / `.semantic`、Return 提交、模式持久化和语义索引刷新。
- `HomeViewModel.reloadItems()` 已有取消旧任务、错误状态、列表更新和语义命中映射。
- `SemanticSearchService` 已按本地优先路线落地：用户 Provider 生成 embedding，本地 SQLite 缓存，Swift 内存计算 cosine。
- `UnifiedRepoRow`、`RepoMetadataHeaderView`、详情 scaffold、`MultiSelectionStore` 等已形成多来源复用基础。
- `GitHubAPIClientProtocol` 已有 repo / README / star / unstar 等端点，可继续增加 repository search。

### 2.2 `d9bd9f7` 值得保留的部分

- `⌘K` 全局入口和 window-level overlay，不污染当前 Sidebar / 中栏筛选状态。
- `idle -> searching -> results -> actions -> summary` 的渐进式交互。
- 搜索结果选中后提供 Open / Copy / Ask / Summarize 等 repo command。
- 用户明确执行 Open 后才写回三栏详情。

### 2.3 `d9bd9f7` 不应直接搬回的部分

- 只搜索本地 starred repo，无法承接 GitHub / Web 多来源。
- ViewModel 同时承担检索、动作、分享和摘要，职责过宽。
- 最多 8 条平铺结果，不支持分区、分页、来源状态和跨来源去重。
- 新建约 1000 行独立 UI，和当前 `UnifiedRepoRow`、详情 scaffold、共享 action service 重复。
- 使用硬编码中英文文案，未接入 String Catalog。

## 3. 产品边界

### 3.1 Manage 快速过滤

适合回答：

- “我收藏的仓库里哪个是 Rust CLI？”
- “查找笔记里提到 SQLite 的项目。”
- “用自然语言找适合做后台任务的框架。”

约束：

- 只搜索本地 Starcat 知识库。
- 继续使用当前中栏和右栏，不弹浮层。
- Keyword 和 Semantic 共享 query，但不自动同时调用 embedding。
- 不承担 GitHub 全站发现和网页搜索。

### 3.2 全局搜索中心

适合回答：

- “有没有新的 MCP Server 项目？”
- “搜索 GitHub 上 stars > 1000 的 SwiftUI 组件。”
- “找某个项目的官方文档、教程和社区讨论。”
- “从结果中直接 Star、打开详情或发起 AI 分析。”

约束：

- 不改变用户当前 Manage / Trending / Activity 上下文，关闭后原页面原样恢复。
- 本地结果先返回；GitHub / Web 独立加载和独立失败。
- AI 只按用户动作触发，不因输入一次搜索而批量生成摘要。
- 私有仓库信息默认不发送给 AnySearch。

- `⌘K`：从主窗口任意页面打开搜索中心。
- toolbar：增加独立 `sparkle.magnifyingglass` 按钮，tooltip 为“全局搜索（⌘K）”。
- 当前 `SmartSearchField` 保留，不替换成 `d9bd9f7` 的 Search or ask 胶囊。

### 4.2 浮层布局

┌──────────────────────────────────────────────────────────┐

├──────────────────────────────────────────────────────────┤

### 4.3 默认搜索策略

默认 Scope 为 `All Repositories`：

1. 立即并行启动 Local FTS5 与 GitHub Search。
2. Local 通常先返回并先上屏。
3. GitHub 返回后按 repo identity 与 Local 合并状态，而不是重复显示同一 repo。
4. AnySearch Web 不默认自动请求；用户切到 Web、点击“搜索网页”，或在设置中主动开启“在 All 中包含 Web”后才调用。
5. Semantic 不默认参与 All；用户点击“AI 语义重排”后，只对本地候选重排。

这样可以避免一次普通输入同时消耗 GitHub Search、AnySearch 和 embedding 三套额度。

Repo 结果动作：

- 在 Starcat 打开
- Star / Unstar
- 在 GitHub 打开
- 复制 URL
- AI 摘要
- Ask
- 分享

Web 结果动作：

## 5. 搜索架构

### 5.1 Provider 协议

```swift
protocol SearchProvider: Sendable {
    var source: SearchSource { get }
    func search(_ request: SearchRequest) async throws -> SearchProviderPage
}
```

首批 Provider：

| Provider | 数据源 | 返回类型 | 是否默认启用 |
|---|---|---|---|
| `LocalKeywordSearchProvider` | `RepoRepository.searchFTS` | Repo candidate | 是 |
| `LocalSemanticSearchProvider` | `SemanticSearchService` | Repo candidate + score | 用户主动 |
| `GitHubRepositorySearchProvider` | GitHub REST Search API | Repo candidate | 是 |
| `AnySearchWebProvider` | AnySearch REST API | Reference candidate | 否，用户 opt-in |

### 5.2 Coordinator 职责

`SearchCoordinator` 只负责：

- 管理 query、scope、filter 和 request generation；
- 并行调用 Provider；
- 取消旧请求，拒绝迟到结果覆盖新 query；
- 按 source 独立维护 loading / result / error；
- repo 去重与本地状态补全；
- GitHub 分页和 session cache。

它不负责 Star、AI、Share、打开浏览器等业务动作。

### 5.3 统一候选模型

```swift
enum SearchCandidate: Identifiable, Hashable {
    case repository(RepositoryCandidate)
    case reference(ReferenceCandidate)
}

struct RepositoryCandidate: Identifiable, Hashable {
    let identity: RepoIdentity
    var card: RepoCardViewData
    var sources: Set<SearchSource>
    var localRepoID: Int64?
    var isStarred: Bool
    var semanticScore: Double?
}

struct ReferenceCandidate: Identifiable, Hashable {
    let url: URL
    let title: String
    let snippet: String?
    let domain: String
    let source: SearchSource
}
```

Repo 去重键优先级：

1. GitHub repo ID；
2. 标准化后的 `owner/name`；
3. 不用 title 或 URL 猜测 repo identity。

Local 与 GitHub 命中同一 repo 时合并为一条，`sources = [.local, .github]`，并补上本地 Star、笔记、标签、README、AI 摘要等状态。

## 6. GitHub Search 方案

### 6.1 接入方式

客户端直连 GitHub REST Search API，不增加 Starcat 自建代理：

```text
SearchCenter -> GitHubRepositorySearchProvider
             -> GitHubAPIClient.searchRepositories(...)
             -> GET /search/repositories
```

- 复用现有 OAuth token、网络错误、rate-limit header 和 endpoint 组织方式。
- 不硬编码固定 rate limit 数字；以响应头和 GitHub 返回的 reset / retry 信息为准。
- 未登录时可以匿名搜索公开仓库，但 UI 必须展示匿名额度状态。

### 6.2 MVP 筛选

- Language
- Topic
- Minimum Stars
- Created After
- Pushed After
- Sort：Best Match / Stars / Forks / Updated
- Order：Asc / Desc（Best Match 不展示）

所有 qualifier 由结构化 builder 生成，禁止 View 层手工拼接 query string。

### 6.3 分页

- 每页 30 条，滚动到底加载下一页。
- 新 query / filter 改变时取消旧页请求并重置 pagination。
- 到达 GitHub 返回上限后明确提示，不制造“还能继续加载”的假状态。

## 7. AnySearch 方案

### 7.1 定位

AnySearch 只承担两项能力：

1. 搜索中心的 Web reference provider；
2. AI 摘要的可选 external context provider。

它不替代 GitHub Repository Search，不承担源码分析，也不把网页结果伪装成 Repo。

### 7.2 配置与隐私

设置位置：`Settings -> Integrations -> AnySearch`。

- 总开关默认关闭。
- API Key 存 Keychain。
- 匿名模式必须由用户明确开启，不能因 Key 缺失静默降级。
- “在 All 中包含 Web”默认关闭。
- “用于 AI 摘要外部上下文”默认关闭。
- 私有 repo external context 永久默认关闭；开启时需要单独风险确认。

若配置了无效 API Key，直接展示鉴权错误，不自动改走匿名请求。

### 7.3 Web 结果规则

- 规范化 URL，移除常见 tracking query 后去重。
- 官方域名、项目文档、GitHub Discussions 等来源可提高排序权重。
- snippet / content 只做展示与临时上下文，不直接写入用户知识库。
- 第一阶段不新增 `repo_external_references` 表；“保存为资料”确认有真实使用需求后再设计。

## 8. 详情页复用

Repo 搜索结果点击后不新造第五套详情页：

1. 先用 repo identity 查询本地 repository / registry。
2. 本地命中时直接复用完整 repo detail scaffold。
3. 未命中时使用现有 ephemeral repo 规则：展示 metadata + README，隐藏依赖本地 ID 的 Tags / Notes / Release 私有区块。
4. 用户 Star 成功后触发本地状态刷新；是否立即 upsert 本地 Repo 由 Star 同步策略统一决定，搜索模块不私自写一套半成品记录。

`id = 0` 只能作为 UI 临时占位，不能进入任何数据库写入路径。

## 9. 缓存与历史

### 9.1 搜索结果缓存

- Local：以数据库为真源，不增加缓存层。
- GitHub：仅做进程内 LRU / session cache，建议 5 分钟；不落 GRDB。
- AnySearch：仅做进程内 session cache，建议 15 分钟；第一阶段不落 GRDB。
- 缓存 key 必须包含 normalized query、scope、filters、page 和 provider 配置版本。

### 9.2 搜索历史

- 保存用户实际提交过的 query，不保存逐字符草稿。
- UserDefaults 最多保留最近 50 条，按 normalized query 去重并前移。
- 支持单条删除和全部清空。
- 私有 repo 派生 query、AI 生成 query 不自动进入历史。

## 10. AI 增强边界

### 10.1 语义搜索

当前事实源：

```text
Provider 生成 embedding
-> repo vector 存 SQLite
-> query vector 临时生成
-> Swift 内存 cosine 排名
```

搜索中心第一阶段只复用现有服务，不引入 pgvector、自建后端或新的向量数据库。

### 10.2 AI 摘要外部上下文

第二阶段才接 AnySearch context：

- 用户在单个 repo 上主动点击 AI 摘要；
- 最多生成 2-3 个受控 query；
- 去重、域名筛选、字符预算后形成 `ExternalSearchContext`；
- Prompt 明确标记外部资料为“不可信补充上下文”；
- 摘要 UI 展示实际使用的来源链接。

任何外部网页内容都不能触发自动标签写入或用户数据变更。

## 12. 分阶段实施

### Phase 1：搜索中心骨架 + 本地搜索

- 从 `d9bd9f7` 提炼 overlay、`⌘K`、键盘导航和 phase 交互。
- 接入 Local FTS5。
- 复用 `UnifiedRepoRow` 和当前详情页打开路径。

### Phase 2：GitHub Repository Search

- 新增 GitHub search endpoint、DTO、query builder 和协议 mock。
- 接入筛选、分页、rate-limit 状态和 repo 去重。
- 未 star repo 复用 ephemeral detail；支持 Star / Open GitHub。

验收：Local 与 GitHub 可并行返回；同一 repo 只显示一次；失败互不影响。

### Phase 3：AnySearch Web

- 新增 Integrations 设置、Keychain key、client 和 provider。
- Web scope 手动触发；支持打开、复制和临时 AI context。

验收：默认安装不发送 AnySearch 请求；启用后 Web 失败不影响 Local / GitHub。

### Phase 4：AI 与资料沉淀

- 本地 semantic rerank。
- AI 摘要 external context provider。
- 根据真实使用数据再决定是否增加 external references 持久化。

## 15. 成功标准

1. Manage 快速搜索零回归，keyword / semantic 行为保持当前契约。
2. `⌘K` 在任意主页面可用，关闭后原上下文不变。
3. Local 结果先展示，GitHub / Web 可独立加载、独立失败。
4. 同一 GitHub repo 跨来源只显示一次，并正确展示本地状态。
5. 默认配置不向 AnySearch 发送请求，不泄露私有 repo 信息。
6. 远端搜索不引入 Starcat 自建服务端。
7. 新实现复用现有 row、detail scaffold 和 action service，不形成第二套 repo UI 体系。
