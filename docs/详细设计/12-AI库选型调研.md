## 一、调研背景

Phase 2-AI 需要客户端 SDK 调 OpenAI / 兼容 provider（BYOK 模式由用户自带 key）。在 `项目结构` 层面，客户端层位于 `Starcat/Features/AI/`，向上接 ViewModel，向下经 `URLSession` 出网。

选型有 3 个事实约束（来自 `CLAUDE.md` + 已落地代码）：

1. **平台**：macOS 15+（已定，为了 Liquid Glass API），`watchOS` 不做
2. **Swift**：编译器 6.0 + 语言模式 5 + `@Observable`
3. **Keychain**：已有 `CryptoManager`（D-16 已收口），任何 SDK 都不能自己管 key

## 二、候选库

### 2.1 jamesrochabrun/SwiftOpenAI

- **仓库**：[jamesrochabrun/SwiftOpenAI](https://github.com/jamesrochabrun/SwiftOpenAI)
- **最低平台**：iOS 15+ / **macOS 13+** / watchOS 9+ / Linux
- **Swift**：5.9+
- **License**：MIT
- **API 风格**：类化（`OpenAIServiceFactory.service(apiKey: ...)`）
- **覆盖**：OpenAI 全套（Audio、Chat、Response、Embeddings、Fine-tuning、Batch、Files、Images、Moderations、Assistants、Realtime）
- **多 provider**：通过 `OpenAIServiceFactory` 接 OpenAI-兼容端点（Azure、Anthropic、Gemini、Ollama、Groq、xAI、OpenRouter、DeepSeek、**AIProxy**）
- **配套**：另有 [CLI](https://github.com/jamesrochabrun/SwiftOpenAICLI) 和 [MCP](https://github.com/jamesrochabrun/SwiftOpenAIMCP) 独立包

### 2.2 MacPaw/OpenAI

- **仓库**：[MacPaw/OpenAI](https://github.com/MacPaw/OpenAI)
- **最低平台**：跨平台（Apple 全家桶 + Linux）
- **Swift**：5.9+
- **License**：MIT
- **API 风格**：协议化（`OpenAIProtocol`），可注入 mock
- **覆盖**：OpenAI 全套（含 Responses API、Assistants、Images、Audio、Embeddings、Moderations），**内建 MCP 集成**
- **多 provider**：`.relaxed` 解析选项 + `Configuration.customHeaders` 接 OpenAI-兼容端点（Gemini、DeepSeek、Perplexity、OpenRouter）
- **结构化输出**：3 种姿势——`jsonSchema`（手写）/ `derivedJsonSchema`（Pydantic 风格，从 `Codable` 类型自动生成）/ `dynamicJsonSchema`（`Encodable` 字典）
- **背书**：MacPaw（公司）维护，社区驱动

### 2.3 teunlao/swift-ai-sdk

- **仓库**：[teunlao/swift-ai-sdk](https://github.com/teunlao/swift-ai-sdk)
- **最低平台**：全平台（含 visionOS / Wasm / Android）
- **Swift**：6.0+
- **License**：Apache 2.0
- **API 风格**：函数式（`streamText(model:prompt:)`），对齐 Vercel AI SDK（TypeScript 生态）
- **覆盖**：**37 个 provider 原生模块**（OpenAI、Anthropic、Google、Groq、xAI、Vercel、TogetherAI、Amazon Bedrock、Cohere、Mistral、DeepSeek、Ollama……）
- **结构化输出**：`Schema.codable(MyType.self)` 直接从 `Codable` 类型出 schema
- **MCP + Middleware**：内建
- **成熟度**：v0.17.6（pre-1.0），908 commits / 62 releases，135 stars

## 三、评估维度

从 Starcat 实际需求提炼 7 个维度（这些维度的具体业务意义在 `11-Phase2-AI与Release详细设计.md` 里都展开过，这里只作"打分维度"用）：

| 维度 | 来源需求 | 重要度 |
|---|---|---|
| D1. **BYOK 友好** | 用户在 `AISettingsView` 自配 key + 自定义 Base URL | 必选 |
| D2. **macOS 15 / Swift 6 兼容** | 平台最低版本 | 必选 |
| D3. **结构化输出 DX** | 标签推荐需要"模型 → `[TagSuggestion]` 数组" | 高 |
| D4. **测试友好**（协议化 / 可 mock） | `StarcatTests` 现有 `URLProtocolStub` 模式 | 高 |
| D5. **Provider 扩展性** | P1 阶段就要接 DeepSeek + 自建代理 | 高 |
| D6. **API 稳定性 / 维护活跃度** | 长期维护，不被弃坑 | 中 |
| D7. **Streaming 一等公民** | AI 摘要/标签建议要实时反馈 | 中 |

## 四、评分矩阵

评分 1–5（5 = 最优）。

| 维度 | SwiftOpenAI | MacPaw/OpenAI | swift-ai-sdk |
|---|---|---|---|
| D1. BYOK 友好 | 4（`OpenAIServiceFactory` 单独配 URL） | 4（`Configuration` 改 host/port） | 5（每个 provider 是独立 SwiftPM product，按需引入） |
| D2. macOS 15 / Swift 6 | 4（macOS 13+，Swift 5.9，向上兼容） | 4（跨平台，Swift 5.9+） | **5**（Swift 6.0+，原生匹配） |
| D3. 结构化输出 DX | 3（手写 JSON Schema） | **5**（3 种姿势，文档齐全） | **5**（`Schema.codable` 最优雅） |
| D4. 测试友好 | 2（`OpenAIServiceFactory` 抽得不够深） | **5**（`OpenAIProtocol` 标准注入） | 4（`LanguageModel` 协议，但闭包风格 mock 稍绕） |
| D5. Provider 扩展性 | 3（OpenAI-兼容适配要写多份） | 3（同上，但 `.relaxed` 解析省事） | **5**（37 providers 即开即用） |
| D6. 稳定性 / 活跃度 | 4（个人维护，活跃） | **5**（MacPaw 背书，社区） | 2（pre-1.0，135 stars） |
| D7. Streaming | 4（`AsyncSequence` 流式） | 4（`AsyncThrowingStream`） | **5**（Vercel AI SDK 风，UI 集成开箱即用） |
| **总分（满分 35）** | **24** | **30** | **31** |

## 五、决策

**主选 `MacPaw/OpenAI`**（MVP 阶段）。**`swift-ai-sdk` 作升级候选**，不立即用。**`SwiftOpenAI` 不选**。

### 5.1 为什么不选 `SwiftOpenAI`

总分 24 是三者最低，但更关键的是 **D4（测试友好）= 2**——它的 `OpenAIServiceFactory.service(apiKey:)` 抽得不够深，**没法做轻量级 mock**。Starcat 现有测试约定是 `URLProtocolStub` 直接拦 `URLSession`（见 `StarcatTests/URLProtocolStub.swift`），SwiftOpenAI 的内部 URL 路径直写死，stub 维护成本高。

### 5.2 为什么主选 `MacPaw/OpenAI`（不是 `swift-ai-sdk`）

总分 30 vs 31，差距不大。**D6（稳定性）= 2 vs 5** 是决定性的——`swift-ai-sdk` 还在 0.17.x，pre-1.0 意味着 API 还会变。Starcat 客户端是付费产品，**不应用 0.x 依赖做核心链路**。等它 1.0 再切。

加分项：
- **D3（结构化输出）= 5**——`derivedJsonSchema([TagSuggestion].self)` 写一次就好，直接喂 Swift 类型
- **D4（测试友好）= 5**——`OpenAIProtocol` 协议化注入，符合 Starcat 现有测试套路
- **D5（Provider 扩展）= 3** 偏低，但 P1 阶段 3 个 provider（OpenAI / DeepSeek / 自建代理）已经够用
- **D1（BYOK）= 4**——`Configuration` 改 `host` + `basePath` + `customHeaders` 即可接自建代理

### 5.3 为什么 `swift-ai-sdk` 是升级候选

- D2 / D3 / D5 / D7 = 5，**纯能力上是最强的**
- 37 providers 一行 swap（`openai("gpt-5")` → `anthropic("claude-4.5-sonnet")`）——这正是 Phase 2-AI 设计里"Provider 切换"想要的效果
- **触发重新评估的信号**：
  1. 官方 1.0 release
  2. 三个 provider 已不够用（用户开始要 Claude / Gemini / Bedrock）
  3. MacPaw/OpenAI 出现 6 个月以上无 commit

## 六、落地计划

> 这一节是"现在该做什么"，对应 `功能实现总览.md §4.2` 的 W6 AI 任务清单。

### 6.1 依赖接入

在 `project.yml` 加：

```yaml
packages:
  OpenAI:
    url: https://github.com/MacPaw/OpenAI
    from: "1.0.0"   # 等正式 1.0 出来再锁；当前 0.x 阶段用 branch = main
```

跑 `xcodegen generate` 同步 `.xcodeproj`。

### 6.2 抽象层（不耦合 SDK 细节）

新建 `Starcat/Features/AI/AIProvider.swift`：

```swift
protocol AIProvider: Sendable {
    func chat(
        systemPrompt: String,
        userPrompt: String,
        jsonSchema: AIJSONSchema?,
        model: String
    ) async throws -> AIChatResponse

    func streamChat(
        systemPrompt: String,
        userPrompt: String,
        jsonSchema: AIJSONSchema?,
        model: String
    ) -> AsyncThrowingStream<AIChatChunk, Error>
}
```

新建 `Starcat/Features/AI/OpenAIProvider.swift`——内部包 `OpenAIProtocol`，对外只暴露 `AIProvider`。

这样未来想换 `swift-ai-sdk` 或加 Claude，**只换 `OpenAIProvider` 实现**，业务层（`AISummaryService` / `AITagService` / `AITrendingService`）零改动。

### 6.3 测试 Spike（W6 Day 1）

加 `StarcatTests/OpenAIProviderTests.swift`：

- 用 `URLProtocolStub` 拦截 MacPaw/OpenAI 的出网请求
- 测：① 单轮 chat ② 结构化输出（`derivedJsonSchema`）③ Streaming 4 个 chunk 后中断 → `Task.cancel()` 行为
- 测 key 走 `TestEnvironment.isRunning` 门控，不触发真 Keychain

### 6.4 自建代理兼容

W6 末做：把 `Configuration` 改成读取 `AISettingsView` 的"自定义 Base URL"字段：

```swift
let config = OpenAI.Configuration(
    token: apiKey,
    host: "api.deepseek.com",  // 或自建代理域名
    port: 443,
    scheme: "https"
)
```

## 七、升级路径

如果未来切到 `swift-ai-sdk`，迁移成本评估：

| 改动面 | 工作量 | 原因 |
|---|---|---|
| `OpenAIProvider` 内部实现 | 中 | API 风格从"实例方法"变"顶层函数 `streamText(model:prompt:)`" |
| 抽象层 `AIProvider` | 无 | 协议契约不变 |
| 业务层（Service / ViewModel） | 无 | 它们只依赖 `AIProvider` |
| 单元测试 | 小 | `URLProtocolStub` 仍可用（底层是 `URLSession`） |

——结论：**业务层零成本**，只看 `OpenAIProvider` 这个 adapter 的实现。
