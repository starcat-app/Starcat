## 1. 背景与目标

发展规划 §9 已经定调："使用规则评分 + AI 解释"。本设计把这一句话拆成可落地的数据、计算、UI、AI 边界，作为 HOM-92 父任务下若干子任务的共同参考。

需要解决的问题：

1. 用户 star 时常凭兴趣，但**判断是否值得长期依赖**需要额外事实（活跃度、文档完整度、License、安全风险）。
2. 现阶段 `repos` 表只保存 GitHub Repo 元数据中的常量字段（stars、forks、archived、license 名）。**缺少 Community Profile、Issues/PR 节奏、最近 commit/release 节奏、安全公告**等画像所需数据。
3. AI 不能"凭空"给健康度结论，必须建立在**可解释、可追溯**的本地规则评分之上；AI 只负责把分数翻译成自然语言。

第一版目标：

- 在详情页顶部和 Insights 页给出"Health / Maintenance / License / Security / Latest Release"五项指标，**全部可下钻到具体事实**。
- 不依赖 Starcat 后端服务，全部计算在本地完成。
- 不引入新的远程服务（OpenSSF Scorecard 留作可选增强）。
- 算分结果**可被 Discover 排序、技术选型助手、Security 解释复用**，因此分数与维度都需稳定的对外契约（见 §8）。

非目标：

- 不做 SBOM、不做依赖图深度分析（属于发展规划第五阶段，不在 HOM-92 范围内）。
- 不做后台批量重算所有 stars 的健康度（API 配额无法支撑），保持"详情页打开时按需抓取 + 后台局部刷新"。
- 不输出"AI 风险等级"作为唯一字段（必须先有规则分，再有 AI 文本解释）。

## 2. 与现有实现的对接边界

为避免重复造轮子，明确这次**新增什么、复用什么**：

| 组件 | 现状 | 本次方案 |
|---|---|---|
| `GitHubAPI` 枚举 | 已有 `repo` / `readme` / `releases` 端点 | 新增 `communityProfile` / `repoStatsParticipation` / `issuesSearch` / `securityAdvisoriesForRepo` 等端点 |
| `Repo` 表 | 已有 license（仅名称）、archived、pushed_at 等 | 不动主表 schema；新增 `repo_health_facts`（事实层）与 `repo_health_scores`（评分层）两张副表 |
| `ReleaseRepository` (HOM-47) | 已有 Release 抓取与缓存 | 健康度的"最近 release"事实直接复用 `release_records`，不再二次抓取 |
| `RepoAIInsightService` (Phase 2 AI) | 已有 README 摘要 / 标签推荐 | 复用其 Provider 抽象与 AI 设置；新增 `HealthExplainerTask`，不污染摘要逻辑 |
| `RepoMetadataHeaderView` | 已有详情页头部 | 新增 `RepoHealthBadgeBar` 子视图嵌入，**不改造现有头部** |

复用原则：**只新增、不重构**。一切现有模块的内部实现都不动；只在 ViewModel/Repository 层加新方法。

## 3. 数据源与缓存层

### 3.1 需要的 GitHub API

| API | 用途 | 调用时机 | 速率风险 |
|---|---|---|---|
| `GET /repos/{owner}/{repo}/community/profile` | README/LICENSE/CONTRIBUTING/Code of Conduct/Issue Template 完整度（preview header） | 详情页打开 / 周级刷新 | 低，1 次/repo |
| `GET /repos/{owner}/{repo}/stats/participation` | 最近 52 周 commit 计数 | 详情页打开 | 中，首次返回可能是 202，需要二次轮询 |
| `GET /repos/{owner}/{repo}/stats/contributors` | 贡献者分布（判断 bus factor） | 详情页打开 | 中，同上 202 行为 |
| `GET /search/issues?q=repo:owner/repo+is:issue+state:open` | 开 issue 数 | 详情页打开 | **走 Search API 配额，限制 30 req/min**，需独立节流 |
| `GET /search/issues?q=repo:owner/repo+is:issue+is:closed+created:>=N` | 最近 N 天关闭 issue 数（判断响应度） | 详情页打开 | 同上 |
| `GET /repos/{owner}/{repo}/license` | License SPDX id（补足主表 license 字段） | 详情页打开 / 仅在主表 license 为空时 | 低 |
| `GET /advisories?affects=...` 或 `GET /repos/{owner}/{repo}/security-advisories` | 已知安全公告 | 详情页打开 | 低 |
| OpenSSF Scorecard `https://api.securityscorecards.dev/projects/github.com/{owner}/{repo}` | 第三方质量评分（**可选**，仅作为 AI 解释里的引用，不计入主分） | 用户在设置中显式开启时 | 中，外部 API |

调用约束：

1. **统一走 `GitHubAPI` 枚举 + 现有网络层**（保持 token 注入、UA、retry-after 处理一致）。Search API 在 `RateLimitHandler` 里加独立计数桶。
2. **Stats 接口的 202 行为**：首次调用 GitHub 返回 202 时，让前端显示"统计正在生成"，后台 60s 后重试一次；连续 3 次仍 202 则放弃，仅以现有数据评分（不阻塞 UI）。
3. **所有调用都走 `repo_health_facts.fetched_at` 缓存**，TTL 默认 7 天，可在设置中调整为 1 天 / 7 天 / 30 天。

### 3.2 新增数据库表

不动 `repos` 主表，新增两张表。Schema 与 `01-数据库设计.md` 风格保持一致：

```sql
-- 事实层：每个 repo 一行，存所有原始事实数据（JSON 存复合结构）
CREATE TABLE repo_health_facts (
    repo_id INTEGER PRIMARY KEY,                -- FK -> repos.id

    -- 来自 Community Profile API
    has_readme INTEGER,                          -- 0/1/NULL（NULL 表示尚未抓取）
    has_license INTEGER,
    has_contributing INTEGER,
    has_code_of_conduct INTEGER,
    has_issue_template INTEGER,
    has_pull_request_template INTEGER,
    community_health_percent INTEGER,            -- GitHub 自带的 0-100 分

    -- 来自 stats/participation
    commits_last_4w INTEGER,                     -- 最近 4 周 commit 数
    commits_last_52w INTEGER,                    -- 最近 52 周 commit 数

    -- 来自 stats/contributors
    contributors_count INTEGER,
    top_contributor_commit_share REAL,           -- 0.0 - 1.0，>= 0.8 视为单维护者风险

    -- 来自 search/issues
    open_issues_count INTEGER,
    closed_issues_90d INTEGER,
    median_issue_response_days REAL,             -- 可选，第一版可留 NULL

    -- 来自 license API（补足）
    license_spdx_id TEXT,                        -- "MIT" / "Apache-2.0" / "NOASSERTION" / NULL
    license_risk_tier TEXT,                      -- 见 §6：permissive / weak_copyleft / strong_copyleft / proprietary / none / unknown

    -- 来自 advisories
    known_advisories_count INTEGER,
    critical_advisories_count INTEGER,

    -- 来自 release_records 关联派生（不重复存）
    -- 通过 SELECT 计算 latest_release_at，不在表里冗余

    fetched_at TEXT NOT NULL,                    -- 本批事实抓取完成时间 (ISO8601)
    partial INTEGER DEFAULT 0,                   -- 1 表示部分接口失败 / 202 未就绪
    error_summary TEXT,                          -- 失败简述，仅 UI 提示用

    FOREIGN KEY (repo_id) REFERENCES repos(id) ON DELETE CASCADE
);

CREATE INDEX idx_repo_health_facts_fetched_at ON repo_health_facts(fetched_at);

-- 评分层：每次重算覆盖一行；保留 detail JSON 供 UI 展示"为什么是 82 分"
CREATE TABLE repo_health_scores (
    repo_id INTEGER PRIMARY KEY,                 -- FK -> repos.id

    overall_score INTEGER NOT NULL,              -- 0-100
    activity_score INTEGER NOT NULL,             -- 0-100
    docs_score INTEGER NOT NULL,
    community_score INTEGER NOT NULL,
    risk_score INTEGER NOT NULL,                 -- 0-100，越高越安全（与 risk_flag 不同）
    security_score INTEGER NOT NULL,

    maintenance_status TEXT NOT NULL,            -- active / slowing / dormant / archived / unknown
    license_risk_tier TEXT NOT NULL,             -- 同上 §6

    detail TEXT NOT NULL,                        -- JSON：每条规则命中的事实 + 扣分 / 加分 + 文案
    rule_version TEXT NOT NULL,                  -- 规则版本号，规则升级时强制重算

    computed_at TEXT NOT NULL,

    FOREIGN KEY (repo_id) REFERENCES repos(id) ON DELETE CASCADE
);

CREATE INDEX idx_repo_health_scores_overall ON repo_health_scores(overall_score);
CREATE INDEX idx_repo_health_scores_status ON repo_health_scores(maintenance_status);
CREATE INDEX idx_repo_health_scores_license ON repo_health_scores(license_risk_tier);
```

设计要点：

1. **事实和分数分两张表**：事实层稳定，规则迭代只需重算 `repo_health_scores` 而不重新打 GitHub。
2. **`detail` 用 JSON 而不是新建关联表**：每个 repo 的命中事实数量有限（10~20 条），用 JSON 简化读取与 UI 展示；类型用 Codable 结构在 Swift 侧严格化（见 §4.3）。
3. **`rule_version`**：规则升级后用 `MIGRATION` 触发的批量任务重算，不依赖用户主动刷新。
4. **不在主表加字段**：避免影响现有所有读写路径；`overall_score` 仅在需要时通过 `LEFT JOIN repo_health_scores ON repo_health_scores.repo_id = repos.id` 取得（NULL 表示尚未计算，UI 渲染"--"）。

## 4. 评分规则（核心：可解释）

### 4.1 总分构成

总分采用**加权求和**，五个维度权重固定，可在 `HealthRule.swift` 中以常量形式声明、便于审查：

| 维度 | 权重 | 满分 | 说明 |
|---|---|---|---|
| Activity（活跃度） | 25 | 25 | 最近 push / commit / release 频率 |
| Docs（文档） | 20 | 20 | Community Profile 完整度 |
| Community（社区响应） | 20 | 20 | Issue/PR 响应、贡献者分布 |
| Risk（项目风险标记） | 15 | 15 | archived、无 license、长期无 release、stale |
| Security（安全） | 20 | 20 | 已知 advisories（关键级别越多扣得越重） |
| **合计** | **100** | **100** | overall_score = 五项相加 |

### 4.2 规则明细（第一版）

每条规则使用**绝对扣分制**：每个维度从满分开始，命中的负面事实直接扣分；命中正面事实不再加分（避免双向规则互相抵消），保持分数与维度一一对应、可解释。

> 表中 *阈值* 与 *分值* 在 `HealthRule.swift` 中以 `static let` 暴露，便于代码评审与单元测试。下表给出第一版数值（保守口径，可在试用后微调）：

**Activity（满分 25）**

| 事实 | 阈值 | 扣分 | 文案（中文） |
|---|---|---|---|
| `pushed_at` | > 365 天 | -15 | 超过一年未 push |
| `pushed_at` | 180–365 天 | -10 | 近一年未 push |
| `pushed_at` | 90–180 天 | -5 | 三个月以上未 push |
| `commits_last_4w` | == 0 | -5 | 最近 4 周无 commit |
| 最近 release `published_at` | > 365 天 或无 release | -5 | 长期未发布版本 |

**Docs（满分 20）**

| 事实 | 阈值 | 扣分 | 文案 |
|---|---|---|---|
| `has_readme` | 0 | -10 | 无 README |
| `has_license` | 0 | -5 | 无 LICENSE |
| `has_contributing` | 0 | -2 | 无 CONTRIBUTING |
| `has_code_of_conduct` | 0 | -1 | 无 Code of Conduct |
| `has_issue_template` | 0 | -2 | 无 Issue/PR 模板 |

> Docs 维度也直接接受 GitHub 自带的 `community_health_percent` 作为参考（写入 detail 但不直接折算到分数），便于解释。

**Community（满分 20）**

| 事实 | 阈值 | 扣分 | 文案 |
|---|---|---|---|
| `contributors_count` | == 1 | -8 | 只有单一贡献者 |
| `contributors_count` | 2–3 | -3 | 贡献者人数很少 |
| `top_contributor_commit_share` | >= 0.9 | -5 | 维护严重依赖单人 |
| `open_issues_count` | > 500 且 `closed_issues_90d` < 10 | -5 | Issue 严重积压 |
| `median_issue_response_days` | > 60 或为 NULL 且 issue 多 | -2 | Issue 响应慢（可选） |

**Risk（满分 15）**

| 事实 | 阈值 | 扣分 | 文案 |
|---|---|---|---|
| `is_archived` | == true | -15 | 仓库已归档（直接扣完） |
| `license_spdx_id` | NULL / "NOASSERTION" | -10 | 无明确 License |
| 最近 release | > 730 天 且 `pushed_at` 同样 stale | -5 | 长期无更新（双重确认 stale） |

**Security（满分 20）**

| 事实 | 阈值 | 扣分 | 文案 |
|---|---|---|---|
| `critical_advisories_count` | >= 1 | -15 | 存在关键级安全公告 |
| `known_advisories_count` | >= 3 | -5 | 多条历史安全公告 |

最低 0 分，扣分溢出按 0 计；详细命中规则记录在 `detail` JSON 里，UI 展开后可看到每条扣分原因。

### 4.3 detail JSON 结构

```swift
struct HealthScoreDetail: Codable {
    struct Dimension: Codable {
        let key: String                       // "activity" / "docs" / ...
        let max: Int                          // 维度满分
        let score: Int                        // 该维度最终得分
        let hits: [Hit]                       // 命中的事实
    }
    struct Hit: Codable {
        let factKey: String                   // "pushed_at_180_365" 等稳定 ID
        let delta: Int                        // 负数：扣分；0：参考事实
        let messageZh: String                 // 中文文案（i18n 由 String Catalog 兜底）
        let messageEn: String?                // 第一版可留空，后续接 i18n
        let evidence: String?                 // "最后 push: 2024-11-02" 等可点开看的证据
    }
    let dimensions: [Dimension]
    let ruleVersion: String
}
```

UI 展开"Why 82?"时直接渲染该结构，**不再二次计算**。

### 4.4 maintenance_status 派生

不另外存事实，从已有字段直接派生：

| 条件（按顺序判断，首匹配生效） | maintenance_status |
|---|---|
| `is_archived == true` | `archived` |
| `pushed_at > 365 天` 且 `commits_last_4w == 0` | `dormant` |
| `pushed_at` 在 90–365 天 或 `commits_last_4w < 4` | `slowing` |
| 其余有数据 | `active` |
| 无任何抓取数据 | `unknown` |

`maintenance_status` 单独存一列，是为了支持 Discover 排序（如"过滤掉 dormant"）与 Insights 分类（"长期无人维护"）走索引而不解析 JSON。

### 4.5 不做的事

- **不做加权机器学习模型**：规则可解释优先，模型黑盒不接受。
- **不做"Starcat 综合分"压过 GitHub 原生 community_health_percent**：两者并列展示，由用户判断。
- **不做评分历史时间序列**：第一版只保存最新一份；趋势在第二版评估（需要额外表）。

## 5. 维护活跃度指标

`maintenance_status` 与 Activity 维度的事实组合后，在 UI 上呈现为：

```text
Maintenance Active          ← 主标签
最近 push: 3 天前            ← 关键事实
最近 4 周 commit: 47         ← 关键事实
最近 release: 12 天前        ← 关键事实
```

不引入新的"活跃度评分"独立字段（避免与 Activity 维度重复）；`maintenance_status` 作为分类标签使用，Activity 维度的分数作为数值使用，二者职责分离。

Insights 页"维护活跃度雷达"分类直接对 `repo_health_scores.maintenance_status` 做分组查询：

- 最近恢复活跃：`computed_at` 在最近 30 天内、且 `maintenance_status` 从 `dormant` / `slowing` 变成 `active`（需要新增 `maintenance_status_prev` 列或 fact 表保留上一次值，第一版可先不做差分，单纯展示 `active` 列表）。
- 长期无人维护：`maintenance_status IN ('dormant', 'archived')`。
- 单维护者风险：`detail` JSON 中含 `factKey = "top_contributor_share_90"`（**第一版可暂用 `contributors_count == 1` 简化**）。

## 6. License 风险分类

License 风险不计入主健康分（已经在 Risk 维度有"无 License 扣 10 分"），但作为独立标签存在，因为**技术选型助手需要按风险等级筛选**，比"分数高低"更直接。

分类规则（写在 `LicenseRiskClassifier.swift`，单元测试覆盖）：

| `license_spdx_id` | risk_tier | UI 标签 | 说明 |
|---|---|---|---|
| `MIT` / `Apache-2.0` / `BSD-2-Clause` / `BSD-3-Clause` / `ISC` / `Unlicense` / `0BSD` | `permissive` | 宽松 | 商用基本无风险 |
| `MPL-2.0` / `LGPL-2.1` / `LGPL-3.0` / `EPL-2.0` | `weak_copyleft` | 弱传染 | 需注意动态/静态链接边界 |
| `GPL-2.0` / `GPL-3.0` / `AGPL-3.0` | `strong_copyleft` | 强传染 | 商用前必须法务评估 |
| `NOASSERTION` / NULL / 空 | `none` | 无 License | 默认无授权，禁止商用 |
| 其余已知非 OSI（Custom / Proprietary） | `proprietary` | 私有协议 | 阅读原始 LICENSE |
| 未在白名单且非空 | `unknown` | 未识别 | 提示用户查看原文 |

UI 配色（与现有视觉规范对齐）：

| risk_tier | 颜色（macOS Native） |
|---|---|
| `permissive` | `Color.green.opacity(0.85)` |
| `weak_copyleft` | `Color.yellow` |
| `strong_copyleft` | `Color.orange` |
| `none` / `unknown` | `Color.red` |
| `proprietary` | `Color.purple` |

License 列表与配色作为常量集中在一个文件，便于后续按需扩充，不引入第三方 license 库（与`第三方资源使用记录.md`保持节制原则一致）。

## 7. Insights UI 设计

### 7.1 详情页头部 Badge Bar

按发展规划 §9.5 的形态，新增 `RepoHealthBadgeBar` 视图，**插入到现有 `RepoMetadataHeaderView` 下方**，不修改现有头部组件：

### 7.2 Insights 顶层页

发展规划 §6.6 已经定调 `Insights` 顶层导航位（与 Manage / Trending / Activity 同级）。本 HOM-92 范围**只做 Insights 下的 Project Health / Maintenance / Licenses 三个子页**；Contribution Opportunities 与 Risk Radar 分别由其它任务承担。

```text
Insights
├── Project Health    （按 overall_score 排序）
├── Maintenance       （按 maintenance_status 分组）
└── Licenses          （按 license_risk_tier 分组）
```

中栏 / 右栏复用 `Activity` 页的两栏模式（卡片 + 详情），但卡片字段重写为健康度相关。

### 7.3 数据契约（对外）

凡是 Discover、技术选型、Security 想引用健康度数据时，**只读 `repo_health_scores` 表**，不要直接读 `repo_health_facts`，也不要在调用方重新算分。导出契约：

```swift
struct RepoHealthSummary {
    let repoId: Int64
    let overallScore: Int
    let dimensions: [String: Int]           // "activity" -> 18, ...
    let maintenanceStatus: MaintenanceStatus
    let licenseRiskTier: LicenseRiskTier
    let computedAt: Date
    let ruleVersion: String
}
```

放在 `Core/Health/RepoHealthSummary.swift`，作为跨模块边界类型。

## 8. AI 解释层

### 8.1 边界

- AI **只生成文本解释**，不产生分数，不修改分数。
- AI 输入是已经算好的 `HealthScoreDetail`，**不读原始 GitHub 数据**。
- AI 输出是一段 2-4 句的中文描述，存到 `repo_health_scores.detail` JSON 的 `aiExplanation` 字段中（懒生成）。

### 8.2 与 §15 AI 调用链的集成

复用 15 号文档定义的多服务商 BYOK 调用链，新增一个 task 类型：

| task | 默认模型策略 | 备用模型 |
|---|---|---|
| `repoHealthExplain` | 走"轻量解释类"任务，默认与 README 摘要共享同一组配置 | 用户可在设置中单独选 |

输入 Prompt 模板（中文版，存在 `Resources/Prompts/health_explain_zh.md`）：

```text
你是 Starcat 项目健康度解释器。请根据下列结构化分数与命中事实，生成一段 2-4 句的中文说明，
帮助用户判断是否值得长期依赖这个仓库。

要求：
1. 直接给结论，不要复述"根据数据"等套话。
2. 必须引用至少一条具体事实（如"最近 4 周仅 2 次 commit"）。
3. 不得编造未在输入中出现的事实。
4. 不超过 80 字。

输入：
- 仓库：{full_name}
- 总分：{overall_score}
- 维度分：{dimensions_json}
- 主要扣分原因：{top_hits_json}
- 维护状态：{maintenance_status}
- License：{license_spdx} ({license_risk_tier})
```

### 8.3 失败兜底

- AI 失败 / 用户未配置 AI 时，前端直接渲染**规则模板文案**：
  - 取 `detail.dimensions` 中扣分最多的两个维度
  - 拼成 "该仓库 {维度1 文案}，{维度2 文案}"
  - 例："该仓库已超过一年未 push，且只有单一贡献者，建议谨慎引入生产环境。"
- 这一模板在 `HealthExplanationFallback.swift` 中实现，单元测试覆盖；保证**无 AI 也能给解释**。

## 10. 风险与开放问题

| 风险 | 处理 |
|---|---|
| Search API 配额限制（30/min） | 加独立计数桶；详情页一次性请求合并；列表批量重算明确禁用 Search 类调用 |
| stats/* 接口 202 行为 | 前端显示 "统计生成中"；后台 60s 重试 3 次后放弃 |
| `community_health_percent` 已含部分 docs 信号 | 不重复计分；展示 GitHub 原值作为参考，Starcat docs 维度独立打分 |
| 私有仓库 advisory 接口权限差异 | 第一版仅支持公开仓库；私有仓库 security 维度直接置满分并在 UI 标注"未评估" |
| 规则版本升级后历史数据需重算 | `rule_version` 字段控制；启动时若发现 score.rule_version 与代码常量不一致，丢入后台重算队列 |
| OpenSSF Scorecard 是否引入 | 第一版**不**引入；留接口预留位，后续作为可选增强（用户在设置中开关） |

开放问题（留给子任务在实施前确认）：

1. `repo_health_scores` 是否需要与 CloudKit 同步？倾向 **否**（属于派生缓存），但 `rule_version` 跨设备口径需要统一。
2. Insights 顶层导航位与现有 `Activity` / `Manage` / `Trending` 的占位顺序由 UI 任务统一决定，本设计不强约定。
3. AI 解释的多语言：第一版只做中文，英文版由 §10 国际化任务统一处理。
