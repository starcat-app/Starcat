## 1. BYOK 设置与 MacPaw/OpenAI Adapter

### 1.1 技术选型过程

- 继续采用 `docs/详细设计/12-AI库选型调研.md` 的结论：第一版使用 `MacPaw/OpenAI`。
- 接入方式选择 `branch: main`，原因是调研文档已说明当前阶段按 main 接入；本次 `xcodebuild -resolvePackageDependencies` 实际解析到 `c9342438e70e6c9a93d09220a8855459deaba00a`。
- Provider 产品路线收敛为 OpenAI-compatible：OpenAI / DeepSeek / OpenRouter / Ollama / LM Studio 都通过 Base URL + API Key + 模型名配置表达，不引入 Starcat 自建 AI 代理。

### 1.2 落地方案

- `project.yml` 增加 `OpenAI` SwiftPM 包，并重新执行 `xcodegen generate`。
- 新增 `Features/AI/AIClient.swift`，定义 Starcat 自己的 `AIClientProtocol` 和 `AIClientConfiguration`。
- 新增 `Features/AI/OpenAIClient.swift`，内部使用 MacPaw/OpenAI 的 `OpenAIProtocol`，对外只暴露 `chat` / `embedding` / `testConnection`。
- `AppSettings` 增加 AI 偏好：
  - `aiProvider`
  - `aiBaseURL`
  - `aiChatModel`
  - `aiEmbeddingModel`
  - `smartSearchMode`
- `AISettingsView` 从临时 `@State` 占位改为真实 BYOK 设置页：
  - API Key 读写 `KeychainManager.storeAIKey/loadAIKey/deleteAIKey`
  - Base URL / 模型 / 搜索模式写入 `AppSettings`
  - `测试连接` 发起一次短 embedding 请求验证 Key、Base URL 和 embedding 模型

### 1.3 最终实现方式

- API Key 不进入 `UserDefaults`，继续走项目已有 AES-GCM 本地加密文件 `credentials.json`。
- MacPaw/OpenAI 的 `Configuration` 不直接接收完整 Base URL，本次在 `OpenAIClient.makeSDKConfiguration` 中把用户输入拆成 `scheme` / `host` / `port` / `basePath`。
- 实测 MacPaw/OpenAI 当前 main 的 `EmbeddingsQuery` 签名与 README 示例不同，最终按源码使用 `EmbeddingsQuery(input: .string(input), model: model)`。
- 设置页 Provider 切换会自动填充默认 Base URL 和模型，但用户仍可手动覆盖。

### 1.4 验证

- `xcodebuild -resolvePackageDependencies -scheme Starcat` 通过。
- `xcodegen generate` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' build` 通过。
- `xcodebuild -scheme Starcat -destination 'platform=macOS,arch=arm64' -only-testing:StarcatTests/AppSettingsTests test` 通过，`AppSettings` suite 9 项全绿。

### 1.5 待 dong4j 审计确认

- **需审计确认，但已按最佳方案实现**：Provider 列表第一版只做 OpenAI-compatible 兼容入口，不单独引入 Gemini 原生 SDK；Gemini 如需使用，后续建议通过 OpenAI-compatible 网关或另开 adapter。
- **需审计确认，但已按最佳方案实现**：连接测试优先验证 embedding，而不是 chat。理由是语义搜索是第一阶段硬依赖，embedding 测通后 chat 通常只剩模型名差异。

## 2. AI 语义搜索与 SQLite 向量缓存

### 2.1 技术选型过程

- 入口延续 `docs/详细设计/13-智能搜索栏交互设计.md` 的系统 `.searchable(..., placement: .toolbar)` 方案，不重新自绘搜索框。
- 结果展示选择“中栏列表内联展示”，不弹独立窗口：
  - 优点：不破坏 Starcat 现有三栏工作流，选中结果后右侧 README / 详情仍然复用；
  - 优点：列表过滤、状态筛选、多选等能力不用为弹窗重做；
  - 代价：无法像 Spotlight 一样展示长解释，但仓库管理场景更需要连续浏览和对比。
- 向量存储选择 SQLite BLOB + Swift cosine：
  - 不用 sqlite-vss / sqlite-vec 动态扩展，避免 macOS 沙盒签名、extension 加载路径和分发风险；
  - Starcat MVP 规模在几千个 starred repo，内存 cosine 排名足够；
  - 后续若达到 10k+ 或需要 ANN，再把 `RepoEmbeddingRepository` 替换为 sqlite-vec / 独立向量索引。
- 向量计算选择 BYOK provider 调用 OpenAI-compatible embeddings，而不是 Starcat 自建服务端。这样与“本地优先、不自建 AI 代理默认路线”一致。

### 2.2 落地方案

- 数据库新增 v5 migration：
  - `repo_embeddings(repo_id, model, content_hash, dimensions, embedding, indexed_text, updated_at)`
  - `ai_summaries(repo_id, model, source_hash, summary_json, generated_at)` 先随 v5 建好，供单仓智能化复用
- 新增 `RepoEmbedding` 模型，把 `[Float]` 编码为 Float32 BLOB。
- 新增 `GRDBRepoEmbeddingRepository`，提供按 repo ids 读取和批量 upsert。
- `AIClientProtocol` 增加 `embeddings(inputs:model:)`，`OpenAIClient` 通过 MacPaw/OpenAI 的 `.stringList` 批量生成向量，避免逐仓库发请求。
- 新增 `SemanticSearchService`：
  - repo 元数据转稳定索引文本；
  - SHA256 `content_hash` 判断缓存是否过期；
  - 缺失 / 过期向量按 32 条一批生成并写入 SQLite；
  - 查询时生成 query embedding，加载候选 repo 向量后用 cosine similarity 排名。
- `HomeViewModel` 增加 `smartSearchMode`、`isSemanticIndexing`、`semanticHitMap`：
  - keyword 模式继续走原 FTS5；
  - semantic 模式先取全量 starred repos，再由 `SemanticSearchService` 返回排序结果；
  - 搜索结果不写入 sidebar list cache，避免污染 All Stars / Tags 等分类缓存；
  - semantic 排名不再套用户 sortOption，避免破坏 cosine 排序。
- `RepoListView` toolbar 增加搜索模式菜单和语义索引刷新按钮；`RepoRowView` 在 compact/card 两种密度显示 AI 分数与命中说明。

### 2.3 最终实现方式

- 搜索入口：仍使用右上角系统搜索框，旁边 `sparkles` 菜单切换 Keyword / AI Semantic。
- 搜索结果：
  - 直接渲染在中栏 repo list；
  - compact 行显示 `sparkles + 百分比分数`；
  - card 行显示“命中原因 + 分数”；
  - 选中后右栏详情不变。
- 索引刷新：
  - 搜索时自动补缺失 / 过期 embedding；
  - AI 模式下 toolbar 额外提供手动刷新索引按钮，适合切换 embedding model 或大量同步后使用。
- 命中说明第一版采用本地轻量解释：仓库名 / 描述 / topics 直接命中时给出对应原因，否则显示 AI 向量相似度。没有让 LLM 为每条结果生成解释，避免一次搜索触发大量 chat 调用。

### 2.5 待 dong4j 审计确认

- **需审计确认，但已按最佳方案实现**：语义搜索结果不弹独立窗口，而是复用中栏列表展示。理由是 Starcat 的核心任务是“浏览、筛选、打开详情、继续管理”，内联结果最少破坏现有工作流。
- **需审计确认，但已按最佳方案实现**：第一版不用 sqlite-vss / sqlite-vec，使用 SQLite BLOB + Swift cosine。理由是 MVP 数据规模可控，动态扩展分发风险高于收益。
- **需审计确认，但已按最佳方案实现**：命中说明不调用 LLM 逐条生成，先做本地解释。理由是每次搜索都生成 LLM explanation 会显著增加延迟和 BYOK 成本。
