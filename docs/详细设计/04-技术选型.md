## 四、平台兼容性

### 4.1 最低系统要求

|| 平台 | 最低版本 | 说明 |
|------|---------|------|
| macOS | 15 (Sequoia) | 兼容 Liquid Glass API（macOS 26+）|
| iOS | 18 | iOS 18+ 支持 SwiftUI 最新特性 |
| iPadOS | 18 | 与 iOS 保持一致 |
| watchOS | 11 | watchOS 11+ 支持 |

### 4.2 Swift 版本

| 项目 | 版本 | 说明 |
|------|------|------|
| Swift 编译器 | 6.0 | Xcode 16 内置（macOS 15 Sequoia） |
| Swift 语言模式 | 5 | 避免 Swift 6 强制严格并发检查，渐进迁移 |

> **说明**：Xcode 16 内置 **Swift 6.0 编译器**，但语言模式可以选择 **Swift 5**（`SWIFT_VERSION = 5`），不会强制开启严格并发检查（Sendable、data race safety）。这样可以在享受 Swift 6 编译器性能优化的同时，渐进式采用 `@Observable` 等新特性，避免大规模并发改造。

### 4.3 Swift 6 迁移策略

| 阶段 | 内容 |
|------|------|
| v1.0 | Swift 5 语言模式，渐进式采用 @Observable |
| v1.1+ | 逐步迁移到 Swift 6 语言模式 |
| @Observable | 可在 Swift 5.9+ 使用，不需要 Swift 6 |

## 七、技术选型决策

### 7.1 为什么不用 SwiftData

| SwiftData | GRDB |
|-----------|------|
| 上手快 | 学习曲线稍陡 |
| 适合简单场景 | 复杂查询更灵活 |
| CloudKit 集成好 | 需要自己实现同步 |
| 大量数据性能一般 | 性能更好 |

**结论**：对于 1000+ stars 场景，GRDB 的性能和可控性更好。

---

### 7.2 SwiftUI vs AppKit 选择

**结论**：**以 SwiftUI 为主，AppKit 作为补充**。

#### SwiftUI vs AppKit 对比

| 维度 | SwiftUI | AppKit |
|------|---------|--------|
| 编程风格 | 声明式，简短 | 命令式，冗长 |
| 开发效率 | 高（现代 API） | 低（样板代码多） |
| 跨平台 | 一套代码覆盖 iOS/macOS/watchOS | 需要分开写 |
| 性能（大数据集） | 一般（万级 items 以下 OK） | 优秀（NSCollectionView 细胞复用） |
| 系统集成 | 部分支持 | 完整支持 |
| Apple 投资方向 | 主推 | 维护中 |

#### Starcat 的选择

**主要用 SwiftUI**，原因：
1. **GitHub Star 管理场景**：一般用户 star 数量在几百到几千，极少超过 1 万，SwiftUI 性能足够
2. **多平台规划**：未来可能扩展到 iOS/iPad，SwiftUI 可以复用大部分代码
3. **开发效率**：声明式 UI 开发更快，维护成本低

**必要时用 AppKit**，场景：
1. **NSCollectionView 细胞复用**：如果未来需要展示数万级数据（如 Trending 列表），考虑用 AppKit
2. **特定 API 仅 AppKit 支持**：如某些系统集成功能
3. **MenuBarExtra**：SwiftUI 的菜单栏 API 在 macOS 14+ 才完善，之前需要 AppKit

#### 混合使用模式

```
SwiftUI 作为主框架：
- 窗口管理：SwiftUI WindowGroup
- 主界面：三栏布局（List + Detail）
- 设置页面：SwiftUI Settings
- 状态管理：@Observable / @State

AppKit 作为补充：
- 菜单栏：NSMenu / NSStatusItem（可选）
- 大数据列表：NSCollectionView（性能瓶颈时）
- 特定系统 API：NSViewRepresentable 封装
```

#### 参考案例

| 应用 | 框架 | 原因 |
|------|------|------|
| Apple Photos | AppKit | 百万级数据，需要极致性能 |
| Apple Books | SwiftUI | 适中规模，SwiftUI 足够 |
| Raycast | AppKit | 菜单栏 + 高性能 |
| 大多数新晋 App | SwiftUI | 快速开发，够用就好 |

**对于 Starcat**：
- star 数量一般 < 10,000
- SwiftUI 的 LazyVGrid/List 足够流畅
- 优先 SwiftUI，必要时才引入 AppKit

### 7.3 为什么需要 BYOK + Pro 订阅

| BYOK 模式 | 自建服务 |
|---------|---------|
| 用户自己承担 API 费用 | 需要维护服务器 |
| 客户端直调 AI API | 更安全、可控 |
| Pro 订阅解锁 | 灵活配置 |

**结论**：BYOK 模式让用户自主选择 AI Provider，Pro 订阅提供更好的使用体验和服务端能力。
