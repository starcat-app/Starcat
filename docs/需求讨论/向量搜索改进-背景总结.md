# 向量搜索改进 — 对话背景总结

> 2026-06-12，为后续方案设计提供原始输入

## 问题起点

当前向量搜索不准，怀疑是构建向量的原始文本信息量不够。对话围绕五个问题展开：现在用什么文本建向量、数据库有没有存 README、AI 摘要传给模型什么上下文、向量存储会不会太大。

## 关键发现

### 1. 当前向量构建只用 10 个元数据字段，不含 README

`Starcat/Features/AI/SemanticSearchService.swift:206-220`，`makeIndexedText(from:)`：

```
Repository: {fullName}
Owner: {owner}
Name: {name}
Description: {description}
Language: {language}
Topics: {topics}
License: {license}
Homepage: {homepage}
Stars: {starsCount}
Forks: {forksCount}
```

全是 key-value 结构，不是自然语言。用户搜"适合做后台任务的框架"，元数据里没有"后台任务"这个词，embedding 模型也提取不到语义信号。

### 2. README 没存后端，客户端用 SWR 懒加载

- `starcat-weekly-api`（后端）的 `github_repos` 表只有 25 个元数据字段，没有 README/markdown 列
- README 存在 Starcat macOS 客户端本地 SQLite 的 `readmes` 表（`rendered_html` 列，GitHub 渲染的 HTML）
- 拉取策略：SWR 模式，用户打开仓库详情页时先读缓存上屏，超 6 小时 softTtl 后台刷新
- 不是全量预拉，只有用户点进过详情页的 repo 才有 README 缓存

### 3. AI 摘要生成的上下文包含 README 纯文本，但只在内存里

`Starcat/Features/AI/RepoAIInsightService.swift:338-353`，`makeSource(for:)`：

```
元数据 8 字段（同向量，去掉 owner/name) + README: {rendered_html → stripHTML → prefix(12_000)}
```

- `stripHTML()` 实时从 HTML 扒出纯文本，不存库，每次调用时临时处理
- 只把 `source_hash`（SHA256）写入 `ai_summaries` 表，用于后续缓存失效判断
- AI 摘要结果写入 `ai_summaries` 表（`summary_json` 列，包含 Markdown 正文 + 标签建议）
- README 截断 12,000 字符，约 3,000-4,000 tokens，在 embedding API 上限（8,192 tokens）内

### 4. 向量存储不用担心，真正的问题是文本质量不是大小

| 方案 | indexedText/条 | embedding BLOB/条 | 10,000 repo 总计 |
|------|---------------|-------------------|-----------------|
| 当前（元数据） | ~400 字节 | ~3-6KB | ~35-65MB |
| 换成 README 文本 | ~12KB | ~3-6KB（不变） | ~150-180MB |

向量维度由 embedding 模型决定（`nomic-embed-text-v1.5` 768 维约 3KB，`text-embedding-3-small` 1536 维约 6KB），和输入文本长度无关。只有 `indexed_text` 列会随文本变长，180MB 对 macOS SQLite 完全可以接受。

## dong4j 提出的改进方向

三级降级的 `indexedText` 构建策略：

1. 优先用 AI 摘要（`ai_summaries.summary_json` → 提取 `summaryMarkdown`）：最优的自然语言文本，但依赖用户手动生成，覆盖率最低
2. 没有摘要时用 README 纯文本（`readmes.rendered_html` → stripHTML → prefix(N)）：有 README 缓存的 repo 可用，但覆盖率取决于用户浏览习惯
3. 都没有时降级到当前元数据拼接：保证所有 repo 都能建向量
4. 最后还要加上用户的私有笔记（如果有的话），因为笔记里可能包含用户自己评价、使用感受等关键信息。

担心点：AI 摘要是用户手动触发的，大部分 repo 没有；README 是 SWR 懒加载的，也只有浏览过的 repo 有。实际运行中，可能大量 repo 仍然落在优先级 3，和现在差别不大。

## 待决策项

- 是否在向量重建前批量预拉 README（代价：GitHub API 配额，5000/h，5000 个仓库约 7 小时）
- README 截断长度（当前 AI 摘要用 12,000，embedding API token 上限通常 8,192 tokens）
- 改了 `makeIndexedText` 逻辑后，`contentHash` 全变，现有 `repo_embeddings` 全量失效，需要一次性重建
