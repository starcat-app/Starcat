## 1. 改造目标与边界

### 1.1 改造目标（4 项强目标）

#### G1：字段补齐到「前端开箱即用」

让客户端通过任意一个后端 API 拿到的 repo 卡片数据，都能直接渲染统一的 `RepoCardViewData`，**无需客户端二次调用 GitHub API 补字段**（详情页 fallback 除外，那是另一条链路）。

为此：
- **trending-api**：从无状态爬虫升级为「爬虫 + GitHub API enricher」二阶段，补 `gh_repo_id / forks / topics / watchers / dates / archived / fork / license / homepage / owner_avatar / default_branch / open_issues` 等 13 字段（详见 `R-01-trending-api-改造方案.md`）
- **weekly-api**：现有 enricher 扩字段（已有 `stars / language / topics / description`，再补上述 14 字段，详见 `R-01-weekly-api-改造方案.md`）

#### G2：3 个 API 接口契约层完全一致

- **URL 版本化**：所有响应数据的列表 / 详情 endpoint 统一改 `/api/v1/*` 前缀（本文档 §3.1）
- **顶层 envelope**：响应统一包成 `{ "schema_version": 1, "data": ... }` 形式，前端按 `schema_version` 判断升级（本文档 §3.2）
- **错误响应统一形态**：`{ "error": { "code": "...", "message": "...", "details": { ... } } }`（本文档 §3.3）
- **扩展段硬边界**：核心 `StarcatRepoCardDTO` 字段仅放 GitHub Repo metadata 原生语义，场景特定字段放扩展段（本文档 §3.8）

#### G3：3 个 API 接口安全鉴权层完全一致

- **Bearer Token 鉴权**：所有 `/api/v1/*` 数据接口 + `/internal/sync/*` 管理接口必须携带 `Authorization: Bearer <api-key>` 头（本文档 §3.4）
- **per-API 白名单**：每个 API 服务读各自 `.env` 文件里的 `API_KEYS=key1,key2,...` 逗号分隔白名单（本文档 §3.6）
- **客户端两套场景**：内置服务编译期注入 / 自建服务用户手动填写（本文档 §3.5）

#### G4：GitHub PAT 高可用 + 故障冗余

- **多 token 池**：每个 enricher 服务（trending / weekly）读 `.env` 里的 `GITHUB_TOKENS=ghp_xxx,ghp_yyy,...` 逗号分隔池
- **Quota-aware 选择**：优先选 `X-RateLimit-Remaining` 最高且未 dead 的 token
- **故障切换**：401 标 dead + 跳下一个；429 sleep + retry（本文档 §3.7）

## 3. 统一接口契约（3 个 API 共识）

### 3.1 URL 版本化规则

所有「返回 JSON 数据给客户端解码」的 endpoint **必须**放在 `/api/v1/*` 前缀下；HTML 渲染、健康检查、内部管理接口**不受**版本化约束（用途不同）。

| 用途 | URL 前缀 | 版本化？ | 鉴权？ | 示例 |
|---|---|---|---|---|
| 数据 endpoint（JSON 给客户端） | `/api/v1/*` | ✅ 必须 | ✅ 必须 | `/api/v1/repos`、`/api/v1/weekly`、`/api/v1/issues`、`/api/v1/zread`、`/api/v1/share` |
| 健康检查 | `/healthz` | ❌ 不版本化 | ❌ **不**鉴权 | `/healthz`（给 fly.io health check 用） |
| HTML 渲染（人类访问） | 自由 | ❌ 不版本化 | ❌ **不**鉴权 | `/s/{id}`（sharing 浏览器分享场景） |
| 内部管理（admin 手动触发） | `/internal/*` | ❌ 不版本化 | ✅ 必须 | `/internal/sync/repos`、`/internal/sync/weekly`、`/internal/sync/zread` |

> ⚠️ **旧路径完全删除**：本次没有兼容旧 endpoint 的需求（dong4j 在 13:10 明确）。旧 `/lang` `/repo` `/user` `/api/weekly/*` `/api/share` 等路径**全部不保留**。

#### 升级到 v2 的触发条件

只有发生**不可向后兼容**变更时才升 `/api/v2/*`：
- 字段类型变化（如 `stars: int` → `stars: string`）
- 字段语义变化（如 `change` 从「stars 增量」改成「ranking 变化」）
- 字段删除
- 响应顶层结构变化（如 envelope 改 schema）

可向后兼容的变更**留在 `/api/v1/*`** + 升 `schema_version` 数字：
- 加字段（核心字段或扩展段）
- 加可选 query 参数
- 错误码加新值（在 enum 末尾）

### 3.2 顶层响应 envelope

所有 `/api/v1/*` 数据接口的 200 响应必须是同一个 envelope 形态：

```jsonc
{
  "schema_version": 1,           // 当前 schema 版本号，整数；同版本内只能加字段不能破坏
  "data": <实际业务数据>,         // 业务数据，可以是数组 / 对象，由具体 endpoint 定义
  "meta": {                      // 可选，分页 / 性能 / 限流元数据
    "page": 1,
    "page_size": 50,
    "total": 1234,
    "next_page": null,
    "generated_at": "2026-06-09T12:30:00Z",
    "cache_status": "fresh"      // fresh / stale / cold
  }
}
```

#### 关键规则

1. **必填字段**：`schema_version`（整数）+ `data`（任意 JSON 值）。`meta` 可选，但分页接口建议都带。
2. **schema_version 不放 `data` 内部**：放顶层一处，避免数组里每条都写一遍浪费带宽 + 改版本时只改一处。
3. **同版本内只允许加字段**：客户端老版本忽略未知字段（Go 端 `json.Decode` + Swift 端 `Decodable` 都天然忽略未知字段，无需特别处理）。
4. **跨 API 一致**：3 个 API 的 envelope 形态必须 byte-level 一致，避免客户端 3 套解码代码。

#### 3 个 API 各自的 `data` 形态

| API | endpoint | data 类型 |
|---|---|---|
| trending | `GET /api/v1/repos` | `[StarcatRepoCardDTO]`（数组） |
| trending | `GET /api/v1/languages` | `[Language]`（数组） |
| trending | `GET /api/v1/users` | `[Developer]`（数组） |
| weekly | `GET /api/v1/weekly` | `[StarcatRepoCardDTO]`（数组，带 weekly 扩展段） |
| weekly | `GET /api/v1/weekly/{owner}/{repo}` | `StarcatRepoCardDTO`（单对象） |
| weekly | `GET /api/v1/issues` | `[WeeklyIssue]`（数组） |
| weekly | `GET /api/v1/issues/{n}` | `{ issue: WeeklyIssue, projects: [StarcatRepoCardDTO] }` |
| sharing | `POST /api/v1/share` | `ShareResponseDTO`（单对象） |
| 任意 admin | `POST /internal/sync/*` | `{ task_id: "...", started_at: "...", status: "running" }`（fire-and-forget） |

### 3.3 错误响应统一形态

所有非 2xx 响应必须是同一个错误形态：

```jsonc
{
  "schema_version": 1,
  "error": {
    "code": "UNAUTHORIZED",                        // 大写 SCREAMING_SNAKE_CASE 错误码（前端 switch 用）
    "message": "missing or invalid API key",        // 人类可读，可中英混合
    "details": {                                    // 可选，结构化补充信息
      "header": "Authorization"
    }
  }
}
```

#### 错误码约定（跨 3 个 API 共用）

| code | HTTP 状态 | 含义 |
|---|---|---|
| `BAD_REQUEST` | 400 | 请求参数非法 |
| `UNAUTHORIZED` | 401 | 缺失 / 无效 API Key（本次新增，**所有 `/api/v1/*` 和 `/internal/*` 鉴权失败统一返回此码**） |
| `NOT_FOUND` | 404 | 资源不存在（如 `issue/{n}` 不存在的期号） |
| `METHOD_NOT_ALLOWED` | 405 | 方法不允许 |
| `RATE_LIMITED` | 429 | 后端被 GitHub 限流，或客户端打太快被本服务限流（未来） |
| `SCHEMA_VERSION_TOO_NEW` | 426 (Upgrade Required) | 服务端 schema 已比客户端先升级（极少用，预留） |
| `INTERNAL_ERROR` | 500 | 后端代码 / DB 异常 |
| `UPSTREAM_UNAVAILABLE` | 502 | GitHub API / git clone 等上游不可用 |

`details` 内字段为约定俗成，按错误码自由扩展（如 `retry_after_seconds` / `field` / `expected_type` 等），客户端按 code 决定是否读 `details`。

#### 鉴权失败响应必带头

`UNAUTHORIZED` (401) 响应必须带 RFC 7235 标准头：

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer
Content-Type: application/json; charset=utf-8
```

### 3.4 API Key 鉴权（本次新增）

#### 3.4.1 鉴权方式

所有 `/api/v1/*` 数据接口 + `/internal/sync/*` 管理接口必须携带 Bearer Token：

```
Authorization: Bearer sk-starcat-7Y2K9F3P0XJTV5HW1MNCQR8BLZD4G6AE
```

> **为什么选 Bearer**：与 OpenAI / Anthropic 等业界 AI 接口风格一致，dong4j 在 13:10 明确「类似 AI 请求鉴权方式，放在 header 中」。

#### 3.4.2 鉴权范围

| endpoint | 鉴权要求 | 备注 |
|---|---|---|
| `GET /healthz` | ❌ 不鉴权 | 给 fly.io health check 用，加了反而打挂自动重启 |
| `GET /s/{id}` | ❌ 不鉴权 | sharing HTML 渲染，浏览器直访场景 |
| `/api/v1/*` 全部 | ✅ **必须** | 业务数据接口，无 key 一律 401 |
| `/internal/sync/*` 全部 | ✅ **必须**（同业务 key 白名单） | dong4j Q2 选 A，统一鉴权层 |

#### 3.4.3 API Key 格式约定

```
sk-starcat-<32 字符 base32 大写>
^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
固定前缀     随机部分（[A-Z2-7] 共 32 字符）
总长度：43 字符
```

**示例**：`sk-starcat-7Y2K9F3P0XJTV5HW1MNCQR8BLZD4G6AE`

**生成方式**：使用 `supports/scripts/gen-api-key.sh`（一键生成，详见该脚本头注释）。

#### 3.4.4 鉴权中间件实现要点

每个 API 在 `internal/middleware/auth.go` 实现统一鉴权中间件（**byte-level 一致 复制粘贴策略**，详见 §4.1）。中间件逻辑：

```
1. 从 request header 读 "Authorization"
   ↓
2. 不存在 → 401 UNAUTHORIZED { message: "missing Authorization header" }
   ↓
3. 不以 "Bearer " 开头 → 401 UNAUTHORIZED { message: "expected 'Bearer <token>' format" }
   ↓
4. 截出 token 字符串 → trim 空白
   ↓
5. 在 authMiddleware 持有的 allowedKeys map[string]bool 中查找
   ↓
6. 不存在 → 401 UNAUTHORIZED { message: "invalid API key" }
   - 日志只记 key 的前 4 + 末 4 字符 + 中间星号（详见 §3.4.5）
   ↓
7. 存在 → 放行到下一个 handler
```

#### 3.4.5 日志脱敏

所有涉及 API Key 的日志（包括成功 / 失败 / 调试）必须脱敏：

```go
func maskKey(key string) string {
    if len(key) < 16 { return "****" }
    return key[:7] + "****" + key[len(key)-4:]  // sk-star****G6AE
}
```

**绝对禁止**：`log.Printf("auth ok, key=%s", key)`。

### 3.6 .env 配置管理（本次新增）

#### 3.6.1 配置加载顺序

每个 API 启动时加载顺序：

```
1. 进程启动
   ↓
2. godotenv.Load() 读 ./.env 文件（不存在不报错）
   ↓
3. os.Getenv("KEY") 优先级：
```

### 3.7 GitHub Token Pool（本次新增）

> ⚠️ 仅 trending-api / weekly-api 需要（调 `/repos/{o}/{r}` 等 REST API）。sharing-api 不需要。

#### 3.7.1 配置

`.env` 文件：

```bash
GITHUB_TOKENS=ghp_xxxxxxxxxxxxxxxxx,ghp_yyyyyyyyyyyyyyyyy,ghp_zzzzzzzzzzzzzzzzz
```

- 最少 1 个（dong4j Q9 选 A，启动不强制 ≥2）
- 建议 2-3 个做冗余（防 PAT 失效）
- 用逗号分隔，token 字符串自身不含逗号（GitHub PAT 是 `ghp_` 或 `github_pat_` 前缀 + 字母数字）

#### 3.7.2 Token Pool 数据结构

```go
type TokenState struct {
    Value      string    // PAT 字符串
    Remaining  int       // 从 X-RateLimit-Remaining 实时更新；初始 -1 表示「未知」
    ResetAt    time.Time // 从 X-RateLimit-Reset 实时更新
    Dead       bool      // 401 标记 dead 后跳过
    LastUsedAt time.Time // 监控用
    ConsecutiveFailures int  // 连续失败计数（用于额外 dead 判定）
}

type TokenPool struct {
    mu     sync.Mutex
    tokens []*TokenState
}
```

#### 3.7.3 选 token 算法（Quota-aware，dong4j Q3 选 B）

```
pickBest():
    candidates = filter(tokens, not dead and (remaining > 0 or remaining == -1))

    if candidates empty:
        log.warn "all tokens dead or exhausted"
        return nil  // 上层 sleep_until_earliest_reset

    // 优先选 remaining 未知的（让它们去试一次拿到 quota 信息）
    unknowns = filter(candidates, remaining == -1)
    if unknowns not empty:
        return pick random from unknowns

    // 否则选 remaining 最高的
    sort candidates by remaining desc
    return candidates[0]
```

#### 3.7.4 调用后更新 token 状态

每次 HTTP 调用响应后必须读响应头更新 token state：

```go
func (p *TokenPool) UpdateFromResponse(token *TokenState, resp *http.Response) {
    if r := resp.Header.Get("X-RateLimit-Remaining"); r != "" {
        token.Remaining, _ = strconv.Atoi(r)
    }
    if r := resp.Header.Get("X-RateLimit-Reset"); r != "" {
        ts, _ := strconv.ParseInt(r, 10, 64)
        token.ResetAt = time.Unix(ts, 0)
    }
    token.LastUsedAt = time.Now()
    if resp.StatusCode == 401 {
        token.Dead = true
        log.Errorf("[token-pool] %s marked DEAD (401)", maskToken(token.Value))
    }
    if resp.StatusCode >= 500 {
        token.ConsecutiveFailures++
        if token.ConsecutiveFailures >= 5 {
            token.Dead = true
            log.Errorf("[token-pool] %s marked DEAD (5 consecutive 5xx)", maskToken(token.Value))
        }
    } else if resp.StatusCode < 500 {
        token.ConsecutiveFailures = 0
    }
}
```

#### 3.7.5 故障切换流程

```
enrichOne(repo):
    for attempt in 1..3:
        token = pool.PickBest()
        if token == nil:
            sleepUntilEarliestReset()  // 找池中 resetAt 最早的，sleep 到那个时间
            continue
        resp = httpGet(/repos/{o}/{r}, auth=token.Value)
        pool.UpdateFromResponse(token, resp)
        switch resp.StatusCode {
            case 200:
                parse + persist + return
            case 404:
                mark repo is_available=0 + return
            case 401:
                // pool 已标 token dead，重试自动用下一个
                continue
            case 429, 403 (with X-RateLimit-Remaining=0):
                // pool 已更新 resetAt，下次 pickBest 自动避开
                if retryAfter := resp.Header.Get("Retry-After"); retryAfter != "" {
                    sleep(parseRetryAfter)
                }
                continue
            case 5xx:
                // 已计入 ConsecutiveFailures
                continue
        }
    return error "enrichOne failed after 3 attempts"
```

### 3.8 schema_version 演进 SOP

#### 3.8.1 何时升 schema_version

| 变更类型 | 是否升 schema_version |
|---|---|
| 加新字段（核心 / 扩展段） | ❌ 不升 |
| 加可选 query 参数 | ❌ 不升 |
| 错误码 enum 加新值 | ❌ 不升 |
| 字段语义微调（但不破坏老解码） | ⚠️ 强烈建议升小版本号（如 1 → 2，**但保持在 `/api/v1/*` 路径下**） |
| 删字段 / 改字段类型 / 改字段语义破坏老解码 | ✅ 必须升大版本号 + 移路径到 `/api/v2/*` |

> 当前 v1 起步，预期版本演进路径：`1 → 2 → 3 → ...`（数字递增 + 同路径），破坏性变更则进 `/api/v2/*` 重置版本号。

#### 3.8.2 客户端老版本接收到「未来 schema_version」的行为

| 场景 | 客户端表现 |
|---|---|
| `schema_version <= supportedSchemaVersion` | 正常解码 |
| `schema_version > supportedSchemaVersion` | 尝试解码（Swift Decodable 忽略未知字段）+ 控制台 warning「请升级 Starcat」+ **不阻塞 UI**（除非解码真失败） |
| 解码彻底失败（如核心字段缺失） | 走 RepoResolver chain 的 `MinimalRepoSource` 兜底，避免白屏 |

### 3.9 扩展段硬边界规则（再陈述，对应前端 §6.1.4）

`StarcatRepoCardDTO` 的字段必须严格分两层：

#### 3.9.1 核心字段（顶层）

只允许放与 GitHub Repo metadata **原生语义**对齐的字段（GitHub `/repos/{o}/{r}` 响应里有的字段 + 派生字段如 `license_spdx`）。

#### 3.9.2 扩展段（嵌套子对象）

按场景命名：`trending` / `weekly` / `sharing`（如果以后用）。每个扩展段下面**只能放该场景的发现型语义字段**。

#### 3.9.3 红线（绝对不允许）

1. ❌ 把非 Repo metadata 字段（如 `editorComment` / `reason` / `relatedArticles`）放到顶层核心字段
2. ❌ 试图把扩展段字段提升到顶层（如把 `weekly.editorComment` 改成顶层 `editorComment`）
3. ❌ 在扩展段塞超出「该场景发现型语义」的字段（如 `weekly.unrelatedDiscussion`）

#### 3.9.4 替代方案（当 Weekly 真演化成 Article 模型）

不要扩 `StarcatRepoCardDTO`，而是另起 endpoint：

```
GET /api/v1/weekly                    → [StarcatRepoCardDTO]（卡片 = repo metadata 语义）
GET /api/v1/weekly/articles          → [StarcatWeeklyArticleDTO]（含编辑点评 / 相关文章 等，独立 schema）
```

## 4. 跨 API 共享方案

### 4.1 共享代码同步约定（不共享 Go 模块，复制粘贴策略）

依据 `supports/CLAUDE.md` 的「不要跨项目 import」原则，envelope / ErrorResponse / RateLimitHandler / authMiddleware / TokenPool 等共享代码在三个项目各自持有一份完全相同的代码。

#### 4.1.1 跨项目共享代码登记表（强制）

下表中的文件**必须**在 N 个项目（如表所示）byte-level 一致：

| 共享文件 | trending | weekly | sharing | 备注 |
|---|---|---|---|---|
| `internal/model/envelope.go` | ✅ | ✅ | ✅ | 3 份一致 |
| `internal/middleware/auth.go` | ✅ | ✅ | ✅ | 3 份一致（Bearer Token 鉴权） |
| `internal/middleware/cors.go` | ⚠️ 按需 | ⚠️ 按需 | ⚠️ 按需 | 若都需要 CORS 则 3 份一致 |
| `internal/enricher/ratelimit.go` | ✅ | ✅ | — | sharing 不调外部 API，无 ratelimit 需求 |
| `internal/tokenpool/tokenpool.go` | ✅ | ✅ | — | sharing 无 GitHub 调用，不需要 |

#### 4.1.2 同步约定

- 三份代码 **byte-level 完全一致**（除 package 名 / module path 引用）
- 任何一份更新时，**必须**同步另外 N 份（PR 描述里勾「跨 N 个 API 同步 xxx.go」清单）
- 由 `supports/AGENTS.md` 加一条「跨项目共享代码同步约定」表登记此类文件

> 未来若需要：dong4j 可以决定升级到「Go workspace mode + 共享 supports/pkg/*」，但本次 R-01 沿用 CLAUDE.md 现有约束。

### 4.2 GitHub Token 配置策略

3 个 API 通过 `.env` 文件 + fly secrets 配置 GitHub Token Pool。**实际使用**：

- **trending**：enricher 调 `/repos/{o}/{r}`，配 `GITHUB_TOKENS=ghp_a,ghp_b,...`
- **weekly**：enricher 调 `/repos/{o}/{r}`，配 `GITHUB_TOKENS=ghp_a,ghp_b,...`
- **sharing**：不用（不调 GitHub API），**不配** `GITHUB_TOKENS`

理论上 trending + weekly **可以共享同一组 PAT**（节省 token 管理成本），实际上 fly.io secrets 是 per-app 配置，**改造时建议两个 API 各持一份相同的 PAT 列表**，未来如有需要再拆。

**配额竞争预估**：trending daily 300 repo × 1 enrich/day + weekly 增量 < 30 repo/day = 总计 < 400/day，远低于 5000/h 单 token 配额。

**Token Pool 的实际价值**：不是「扩容配额」（5000/h 已远超需求），而是「单 PAT 失效冗余备份」（避免 token 被吊销 / 误删 / 误配后服务完全断 enrich）。

### 4.3 schema_version 升级 playbook

#### 场景 1：加新字段（同版本，不升）

1. Go struct 加字段（带 `json:"foo,omitempty"` 标签让旧客户端不收到 null 困扰）
2. 写入路径补字段
3. 不动 `schema_version` 数字
4. CHANGELOG 写「v1 schema：加字段 `foo`，向后兼容」

#### 场景 2：删字段 / 改语义（升大版本）

1. 起新 `/api/v2/*` 路径，新 handlers 用新 DTO
2. 旧 `/api/v1/*` 保留至少 6 个月（**v2 上线后**才需要这个机制；R-01 本次没有旧 v1 要兼容）
3. 客户端版本 ≥ X 后才走 `/api/v2/*`
4. 6 个月后 `/api/v1/*` 下线

#### 场景 3：字段类型微调（升小版本，同路径）

1. 同一 `/api/v1/*` 路径
2. `schema_version` 1 → 2
3. 老客户端解码到 schema_version=2 时弹「请升级」+ 继续尝试解码（容错向上）

## 5. 测试策略

### 5.1 单元测试范围（总览）

具体 test case 列表见各子文档「测试范围」章节。这里只列跨 API 共识层：

#### 5.1.1 envelope 形态测试（每个 API 必有 1 个）

- 200 响应包装 envelope，`schema_version` / `data` / `meta` 字段齐全
- 404 / 400 / 500 响应包装 envelope 错误形态，`error.code` / `error.message` 字段齐全

#### 5.1.2 鉴权中间件测试（每个 API 必有 4 个）

- 缺失 `Authorization` 头 → 401 + `WWW-Authenticate: Bearer` + `error.code = UNAUTHORIZED`
- 非 `Bearer xxx` 格式 → 401
- key 不在白名单 → 401 + 日志脱敏验证（前 7 + 末 4 + 中间星号）
- key 在白名单 → 通过，handler 正常执行

#### 5.1.3 RateLimitHandler 测试（trending / weekly 必有）

- 429 响应 → 按 `Retry-After` sleep + 重试此 repo
- 剩余 quota < 100 + reset 还远 → 主动暂停 5s/req

#### 5.1.4 Token Pool 测试（trending / weekly 必有 5 个）

- Pool 从 `GITHUB_TOKENS` 解析 3 token，启动期 remaining=-1
- 调用后 UpdateFromResponse 正确更新 remaining / resetAt
- 401 响应 → token.Dead=true，PickBest 跳过该 token
- 所有 token dead → PickBest 返回 nil
- Quota-aware：3 token remaining=[10, 50, 30] → PickBest 选 remaining=50 的

### 6.1 设计取舍

| 决策 | 选择 | 拒绝 | 理由 |
|---|---|---|---|
| 文档形态 | v1.1 拆为 1 总体 + 3 子文档 | v1.0 单一大文档 | dong4j 在 12:50 要求拆分；保留总体设计承载跨 API 共识层 |

| Token Pool 数量下限 | 至少 1 个（v1.2 新增） | 强制 ≥ 2 | dong4j Q9 选 A，本地开发友好 |
| .env 加载库 | godotenv（v1.2 新增） | viper / 纯环境变量 | dong4j Q5 选 A，最小依赖 + 业界主流 |
| .env 位置 | 每个 API 项目根目录（v1.2 新增） | supports 根目录共享一份 | dong4j Q6 选 A，项目独立部署 |

| migration 工具 | 手写 `migrateVN()` + PRAGMA user_version | 引入 goose / golang-migrate | 最小依赖，weekly 已有手写 migrate 路径 |

### 6.2 已知约束

1. **SQLite ALTER TABLE 只能 ADD 不能 DROP**（除非 3.35+ 的 DROP COLUMN）—— R-01 内无 drop 需求，避开此约束
2. **GitHub trending HTML 解析对页面 DOM 变化敏感**：goquery 解析当前依赖 `[data-hpc] article` 选择器，GitHub 改版可能失效。R-01 内**不增加** DOM 监控告警机制（列入未来运维改进）
3. **fly.io 持久卷大小**：当前 trending / weekly / sharing 各 1GB 卷，R-01 预计 trending SQLite < 50MB / 年，weekly < 100MB / 年，sharing < 10MB / 年，远低于上限
4. **trending 冷启动数据缺口**：首次部署后 SQLite 空，scheduler 启动 + enricher 全量约 70s 内填充。期间 `/api/v1/repos` 返回空数组 + meta.cache_status = "cold"，客户端走「空态 + retry」（与前端 §6.2.1 一致）
5. **enricher token 配额竞争**：trending / weekly 都用同一组 GitHub PAT，理论可能互相挤占。预计 trending daily 300 repo × 1 enrich/day + weekly 增量 < 30 repo/day << 5000/h，无问题
6. **API Key 客户端反编译风险**：内置服务的 key 编译期注入 Info.plist，二进制可被反编译拿到。R-01 接受此风险（key 本身不绑用户数据，泄露后吊销 + 重发 + Bumper App 版本即可）；自建用户走 B 路径自己生成 key 无此问题
7. **sharing-api 改 SQLite 需考虑并发**：write 路径串行化（SetMaxOpenConns(1)），但短链生成 API 写频率低，无瓶颈
8. **`/internal/sync/*` 异步任务无进度反馈**：客户端发起后立刻返 200 + task_id，进度只能看 fly logs（R-01 不做 task status 查询）

### 6.3 未决问题（不在本次范围，记录待办）

1. **trending HTML 解析失败告警**：GitHub Trending 改版时 goquery 失效如何通知 dong4j？建议加 Prometheus / Sentry / 简单的「连续 3 次爬到空数据就发邮件」机制（待 P2）
2. **weekly 单 repo endpoint 是否做**：R-01 默认做（前端 `BackendAggregateRepoSource` 需要），实现成本仅 ~30 行 handler
3. **是否给 `meta.cache_status` 加更细粒度**（cold / warm / fresh / stale）：当前只有 fresh / stale / cold 三档，未来如果加客户端预热提示再细化
4. **trending Search API 调用场景**：本次 R-01 不调，但未来如果加「按 topic 反查 trending」功能，需要启用 Search 独立桶
5. **三个 API 共享配额监控**：每个 API 单独看 fly logs 时无法判断「trending 是否吃了 weekly 的配额」。未来如果都需要观察，建议加 OpenTelemetry trace
6. **GitHub Token Pool 自动轮转**：当前一组 PAT 用一辈子，token 泄露 / 过期后需要手动 `fly secrets set` 重设。未来如有需要可接入 GitHub App auto-refresh
7. **sharing-api 真正演化成 article 模型**（前端 §6.1.4 假设）：如果未来 weekly 加「编辑点评」等 article 字段，应另起 `/api/v1/weekly/articles` endpoint + `StarcatWeeklyArticleDTO`，**不污染** `StarcatRepoCardDTO`
8. **admin endpoint 进度查询 API**（`GET /internal/sync/status/{task_id}`）：P2 补
9. **API Key 速率限制 / 滥用检测**：当前只验证「合法 key」，未限「单 key 每分钟 ≤ N 请求」。如果未来某 key 滥用，需要加 per-key rate limit
10. **客户端「设置-服务」页面**：API Key 输入 UI 实现（自建模式）属于客户端需求，后端文档仅记录约束（§3.5）

| **weekly 扩展段** | `weekly` | `Weekly *WeeklyExtension` | `weekly: WeeklyExtension?` | nullable |
| `weekly.first_issue` | — | `FirstIssue int` | `firstIssue: Int` | ✅ in weekly |
| `weekly.issue_url` | — | `IssueURL string` | `issueUrl: URL` | ✅ in weekly |

#### 关键约束

- **必填字段缺失** → 客户端走 `MinimalRepoSource` 兜底
- **nullable 字段缺失或 null** → 客户端 UI 显示 "—" 或省略对应 chip
- **扩展段缺失** → 客户端按场景判断（Trending 详情没 trending 段 = 后端字段未填，UI 不渲染对应区块）
- **JSON key** 命名严格 snake_case（与 GitHub 风格一致），不要写成 camelCase
