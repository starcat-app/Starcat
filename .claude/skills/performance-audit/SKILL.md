# Starcat 发版前性能专项审查

## 触发时机与目标

本项目（macOS SwiftUI + GRDB/SQLite + WKWebView）每次发版前执行一次全量性能专项审查。
目标：页面流畅不卡顿（合理的动画、后台异步工作不算卡顿）。
本任务为**只读审查**：不改任何业务代码，交付物是一份性能分析报告。

## 硬性约束

1. 全程只读源码；唯一允许写入的文件是最终报告，且必须先在回复中全文交付、经 dong4j 确认后才落盘。
2. 禁止执行打包 / 发布 / 上传脚本；允许只读检查命令与 `make benchmark-*` 基准脚本。
3. 禁止改 `docs/功能实现总览.md`。
4. 开工先读 `docs/4-工程进度/` 下最近一次性能审查报告：已知问题只复核「是否复发 / 是否已修复」，
   不重复立案；重点转向新增代码的回归点。
5. 报告头部记录基线：git commit hash、分支、worktree、工作区是否干净。

## 审查口径（五类问题 × 本项目高发模式）

全仓审查（不是只看最近提交），逐域排查：

1. **该异步却同步**：`@MainActor` 上的磁盘 IO、目录枚举、大 JSON 编解码、
   SQLite 建池/迁移、WKWebView 桥传大对象。
2. **可复用却重复计算/请求**：「写后全量 reload」模式（`Disk*Cache` 家族逐个核对）、
   每请求重读 Keychain / 重派生密钥、全表读取只用一小段、
   getter 里 filter+sort 每次求值重跑、`.task(id:)` 的 id 表达式里构造重对象
   （SwiftUI 中 id 先于任务体求值；guard 放任务体内则功能关闭时照样全额支付）。
3. **外部 API 超时**：URLSession 配置是否兜底、每类第三方调用是否显式超时、
   重试是否引发重复副作用。
4. **异常处理**：错误被静默吞掉、本地 IO 失败被当作可重试的远端来源、
   失败路径反而触发更大成本。
5. **UI 重复计算/布局**：body / `.task(id:)` / onChange 里重复构造候选集、
   列表合并 O(M²)（增长数组上 `firstIndex`）、SQL 无 LIMIT 上层再全量重排截断、
   每帧/每重绘重复枚举。

## 工作方法

1. **分域审查**（6 域）：浏览与渲染 / 数据与同步 / 启动与周边 / 知识与代理 /
   网络与集成 / 内容与可视化。支持多 agent 编排时用 Workflow 工作流并行执行，
   否则按域顺序完成。
2. **独立对抗复核（必须环节，不可省略）**：每个域的发现由独立 agent 逐项复核，
   判定 KEEP / DOWNGRADE / DROP；复核必须核对原始行号与机制描述，
   修正错误锚点、撤回夸大表述（「无限增长」「每帧」「必现」类断言一律要求给出可证依据）。
3. 未被复核覆盖的域，主审必须**亲自抽查全部高优项**。
4. 有基准脚本的链路（`make benchmark-*`）跑实测；没有的标注「静态推断，待 Instruments 实测」，
   禁止把静态推断写成实测结论。

## 报告要求（中文）

落盘路径：`docs/4-工程进度/YYYY-MM-DD-性能专项审查报告.md`。
每个发现必须包含：源码锚点（file:line）、用户操作触发场景、影响、优化方案、可执行验收方法。

按严重度分级：
- **P0**：数据丢失 / 正确性缺陷（优先于一切性能项）
- **P1**：高频主线程卡顿源（直接命中流畅度目标）
- **P2**：中低优先级 / 条件触发
- **观察**：低优先级，不列修复排期

报告还必须包含：
- 「复核修正与撤回记录」表（原指控 → 处理 → 依据），如实记录误报
- 「已核实有保护、无需修改」清单，防止后续重复排查
- 「覆盖缺口与待实测项」如实声明
- 附录：本次实测基准数据与机器环境

跨域重复发现合并为一条，注明来源域。

## 收尾

报告先在回复中全文交付，等 dong4j 确认后再落盘到 `docs/4-工程进度/`。
修复实施不在本任务范围，须 dong4j 单独授权后按 P0 → P1 顺序另行立项。
