# Starcat 版本迭代

唯一维护源在项目 `skills/`，不创建用户级副本。根 `AGENTS.md` 也指向本入口，无须为了使用而修改工具全局配置。

先读取当前的[版本迭代规范](../../docs/5-规范/版本迭代规范.md)，其授权、范围、完成状态与 Changelog 规则为执行依据。本文件提供执行入口，不复刻 Git 或发布 SOP。

## 选择阶段

- **启动**：尚未初始化目标版本，执行下节；已给版本号不重复问。
- **继续/维护**：读取原清单，按授权增补、登记进展、延期或取消；不重新初始化分支或重置常规项。
- **查看进度**：只读汇总已完成、待验收、剩余及阻断项。
- **收口**：核对实际交付与本轮依赖检查，准备日志素材，转交日志和发版准备入口，不自行发布。

## 启动迭代

### 1. 只读预检

在 Starcat 根目录读取 `AGENTS.md`、`LESSONS.md`、`BRANCH.md`、Git 分支与 Worktree 规范、Changelog 规范、开发前问题清单及相关历史版本计划。只读检查功能总览，不回写。

使用[检查脚本](scripts/check_workspace.py)收集事实，将示例版本替换为用户明确指定的基础版本：

```bash
rtk proxy python3 skills/starcat-version-iteration/scripts/check_workspace.py --root . --version 1.9.8
```

实时核对远端 dev 时加 `--check-remote`，仅执行 `ls-remote`，不更新 refs；失败显示未核实。未加时远端比较来自本地缓存，不得声称已核实最新状态。退出成功仅表示采集完成，不表示允许切分支或已通过发版门禁。

JSON 覆盖登记与实际仓库、各 worktree、未提交修改、未结束 Git 操作、dev/main/目标分支关系、本地目标 tag、Changelog 标题、规范目录下的计划及必要配置/工具存在性。脚本不判定额外仓库的产品归属、不读取远端 Release、不查询全部最新依赖；Agent 按证据补充。本地 tag 不等于对外发布，配套仓库独立版本也不能按同号误判；必要时另核对目标远端分支与真实 App 发布事实。已有其他目录的同版本规划按文档检索补充，不只依赖规范路径。

压缩成“仓库 / 分支 / 未提交修改 / worktree / dev 基线 / 问题”表格，另列版本与环境，区分通过、提醒、阻断、未核实。列出全部异常；有 worktree 或目标日志缺失不自动阻断。不自动同步、stash、提交、清理、升级、构建或跑全量测试。

### 2. 收集并展示范围

预检后询问新增、优化、修复、必须项与渠道，已有答案直接整理。默认主仓库与全部活跃自维护 supports 项目参与；展示完整名单及归档、第三方副本和其他排除项的原因，额外仓库不猜归属。

按[模板](assets/迭代计划.md)展示轻量 Checklist，保留本轮依赖/二进制/内嵌资源版本检查。确认日志归属，本次交付版本与汇总版本可不同，沿用现行渠道规则。

同时展示每仓 dev commit、将创建并切换的 `feature/X.Y.Z`、计划路径及登记范围。等待“开干 / 改吧 / GO / 实施”等明确授权，功能列表不等于许可；不先写计划，不逐仓重复申请。

### 3. 执行已确认初始化

重新核对全部参与仓库。阻断未解决时只处理已获授权事项，不自行 stash、提交、删除或绕开。逐仓创建并切换同名分支；已有分支核对后续用，不覆盖；缺少 dev 不改用 main。只有已确认的并行方案才建 worktree，仍执行本机配置复制与登记要求。

分支完成后将模板落盘为 `docs/4-工程进度/版本迭代/X.Y.Z-迭代计划.md`，状态设为“开发中”，填入真实范围、渠道、日志归属、仓库基线及简短预检结论，移除占位说明；新清单常规项未勾选。同版本已有清单继续维护，详细大版本规划只链接。

同步主仓库 `BRANCH.md` 及各仓库自己的登记；逐仓回读，报告分支、用途、基线、目录、状态、验收后合回 dev 的归宿。中断时明确部分完成与未执行项，重跑续接，不强行回滚。完成初始化后等待下一项业务开发指令，不自动执行全部功能，不提交或推送。

## 持续维护

1. 用户指定版本优先；否则核对 `feature/X.Y.Z`、计划头部及有效授权。多个活跃计划无法确定时先澄清，不按最高版本号猜测。
2. 明确要求“加一项 / 更新清单 / 延后”则维护原文件；讨论想法时先展示建议。普通本版交付在既有授权范围内同批维护清单，无须再次申请。
3. ID 稳定，同一新功能的反复修复归并回原条目，只写最终结果。已实现待验收保持 `[ ]` 并注明，满足约定验收条件再 `[x]`，附简短证据或链接。
4. 延后/取消保留 ID、去向或原因；新增跨仓范围先确认，不偷偷切分支。现有 GitHub/Multica 任务仅链接，远端写入遵守原流程和授权。
5. 已确认且仍在进行的当前计划承接日常记录，不逐任务询问 Changelog。没有当前计划继续原询问规则，不擅自补建计划，不改功能总览。

## 收口

- 核对本轮常规依赖检查；执行时查看官方上游和实际集成，不沿用上一轮勾选，不把检查变成自动升级。
- 以已验收且属于实际交付的条目形成素材，结合各参与仓库实际发布范围的完整提交补漏；内部维护、未验收、延期及取消项不当成已交付，发现未登记变更先核实。
- 读取 [starcat-update-changelog](../starcat-update-changelog/SKILL.md)，经日志授权统一整理渠道中英文 Markdown；尚未授权先展示草稿。1.9.x → 2.0.0 汇总规则继续适用。
- 封版转交 [starcat-release-readiness](../starcat-release-readiness/SKILL.md)；实际发布读取现行发布 Skill/SOP，仍需当前消息明确授权，不自动 tag、打包或上传。
- 真正发布成功后才将计划改为“已发布”，记录证据和未交付项去向，不以 Checklist 完成代替发布结果。
